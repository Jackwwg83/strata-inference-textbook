1.1 先回答：我们到底在研究什么？

模型可以理解为一组经过训练的数值参数与计算规则。推理引擎负责在给定硬件上执行这些规则；聊天界面负责组织输入、呈现输出。三者不是同一件东西。把引擎运行得更快，不等于重新训练出了更聪明的模型；支持一种 API，也不等于支持该 API 的全部语义。

Strata 是本书的系统案例。它的仓库以 Qwen3.8-Flash-Next 为主要目标，围绕消费级设备设计 CPU、GPU 与存储的协同路径。模型名称及支持范围以固定版本的仓库声明为准，本书没有另行复核所有模型权重。不要把其他同名 Strata 项目或相邻型号的结构搬进来。[S01][S02]

1.2 一次请求的六次转换

用户写下文本；服务层把消息和工具定义套入聊天模板；分词器把文本变成整数 ID；引擎把 ID 变成向量并逐层计算；采样器从下一 token 的分布中选择 ID；输出解析器把 ID 对应的字节流组织成内容或工具调用。服务端的真实边界是 Engine.generate(ids, max_new, sampling, cancel)，而不是“HTTP 直接调用显卡”。[S15]

把这个路径写成图：

消息 → 模板 / token IDs → prefill → 状态
                                      ↓
呈现 ← 协议事件 ← 解码 / 采样 ← decode 循环
                                      ↕
                             GPU · RAM / CPU · SSD

每条箭头都可能出错：模板不一致，数学相同但输入已不同；状态串用，单个算子再正确也无济于事；网络分片丢失，模型实际上生成了正确答案但用户没看到。

1.3 不同层次的“缓存”不能混为一谈

CPU 硬件缓存保存近期访问的内存行。Strata 的专家缓存把部分权重放入显存；KV 缓存保存序列历史的中间结果；会话缓存保存可恢复的序列状态；PLE 行缓存保存查询得到的模型表行。它们复用的对象、生命周期、失效条件完全不同。“加缓存”只有说明缓存什么、如何确认还是同一个对象、何时失效才有意义。

从大学课程看，这是一条连接线：计算机组成原理解释容量与带宽，操作系统解释页和并发，算法课解释查找与替换，数据库课程解释身份与一致性。后续每章都沿这条线展开，而不是只学习命令行参数。

1.4 例题：24,576 与 10 应该怎样读？

固定源码的几何定义为 48 层、每层 512 个路由专家；序列状态中 k=10。[S04][S13] 因此模型共有 48 × 512 = 24,576 个“层—专家”实体。一个 token 经过所有层，会发生 48 × 10 = 480 次路由专家选择，另有共享专家等计算。并不是从整台模型的 24,576 个专家里只选 10 个就结束。

这种错误看似只是措辞问题，却会让内存流量估计少 48 倍。教授式的阅读不是重复宣传图，而是回到循环的层次、计数器的单位与真正的执行范围。

1.5 四种证据，四种表述

基础原理是一般性的数学或计算机规律；代码事实是固定版本的字段、函数与控制流；上游报告是作者给出的实验和说明；教学推演是我们用简化模型解释取舍。交互实验都属于最后一类，不是硬件跑分。

本书的代码导读是对列出的关键文件窗口的审阅，不是逐行审计整个仓库。某个函数存在，不足以证明所有入口都调用了它；一个注释描述“曾经没有缓存”，也不足以证明今天仍然没有。读者应把“已读到的实现”与“尚待追踪的调用链”分开记录。

1.6 课堂活动：为一个 token 画责任边界

用纸画出服务层、序列状态、权重存储、计算内核、硬件五个框。为每个框写一个输入、一个输出、一个不变量。例如“序列状态只能属于它对应的历史”。然后把“答案正确但慢”“答案随机变化”“后半段文字乱码”分别放到多个可能的框中。目标不是立刻猜中，而是学会设计能区分假设的实验。
