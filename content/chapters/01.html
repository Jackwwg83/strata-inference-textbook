先从一件怪事说起

Strata 的 README 开头写着：在你自己的游戏电脑上，运行一个 1250 亿参数的 AI 模型。它对显卡的要求是 12 GB 显存起步。上游报告[S01]

按常识算一下：1250 亿个参数，就算每个只占 1 字节，也要 125 GB。一张 12 GB 的显卡，怎么装得下？这本书要回答的就是这类问题：一个 AI 模型在你的电脑里，到底是怎样跑起来的。顺着这个问题，我们会把计算机组成、操作系统、算法、网络这些基础知识串起来。

一句话：聊天 AI 每次只生成一个 token。生成这一个 token，要动用显卡、内存、处理器和硬盘。Strata 的本事，是把这四样东西安排得刚好够用。

1.1 你按下回车之后，发生了什么

你在聊天框里输入一句话，按下回车。几秒后，回答一个字一个字地冒出来。这中间，你的话经历了六次转换，见图 1-1。

图里有几个新词，先用大白话解释。

token是模型读写文字的最小单位。它可能是一个汉字、一个词、半个英文单词，或者一个标点。模型不直接认字，只认 token 的编号。分词器就是把文字切成 token、再换成编号的程序，见图 1-2。

采样是第 ⑤ 步。模型不会直接“说出”下一个词，而是给出每个候选 token 的概率，采样就是按这些概率挑一个。第 2 章细讲。

注意图 1-1 里那条虚线。模型每一轮只生成一个 token：要写 300 个 token 的回答，第 ④ 到第 ⑥ 步就要重复 300 次。所以“生成速度”通常用每秒多少个 token 来衡量，写作 token/s。

学过计算机的同学：整个生成过程就是一个循环：while 没结束: 概率 = 模型(已有 token); t = 采样(概率); 已有 token.append(t)。每一轮的输入都包含上一轮的输出，这种“用自己的输出喂自己”的模型叫自回归模型。

1.2 为什么第一个字总是慢一点

你可能注意到：发出问题后，要等一会儿才出现第一个字；之后的字就出得很快。这是因为一次回答分成两个阶段，见图 1-3。

第一阶段叫 prefill（读题）：模型把你的整段提问一次读进去。提问里的 token 都是已知的，可以一起算。第二阶段叫 decode（写答案）：每个新 token 都依赖上一个，只能一个一个来。

Strata 的上游测量显示，同一台机器上，读题每秒能处理约 1,299 个 token，写答案每秒约 93 个。上游报告[S03] 所以提问越长，等第一个字的时间越长。README 也提醒：一段对话的第一条消息要完整读一遍，大约每 30,000 个 token 需要 1 分钟；之后的追问只读新增部分，几秒就能开始回答。[S01]

1.3 模型、引擎、应用：三个常被混为一谈的角色

用一家餐厅来比喻，见图 1-4。Strata 自己的文档也用了厨房的比喻。[S02]

  • 模型是配方。它是训练好的一大堆数字（叫“参数”或“权重”），加上一套固定的计算规则。Qwen3.8-Flash-Next 就是一个模型。
  • 推理引擎是厨房和厨师。它负责在你的硬件上，按配方把计算做出来。Strata 就是一个推理引擎；llama.cpp、vLLM 也是。
  • 应用是前台。它接待你，把你的话整理好交给厨房，再把做好的菜端给你。Strata 自带的网页聊天界面、以及通过 API 接入的编程工具，都在这一层。[S01]

分清这三层，排查问题时就不会找错地方。引擎做得再快，模型也不会变聪明：配方不变，换个厨房，菜的味道应该一样。反过来，如果回答质量变差，原因可能在配方（换了模型或压缩得太狠），可能在厨房（引擎有 bug，算错了），也可能在前台（模板或协议把你的话传错了）。

1.4 一台电脑里的三层“仓库”

厨房快不快，很大程度取决于东西放在哪。电脑也一样。和推理有关的存储有三层，见图 1-5。

显卡（GPU）算得最快，但显存最小，常见的游戏卡只有 12–24 GB。内存（RAM）大得多，但它离显卡远，数据要经过一条叫 PCIe 的总线才能送过去。硬盘（SSD）最大，也最慢。

Strata 的分工是这样的 上游报告[S02]：

  1. 每个 token 都要用的部分，加上最常被用到的几千个“专家”，放在显存里。
  2. 全部专家放在内存里。显卡上没有的那些，由处理器在内存里就地计算，和显卡同时干活。
  3. 硬盘上放一张 28.8 GB 的查找表，每个 token 只读其中几行。

“专家”是什么，第 10 章专门讲。现在只需要知道：它是 Strata 能在小显卡上跑大模型的关键。

存储层次结构

计算机里的存储设备，总是在“快”“大”“便宜”三者之间取舍：越快的越小、越贵，越大的越慢。于是计算机把它们叠成一座金字塔：最常用的数据放在最快的一层，不常用的放在下面，需要时再往上搬。这就是存储层次结构。

衡量“快”有两个指标。带宽是每秒能搬多少字节，像水管的粗细；延迟是从发出请求到拿到第一个字节要等多久，像水从龙头流到杯子的时间。推理引擎每生成一个 token 都要读大量参数，所以最在意带宽。图 1-6 是上游测速机器上各层的理论带宽。

Strata 的全部设计，都可以看成在这座金字塔上摆放数据：热门的专家放显存，全部专家放内存，大查找表放硬盘。后面的章节会反复回到这张图。

延伸阅读：维基百科：存储器层次结构 · Wikipedia: Memory hierarchy · 《深入理解计算机系统》（CS:APP）第 6 章

学过计算机的同学：这就是《计算机组成原理》里的存储层次，只是多了显存这一层。对 CPU 来说，显存是另一块设备上的内存，CPU 不能像访问自己的内存那样直接读写它，数据要经 PCIe 搬运（第 14 章讲 DMA）。

1.5 算一笔账：24,576 和 480

README 说，这个模型由 24,576 个“专家”组成，每写一个词只需要其中 10 个。[S01] 为了好懂，这句话做了简化。我们去源码里核对一下。

源码定义的模型结构是 48 层、每层 512 个专家 代码事实[S04]；每个 token 在每一层选 10 个专家 代码事实[S13]。图 1-7 把这个结构画了出来。

  • 48 × 512 = 24,576，这是专家的总数。
  • 一个 token 要走完 48 层，每层选 10 个，一共 48 × 10 = 480 次专家选择。

“10 个”说的是每一层，不是整个模型。如果理解成整个模型只用 10 个专家，你估算的计算量和数据搬运量会少 48 倍。这是本书反复强调的习惯：一个数字要带着它的单位和范围。

1.6 读这本书的方法：每个数字都有出处

本书的每个结论，都会标明它属于哪一类证据：

  • 代码事实从固定版本的源码里直接读到的。例如“48 层”。
  • 上游报告Strata 作者在文档里写的说明或测得的数据，本书没有自己复测。例如“RTX 5070 上每秒生成 94 个 token”。[S01]
  • 教学推演本书用简化模型推算的结果，用来帮你建立直觉，不是实测。浏览器里的交互实验都属于这一类。
  • 基础原理：数学或计算机的通用规律，不依赖 Strata，不另加标签。

为什么要这么讲究？因为 AI 圈里的数字特别容易被搬错地方。别人显卡上的速度、某个配置下的显存占用、一张宣传图里的简化说法，一旦脱离了条件，就可能误导人。学会问“这个数字是在什么条件下得到的”，比记住任何一个数字都有用。

本书的源码阅读固定在 Strata v0.1.39 上，也就是 2026-10-04 的提交 6f32ec0…，页脚有它的完整编号。书里的事实在 2026-10-05 核对过。Strata 还在快速迭代，新版本里的数字可能已经不同。

动手：打开本章的交互实验「一个 token 的旅程」。它把图 1-1 的路径拆成可以逐步检查的环节，让你看清每一步的输入和输出。试着为其中一条箭头想一个“出错会怎样”的例子：比如模板换了，或者分词器和模型不配套。实验里的数字都是教学推演，不是你电脑上的实测。

记住这三点

  1. 模型是配方，推理引擎是厨房，应用是前台。三者各管一段。
  2. 先读题、后写答案：读题时整段提问一起算，写答案只能一轮一个 token。
  3. 每个数字都要问：它是代码事实、上游报告，还是推算？它的单位和范围是什么？

常见误解：“模型文件多大，就要多大显存。”

不一定。文件大小只说明权重在硬盘上占多少字节。运行时，一部分权重可以留在内存里，由 CPU 计算或按需送到显卡；显存里还要放对话历史和临时数据。Strata 要下载约 70 GB 的模型，却能在 12 GB 显卡上运行。[S01]

深入一层：给想读源码的人

服务层和引擎的真实边界

在 Strata 的服务代码里，应用层交给引擎的不是 HTTP 请求，也不是原始 JSON，而是一串 token 编号：接口是 Engine.generate(ids, max_new, sampling, cancel)，返回一个逐个产出 token 编号的迭代器。代码事实[S15] 模板渲染、分词、协议解析都在这条边界之外。所以排查问题时，第一步是判断错误发生在边界的哪一侧。

同一个文件开头还写着：服务一次只处理一个序列，请求按先来先服务（FIFO）排队。[S15] 这是默认行为。从 v0.1.39 起，在模型的配置文件里写 "parallel": N，引擎就能同时解码最多 N 段对话，N 最大是 8；不写或写 1，仍是一次一个。代码事实server.py README 提醒，在 12 GB 显卡上这样做会让每个回答都变慢。[S01] “支持 OpenAI 兼容 API”仍不等于“支持多人同时使用”，第 25 章会讨论把它扩展到多用户需要什么。

不同层次的“缓存”不能混为一谈

CPU 的硬件缓存保存最近访问过的内存行；Strata 的专家缓存把部分权重放进显存；KV 缓存保存对话历史的中间结果；会话缓存保存可以恢复的整段序列状态；查找表的行缓存保存从硬盘读到的表行。它们缓存的对象、生命周期和失效条件完全不同。“加个缓存”只有说清缓存什么、怎样确认还是同一个对象、何时失效，才有意义。

注释不等于事实

源码注释可能停留在旧的开发阶段。例如 expert_source.hpp 开头写着“Phase 2 没有缓存（命中率 h = 0）”，并说明 Phase 3 会用显存缓存替换这个对象。[S06] 而当前版本的引擎确实有专家缓存。[S02][S05] 遇到这种矛盾，不能只凭一句注释下结论，要追踪当前的调用链、默认配置和测试。本书的源码导读审阅的是列出的关键文件窗口，不是逐行审计整个仓库。

课堂活动：为一个 token 画责任边界

在纸上画五个框：服务层、序列状态、权重存储、计算内核、硬件。为每个框写一个输入、一个输出、一个必须一直成立的条件，例如“序列状态只属于它自己的那段对话”。然后把三种故障分别放进可能的框里：“答案正确但很慢”“答案每次随机变化”“后半段文字乱码”。目标不是立刻猜中，而是学会设计能区分这些假设的实验。
