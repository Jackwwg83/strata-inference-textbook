你可能注意到过

同一个问题问两遍，聊天 AI 给的回答常常不一样。可它明明是一台计算机：同样的输入，怎么会有不同的输出？

答案藏在第 1 章那六步里的第 ⑤ 步。模型从来不直接“说出”下一个词。它只给出一张概率表，然后像掷骰子一样，从表里挑一个。这一章把这张表怎么来、骰子怎么掷、掷之前要先做哪些筛选，一步步讲清楚。

一句话：模型每一步只做一道选择题：根据前文，给词表里每个 token 打分；softmax 把分数变成概率，再用一个随机数按概率挑一个。温度、top-k、top-p 这些参数，都是在“挑”之前修改这张概率表。

2.1 模型读到的不是字，是一串编号

第 1 章说过，分词器把文字切成 token，再换成整数编号。Strata 用的分词器有 248,320 个 token，切法叫字节级 BPE：先把文字拆成最小的字节，再把训练语料里经常挨在一起的片段反复合并成一个 token。常见的词合成一个 token，生僻的字就拆成几块。代码事实strata_tokenizer.py

因为最底层是字节，任何文字都能被表示，不会出现“这个字不认识”。这个分词器的说明里还写了它最看重的检查：把一段文字编码再解码，必须一个字节不差地变回原文。表情符号、多字节的汉字、连续空格，都在检查范围里。

所以，一个 token 不等于一个字。Strata 的 README 说“一个 token 大约是 ¾ 个英文单词”。[S01] 这是英文的经验值，中文、代码、表格的比例都不一样。要算一段话占多少 token，唯一可靠的办法是真的用这个分词器切一遍。

还有一件容易忽略的事：你打的那句话，并不是模型读到的全部。第 ② 步的聊天模板会在前后加上角色标记、系统提示、工具说明，见图 2-1。

Strata 的服务层用模型自带的 Jinja 模板来渲染，而且要求结果和 Hugging Face 的做法完全一致，用 10 个标准样例核对过，其中包括思考模式和工具调用。代码事实[S16] 渲染之前，服务层还会先删掉历史里的空助手回合，也就是没有文字、图片和工具调用的那些（最后一条消息除外），免得模型把“什么都不答”当成榜样；这是 v0.1.40 加的默认行为，设 STRATA_KEEP_EMPTY_TURNS=1 可以恢复原样。[S16] 你在界面上选的“思考档位”，也是作为参数交给模板的：选 high 时，传给模板的实际值是 xhigh；选 none 时，传的是“关闭思考”。[S16] 这些都会改变最后那串编号。

服务层和引擎之间的接口是 Engine.generate(ids, max_new, sampling, cancel)：交进去的是编号列表，拿回来的是一个个 token 编号。[S15] 文字只存在于这条边界之外。

2.2 一次只猜下一个：链式法则

手机输入法会在你打字时猜下一个词。大模型做的是同一件事，只是猜得准得多。它每一步只回答一个问题：已知前面所有的 token，下一个是什么？答案不是一个词，而是一张概率表：词表里每个 token 各有一个概率，加起来等于 1。

一整句话的概率，就是一步步猜下来的概率连乘，见图 2-2。这个规则叫链式法则。

条件概率与链式法则

先看一个直觉：街上随便一个人带伞的概率不高；可如果已知“外面在下雨”，这个概率就高多了。“已知 B 发生时 A 的概率”叫条件概率，写作 P(A | B)，定义是 P(A | B) = P(A 且 B) ÷ P(B)。

把定义移一下项，就得到乘法公式：P(A 且 B) = P(B) × P(A | B)。反复使用它，一长串事件的联合概率就拆成了一串条件概率的乘积：P(x₁, x₂, x₃) = P(x₁) × P(x₂ | x₁) × P(x₃ | x₁, x₂)。这就是链式法则。它不需要任何假设，对所有概率分布都成立。

语言模型正是按这个公式造的：它每一步只学一件事，就是 P(下一个 token | 前面所有 token)。图 2-2 里“我爱你”的概率 0.012，就是三个条件概率相乘。注意条件里是前面所有 token，所以前文改一个字，后面每一步的概率表都可能跟着变。

延伸阅读：OI Wiki：条件概率与独立性 · 维基百科：条件概率 · Wikipedia: Chain rule (probability)

学过计算机的同学：这就是《概率论》里的乘法公式。和马尔可夫链不同，这里的条件是全部历史，不是只看上一个状态。正因为条件里有全部历史，引擎才要把历史存下来反复用（第 17 章的 KV 缓存）。

顺带澄清一个常见的混淆：生成的时候，模型的参数一个都不变，变的只是“已有的 token”这份历史。参数只在训练时改。第 10 章讲的专家缓存会随着对话调整，但它调整的是参数放在哪，不是参数是多少，所以那也不是“模型在学习”。

2.3 从分数到概率：softmax 与温度

模型最后一层输出的并不是概率，而是一串分数，行话叫 logits：词表里每个 token 一个数，可正可负，加起来也不等于 1。要变成概率，得经过一个叫 softmax 的函数：先给每个分数取指数 ez，变成正数；再除以所有指数的总和，让它们加起来等于 1。

在取指数之前，还可以先把每个分数除以一个数 T，这个 T 就叫温度。T 小于 1，分数之间的差距被放大，高分的更高，分布变“尖”，回答更保守；T 大于 1，差距被缩小，分布变“平”，冷门词更有机会，回答更发散。图 2-3 是同一组分数在三种温度下的样子。

softmax 的公式里有指数，指数长得极快。这在计算机里会惹麻烦，下面的专栏讲为什么，以及怎么一招化解。

softmax 与浮点溢出

计算机里的小数用浮点数存，位数有限，能表示的最大值也有限。最常用的 32 位浮点数（FP32），最大约 3.4 × 10³⁸。听上去很大，可 e89 就已经超过它了。超过上限的结果会变成“无穷大”（∞），这叫上溢。一旦分子分母都是 ∞，∞ ÷ ∞ 在浮点数里是 NaN（Not a Number），整张概率表就坏了。

化解的办法只要一行：取指数之前，让每个分数先减去它们当中的最大值 m。因为 ez−m = ez ÷ em，分子分母同时除以同一个 em，比值一点不变。但减完之后，最大的数变成 0，e0 = 1，其余都小于 1，再也不会上溢。数学上等价，数值上安全，这叫数值稳定的写法。

举个例子：分数 [1000, 999] 直接取指数，两项都是 ∞；先减去 1000，变成 [0, −1]，指数是 [1, 0.3679]，概率是 [0.7311, 0.2689]。Strata 的采样内核（sampler.cu）正是这样做的：每一项都先减去最大值，再用双精度算指数和累计概率。代码事实sampler.cu Intel Arc 显卡上的版本默认改用单精度累加，因为 Arc 没有硬件双精度，模拟出来太慢；编译时设 STRATA_SYCL_SAMPLER_FP64=1 可以换回双精度。代码事实sycl_math.hpp

延伸阅读：维基百科：Softmax 函数 · Python 文档：浮点算术的问题与限制 · Wikipedia: Softmax function

浮点数为什么有上限、FP32 和 FP16 有什么不同，第 4 章细讲。

2.4 掷骰子：按概率挑一个

有了概率表，怎么“按概率挑”？想象一根长度为 1 的尺子。把每个候选的概率依次排上去：猫占前 0.62，狗占接下来的 0.23，以此类推，正好铺满整根尺子。然后随机扔一枚针，针落在哪一段，就选哪个词，见图 2-4。概率大的段长，被扎中的机会就大。

这个方法叫逆变换采样：先算出累计概率（0.62、0.85、0.94……），再找第一个大于 u 的位置。Strata 的采样内核默认就是这样挑的：累计概率一项项往上加，第一次超过 u 的那一项就是结果。代码事实[S07] 它还有一种可选的挑法，默认关闭，设 STRATA_SPEC_GUMBEL=1 才打开：给每个候选配一个随机噪声 E，E 由（种子, 位置, token 编号）算出，然后选 p ÷ E 最大的那个。这叫 Gumbel-max 技巧。抽样的分布完全不变，但同一个种子挑中的 token 可能和默认挑法不同。它是为投机解码准备的：噪声跟着 token 走，草稿和目标模型的候选名单差一个词，也不会让其余的挑选全部错开（第 18 章）。代码事实sampler.cu

另一种做法是贪心：不掷骰子，永远选概率最高的那个。贪心的输出完全确定，适合需要稳定答案的场合，比如做题、测试。Strata 的采样参数里约定，温度小于等于 0 就走贪心；请求里不写温度时，服务层说明引擎默认也是贪心。代码事实sampler.hpp · server.py

剩下一个问题：计算机怎么“随机”扔针？它其实是在算一个看起来随机的数。

伪随机数与种子

计算机是确定的机器，同样的输入永远得到同样的输出。它产生的“随机数”，其实是一个公式算出来的数列，只是看上去毫无规律，这叫伪随机数。公式的起点叫种子（seed）：种子相同，整串数列就相同。这是好事：出了问题，可以用同一个种子把现场原样重放。

常见的生成器是顺序式的：每个数由上一个数算出来，想要第 1000 个，就得先算出前 999 个。还有一种计数器式的：第 n 个数直接由（种子, n）算出来，和前面算过几个无关，见图 2-5。

Strata 的采样默认用一种叫 Philox 的计数器式生成器：第 t 个 token 用的随机数只由（种子, 位置 t）决定。源码注释点明了这样选的原因：一批 token 可以按任意顺序采样，结果仍然可以重现。生成的 u 取 24 个二进制位，严格落在 [0, 1) 之内，不会被舍入成 1。代码事实sampler.cu 前面说的 Gumbel-max 挑法不用 Philox：它的噪声由另一个哈希函数算出，输入多了 token 编号，同样和之前抽过几次无关。

延伸阅读：OI Wiki：随机函数 · Python 文档：random 模块 · 维基百科：伪随机数生成器 · Wikipedia: Counter-based RNG

学过计算机的同学：逆变换采样就是在累计分布函数（CDF）上做查找：把 [0, 1) 上的均匀分布，映射成任意离散分布。候选很多时，累计数组是有序的，可以用二分查找把一次采样降到 O(log n)。

2.5 采样链：先后顺序也算数

真实的引擎在掷骰子之前，还会先把概率表“修剪”几遍。Strata 的采样链有六步，顺序固定，见图 2-6。代码事实[S07]

  • 重复惩罚：最近出现过的 token，分数被调低，防止模型车轱辘话来回说。
  • top-k：只保留分数最高的 k 个。Strata 采样参数的默认值是 20；服务层把 top-k 限制在 1 到 64，因为引擎的采样路径最多只保留 64 个候选。代码事实server.py
  • top-p：按概率从高到低累加，加到 p 就停，后面的全砍掉。默认 p = 0.95。
  • min-p：去掉概率不到第一名 min_p 倍的候选。默认 0，也就是关闭。
  • 温度和挑选：前面讲过。

为什么顺序要紧？看温度的位置：它排在截断之后。所以 top-p 那一刀，是按温度为 1 时的概率砍的。温度再高，也救不回已经被砍掉的候选。反过来，如果把温度挪到最前面，同样的参数会砍出另一批候选。

Strata 自己就踩过这个坑。源码注释记录了一次修复：早先的版本把重复惩罚做了两遍（温度之后又做一遍），还把 min-p 放到了 top-p 前面。注释说得很直白：每一种顺序都能产出一个“合法”的 token，所以只看输出根本发现不了，必须在概率分布这一层和独立算出的结果逐项比对。代码事实sampler.cu

这给我们一个重要的习惯：判断两个采样实现是否一致，要比概率表，不要只比最后的文字。文字一样，分布可能不同；分布只差一点点，文字也可能在某一步分叉。

2.6 动手：把“分布”和“抽样”分开看

打开本章的交互实验「从 logits 到概率」。它只用三个分数，把温度和随机数 u 做成两个独立的旋钮。

  1. 固定 u，只改温度。你会看到概率条的长短在变，选中的 token 可能跟着变。温度改的是分布。
  2. 固定温度，只改 u。概率条纹丝不动，只有针扎的位置在变。u 改的是从分布里抽到哪个样本。
  3. 把三个概率加起来。屏幕上显示的数字四舍五入后，加起来可能是 0.999 或 1.001。这不是 bug：判断“加起来等于 1”，要允许一个很小的浮点误差。

实验和本页的两个交互图都是教学推演：分数是假设的，随机数用的是一个简单的哈希函数，不是 Strata 的 Philox。

记住这三点

  1. 模型每一步只输出一张“下一个 token”的概率表；整句话的概率是各步条件概率的乘积（链式法则）。
  2. softmax 把分数变成概率。先减去最大值，结果不变，还能防止浮点溢出。温度只改分布的尖平。
  3. 采样 = 用一个伪随机数按累计概率挑一个。采样链的顺序也是语义：顺序不同，概率表就不同。

常见误解：“温度设成 0，同一个问题的回答就永远一字不差。”

温度 0 只保证“每一步都挑最高分”。可最高分本身是浮点运算算出来的，换一种求和顺序，最后几位小数就可能不同；两个候选分数极接近时，这点差别就能换掉一个 token，后面整段都会分叉。Strata 的文档就记录了这种情况：用 IQ 系列模型时，CPU 算一个 token 和一次算几个 token 用的是不同的内核，舍入略有不同，同一个提示在温度 0 下可能得到另一个（同样合理的）回答。想要逐字节相同，还得关掉提示缓存、专家换入换出和 PCIe 分流等几项设置。上游测量（IQ3_XXS，约 3,600 个 token 的提示，重复 4 次）：开齐这三个开关，4 次只出现 1 种回答；用默认设置会出现 2 种。上游报告[S03] 这组测量做在 v0.1.41 之前。v0.1.41 起，一张 NVIDIA 显卡读短提示（小于 1,024 个 token 的块）时，闲着的 CPU 默认分担一部分专家。CPU 算出的结果和显卡不逐位相同，所以还要设 STRATA_PREFILL_CPU_SHARE=0。代码事实[S12]prefill.cpp

深入一层：手算一遍，再看服务层的契约

链式法则的完整写法

设一段序列为 x₁…xₙ，链式法则给出：

P(x₁…xₙ) = ∏ₜ P(xₜ | x₁…xₜ₋₁)

推理循环每一轮计算一个条件分布。“历史”不是可有可无的背景，而是函数的输入。改掉较早的一个 token，之后所有条件分布都可能变。这也解释了为什么缓存前文的计算结果（第 20 章的会话缓存）只能在前缀完全相同时复用。

手算 softmax 和一次采样

取 z = [2, 1, 0]，T = 1。减去最大值 2，得到 [0, −1, −2]，指数约为 [1, 0.3679, 0.1353]，总和 1.5032，归一化得到 [0.6652, 0.2447, 0.0900]。累计概率约为 [0.6652, 0.9100, 1]。若 u = 0.8，第一个超过它的累计值是 0.9100，选第二项；u = 0.5 选第一项；u = 0.95 选第三项。贪心永远选第一项。

温度趋于 0，和贪心不是同一回事

数学上，T 趋于 0 时 softmax 趋向“最高分的那项概率为 1”。但程序里不能真的去算 z ÷ 0，所以工程实现都把贪心写成一个单独的分支。另一个细节是并列：两个分数完全相等时选谁，必须有固定规则。Strata 的贪心内核规定编号小的胜出，并行版本也保持了这条规则，注释称它是“整个正确性论证的核心”。代码事实sampler.cu

重复惩罚的符号陷阱

重复惩罚“把分数调低”，听上去就是除以一个大于 1 的数。可分数可能是负的：负数除以 1.1，反而变大了。Strata 照搬了 llama.cpp 的规则：分数为正时除以惩罚系数，分数小于等于 0 时乘以惩罚系数。注释提醒，无条件相除是读论文时最自然的写法，却会在一半词表上把惩罚变成奖励。另一个细节：“出现过”惩罚（presence）只看出现没出现，是个 0/1 开关，不看出现了几次。sampler.cu

种子相同，不等于输出相同

假设候选 A 原本分数最高，但它在历史里重复了很多次。先做 top-k 再惩罚，和先惩罚再做 top-k，候选集合可能完全不同。所以“种子相同”远不足以证明输出相同。还要固定：历史、采样参数、处理顺序，以及算出 logits 的那条数值路径。Strata 的耦合草稿接口就把这些写进了契约：验证窗口第 t 行用 Philox(种子, pos₀ + t) 抽样，草稿只有在等于这一行的抽样结果时才被接受，所以输出只是种子的函数，草稿只决定一轮能产出几个 token。这个模式默认关闭。代码事实[S07] 另一个可选模式 STRATA_SPEC_PROB=1 换了接受规则：草稿 d 以 min(1, p(d) ÷ q(d)) 的概率被接受，其中 p 是目标模型的分布，q 是草稿的分布。这就是经典的拒绝采样，也默认关闭。代码事实spec_prob.hpp 上游文档写明：这样每个 token 的分布仍和不用草稿时一样，但同一个种子写出的文字会随草稿变化。上游报告DETAILS.md

服务层的契约：拒绝，而不是悄悄截断

读 serve/frontend.py 时，先看 ChatTemplate.render 怎样传入 messages、tools 和 generation prompt，再看 effort_kwargs 怎样把各种写法的“思考档位”归一成模板认识的四档。[S16] 然后看 serve/server.py 的文件头：提示加上最大输出长度超过上下文时，请求被拒绝并返回 400，从不截断；最大输出不填、填 0 或填 −1，都表示“上下文剩多少就能写多少”。[S15] 核算时还留了 CTX_SLACK = 8 个位置的余量，和引擎那边的检查保持一致。[S15] 这 8 个位置不是模型的数学常数，而是前后端之间的约定。

怎样验收一个采样实现

在实验里拖动温度，观察概率，不要只看最后选中的 token。验收时比较的是分布：同样的 logits、同样的参数，两个实现给出的概率表要在浮点容差内一致。不要求屏幕上四舍五入后的数字相加恰好等于 1。
