5.1 一次计算至少需要多久？

设工作量 F 次浮点操作，需跨某个内存层级搬运 D 字节，计算上限 P 次/秒，带宽上限 B 字节/秒。忽略依赖和启动开销时：

T ≥ max(F/P, D/B)，I=F/D，性能 ≤ min(P, B·I)

这就是 Roofline 的核心思想。I 是算术强度。必须说明 D 穿过哪一层：DRAM、显存、PCIe 还是 SSD。把显存带宽拿来计算 RAM 里的专家读取时间，相当于把不同公路的限速写在同一段路上。

下界不是预测值。真实 T 还受启动、同步、访存不规则、低占用率、页故障与串行依赖影响；即使没有某一种开销，也不意味着能同时达到所有峰值。

5.2 例题：同一个权重矩阵，单流与批量不同

教学假设：某线性层有约 8 百万权重，每个 2 字节，总权重约 16 MB。一个输入向量需要约 16 MFLOP；忽略其他读写，I≈1 FLOP/byte。

如果 32 个输入一起计算且权重只读一遍，工作量变成约 512 MFLOP，权重流量仍约 16 MB，理想 I≈32。激活与输出会增加流量，因此这是便于理解的近似。它解释了为什么 prefill 的 GEMM 与 decode 的 GEMV 不应该按同一套“每 token 速度”期待。

5.3 依赖图决定哪些工作可以重叠

如果 A 必须先完成，B 才能读取 A 的结果，两个硬件单元都空闲也不能让 B 提前开始。Strata 的层间残差更新就是这样的因果链。会话接口中甚至明确解释：本层专家结果尚未合并，下一层就不能拿到正确残差。[S13]

同层的一些 GPU 工作与 CPU 专家计算可以重叠，但重叠大小必须由时间线证明。对于可并行分支 A、B，阶段时间近似 max(TA,TB)+Tjoin；对串行分支则为 TA+TB。用“同时启动”来替代实际重叠时间，是常见的性能分析错误。

5.4 Amdahl：优化局部不是优化整体

原时间中比例 f 的部分加速 s 倍，其他不变，则总加速比：

S = 1 / [(1−f)+f/s]

若 GEMV 占 20%，内核快两倍，总时间变为 0.8+0.2/2=0.9，总加速仅 1.111 倍。即便它无限快，上限也只有 1.25 倍。真正的优化机会取决于它在目标工作负载的关键路径占比，不取决于微基准成绩是否漂亮。

5.5 指标要和用户体验对上号

TTFT 是发出请求到第一个输出 token 的时间，可能包括排队、模板、分词、prefill、首步 decode 与传输。输出吞吐率是生成 token 数除以相应解码时间，不是“最终答案字数 / 总时间”。系统总吞吐量还要把多个请求的输出相加。

一个系统可以总吞吐高但每人等待很久；也可以短请求很快、长请求被饿死。因此本书后半部分会引入队列和分位数，而不是把一个 token/s 数字当成产品的全部质量。

5.6 实验：把假设写在结果前面

在 Roofline 实验中输入操作数、流量、计算上限和带宽，观察瓶颈从搬运转向计算。再增加一个不可隐藏的启动时间。报告时保留所有假设和单位，标题必须写“理论下界 / 教学估计”。不能把输入一张显卡的宣传峰值后得到的结果称作那张显卡的实测。
