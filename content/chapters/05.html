你可能注意到过

显卡的宣传页上写着每秒几十万亿次运算。可同一张卡跑大模型，每秒只吐几十个 token。按运算次数算，生成一个 token 远用不了那么久。时间都去哪了？

Strata 的源码注释里有一句很直白的结论：这个引擎“受限于启动开销，而不是带宽”。还有一句：GEMV 只占一个 token 的约 16%，所以把它优化几个百分点，“动不了总数”。代码事实[S13][S14] 这一章教你用三把尺子找出时间花在哪：带宽与延迟、roofline、Amdahl 定律。

一句话：一段计算的耗时，至少是“算的时间”和“搬数据的时间”里较长的那个；写答案时数据多、运算少，所以卡在搬运上。优化之前先量清楚各部分占多少：只占 16% 的部分，快到无穷也只能让整体快 19%。

5.1 显卡那么快，为什么 token 还是慢

想象一位厨师，切菜快得惊人，可食材要从楼下仓库一趟趟搬上来。只要搬运跟不上，厨师刀再快也只能等着。显卡的计算单元就是这位厨师，显存、内存就是仓库，中间的通道每秒能搬多少字节，决定了厨师能不能忙起来。

写答案时，每生成一个 token，都要把这一步用到的权重读一遍。第 10 章算过，光是专家数据就有约 664 MB。Strata 的源码里记着一个测量：在那台测试机上，从内存读专家的速度是 44.14 GB/s。代码事实expert_source.hpp 假如每个 token 的 663.6 MB 专家都从内存读，光读就要 663.6 MB ÷ 44.14 GB/s ≈ 15 ms，每秒最多 66 个 token，还没开始算。教学推演

这就是为什么 Strata 要把热门专家放进显存（显存读得快得多），并让 CPU 在内存里就地计算没命中的专家（数据不必过 PCIe）。上游实测的输出速度是每秒 93 个 token（RTX 5070 12 GB，Q2_0，4K 提问，引擎 0.1.26，开启投机解码），比上面那个“全从内存读”的上限还高。原因有二：大量专家根本不用从内存读；投机解码让一轮能产出不止一个 token（第 18 章）。上游报告[S03]

带宽与延迟

第 1 章的存储层次专栏提过这两个词，这里把它们变成一个公式。延迟是“发出请求到第一个字节到达”要等多久，像快递从下单到出发；带宽是“开始搬以后每秒能搬多少”，像货车的载重。搬一批数据的时间大约是：

传输时间 ≈ 延迟 + 数据量 ÷ 带宽

两项谁说了算，取决于数据量，见图 5-1。小包裹几乎全是延迟：搬 1 KB 和搬 2 KB 差不多一样久。大包裹几乎全是带宽：664 MB 的时间完全由带宽决定。所以优化小而频繁的操作，要想办法减少次数；优化大块搬运，要想办法提高带宽或者少搬。

延伸阅读：维基百科：带宽（计算机） · 维基百科：延迟（工程学） · Wikipedia: Memory bandwidth

5.2 两块天花板：roofline 模型

把“算”和“搬”放在一起看。设一段计算要做 F 次运算，要穿过某一层存储搬 D 字节；硬件每秒最多算 P 次，那一层每秒最多搬 B 字节。不考虑别的开销，耗时至少是：

T ≥ max(F ÷ P, D ÷ B)

两项里大的那个说了算。再定义算术强度 I = F ÷ D：每搬 1 字节，能做几次运算。能达到的速度就被两块“天花板”压着：每秒运算次数 ≤ min(P, B × I)。画出来像一个屋顶，叫 roofline 模型，见图 5-2。

算力与 roofline

算力是每秒能做多少次浮点运算，单位 FLOPS；1 TFLOPS 是每秒一万亿次。roofline 模型说：一段计算能跑多快，看它落在哪块天花板下面。两块天花板相交的地方叫拐点，位置是 I = P ÷ B。I 小于拐点，是带宽受限：再强的算力也在等数据；I 大于拐点，是算力受限：数据管够，运算是瓶颈。

用一个矩阵乘向量来算 I。每个权重对每个输入做一次乘法、一次加法，共 2 次运算；权重如果用 FP16 存，每个 2 字节。一次只算 1 个 token 时，I = 2 ÷ 2 = 1。假设算力 P = 50 TFLOPS（教学假设），带宽 B = 672 GB/s，拐点约在 74；I = 1 时最多只能用到 0.672 TFLOPS，不到上限的 2%。教学推演

两点提醒。第一，D 必须说清是穿过哪一层的字节：显存、内存、PCIe 还是硬盘。拿显存带宽去算内存里的专家读取时间，等于把高速公路的限速套在乡间小路上。第二，这是一个下界，不是预测：真实耗时还会被启动开销、同步、不规则的访存和数据依赖拉长。

延伸阅读：Wikipedia: Roofline model · NVIDIA Nsight Compute 文档：Roofline 分析 · CUDA C++ 最佳实践指南

5.3 一个人吃饭和一桌人吃饭

同一盘菜端上来，一个人吃和一桌人吃，端菜的力气一样，吃到的人数差了十倍。权重也是这样：读一次，给 1 个 token 用，还是给 32 个 token 用，搬运量几乎一样。

算一个具体的例子。教学推演 某个线性层有约 800 万个权重，每个 2 字节，共约 16 MB。只算 1 个输入：约 1600 万次运算，I ≈ 1。一次算 32 个输入，权重仍只读一遍：约 5.12 亿次运算，权重流量仍约 16 MB，I ≈ 32。输入输出本身也有流量，所以这是个近似，但量级不会错。

这正是第 1 章“读题快、写答案慢”的根源。读题时整段提问一起算，一份权重被几千个 token 共用；写答案时一轮只有一个 token。上游在同一台机器上测到：4K 长度的提问，读题每秒 1,299 个 token，写答案每秒 93.0 个（RTX 5070 12 GB，Q2_0，引擎 0.1.26）。上游报告[S03] 两者不能用同一套“每 token 多快”来期待。

量化也会推高 I：同样的权重少占字节，同样的带宽能喂更多运算。第 4 章的 Q2_0 每个权重只占 0.28125 字节，算 1 个 token 的 I 就从 1 变成约 7。代价是每个权重用之前要先解码，这部分额外运算 roofline 的两块天花板里都没画。

学过计算机的同学：这就是《计算机体系结构》里“访存密集”和“计算密集”的区分，和 CPU 上用分块（tiling）提高缓存复用是同一个道理：让每个读进来的字节多参与几次运算。

5.4 依赖链：有些活就是没法并行

家里同时有洗衣机和烘干机，可一桶衣服必须先洗完才能烘。机器再多，这一桶衣服也快不了。谁必须等谁，画成一张图，从头到尾最长的那条链叫关键路径：总时间至少是它的长度。

Strata 每一层的计算就有这样一条链。一层的输出要先合并好，下一层才能拿到正确的输入；层与层之间是严格串行的。源码注释说得很清楚：每层 CPU 算专家的那段时间，藏不进一条严格串行的残差链里。GPU 在这段时间里能并行做的，只有共享专家这一点工作，因为合并之后的一切都依赖专家的结果。代码事实[S13] 见图 5-3。

并行的两路 A、B，这一段的时间近似是 max(TA, TB) 加上合并的时间；串行的两步则是 TA + TB。所以对付 CPU 这段，Strata 的答案不是“更好地重叠”，而是把更多专家放进显存缓存，让 CPU 少算一些（第 10、12 章）。源码注释原话是：CPU 这一项，要靠第 3 阶段的显存缓存来解决，而不是靠这条流水线。[S13]

还要提防一种错觉：“两件事同时启动了”不等于“它们真的重叠了”。Strata 专门加了一个诊断计数器，统计 CPU 是在 GPU 还在算的时候开始干活，还是 GPU 已经算完才开始。两种情况下 token 都是对的，单看每层耗时也一样，只有这个计数能告诉你重叠到底有没有发生。代码事实[S13]

5.5 优化一个局部，整体快多少

假设你把占总时间 20% 的那一步优化到快 2 倍。整体快多少？不是 2 倍，也不是 1.2 倍：新时间 = 80% + 20% ÷ 2 = 90%，整体只快 1.11 倍。下面的交互图可以随意改这两个数：

Amdahl 定律与关键路径

把总时间里比例为 f 的部分加速 s 倍，其余不变，整体加速是：

S = 1 ÷ [(1 − f) + f ÷ s]

这就是 Amdahl 定律。让 s 趋于无穷，S 趋于 1 ÷ (1 − f)：f = 16% 时上限 1.19 倍，f = 50% 时 2 倍，f = 90% 时 10 倍。结论很朴素：优化的回报由“这部分占多少”决定，不由“这部分快了多少倍”决定。

它和关键路径是一对搭档。Amdahl 说“占比小的部分优化了也没用”；关键路径说“不在最长链上的部分，优化了完全没用”，因为总时间由最长的那条链决定，别的链再快也只是早点开始等。所以性能分析的第一步永远是量出时间线：哪些步骤在关键路径上，各占多少。

延伸阅读：维基百科：阿姆达尔定律 · 维基百科：关键路径 · CUDA C++ 最佳实践指南（含 Amdahl 定律一节）

Strata 的源码里有一个教科书式的例子。开发者发现另一个工具把每行的线程数从 32 改成 64 后带宽更高，看起来是“免费的提速”。实测却是：带专家时 64 线程每秒 11.75 个 token，32 线程 11.99 个；不带专家时 20.19 对 20.26，在噪声范围内一样，还略差。注释给出的解释正是 Amdahl：GEMV 只占一个 token 的约 16%，那里快几个百分点，动不了总数。代码事实[S14] 注意这些 token/s 是开发早期的测量，和今天的速度不能直接比。

同一份源码还量出了真正的大头：启动开销。一个只处理 48 个数的小内核，测出来也要约 0.028 ms，因为这就是这台机器上启动一个内核的代价；一层 GDN 要启动约 19 个内核，一个 block 约 45 个。把一个 block 的 43 个节点录成 CUDA Graph 一次重放，耗时从 2.393 ms 降到 1.585 ms，快了 1.51 倍，省下的全是启动开销。代码事实[S13] 见图 5-5。这是 5.1 节专栏里“小包裹看延迟”的翻版：每次启动都是一个小包裹。

5.6 指标要对上体验，然后动手

最后说清几个常被混用的指标。首字延迟（TTFT）是从发出请求到看到第一个 token 的时间，包括排队、套模板、分词、读题和第一步生成。输出速度是生成的 token 数除以生成所用的时间，不是“最终字数 ÷ 总时间”。多人同时使用时，还有总吞吐量：所有人的输出加起来每秒多少。一个系统可以总吞吐很高，但每个人都等很久；也可以短请求很快、长请求被一直挤到后面。所以第 25、27 章会讲排队和分位数，不能把一个 token/s 数字当成全部。

动手：打开本章的交互实验「算力还是带宽」。

  1. 输入运算量、搬运量、算力和带宽，看瓶颈怎样从搬运转到计算。
  2. 加一段“无法隐藏的启动时间”，看下界怎样被它抬高。
  3. 把某一阶段加速 2 倍，看端到端为什么没有快 2 倍。

报告结果时，把所有假设和单位写在数字前面，标题写“理论下界 / 教学推演”。把宣传页上的峰值算力代进去得到的数，不能叫那张显卡的实测。

记住这三点

  1. 耗时至少是 max(运算量 ÷ 算力, 字节数 ÷ 带宽)；字节数要说清穿过哪一层。写答案时 I 很小，卡在搬运上。
  2. 一次算多个 token 让一份权重被多次使用，I 变大，才能用上算力。这就是读题比写答案快十几倍的原因。
  3. 优化前先量时间线：不在关键路径上的部分优化了没用，占比小的部分优化了也没多大用（Amdahl）。

常见误解：“显卡算力翻一倍，生成速度就翻一倍。”

写答案时，速度主要卡在数据搬运和依赖链上，算力大多闲着，翻倍了也只是闲得更多。对 Strata 来说，显存的大小反而更要紧：上游文档说，更大的显存比更快的显卡更重要，每多 1 GB 显存大约能多放 700 个专家，每个放进显卡的专家，CPU 就少算一个。上游报告[S02]

深入一层：下界、重叠与怎样报告性能

下界不是预测

roofline 给的 T ≥ max(F ÷ P, D ÷ B) 只是下界。真实的 T 还受内核启动、同步、不规则访存、并行度不足、缺页和串行依赖的影响。即使某一种开销不存在，也不意味着能同时达到所有峰值。D 必须说明穿过哪一层：显存、内存、PCIe 还是硬盘；同一段计算对不同的层有不同的 I。

例题：同一个权重矩阵，单个和批量

教学假设：某线性层约 800 万个权重，每个 2 字节，约 16 MB。一个输入向量约 1600 万次运算，忽略其他读写，I ≈ 1。32 个输入一起算、权重只读一遍：约 5.12 亿次运算，权重流量仍约 16 MB，理想 I ≈ 32。激活和输出会增加流量，所以这是便于理解的近似。它解释了为什么读题的 GEMM 和写答案的 GEMV 不该按同一套速度去期待。

重叠要用时间线证明

对可以并行的两路 A、B，这一段的时间近似 max(TA, TB) + T合并；对串行的两步是 TA + TB。用“它们是同时启动的”来代替实测的重叠时间，是常见的性能分析错误。Strata 的会话代码给出了一个反例的检测办法：如果主机读到“这一层已经算完”的同时，GPU 的事件查询也显示完成，就说明那一层早结束了，CPU 是在 GPU 空闲时才开始干活，整条流水线其实等于串行。这个区别在返回值里看不出来，在每层耗时里也看不出来，所以要专门计数。[S13]

Amdahl 的两个数

若 GEMV 占 20%，内核快 2 倍，总时间变成 0.8 + 0.2 ÷ 2 = 0.9，整体只快 1.111 倍；即便它无限快，上限也只有 1.25 倍。真正的优化机会取决于它在目标负载的关键路径上占多少，不取决于微基准的成绩多漂亮。

指标的定义要写全

首字延迟可能包括排队、模板、分词、读题、第一步生成和网络传输，报告时要说清包含哪些。输出速度要说清分子分母：是生成的 token 数除以生成阶段的时间，还是别的。上游的速度表就写全了条件：显卡、CPU、内存、操作系统、引擎版本、上下文长度、生成多少 token、是否开启投机解码。[S03] 还要注意，投机解码的速度和文本内容有关，同一个提示的不同回答就能差几个百分点。[S03]

报告模板

把假设写在结果前面：硬件型号和规格、模型和量化格式、上下文长度、引擎版本、测了几次、取均值还是中位数。标题写清“理论下界”“教学推演”还是“实测”。第 27 章会把这套方法讲完整。
