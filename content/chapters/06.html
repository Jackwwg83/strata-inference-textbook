你可能注意到过

同一个大文件，第一次打开要转好一会儿，第二次却几乎瞬间就好。还有一件更怪的事：用 mmap “打开”一个 30 GB 的模型文件，函数眨眼就返回了，可此刻一个字节都还没从硬盘读出来。

模型文件是一大块字节。引擎要的是一个个形状、类型都对得上的张量。这一章讲中间那段路：文件里装着什么，“打开”和“读进内存”为什么是两回事，以及引擎怎样证明读到的字节，正是它以为的那些字节。

一句话：模型文件要闯三关才能变成能用的张量：读懂目录，证明每个张量都完整地落在文件里，让字节真正进到内存。每一关出错都可能“悄无声息”，所以 Strata 在每一关都主动检查，宁可拒绝启动，也不带着错的字节去算。

6.1 模型文件里装了什么

把模型文件想成一本书。封面写着书名和版本；接着是目录，告诉你每一章从第几页开始；最后才是正文。Strata 读的是 GGUF 格式，这是 llama.cpp 生态里常用的模型文件格式，结构正是这样，见图 6-1。

元数据是“关于数据的数据”，比如模型叫什么架构、有几层。张量目录给每个张量登记五样东西：名字、维度数、每一维多长、用什么数据类型存、从数据区第几个字节开始。

Strata 的 GGUF 读取器一打开文件就开始核对。代码事实 开头 4 个字节必须是“GGUF”，版本必须是 3；元数据里的架构必须是 qwen4exp，层数 48、宽度 2560、注意力头 24、KV 头 2 也必须对得上。任何一项不符，它报出具体是哪个键、期望多少、实际多少，然后拒绝运行（gguf_reader.hpp 第 423–427、573–603 行）。这个引擎只为一个模型而写，“差不多能跑”比直接报错更危险。

知道了形状和类型，就能算出一个张量占多少字节。Strata 的主力格式 Q2_0 把 64 个数打包进 18 个字节，相当于每个数 2.25 bit。代码事实（gguf_reader.hpp 第 120–121、213–216 行）一个 2560 × 640 的专家矩阵有 1,638,400 个数，也就是 25,600 个块，占 25,600 × 18 = 460,800 字节。一个专家有三个这样的矩阵，合计 1,382,400 字节，正好等于源码里写死的专家大小。教学推演[S06]

6.2 “打开”不等于“读进来”：mmap 与页缓存

读文件有两种思路。第一种是“复印”：调用 read，操作系统把指定的字节拷进你准备好的内存。第二种是“借阅证”：调用 mmap，操作系统给你一段地址，说“这段地址就代表那个文件”，至于字节什么时候真的从硬盘搬上来，等你用到再说。

文件、内存映射与页缓存

文件是硬盘上一串有名字的字节。程序不能直接对硬盘做加减乘除，数据必须先进内存。操作系统管理内存的单位叫页，常见大小是 4 KiB。

内存映射（mmap）把一个文件“挂”到进程的地址空间上：地址 base + i 就对应文件的第 i 个字节。映射建立时，操作系统只登记了对应关系，并不读数据。程序第一次访问某一页时，硬件发现这页还不在内存里，触发缺页。操作系统接手，从硬盘把这一页读进来，再让程序接着执行。程序自己完全察觉不到这次停顿，只是那一下变慢了。

读进来的页不会马上丢掉，而是留在页缓存里。同一个文件再被访问，直接从内存拿，这就是“第二次打开快得多”的原因。内存紧张时，操作系统会把一段时间没用的干净页回收，以后要用再从硬盘读。专栏后的图 6-2 画出了这三层关系。

和本章的关系：Strata 读 GGUF 文件头用的是 mmap，在低内存模式下读专家一般也用 mmap（例外见 6.3 节）。所以“映射成功”只说明地址准备好了，不说明数据已经在内存里，更不说明以后访问不会卡在硬盘上。

6.3 Strata 把字节放在哪：拷贝、映射、直读

同一个引擎，对不同的数据用了三种完全不同的放法，见图 6-4。选哪种，取决于两个问题：这份数据每个 token 都要反复读吗？内存装得下吗？

常规模式：拷进来，锁住。内存够大时，全部专家（23–50 GB，视量化版本而定）被拷进内存并锁页。上游报告[S03] 锁页的意思是告诉操作系统：这些页不许换出到硬盘。锁住之后，显卡可以通过 DMA 直接从这块内存取数据，不用 CPU 先倒一手。[S06] 平台层的锁页函数在 Linux 上调用 mlock，在 Windows 上调用 VirtualLock，只锁住一部分时会如实报告，而不是假装成功。代码事实（platform/memory.hpp 第 1–24 行）

低内存模式：映射，让页缓存代管。内存放不下全部专家时（引擎 0.1.26 起），安装程序改为映射模型目录里的 experts.bin。显卡没缓存的专家由操作系统的文件缓存代管，内存紧张时可以还回去。如果可用内存连这些字节都留不住，引擎就不再走映射，改为绕过页缓存、直接从硬盘读专家。Windows 早就这样做；v0.1.40 起 Linux 也按同一条规则判断，用的是 O_DIRECT。代码事实（expert_source.cpp 第 377–381 行）上游报告，Coder 版本的引擎已提交内存从 36 GB 降到约 13 GB，回答不变；但显卡小的话，多数专家要从硬盘读，会慢很多。上游报告[S03]

n-gram 表：不进内存，直接读硬盘。这张表有 320,001,536 行，默认的表按 IQ4_NL 格式每行 90 字节，合计约 28.8 GB（26.8 GiB）。代码事实 v0.1.40 起，读取器也接受 Q4_0、Q5_1、Q8_0、BF16 等格式的表，每行 90 到 320 字节（ngram.hpp 第 44–58 行）。读取器的设计要求它永远不占内存，连页缓存也不占：每一行都用不经缓冲的 4 KiB 读取直接从硬盘取，每个 token 要读 16 行，分布在 16 个不同的页上（ple_reader.hpp 第 1–5 行）。底层的直读模块写明了原因：内存映射做不到“不进页缓存”的承诺，不经缓冲的读取可以；代价是偏移、长度和缓冲区地址都必须是 4096 的倍数（direct_file.hpp 第 3–9 行）。这张表是做什么用的，第 11 章细讲。

6.4 每个张量都要过安检

目录说“张量 X 从偏移 o 开始，长 n 字节”。引擎能信吗？文件可能下载到一半就断了，可能被别的工具写坏了，也可能根本是另一个模型的文件。引擎读张量之前，必须先证明 [o, o+n) 这一段完整地落在文件里。

最顺手的写法是 o + n ≤ F（F 是数据区的长度）。可计算机里的整数位数是固定的。无符号整数算出的结果超过上限时，会悄悄“绕回”到很小的数，这叫溢出。如果目录里的 o 被写坏成一个极大的数，o + n 绕回成一个小数，检查就被骗过去了。

Strata 用的是不会溢出的写法：先确认 o ≤ F，再确认 n ≤ F − o。第一步保证了减法不会出负数，第二步不再做加法。代码事实（gguf_reader.hpp 第 530–536 行）下面的模拟器把整数缩小到 8 位，让溢出看得见：

学过计算机的同学：在 C/C++ 里，无符号整数溢出是“定义良好”的：按 264 取模，不报错，不崩溃。正因为它安静，才危险。有符号整数溢出则是未定义行为，编译器甚至可能把你的检查优化掉。

算字节数时的乘法也会溢出。一个张量的元素个数是各维长度相乘，四个维度相乘很容易超过 64 位。Strata 每乘一个维度 d 之前，先检查“当前积 ≤ 上限 ÷ d”，不满足就返回 0，表示“这个形状算不出合法大小”。代码事实（gguf_reader.hpp 第 475–488 行）

这只是安检的一部分。同一个读取器还会拒绝这些文件：两个张量重名（否则查找时谁排前面谁赢，悄悄用错张量）；维度数是 0 或超过 4；元数据数组长度超过 224；数据区起点落在文件末尾之后。代码事实（gguf_reader.hpp 第 326、437–446、458 行）映射专家文件之前，引擎还会核对文件大小是否正好等于专家布局要求的字节数，差一个字节都拒绝（expert_source.cpp 第 563–573 行）。

字节范围对了，形状也要对。layout.hpp 在加载时逐层核对每个张量的形状：名字对应的张量是不是内核以为的那个形状。头文件里写着它的目标：在加载时报出张量名、实际形状和要求的形状，而不是在第 4000 个 token 时变成矩阵乘法里的一个错数。代码事实[S04]

6.5 字节对不对：校验和与哈希

区间检查回答的是“字节在不在文件里”。还有一个问题它答不了：这些字节是不是原本的那些？下载时坏了一个字节，文件大小不变，区间检查照样通过。要回答这个问题，需要给数据算一个“指纹”。

校验和与哈希

直觉：寄一大箱书，怎么知道路上没丢、没换？可以先数一遍总页数写在箱子上，收到后再数一遍。这个“总页数”就是最朴素的校验和：用很短的一个数概括一大块数据，两边一比就知道有没有变。

最简单的校验和是把所有字节加起来。它能发现“某个字节变了”，却发现不了“两个字节换了位置”，因为加法不在乎顺序。更好的校验算法，例如 CRC（循环冗余校验），对顺序敏感，常用来发现传输和存储中的随机错误。

密码学哈希更进一步，例如 SHA-256。它把任意长的数据变成 256 位的摘要，并且有两个性质：输入改一个比特，摘要大约一半的位都会变（雪崩效应）；想故意造出两份摘要相同的不同文件，在现有计算能力下做不到。所以它不但能发现意外损坏，也能发现有人故意替换。专栏后的图 6-6 是一个小例子。

和本章的关系：几十 GB 的模型文件，靠文件名和大小只能证明“有个差不多大的文件”；算一遍哈希，才能证明“就是那个文件”。

Strata 的安装脚本对 Unsloth 的两种模型文件做了完整的哈希核对：实验性的 UD-Q4_K_XL（4 个分片），以及从 v0.1.39 起转为常规选项的 UD-IQ4_XS（3 个分片）。代码事实 每个分片的字节数和 SHA-256 都写死在脚本里。下载完成后，先比字节数，不对就直接报错；再以每次 16 MiB 的块读完整个文件，算 SHA-256。不一致就删掉文件，提示重新下载。算一遍 111 GB 的 UD-Q4_K_XL 大约要 5 分钟，所以结果会记在一个“完成标记”文件里，下次启动不再重算（setup.py 第 155–175、220、1316–1338 行）。其他模型文件不做哈希，安装脚本会读一遍它们的张量目录来核对（第 155–156 行的注释）。

哈希管的是“文件对不对”。字节从内存搬到显存之后，还要再确认一次。专家缓存有一个 verify_slot 函数：把显存里某个槽位的字节读回来，和内存里的原件逐字节比较。注释说，这是“唯一能证明缓存里装的就是它声称的那个专家”的东西，因为槽位编号对、字节错，产出的是一个看起来合理的错 token。[S05] 它还真的抓到过问题：第一版启动填充用了异步拷贝，与读回检查不在同一个执行顺序里，检查直接拒绝了整次运行，报“slot 0 differs from the arena at byte 0”。注释的评价是：这正是检查在尽它的职责。代码事实[S05]

6.6 动手：不下载模型也能练加载器

本章没有独立的实验页，上面两个交互图就是实验。建议按这个顺序玩：

  1. 在「页缓存模拟器」里先让 C ≥ W 跑 10 个 token，再把 C 调成 W − 1。记下两次的命中率，用一句话解释为什么差一个槽位就从接近 100% 掉到 0%。
  2. 在「区间检查」里把 n 固定为 100，从 o = 150 开始往上拖，找出写法 A 第一次被骗的 o 值，并用 o + n − 256 验证你的答案。

进阶练习：自己设计一个 128 字节的假 GGUF 文件，目录里写三个张量。依次测试：合法区间、恰好到末尾、越界 1 字节、极大的偏移、维度相乘溢出、两个张量重名。验收标准不是“坏文件会崩溃”，而是在任何计算开始之前，给出一句人能看懂的拒绝原因。

记住这三点

  1. mmap 只建立“地址 ↔ 文件”的对应关系，字节在第一次访问时才因缺页从硬盘读入，然后留在页缓存里。映射成功不等于数据已在内存。
  2. Strata 按访问方式选放法：反复读又装得下的专家拷进内存并锁页；装不下时交给页缓存；28.8 GB 的 n-gram 表绕过页缓存直接读硬盘。
  3. 每个张量都要过安检：区间检查写成 o ≤ F 且 n ≤ F − o 才不会溢出；形状在加载时核对；文件整体用 SHA-256 这类哈希证明“就是那个文件”。

常见误解：“mmap 成功了，模型就已经在内存里了。”

mmap 返回时，操作系统只登记了对应关系，可能一页都还没读。真正的读取发生在第一次访问时，而且读进来的页在内存紧张时还可能被回收，下次访问再从硬盘读。Strata 的源码里就记录过：页被淘汰得和读进来一样快时，速度会掉到硬盘水平。

深入一层：一致不等于正确、所有权与生命周期、文档和代码打架时信谁

两个工具一致，也可能一起错

layer.cpp 里保留了两段很有价值的故障记录。[S14] 第一段：有个函数自己重新推导量化张量三块数据（编码、缩放系数、偏移）的大小，假设每个缩放系数占 4 字节。可 303 个量化张量里有 90 个的缩放系数是 2 字节的 fp16，包括全部 58 个 Q2_0 专家张量。于是算出来的缩放系数块大了一倍，三块加起来对不上张量总大小。第一反应是怀疑清单里的分组大小写错了；审计全部 303 个张量后发现分组大小没问题，被漏查的输入是缩放系数的宽度。

第二段：两个打包工具都去找名叫 mins 的数据块，可真正的键名是 offsets。两个工具“一致地”漏掉了 54 个 Q4_K/Q5_K 张量的偏移块：内存预算少算了 136 MiB，这些字节也没拷进去。注释的结论是：两个工具一致，只有在它们不共享同一个错误假设时才算证据。现在的 plane_ptrs 不再自己推导，只核对加载器记录的三块大小之和是否等于张量总字节数，以及“有没有偏移块”的标志是否和偏移块大小一致，不符就拒绝。代码事实[S14]

测试设计上的启发：两个 oracle（判定对错的参考实现）要真正独立。一个按格式规范顺序解析，另一个用手工构造、逐字节核对过的固定样本；不要让它们共用同一个布局推导函数，再把“结果相同”当成强证据。

表头游标里的一处加法

读文件头用的 Cursor::need 写的是 pos_ + n > size_（gguf_reader.hpp 第 240–242 行），正是 6.4 节说的加法写法。头部的定长字段很小，这没问题；但字符串长度 n 是从文件里读出来的。练习：如果 n 被篡改成接近 264，这次比较会不会被绕回骗过？提示：即使骗过了，下一行用 n 构造 std::string 时，长度超过上限会抛出异常，文件仍会被拒绝，只是报错信息不再是那句精确的“unexpected end of file”。这说明安全往往靠多层防线，但每一层都值得写对。

RAII 管得住的，和管不住的

C++ 的 RAII（资源获取即初始化）让对象在析构时自动释放资源：GGUF 读取器在构造中途失败时，会先解除映射、关闭文件，再把异常抛出去（gguf_reader.hpp 第 342–345、410–419 行）。可推理引擎里的资源不只是内存和文件句柄，还有显存、锁页内存、CUDA stream 和 event。智能指针只认识它被告知的所有权，不会替你等异步拷贝完成。

所以接口契约要写成“调用者持有这块缓冲，直到拷贝完成事件被确认”，而不是“传入一个地址”。expert_source.hpp 就把指针的寿命写得很清楚：普通来源返回的指针只保证活到下一次 blob() 调用；带缓存的来源必须返回指向缓存本身的指针，不能指向一块会被复用的暂存区，否则 CPU 算这个专家时，读到的可能已经是下一个专家的字节。从 GGUF 分片现拼出来的“临时”专家块，只保证在当前层和之后一两层内有效；要留得更久，必须用 copy_blob 拷一份。[S06] 释放会话内存之前，session_release 还要先撤销别的模块登记过的外部指针（比如旋转位置编码的角度表），免得新会话拿着已释放的地址去算。[S13]

文档和代码说法不一时，信谁

Strata 的说明文档写 n-gram 表“通过操作系统缓存读几行”（docs/HOW_IT_WORKS.md 第 31 行），而读取器的头文件写的是“永远不进内存，每行都用不经缓冲的 4 KiB 读取”（ple_reader.hpp 第 3–4 行）。本书按固定提交的源码叙述，并把这种分歧原样指出来。读开源项目时，文档是作者的意图，代码是实际的行为；二者不一致时，以能运行、能测试的那一方为准，同时记下分歧，别替任何一方圆场。

为什么“异步返回”不能当成“拷贝完成”

异步拷贝函数返回，只表示任务已经排进队列，DMA 引擎可能还没读源缓冲。此时复用或释放源缓冲，拷过去的可能是一半旧、一半新的字节。正确的复用许可，是同一个 stream 上的完成事件，或明确写在契约里的同步点。expert_cache.hpp 里那次 “slot 0 differs” 的失败，本质上就是两条执行顺序没有对齐。[S05]
