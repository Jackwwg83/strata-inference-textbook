你可能注意到过

手机输入法很会“接话”：你打出“今天天气”，它马上提示“很好”“怎么样”。它并不懂天气，只是记住了哪些词经常挨着出现。

Strata 运行的模型里也有一本这样的“词组记忆”，而且大得吓人：一张 28.8 GB 的表，放在固态硬盘上。上游报告[S02] 模型每生成一个 token，都要从里面取 16 行。这一章回答三个问题：行号怎么算出来，怎样从硬盘上又快又省地取，取过的行怎样留着下次再用。

一句话：模型拿最近 2 个和最近 3 个 token 做哈希，算出 16 个行号；每行只有 90 字节，却要按 4 KiB 一页从硬盘读；读过的行放进一个 8 路组相联的行缓存，组满了就按轮换指针替换。

11.1 模型里的“词组记忆”

先说这张表存的是什么。它按 n-gram（n 元组，就是“连续出现的 n 个 token”）来索引：最近 2 个 token 叫二元组，最近 3 个叫三元组。比如上下文是“我 喜欢 猫”，二元组是“喜欢 猫”，三元组是“我 喜欢 猫”。

Strata 源码里，用这张表的模块叫 PLE，它在模型的第 1 层（从 0 数起）工作。代码事实[S13] 每个 token 的流程见图 11-1：二元组和三元组各有 8 个“头”，每个头算出一个行号，一共 16 个；每行存 160 个数，16 行拼起来正好是 2560 个数，也就是模型的主宽度。代码事实（include/strata/kernels/ngram.hpp）

这张表本身就是模型的一部分参数，名字叫 per_layer_token_embd，一共 320,001,536 行。按每行 90 字节算，整张表 28.8 GB（合 26.8 GiB）。代码事实（ple_reader.hpp）它比 12 GB 显存大得多，也不放进内存，就待在硬盘上。

n-gram 语言模型

猜下一个词，最朴素的办法是“看前面几个词”。如果语料里“我 喜欢”后面 30% 是“猫”、20% 是“你”，那就按这个比例猜。只看前 n−1 个词来猜第 n 个词，就是 n-gram 语言模型。n = 2 叫二元模型，n = 3 叫三元模型。

它的麻烦是组合太多。词表有 V 个 token，三元组就有 V³ 种。V 取 10 万，三元组就是 10¹⁵ 种，绝大多数一辈子也碰不到一次，不可能每种都存一份。

Strata 的模型借用了 n-gram 的思路，但做法不同：它不存“下一个词的概率”，而是给每个 n-gram 存一小段训练好的数字，交给神经网络去用。它也不给每种组合单独一行，而是用哈希把天文数字般的组合压进 3.2 亿行里（下一节）。所以这张表更像一本“词组笔记”，不是一个完整的语言模型。

11.2 三个 token 怎样变成 16 个行号

表里没有“我 喜欢 猫”这几个字，只有行号。从 token 到行号，靠的是哈希：把任意的输入搅成一个看起来杂乱、但每次都一样的数。Strata 的哈希分三步：代码事实（ngram.hpp、src/kernels/ngram.cpp）

  1. 相乘：每个 token 编号乘一个很大的固定常数，三个位置各用一个常数。
  2. 异或：把这些乘积按二进制逐位“异或”（相同得 0，不同得 1），得到一个混合值。二元组混两个数，三元组混三个数。
  3. 取余：每个头用混合值除以自己的模数，取余数，再加上这个头在大表里的起点。每个头的模数都在 2000 万左右，都不是 2 的幂，比如 20000003、20000023、20000033。

两个细节值得记住。第一，开头没有前文的位置记作 −1；遇到“对话结束”符，它之前的历史全部截断。这两个 token 的历史属于序列状态，按“旧的在前”存放。代码事实[S13] 第二，这个哈希在 CPU 上算。它要用 64 位整数的乘法和异或，源码注释引用参考实现的说法：GPU 计算框架 ggml 没有这两样运算。代码事实（ngram.hpp）

下面的模拟器用小号数字重现这三步：乘数换成 31、17、7，模数换成 11 到 37，每种 n-gram 只用 4 个头。规则和 Strata 一样，数字小到能手算。

哈希有一个躲不开的后果：撞车（冲突），也就是两个不同的 n-gram 算出同一个行号。算一笔账：这个模型的 token 编号至少排到 248,046（对话结束符就用到了这个编号）代码事实（src/program/generate.cpp），二元组就有超过 248,046² ≈ 615 亿种可能，而一个头只有约 2000 万行。平均每行要“认领”三千多种二元组。教学推演 撞车是设计里就接受了的。

那为什么还能用？一种合理的理解是：各个头的模数不同，两个 n-gram 在某一个头上撞车，在别的头上多半各走各的，模型拿到的 16 行不会全都一样。教学推演 模拟器里多算几组上下文，你能亲眼看到这一点。

哈希表与哈希函数

图书馆有一百万本书。按书名一本本找太慢。换个办法：准备一万个书架，把书名“搅一搅”变成 0 到 9999 之间的一个数，这本书就放在那个书架上。找书时同样搅一搅，直接走到那个书架。这个“搅一搅”的规则叫哈希函数，按它分格存放的结构叫哈希表，每个格子叫一个桶。

好的哈希函数有两个要求：同样的输入永远得到同样的桶；不同的输入尽量均匀地撒开。最常见的写法是“搅拌后取余”：桶号 = h(键) mod 桶数。桶数取质数，余数会受到键的每一位影响；桶数取 2 的幂，取余就只看最低几位，高位的差别全被扔掉。

格子比键少，就一定会有两个键落进同一个桶，这叫哈希冲突（鸽巢原理：10 只鸽子进 9 个笼子，必有一笼不止一只）。普通哈希表会把键也存下来，冲突时逐个比对或换个位置放，保证查得准。Strata 这张 n-gram 表不存键，冲突就让它冲突，靠多个头互相弥补。这种“只存值、不存键、用多个哈希函数”的思路，和数据结构里的 count-min sketch 很像。

还有一个小坑：混合时为什么用异或、不用加法？源码注释点破了：两个相等的乘积，异或得 0，相加得两倍，结果完全不同，而两种写法都能算出“看起来合法”的行号。代码事实（ngram.hpp）

11.3 一行 90 字节，为什么要读 4 KiB

行号有了，接下来去硬盘上取。问题来了：硬盘不按字节读，按页读。Strata 读这张表用的是“绕过操作系统缓存”的直接读取，每次读取的起点、长度和内存地址都必须是 4096 字节的整数倍。代码事实（include/strata/platform/direct_file.hpp）想要一行 90 字节，就得把它所在的整整一页 4096 字节读进来。见图 11-3。

源码里每个读请求的长度只有两种：一页，或者两页（行跨过了页边界）。代码事实[S11] 跨页的比例可以手算：4096 = 45 × 90 + 46，一行只要从某页的最后 89 个字节里开始，就会伸进下一页。行的起点在页内大致均匀分布，所以约 89 ÷ 4096 ≈ 2.2% 的行要读两页。教学推演

一个 token 的 16 行落在 16 个不同的页上。代码事实（ple_reader.hpp）没有缓存时，要读 16 × 4 KiB = 64 KiB，而真正有用的只有 1,440 字节，读放大约 45 倍。教学推演 读一长段提示词时，很多行可能挤在同一页上，Strata 会把同一页的请求合并成一次，并按文件位置排好序再读，让硬盘接近顺序读。代码事实（src/ngram/ple_reader.cpp）

64 KiB 听起来不多。真正的麻烦是延迟：16 次随机的小读，每次都要等硬盘响应。源码注释记录过一组开发期的测量（注释没写硬件）：早期用内存映射的办法，16 行变成 16 次“缺页”，一次接一次地等，每个 token 要 2.10–2.61 毫秒；换成直接读取、16 个请求一起发出去后，约 311 微秒。上游报告（ngram.hpp 注释）同一段注释还警告：如果进程里别处还映射着这个文件，直接读会被拖到每个 token 1,575 微秒。

11.4 读过的行留一份：8 路组相联的行缓存

同一行常常会被反复用到。“我 喜欢”这样的组合，一段对话里可能出现好多次。上游在一组固定语料上测过：如果缓存 100 万行（注释写约 95 MB），最多能省掉约 82% 的读取；一段长提示词内部，也有 20%–34% 的行会重复出现。上游报告（ple_reader.hpp 注释）

所以 Strata 在内存里放了一个行缓存，默认 1,048,576 行，按每行 90 字节算约 94 MB。代码事实（ngram.hpp）本章的字节数都按默认的 IQ4_NL 表算。v0.1.40 起，引擎也能读 Q4_0、Q5_1、Q8_0、BF16 等格式的表，每行 90 到 320 字节。行数不变，行变宽，同样 1,048,576 行的缓存就更大，BF16 表约 335 MB。代码事实（ngram.hpp）行缓存的结构是 8 路组相联：代码事实[S11]

  • 缓存分成很多组，每组 8 个位置（8 路）。默认大小下有 1,048,576 ÷ 8 = 131,072 组。
  • 一个行号先经过一次搅拌（乘一个固定的大奇数，再做一次移位异或），然后对组数取余，决定它属于哪一组。它只能住在这一组的 8 个位置里。
  • 查找时，只需比对这一组的 8 个位置。
  • 没找到，就从硬盘读，读回来后写进这一组的替换指针所指的位置，指针再往后挪一格，转到第 8 格后回到第 1 格。

这个“轮换指针”很省事：每组只要一个小计数器，不用记谁最近被用过。代价是它不看谁更常用，指针转到谁就换谁。什么时候这会吃亏？下面的模拟器给了一个最坏的例子。

这个例子是故意构造的。真实的行号先经过搅拌再分组，很难这样整齐地扎堆在一组里。模拟器里的“热点”访问也说明：访问集中在少数几行时，轮换和 LRU 的命中率差不多。用最简单的策略，换来每次查找只看 8 格、内存占用固定不涨，这是一笔划算的买卖。教学推演

学过计算机的同学：这就是《计算机组成原理》里 CPU 缓存的组相联结构，“行号 → 组号”对应地址里的组索引位，比对 8 个位置对应比较 8 个标记（tag）。区别在于：这里是软件实现，缓存的是硬盘上的表行，一格存 90 字节。

直接映射、组相联、全相联

缓存的格子比要缓存的东西少得多，所以要先定一条规矩：一个东西可以放在哪些格子里？有三种答案，见图 11-5。

  • 直接映射：每个东西只有一个固定的格子。查得最快，只看一格；但两个常用的东西抢同一格时，会你踢我、我踢你。
  • 全相联：放在哪一格都行。最灵活，但每次查找都要把所有格子比一遍，格子一多就太慢。
  • 组相联：折中。先按规则分到一组，组内几格随便放。W 格一组，就叫 W 路组相联。

三种结构对应三种未命中：第一次见到的东西必然不在，叫强制未命中；缓存总共就那么大、装不下，叫容量未命中；总量装得下，只是一组里挤不下，叫冲突未命中。图 11-4 的例子就是纯粹的冲突未命中。

11.5 别让模型干等：早点发请求，另一个线程去收

还剩一个问题：就算只要 311 微秒，模型也不想停下来等。好在 16 个行号只取决于 token 本身，token 一确定，行号就能算出来；而这 16 行要到第 1 层才用。中间隔着两段活：把 token 换成向量（嵌入），以及第 0 层的计算。这就是能用来“藏住”读盘时间的窗口。代码事实（ple_reader.hpp）

所以读取接口被拆成两半：token 一出来就调用 issue（发请求），马上返回；到第 1 层要用之前，再调用 collect（取结果），这时才可能需要等。见图 11-6。

谁去跟硬盘打交道？默认有一个专门的 I/O 线程。它负责提交读请求、收取“读完了”的通知；调用 issue 的那一方只是把请求排进队列，再把它叫醒。源码注释说，这样每次读文件约 11 微秒的系统调用开销，就不再落在主循环上。队列和状态由一把互斥锁保护。代码事实[S11] 同时在路上的读请求默认最多 256 个：生成时每个 token 只要 16 个，读一大块提示词时才用得满。代码事实（ngram.hpp）

还有一个让人会心一笑的细节。有些固态硬盘闲置约 250 毫秒就进入省电状态，下一次读要多等 50–150 毫秒。生成时如果连着几轮都在行缓存里命中，硬盘就可能“睡着”。所以读取器有一个“保持清醒”的功能：一段时间没有读请求，就随便读一页表，让硬盘别睡着。生成程序默认会打开它。代码事实（ple_reader.hpp）这种“先发出去、过会儿再收”的异步思路，第 14 章会系统地讲。

11.6 动手：亲手制造一次冲突

本章两个模拟器分工不同。「n-gram 哈希」让你看清行号怎么来、撞车怎么发生；「行缓存」让你看清组相联和替换指针怎样工作。建议先在「行缓存」里跑一遍“冲突”，记下两个命中率，再换“热点”对比。

然后打开本章的交互实验「缓存轨迹与冲突」。用 16 个槽位、9 个落在同一组的奇数键，对比“全相联 LRU”和“八路轮换”。你还可以自己编访问记录：先猜命中率，再运行验证。注意，实验和模拟器都用“行号取余”来分组，好让冲突容易被制造出来；Strata 实际先搅拌行号再分组，不会这么容易扎堆。

做完后想一个问题：如果把 8 路改成 1 路（直接映射），同样的“热点”访问，命中率会怎样变？

记住这三点

  1. 每个 token 用最近 2 个和 3 个 token 做哈希（相乘、异或、取余），算出 16 个行号，从 28.8 GB 的表里取 16 行，拼成 2560 个数。表里不存键，撞车是允许的。
  2. 硬盘按 4 KiB 一页读：一行 90 字节也要读一整页，跨页的行读两页。真正的难点是 16 次随机读的延迟，不是带宽。
  3. 读过的行进 8 路组相联的行缓存，组满了按轮换指针替换。总容量够，也可能因为挤在一组里而冲突未命中。

常见误解：“28.8 GB 的表放在硬盘上，硬盘带宽一定是瓶颈。”

每个 token 只用 1,440 字节。就算 16 行全都没缓存、每行读一整页，每秒生成 90 个 token 也只读 64 KiB × 90 ≈ 5.9 MB，离常见固态硬盘每秒几 GB 的顺序读还差三个数量级。教学推演 真正要对付的是延迟：16 次小读要等多久、能不能和计算重叠。源码注释说得直白：这是延迟问题，不是带宽问题。代码事实（ngram.hpp）

深入一层：三种“查找”、文档与代码的出入、哈希的陷阱和验收指标

三种查找，不能画成一个框

Strata 里至少有三样东西带着“查找”或“缓存”的名字，正确性条件完全不同。n-gram 表查询是模型数值计算的一部分：它依赖序列历史，读的是训练好的表行，取错一行就是算错。prompt lookup 草稿从前文里已经出现过的文字猜接下来的几个 token（最多 5 个），猜得对不对，最后还要大模型验证。上游报告[S02] 专家缓存在默认配置下只决定某个专家的权重此刻在不在显存，不改变算什么（第 12 章）。三者名字相近，坏了的后果完全不同：第一种坏了输出变错，第二种坏了只是变慢，第三种坏了可能“看起来对、其实错”。

PLE 用到的两个历史 token 是序列状态的一部分，还有一段卷积式的历史缓冲。代码事实[S13] 它们要随对话保存和恢复，不是随手可丢的日志。

注释、文档和代码对不上的地方

ple_reader.hpp 开头的注释说行缓存用“clock 淘汰”，而 ple_reader.cpp 里写的是每组一个轮换指针，没有 clock 算法需要的“最近用过”标记位。代码事实[S11] 没有标记位的 clock 退化成按顺序轮换，所以两者效果一样，但读代码时要以实现为准。

另一处：上游文档说这张表“通过操作系统缓存读取”。上游报告[S02] 而当前代码的默认模式是直接读取，注释明确要求这张表不占用内存，包括操作系统的文件缓存；内存映射只作为对照组保留，另有一个把整张表锁进内存的选项。代码事实（ngram.hpp、direct_file.hpp）文档往往落后于代码，遇到这种出入，要追到默认配置和调用路径上去确认。

哈希里每个错误都“看起来对”

ngram.hpp 的注释列出了一串陷阱：用加法代替异或；用“与上 2 的幂减 1”代替取余（模数不是 2 的幂，两者是不同的函数）；“对话结束”符的截断要向更早的位置传播；缺失的前文是 −1，而编号 0 是一个真实的 token；当前 token 自己是结束符时，不截断它自己的上下文；前文数组是“旧的在前”，读反了方向依然能算出合法行号。代码事实（ngram.hpp、src/kernels/ngram.cpp）每一种写错，算出的行号都在合法范围内，范围检查抓不住，只能拿独立实现的“标准答案”逐项比对。

还有一个偏移量陷阱：表的数据不是从文件第 0 字节开始的，前面有文件头。从 0 开始读，会读到“头部 ＋ 错位的行”，解码出来依然是看似合理的数字。所以读取器从真正解析过的文件头里取偏移，并检查这张表恰好填满文件的剩余部分。代码事实（ngram.hpp）

开线程不等于变快

把系统调用挪到 I/O 线程，主循环里的“提交时间”会变短，但请求本身不一定变快。如果模型马上就要用这行数据，等待只是换了个地方。要看三件事的时间线：什么时候提交、什么时候完成、什么时候被消费。只有在提交和消费之间有独立的活可干，才有真正的收益。

验收看哪些数

读取器的统计里有：请求的行数、行缓存命中数、同页合并掉的行数、发出的读请求数、读取的字节数、collect 阻塞的时间、每次读的延迟（保留最近 65,536 次，用来算分位数）。代码事实（ple_reader.hpp）评估一次改动，至少要报告：行命中率、读取页数、有效字节与实际读取字节之比，以及每个 token 等待时间的 p50 和 p95。只报顺序读带宽，解释不了稀疏随机查表的性能。读取器还支持“故意延迟每次读”的故障注入，用来验证慢盘下系统是等待，而不是悄悄用了没读完的数据。
