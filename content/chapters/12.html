接着第 10 章往下问

第 10 章说过：Strata 把最常被选中的专家放在显存里，其余的留在内存，由 CPU 就地计算；话题变了，显存里的专家也跟着换。听起来很顺。可真要写代码，问题一个接一个：开局先放谁？显存一共几千个位置，48 层怎么分？什么时候换、换谁？换到一半时，正好有 token 要用这个专家，怎么办？

这些都是缓存的老问题。这一章用 Strata 的专家缓存，把它们一个个讲清楚。

一句话：专家缓存开局按历史频率填满，每层分一段槽位；之后每 4 轮按“衰减计数”换掉冷门、换进热门；换的时候先撤表项、等字节拷贝完，再登记，绝不让 GPU 读到半新半旧的槽位。

12.1 命中率：先说清楚分母

缓存好不好，第一个看的数是命中率：要用的东西有多大比例已经在缓存里。对专家缓存来说，“命中”就是被选中的专家正好在显存里，GPU 直接算；“未命中”就要 CPU 从内存里读这个专家的 1.38 MB 来算。

上游在开发这个缓存时测过：显存放 4,105 个专家时，单个专家的命中率是 0.6447，十折留出评估的区间是 0.6110 到 0.6750。上游报告[S05] 同一段注释还记了另一个数：一层的 10 个专家全部命中的比例，只有 0.0456。上游报告[S05] 两个数都叫“命中率”，差了十几倍，因为分母不同，见图 12-1。

这件事直接影响设计。如果只有“整层全命中”才能走某条快路径，那 64.5% 的专家命中率帮不上忙：这样的层只占 4.6%。上游注释据此得出结论：不能按“整层”分组设计 GPU 内核，要允许同一层里一部分专家在 GPU、一部分在 CPU。代码事实[S05]

命中率与工作集

命中率 = 命中次数 ÷ 访问次数。看起来简单，难在“一次访问”怎么数：按 token 数、按“层 × token”数、按专家调用数、按去重后的专家数，还是按字节数？分母一换，数字可以差出一个数量级。报命中率时，还要写清缓存多大、冷启动还是预热后、在什么数据上测。

一个有用的概念是工作集：最近一段时间里真正用到的东西的集合。比如最近 100 个 token 里，第 7 层一共选过 60 个不同的专家，这 60 个就是第 7 层此刻的工作集。缓存装得下工作集，命中率就高；装不下，就会刚换进来又被挤出去，反复搬运，这叫颠簸。

工作集会随时间漂移。写代码时常用的专家，和写散文时常用的不一样。所以缓存要回答两个问题：现在的工作集是谁（统计），以及怎样跟上它的变化（替换策略，见 12.4）。

延伸阅读：维基百科：工作集 · Wikipedia: Working set · OSTEP 第 22 章：换页策略

12.2 开局放谁：按历史频率排一张名单

最省事的开局是“先来先占”：运行起来以后，前几千个被选中的不同专家依次占位，满了就不再变。问题在于，开头碰到谁，全凭这次对话的第一段提示词。上游测过，这样的命中率只有 0.4864。上游报告[S05]

Strata 的做法是事先准备一份专家档案（profile）：在一大段访问记录上统计每个（层，专家）被选中的频率，从高到低排成名单，开局照名单填满显存。同样 4,105 个槽位，留出评估的命中率是 0.6447。上游报告[S05] 见图 12-2。

注释特别强调了一点：名单从文件读入，好处是可以“用这份提示词做名单，在另一份提示词上打分”，这才知道它能不能推广。代码事实[S05] 用同一段记录既排名单又打分，等于开卷考试，分数偏高。注释提到，README 曾公布过 0.6573，那是“在样本内”测出来的数；0.6447 才是留出评估。上游报告[S05]

学过机器学习的同学：这就是训练集和测试集要分开。缓存策略里的“统计热门”也是一种拟合，同样会过拟合。

12.3 别让前几层抢光：每层一段槽位

槽位怎么在 48 层之间分？上游踩过一个很有教学价值的坑。早期的准入规则是：所有层共用一个计数器，按到达顺序发槽位，发完为止。一个 token 从第 0 层往后走，每层选 10 个专家；256 个槽位，大约走到第 26 层就发光了。后面的层永远拿不到槽位，整个运行期间缓存只在前面几层起作用。代码事实[S05]

注释里的数字很扎眼：用 256 个槽位跑，命中 1,781 次、访问 60,000 次，命中率 2.97%；而在同一份路由记录上估算，每层给 8 个槽就能到 21.4%，每层 64 个能到 70.4%。注释的结论是：缓存从来不缺容量，缺的是公平的分配。上游报告[S05]

修法很直接：打开按层准入后，第 l 层只能用第 l·q 到 (l+1)·q 的槽位，q 是总槽位数除以层数，最后一层拿余数。代码事实[S05] 这条修复只改“谁能用哪个槽”，不改别的。这里的教训比修法更重要：命中率低，不一定是缓存太小；先看分配是不是和访问顺序缠在了一起。

12.4 热门会变：LRU、LFU 和带衰减的计数

名单只管开局。聊着聊着，话题变了，热门专家也变了。缓存要跟上，就得决定“换谁出去”，这叫替换策略。先看几种经典做法。

缓存替换策略：LRU、LFU 及其他

缓存满了，新东西要进来，必须请一个旧的出去。请谁？

  • OPT（最优策略）：请“下一次被用到最晚”的那个出去。它是理论上的最好成绩，但要预知未来，只能拿来当参照。
  • FIFO（先进先出）：谁最早进来就请谁出去。简单，但会把常用的老东西也赶走。第 11 章的轮换指针就是每组一个 FIFO。
  • LRU（最近最少使用）：请最久没被用过的出去。理由是“最近用过的，很可能马上还要用”。它反应快，但怕“一次性扫过”：一串只用一次的冷门数据，就能把热门的全挤掉。
  • LFU（最不经常使用）：请累计次数最少的出去。它不怕偶尔的冷门数据，但记性太好：过去攒下大次数的老热门，换了话题也赖着不走。
  • CLOCK（第二次机会）：给每格一个“最近用过”标记，指针转一圈，碰到有标记的就清掉标记、放它一马，碰到没标记的才换掉。它用很小的开销近似 LRU，操作系统换页常用它。

LFU 的毛病有个经典补丁：让次数随时间衰减，比如每隔一段时间所有次数乘 0.7。这样旧功劳会慢慢褪色，新热门有机会超过老热门。这类做法常叫“老化”（aging）。

延伸阅读：维基百科：缓存文件置换机制 · Wikipedia: Cache replacement policies · OSTEP 第 22 章：换页策略

Strata 的专家缓存选的正是“带衰减的计数”。规则藏在生成程序里，几个数字都能对上：代码事实（src/program/generate.cpp、src/core/expert_source.cpp）

  1. 记次数：每层每选中一个专家，它的计数加 1，不管它在不在显存里。
  2. 定期调整：默认每 4 轮调整一次。一轮就是大模型做一次前向，验证一批草稿，产出一个或几个 token。
  3. 够格才换：在同一层里，不在显存的专家计数至少到 2，才算候选；候选要比显存里最冷的那个多出 1.5 以上，才真的交换。一次调整最多换 96 个。
  4. 全体褪色：调整完，所有计数乘 0.7。

乘 0.7 意味着什么？一个专家如果不再被选中，它的计数每调整约 2 次就减半（0.7² ≈ 0.49）。反过来，某一次的“被选中”，算上后面所有的褪色，总共贡献 1 + 0.7 + 0.49 + … = 1 ÷ (1 − 0.7) ≈ 3.3。源码注释正是用这个和来说明累计“热度”。教学推演 图 12-4 画出了褪色的过程。

这套规则和 LRU、LFU 比，到底好在哪？下面的模拟器把一层缩小成 24 个专家、每个 token 选 4 个、显存只放 6 个，三种策略看同一串路由。第 30 个 token 起话题改变；你还可以插入一段“冷门插曲”。

模拟器只有一层、24 个专家，数字不能直接搬到 Strata 上。它想让你看到的是性格：LRU 灵敏但容易被冷门数据冲乱；LFU 稳但不肯忘；衰减计数用“定期调整 ＋ 门槛 ＋ 褪色”在两者之间折中。为什么只在每 4 轮调整一次，而不是每次未命中就换？每次交换都要经 PCIe 搬 1.38 MB，频繁换进换出本身就有代价；设两道门槛（够 2 次、领先 1.5），也是为了不为一点点差距去搬运。教学推演

这几个数是引擎的默认值。最划算的取值，其实因机器而异。安装程序可以做一次校准（--calibrate）；v0.1.40.2 起，它也会在这台机器上试两组更积极的设置：每轮都调整，每次最多换 80 或 160 个，计数每次只乘 0.97。比默认快 3% 以上，才保留。代码事实（tools/calibrate.py）上游在一台用 DDR3 内存的 Xeon E5-2673 v3 上测到，每轮最多换 160 个，比默认快 7.9%。上游报告 CPU 读未命中的专家越慢，多搬几个专家就越划算。

Strata 里其实有好几个缓存，各用各的策略，见图 12-6。

长上下文的 KV 页缓存（第 17 章细讲）在显存里放一部分页，每一步由 GPU 上的一个线程块用 CLOCK 扫描挑出要换掉的槽位，再从锁页内存里把缺的页拷进来。代码事实（include/strata/kernels/kv_stream.hpp）上游文档说，上下文在 64K 及以上、内存又放得下时，安装程序会打开它。上游报告[S03]

12.5 换的时候：先拷贝，再登记

决定了换谁，还要真的换。这一步最容易出“看起来没问题”的错。专家缓存有两样东西：一张驻留表，记录每个（层，专家）在哪个槽位，或者不在显存；还有槽位里真正的字节。GPU 只看表：表上说 #112 在槽位 5，它就去槽位 5 读。

拷贝是异步的：发起拷贝的函数立刻返回，字节还在 PCIe 上走（第 14 章细讲）。如果先在表上登记“#112 在槽位 5”，再开始拷贝，这中间正好有 token 选中 #112，GPU 就会读到一半新、一半旧的字节。下面的模拟器把这一过程放慢了：

Strata 的自适应缓存就是这么做的：交换一发起，被换出的专家马上在表上标成“不在显存”，源码注释写着“此刻起被逐出：期间由 CPU 计算它”；被换入的专家先记在“待定”名单里，拷贝之后记录的完成事件到了，才写进表。代码事实（src/program/generate.cpp）

还有一个更隐蔽的版本。上游曾用“非阻塞地查询一下拷贝完成没有”来决定是否登记：完成了就登记，没完成就下次再说。结果同一个专家这一轮由 GPU 算、下一轮由 CPU 算，全看拷贝快慢；而 GPU 和 CPU 的舍入方式不同，同一个提示词两次运行的答案就可能不一样。现在默认改成等拷贝落地再开始下一轮：哪一轮第一次在 GPU 上算新专家，只取决于轮数。v0.1.40 起还有两个可选开关：一个让交换晚一轮再生效，结果仍可复现；另一个在后台线程里推进交换，不让某一轮等整批拷贝，但两次运行不再逐位相同。代码事实（src/program/generate.cpp）[S03]上游文档也提醒：要得到逐字节相同的重复结果，需要关掉自适应交换等几个开关。上游报告[S03] v0.1.41 起，在单张 NVIDIA 卡上还要设 STRATA_PREFILL_CPU_SHARE=0，关掉读短提示时的 CPU 分担（第 16 章）：它让 CPU 算一部分专家，结果的最后几位会变。上游文档里那份开关清单还没写上它。代码事实（src/prefill/prefill.cpp）

低内存的“驻留”模式又多一层约束：内存里只存显卡没有的那些专家。换出的专家，字节要先从显存拷回内存里，占住换入专家腾出的位置，内存这份副本才能继续“恰好补齐”显卡缺的部分。v0.1.40 起有一个可选开关，让拷回用的缓冲区直接顶替换入专家的位置，省掉内存里的再一次复制。上游报告[S03] 接口里专门有一个函数做这件事。代码事实[S06]

学过操作系统的同学：这和换页时“先把页表项设为无效、写回完成后再复用页框”是同一个道理：映射关系的每次改变，都要等它所依赖的数据真正到位。

怎样证明槽位里装的就是表上说的那个专家？缓存提供了一个逐字节比对的函数：把槽位读回主机，和内存里的原件一字节一字节比。注释说，这是“唯一能证明缓存装着它声称的专家的东西”；表的索引对、字节错，会产出一个看似合理的 token，而这正是这个项目吃亏最多的一类错误。代码事实[S05]

12.6 动手：让三种策略赛跑

先在「三种替换策略赛跑」里跑完 60 个 token，记下三条命中小格在第 30 个 token 之后的样子；再打开“冷门插曲”重跑，看谁的槽位被冲乱。然后到「一次换入换出」里，用错误顺序走一遍，体会“标签对、字节错”为什么最危险。

最后打开本章的交互实验「缓存轨迹与冲突」。在同一串访问上比较 LRU、LFU、FIFO 和八路轮换。实验里的策略都是教科书版本，不是 Strata 的衰减计数；它让你练习的是：同一个容量，策略不同，命中率能差多少；以及怎样构造一串访问，专门让某种策略吃亏。

记住这三点

  1. 命中率先说分母：按专家算 64.5%，按“整层全命中”算只有 4.6%。评估名单要用没见过的记录。
  2. 开局按频率名单填满，每层分一段槽位；全局先到先得会让前几层抢光槽位，命中率掉到 3%。
  3. 之后默认每 4 轮按衰减计数交换（够 2 次、领先 1.5、全体乘 0.7）。交换时先撤表项、等拷贝完成再登记。

常见误解：“命中率低，说明缓存太小，加显存就好。”

不一定。上游的早期版本用 256 个槽位只命中 2.97%，同一份访问记录上，每层分 8 个槽就能到 21.4%。上游报告[S05] 容量没变多少，变的是“槽位给谁”。命中率低时，先查分配是否公平、策略是否和访问顺序纠缠、统计口径对不对，再谈加容量。

深入一层：历史注释、正确性不变量与评估方法

“缓存从不淘汰”和“缓存会换”怎么同时成立

expert_cache.hpp 开头写着：这个文件只是槽位存储和驻留表，自己不做任何计算；GPU 在验证窗口的分组内核和读题路径里算它缓存的专家，其余的交给 CPU 池。括号里补了一句：这段话最初写于“还没有代码用这些槽位、--expert-cache 默认是 0”的时候，现在安装程序的配置用 auto。代码事实[S05] v0.1.38 的版本还写着“打开缓存只会更慢”，直到 v0.1.39 才改掉，这是注释落后于代码的一个实例。它的准入函数也明说“从不淘汰”，因为淘汰策略要靠实测决定，放一个占位策略会让下游所有设计都按错误的命中率来定。代码事实[S05] 这些注释写于开发早期。当前的引擎确实会换专家，但换的动作不在这个类里：生成程序按衰减计数挑出交换对，直接把新专家的字节拷进旧专家的槽位，再改驻留表。v0.1.39 给这个类加了一个小函数 replace，在拷贝完成后把同一层旧专家的槽位转记到新专家名下；目前只有新加的多卡远程专家路径调用它。代码事实[S05] 读代码时要分清“这个类不做什么”和“整个系统不做什么”。

一次交换必须保持的条件

  • 表上任何一个有效项，都指向已经完整填好的槽位。
  • 正在被计算读取的槽位，不能被覆盖。
  • 换出后，旧的映射立即失效；换入的映射在字节落地后才生效。
  • 不同大小的专家块（有的量化格式每层不同），不能越过槽位边界；槽位一旦按某层的大小分好，就不挪给别的层。代码事实[S05]
  • 驻留模式下，换出专家的字节先拷回内存，内存副本才能继续“恰好补齐”显卡缺的部分。

同步还是异步：开机填充为什么要阻塞

平时的填充是异步的，因为拷贝和随后读它的内核排在同一条流上，顺序天然成立。开机按名单填充时没有这种保证：源数据在普通内存里，逐字节校验又在另一条“传统流”上读回，而传统流和非阻塞流之间没有顺序关系。第一版用了异步填充，结果校验报告“槽位 0 第 0 字节就和原件不同”，拒绝运行。注释说：这是校验在尽职。于是有了专门的阻塞版填充。代码事实[S05]

名单能存下来

上游文档说，引擎 0.1.36 起有一个可选功能：把自适应缓存学到的排名存成新名单，下次启动从这里开始。排序规则是：此刻在显存里的排前面，其次按这次运行累计的热度，再按原名单的位置。代码事实[S05] 写文件时先写到一个临时文件，写完再改名覆盖，所以进程崩溃也不会留下半个文件。代码事实[S05]

怎样公平地比较策略

报告一个缓存策略，至少写清：缓存总容量和每层分配、命中率的分母、冷启动还是预热后、访问记录从哪来、名单和评估是否用了不同的记录、换话题后多久恢复、每秒换入换出多少字节。只说一句“命中率 70%”，既不能复现，也不能拿来估算显存预算。
