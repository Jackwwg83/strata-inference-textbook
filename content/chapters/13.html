一件反直觉的事

Strata 让显卡和处理器同时干活。听上去像请了两个工人，速度该快一大截。可上游的开发记录里有这样一件事：他们把 CPU 每个 token 要做的专家计算，从 18.2 毫秒砍到了 10.2 毫秒，CPU 确实少干了将近一半。结果呢？生成一个 token 的总时间，纹丝不动。上游报告（include/strata/core/hit_hook.hpp 注释）

省下的 8 毫秒去哪了？这一章从 CPU 和 GPU 的性格讲起，讲到“谁等谁”，最后落在一个词上：关键路径。

一句话：算专家，大头是读字节，所以 CPU 就地算内存里的专家；同一层里，命中的专家归 GPU、没命中的归 CPU，两边同时算；但层与层之间有数据依赖，只能排队，所以 CPU 的活藏不住，只能靠缓存把它变少。

13.1 两种处理器，两种性格

CPU 像几位全能的老师傅，GPU 像一个上千人的流水线车间。老师傅人少，但每人都能独立处理复杂的、走一步看一步的活；车间人多，最擅长的是“所有人同时做同一个简单动作”。图 13-1 是一个示意。

CPU 与 GPU：SIMD 和 SIMT

CPU（中央处理器）的核心不多，上游测速机器的 Ryzen 5 7600 有 6 个。上游报告[S03] 每个核心都很“聪明”：有大缓存、能预测分支、能乱序执行，适合控制流复杂的程序。CPU 也能一次算多个数：一条 SIMD（单指令多数据）指令，同时对一排数做同一种运算。AVX-512 指令的寄存器有 512 位，一次能装 16 个 32 位浮点数，也就是 16 条“车道”。Strata 的 CPU 专家内核就用 AVX-512 或 AVX2 写成。上游报告[S02]

GPU（图形处理器）把芯片面积花在大量简单的计算单元上，常见的游戏显卡就有几千个。它的执行方式叫 SIMT（单指令多线程）：NVIDIA 的 GPU 把 32 个线程编成一组（一个 warp），同一组同时执行同一条指令，各自处理自己的数据。[R01] 它还配了带宽高得多的显存：RTX 5070 的显存约 672 GB/s，而双通道 DDR5-5200 内存约 83 GB/s（第 1 章有对比）。

两者的共同点是：同时做很多份互不相干的同样工作，才能发挥出力气。如果每一步都要等上一步的结果，车道再多也只能一格一格来。下面的模拟器让你亲眼看到这一点。

延伸阅读：维基百科：单指令流多数据流 · Wikipedia: Single instruction, multiple threads · NVIDIA CUDA Programming Guide

学过计算机组成的同学：SIMD 就是向量指令（x86 的 SSE、AVX，ARM 的 NEON）；GPU 的 SIMT 可以理解成“硬件自动把一组线程打包成一条宽向量来执行”，分支走向不同时，组内线程要分批执行。

13.2 CPU 凭什么也能算专家：大头是读字节

GPU 算得快那么多，为什么 Strata 敢让 CPU 算专家？因为算一个专家，难的不是算，而是读。一个专家 1.38 MB，每个参数只乘加一两次，计算单元大部分时间都在等数据从内存送过来。上游的 CPU 专家池注释写得很直接：专家内核受内存带宽限制，6 个核心实测约 42.55 GB/s，速度几乎和核心数成正比。代码事实（include/strata/kernels/cpu/pool.hpp）

既然瓶颈是读字节，那就让字节少走路。第 10 章算过：把没命中的专家经 PCIe 搬到显卡上，一个 token 光搬运就要 10 毫秒以上。反过来，把“活”送到数据身边，要传的东西就少多了，见图 13-3。

接口是这样约定的：每一层，GPU 把归一化后的输入、选中的 10 个专家编号和它们的权重交给 CPU 这一侧，等着拿回 10 × 2560 个数。代码事实[S06] 一个数 4 字节，输入约 10 KB，结果约 100 KB，比 13.8 MB 小了一百多倍。教学推演

CPU 这一侧是一个专家池：每个物理核心一个工作线程，第一个核心默认留给主循环。v0.1.40 起，可以用 --host-core last 把主循环挪到最后一个物理核心，这是为 Windows 准备的：它通常把显卡的中断送到第一个核心，在那里空转等待的主循环会被打断。每层的 10 个专家分给这些线程同时算；主机要把 10 份结果都收齐、加起来，下一层才能开始，所以每一层都是一道“栅栏”。代码事实（pool.hpp）

学过操作系统的同学：线程绑在物理核心上，而不是绑在逻辑处理器上。一个物理核心的两个超线程共享同一套执行单元和缓存，两个读内存的线程挤在一起，带宽会减半。源码注释还记录了一次实测：主循环线程没有固定在自己的核心上时，专家池从 36.32 GB/s 掉到 26.9 GB/s。上游报告（pool.hpp 注释）

按上游开发期的测量，在专家缓存出现之前，CPU 每个 token 要读 663.6 MB 专家数据，按约 40 GB/s 算要 16.2 毫秒，而当时一个 token 约 53 毫秒。上游报告[S05] CPU 这一份，是整台机器上最大的一笔开销。

13.3 一层之内：命中归 GPU，未命中归 CPU，两边同时

有了专家缓存，一层里的 10 个专家分成三拨：代码事实（src/core/expert_source.cpp、src/program/generate.cpp）

  1. 在显存里的（命中），GPU 直接算。
  2. 没命中的里，按一个比例挑出一部分，GPU 经 PCIe 从锁页内存读过去算。这个比例默认是：Q2_0 模型 0.2，其他原生格式 0.55。
  3. 剩下没命中的，CPU 就地算。

顺序很讲究：GPU 那一份先决定、先发布，让 GPU 先动起来，CPU 再开始自己的那份。代码事实（expert_source.cpp 注释）上游文档提到，把 PCIe 份额设成 0，所有未命中都回到 CPU，生成速度会变慢。上游报告[S03]

下面的模拟器把一层画成时间线。数字是教学推演：每个专家 1.38 MB，CPU 按 40 GB/s、显存按 672 GB/s、PCIe 按 63 GB/s 读；注意力加路由按 0.25 毫秒、合并按 0.05 毫秒假设。

上游第一版就栽在“谁先谁后”上。当时 GPU 算命中的那一步，被放在了 CPU 专家池之后：CPU 的活确实少了一半（18.2 降到 10.2 毫秒），可 GPU 的那一半只是从“旁边”挪到了“后面”，整条路径一点没短。后来改成两步：GPU 先在一块单独的缓冲区里开始算命中的专家，CPU 同时算未命中的；CPU 的结果送上 GPU 后，再把两份加在一起。多一块缓冲区、多一次相加，换回了真正的并行。上游报告（hit_hook.hpp 注释）你可以在模拟器里关掉“两边同时算”，重现这件事。

13.4 层与层之间：依赖把并行挡住了

一层之内能并行，那能不能让 CPU 还在算第 l 层时，GPU 先开始第 l + 1 层？不行。第 l + 1 层的输入，就是第 l 层合并完 10 个专家之后的结果。这条线一环扣一环，见图 13-5。

数据依赖与关键路径

两个计算之间，如果后一个要用前一个的结果，就叫有数据依赖（更准确地说是“先写后读”依赖）。有依赖的两步只能先后做；没有依赖的，才可能同时做。

把所有计算画成一张图：每个计算是一个点，依赖是一条箭头。从起点到终点，最长的那条箭头链叫关键路径。整件事最快也要这么久，不管你有多少个工人。想变快，只有两个办法：缩短关键路径上的某一步，或者把关键路径上的某一步挪到旁边去，和别的步骤并行。

反过来，缩短不在关键路径上的步骤，一点用都没有。开头那件事就是这样：CPU 少干了 8 毫秒，可那 8 毫秒挪出去以后，GPU 的那份顶了上来，关键路径的长度没变。这和第 5 章的 Amdahl 定律是同一个道理：只优化一部分，整体的收益受其余部分限制。

延伸阅读：维基百科：关键路径 · Wikipedia: Data dependency · Wikipedia: Critical path method

Strata 的源码把这件事写成了结论。每一层被拆成两张 GPU 计算图：前一张从注意力算到路由和共享专家，后一张负责合并专家结果、写回主干，要等 CPU 交回结果才能启动，这样第 l 层的专家结果才会配上第 l 层自己的路由权重。代价是：留给 CPU 和 GPU 重叠的时间，只剩共享专家那一小段。注释写道：每层一次的 CPU 专家池，藏不到一条严格串行的残差链后面。代码事实[S13]

缓存的注释给了数字：当时的流水线在 19.035 毫秒的 CPU 工作里只藏住了 1.055 毫秒，96% 都露在关键路径上，“因为残差链是严格串行的”。所以唯一的出路是少读字节：把一部分专家放进显存，让 CPU 只读没命中的。上游报告[S05] 这就是第 12 章专家缓存存在的理由。

13.5 怎样证明真的并行了

“CPU 和 GPU 都在忙”不等于“它们在同时忙”。图 13-6 的两种情况，两边的忙碌总时间一样，总耗时却差很多。

Strata 的会话代码专门数这件事：每一层，主机看到“门铃”（GPU 发出“路由选好了”的信号）时，GPU 的计算图是不是还在运行。还在运行，说明 CPU 有一段和 GPU 重叠的窗口；已经结束了，CPU 就是在 GPU 空闲时干活，整条流水线等于串行。这个计数器叫 rings_mid_graph，注释称它是“判断门铃是不是摆设”的那个诊断量。代码事实[S13]

注释还点破了它为什么必要：两种情况都能算出正确的 token，每层的耗时也一样，区别只表现为“重叠什么都没藏住”。另一个计数器记下从启动计算图到看见门铃的毫秒数，CPU 能用的窗口就是“层的时长减去它”。代码事实[S13] 配置里写着“开启重叠”只是意图，事件时间线才是行为。

13.6 动手：找平衡点

先用本章的「一层之内」模拟器：命中率拖到 0%、再到 65%，看关键路径从 CPU 换到哪里；关掉“两边同时算”，重现上游第一版的教训；按“设为最佳份额”，看两条分支怎样一样长。再去「一次算 16 个」把三种算法都跑一遍。

然后打开本章的交互实验「CPU / GPU 工作分配」。它只有两条分支：CPU 和“经 PCIe 交给 GPU”。改变两边的有效速率和分工比例，找出总时间最短的那个比例。实验任务：把 PCIe 分支的有效速率减半，解释为什么最佳分工不再是“一人一半”。注意，实验和模拟器都假设两条分支互不抢资源；真实机器上，CPU 读专家和 PCIe 读锁页内存，用的是同一条内存带宽。

记住这三点

  1. 算专家的大头是读字节。让 CPU 就地算内存里的专家，过 PCIe 的只有 10 KB 输入和 100 KB 结果。
  2. 同一层里，命中的专家归 GPU、一部分未命中经 PCIe 归 GPU、其余归 CPU，两边同时算，汇合时等慢的一边。
  3. 层与层之间有数据依赖，48 层是一条关键路径。CPU 的活藏不住，只能靠缓存减少；优化不在关键路径上的步骤，没有用。

常见误解：“CPU 和 GPU 一起算，速度就能翻倍；CPU 少干一半活，总时间就少一截。”

只有被省下的那部分在关键路径上，总时间才会变短。上游把 CPU 的活从 18.2 毫秒减到 10.2 毫秒，token 一点没快，因为 GPU 的那份被排到了 CPU 后面。上游报告 同样，“GPU 利用率 100%”也说明不了什么：它可能在空转等待，也可能在算一份本可以并行的活。要看的是关键路径和事件时间线。

深入一层：分工公式、它为什么不准，以及并发里的坑

两条分支的分工公式

设剩下要算的专家数据量为 D，比例 f 交给“经 PCIe 的 GPU 分支”，其余交给 CPU。把 CPU 分支的持续处理能力折算成每秒 Bc 字节，PCIe 分支折算成每秒 Bp 字节，假设两者互不影响：

T(f) ≈ max((1 − f)·D / Bc, f·D / Bp) ＋ T合并

两条分支一样长时最快，解得 f = Bp ÷ (Bc ＋ Bp)。若 Bc = 40、Bp = 20，f = 1/3，而不是“一人一半”。教学推演 这里的 Bp 不是 PCIe 的标称带宽，而是包含这条分支全部代价的有效速率。

为什么真实的最优点不在这里

公式假设两条分支各用各的资源，可真实机器上它们会抢：CPU 读专家和 GPU 经 PCIe 读锁页内存，走的是同一组内存通道；PCIe 还可能同时在传长上下文的 KV 页；专家大小、同一专家在一个验证窗口里被几个 token 复用、GPU 启动开销、主机线程绑核，都会改变两边的有效速率。所以 Strata 的默认份额（Q2_0 为 0.2，其他原生格式为 0.55）来自实测，而不是这个公式。代码事实（generate.cpp）公式适合用来提出假设；调参要记录每条分支的完成时间、搬运字节和总时间，并在另一组任务上复验。

计算对了吗：时间对得上，结果却错了

hit_hook.hpp 记录了一个教科书级的并发错误。第一版的“GPU 先算命中”这一步，读的是专家池回调里才决定的命中名单，而那个回调在它之后才运行。于是它读到的是上一层的名单，把上一层的专家算进了这一层的位置。程序照常产出 token，耗时也正常，可和标准答案比，平均 KL 散度从 9.69×10⁻² 涨到 1.03，最可能的 token 的一致率从 0.867 掉到 0.333。修法是让这一步直接接收本层路由器发布的编号。代码事实（hit_hook.hpp）

线程池里的一场竞态

CPU 专家池等一批任务完成时，最初只等“完成计数 = 任务数”。可在显存很大的卡上，大部分专家都命中，工作线程常常睡着；一批任务太小，睡着的线程还没醒，这批就做完了。醒来的线程可能从下一批里抢任务，把同一个任务做两遍，或者在主机清零之后才加计数，于是“完成计数 = 任务数”永远不成立，GPU 一直等下去。修法是给每次领任务带上批次号：任务指针是一个 64 位字，装着“批次 | 任务数 | 序号”，领任务用比较并交换，只有批次对得上才能成功，迟到的线程自然领不到。代码事实（pool.hpp）上游文档把这次卡死记作 issue #29，在引擎 0.1.12 修复。

注释和设计对不上的地方

session.hpp 后半段有一段较早的注释，说“重叠来自一层的延迟：专家池的结果由下一层消费”。代码事实（session.hpp）而前面关于两张计算图的注释说的正相反：为了不让第 l 层的专家配上第 l + 1 层的路由权重，合并必须留在本层。代码事实[S13] 遇到这种矛盾，以当前的调用顺序和测试为准。

GPU 和 CPU 算同一个专家，最后几位可能不同

GPU 和 CPU 的内核舍入方式不同。哪个专家由谁算，取决于缓存状态和 PCIe 份额，所以同一提示词重复运行，答案可能不逐字节相同。上游文档说，想要可重复的结果，可以把 PCIe 份额设成 0 等几个开关，代价是生成变慢。上游报告[S03]
