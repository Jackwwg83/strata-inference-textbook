一个奇怪的计时

Strata 的源码注释里记着一件怪事：有个叫 gdn_gate 的 GPU 小程序，一共只处理 48 个数，每次却要花 28 微秒。作者的评语是：这么小的 kernel，不可能真的执行 28 微秒。代码事实[S13]

48 个数，GPU 一眨眼就算完了。多出来的时间花在哪？答案是“挂号”：CPU 每让 GPU 跑一个小程序，都要先走一遍提交手续。如果一个一个地提交，生成一个 token 要提交两千次左右。这一章讲 GPU 怎样分活，挂号费从哪来，以及 Strata 怎样把两千次挂号压到几十次，甚至一次。

一句话：GPU 上的小程序叫 kernel，每启动一次都有几十微秒的固定开销。Strata 用两招省掉它：把几个 kernel 融合成一个，把整层的 kernel 录成 CUDA Graph 一次提交。代价是图会把参数录死，所以每步都变的“位置”必须放进一块固定地址的显存里。

15.1 GPU 怎样分活：线程、线程块和 warp

先想象一个大型阅卷现场。几万份试卷，每位老师批一份。老师们分成很多个考场，每个考场里再按 32 人一排坐好，一排人听同一声口令：“翻页”“看第一题”“打分”。口令相同，手里的卷子各不相同。

GPU 就是这样干活的。CPU 交给 GPU 的一段小程序叫 kernel（内核函数）。启动一次 kernel，GPU 就开出成千上万个线程，每个线程跑同一段代码，只是处理的数据下标不同。线程先分成若干线程块（block），一个块里的线程在同一个计算单元上运行，可以共享一小块高速存储。块里的线程再按 32 个一组排成 warp：同一个 warp 的 32 个线程同时执行同一条指令。[R01] 图 15-1 把这三层画在一起。

Strata 里到处是这种安排。比如第 17 章会讲到的 KV 换页，源码写的是“用一个 1,024 线程的线程块，扫一遍被选中的编号”。代码事实 又比如 GDN 层的递推，源码注释说每一行公式只涉及状态的某一列，列与列之间互不相干，所以“一个线程可以包下一整列，整步都不需要线程之间互相等待”。[S17]

GPU 编程模型：线程、线程块与 warp

直觉：CPU 像几位全能教授，每人能处理复杂的分支和判断；GPU 像几千名助教，每人只会照口令做简单的事，但人多。想让 GPU 快，就要把工作拆成成千上万份互不依赖的小任务。

定义：程序员写一个 kernel 函数，启动时指定“开多少个线程块、每块多少线程”。CUDA 的写法是 vecAdd<<<4, 256>>>(A, B, C)：4 个块，每块 256 个线程，共 1,024 个线程，各自用 threadIdx.x + blockDim.x × blockIdx.x 算出自己负责第几个元素。当前的 NVIDIA GPU 上，一个线程块最多 1,024 个线程；块里的线程按 32 个一组组成 warp。[R01]

一个具体数字：一个 warp 读显存时，如果 32 个线程读的是相邻地址，硬件能把它们合成很少几次内存事务，这叫合并访问。如果它们读的地址彼此隔得很远，就要拆成很多次事务，每次只用上一小部分字节。下一节的 Strata 例子会给出差距有多大。

和本章的关系：kernel 是 CPU 交给 GPU 的最小工作单位。kernel 越小、越多，“交接”本身的开销就越显眼。

延伸阅读：NVIDIA CUDA 编程指南：编程模型 · NVIDIA：CUDA C++ 入门（含 vecAdd 例子） · 维基百科：CUDA · Wikipedia: Thread block

学过计算机的同学：warp 就是 SIMT（单指令多线程）的执行单位：一条指令驱动 32 个线程，像 SIMD 的向量指令；但每个线程有自己的寄存器和程序计数器，可以走不同分支，代价是分支两边要轮流执行。第 13 章细讲 SIMD 和 SIMT 的区别。

15.2 相邻线程读相邻地址：数据怎么摆很重要

同样的数学，数据摆法不同，速度能差好几倍。图 15-2 对比了两种读法。

Strata 的 GDN 层吃过这个亏。融合版内核的注释写道：原来的写法让一个 warp 负责状态的一列，32 个线程沿着 128 行往下走；可状态按“行、头、列”存放，相邻两个线程要读的数据相距约 24.5 KB。结果每取一个 32 字节的扇区，只用上 4 个字节，每层花 47.6 微秒才搬完 6.3 MB 的状态。代码事实

改写后，一个线程块包下一个完整的头，512 个线程按“行组、列”排开，一行的 128 列正好是一次连续的 512 字节读取。代码事实 道理和图 15-2 一样：让相邻线程读相邻地址。GDN 的基础 kernel 也遵守这一条：状态按 (i, h, j) 存，j 变化最快，所以 i 固定时，一个 warp 沿着 j 读到的是连续内存。[S17]

数据摆法是个“免费”的选择：状态是运行时缓冲，不是模型权重，想怎么摆都行。但源码特意提醒，两种摆法索引的是同样三个数，一旦读写双方摆法不一致，程序照样跑，结果悄悄出错。[S17]

15.3 每启动一次 kernel，都要付一笔“挂号费”

回到开头的怪事。CPU 让 GPU 跑一个 kernel，要经过驱动程序：检查参数、打包命令、放进提交队列。这些手续在 CPU 上做，要花时间，叫启动开销。如果 kernel 本身只算几微秒，而手续要十几、二十微秒，GPU 就会算完一个、干等下一个。图 15-3 画出了这个“等”。

这不是假想。Strata 的注释直接下了结论：“这个引擎受启动开销限制，而不是受带宽限制。”GDN 层里每个 kernel 都测出约 0.028 毫秒，连只处理 48 个数的 gdn_gate 也一样，这正是这台机器上一次普通启动的开销。一个 GDN 层大约启动 19 次，一个完整的层块约 45 次。代码事实[S13] 注释没有写明测试用的显卡和驱动版本，下面这些数字只用来体会数量级。

算一笔账。另一处注释说，按 kernel 逐个启动，一个 token 要启动约 2,000 次；每次调用驱动的开销实测 10–22 微秒。代码事实 光是“挂号”，每个 token 就要 2,000 × 10 µs ＝ 20 毫秒到 2,000 × 22 µs ≈ 44 毫秒。换成速度，即使 GPU 一点不算，也最多每秒 23–50 个 token。教学推演

kernel 启动开销与算子融合

直觉：去医院看病，挂号要排队。如果每个小检查都要重新挂号，一上午就耗在挂号窗口了。两种办法：一是把几个检查合并成一次（算子融合）；二是让医生一次开好整套检查单，护士照单执行（CUDA Graph）。

定义：启动开销是 CPU 准备并提交一个 kernel 的固定成本，和 kernel 算多少几乎无关。设一个 kernel 计算要 w 微秒，提交要 L 微秒。逐个提交 n 个 kernel：如果 w < L，总时间约为 n × L + w，GPU 大部分时间在等；如果 w ≥ L，总时间约为 L + n × w，提交被藏在计算后面。教学推演

融合的好处不止少挂号：几个算子合成一个 kernel 后，中间结果可以留在寄存器或片上存储里，不用写回显存再读出来。代价是这个 kernel 更复杂，可能占更多寄存器，同时能在 GPU 上跑的线程变少。CUDA Graph 则不改 kernel 本身：它把一串操作和依赖关系录下来，以后一次提交、整串重放，省的是 CPU 端的提交成本。[R01]

和本章的关系：Strata 两招都用。下一节看具体数字。

15.4 两种省法：融合与 CUDA Graph

图 15-4 把两招放在一起对比：融合改的是 GPU 上跑什么，图改的是 CPU 怎么提交。

融合。Strata 有一批文件名带 fused_ 的内核。比如 fused_gdn_conv_l2 一个 kernel 顶替了原来的“卷积加 SiLU”和两次 L2 范数共三次启动；fused_gdn_ab 顶替了两次矩阵向量乘和两个逐元素 kernel。代码事实 混合残差的读取原来每次要六个 kernel，每个 token 走 96 次，融合后压到两个 kernel。代码事实

CUDA Graph。Strata 把每一层的 kernel 录成一张图。注释给出了实测：同一个层块的 43 个节点，逐个启动要 2.393 毫秒，录成图重放只要 1.585 毫秒，快了 1.51 倍，而且省下的“全是启动开销”。代码事实[S13] 另一处注释说得更直白：重放和逐个启动的算术完全一样，区别只是“约 2,000 次 kernel 启动变成 48 次图启动”。代码事实

还能再进一步吗？能。在 Windows 的显示驱动模式下，每次图启动本身也要约 0.3–0.4 毫秒；逐层循环每个 token 要启动 96 次图，实测一个 token 花 48.6 毫秒，而 GPU 上真正的 kernel 只占 12 毫秒。于是 Strata 又写了“整个 token 一张图”的版本，把 48 层全装进去。代码事实 图 15-5 把三个阶段排在一起。

为什么不一开始就录整个 token？因为每层中间要和 CPU 专家池交接：GPU 算到路由那一步，CPU 才知道该算哪些专家。Strata 最早把“一层”作为图的单位，就是为了让主机在层与层之间插手，让 CPU 专家池在 GPU 跑下一段时同时开工。[S13] 整 token 图改用一个 GPU 上的单线程 kernel 在设备端等主机写好标志位，主机不再调用驱动。代码事实

15.5 图会把参数录死：被冻住的位置

CUDA Graph 有个脾气：录制时，kernel 的参数被原样抄进图里，以后每次重放都用这份抄本。Strata 专门写了个小实验验证：图在重放时会重新读取输入缓冲里的数据，但不会重新读取 kernel 参数。代码事实

麻烦在于，有些参数每个 token 都变。最典型的是位置：这是第几个 token。如果把位置当参数传给写 KV 缓存的 kernel，录图时它是 0，之后每次重放都还是 0。下面的模拟器把这个过程放慢了，先选“按值录进图”，按单步走几个 token：

Strata 的 qsa.hpp 把这种错误的后果写得很具体：位置被冻住后，每个 token 都写进第 0 格，打分和选择只看 1 格，注意力始终只看一格历史。注释的评价是“比崩溃更糟”：输出是有限的、看起来合理的数，症状和“模型不会用上下文”一模一样，人们会去怀疑 KV 缓存、选择算法或权重，就是想不到图。代码事实[S18]

它的修法是“一块显存，而不是改六个函数签名”：把每步都变的四个数放进一个小小的 step 缓冲：

  • step[0] = pos：新 token 的位置；
  • step[1] = n_kv = pos + 1：缓存里有几格；
  • step[2] = n_bid：已经填满几个 4 格的块；
  • step[3] = width：这一步选几格，等于 min(n_kv, 2051)。[S18]

每个 kernel 从这块显存里读自己要的数，参数列表在每个 token 之间完全不变，整条 QSA 路径就能录成图。主机每步只做一次小拷贝，改写这块显存的内容。代码事实[S18] 四个数互相依赖，放在一处、由一段代码统一计算，就不会出现“改了 pos、忘了 n_kv”。

学过计算机的同学：这和 C 语言里“传值”与“传指针”的区别一模一样。图录下的是值，就永远是那个值；录下的是指针，每次解引用都能读到新内容。前提是指针指向的内存一直有效，这一点图自己检查不了。

同样的道理也用在采样上：温度、top-p 这些参数每个请求都可能不同，所以 Strata 把采样放在被录制的图之外，否则这些参数会被“永久烤进图里”。代码事实[S08]

15.6 动手：自己找出瓶颈和冻结

本章的两个交互图都可以当作小实验来做。

  1. 启动开销时间线（图 15-3）：先用默认参数播放，记下三种方式的总时间和 GPU 忙碌占比。再把每个 kernel 的计算时间 w 从 5 µs 慢慢拉到 40 µs，找出“图不再明显更快”的那个点。你会发现它大约出现在 w 接近 L 的地方：kernel 比提交还长时，提交开销自然被藏起来了。
  2. 被冻住的位置（图 15-6）：两种写法各走 4 个 token。对比 KV 格子和“注意力能看到几格”。再想一想：如果只检查“程序有没有报错、输出是不是有限的数”，能不能发现错误写法？

想在真 GPU 上验证，可以写一个只做 state[pos] = token 的小图，分别用 pos = 0、1、2 重放，检查三个位置是否都被写到。只看最后的返回值“成功”是不够的。

记住这三点

  1. GPU 用成千上万个线程干活：线程分成线程块，块里每 32 个线程组成一个 warp。让相邻线程读相邻地址，搬运才不浪费。
  2. 每启动一次 kernel 都有固定开销。Strata 每个 token 原本要启动约 2,000 次，它用融合减少 kernel 数，用 CUDA Graph 把提交压到每层一次，再到每个 token 一次。
  3. 图会把 kernel 参数录死。每步都变的值（位置、n_kv、选择宽度）必须放进固定地址的显存缓冲，由 kernel 每次去读。

常见误解：“CUDA Graph 就是把很多 kernel 合成一个大 kernel。”

不是。图只是把一串操作和它们的依赖录下来，重放时每个节点照旧是一个独立的 kernel，中间结果照旧写回显存。它省的是 CPU 端的提交成本。把计算真正合并进一个 kernel 的是算子融合，那需要重写 kernel。两者解决不同的问题，Strata 同时用了两种。[R01]

深入一层：融合的代价、录图的三条义务和验收方法

融合不是免费的

把几个算子写进一个 kernel，可以少启动几次，也少写读几次中间结果。代价是：kernel 里同时活着的变量更多，每个线程要占更多寄存器；寄存器总量固定，每个线程占得多，同时能驻留的线程就少，GPU 用来掩盖访存等待的“备用线程”也少了，这叫占用率下降。实现也更复杂，更难测试。所以融合要按测量结果来定。比如 Strata 的混合残差融合读取有几个变体，引擎在每张卡上先用随机权重跑一遍，只采用和基准写法逐位相同的最新变体。代码事实

教学算例：一个层有 20 次启动，每次主机开销 5 µs，光启动就约 100 µs。对每次只算几微秒的小算子，这很可观；如果每个 kernel 本身要算几毫秒，同样 100 µs 就只是零头。这些都是假设值，用来判断“值不值得优化”，不是实测。教学推演

录图的三条义务

graph.hpp 把三件事写成了接口的前提，每一条都来自一个专门的小实验。代码事实

  1. 等待必须调用驱动，不能只读内存。在 Windows 的显示驱动模型下，命令提交是攒批的。一个只读内存、不调用驱动的自旋循环，500 毫秒里转了 5,907,703 圈，kernel 却根本没开始跑；直到有代码调用了驱动，数据才翻转。所以等待改成反复查询一个事件，每次查询约 0.021 毫秒，它是“查询”，不是“同步”。
  2. 图会重读输入缓冲，不会重读 kernel 参数。8 次重放、每次换一份锁页输入，结果都跟得上；而参数在录制时被拷进节点，再也不读。凡是每步变化的值（位置、页表基址、token 编号）都必须是显存里的数据，不能是参数。
  3. 固定地址是调用方的责任。图持有的是图，不是内存。被录制的代码用到的每一块缓冲，都必须在录制前分配好，之后不能重新分配。

另外两条防御也值得学：录制结果是 0 个节点时直接报错，因为“一张什么也不做的图”会永远安静地重放，不产生错误也不产生输出；录制体里如果留下了 CUDA 错误，就放弃这次录制，不实例化一张坏图。代码事实

不要把一条执行路径当成全部

Strata 里同时存在好几种图：SessionGraphs 每层一张或两张（路由前一段、专家合并后一段）[S13]，投机解码验证窗口用的多 token 图（第 18 章）[S08]，整 token 的 TokenGraph，还有用来逐段计时的前缀图。 读到某个头文件写着“一层一张图”，不能据此断言整个引擎永远不录更大的图。源码里常常并存参考路径、调试路径、快速路径和按设备能力选择的实现；调用上下文和启用条件，是结论的一部分。这和编译原理课里“同一个函数有多个特化版本”是一回事。

验收：地址、数值、状态三件事

一项图优化至少要验证三件事：每步变化的值每轮都正确更新；被录制的地址在所有重放期间有效；重放后的状态和不录图的参考路径一致。一个典型的生命周期陷阱是：请求结束时释放了缓冲，却留着图对象给下一个请求用，下一次重放就会读写已释放的内存。

测试也要能“看见”错误。只用同一个提示词、同一个温度重复一遍，证明不了参数切换正确。更好的做法是：固定 logits，两个连续请求分别用贪心和高温度（或不同的固定随机数），与不录图的参考实现比较实际使用的参数和结果；第二个请求必须走一条与第一个不同、而且可以预测的分支。

进阶的 GPU 作业才需要性能分析器：记录启动时间、kernel 时间、寄存器用量和重放时间，再用端到端的 A/B 对比，判断局部优化是否真的缩短了关键路径。Strata 的注释里就有反例：某轮用不录图模式测出的分段计时，比录图后同一段工作的真实成本高了 4 倍，差点误导了优化方向。代码事实
