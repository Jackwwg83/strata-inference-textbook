同一台电脑，两种速度

Strata 的上游测速表里有两列数字。同一台装着 RTX 5070 的电脑，读一段 32K token 的提问，每秒能读 2,171 个 token；可写答案时，每秒只写 81.8 个。上游报告[S03]

同一个模型、同样 48 层、同一张显卡，为什么“读”比“写”快二十多倍？秘密只有一个词：批量。这一章讲清楚为什么一起算比一个个算快，一块切多大合适，以及怎样让搬运和计算同时进行。

一句话：写答案时每次只能算一个 token，权重读一遍只用一次；读题时提示词全都已知，可以几千个 token 一块算，权重读一遍供整块共用。Strata 每块最多读 8,192 个 token，并让下一层的专家在当前层计算时就开始搬运。

16.1 为什么读题比写答案快二十多倍

先看数字。图 16-1 是上游在同一台电脑上测的两种速度。

测试条件写在上游文档里：RTX 5070 12 GB 显卡，Ryzen 5 7600 处理器，64 GB DDR5-5200 内存，Windows，引擎 0.1.26，Q2_0 模型，写答案时开着投机解码。上游报告[S03]

差别来自两个阶段的本质不同。decode（写答案）时，下一个 token 要等上一个 token 选出来才知道是什么，只能一个一个来。prefill（读题）时，提示词里的每个 token 都已经摆在那里，可以一大块一起送进模型。注意，“一起算”不等于“互相偷看”：第 5 个 token 仍然只能看到前 4 个，模型的因果规则一点没变，变的只是计算怎么组织。

16.2 一起算为什么快：矩阵乘向量与矩阵乘矩阵

想象一位老师批改选择题。每改一份卷子，都要从柜子里取出标准答案，对完再放回去。如果一次只来一份卷子，大半时间花在取放答案上；如果一次来 50 份，取一次答案，对 50 份，再放回去，平摊下来几乎不花时间。

模型里的“标准答案”就是权重。每算一层，都要把这一层的权重从显存读进计算单元。图 16-2 把两种情况画在一起。

批处理：矩阵乘向量与矩阵乘矩阵

直觉：搬运和计算是两笔账。一个 token 一个 token 地算，每次都要把整份权重搬一遍，搬运成了大头；一批 token 一起算，搬运只付一次，计算却一点没少，于是“每搬一个字节做的计算”变多了。第 5 章讲过，这个比值叫算术强度，它决定了程序受带宽限制还是受算力限制。

定义：一层的权重是一个 m × n 的矩阵 W。一个 token 的输入是长度 n 的向量 x，算 W·x 叫矩阵向量乘（GEMV）：读 m × n 个权重，做约 2mn 次乘加。把 C 个 token 的向量排成一个 n × C 的矩阵 X，算 W·X 叫矩阵矩阵乘（GEMM）：权重还是读 m × n 个，计算变成约 2mnC 次。算术强度提高到原来的约 C 倍。

一个具体数字：Strata 的投机解码控制器里有一张默认表，记录“同时算 n 个 token 的稠密部分，要花单个 token 的几倍时间”：2 个 token 是 1.05 倍，4 个是 1.45 倍，8 个是 3.0 倍。代码事实 也就是说，8 个 token 一起算，平均每个只要单独算时的 3.0 ÷ 8 ≈ 38%。教学推演

和本章的关系：读题时 C 可以是几千，所以读题快得多。批处理也有代价：要更多临时存储放这一整块的中间结果，单块的完成时间也更长。

延伸阅读：OI Wiki：矩阵 · 维基百科：矩阵乘法 · Wikipedia: BLAS（GEMV 与 GEMM 的来历）

Strata 在别处也用了同一招。投机解码的验证窗口一次送进几个 token，源码说这个窗口的代价是“稠密权重只读一次，供 T 个 token 共用”。[S08] 混合残差的融合读取也有多 token 版本，最多 8 个 token 共享权重，“权重为它们全体只读一次”。代码事实

学过计算机的同学：这就是《计算机组成原理》里的“访存局部性”和《数值线性代数》里 BLAS 分级的道理：BLAS-2（矩阵乘向量）受带宽限制，BLAS-3（矩阵乘矩阵）才能把算力吃满。读题把一串 BLAS-2 合成了 BLAS-3。

16.3 专家怎么批：按专家分组

稠密部分好办，所有 token 用同一份权重。专家部分麻烦一点：每个 token 每层选 10 个专家，不同 token 选的不一样。Strata 的做法是先按专家分组：把选了同一个专家的 token 归到一起，这个专家的权重读一次，算完一组。[S12] 图 16-4 是一个缩小的示意。

放大到真实规模：一块 8,192 个 token，每个 token 每层选 10 个专家，一层就有 81,920 次专家调用，而每层只有 512 个专家。平均下来，每个专家被 81,920 ÷ 512 = 160 个 token 共用。教学推演 源码注释也说，块大到 1,024 个 token 以上时，每层 512 个专家“几乎全都会被选到”。代码事实

分组之后，专家从哪来？显存里缓存着的热门专家直接读；不在显存的，从内存里的专家区经一条锁页内存“环形队列”、用单独的拷贝流送上 GPU。[S12] 算完之后，结果要按原来的 token 顺序放回去，再按各自的路由权重相加。顺序放错一个，结果就加到了别的 token 身上。

注意这和写答案时的分工不同：写答案时没命中的专家主要由 CPU 在内存里就地计算（第 10 章）；读题时专家被成百上千个 token 共用，搬上 GPU 一起算就划算了。只有一个例外：块不到 1,024 个 token 时（比如智能体调用工具后读回的一小段输出），引擎会把只被少数几个 token 选中的非驻留专家，交给此时闲着的 CPU 专家池去算，其余照常经 PCIe 搬运。v0.1.41 起，这个 CPU 分担在单张 NVIDIA 卡上默认打开（CUDA 版，不开 --batch）；层切分、批槽位和 AMD（HIP）版仍默认关闭。代价是 CPU 用自己的激活格式，算出的结果和 GPU 不逐位相同。设 STRATA_PREFILL_CPU_SHARE=0 就关掉它，输出回到 0.1.40.x 的字节。代码事实（src/prefill/prefill.cpp）[S12] 上游在三张 NVIDIA 卡上测过：512 和 1,000 个 token 的提示，读题时间缩短 20% 到 34%；首 token 的 KL 散度平均约 0.004。上游报告 注意，prefill.hpp 里 set_cpu_pool 的注释还写着“不设就不分担”，紧挨着的 arm_cpu_share 注释和代码已经改成默认打开。两者不一致时，以代码为准。代码事实[S12]

16.4 一块切多大：块越大越好吗

提示词会被切成一块（chunk）一块地读，每块走完全部 48 层，再接下一块。[S12] 块越大，权重和专家被越多 token 共用；但块也不是越大越好。下面的教学模型把这个取舍画了出来：

真实的 Strata 怎么选块？上游的说明是：长文本按大块读，每块最多 8,192 个 token，所以长文档能读到每秒 1,000 个 token 以上。[S02] 设置成 --prefill auto 时，引擎在不超过借用上限的前提下，找放得下的最大块。默认最大 8,192，用户可以显式放开到 16,384 或 32,768。代码事实 怎么找，v0.1.39 改过一次。以前引擎从一张固定的候选表（32,768、16,384、8,192、6,144……）里挑第一个放得下的。这张表太粗：一台能放下约 8,700 个 token 的机器，只能拿到 8,192。现在改成在 256 个 token 的网格上二分查找：块越大，要借的显存只会越多，所以“放得下的最大块”可以二分。代码事实 服务端为了估算“读题要等多久”，也按每块最多 32,768 个 token 来算。[S15]

块大的代价是临时显存。一块 8,192 个 token 的中间结果要占不少地方，Strata 的办法是向专家缓存“借”：读题期间把缓存末尾的一些槽位借给块缓冲，读完再把原来的专家填回去。每个请求只借自己的提示词需要的大小。[S12] 图 16-6 是源码注释里的一组实测。

速度提升 973 ÷ 791 ≈ 1.23 倍。教学推演 块再大还能快一些：注释记录了一张 RTX 5090 读 32K 提示词的例子，用 8,192 的块每秒 5,624 个 token，整段一块（32,768）每秒 6,465 个。但这要显存足够大，所以默认不开。代码事实

块也不能太小。源码注释提到，块小于大约 1,000 个 token 时，引擎会换用另一套 kernel，Q2_0 的输出就会变，所以“所有专家一律搬运”的模式以 1,024 为下限。用 STRATA_PREFILL_CPU_SHARE_MAX=3072 把 CPU 分担扩展到更大的块时，这个下限也跟着抬到 3,072。代码事实 另外，引擎在每块开始前检查一次“要不要停”，所以块越大，取消请求后要等的时间也越长。[S12]

16.5 流水线：这一层在算，下一层已经在路上

块切好了，每块还要走 48 层。每一层都分两件事：把这一层要用的专家搬上 GPU，再计算。如果两件事轮流做，GPU 算的时候拷贝通道闲着，搬的时候 GPU 闲着。Strata 让它们重叠：当前层在算注意力时，下一层的专家已经在经 PCIe 搬来。[S02]

流水线：让几道工序同时开工

直觉：洗衣服分“洗”和“烘”两步。只有一台洗衣机和一台烘干机时，聪明的做法是第一筐进烘干机的同时，第二筐进洗衣机。每筐用时不变，但一堆衣服的总用时短了很多。

定义：把一件工作拆成几道前后相连的工序，每道工序由不同的部件做；第 i 件工作在做第 2 道工序时，第 i+1 件已经开始第 1 道。这就是流水线。稳定以后，总用时由最慢的那道工序决定，而不是各道工序之和。图 16-7 是两道工序、四层的例子。

流水线的前提是：两道工序用不同的部件（这里是拷贝引擎和计算单元），中间有缓冲区存放“搬来了、还没算”的东西。缓冲区太小，搬运就会停下来等。

延伸阅读：维基百科：流水线（计算机） · 维基百科：指令流水线 · Wikipedia: Pipeline (computing)

Strata 的缓冲区就是那条锁页内存环形队列。源码注释记录了它的大小有多重要：用 8,192 的块读 Q2_0 时，环形队列 96 个槽位每秒读 1,153 个 token，加到 384 个槽位每秒 1,294 个，因为“下一层的专家能在本层的注意力阶段就到位”。代码事实

环形队列和块缓冲借的是同一份显存，v0.1.39 因此把两者放在一起算。环的大小改按字节定：一个槽装一个完整的专家，专家大的模型分到的槽就少。自动选块时，找的是“环形队列仍然装满”的最大块。源码注释记录了理由：在一台 4 卡机器上读 120K 的提示词，环多一个槽约值每秒 0.53 个 token，块多一个 token 只值约 0.05 个，所以先保住环，再加大块。能装进旧规则那一块的提示词仍用旧的环，结果逐位不变。代码事实 更长的提示词，专家在“缓存里算”和“搬上来算”之间的分配变了，逐位结果也跟着变；上游拿 FP16 的读题路径作对照测过，质量仍在原来的范围内。上游报告

多张显卡时，流水线又多了一层：每张卡负责一段层，前一段把一块的中间结果交给后一段之后，马上开始读下一块。用接口注释的话说，后一段在读第 c 块时，前一段已经在读第 c+1 块。[S12]

最后别忘了交接。一块读完，引擎要把会话状态留在“逐个 token 读到这里时应有的样子”：GDN 的递推状态和卷积历史、QSA 的 KV 缓存和索引器、PLE 的历史，一样不能少，写答案才能从下一个 token 无缝接上。[S12]

16.6 动手：找出既快又放得下的块

  1. 先玩上面的交互图（图 16-5）。把 C 从 1 拉到 8192，看柱子在哪里由“上涨”变成“平台”。再关掉流水线，在 C = 1024 时各播放一次，比较两次的“每块用时”。
  2. 打开本书的交互实验「分块与空间取舍」。它在一条显式给定的复用曲线下，同时算每块的速度和所需空间。先找绝对最快的块，再排除超出显存预算的那些，比较“可行的最优”和“绝对最优”差多少。实验里的复用曲线和每 token 空间都是人为参数，不是 Strata 的分配器。
  3. 想一想：同一段提示词用 C = 1 和 C = 8192 读，最后的状态应该一样吗？读完“深入一层”再回答。

记住这三点

  1. 写答案是矩阵乘向量，权重读一遍只服务一个 token；读题是矩阵乘矩阵，权重读一遍服务一整块。同一台电脑上，读题能比写答案快二十多倍。
  2. 专家部分靠按专家分组来批量：选了同一个专家的 token 归到一起，权重只读一次。块越大复用越多，但要借更多显存，取消也更慢。Strata 默认每块最多 8,192 个 token。
  3. 流水线让搬运和计算重叠：当前层计算时，下一层的专家已经在路上。总用时由最慢的工序决定。

常见误解：“读题时 token 都已知，所以它们可以互相看见，因果规则不用管了。”

不对。批量只是改变了计算怎么组织，没有改变模型的规则：第 i 个 token 仍然只能看到它前面的 token。读题阶段照样要用因果掩码，递推层照样要按顺序走完整块。输入“已知”和语义上“允许看未来”是两回事。

深入一层：状态交接、舍入差异与借用显存的安全条件

状态交接不是只留下最后一个向量

一块读完，需要交接的状态包括：GDN 的递推状态和卷积状态、QSA 的 KV 和索引器、PLE 的历史，以及与草稿层相关的状态。[S12][S13] 如果只保留最后一行 logits，丢掉这些状态，下一步写答案就不再是同一段历史。

一个有力的测试：同一串 token 分别用 C = 1、C = 7、C = 32 等不同切法读完，比较块边界处的状态和之后固定历史下的输出。最容易出错的样本是：长度恰好跨过块边界、最后一块不满、提示词极短、读到一半被取消、读完马上接着写答案。

批量会改变舍入，但不能拿“浮点”当万能借口

批量计算和逐个计算可能走不同的舍入路径。上游文档举过例子：使用 IQ 系列模型时，CPU 算一个 token 的专家用 ggml 的点积，算多个 token 时用 Strata 自己的多 token kernel，两者舍入略有不同；于是温度为 0 时，同一个提示词也可能因为草稿不同而得到另一个同样合理的回答。上游为此提供了一个开关，让所有分组都用多 token kernel。[S03] v0.1.41 起，默认路径上也有一个这样的例子：单张 NVIDIA 卡读不到 1,024 个 token 的块时，CPU 分担的那部分专家用 CPU 自己的激活格式算（16.3 节）。上游在 500 和 1,000 个 token 的提示上比较过开和关：32 个 token 的贪心回答约一半完全相同，其余在约第 23 个 token、两个候选几乎打平的地方分岔。上游报告

所以 C = 1 和大 C 的输出不完全逐字相同，既不能立刻断定某一边有 bug，也不能一句“只是浮点”就放过。应该在同一段固定历史上比较中间张量、选中的专家和索引编号、误差从哪一层开始增长，再按事先定好的容差和质量门槛判断。状态位置、因果掩码、索引编号这些“非数值契约”必须单独精确核对。

借用显存的安全条件

块缓冲向专家缓存借槽位，带来两个问题。第一，借用期间，被借走槽位里原来的专家已经不在了，路由表不能再把它们当作“命中”；源码里，这些专家在读题期间改为从内存搬运，读完再填回去。[S12] 第二，填回必须完成之后，才能重新宣布这些槽位里是哪个专家。只算“预算加起来没超显存”，证明不了借用是安全的；要证明的是“任何时刻，标签和槽位里的字节一致”。

文档里的几个块大小

上游不同地方出现过不同的块大小：说明文档写“最多 8,192 个 token”[S02]；详情文档讲内部原理的那一段，在 v0.1.38 还写着 2,048，到 v0.1.39 才改成“最多 8,192，32,768 需手动打开”，讲 0.1.13 改动的历史段落则仍记着“以前是 2,048”；服务端为了估计等待时间用 32,768 作上限[S15]；引擎的自动档默认最大 8,192，可显式放开到 32,768。代码事实 这些数字不矛盾，它们回答的是不同的问题（默认值、历史值、上限）。写公式时，本书一律把块大小记作变量 C。

教学成本式的边界

本章交互图和「分块与空间取舍」实验都用了简化的成本式，形如 T ≈ N ÷ r(C) ＋ ⌈N ÷ C⌉ × 每块固定开销，其中 r(C) 是显式设定的复用曲线。它能说明“固定开销被摊薄”和“空间约束”这两件事，不能预测 Strata 的真实吞吐。真实速度还取决于专家命中率、PCIe 带宽、CPU 拷贝线程、注意力随上下文变长而增加的计算等。

做 GPU 进阶实验时，每次只改 C，其余设置（量化、KV 格式、草稿、输入、缓存状态）保持不变，再解释速度和质量的变化。
