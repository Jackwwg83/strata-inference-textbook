16.1 输入已知，调度空间不同

生成时，下一 token 要等当前条件分布和采样完成；prefill 时，prompt 的 ID 都已知，可以把多个位置的线性投影组织成 GEMM。因果掩码和递归依赖仍然存在，并不是所有位置之间都没有关系。

Prefill 接口说明：chunk 逐层处理，专家按 expert 分组，GPU 驻留专家直接读缓存，其他专家通过锁页环和 copy stream 传入。[S12] 让多个 token 共用某专家的权重，能摊薄读取与解包成本。

16.2 按专家分组为什么有效？

教学例子：8 个 token，每个选 2 个专家，共 16 个路由项。如果其中 6 项都选专家 E，可以把对应输入组成小矩阵，一起计算 E，而不是读 6 次同一权重。真实缓存层级可能已经复用部分读取，因此“6 次变 1 次”是理想化解释，不是通用实测倍率。

分组还引入 scatter / gather、排序或分桶以及输出恢复顺序。只有恢复到正确的 token—专家位置，后续路由权重合并才合法。吞吐提高不能以把 token 顺序打乱为代价。

16.3 chunk 越大越好吗？

大 chunk 往往提高权重复用，但激活、索引、工作矩阵与 staging 空间也增大；单块运行时间变长，取消和共享服务的响应也变慢。短 prompt 为大 chunk 预留全部空间，可能无谓挤掉热专家。

上游不同说明中出现 8192 的常用块示例，而固定服务源码为 watchdog 估计使用 PP_CHUNK_MAX=32768。[S02][S15] 这不是可随意统一的“唯一硬上限”：实际 chunk 由配置、实现与可用空间决定。教材公式一律把 chunk 记作变量 C。

16.4 借用专家缓存：内存的时间复用

Prefill::init 可以借用专家缓存尾部作为 prompt scratch；relayout 在请求间按实际需要调整，完成后再恢复被借走槽位的专家。[S12] 这是操作系统中生命周期分析的具体应用：两种不会同时使用的对象可以复用同一区域。

必须明确借用期间哪些专家仍可视为命中；还要保证恢复完成后才重新发布对应标签。仅仅“预算上加起来没超显存”不足以证明该复用安全。

16.5 状态交接不是只留下最后一个向量

chunk 结束后需要正确的 GDN 递归与卷积状态、QSA KV 和 indexer、PLE 历史，以及相关草稿状态。[S12][S13] 如果只保留最后一行 logits，而丢掉这些状态，下一步 decode 就不是同一个模型历史。

一个强测试是：同一 token 序列用 C=1、C=7、C=32 等不同切法处理，比较边界状态与后续固定历史输出。浮点重排可能需要数值容差，但状态位置、因果掩码、索引 ID 的契约必须单独核验。

16.6 实验与验收

教学 chunk 实验使用 T≈N/r(C)+ceil(N/C)·launch 的简单成本式，r(C) 为显式设定的饱和复用曲线。它能说明启动摊销与容量约束，不能预测真实 Strata 吞吐。

GPU 进阶实验要对短输入、跨 chunk 边界、末块不满、取消中断和继续 decode 分别测试。每次只改 C，其余量化、KV、MTP、输入和缓存状态固定，再解释速度与质量变化。
