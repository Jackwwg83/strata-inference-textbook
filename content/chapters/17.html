17.1 容量公式从每个因子开始

一般 GQA 的原始 K/V 载荷为 M=L×T×Hkv×d×(bK+bV) 字节。这里 L 是需要 KV 的层数，不是整个模型层数；T 是实际或预分配位置数，要说明是哪一个；bK、bV 为每元素字节数。

本案例 L=12、Hkv=2、d=256。[S04] FP16 两项各 2 字节，得到 24 KiB/token。T=131072 时主 QSA KV 载荷为 3 GiB。若教学近似将 K/V 都按每元素 1 字节，则为 1.5 GiB；实际量化 scale、indexer、page table、尾部和对齐还需另加，不能叫完整占用。[S18]

17.2 历史全集与当前工作集

稀疏选择每步只读取一部分历史，显存可仅驻留常用页面，其他历史保留在 RAM。这样节省的是显存驻留量，不必删除历史。ConversationKv 说明，streamed 模式下权威数据来自 host pool，而不是可替换的 VRAM slot。[S10]

如果未来查询选中一个不在显存的页，系统必须把正确数据取回或按正确路径访问。命中率决定代价；映射与完成顺序决定结果。把未驻留页直接当作零，是错误的“优化”。

17.3 预算是多项之和，且有阶段峰值

总预算至少包括：常驻非专家权重、热专家、QSA KV、GDN 主状态、卷积 / PLE / MTP 状态、索引、scratch、图与框架开销、预留空间。主机端还可能有全部专家或 GPU 补集、host KV、会话快照和 OS headroom。[S03][S06]

对 prefill 与 decode 分别画一张账。借用内存区域不能同时算作两份物理占用；但两段生命周期若实际重叠，就不能乐观地只取最大值。预算公式应与真实分配一致，并用启动后及运行峰值验证。

17.4 不要把所有“省内存开关”叠加

固定上游说明中，K8V4 模式与 KV streaming 不是可任意相乘的两个收益：说明明确该混合格式不走相同 streaming 路径。[S03] 若一个表同时假设二者效果却未验证配置，会给出虚假的容量和速度。

同理，4 位量化通常改变数值，不同数据放置方式本身则可以保留相同值。前者要做质量评估，后者要做映射与拷贝正确性检查，不能用同一种“无损”标签笼统覆盖。

17.5 多个会话如何改变预算？

只读权重理论上可共享，序列状态通常按活动会话独立增长。教学近似为 M≈Wshared+Σstate_i+scratch+reserve。若请求有相同前缀，物理页共享与 copy-on-write 可能省空间，但需要严格身份、引用计数与写时隔离；这是扩展设计，不是仅靠文本相似就能复用。

5 个会话“最大 128K”与 5 个会话“实际均占 128K”也不同。报告容量时必须区分配置上限、实际 token 长度、已分配容量与当前驻留工作集。

17.6 实验与验收

KV 实验允许调整上下文、活动会话数、位宽和驻留窗口，分别显示主 KV 载荷、固定 GDN 主状态与未计入项。其默认几何来自固定代码，但量化元数据开销由用户输入，故输出是预算练习，不是精确 allocator 模拟。

真实验收必须验证超过预算时明确拒绝或选择受支持回退，绝不能默默缩短上下文或丢弃历史。需要同时测 RAM 峰值与显存峰值，而不是只截图一次空载显存。
