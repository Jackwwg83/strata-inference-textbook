18.1 草稿不是未经检查地替目标回答

一个便宜的过程先猜若干 token，较贵的目标模型批量验证。只有满足验证规则的连续前缀被接受；第一次不一致之后的草稿不再属于正确条件历史。目标模型还会提供用于继续生成的选择。[S08]

草稿可以来自 MTP 层，也可以来自 prompt lookup。草稿质量主要影响接受率与成本，不能允许未经目标确认的内容混入已提交历史。保存目标语义是投机执行的核心，与 CPU 分支预测中的“预测执行，错误时恢复”有直观联系。

18.2 贪心情况下，为什么只能接受连续前缀？

假设已提交历史为 H，草稿为 a,b,c。目标对 H 选 a，说明 a 可以接受；目标对 H+a 选 b，b 也可接受；目标对 H+a+b 选 d≠c，于是拒绝 c，并继续使用目标选择 d。

不能再单独检查草稿后面的 e “恰好也对”就接受，因为它是基于包含错误 c 的历史计算的。正确性是沿前缀归纳成立的，不是把窗口每个位置独立打勾。

18.3 经典拒绝采样与本项目精确匹配不能混写

经典投机采样论文讨论了基于目标分布 p 与草稿分布 q 的接受 / 修正方法。[R04] 但读到的 Strata 接口描述的是：目标每行按固定 seed 和绝对位置采样，草稿 token 与该目标样本相等才接受；可选 coupled draft 使用同一均匀随机数提高相等概率。[S07]

因此本书没有把 min(1,p/q) 写成 Strata 当前代码。两类方法都可研究，但其分布论证、随机数组织和实现条件不同。相同输出还依赖目标数值路径和惩罚历史保持一致；上游自身也说明不同内核及缓存放置可能导致舍入差异。[S03]

18.4 窗口运行与状态提交分离

Verifier 的窗口包含最后接受 token 与若干草稿；run 计算候选结果，commit 只永久保留前缀。[S08] 各状态采用不同处理：GDN 通过保存的输入重放接受前缀更新递归和卷积；indexer 尾部恢复快照后追加接受键；PLE 恢复到接受位置；拒绝部分的 KV 物理单元将在可见读取前被正确覆盖。

这不是“把数组长度减一下”能概括的行为。不同模块的历史压缩方式不同，回滚能力也不同。任何新增状态都必须回答：run 会不会写它、commit 如何保留前缀、拒绝部分如何失效、谁确认异步操作完成。

18.5 例题：三份草稿拒绝第二份

已提交长度为 100，草稿 d₁,d₂,d₃。若只有 d₁ 被目标认可，后续推进应基于已接受前缀和目标产生的下一 token，而不是包含 d₂ 的状态。特别注意实现窗口的 row 0 是输入的 last accepted token，窗口提交计数与“接受了多少草稿”存在一个偏移。[S08]

数学推导可用“本轮至少贡献一个目标推进，加上接受草稿数”解释期望产出；工程里则必须逐项核对 pos0、row、预测下一位置与 commit(n_keep)，不能直接把两个计数变量当成同一含义。

18.6 实验与验收

在“事务化前缀”实验中设置拒绝位置，查看哪些候选仍属于接受前缀，以及固定递归 toy state 如何恢复。它是教学状态机，不模拟完整模型。

GPU 作业需覆盖：全拒绝、全接受、中途拒绝、接近上下文上限、EOS、取消、惩罚历史与跨请求参数切换。比较相同目标历史下的 logits、提交状态与最终 token，不只看平均接受率。
