一个“作弊”的提速

Strata 的说明文档这样介绍它的一个提速手段：一个又小又快的助手先猜接下来的几个词，大模型一次把这些猜测全部检查一遍，留下它认同的，再自己写下一个词。“助手只管猜，每个词都由大模型决定，所以回答质量不变，只是快了 1.6–1.8 倍。”上游报告[S02]

猜测怎么能让计算变快，又不改变答案？猜错了怎么办？已经按错的猜测算出来的东西，又怎样“撤回”？这一章用 Strata 的验证窗口回答这三个问题。

一句话：草稿层先猜最多 3 个 token，目标模型把它们放进一个窗口一次算完，从左往右比对，接受到第一个不一致为止，其余全部作废；目标模型在不一致处给出自己的选择，所以每轮至少前进 1 个。这和 CPU 的推测执行、数据库的“先暂写、再提交、错了回滚”是同一个思路。

18.1 先猜后验：猜错了也不亏

第 16 章讲过：一次算好几个 token，比一个个算便宜得多，因为权重只读一遍。写答案时，下一个 token 要等上一个选出来才知道，没法批量。投机解码（speculative decoding）的办法是：先用一个便宜的方法猜出接下来几个 token，再把“上一个结果 ＋ 这几个猜测”当成一批，交给大模型一次算完。大模型在每个位置都会说出“我在这里会写什么”，拿它和猜测比一比，就知道哪些猜对了。

负责猜的叫草稿（draft），负责拍板的大模型叫目标模型（target）。Strata 的草稿来自模型自带的一层 MTP（多 token 预测）层，最多猜 3 个；如果回答在重复上文（比如改代码、引用原文），还可以从上文里“抄”出最多 5 个，叫 prompt lookup。一次验证要把全部 48 层过一遍，平均每轮能前进 2.4–3.2 个 token。[S02] 图 18-1 是一个对比。

为什么一轮多验几个 token 不怎么费事？源码给了一笔账：一个窗口的代价是“稠密权重只读一次，供 T 个 token 共用”，外加 T 个 token 各自没命中的专家的并集要在 CPU 上算。按实际解码记录统计，要在 CPU 上算的未命中专家，T ＝ 2 时是单个 token 的 1.75 倍，T ＝ 3 时 2.4 倍，T ＝ 4 时 3.05 倍。[S08] 多验一个 token 的边际成本，远小于再跑一轮。

猜得准不准，直接决定赚多少。源码注释记录，MTP 层在第 1、2、3 步猜中贪心结果的比例分别是 0.89、0.86、0.85。代码事实 上游文档也提醒，输出速度和文本有关：草稿被接受得越多就越快，同一个提示词换一个回答，速度能差好几个百分点。[S03] 每次该猜几个、值不值得猜，是第 19 章的话题。

18.2 只接受连续的前缀

比对规则只有一条：从左往右，接受到第一个不一致为止。设窗口第 0 行是上一轮定下的 token x，后面是草稿 d₁、d₂、d₃。目标模型算出“在 x 之后我会写 a”“在 x、d₁ 之后我会写 b”……依次比较：

  • 目标在 x 之后选 a，草稿 d₁ ＝ a，接受；
  • 目标在 x、a 之后选 b，草稿 d₂ ＝ b，接受；
  • 目标在 x、a、b 之后选 e，草稿 d₃ ≠ e，停。d₃ 作废，换成目标自己的 e。

Strata 的生成循环里，这条规则就是一行代码：while (a < T - 1 && window[a + 1] == outv[a]) ++a;，紧接着 ver.commit(a + 1)。代码事实 其中 outv[t] 是目标在窗口第 t 行之后的选择，a 是接受的草稿数。不一致处目标自己的那个 token 也会输出，所以每轮前进 a ＋ 1 个，最少 1 个。投机控制器的注释也写着：“验证这一遍总会提交一个 token。”[S09]

为什么第一个不一致之后的草稿一律作废，哪怕它“看起来是对的”？因为它是接在错的 token 后面猜的，它的前提已经不成立。下面的模拟器专门设计了这种情况，按单步走第 2 轮看看：

学过计算机的同学：这条规则的正确性可以用数学归纳法证明。设已提交的历史 H 等于贪心生成的结果；若 d₁ 等于目标在 H 之后的选择，则 H＋d₁ 仍等于贪心结果；依此类推，直到第一个不一致。不一致之后的草稿基于一个错误的历史，归纳链断了，没有任何理由接受它们。正确性是沿着前缀链式成立的，不是窗口里每个位置各自打勾。

贪心时（每步取概率最大的 token），Strata 的验证窗口还做了一个更强的保证：窗口里第 t 行的结果，和普通逐个生成在那个位置的结果逐位相同，因为窗口里的每个 kernel 要么就是单 token 的 kernel，要么每个 token 的算术和单 token 版本完全一样。所以“草稿被接受”恰好等于“普通生成也会写出它”。[S08]

18.3 推测执行：CPU 早就这么干了

“先猜着往下做，猜错再撤回”不是语言模型发明的。现代 CPU 每秒都在这么做几十亿次。

推测执行与分支预测

直觉：你在食堂排队，前面的人还没决定吃面还是吃饭，阿姨已经根据他平时的习惯先下了面。猜对了，省下等待的时间；猜错了，把面放一边重新做，最多白忙一场，不会端错菜。

定义：CPU 用流水线执行指令（第 16 章讲过流水线），遇到 if 这样的分支时，条件还没算出来，下一条指令该取哪条就不确定。分支预测器根据历史猜一个方向，CPU 沿着猜的方向继续执行，这叫推测执行。关键是：推测执行的结果先放在临时的地方，不写进正式状态。条件算出来后，猜对了就把结果“退休”（提交）；猜错了就清空流水线里那些指令，从正确的方向重来。

一个具体数字：现代处理器的分支预测准确率通常在九成以上，所以“偶尔白做一点”远比“每次都停下来等”划算。猜错的代价是流水线越长、白做的越多。

和本章的关系：草稿就是分支预测，验证窗口就是推测执行，commit(a + 1) 就是退休。两边都遵守同一条纪律：猜测的结果在核对之前不能生效。

延伸阅读：维基百科：推测执行 · Wikipedia: Branch predictor · 维基百科：指令流水线

18.4 先暂写，再提交：事务式的状态管理

难点在“撤回”。验证窗口算 T 行时，模型的各种状态都可能被改动：KV 缓存多了 T 格，GDN 的递推状态往前走了，索引器多了几个键。如果只接受了前 2 行，后面那些改动必须像没发生过一样。这正是数据库里“事务”要解决的问题。

事务的提交与回滚

直觉：银行转账要做两步，A 账户减 100，B 账户加 100。做完第一步时断电了怎么办？银行的做法是把两步包成一个事务：要么全部生效，要么像什么都没发生。

定义：事务执行期间的修改先记在临时的地方（日志或副本），外界看不到。全部检查通过后执行提交（commit），修改一次性生效；中途出错就回滚（rollback），丢掉临时修改，回到事务开始前的状态。实现回滚有两种常见做法：一是先存一份快照，出错时恢复；二是记下输入，确认后再按输入重做一遍。文件系统的“日志”（journaling）用的也是这套思路。

一个具体例子：Strata 的 commit(n) 不是“提交整个窗口或者全部回滚”，而是“只提交前 n 行”。这比教科书里的事务更细：一个窗口里，前缀生效，后缀回滚。

和本章的关系：不同的状态有不同的撤回方式。下面逐项看。

延伸阅读：维基百科：数据库事务 · 维基百科：回滚 · OSTEP：Crash Consistency: FSCK and Journaling（PDF）

Strata 的验证窗口把这件事写得很清楚。窗口运行时，为全部 T 个位置追加 K/V 和索引器的键，但不动 GDN 状态。commit(n) 再让前 n 个 token 生效，每种状态各有办法：[S08]

  • GDN 递推状态：窗口里根本不改它，只把每行的输入存下来。提交时，用存下的输入把前 n 个 token 重放一遍，状态就前进到正确的位置。这是“记输入、确认后重做”。
  • 索引器的键：先恢复窗口前存的快照，再把接受的键重新追加。注释特别说明了原因：被拒绝的键可能落在当前块还要用的槽位里。这是“快照 ＋ 重做”。
  • PLE 历史：直接设成第 n−1 个 token 之后的快照。
  • KV 缓存：多写的那些格什么都不用做。这些位置下一轮会被重新处理，新值在任何查询读它之前就会覆盖上去。[S08] 第 17 章讲的 KV 流式也遵守同一条：新 token 总写进内存里的权威副本，所以“拒绝了草稿”之后不需要作废任何显存槽位。代码事实

有一个例外。没有草稿的窗口（T ＝ 1）只有第 0 行，它一定被接受，用不着撤回。所以 v0.1.40 起，在 CUDA 上这种窗口的图直接推进 GDN 状态，commit 不再启动提交图，省掉一次图启动；设 STRATA_ONE_TOKEN_COMMIT=0 可以关掉它。可能被拒绝的多行窗口，仍按上面的规则走。代码事实

注意窗口的“行数”和“接受的草稿数”差 1：窗口第 0 行是上一轮定下的 token，它本身也要在这一轮写进状态。所以接受了 a 个草稿时，提交的是 a ＋ 1 行。生成循环里的注释说：“窗口的前 a ＋ 1 个 token 现在进入了会话；最后那个输出还没有，它是下一轮的第 0 行。”代码事实 草稿层的位置计数也按这个偏移来算：在位置 p 的窗口接受 a 个草稿后，下一个窗口从 p ＋ a ＋ 1 开始。[S07]

学过计算机的同学：每加一种新的序列状态，都要回答四个问题：窗口运行时会不会写它？commit(n) 怎样只保留前缀？被拒绝的部分怎样失效？异步的读写由谁确认完成？这和给数据库加一张新表、要想清楚它的日志和恢复，是一回事。

18.5 采样时怎么验：和目标的抽样结果精确相等

贪心时比对很简单：目标在这一行概率最大的 token 是不是草稿。可聊天时常常开着温度采样，每一步是“按概率抽一个”。抽样结果本身是随机的，怎么比？

Strata 的做法是让目标模型的抽样可以复现：窗口第 t 行的随机数由“种子”和这一行的绝对位置决定，再走完整的采样链（重复惩罚、top-k、top-p、min-p、温度，最后按累积分布抽一个）。草稿只有和这一行的抽样结果完全相等才被接受。于是在这条默认规则下，输出只取决于种子，和草稿是什么无关；草稿只决定一轮能前进几步。[S07] 每一行的重复惩罚也按“这一行之前应有的历史”单独准备，和普通逐个生成时数的一样。[S08]

草稿怎么猜，才更容易“撞上”目标的抽样？Strata 有一个默认关闭的“耦合草稿”模式：草稿层不再提交它最有把握的 token，而是用目标同样的采样链，配上目标将要使用的同一个随机数去抽。两个分布接近时，用同一个随机数按累积分布去抽，结果相同的机会远大于“拿最大值去碰一个随机样本”。目标的抽样不变，所以输出文字也不变。[S07] 图 18-5 是这个想法的示意。

注意，这和投机解码的经典论文不是一回事。经典方法按 min(1, p ÷ q) 的概率接受草稿，被拒绝时再从修正后的分布里补抽一个，从而保证输出分布和目标完全一致。[R04] Strata 默认用的是“和目标的抽样结果精确相等”，不是这个公式。v0.1.40.2 加了一个默认关闭的开关 STRATA_SPEC_PROB=1，实现的正是经典方法：草稿层按自己的分布 q 抽一个草稿，验证时按 min(1, p ÷ q) 接受，被拒绝时从 max(0, p − q) 归一化后的分布里补抽。这里的 p 是目标走完整条采样链之后的分布，不是原始的 softmax。它只对采样请求生效，贪心请求不受影响。代码事实 两种规则保证的东西不同：精确相等保证同一个种子写出同样的字；经典方法只保证每个 token 的分布不变，同一个种子写出的字会随草稿变。上游文档写明，开了它，文字只在引擎、参数和提示词都相同时才能复现。上游报告 两种方法的分布论证、随机数的组织方式和实现条件都不同，不能混写。另一个默认关闭的开关 STRATA_SPEC_GUMBEL=1 仍用精确相等，只把抽法换成 Gumbel-max（配合耦合草稿时，草稿和目标两边都换）：同一个种子写出的字可能和默认不同，但仍然和草稿无关。代码事实

草稿能猜什么，还受一个现实限制：MTP 草稿层只能从词表的一个子集里提议 token。从引擎 0.1.27 起，这个子集加进了全部中文、日文和韩文的 token，上游实测这些语言的回答因此快了 15–38%（Q2_0，RTX 5070）。[S03] 中文用户用到的提速，有一部分就来自这里。

记住这三点

  1. 草稿负责猜，目标负责拍板。比对从左往右，接受到第一个不一致为止；不一致之后的草稿哪怕碰巧正确也作废。每轮前进 a ＋ 1 个 token，至少 1 个。
  2. 这和 CPU 的推测执行同一个纪律：猜测的结果在核对前不能生效。Strata 用 commit(a + 1) 只让窗口的前缀生效。
  3. 撤回要逐项设计：GDN 重放存下的输入，索引器恢复快照再追加，PLE 恢复到对应快照，KV 多写的格等着被覆盖。只把位置减一下是不够的。

常见误解：“草稿层又小又不准，用了它，回答质量会变差。”

不会。默认规则下，草稿只是提议，每个 token 都要和目标模型自己的选择（或可复现的抽样结果）完全相等才能留下。猜得差只会让每轮前进得少、速度变慢，不会改变写出来的字。[S02][S07] 打开 18.5 节的 STRATA_SPEC_PROB=1 后，写出来的字会随草稿变，可每个 token 的分布仍和不用草稿时完全一样，所以质量同样不变。代码事实 上游也记录了一个需要知道的例外：使用 IQ 系列模型时，CPU 算一个 token 和算多个 token 的专家用的是两套 kernel，舍入略有不同，所以温度为 0 时，同一个提示词可能因草稿不同而得到另一个同样合理的回答；打开一个开关让所有分组都用多 token kernel，答案就不再依赖草稿。[S03]

深入一层：偏移量、异步提交与验收清单

窗口里的几个计数，别混成一个

设已提交长度为 100，窗口第 0 行是第 100 个位置的 token x，草稿 d₁、d₂、d₃ 占位置 101–103。若只有 d₁ 被接受（a ＝ 1），提交 2 行（位置 100 和 101），目标在位置 101 之后的选择成为下一个窗口的第 0 行，下一个窗口从位置 102 开始。[S07] 数学上可以说“本轮至少贡献一个目标推进，再加上接受的草稿数”；工程上则要逐项核对窗口起点、行号、下一个位置和 commit(n_keep) 的含义，不能把“接受的草稿数”和“提交的行数”当成同一个变量。耦合草稿的随机数计数也遵守同样的偏移：在 MTP 第 c 格做出的草稿，由计数器 c ＋ 1 那一行来验证。[S07]

每一行的惩罚历史

重复惩罚要数“这一行之前出现过哪些 token”。窗口第 t 行之前的历史，是已提交的内容加上草稿 1 到 t。Strata 给窗口的每一行单独准备一份历史；0.1.19 之前只准备了第 0 行，草稿行读到的是没写过的槽位。[S08] 这类错误不会让程序崩溃，只会在开着惩罚时悄悄让结果和普通生成不一致。

异步提交

单 GPU 时，commit() 默认不等它的图跑完就返回：下一个窗口在同一个流上排在它后面，草稿层又不读它写的东西，于是提交和下一轮的草稿可以重叠。任何从别的流或主机读写会话的人（新请求、检查点、快照、读题路径、运行结束），都要先调用 wait_commit()。[S08] 这是第 14 章“同步与异步”的又一个例子：快路径省掉了等待，代价是每个旁路读者都必须记得自己去等。

草稿层的“偷懒”为什么不影响输出

MTP 草稿层在实现上做了好几处简化：大投影用 Q8_0 量化，注意力在它见过的所有格子上做稠密计算，全部 512 个专家常驻显存（708 MB）。源码说得明白：这些选择只影响草稿的质量，从不影响输出，因为每个输出的 token 都由验证窗口决定。投机写入的格子也从不碰索引器状态，到位置被重新处理时直接覆盖。代码事实

验收清单

测试投机解码，不能只看平均接受率。至少覆盖：全部拒绝、全部接受、中途拒绝、接近上下文上限、遇到结束符、中途取消、开着重复惩罚、请求之间切换采样参数。比较的对象是“同一段固定历史下不开投机的参考结果”：logits、提交后的状态和最终 token 都要一致。新增任何序列状态时，按 18.4 节的四个问题逐项回答，并补上对应的测试。
