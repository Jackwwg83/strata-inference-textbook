你可能注意到过

看 Strata 写字，有时会觉得它是“一蹦一串”地往外冒，而不是一个字一个字地挤。README 的说法是：一个小帮手先猜后面几个词，大模型一次把这些猜测全部检查一遍，所以同样的答案能快 1.6–1.8 倍。上游报告[S01]

上游文档还说，模型自带的猜测层一次最多猜 3 个 token。上游报告[S02] 问题来了：猜对的 token 等于白赚，为什么不一次猜 10 个？这一章回答两件事：猜几个最划算，以及接受率一直在变时，引擎怎样边跑边改主意。

一句话：多猜一个 token，期望多拿到的部分按几何级数越来越少，验证一轮的时间却一直在涨。Strata 比较的是“每毫秒期望提交几个 token”，并用指数移动平均边跑边更新接受率。

19.1 猜一次、验一次：一轮能拿到几个 token

先复习第 18 章的投机解码：先便宜地猜，再让大模型批改。负责猜的是模型自带的 MTP 层（multi-token prediction，多 token 预测层），它猜出的候选叫草稿。上游报告[S02]

大模型把“上一个已确定的 token + k 个草稿”排成一排，48 层只走一遍，就能同时给出每个位置“我认为这里该是什么”。这一排叫验证窗口，长 k + 1。图 19-1 走一遍 k = 3 的例子。

规则很简单：从左往右比，第一个不一致的地方就停。前面一致的草稿全部接受，再加上大模型在停下处自己的答案。所以接受 a 个草稿，这一轮就提交 a + 1 个 token。Strata 的生成循环正是这样数的：逐个比对窗口里的草稿和大模型的输出，再调用 commit(a + 1)。代码事实

就算一个都没猜对，这一轮也有大模型自己的 1 个 token，和不猜时一样多。猜错不会让答案变差，因为每个字都由大模型拍板。上游报告[S02] 猜错的代价只有一个：这一轮的验证白白多算了几个位置。

19.2 平均一轮拿几个：期望值登场

每一轮接受几个草稿，事先说不准。我们能算的是平均一轮拿几个，也就是期望值。

设第 i 个草稿的条件接受率是 pᵢ：在前面 i − 1 个都被接受的前提下，第 i 个也被接受的概率。“前提”两个字很要紧：前面一旦有一个被拒，后面的根本轮不到比对。

第 i 个草稿能派上用场，要求前 i 个全部接受，概率是 p₁ × p₂ × … × pᵢ。把每个位置“派上用场的概率”加起来，就是一轮期望提交的 token 数：

E = 1 + p₁ + p₁p₂ + … + p₁p₂…pₖ

开头的 1 是大模型自己的那个 token，每轮必得。Strata 的源码就是这样一项一项乘、一项一项加的。代码事实[S09] 如果每个位置的接受率都一样，都是 p，这个和就是一个等比数列的前 k + 1 项。下面的专栏讲它为什么会“越加越没劲”。

期望值与几何级数

直觉：期望值就是“做很多很多次以后的平均结果”。掷一个公平的骰子，单次可能是 1 到 6 中的任意一个，平均下来是 3.5。期望值的定义是：每种结果乘以它的概率，再全部加起来。

算“一轮拿几个 token”时，有一个更省事的办法：把每个位置“被用上的概率”加起来。位置 1 必定用上，概率 1；位置 2 用上的概率是 p；位置 3 是 p²……于是 E = 1 + p + p² + … + pᵏ。这种每一项都是前一项乘同一个数的和，叫几何级数（等比数列求和），有现成的公式：E = (1 − pᵏ⁺¹) ÷ (1 − p)。

所以多猜的收益是递减的：p = 0.86 时，第 8 个草稿只贡献 0.86⁸ ≈ 0.30 个 token。等比数列还有一个上限：项数趋于无穷时，和趋于 1 ÷ (1 − p)。p = 0.86 时，就算猜无穷多个，一轮平均也只有约 7.1 个。

延伸阅读：OI Wiki：期望 · 维基百科：期望值 · 维基百科：等比数列

学过计算机的同学：把“一轮提交的 token 数”记作随机变量 N，上面的算法就是概率论里的尾和公式 E[N] = Σ P(N ≥ i)。它对任意分布都成立，所以推导时用不着假设各位置相互独立，只要用条件概率连乘。

代入 Strata 的数字。源码给 MTP 每个位置的初始接受率都是 0.86，注释说这来自在同一个模型上的测量。代码事实[S09] 猜 3 个时 E = 1 + 0.86 + 0.74 + 0.64 ≈ 3.24。上游文档报告的实际情况是：一次验证平均提交 2.4–3.2 个 token。上游报告[S02] 两者在同一个量级，说明 0.86 是个说得过去的起点。真实接受率随文本变化，这一点 19.4 节细讲。教学推演

19.3 账的另一半：窗口越宽，验证越贵

如果验证不花时间，当然是猜得越多越好。可验证是要时间的。Strata 的成本模型 step_ms 把一轮的时间拆成四块：代码事实[S09]

  • 稠密部分：注意力等每个 token 都要算的部分。窗口越宽，这部分越慢，源码用一张按窗口长度查的倍率表。
  • CPU 算专家：没缓存在显卡上的专家由 CPU 算（第 10 章讲过）。窗口里的 token 越多，用到的不同专家越多，CPU 越忙。
  • 同步：每轮固定的协调开销。
  • 起草：MTP 层猜每个草稿也要时间。

这几块的默认值写在头文件里：稠密部分 11 ms，480 个专家全在 CPU 上算要 15.8 ms，显存命中率 55%，同步 2.4 ms，每个 MTP 草稿 1.2 ms。注释说，倍率表这类默认值来自 9 月 23 日的测量，11 ms 是计划里的目标值，引擎里应换成实测值。代码事实 图 19-3 把这些默认值代进公式，看四块怎样随窗口变宽。

注意 CPU 那一块。9 个 token 如果各自用一套互不相同的专家，CPU 的活儿应该是 1 个 token 时的 9 倍。源码里的倍率表却只到 5.2 倍，注释说这张表来自路由轨迹的测量。代码事实 同一个窗口里的 token 经常选中同一批专家，这正是第 10 章说的“热门专家”在起作用。

有了分子和分母，目标就清楚了：速度 = 一轮期望提交的 token 数 ÷ 一轮的时间。控制器对每个 k 都算一遍，挑速度最大的那个。代码事实[S09] 下面的交互图把这个计算摊开给你看。

这张图的数字是把源码默认值代进公式算出来的，不是实测：不猜时一轮 20.5 ms，每秒 48.8 个 token；猜 3 个时一轮 44.4 ms，期望 3.24 个，每秒 72.8 个。教学推演 它说明的是形状：曲线有一个山顶，山顶的位置取决于接受率和成本。

还有一道门槛。最好的窗口必须比不猜快 5% 以上，控制器才会用它；否则宁可不猜。代码事实[S09] 头文件注释把这 5% 写成计划里的设定。代码事实 这样做的好处是：接受率的估计本身有误差，只快一两个百分点的“收益”很可能是误差造成的假象。

19.4 接受率会变：边跑边学

0.86 只是起点。写代码时，后面的内容常常能从前文猜出来；写一首新诗，就难猜得多。上游文档也提到，同一个提示词换一个回答，输出速度就能差好几个百分点，因为被接受的草稿多少变了。上游报告[S03] 所以接受率必须边跑边估计。Strata 用的工具叫指数移动平均。

指数移动平均（EMA）

直觉：你想知道最近的平均气温，但不想存下每天的记录。办法是只记一个数“估计值”，每来一个新温度，就把估计值往新温度挪一小步：

新估计 = 旧估计 + α × (新数据 − 旧估计)

这就是指数移动平均，α（0 到 1 之间）叫更新权重。展开来看，最新的数据权重是 α，上一个是 α(1 − α)，再上一个是 α(1 − α)²……越旧的数据权重越小，按指数衰减，名字由此而来。它只需要一个数的内存，每次更新一次乘法、两次加减。

α 决定了取舍。α 大，估计跟得快，但容易被一两次偶然结果带偏；α 小，估计稳，但变化来了要很久才反应过来。一个好用的量是半衰期：旧数据的权重降到一半要多少次更新，等于 ln 0.5 ÷ ln(1 − α)。α = 0.05 时约 13.5 次，α = 0.3 时不到 2 次。

Strata 的控制器正是用这个式子更新每个位置的接受率：接受记 1，拒绝记 0。代码事实[S09] 头文件里 α 的默认值是 0.05。代码事实

延伸阅读：维基百科：移动平均 · Wikipedia: Exponential smoothing · RFC 6298：TCP 重传计时器

学过计算机的同学：《计算机网络》里 TCP 估计往返时间（RTT）用的就是 EMA：SRTT ← (1 − 1/8) × SRTT + 1/8 × 新的 RTT 样本，见 RFC 6298。估计接受率和估计网络延迟，是同一类问题：数据有噪声，环境会变，内存还要省。

记账时还有一个陷阱。假设这一轮猜了 3 个，第 1 个就被拒了。第 2、3 个草稿怎么记？它们根本没被比对过，是没观测到，不是“失败”。统计学把这种“结果没被看到”的情况叫删失。

Strata 的 observe 只更新被接受的那些位置，加上第一个被拒的位置；后面的位置一律不动。代码事实[S09] 还有一个反方向的情况：一轮猜的全部被接受，窗口外的位置也没被试过。如果永远不更新它们，窗口就再也长不大。源码的办法是把这些位置的估计往“最深一个已观测位置”的估计挪一小步。代码事实[S09]

19.5 Strata 真正在跑的是哪一个

到这里讲的控制器在 src/spec/controller.cpp 里。它编译进 strata_spec 库，有自己的单元测试 controller_test。代码事实 但打开生成主程序 generate.cpp（它就是可执行文件 strata 的源码），它引入的是另一个头文件 draft_policy.hpp，生成循环调用的是 DraftPolicy。本书检查过的引擎源码里，没有找到对 Controller 的调用。代码事实 图 19-7 把两者并排放。

先说 MTP 这一侧。生成循环里，MTP 的窗口长度来自启动参数 --spec，除第一轮外每轮固定；只有设置了 --spec-min-p 时才会缩短：草稿层对某个草稿的把握低于这个门槛，就不再往窗口里加。代码事实 上游文档的说法是 MTP 一次最多猜 3 个。上游报告[S02]

DraftPolicy 管的是另一件事：提示词查找（prompt lookup）。如果正在写的内容重复了上下文里的某一段，比如改代码时照抄原来的几行，那么上次那段后面跟着什么，这次多半也一样，可以直接拿来当草稿。查找草稿最多 5 个，而且只在实测的接受率和成本都说划算时才用。上游报告的效果是：改代码快 6–11%，普通文本不变。上游报告[S02] 生成循环里还有一个前提：启用 MTP 时，查找草稿的第一个 token 必须和 MTP 自己的第一个草稿一致，才交给 DraftPolicy 判断。代码事实

DraftPolicy 的算法仍是这一章的公式：查找一侧 E(k) = 1 + q + q² + … + qᵏ，q 是按“匹配了多长”分桶统计的接受率；MTP 一侧直接用实测的每轮平均产出。分母不再是公式，而是每种窗口长度实测的每轮耗时，用 α = 0.1 的 EMA 平滑；没测过的长度，按一条预设的形状曲线从测过的长度换算。查找窗口要比 MTP 窗口快 3% 以上才会被选中。代码事实

这是一个很好的工程教训：成本模型写得再细，也比不上直接测。机器不同、上下文长度不同，每轮的时间都会变；实测值天然跟着机器走。

19.6 动手：自己找最佳窗口

打开本章的交互实验「草稿值得猜多长」。它用一个更简单的成本式：基线时间加上每个草稿固定的验证和起草成本，每个位置用同一个接受率 p，比较 k = 0 到 5 的期望 token 数、时间和净收益。

  1. 把 p 设成 0：所有 k 的期望都是 1，草稿只加时间。最佳答案应该是 k = 0。
  2. 把 p 设成 1：期望正好是 k + 1。看看这时最长的窗口是不是总赢。
  3. 保持 p 不变，把草稿成本调大：找到最佳 k 退回 0 的那个点。

做完再回到本章的两个交互图对照。实验里的成本是一条直线；Strata 的成本模型里，专家共享让 CPU 那一块涨得比直线慢，而稠密部分的倍率在窗口长到 5 个 token 时跳了一大步。成本曲线的形状不同，山顶就会挪位置。

记住这三点

  1. 一轮期望提交 E = 1 + p₁ + p₁p₂ + …：每多猜一个，贡献再乘一次接受率，收益递减。p = 0.86 时，猜无穷多个也超不过 7.1 个。
  2. 该优化的是速度 = E ÷ 一轮的时间。窗口越宽，验证越贵，所以速度曲线有山顶；还要比不猜快出一截才值得猜。
  3. 接受率要边跑边估计，用 EMA：α 大反应快但抖，α 小稳但慢。没被比对的位置是“没看到”，不能记成失败。

常见误解：“接受率越高，速度一定越快。”

接受率只是分子的一部分。假设换一个更聪明但更慢的草稿方法，每轮期望从 2 个涨到 2.5 个，可每轮时间从 10 ms 涨到 15 ms：速度从每秒 200 个降到约 167 个。教学推演 判断草稿方法好不好，要看每毫秒提交几个 token，不能只看猜对了多少。

深入一层：条件概率、删失、探索与验收标准

期望公式不需要独立假设

pᵢ 定义为“前 i − 1 个都接受时，第 i 个也被接受的条件概率”。第 i 个草稿有贡献，当且仅当前 i 个都接受，其概率由条件概率的乘法公式直接得到 p₁p₂…pᵢ，不需要宣称各位置相互独立。例：p = [0.8, 0.6, 0.5]，E = 1 + 0.8 + 0.48 + 0.24 = 2.52。如果起草加验证一轮 18 ms，速度约 140 token/s；不猜一轮 8 ms，速度 125 token/s，净收益约 12%。这些是教学例题，不是 Strata 的跑分。教学推演

源码的 expected 有两种用法：MTP 用逐位置的数组；查找草稿每个位置用同一个 q，即等比数列。代码事实[S09]

成本模型逐项

step_ms(k) 中 n = k + 1，被截到 1 到 K_MAX + 1 之间。稠密部分 = dense_ms × dense_ratio[n−1]。CPU 部分 = (1 − 命中率) × cpu_all_miss_ms × U × (1 + extra_use_cost × (n ÷ U − 1))，其中 U 是窗口里不同专家的数量相对单个 token 的倍数，n ÷ U 是每个专家平均被几个 token 用到。起草部分 = k × 每个草稿的时间。代码事实[S09] 头文件给出的默认值：K_MAX = 8；extra_use_cost = 0.25，意思是每多一个 token 用同一个专家，只多花一次读取的 25%；查找草稿每个 0.01 ms，几乎免费。代码事实

把“权重只读一次”的理想情况无条件套到所有草稿上，会高估收益；完全不考虑专家复用，又会低估。U 的具体值取决于路由，必须测。

先验不是物理常数

MTP 的初始接受率 0.86 和查找草稿按匹配长度分桶的先验 {0.35, 0.6, 0.8, 0.92}，都只是起点。注释说前者来自在同一模型上的测量，后者来自离线回放，之后都按会话学习。代码事实[S09] 换语言、换量化、换任务，草稿质量和专家复用都会变。DraftPolicy 的查找先验另成一套：{0.75, 0.88, 0.93, 0.96}，每个先验折合 4 次观测，几轮真实数据就能盖过它；旧观测每轮乘 0.97 衰减。代码事实

删失、窗口外的位置与“探索”

第一个草稿被拒后，后面的位置不在“前缀都已接受”的条件下，属于未观测。把它们记为 0，会形成自我强化：窗口越短，深位置越显得差，控制器越不愿再试长窗口。全部接受时则相反：窗口外的位置从未被测试，源码把它们往最深已观测位置的估计拉，否则窗口永远长不大。代码事实[S09]

单看 Controller 的两个函数，还有一个值得注意的边界：选了“不猜”之后，observe 会直接返回，估计不再更新。代码事实[S09] 如果噪声把估计一度压到门槛以下，单靠这两个函数就再也学不回来，需要调用方另行探索。（本章模块里有一个测试专门演示了这一点。）DraftPolicy 有显式的探索：一个没测过耗时的查找窗口，只要接受率估计不低于 0.85，前 3 次会被直接试用；注释说验证保证了输出不变，赌上的只是这一轮的速度。代码事实

输出会不会因为草稿而变

原理上不会：每个提交的 token 都是大模型自己的选择。但上游文档指出一个浮点层面的例外：使用 IQ 量化的模型时，CPU 算一个 token 的专家和算多个 token 的专家用不同的内核，舍入略有不同；而一个专家被几个 token 共享，取决于验证窗口里的草稿。所以温度为 0 时，同一个提示词也可能得到另一个同样合理的回答。设置 STRATA_IQ_MT_MIN=1 后，所有分组都用多 token 内核，答案就不再依赖草稿。上游报告[S03]

验收标准

检验一个窗口控制器，边界比一条漂亮的曲线更有说服力：

  • 草稿成本很高时，能退回 k = 0。
  • p = 0 时，额外草稿不产生任何虚假收益。
  • p = 1 时，E 恰好等于 k + 1。
  • 未观测的位置不被计为失败；全部接受时，窗口外的位置能被拉高。
  • 只比不猜快不到门槛时，保持不猜。
