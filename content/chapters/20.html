20.1 为什么多轮不必每次从头算？

若新输入严格包含已经处理过的相同前缀，就可以从对应状态继续处理新增尾部。省掉的是重复计算，不是省略输入含义。关键在于前缀的内容与执行配置相容，而不是文本“看起来差不多”。

conversation_prefix 检查 ID 序列及前缀范围内的图像身份；缓存匹配还考虑 steering 模式。其匹配条件要求 checkpoint 长度小于 prompt 长度，因为最后一个 prompt token 要启动后续验证窗口。[S10]

20.2 多模态身份为何不能只靠 token？

两个请求可以含相同的 image_pad 标记，却对应不同图片。如果只用 token IDs 命中缓存，图像语义就被错换。当前 ConversationImageKey 包含 start 和 hash，强调图像身份进入匹配条件。[S10]

同理，一个生产系统扩展还需考虑模型权重版本、tokenizer / 模板、RoPE、量化、设备数值模式与授权域。这些是本教材提出的扩展检查清单。源码的 geometry 数组自己说明只是运行时兼容性，不是模型权重身份或磁盘 schema，不能用它替代全部身份键。[S10]

20.3 一份快照要包含什么？

读到的 checkpoint 包含 IDs、图像、GDN、PLE、tail、block position 等；KV 部分又有格式、页信息、量化 scale 和 pooled indexer；草稿层状态也可能参与。[S10] 这解释了为什么把 KV 文件保存一下并不足以声明“任意对话可无损恢复”。

不同设备分层还会有 stage_parts；固定接口说明普通分层 checkpoint 与整会话 parking 的支持边界不同。[S10] 不能从“支持多 GPU”推导“每种缓存与恢复组合都支持多 GPU”。

20.4 例题：同前缀分叉需要写时隔离

会话 A、B 共享前 1000 个 token。随后 A 写入 token a，B 写入 b。只读共享前缀可以节省复制，但第 1001 个位置及可变递归状态必须独立。若两个 session 直接指向同一可写状态，一次请求就会污染另一次。

教学设计可以采用 immutable prefix pages + reference count + copy-on-write；GDN 则按所需边界复制完整递归状态。这是扩展设计，不是声称上游已经具备完整多租户 COW 系统。

20.5 数据库思维：原子可见与预算

恢复时先校验身份和完整性，再获得目标容量，再安装完整状态，最后发布可用。任何阶段失败，不应暴露半份新状态。对磁盘快照可以用临时文件完成后原子发布，再加校验和与版本；实际持久性语义还要按文件系统确定。[R02]

当前会话缓存的容量核算包括 vector capacity 和 retained reuse 缓冲，并使用避免减法下溢的条件检查。[S10] 容量算法若漏算保留的物理缓冲，逻辑上只停了两条会话也可能用尽 RAM。

20.6 实验与验收

为相同 token、不同图片；相同前缀、不同 steering；不同模型版本；恰好等长 prompt 等案例写出应命中 / 应拒绝的矩阵。注意“上游已检查”和“扩展要求”分列。

恢复测试采用 A→保存→B→恢复 A→继续，与 A 从未离开的参考结果比较。再注入截断快照、错误格式、预算不足及未完成 commit。安全的失败结果是明确拒绝而保留原状态，不是继续生成貌似合理的文字。
