你可能注意到过

把一份长文档丢给聊天 AI，第一个问题要等好一会儿才开始回答。接着追问，回答几乎马上就冒出来。Strata 的文档也这么写：第一条消息之后，它会留住这段对话，只读新加的部分，所以追问几秒钟就能开始。上游报告[S02]

引擎“留住”的到底是什么？两次请求差一个字、换一张图，它还敢不敢复用？两个对话开头相同、后面分岔，能不能共用一份？这一章讲前缀复用、快照和写时复制。

一句话：Strata 把读过的前缀存成检查点（一种快照），新请求的 token、图片和 steering 模式与检查点一字不差时，就从检查点接着读新增的尾巴。快照必须装下全部运行状态，只存 KV 缓存不够。

20.1 追问为什么快：不重读已经读过的

多轮对话有个特点：每次请求都把整段历史再发一遍。第 5 轮的请求，开头就是第 1 到第 4 轮的全部内容，最后才是你的新问题。新内容往往只占一小截，前面一大段是前缀，也就是和上一次请求开头完全相同的那部分。

如果每次都从第一个 token 读起，长对话会越聊越慢。聪明的做法像读书夹书签：上次读到哪，这次从哪接着读。这种做法叫前缀复用，在引擎里也常叫 prompt cache（提示缓存）。

省下多少？Strata 读长文本的速度是每秒 1,000 个 token 以上。上游报告[S02] 源码注释里也算过一笔账：一段 3 万 token 的系统提示，按每秒约 1,000 个读，要约 30 秒。上游报告 图 20-1 把两种做法放在一起比。

接上检查点本身也有成本：检查点存在内存里，要搬回显卡。一个检查点约 118 MB（下一节解释为什么），按第 10 章用过的 PCIe 5.0 理论带宽约 63 GB/s 算，118 ÷ 63 ≈ 2 毫秒。教学推演 和 30 秒比，可以忽略。

上游文档还提醒了一个副作用：提示缓存会让重复的请求只读尾巴，走的计算路径和从头读不同，回答可能和从头读时不完全一样。想要逐字节相同的输出，要用 --prompt-cache 0 等参数关掉它。上游报告[S03]

20.2 什么才算“同一个前缀”

复用的前提是：检查点代表的历史，和新请求的开头完全相同。“看起来差不多”不行。差一个 token，后面每个位置的计算结果都会跟着变。

Strata 用一个叫 conversation_prefix 的函数做这个判断，再加上会话缓存挑选时的一项检查。代码事实[S10] 合起来是四条规则：

  1. steering 模式相同。steering 是一种可选的“控制向量”，开启后会改动模型许多层的中间结果。两边模式不同，检查点里的状态是按另一种方式算出来的，直接跳过。
  2. 检查点比请求短。请求的最后一个 token 必须真的读一遍，用它启动下一轮验证。所以和请求一样长的检查点反而不能用。
  3. 前缀里的 token 编号逐个相同。
  4. 前缀里的图片身份相同。图片在 token 序列里只是一串占位符，同样的占位符可以对应完全不同的图。所以引擎为每张图另记一个身份：起始位置加内容哈希。代码事实[S10]

学过数据结构的同学：判断“检查点是不是请求的前缀”就是字符串前缀比较；在一堆检查点里找最长的那个前缀，正是字典树（trie）和基数树擅长的事。Strata 的源码注释直接拿基数树作比，见 20.4 节。

20.3 快照里要装什么：笔记本能翻回去，白板不能

检查点是一种快照：把某一时刻的全部状态拍下来，以后可以回到那一刻，像游戏存档。要存什么，取决于模型“记住”历史的方式。Strata 用的模型 48 层里有两种层，记历史的方式完全不同。代码事实[S04]

  • 12 个注意力层（QSA）用 KV 缓存。每读一个 token，就按位置往后记一行，像笔记本。想退回某个前缀，后面几行不用管：验证器的说明写得很直白，被拒绝的位置以后重新处理时会被直接覆盖，在任何查询读到它们之前。代码事实[S08]
  • 36 个 GDN 层用递推状态。每读一个 token，就把一块固定大小的状态原地整块改写，像白板。代码事实[S17] 读完第 5 个 token，第 4 个 token 时的样子就擦掉了，再也算不回来。

白板有多大？每个 GDN 层的状态是 128 × 48 × 128 个 32 位浮点数，36 层合计 36 × 128 × 48 × 128 × 4 字节 ≈ 113 MB。教学推演[S04][S17] 不管对话多长，这块白板的大小都不变。KV 笔记本则越写越厚：如果按每个数 2 字节存，12 层每个 token 要 12 × 2 × 2 × 256 × 2 字节 ≈ 24.6 KB，3 万 token 约 737 MB。教学推演

所以 Strata 的检查点主要存白板：GDN 递推状态，加上 PLE（每层嵌入）的历史、注意力索引器的尾部等几块小状态，再记下这段前缀的 token 编号和图片身份。代码事实[S10] 上游文档说一个检查点约 118 MB，上游报告 和白板的 113 MB 对得上：大头就是它。

20.4 一条检查点链：根钉住，其余轮换

引擎什么时候拍照？上游文档写的是：每个新的助手回合开始时拍一张，长提示每读 16K 个 token 再拍一张；内存里最多留 6 张。上游报告

这些检查点有个特别的形状。显卡上的 KV 缓存只有一块区域，一次只能装一条历史分支。所以留下来的检查点都必须是当前历史的前缀，按长度排好，每一个都是下一个的前缀，连成一条链。源码注释把它比作基数树：一棵树压扁到会话能装下的那一条分支上。代码事实

链满了，淘汰谁？早期的做法是先进先出，最早的检查点最先被扔。可最早的那个往往是系统提示的末尾，也就是同一个客户端每次新开聊天都会经过的地方。扔掉它，每个新聊天都要把系统提示从头再读一遍。代码事实

现在的规则是：根钉住，其余按最近最少使用（LRU）轮换。源码里的淘汰函数只有几行：容量不足 2 个时关掉钉住，扔最老的；否则跳过第 0 个，在剩下的里面挑最久没被用过的。代码事实 上游文档还补了一条：从头读的提示，如果系统提示有 2,048 个 token 或更多，也会在系统提示末尾拍一张，好让根存在（引擎 0.1.20 起）。上游报告 第 12 章会细讲 LRU 这类缓存替换策略。

20.5 两个对话共用一个开头：写时复制

再看一个更难的场景：对话 A 和 B 开头完全相同（比如同一段系统提示加同一份文档），然后各问各的。能不能让它们共用前缀，只为不同的部分花钱？操作系统和数据库早就有一个经典答案。

快照与写时复制

想给一份数据拍快照，最笨的办法是整份复制。数据有 1 GB，就复制 1 GB，慢，还占双倍空间。可大多数时候，快照和原件之后只改了很少几处。

写时复制（copy-on-write，简称 COW）换了个思路：先不复制，两边共用同一份数据，给每块数据记一个引用计数，也就是“有几个人在用”。谁要往一块共用的数据里写，谁才把这一块复制一份，改自己的副本。没人改的块，永远只有一份。图 20-5 是一个三页的例子。

最有名的例子是 Linux 的 fork()：创建子进程时只复制页表，父子进程共用全部物理内存页，并把它们标成只读。谁先写某一页，就触发一次缺页异常，内核这时才复制那一页。所以 fork 一个占几 GB 内存的进程，也几乎是瞬间完成。文件系统的快照、数据库的多版本并发控制（MVCC），用的都是同一个思路。

回到本章：两段对话的共同前缀，就是“没人改的页”。只要前缀里的 KV 页只读不写，就可以放心共用。下面的模拟器让你亲手试。

延伸阅读：维基百科：写入时复制 · Linux 手册：fork(2) · OSTEP（公开操作系统教材，虚拟内存各章） · 维基百科：多版本并发控制

模拟器揭示了两件事。第一，KV 页可以共用，但前缀没填满的最后一页会被两边写，必须复制。第二，递推状态（白板）怎么都没法共用：它每个 token 都整块改写，分叉时只能整份复制。

那 Strata 自己怎么做？它没有在两个对话之间共用页。源码在存放快照数据的缓冲区上写明：快照和它保留下来的缓冲区只有一个主人，所以不需要共享，也不需要写时复制。代码事实 前面说过，显卡上的 KV 区域一次只装一条历史分支，一条链就够用了。写时复制在这里是我们的教学扩展，不是 Strata 的实现。

不过 Strata 有一个相近的省钱技巧。它可以把几个对话“停”在内存里（这个功能默认关闭，要手动打开），每个停着的对话存一整份快照，包括运行状态、检查点、用过的 KV 页和草稿层的 KV（不带草稿层运行时，就没有最后这一份）。上游报告 一个对话被恢复后，没改过的 KV 页可以留着，下次再停车时直接用，不必重新拷贝；对话变长时只在后面追加，不搬动已有的页；被回退改写过的页才重新拷贝。上游报告 这和写时复制的精神一样：没变的东西不复制。

20.6 动手：存、切、恢复，再对一遍

快照恢复有一条铁律：要么完整装回，要么明确拒绝。装回一半的状态最危险，模型会照样生成看起来通顺、其实全错的文字。Strata 的做法是先校验所有层、所有检查点，全部合格才开始写入；校验不过的快照在任何显卡操作之前就被拒绝。如果搬运途中出错，接口要求调用方不得继续用这个会话推理。代码事实

学过数据库的同学：这就是事务的原子性：要么全部生效，要么像没发生过。第 18 章讲过投机解码里的“只提交接受的前缀”，这里是同一个思想用在会话恢复上。

打开本章的交互实验「只提交接受前缀」。它用一个玩具递推 s ← 0.5s + t 演示：候选状态和已提交状态为什么不同，只把计数器往回拨为什么会留下错误的状态。把第二份草稿设成被拒绝，找出那个“计数器回退了、状态没回退”的位置。这正是白板不能靠“假装没写”来回退的原因。

想更进一步，可以自己设计一个不用显卡的测试：用同一个玩具递推跑对话 A，存快照；切去跑对话 B；再恢复 A 继续。最后和“A 从来没离开过”的结果逐位比较，两者必须完全相同。

记住这三点

  1. 前缀复用只认“一字不差”：token 编号、图片身份、steering 模式全都相同，检查点还要比请求短，才能接着读。
  2. KV 缓存像笔记本，回退时忽略后面几行即可；递推状态像白板，每个 token 整块改写，只能靠事先拍下的检查点回退。Strata 的检查点大头就是约 113 MB 的 GDN 状态。
  3. 写时复制让多个分支共用没人改的页，只复制被写的那一页。Strata 用一条“根钉住、其余 LRU 轮换”的检查点链，停车的对话各自独占缓冲区，没有用写时复制。

常见误解：“把 KV 缓存存下来，就等于存下了整段对话。”

对 Strata 用的模型来说远远不够。48 层里有 36 层靠递推状态记历史，它不在 KV 缓存里。此外还有 PLE 的历史、注意力索引器的尾部、草稿层的 KV，以及这段前缀的 token 编号和图片身份。代码事实[S10] 少存任何一样，恢复出来的对话都会悄悄算错。

深入一层：匹配规则、快照清单、容量核算与恢复契约

匹配规则的源码细节

conversation_prefix 先要求检查点非空、长度严格小于请求长度、前 n 个 token 编号逐个相等，否则返回 0。然后遍历请求里的图片：起始位置不在前缀内的跳过；在前缀内的，必须与检查点记录的图片依次相等（起始位置和哈希都相等）；最后检查点记录的图片也必须恰好用完。多一张、少一张、换一张，都返回 0。代码事实[S10]

会话缓存挑检查点时，从最近停放的条目往前找，steering 模式不同的条目直接跳过；每个条目既考虑它的当前状态，也考虑它的每个检查点，取匹配最长的那个。长度相同时，优先选最近停放的分支；调用方在同样长度下还会优先用自己手上正在用的状态。代码事实[S10]

身份清单：上游已检查的，和本书建议的

上游检查的是 token、图片身份和 steering 模式。快照里还有一个 18 个整数的 geometry 数组，源码注释明确说它只用于运行时兼容性检查，不是模型权重的身份，也不是磁盘格式。代码事实[S10] 两个模型形状相同、权重完全不同，geometry 也一样。

如果把这套机制推广到生产环境（快照落盘、跨进程共享、多用户），本书建议身份键至少再加上：模型权重版本、分词器与聊天模板、RoPE 设置、量化格式、设备数值模式、以及授权范围（谁的对话只能给谁用）。这是教学扩展清单。上游只在 v0.1.40 的会话文件（见本节末尾）上做了其中一部分：文件头记着一个模型指纹和一个配置指纹。模型指纹抽样每个模型文件的大小和首尾各 1 MiB；配置指纹覆盖引擎版本、CUDA 还是 HIP、KV 格式、RoPE 设置和会改变计算结果的开关。有一个对不上，就拒绝恢复。代码事实 内存里的停放缓存仍只查 token、图片身份和 steering 模式。

一份快照的完整清单

检查点（ConversationCheckpoint）包含：token 编号、图片身份、GDN 状态、PLE 历史、索引器尾部（tails）、dead、block_pos 等字节块，以及分层运行时每个设备的子检查点 stage_parts。KV 部分（ConversationKv）有格式编号、单元数、头数、头维度、页大小、索引器行数，以及 K、V、各自的量化缩放系数和 pooled 索引行。整段对话的快照（SavedConversation）再加上 geometry、层范围 layer_lo / layer_hi、当前状态、检查点列表、主层加草稿层的 KV，以及 steering 标志。v0.1.39 还加了 stage_images：分层运行时，后面每个阶段各自的一份快照。代码事实[S10]

注意多 GPU 的边界。v0.1.38 时，整段会话停车只支持单 GPU：打开停车再加 --layer-split，会在加载模型前被拒绝。v0.1.39 取消了这个限制：每个分层阶段各存一份快照，全部校验通过后才开始写入，再在各自的卡上恢复。上游在 4 卡上测过：一段 9,276 个 token 的对话 51 毫秒就恢复了，之后解码出的 token 和对话从没离开时完全相同。上游报告 停车时，每个检查点按阶段拆开，恢复时再拼回去；源码里有一对函数做这件事，注释要求“拼回(拆开(x)) == x”。代码事实[S10] 可同一个文件第 28–29 行的旧注释还写着“整段会话停车目前只支持单 GPU，会拒绝这些子检查点”。这又是一处注释落后于代码的例子：注释和代码说法不一致时，以代码和测试为准。代码事实[S10] 上游文档也提醒：Windows / HIP 和多 GPU 上的运行证据，要和 Linux / CUDA 的证据分开报告。上游报告 不能从“支持多 GPU”推出“每种缓存与恢复组合都在多 GPU 上验证过”。

容量核算：按容量算，防下溢

快照的字节数按各个 vector 的 capacity() 累加，而不是 size()：已经申请但还没用满的空间也算在内。代码事实[S10] 能否放下新快照的判断写成 held <= budget_ && incoming <= budget_ - held && …，每次减法之前先确认不会减成负数。无符号整数减出负数会绕回一个巨大的正数，预算检查就形同虚设。保留下来复用的 KV 也计入同一个预算。代码事实[S10]

腾空间时，先扔掉保留复用的 KV，再按停放先后淘汰最老的条目。代码事实 上游文档还要求物理内存至少留出 --conversation-cache-min-free-mib（默认 2560）的余量，分配前查一次、拍完再查一次；查不到内存数据就不停车。上游报告 对应的判断函数把“查不到”和“查到 0”明确区分开：没有数据时直接拒绝。代码事实 默认预算是 0，也就是不启用；文档举的例子是 8 GiB、4 个槽位，并说明这是上限，不是推荐值。上游报告

恢复契约与持久化

快照接口把恢复结果分成三种：成功、快照无效、搬运失败。无效的快照在任何 CUDA 调用和写入之前就被拒绝；搬运失败可能留下半份状态，调用方不得继续用这个会话推理。代码事实 上游文档说，搬运或同步失败按致命错误处理；停放在内存里的快照不会在重启后保留。上游报告

如果要把快照存到磁盘，常见的稳妥做法是：先写临时文件，写完、刷盘、校验和通过后，再用一次原子的重命名“发布”出去，并在文件里记录格式版本。具体的持久性保证还取决于文件系统。[R02] v0.1.40 加了可选的会话文件，走的正是这条路：启动服务时给 --slot-save-path 一个目录，就能把当前会话存成文件，重启后再恢复；默认关闭。上游报告 存盘时先写一个隐藏名的临时文件，刷盘，再把它重命名成正式的文件名；在 POSIX 系统上还要再刷一次目录。重命名之前出错，旧文件原样保留。文件头有魔数、格式版本号和两个指纹，数据后面还有一个哈希；版本号不认识就拒绝。代码事实 恢复也守上面那条铁律：所有检查都在写显卡之前做完，被拒绝时当前会话保持原样。上游报告

KV 页复用的边界

快照接口有一句容易被忽略的注释：token 编号相同，不能证明 KV 字节没变。“未改变的 token 数”只对真正从快照恢复进本会话、并且之后每次改写都已扣减过的存储有效。代码事实 会话缓存里对应的函数每遇到一次改写，就把“未改变的长度”收缩到第一个被弄脏的位置，缩到 0 就整块丢弃。代码事实[S10]

存放快照数据的缓冲区由 16 MiB 的段组成，追加时不搬动已有的数据，只有很小的段目录可能移动。代码事实 这就是“变长只追加、不拷贝已有页”的底层支撑。

例题：同前缀分叉为什么需要写时隔离

会话 A、B 共享前 1000 个 token。随后 A 写入 token a，B 写入 b。只读的共享前缀可以不复制，但第 1001 个位置以及可变的递推状态必须各自独立。如果两个会话直接指向同一份可写状态，一次请求就会悄悄污染另一次。教学设计可以用“不可变前缀页 + 引用计数 + 写时复制”；GDN 递推状态则要在分叉点整份复制。
