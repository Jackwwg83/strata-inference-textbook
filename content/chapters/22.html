你可能见过

下载开源软件时，发布页上常常排着一串文件：windows-x64、linux-x64、macos-arm64……同一个程序，为什么要准备这么多份？

Strata 的 README 开头写着：NVIDIA 或 AMD 显卡，Windows 或 Linux。上游报告[S01] 它的原理文档说得更干脆：在 NVIDIA（CUDA）和 AMD（HIP）显卡上，跑的是同一个引擎，只是各自编译一次。[S02] 这一章回答两个问题：同一份源码，怎样变成能在不同机器上跑的程序？“能跑起来”又证明了多少？

一句话：每种芯片只懂自己的指令。Strata 只写一份源码，靠编译开关、条件编译和一张 CUDA→HIP 的“改名表”，编出 NVIDIA 版和 AMD 版两个引擎；CPU 这边则在启动时先问清 CPU 会哪些指令，再挑 AVX-512 或 AVX2 内核。能编译、测试通过、真卡跑通、维护者验证，是四级不同的证据。

22.1 同一份菜谱，三种厨房

想象你写了一份菜谱，要寄给三家餐馆。一家用燃气灶，一家用电磁炉，一家只有烤箱。菜谱上的“炒三分钟”，每家都得翻译成自己设备上的操作。

程序也一样。程序员写的是源代码：人能读懂的文字。芯片真正执行的是机器码：一串二进制指令。芯片能执行哪些指令、每条指令怎样编码，由它的指令集规定，相当于“这个厨房里有哪些电器”。把源代码翻译成某一种指令集的机器码，是编译器的活。

图里的 sm_120、gfx1100 是显卡架构的编号，相当于厨房的型号。Strata 的构建脚本要求 NVIDIA 显卡的计算能力至少是 7.5，也就是 RTX 20 系列及更新；AMD 这边只收一份明确的名单，名单外的架构直接报错。代码事实 v0.1.39 另开了两条实验路径：给 Pascal、Volta 老卡的 CUDA 12 引擎，和给 gfx906 的单独构建。22.3 节会讲到它们。上游报告

编译器、指令集与条件编译

指令集是硬件和软件之间的契约：芯片承诺“我认识这些指令”，软件只能用这些指令说话。同一个家族的芯片会不断加新指令。比如 x86 CPU 家族先有了 AVX2，后来又加了更宽的 AVX-512。老芯片遇到不认识的指令，会直接报“非法指令”并让程序崩溃。

编译器把源代码翻译成机器码。C 和 C++ 的编译分两段：先由预处理器做文字加工，再由编译器本体做翻译。预处理器干三件事：把 #include 的文件原样贴进来；把 #define 定义的宏按名字替换掉，像“查找替换”；按 #if 的条件只留下一个分支，其他分支整段删掉。最后这一招叫条件编译。

这正是 Strata 在 AMD 显卡上做“四字节点积”的写法：RDNA3、RDNA4 显卡用一条 sudot4 指令；RDNA2 没有这条，改用老一些的 sdot4；RDNA1（gfx1012）连 sdot4 也没有，就用一小段汇编，以 4 次乘法、2 次三数相加拼出同样的结果；其他情况退回一个逐字节相乘再相加的循环。四条路算出的整数一模一样，快慢不同。代码事实 22.3 节会亲手编译它。

学过计算机的同学：《编译原理》课讲的是词法分析、语法分析、代码生成这条主线；预处理发生在这一切之前，是纯文本加工，不懂语法。所以宏替换出了错，报错位置常常很怪：编译器看到的已经是替换之后的代码。

22.2 CPU：先问清会哪些指令，再挑内核

第 10 章讲过，显卡没缓存的专家，由 CPU 在内存里就地计算。上游文档的概括是：这些计算用 AVX-512 或 AVX2 内核，i-quant 格式的模型用 ggml 的内核。上游报告[S02] 源码里分得更细：i-quant 格式在一组有多个 token 时，也会改用 Strata 自己的多 token 内核。代码事实 这里的内核，指一段专门写来跑得飞快的核心计算代码。

AVX2 和 AVX-512 都是 SIMD 指令：一条指令同时处理一排数（第 13 章细讲）。区别在于这一排有多宽。AVX2 的寄存器是 256 位，AVX-512 是 512 位，见图 22-3。

麻烦在于：如果整个程序都用 AVX-512 编译，编译器可能在任何地方插入 AVX-512 指令，程序到了老 CPU 上就会崩。Strata 的构建脚本只给几个内核源文件加上 AVX-512 或 AVX2 的编译开关（GCC 写作 -mavx512f 这类参数，MSVC 写作 /arch:AVX512）。负责“探测 CPU”的那个文件不加，所以在任何 x86-64 CPU 上都能安全运行。代码事实

  • 没有 AVX2，现成的引擎不启动。Strata 自己的 CPU 专家内核最低都要 AVX2、FMA 和 F16C，发布版里的 ggml-cpu 也按 AVX2 编译。引擎会报出 CPU 型号，说明需要 Intel Haswell（2013 年）、AMD Zen（2017 年）或更新的 CPU。v0.1.39 起，提示还多一句：更老的 CPU 可以让 setup 在本机现场编一个实验版引擎（STRATA_ISA_FLOOR=avx 或 none）。这个版本的 ggml-cpu 按 AVX 或 SSE4.2 编译，CPU 那份专家全交给它算。代码事实 上游的安装文档说，这个版本只能跑 i-quant 模型，而且很慢：在 Ryzen 5 7600 + RTX 5070 上强制走这条路、专家缓存固定为 1500 个槽位时，解码从每秒 26 个 token 降到 11–17 个（AVX 版）和 3.5–3.8 个（SSE4.2 版）。上游报告
  • 标准 Q2_0 包只有 AVX-512 内核。上游安装文档说，setup 只在 AVX-512 CPU 上为 Q2_0 额外写出一份约 40 GB 的专家副本，给这个快速内核用。上游报告 头文件的注释把为什么要在启动时就拒绝说得很直白：让老 CPU 的用户在第 0 秒就知道原因，而不是到第 4000 个 token 时撞上一条非法指令。

学过计算机的同学：这是“运行时分派”，和面向对象里的虚函数一个思路：调用的地方不变，真正执行哪段代码，到运行时才定。区别是这里的依据不是对象类型，而是 CPUID 返回的功能位。

22.3 GPU：一份 CUDA 写法，编出 NVIDIA 和 AMD 两个引擎

CPU 这边，一个程序文件里装两套内核，运行时挑。GPU 这边走得更远：NVIDIA 和 AMD 的显卡指令完全不同，连编程平台都不同，只能为每家各编一个引擎。

CUDA 与 HIP

CUDA 是 NVIDIA 的 GPU 编程平台：一套 C++ 扩展语法、一套运行时函数库，加上编译器 nvcc。程序员用它写在 GPU 上并行执行的函数，再用 cudaMalloc、cudaMemcpy 这类函数申请显存、搬运数据。CUDA 只能编出 NVIDIA 显卡的机器码。

HIP 是 AMD 在 ROCm 平台上提供的对应物。它有意照着 CUDA 设计：函数名大多只把前缀 cuda 换成 hip，比如 cudaMalloc 对应 hipMalloc，语义基本一致。所以一份 CUDA 代码，常常只要“改名”就能在 AMD 显卡上编译。AMD 官方还提供了自动改名的工具 HIPIFY。

改名之外，还有改不掉的差异。GPU 把一组线程捆在一起同步执行，NVIDIA 叫 warp，AMD 叫 wavefront（简称 wave）。NVIDIA 的一组固定是 32 个线程；AMD 的老架构是 64 个，RDNA 系列可以是 32 个。依赖“一组 32 个”的代码，搬到 64 的机器上就会出错。Strata 的 HIP 后端只支持 wave32，启动时还会再查一遍。代码事实 v0.1.39 给 wave64 的 gfx906 另加了一个手动打开的构建：它走另一套兼容层，把 CUDA 的一个 warp 对应到 64 线程 wavefront 的一半，而且和 HIP 后端只能二选一。上游报告 线程、warp 这些概念，第 15 章会细讲。

和本章的关系：Strata 没有用工具把源码改写一遍，而是把一张“改名表”在编译时自动塞进每个源文件。下面马上看它怎么做。

Strata 的 GPU 代码按 CUDA 的写法写，放在 .cu 文件里，src 目录下有 55 个。打开 HIP 构建开关后，发生三件事：代码事实

  1. 构建脚本把所有 .cu 文件标成 HIP 语言，交给 AMD 的编译器。
  2. 编译参数里加上 -include hip_compat/cuda_runtime.h，把这份垫片头文件强行塞到每个源文件的最前面。这里的垫片（shim），指夹在两层之间、专门抹平差异的一薄层代码。
  3. 垫片里有 88 行形如 #define cudaMalloc hipMalloc 的宏；其中几个名字按 HIP 版本或平台给了两种写法，每次编译只留一种。另一份 cublas_v2.h 垫片再管矩阵库的名字：新版 hipBLAS 用 17 行，老版本（0.x）另有 15 行，直接换成更底层的 rocBLAS 的名字。预处理器一替换，CUDA 的名字就变成了 HIP 的名字。

光改名还不够。有些 CUDA 的显卡内置函数，HIP 在 RDNA 显卡上没有现成的，垫片只好自己实现。比如四字节点积 __dp4a：把两个 32 位整数各拆成 4 个有符号字节，对应相乘再加到累加器上。垫片按显卡架构分四路（见 22.1 节的专栏）。再比如 warp 内交换数据的 __shfl_xor_sync：垫片先检查“32 条通道是否全部参与”，不是就立刻中止，而不是悄悄丢掉这层语义。代码事实

22.4 “能编译”离“支持”还有多远

假设你的显卡架构在名单里，引擎也编出来了。这算“支持”吗？Strata 自己的构建脚本给出了很细的回答。它把 AMD 架构分成三档，CMake 配置时对每档的态度不同：代码事实

  • 维护者验证：gfx1100（RX 7900 XT / XTX）和 gfx1201（RX 9070 系列、Radeon AI PRO R9700），维护者在真卡上跑过。
  • 用户验证：gfx1101 和 gfx1200，由显卡的主人跑通并回报。配置时只打一行提示。
  • 未验证：gfx1012、gfx1102、gfx1030 和 gfx1031 能编译，配置时给出警告，请用户回报结果。gfx1102 通过了自带测试，但还没有人报告过完整的模型运行；gfx1030 有一台社区机器跑通了，维护者还没亲自验证。gfx1012（RX 5500 XT，RDNA1）和 gfx1031（RX 6700 XT）是 v0.1.39 新加的，各有一位用户在自己的卡上跑过。上游报告

第二个陷阱是数值。图 22-5 里的 dp4a 是整数运算，每条路都逐位相同。浮点运算就不同了：加法的先后顺序一变，最后几位就可能不同（第 4 章讲过浮点数的舍入）。Strata 的 AMD 文档明说：不承诺两个后端给出逐位相同的回答。上游报告 同一台机器上也会这样。用 IQ 系列模型时，CPU 单独算一个 token 用 ggml 的点积，成组算用 Strata 的多 token 内核，两者舍入略有不同；一组有几个 token 又取决于草稿。所以温度为 0 时，同一个提示词也可能得到另一个同样合理的回答。引擎 0.1.30 起可以设置 STRATA_IQ_MT_MIN=1 消除这一差异，代价是上游在 Ryzen 7600（AVX-512）上测得 IQ3_S 解码慢 1–3%。上游报告[S03]

所以构建配置是实验条件，和硬件一样要写进报告。同一个提交，开不开 STRATA_PORTABLE，ggml 的 CPU 部分就会按“任何 AVX2 CPU”或“本机 CPU”来编；改一个环境变量，就换了一条计算路径。代码事实 再看 README 里的速度表：Q2_0 模型在 RTX 5070 的机器上每秒写 94 个 token，在 RX 9070 XT 的机器上每秒 60 个。上游报告[S01] 表下的说明只写了 NVIDIA 这台的条件：Q2_0 用引擎 0.1.36 测，其余几行用 0.1.26 测，写答案按 4K 测，读题按 32K 测；AMD 那台没写引擎版本。v0.1.39 的发布说明还特意交代，这张表这次没有重测。两台机器的 CPU 也不同：一台是 Ryzen 5 7600，有 AVX-512；一台是 Ryzen 9 3900X（Zen 2），只有 AVX2。这组数字说明“两台机器都能跑”，却不能拿来比较 NVIDIA 和 AMD 谁快。

22.5 动手：把一行源码交给两个后端

本章没有单独的交互实验，两个模拟器就是实验台。建议按这个顺序玩：

  1. 在「一份源码，两个后端」里依次编译 RTX 50、RX 7900、RX 6900。对比预处理之后的三行：哪些名字换了，dp4a 落到了哪条分支。再看例题结果是否始终是 95。
  2. 选“名单外的架构”，体会 CMake 为什么宁可在第一步拒绝。
  3. 在「CPU 内核选择器」里固定 CPU 和模型包，只改环境变量和 token 数。数一数：同一台机器上能走出几条不同的计算路径？

手边有 C 编译器的同学，可以再做一个小实验：写一个标量的点积函数，再写一个每 8 个数一组累加的版本。用同一组随机浮点数比较两者的结果和耗时。你会看到最后几位不同。先确认逻辑正确，再谈性能；数组太小时测出的速度，代表不了真实的 SIMD 内核。

22.6 边界：许可证、模型和这本教材自己

“可移植”还有一层意思：代码、模型和文档，各自能被谁拿去、怎么用。Strata 仓库的代码采用 MIT 许可证。代码事实[S19] 仓库里少数部分另有许可证：third_party/ggml 来自 llama.cpp / ggml（MIT），网页应用用的字体是 SIL 开放字体许可证。模型文件不在仓库里，每个模型适用它自己的许可证。上游报告[S02]

这本教材本身是一个静态网站：HTML、CSS 和 JavaScript，不含推理引擎，也不下载模型权重。把它部署到任何网页托管服务，只是在发布课程，并不等于在那台服务器上运行了 Strata。教材里的交互图都是教学模拟：它们复刻了 Strata 源码里的判断逻辑，却不是 Strata 的内核，也不预测任何真实机器的性能。

引用上游代码时，本书记录固定的提交号，不重新打包上游的字体或模型，并说明这是一本独立编写的教材，没有获得原项目或模型厂商的官方认证。

记住这三点

  1. 芯片只懂自己的指令集。同一份源码，要为每种目标各编译一次；条件编译让一份源码在每次编译时只留下与目标相符的分支。
  2. Strata 在 CPU 上运行时分派：先用 CPUID 问清有没有 AVX-512、AVX2，再挑内核。在 GPU 上编译时分派：一张 CUDA→HIP 的改名表加几段自写的内置函数，编出 NVIDIA 版和 AMD 版两个引擎。
  3. 能编译、测试通过、真卡跑通、维护者验证，是四级不同的证据。浮点结果跨后端也不保证逐位相同，构建配置和环境变量都要当作实验条件记录下来。

常见误解：“代码在我的显卡上能编译通过，就说明支持我的显卡。”

编译通过只说明编译器认得这段代码。Strata 的构建脚本里就有现成的反例：gfx1102 能编译，也通过了自带测试，但还没人报告过完整的模型运行，所以配置时照样给出“未验证”的警告。真正的支持，要靠在真卡上跑真模型、结果对得上，并且有人能复现。

深入一层：编译期与运行期的分工、垫片的边界与支持声明

为什么 AVX-512 开关只加在单个文件上

构建脚本的注释说明了理由：一个用 /arch:AVX512 编译的源文件，编译器可以在任何地方使用 AVX-512 指令，包括你以为是“退路”的那段标量代码。如果把标量退路和 AVX-512 内核放在同一个文件里，退路就不再是退路，在老 CPU 上一样会崩。所以 Strata 只给内核文件加开关；探测 CPU 的函数放在不加开关的文件里，保证“问一问”这一步在任何 x86-64 CPU 上都安全。代码事实

探测本身也用了条件编译：同一段 CPUID 代码，MSVC 编译器用 __cpuidex 和 _xgetbv，GCC/Clang 用 __cpuid_count 和内联汇编 xgetbv。检查 XCR0 寄存器，是确认操作系统在线程切换时会保存 AVX-512 的大寄存器；CPU 支持而系统不保存，照样不能用。代码事实

垫片的边界：宁可中止，不可悄悄改语义

CUDA 的 warp 交换函数带一个“哪些通道参与”的掩码参数。HIP 的对应函数没有这个参数。垫片的做法是：当前内核只用全掩码，所以遇到不是全掩码的调用就直接中止（__builtin_trap），而不是把掩码丢掉继续算。__nanosleep 在 CUDA 里按时钟周期计数，AMD 的休眠指令只接受 0 到 15，垫片干脆统一用最小值 1，因为这里只把它当作“稍等一下”的提示。代码事实

dp4a 的四条路也各有讲究。RDNA3/RDNA4 的 sudot4 指令能分别指定两个操作数是否有符号，垫片把两个都标成有符号，才和 CUDA 的 __dp4a 语义一致。RDNA2 的 sdot4 本来就是“有符号 × 有符号，按 2³² 取模累加”，语义相同。RDNA1 的汇编先把每个字节符号扩展再相乘（v_mul_i32_i24），再用 v_add3_u32 每次把两个乘积加进累加器；32 位无符号加法本身就是模 2³²。这段写法改编自 llama.cpp；打开编译开关 STRATA_GFX1012_PORTABLE_DOT，gfx1012 就改用可移植循环，方便对照。可移植循环用无符号 32 位整数累加，再按有符号解释，结果同样是模 2³²。本章模拟器的测试文件逐一核对了 RDNA1 汇编、可移植循环和 NVIDIA 老卡的软件循环，在溢出边界上也和参考值逐位相同。

名字不决定格式：按类型分派

同一个张量名，在不同层可能用不同的量化格式。layer.cpp 的注释记录了一次教训：早期代码假设“名字决定格式”，比如 attn_qkv 一定是某种 K-quant；实际的模型包里，36 个 GDN 层的 attn_qkv 有 IQ4_XS、Q3_K、Q2_0、Q4_K 四种。规则因此改成按类型分派：2 位编码走 Q8_0 激活，其余量化格式走 Q8_K。用错了，矩阵向量乘法的误差是 0.6%–1.4%：算出的是一个“看起来合理”的向量，而不是一个明显坏掉的向量，最难发现。代码事实[S14]

依赖也要钉死

Strata 的 CPU 专家用 ggml-cpu 的点积，构建时从 llama.cpp 仓库拉取 ggml。拉取的不是“最新版”，而是 third_party/ggml/VERSION.txt 里写死的一个提交号。代码事实 道理和本书固定 Strata 的提交号一样：依赖一变，数值路径就可能变。

一份最小的支持声明

为一个新后端写支持声明时，至少写清：

  • 源码提交号；编译器及版本；目标架构列表；全部编译开关；依赖库的版本；运行时的环境变量。
  • 测过的设备、驱动、模型包、量化格式、KV 格式、预填充和解码两种路径、上下文长度范围。
  • 证据按层级分列：编译通过、自带测试通过、张量级对比（与参考实现的误差）、端到端质量、稳定性、性能。
  • 没测过的组合明确列为“未测”，不写“全面支持”。

两个二进制即使来自同一个提交，编译开关不同，也可能走不同的代码路径。启动日志应当说出实际用了哪个后端、哪条 CPU 路线、有没有回退；Strata 在没有 AVX-512 的 CPU 上启动时，就会打印它改用了 AVX2 还是 ggml。代码事实 用户不该靠文件名去猜。
