你可能注意到过

聊天网页上有个“停止”按钮。你一点，字立刻不动了。可是，显卡真的停了吗？

Strata 的源码里有一段很坦白的注释（问题编号 #430、#431）：以前，客户端挂断以后，那个请求还会让引擎一直忙下去，直到答案写完，或者整段提问读完。屏幕上早就停了，显卡还在为一个已经离开的人干活。这一章讲三件事：一个请求怎样出生、怎样结束；“停”字怎样一层层传到显卡；以及谁有资格让你的显卡干活。

一句话：一个请求要穿过浏览器、HTTP 连接、服务进程、引擎进程四层。“停止”是一个要层层传递、层层确认的信号；“认证”决定谁能把请求送进来。

24.1 点了“停止”，到底停了什么

从你点下按钮，到显卡不再为这个请求计算，中间隔着好几层。每一层“停了”的意思都不一样，见图 24-1。

为了把这件事讲清楚，先给请求画一张状态机：请求在任何时刻都处于某一个状态，只有特定的事件能让它换到另一个状态。下面是本书的教学版本：

  • 排队：请求到了，但引擎正在服务别人。Strata 一次只服务一个序列，后来的都在 FIFO（先进先出）队列里等。[S15]
  • 读题：引擎一块一块地读你的提问（第 1 章讲过的 prefill）。
  • 生成：一个 token 一个 token 地写答案。
  • 完成 / 已取消 / 失败：三个终点。每个请求最后都必须落到其中一个，不能悬着。
  • 取消中：已经喊了“停”，但引擎还没确认停下。这个中间状态最容易被忽略。

这些状态名是本书的抽象，不是上游代码里的枚举。Strata 实际记录的是一个请求是“排队中”还是“生成中”，再加一句阶段说明，比如“正在读提问”“正在回答”。代码事实 下面的模拟器把整个过程放慢了：

24.2 进程与线程：到底是谁在干活

要知道“停”字该传给谁，得先知道活是谁在干。

进程与线程的生命周期

进程是一个正在运行的程序，操作系统给它分配一块独立的内存，还有打开的文件、网络连接等资源。两个进程默认看不到对方的内存，只能通过管道、网络等渠道互相传消息。进程结束时，操作系统把它占的内存、显存一并收回。

线程是进程里的一条执行路线。一个进程可以有好几个线程，它们共享同一块内存，所以交换数据很方便，但也容易互相踩脚。

两者都有生命周期：创建、运行、等待（比如等网络数据）、结束。结束的方式分两种：自己走完，或者被别人结束。在类 Unix 系统里，一个进程可以给另一个进程发信号：SIGTERM 是“请你退出”，对方有机会先收拾一下；SIGKILL 是“立即结束”，对方没有任何机会清理。

和 Strata 的关系：服务器和引擎是两个进程，靠管道一行一行地传文本；服务器内部又有好几个线程分工，见图 24-3。

延伸阅读：维基百科：进程 · 维基百科：线程 · OSTEP：进程（英文） · Python 文档：subprocess · man 7 signal

服务器用 Python 的 subprocess.Popen 启动 strata --serve，把它的标准输入和标准输出都接成管道。代码事实 引擎加载好权重后，会先写几行 INFO，再写一行 READY 加上下文长度；如果这一行还带着 stop，说明这个引擎版本支持中途停止。服务器读到 READY，才把引擎当作“活着”。之后，服务器写一行 GEN 命令提交一个请求，引擎回 T（一个 token）、PP（读题进度）、DONE（结束）或 ERR（出错）。

还有一个专门的读取线程，把引擎的每一行输出放进队列。这样，处理请求的线程就能“带超时地”等待下一行：等不到，可以先发个心跳、检查一下取消标志，而不是一直傻等。代码事实

引擎进程也会意外结束。代码里专门有一个 EngineDied 异常，注释写着最常见的原因：在 Linux 上，被内存不足时的 OOM killer 结束了。[S15] 这时当前请求以错误收尾，下一个请求到来时，服务器用同样的命令重新启动引擎。

正常关闭引擎也有讲究。服务器分三步走，每一步最多等 20 秒，见图 24-4。

注释解释了为什么第一步是 QUIT：引擎会自己释放内存，而解除几十 GB 锁页内存的锁定需要一些时间。代码事实 如果三步都失败，服务器抛出 EngineStuck，并且继续保留这个进程的记录，不会宣称它的显存和内存已经还回来了。另外，在 Windows 上，服务器把引擎放进一个设置了“关闭即结束”的作业对象。这样，即使你直接关掉控制台窗口，引擎也会随之结束，不会变成没人管的孤儿进程。代码事实

24.3 取消：把“停”一层层传下去

取消：为什么只能“请你停下”

最直接的取消方式，是从外面把正在干活的线程掐断。可这很危险：它可能正拿着一把锁、正写到一半的数据结构、正借着一块显存。被掐断后，锁没人释放，数据半新半旧，后面的人全都会出错。

所以实际系统大多用协作式取消：外面只负责设一个取消标志，干活的一方在约好的检查点上看一眼标志，看到了就自己收拾干净再退出。Python 的 threading.Event、Go 的 context、C# 的 CancellationToken 都是这个思路。

由此得出两条规律：第一，取消不是瞬间完成的，最坏要等到下一个检查点；第二，检查点隔得越远，取消越慢。所以“喊了停”和“真的停了”是两回事，中间那段就是图 24-2 里的“取消中”。

延伸阅读：Python 文档：threading（Event 对象） · OSTEP：并发与线程（英文） · 维基百科：多线程

Strata 的取消就是协作式的。每个请求开始时，服务器创建一个 threading.Event 作为取消标志。有两条路能把它设上：

  • 写不出去：服务器往连接里写 SSE 事件时出了错，说明客户端走了，立刻设标志。注释写着：“客户端走了：停掉引擎。”代码事实
  • 监视线程：光靠写出错还不够。读一段长提问时，服务器很久才写一次保活注释，而且挂断后的第一次写入通常还会“成功”。所以每个请求另起一个监视线程，每 0.5 秒检查一次连接：如果连接显示“可读”，却读不到任何数据，就说明对方关闭了，设标志。代码事实 这正是开头提到的 #430、#431 的修复。

标志设上以后，要靠检查点生效，见图 24-5。

第 ⑤ 步的检查点在哪里？生成时，每产出一个 token，循环就看一眼标志。读题时，引擎是一块一块读的：prefill.hpp 里的 should_stop 在每一块开始之前检查一次，返回真就提前结束，错误信息是 “cancelled”。代码事实[S12] 服务器的注释也写明：读题过程中发出的 STOP，要等当前这一块读完才会被看到。一块最多可以有 32768 个 token。[S15] 交互图里的“最坏要等多久”就是按这个算的。

第 ⑥ 步同样重要。STOP 发出后，服务器要继续读引擎的输出，一直读到这个请求自己的 DONE，而且全程拿着 FIFO 锁。注释解释了原因：如果提前放手，引擎队列里还残留着上一个请求的 DONE，下一个请求就会把它当成自己的结束信号。代码事实 这一步也有时限：等 STOP 的回音时绝不无限期地等，因为等待期间 FIFO 一直被占着，后面所有人都在排队。

测试时用的 MockEngine 也遵守这个约定：每吐一个 token 前，先看一眼取消标志。[S15] 所以取消逻辑可以在没有显卡的机器上测。

24.4 卡住了怎么办：看门狗

取消依赖引擎“配合”。如果引擎卡死了，一句话都不说呢？服务器需要一只看门狗：一段时间没有动静，就判定出了问题。

难点在于“多久算太久”。引擎生成时，每个 token 都会写一行，很热闹；读一段很长的提问时，却可能好几分钟一声不吭。看门狗如果一刀切，要么误杀正在认真读题的引擎，要么对真正卡死的引擎等上半天。Strata 的做法是按阶段给不同的时限 [S15]：

  • 基础时限 300 秒：请求进行中，引擎超过这么久没有任何输出，就判定失联。配置里可以改，设成 0 表示永远等。
  • 读题的第一块：在 300 秒之上，再按“最慢的电脑每秒只读 50 个 token”加上这一块的时间。
  • 读完一块以后：下一块最多可以用上一块实际耗时的 3 倍，但不少于 300 秒。

图里的数字是代入代码常量算出来的。教学推演 第一块：300 + 32768 ÷ 50 ≈ 955 秒。快的电脑按上游实测的每秒 2171 个 token 读一块 32768 个 token，约 15.1 秒，3 倍是 45.3 秒，不到 300 秒，所以时限仍是 300 秒；慢的电脑每秒 100 个，一块要 327.7 秒，3 倍约 983 秒。

超时以后怎么办？注释里管这叫“两边失步”：引擎的主线程在等下一条命令，服务器却在等这个请求的结束。服务器结束引擎进程，这个请求以错误收尾，下一个请求到来时重新启动引擎。[S15] 结束进程虽然粗暴，好处是显存和内存一定会随进程一起还回来。

更底层也有同样的思路。负责验证草稿 token 的 Verifier 有一个 release_gpu_waits：显卡上的一批计算卡住、无法正常结束时，它把显卡上所有等待的标志强行放行，让这批计算排空。但从此以后，这个 Verifier 拒绝再执行任何新的计算窗口，因为那批计算是在不可信的条件下跑完的。代码事实[S08] 强行排空不等于正常完成，不能装作什么都没发生，继续服务下一个请求。

24.5 谁能用你的显卡：认证与 API Key

前面讲的是“怎样停”。这一节讲“谁能开始”。如果别人能随便往你的 Strata 发请求，你的显卡就成了公共资源。

认证与 API Key

认证回答“你是谁”，授权回答“你能做什么”。最简单的认证方式是 API Key：服务器和客户端事先共享一串很长的随机字符，客户端每次请求都在 HTTP 头部带上它，常见写法是 Authorization: Bearer 密钥。服务器比对一致就放行，不一致就回 401。

API Key 就像一把共用的钥匙：谁拿到谁就能开门，所以它必须保密，不能写进网页源码、不能提交到公开仓库。网络传输最好走 HTTPS，否则路上的人能看到它。

比对本身也有讲究。普通的字符串比较一旦遇到不同的字符就立刻返回，猜对的前缀越长，比较花的时间就越久。攻击者测量时间，就能一位一位地猜出密钥。这类利用耗时、功耗等“副产品”泄露信息的攻击叫旁路攻击，这一种叫计时攻击。防法是用恒定时间比较：不管从哪一位开始不同，都把整串比完再返回。

延伸阅读：维基百科：API 密钥 · 维基百科：旁路攻击 · MDN：Authorization 头 · Python 文档：hmac.compare_digest · RFC 6750：Bearer 令牌

Strata 的第一道防线是默认只听本机：服务器默认监听 127.0.0.1，别的设备根本连不上。代码事实 这时 README 告诉你，应用里随便填一个 API Key 都行。[S01] 想从手机或另一台电脑访问，就要改成监听 0.0.0.0，README 的原话是“一定要带上密钥”。[S01] 如果你改了监听地址却没设密钥，服务器启动时会打出一行警告：没有 API Key，网络里的任何人都能用这个模型。代码事实

设了密钥以后，访问 /v1/* 的请求必须带上它：写成 Authorization: Bearer …，或者写在 x-api-key 头里（Anthropic 风格的客户端用这个）。比对用的是 hmac.compare_digest，代码注释写着“恒定时间”；比对失败回 401，类型是 authentication_error。代码事实 整个判断过程见图 24-7。

真实世界里，每次比较只差几纳秒，网络抖动却有几毫秒，所以真正的攻击要对同一个猜测重复测量成千上万次，再用统计方法把差别挖出来。这很难，但并非做不到。用 hmac.compare_digest 只是一行代码的事，没有理由冒这个险。

Strata 还防了一种更隐蔽的攻击：DNS 重新绑定。你打开的某个恶意网页，可以把自己的域名临时指向 127.0.0.1，然后以“自己网站”的身份访问你本机的服务。所以在没设密钥时，服务器只回应 Host 头是它认识的名字的请求，比如 localhost 和 IP 地址；带着陌生网页来源的 POST 请求也会被拒绝。设了密钥以后，就由密钥说了算，因为别人的网页拿不到你的密钥。上游报告

24.6 动手：亲手取消一次

本章没有单独的实验页，两个交互图就是实验。按顺序做三件事：

  1. 在生命周期模拟器里，分别在排队、读题、生成三个状态按“取消”，记下“最坏要等多久”。读题阶段要等约 15.6 秒，生成阶段只要约 0.51 秒。想一想：如果你来设计，怎样让读题阶段也能更快停下？代价是什么？
  2. 按取消后，在“取消中”按“引擎失联”。看看服务器怎样收场，为什么等 STOP 的回音也必须限时。
  3. 在计时攻击模拟器里，用两种比较方式各破解一次，数一数分别要试多少次。

如果你会写 Python，可以用 Strata 自带的 MockEngine（python -m serve.server --engine mock）在没有显卡的机器上起一个服务，用 curl 发一个流式请求，中途按 Ctrl+C 断开，再看服务器窗口里这个请求的结局。[S15]

记住这三点

  1. 一个请求要穿过浏览器、HTTP 连接、服务进程、引擎进程和显卡。每层“停了”的含义不同，取消信号要一层层传下去，并且要确认。
  2. Strata 的取消是协作式的：监视线程每 0.5 秒查一次连接，设下取消标志；引擎在检查点停下，服务器读到这个请求自己的 DONE 才释放 FIFO。读题时检查点隔得远，取消就慢。
  3. Strata 默认只听本机。对外开放时必须设 API Key，比对用恒定时间的 hmac.compare_digest，防止计时攻击。

常见误解：“关掉网页，显卡就停了。”

关掉网页只停了最上面一层。服务器要先发现连接断了，再通知引擎，引擎还要走到下一个检查点才会停。Strata 在修复 #430、#431 之前，就出现过客户端早已离开、引擎还在一直算的情况。“停了”要在每一层分别确认。

深入一层：取消的线性化点、迟到的旧回包与信任边界

取消从哪一刻起算“生效”

可以把取消定义为：从某个已经确认的边界开始，不再向用户提交新的 token，并且相关资源最终停止使用。这个边界就是取消的线性化点。只设了一个标志、还没被读题的分块循环或生成循环看到时，取消并没有完成。

按本书对 serve/server.py 的阅读，一个还在排队的请求，要等拿到 FIFO 锁、把 GEN 命令发给引擎之后，才会在等待引擎输出的循环里检查取消标志：收到第一行 token 或读题进度时，或者等满 10 秒没有输出时。代码事实 这意味着一个早已挂断的排队请求，仍会让引擎开始读它的提问，之后才收到 STOP。一个值得做的扩展练习：拿到锁之后、发命令之前，先检查一次标志。

例题：超时后的旧回包

请求 A 超时，服务开始处理请求 B。如果 A 迟到的结果仍然写进共享的输出队列，B 就可能收到 A 的 token，或者把 A 的 DONE 当成自己的结束。解决方向是给输出加上归属校验，并且在旧执行确认结束之前，不复用同一份可变状态。

Strata 的做法正是后者：发 STOP 之后，一直读到这个请求自己的 DONE，全程拿着 FIFO 锁；统计用量时，也只认这个请求期间到达的 DONE，否则一个出错或断开的请求，会把上一个请求的解码数字记成自己的。代码事实 本书没有审计上游所有的输出归属路径；课堂上可以用一个故意延迟的 mock 引擎构造这种风险，再验证修复。

看门狗要懂工作阶段

把“暂时没有文字输出”一律当成死锁，会误杀正在读长提问的健康请求；永远等待，又会堵死整个 FIFO。合理的诊断要能区分：排队、合法的长计算、慢速 I/O、子进程失联、协议失步，并且报告状态和最后的进度，而不是只给一个含糊的“超时”。Strata 按读题分块调整时限，并把失联原因写进错误信息，就是这个思路。[S15]

同理，“显式的模型控制”（加载、卸载）不能打断正在运行或排队的请求：代码里为此专门定义了 ModelBusy。[S15] 上游文档说明，这时控制接口返回 409。上游报告

工具、图片 URL 和本地文件都是信任边界

模型输出是不可信输入。工具参数要经过结构校验和权限检查；获取远程 URL 牵涉对外访问和资源限制；读取本地路径牵涉文件权限和路径范围。Strata 的图片输入支持 base64 数据、http(s) URL 和本地文件路径三种来源。[S15] 是否防住了 SSRF、路径穿越等问题，要逐个入口审计，不能因为某处用了一个安全的库，就断言整体安全。

在 mock 引擎里注入这些情况：读题时取消、输出中断、重复取消、引擎无响应、旧结果迟到、恢复后再次请求。验收条件：不再提交新的用户可见 token；所有读写相关缓冲的任务都已停止或完成；队列和状态不会被下一个请求误用；迟到的旧输出能被识别并丢弃；资源只释放一次；客户端得到明确的“已取消”或“失败”，而不是“成功”。
