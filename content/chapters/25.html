25.1 先划清现状与设计

固定上游服务文件写明 FIFO 后一次处理一个序列。[S15] 用户曾说明自己修改过 Strata 的多并发能力，但该 fork 源码不在本次审阅输入中。本章提出多用户扩展设计与验收方法，不声称已经审计或实现了那个 fork。

HTTP 同时连接数、排队请求数、活跃生成序列数、同一 kernel 内处理的序列数，应分别计数。四个数字可以完全不同。多开线程不自动解决 KV、GDN、PLE、随机数和临时缓冲的隔离问题。

25.2 首先隔离可变状态

只读权重和只读缓存内容在适当同步下可以共享；每个序列的 token 历史、KV 页映射、GDN 状态、PLE、采样参数、随机计数器和取消标记必须有明确归属。当前 SessionState 是权重之外序列状态的良好阅读入口。[S13]

共享 scratch 是否安全取决于调度是否保证互斥。若原先假设“各层永不并发”的 scratch 被两个会话同时使用，代码原来正确也会立刻失效。改并发时应列出所有单序列假设，而不是仅寻找一个全局 mutex。

25.3 例题：权重不乘五，状态可能要乘五

教学预算：共享权重与缓存占 20 GiB，每条序列状态 2 GiB，共享 scratch 2 GiB，reserve 2 GiB。五条活动序列需要约 20+5×2+2+2=34GiB，而不是 5×24=120 GiB，也不是仍然只需 24 GiB。

若五条同时需要独立 scratch，2 GiB 应再按实际并发分配计算。若 context 长短不同，每条状态也不同。准入控制必须在承诺活动序列之前原子预留预算，不能先全收进来再指望 allocator 不失败。

25.4 调度不是只追求总 token/s

FCFS 简单，但长请求会阻塞后面的短请求；轮转改善首次响应公平性，却增加切换成本，可能拖慢短任务完成。continuous batching 把不同序列的当前位置组合计算，还需要动态加入、退出、页管理和变长掩码。

浏览器调度实验只模拟已就绪的 decode 作业，用固定 token 服务时间比较 FCFS 与轮转。它不模拟真实 GPU batching，也不包含 prefill、MTP、prefix hit 或异构竞争，因此不能用图里的倍率宣传真实系统。

25.5 一个小算例

请求长度 [8,3,5]，同时到达，单 token 1 ms，不计切换。FCFS 的完成时间为 [8,11,16] ms，首 token 为 [1,9,12] ms。按量子 1 轮转时，首 token 为 [1,2,3] ms，短请求更早开始，但总工作仍为 16 ms。

若每次切换还需保存或恢复较大 GDN 状态，过小量子会显著增加成本。公平不是免费的；应同时看首次响应、完成时间、吞吐和状态搬运量。

25.6 多并发验收必须击中串状态风险

设计 A/B 两条不同语言或任务的固定请求，分别独立运行得到参考，再交替或并行运行。覆盖 A 取消时 B 继续、A 长 prefill 时 B decode、相同前缀不同图片、会话恢复、预算只够最后一个槽的并发抢占。

最小通过条件是正确隔离、无超预算承诺、无重复结束、无旧 generation 输出、无长请求饥饿。只有提高总吞吐而出现偶发串上下文的系统，不是合格的并发推理服务。
