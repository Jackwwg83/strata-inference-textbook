先想一个场景

你在家里的电脑上跑起了 Strata，室友、同学也想用。五个人同时打开网页提问。Strata 的 README 写得很直白：它一次只回答一个请求。上游报告[S01] 那么，第五个人要等多久？如果其中一个人让它写一篇长文，其他四个人是不是都得干等？

这一章是一堂设计课。上游 Strata 只在一个先进先出的队列后面服务一条序列；多用户调度不是它的功能，而是我们要动手设计的扩展。我们先用调度算法和排队论算清“等多久”，再看把单序列改成多序列，到底要动哪些东西。

一句话：谁先上、等多久、能不能一起算，是三个不同的问题，分别由调度策略、排队论和批处理回答；而动手改造之前，必须先把每条序列的状态隔离干净。

另一方面，HTTP 服务器用的是 Python 的 ThreadingHTTPServer，每个连接一个线程，所以五个人可以同时连上。连上不等于被服务，见图 25-1。

上游也有一个和“多会话”沾边的功能：可以选择打开一个容量受限的会话停车区，在内存里最多停放几段对话的状态，让交替到来的请求不必每次从头读题。但文档明确说，它不会并发执行请求。上游报告 管理这些停放会话的代码，复用的条件也很严格：token 完全一致、图片身份一致、引导模式一致，三者缺一不可。代码事实[S10]

25.2 谁先上：FIFO、SJF、轮转

调度算法：FIFO、SJF 与轮转

只有一个服务员、却有一群客人时，“先服务谁”就是调度问题。操作系统给进程分配 CPU、打印机排打印任务、推理服务排请求，都是同一个问题。三种最经典的策略：

  • FIFO（先进先出，也叫 FCFS 先来先服务）：按到达顺序，一个做完再做下一个。简单、公平，但一个长任务会把后面所有短任务挡住，这叫护航效应。
  • SJF（短作业优先）：每次挑最短的先做。可以证明，在所有任务同时到达时，它让平均等待时间最短。代价有两个：要事先知道每个任务多长；长任务可能被源源不断的短任务一直往后推，这叫饥饿。
  • 轮转（Round-Robin）：每人轮流做一小段，叫一个时间片，没做完就回到队尾。每个人都很快能开始，但来回切换有开销，平均完成时间也未必更短。

衡量好坏的指标也不止一个：等待时间（完成时刻 − 到达时刻 − 自身长度）、首次响应（多久开始被服务；对聊天来说就是多久看到第一个字）、吞吐（单位时间做完多少）。不同策略在不同指标上各有输赢。

延伸阅读：OSTEP：调度入门（英文） · 维基百科：调度（计算机） · 维基百科：饥饿 · Wikipedia: Round-robin scheduling

先看一个最小的例子：三个请求同时到达，回答长度分别是 8、3、5 个 token，假设每生成一个 token 花 1 个时间单位，切换不花时间。教学推演

算一下 FIFO：A 在 8 完成，B 在 11，C 在 16；等待时间分别是 0、8、11，平均约 6.33。SJF 先做 B（3）、再做 C（5）、最后做 A（8），等待是 8、0、3，平均约 3.67，最短。轮转每人轮流做 1 个单位，首字时刻是 1、2、3，每个人都很快有了回应；可三个人都被拖到很晚才做完，平均等待是 7，反而最长。

如果每次切换还要保存、恢复一大块序列状态（比如第 9 章讲的 GDN 循环状态），时间片太小，切换的开销会吃掉大量时间。公平不是免费的，要同时看首字时间、完成时间、吞吐和状态搬运量。

学过计算机的同学：这就是《操作系统》CPU 调度一章的内容，只是“进程”换成了“生成请求”，“CPU 时间片”换成了“token 步”。有一处关键差别：操作系统切换进程，只需保存寄存器等少量上下文；推理引擎切换序列，背后是 KV 缓存和循环状态这些大块数据。

25.3 排队论入门：忙到八成就开始堵

调度决定谁先上，但还有一个更根本的问题：请求来得有多密？哪怕调度策略再聪明，来的比做的快，队伍也会无限变长。

排队论入门：利特尔法则与 M/M/1

排队论研究“到达、排队、服务”这类系统。它用几个量描述系统：到达率 λ（每单位时间来几个），服务率 μ（每单位时间能服务几个），利用率 ρ = λ ÷ μ（服务员有多大比例的时间在忙）。

最有用的一条结论是利特尔法则：L = λ × W。系统里平均有 L 个顾客，等于到达率乘以每人平均停留的时间 W。它几乎不依赖任何假设，奶茶店、高速公路、推理服务都适用。比如每分钟来 3 个请求，每个平均停留 20 秒（1/3 分钟），系统里平均就有 1 个请求。

最简单的排队模型叫 M/M/1：到达是随机的（相邻两次到达的间隔服从指数分布），服务时间也是随机的，只有一个服务员。它的平均停留时间是 W = 1 ÷ (μ − λ)。这个式子告诉我们一件反直觉的事：利用率越接近 100%，等待时间越是急剧变长。ρ = 50% 时，W 是服务时间的 2 倍；80% 时是 5 倍；95% 时是 20 倍。

延伸阅读：维基百科：利特尔法则 · 维基百科：M/M/1 · 维基百科：排队论

套到 Strata 上算一笔账。教学推演 假设平均每个回答 10 秒（比如 500 个 token，每秒 50 个），那么一台 Strata 每分钟最多服务 μ = 6 个请求。如果平均每分钟来 3 个（ρ = 50%），平均停留 1 ÷ (6 − 3) 分钟 = 20 秒；每分钟来 4.8 个（ρ = 80%），就是 1 ÷ 1.2 分钟 = 50 秒；每分钟来 5.7 个（ρ = 95%），变成 200 秒。请求只多了不到一倍，等待却涨了十倍。

M/M/1 只是一个粗糙的模型：大模型的回答长度并不服从指数分布，读题和生成的耗时也差别很大。但它给出的定性结论非常稳健：只要接近满负荷，等待就会失控。真实系统里，这意味着要么加机器，要么限流（排队太长就直接告诉用户“稍后再试”），要么想办法提高 μ，也就是下一节的批处理。

25.4 连续批处理：让多条序列一起走

前两节都假设引擎一次只服务一条序列。提高 μ 的一个办法，是让多条序列在同一次计算里一起前进。

连续批处理

生成一个 token 时，引擎要把相关的权重从显存读一遍。只服务一条序列时，读一遍权重只算一个 token；同时服务 8 条序列时，读一遍权重能算 8 个 token。这就是批处理的收益：把矩阵乘向量变成矩阵乘矩阵，权重读一次、用多次（第 16 章细讲）。

朴素的静态批处理把几条序列凑成一批，一起开始、一起结束。问题是回答有长有短：短的早就写完了，它的位置只能空着，等最长的那条写完，下一批才能开始。

连续批处理（也叫迭代级调度）把调度的粒度从“一批请求”缩小到“一步生成”：每生成一个 token，就检查一次有没有序列写完，有就立刻让排队的新序列补上它的位置。这个思路由 Orca 系统较早系统地提出，后来被 vLLM 等推理框架普遍采用，并配合分页式的 KV 缓存管理（第 17 章）。

延伸阅读：vLLM / PagedAttention 论文（arXiv） · 维基百科：批处理任务

25.5 改成多序列：先隔离状态，再谈速度

假设你决定动手，让 Strata 同时服务两条序列。第一步不是写调度器，而是列清楚：哪些东西是共享的，哪些是每条序列私有的。

上游代码给了一个很好的阅读入口。session.hpp 里的 SessionState，注释写的是“一条序列需要的、除权重以外的一切”：每层的状态、块计算的临时空间、GPU 与 CPU 专家池之间的交接区。代码事实[S13] 也就是说，在上游的设计里，一条序列对应一份 SessionState。

更要紧的是注释里的这两句。36 个 GDN 层共用一套临时空间，它们的状态才是每层一份；12 个 QSA 层也共用一套临时空间，理由写在括号里：“它们从不同时运行”。代码事实[S13] 在单序列、逐层顺序执行的前提下，这个共享完全正确，还省了显存。可一旦两条序列同时跑，“从不同时运行”这个前提就不成立了，共享的临时空间会被两边同时写，结果是两条序列的数据互相串扰。

学过计算机的同学：这是并发编程里最典型的陷阱：代码原本正确，是因为某个“只有一个执行者”的隐含假设。改成多线程时，要把所有这类假设逐条找出来，重新证明互斥或者改成每人一份，而不是只在外面加一把全局锁就算完事。

其次是显存预算。上游在会话初始化时一次性按最大上下文分配所有层的状态，注释说明这是因为它要求生成每个 token 的路径上零分配：一次临时的 cudaMalloc 能通过所有其他测试，却过不了这一条。代码事实[S13] 多序列时，同样的原则意味着：接纳一条新序列之前，必须先把它的全部状态空间预留好。图 25-6 用一组教学数字算这笔账。

这组数字是教学假设：共享权重与缓存 20 GiB，每条序列状态 2 GiB，临时空间 2 GiB，预留 2 GiB。教学推演 五条活动序列需要 20 + 5 × 2 + 2 + 2 = 34 GiB。注意两点：上下文长短不同，每条序列的状态也不同；如果五条序列真的同时计算，临时空间也要按并发数重新算，不能再共用一份。

由此得出准入控制的原则：一条序列被承诺为“活动”之前，要原子地预留它的全部预算；预算不够，就让它排队或明确拒绝。不能先把请求全收进来，再指望显存分配器别出错。

25.6 动手：短请求为什么一直等

打开本章的交互实验「短请求为何一直等」。它比较 FIFO 和轮转在首字时间、完成时间和切换成本上的差别。所有请求在 0 时刻就绪，1 个 token 算 1 毫秒，不模拟真实显卡上的批处理和读题。按顺序试：

  1. 用默认的几条请求，比较 FIFO 和轮转的首字时间：轮转让短请求更早开始。
  2. 把切换成本调高：轮转的总时长变长，公平的代价变得看得见。
  3. 把时间片调大，直到轮转的结果和 FIFO 完全一样。

再回到本章的两个交互图：在调度比较器里试试“短请求接连到”，看 SJF 怎样饿着长请求；在排队曲线上把利用率拉到 95%，多按几次模拟。实验里的数字只用来讨论调度取舍，不能当成任何真实系统的跑分。

记住这三点

  1. 上游 Strata 一次只服务一条序列，其余请求在 FIFO 锁前排队。多用户调度是本章的设计练习，不是上游功能。连接数、排队数、活动序列数要分开统计。
  2. FIFO 简单但会被长请求挡住，SJF 平均等待最短但会饿着长请求，轮转让人人更早看到第一个字但要付切换开销。利用率越接近 100%，等待越是急剧变长。
  3. 改成多序列，先找出所有“只有一个执行者”的隐含假设，比如共享的临时空间；再按“权重一份、状态每条一份”算预算，并在接纳新序列前原子地预留。

常见误解：“Strata 的 HTTP 服务器是多线程的，所以它能同时服务多个用户。”

多线程只让多个人能同时连上。真正干活的引擎前面有一把 FIFO 锁，同一时刻只有一条序列在生成。连接并发、线程并发和序列并发是三个层次的事，不能看到 ThreadingHTTPServer 就断定引擎支持连续批处理。

深入一层：四个计数、预算细节、切换成本与并发验收

先划清现状与设计

固定提交的上游服务文件写明：FIFO 后面一次处理一条序列。[S15] 本书的发起人曾说明自己改过一个支持多并发的 Strata 分支，但那个分支的源码不在本次审阅范围内。本章提出的是多用户扩展的设计与验收方法，不声称已经审计或实现了那个分支。

四个数要分别计数：HTTP 同时连接数、排队的请求数、正在生成的序列数、同一次内核计算里处理的序列数。它们可以完全不同。多开线程，并不会自动解决 KV 缓存、GDN 状态、PLE 状态、随机数和临时缓冲的隔离问题。

可变状态逐项列清归属

只读的权重和只读的缓存内容，在适当同步下可以共享。每条序列的 token 历史、KV 页映射、GDN 状态、PLE 状态、采样参数、随机数计数器和取消标志，必须有明确的归属。上游的 SessionState 是阅读“除权重以外的序列状态”的好入口 [S13]；注意 PLE 的历史和 token 窗口也被注释明确称为“序列状态”。

共享临时空间是否安全，取决于调度能否保证互斥。原先假设“各层从不并发”的临时空间，被两个会话同时使用时，原本正确的代码会立刻失效。改并发时，应列出所有单序列假设，而不是只找一把全局互斥锁。

预算的细节

正文的 34 GiB 只是一个起点。如果五条序列需要各自独立的临时空间，那 2 GiB 要按实际并发数再算；上下文长短不同，每条序列的状态大小也不同。准入控制必须在承诺活动序列之前原子地预留预算。会话停车区（上游可选功能）占的是主机内存，也要单独计入预算。上游报告

轮转的真实成本

教学模拟假设切换不花时间，或者只花一个固定的常数。真实引擎切换序列时，如果要把一条序列的 KV 缓存和循环状态从显存挪出去、再把另一条挪进来，时间片太小会让搬运开销压倒计算。所以“公平”的评估要同时看首字时间、完成时间、吞吐和状态搬运量。SJF 还有一个现实难题：回答长度在生成完之前并不知道，只能估计；为了防止饥饿，常见做法是给等得越久的请求越高的优先级，这叫老化。

例题：最后一个槽位，两个请求同时到达

验收断言：恰好一个请求拿到有效预算并进入活动状态，另一个排队或被明确拒绝；不能重复预留，也不能因为客户端重试而创建两个会话。完成或取消后，预算恰好释放一次；旧请求不能继续写入新槽位的状态。

多并发验收要击中“串状态”风险

设计 A、B 两条语言或任务不同的固定请求，先分别单独运行，记下参考输出；再交替或并行运行。覆盖这些情况：A 取消时 B 继续；A 长时间读题时 B 在生成；相同前缀但图片不同；会话恢复；预算只够最后一个槽位时的并发抢占。

最低通过条件：状态隔离正确、没有超预算的承诺、没有重复结束、没有旧请求的输出混入、没有长请求饥饿。一个总吞吐提高了、却偶尔串上下文的系统，不是合格的并发推理服务。
