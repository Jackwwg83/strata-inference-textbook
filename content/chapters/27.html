27.1 实验单位是一次完整条件组合

至少记录：仓库 SHA、二进制与 flags、模型 pack 哈希、量化、CPU/GPU、内存通道和频率、驱动、上下文、输入 token 数、输出上限、KV 模式、chunk、草稿、缓存冷热、并发定义、采样和随机种子。缺一个关键变量，两组数字可能就不再可比。

固定 DETAILS.md 中的主表包含不同引擎版本的沿用单元格，并有新的内核版本补充段。[S03] 这可以作为“读性能表”的课堂材料，但不能把所有单元格当成同一次统一实验，更不能外推为本教材实测。

27.2 定义时钟边界

端到端 TTFT：请求发起到首个输出 token；排队时间：进入队列到获准执行；prefill 时间：开始处理新输入到所需历史状态就绪；decode 时间：按明确边界统计生成过程；完成时间：请求到成功或失败终态。

输出 rate 可以使用 N/总 decode 时间，也有人使用 (N−1)/(最后 token 时间−首 token 时间)。二者都可报告，但定义必须写清，不能在不同系统间暗换。N=1 的后一种分母无意义，应显示未定义而不是巨大速率。

27.3 coding agent 的三个代表场景

冷仓库理解：长系统提示、工具定义、代码上下文、首次回答，主要观察冷 prefill、TTFT 和内存峰值。增量修改：大前缀复用，只新增报错与代码差异，观察缓存有效性和尾部处理。工具循环与分叉：短生成、工具输出、续写、另开分支，观察状态恢复、取消与协议语义。

输入长度可设 1K、4K、16K、32K、64K、128K 及实际支持的近满窗口；输出上限预留明确空间。不要把“最大上下文”全部用作 prompt 后还要求额外生成。具体模型与配置的合法边界应从真实引擎核验。[S15]

27.4 单流与多流分别回答问题

单流测试关注每个用户的即时体验。多流测试还需报告活动流数、总吞吐、每流 TTFT / inter-token latency 的 p50/p95、失败率、排队和公平性。不能把五个流合计 100 token/s 写成“每人 100 token/s”。

稀疏工作负载与同步高峰也不同。多流扩展测试应固定到达过程、请求长度分布和冷热状态，并保留每个请求的原始时间戳；平均几个已经算好的 rate，通常不等于总 token / 总时间。

27.5 统计：重复、配对与区间

至少做多次重复和预先定义的 warm-up；A/B 尽量交错或配对，减小热状态和系统漂移影响。报告中位数与尾部，不隐去失败运行。样本很少时，p95 会高度不稳定，要同时展示样本数与原始记录。

例如 5 个值 [8,9,10,11,100] ms，均值 27.6 ms，中位数 10 ms，两者讲的是不同故事。不能随意删掉 100，除非事先定义排除规则且保留原因。选完最快一次再报告，通常没有可推广的统计意义。

27.6 发布前的质量门

先通过数值和任务质量，再比较速度。投机、量化、KV、前缀缓存与 CPU/GPU 分派都可能影响执行路径；“快 20%”但答案少生成一半或失败被漏计，不是成功优化。

使用 labs/benchmark_template.csv 记录每次运行，benchmark_protocol.md 给出 A/B 与拒绝条件。没有真实硬件数据的格子保持空白；本教材没有填入推测的显卡跑分。
