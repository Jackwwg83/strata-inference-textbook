先看三个数

Strata 的 README 写着：在 RTX 5070 上，Q2_0 版本每秒能写出 94 个 token。上游报告[S01] 这个数看起来很确定。

再看一位社区成员交上来的测试：一张 RTX 3090，跑 Coder 模型，32K 长度的提示，同样的设置连跑三次，前后不到 30 秒。三次的输出速度分别是每秒 52.7、66.8 和 97.4 个 token。上游报告 最快和最慢差了将近一倍。这台机器到底有多快？这一章讲怎样测，才能让一个速度数字经得起追问。

一句话：一个性能数字必须带着它的条件、样本数和统计方法才有意义：先预热，再重复，报告中位数和波动范围，把第一次运行单独列出来，并写清楚“速度”是用哪个公式算的。

27.1 同一台机器，30 秒里跑出三个速度

先看这三次运行的原始记录。它们来自 Strata 仓库里一份社区提交的测试报告，引擎版本 0.1.26，一张 RTX 3090，Coder 模型，32K 长度的提示。上游报告（RTX 3090 测试报告）

为什么差这么多？原始记录里有线索 上游报告：

  • 输出太短。三次分别只生成了 48、26、45 个 token，模型提前说完就停了。解码阶段每次都不到 1 秒（911、389、462 毫秒）。这么短的时间里，任何一点波动都会被放大。
  • 每次写的内容不一样。三次回答的开头各不相同。Strata 用投机解码加速：先猜几个 token，再一次验证。猜中得多，速度就快。三次分别接受了 38 个草稿里的 31 个、21 个里的 12 个、37 个里的 33 个。第 2 次猜得最差，速度却排在中间，可见影响速度的不只一个因素。
  • 输入也在漂。名义上都是“32K 提示”，实际长度是 28,317、31,630 和 31,601 个 token。报告特意记录了实际长度，因为“名义上的长度标签会漂移”。

报告自己的结论很克制：每个格子跑三次、报告中位数，同时列出第一次的值；整份结果标明是“初步”的。这正是这一章要讲的习惯。

先把两个词说清楚。吞吐是单位时间完成多少工作，这里是每秒输出多少个 token，写作 token/s，越大越好。延迟是等一件事完成要多久，比如从发出请求到看到第一个字的时间，越小越好。两者经常被混着说，可它们回答的是不同的问题。

27.2 一个数字要带着它的条件

README 里的“94 token/s”从哪来？v0.1.39 的 README 在表下补了一行说明：Q2_0 这一行用的是引擎 0.1.36，其他行是 0.1.26。上游报告[S01] 详细文档里，0.1.36 那一段写着：Q2_0 在 4K 时的输出从 89 提到 93.5 token/s，32K 的读题从 2,170 提到 2,653。主表却是 0.1.26 的，同一格分别是 93.0 和 2,171。上游报告[S03] README 的读题速度写的是 2,650，对得上 0.1.36，对不上主表。只看“94”这个数，分不出它来自哪个版本，要看版本说明。主表的条件写在文档开头，见图 27-2。

这份文档还有几处值得学的细节 上游报告[S03]：

  • 标出版本混用。表格主体是 0.1.26 的结果，可 262K 那一列有几格没有重测，沿用的是 0.1.22 或 0.1.14 的数，用符号单独标了出来。混在一张表里的数，不一定是同一次实验。
  • 说明数字会随内容变。输出速度也取决于文字本身：投机解码猜中得越多越快，所以同一个提示换一个回答，速度就能差好几个百分点。
  • 对比时背靠背地跑。文档比较 0.1.14 和 0.1.12 时，是在同一个 4K 提示上背靠背运行，得到 88.5 和 85.7 token/s。

回到开头那张 3090。README 估计 RTX 3090 “大约能写到每秒 100–140 个 token”。[S01] 社区报告测到的数比这低，可两者的条件差得很远：报告用的是一台虚拟机，测试机上两张显卡的功耗都被手动限制在 280 W，提示是测试者自己从源码生成的，好几次请求提前结束。报告自己写明：在拿到上游的提示和测试方法之前，所有和上游的对比“只能作参考”。上游报告 两个数都没错，它们只是不能直接比。

学过计算机的同学：这就是《计算机体系结构》讲性能评测时的第一条规矩：写清测试环境，一次只改一个变量。科学实验里叫“控制变量”。一个没有条件的跑分，和一个没有单位的物理量一样，没法用。

27.3 平均数会被一个慢请求拖走

同一件事测了好几次，得到一串数，用哪个数代表它？最常见的答案是平均数，可它有一个大毛病。下面的专栏讲清楚。

均值、分位数与方差

先看一组请求的耗时：8、9、10、11、100 毫秒。前四次都很正常，最后一次可能碰上了别的程序抢资源。

均值是全部加起来再除以个数：(8 + 9 + 10 + 11 + 100) ÷ 5 = 27.6 毫秒。可五次里没有一次接近 27.6，它被那个 100 拖走了。中位数是排好序后正中间的那个数，这里是 10 毫秒。哪怕把 100 换成 10000，中位数也不动。这种“不怕个别极端值”的性质叫稳健。

分位数回答“大多数请求有多慢”。p95 的意思是：95% 的请求不比它慢。用户体验往往由慢的那一头决定：每 20 次请求里最慢的那 1 次，用户记得最清楚。计算 p95 有好几种约定，本书用最简单的“最近秩”法：从小到大排序，取第 ⌈0.95 × n⌉ 个。注意：样本少于 20 个时，p95 就是最大值。只跑 5 次就报告 p95，其实报告的是“最慢的那一次”。

方差和标准差衡量数据有多分散。样本标准差 = √( Σ(xᵢ − 均值)² ÷ (n − 1) )。上面那组数的标准差约 40.5 毫秒，比典型值本身还大，这就在提醒你：数据里有离群值，均值不可信。

延伸阅读：维基百科：中位数 · 维基百科：百分位数 · 维基百科：标准差 · Python 文档：statistics（含 quantiles 的两种算法）

回头看图 27-1 的三次运行：中位数 66.8，均值 72.3，“p95”就是最快的那次 97.4（这里数越大越好，要看慢的那一头，就得看最小值 52.7）。三个数，任何一个单独拿出来都不完整。上游报告的做法是报中位数，再把第一次的值和原始记录一起附上。

学过计算机的同学：《概率论与数理统计》里，中位数的“崩溃点”是 50%：一半以下的数据变成任意值，中位数都不会跑到无穷远；均值的崩溃点是 0，一个坏数据就能把它拖走。性能数据恰恰最容易出现个别极端值。

27.4 第一次总是特别慢：预热与重复

很多系统第一次运行都比后面慢。Strata 里就有好几样东西会随着使用“热”起来：

  • 专家缓存。显存里放哪些专家，会跟着对话调整，越用越贴合当前的内容。上游报告[S02]
  • 草稿控制器。它对“草稿能猜中几个”有一个初始估计，然后在每个会话里边用边学。代码事实[S09]
  • 计算图。验证窗口的 GPU 计算图在第一次使用时才录制。代码事实[S08]
  • 操作系统的文件缓存。刚读过的文件留在内存里，第二次读快得多。

反过来，也有东西会让后面的运行“快得不真实”。Strata 会保留对话，追问时只读新增的部分。[S02] 如果测速时反复发同一个提示，第二次起读题几乎不花时间，测到的就不是“读一个 32K 提示”的速度了。所以那份 3090 报告的每次请求都用不同的 ID，不复用对话。上游报告

另一份社区报告把测量方法写得更完整，见图 27-4。它在 RTX 5090 上测 IQ2_XS 量化版，引擎 0.1.29：先发一个很短的预热请求，不计入结果；然后在同一个已加载的引擎上，按 4K、32K、128K 的顺序，每个长度连跑三次；每次请求都完整读题，复用的 token 数为 0；表格里每格写“中位数 [最小值–最大值]”。上游报告（RTX 5090 测试报告）

注意那个预热请求：它的提示只有 19 个 token，只输出 2 个。这么短的请求没能把一切都预热好，4K 的第一次正式运行首 token 延迟多了约 0.2 秒，解码也慢了约 10%。报告没有偷偷删掉这次运行，而是写明“较慢的第一次 4K 运行保留在范围里”。上游报告 这比删掉它诚实，也给读者留下了判断的材料。

预热与基准测试方法

基准测试就是在受控条件下，反复运行同一个任务，测它的性能。要让结果可信，有几条基本功：

预热。正式计时前先跑几次，让缓存、计算图、文件缓存进入稳定状态，这几次不计入结果。预热几次、预热什么内容，要事先定好并写进报告。如果你关心的恰恰是冷启动（比如用户第一次打开），那就单独测冷启动，不要和热状态混在一起。

重复。一次运行只是一个样本。重复多次，才能看到波动有多大。重复次数要事先定好，不能“跑到满意为止”。

交替。比较 A 和 B 时，不要先跑完 A 再跑 B，而是 A、B、A、B 交替。否则机器的冷热、温度、后台任务的变化，会全部算到某一边头上。

保留原始数据。报告中位数和范围，同时附上每一次运行的原始记录，包括失败和异常的那几次。

有一种场合可以只看最快的一次：测一段确定性的小代码。Python 的 timeit 文档就建议看最小值，因为较慢的结果通常是别的进程干扰造成的，最小值给出了机器运行这段代码的下限。可推理服务的速度还取决于输入内容、草稿猜中多少、缓存命中多少，这些不是“干扰”，而是用户真实会遇到的情况。

延伸阅读：维基百科：基准测试 · Python 文档：timeit · Wikipedia: Benchmark (computing)

预热、重复、交替各能解决什么问题？下面这个实验让你自己设计测量方案。它的好处是“知道真相”：B 真的比 A 快 5%，你可以直接看到自己的方案测得准不准。

27.5 先定义时钟：TTFT 和“每秒多少 token”

就算测量方法没问题，“速度”这个词本身也可能有好几种算法。用户发出一个请求后，会经历几段时间：排队、读题、第一个 token 出现、后面的 token 陆续出现、结束。从哪里开始掐表、到哪里停，算出的数完全不同，见图 27-6。

TTFT（time to first token，首 token 延迟）是从发出请求到第一个 token 出现的时间。它包含排队和读题，决定了用户“等多久才看到动静”。RTX 5090 报告对它的定义很精确：从发出 HTTP 请求之前开始计时，到收到第一段非空文本为止，忽略空的角色信息和保活消息。上游报告

输出速度的算法更多。上面图里的速度 ② 和 ③ 只差一个“减 1”，可在输出很短时差别不小：只输出 26 个 token 时，两者相差 26 ÷ 25 − 1 = 4%。教学推演 输出只有 1 个 token 时，速度 ③ 根本没有定义，硬算就是除以 0。

“实时速度表”也有讲究。Strata 服务端源码的注释说，界面上显示的实时速度是一个时间窗口内的速率，而不是“从第一个 token 起的平均”：后者在第一个 token 刚出来时约等于 1 ÷ 已过时间，曾经在监控界面上显示出五位数，之后的一秒钟里又偏低。代码里的窗口是 2 秒，不满 0.25 秒时按 0.25 秒算。代码事实[S15]

多个用户同时使用时，还要再分清两件事。系统总吞吐是所有请求加起来每秒输出多少 token；单流速度是每个用户自己看到的速度。五个用户合计每秒 100 个 token，不等于每人每秒 100 个。默认配置下，Strata 的服务端一次只处理一个序列，请求按先来先服务排队。[S15] 所以“五个人同时用”意味着后面四个人在排队，他们的 TTFT 会变长，而解码速度不变。第 25 章讲过这种排队的代价。从 v0.1.39 起，可以在配置里打开 "parallel"，让几个请求一起解码，结果正好反过来。上游在 RTX 5070 上实测：4 个请求同时到达时，最后一个的首 token 从 11.2 秒提前到 1.8 秒；可总吞吐从 70.7 降到 63.1 token/s，每条流的速度从 79.6 降到 16.9 token/s。上游报告（BATCHING.md）这时服务端的实时速度 tok_s 是所有请求速率之和，也就是系统总吞吐。代码事实（server.py）每个槽位自己的速度，另列在 /metrics 的 live.slots 里。上游报告（BATCHING.md）两种配置哪个“更快”，要看你问的是 TTFT、总吞吐，还是单流速度。

27.6 动手：把一次测量写成可复核的记录

本书随附了一份测量协议 labs/benchmark_protocol.md 和一个记录模板 labs/benchmark_template.csv。模板有 31 列，从仓库版本、构建参数、模型文件的哈希，到排队、TTFT、解码时长、显存峰值和质量是否通过，每次运行填一行。模板里一个真实跑分都没有填：没有在真实硬件上测过的格子，就该空着。

  1. 先玩本章的两个实验。在“测量实验”里找出一个能稳定测出 5% 的方案，记下你用的重复次数、预热次数和运行顺序。在“三种速度”里，把输出长度拉到 1，看哪些公式失效。
  2. 再打开交互实验「短请求为何一直等」。它比较先来先服务和轮转两种调度下，每个请求的首 token 时间和完成时间。注意：总吞吐几乎不变，每个人的体验却差很多。这正是“单流”和“总吞吐”要分开报告的原因。
  3. 最后写一份记录。如果你有能运行 Strata 的电脑，按协议跑一组 A/B：一次只改一个设置，A、B 交替，每组预热后至少重复 5 次，把每次的原始数据填进模板。没有这样的电脑，就拿上游的 RTX 3090 报告练习：从它的原始 JSON 里抄出每次运行的数，自己重算中位数，并列出报告缺了模板里的哪些列。

本章两个交互实验里的时间都是教学假设，不是 Strata 的实测；它们演示的是测量方法，不是某张显卡的速度。

记住这三点

  1. 一个性能数字要带着条件：硬件、模型与量化、引擎版本、输入输出长度、缓存冷热、并发数。条件不同的数不能直接比。
  2. 先预热、再重复，A/B 交替运行；报告中位数和范围，第一次运行单独列出，原始数据和失败的运行都保留。
  3. “速度”要先定义时钟：TTFT、端到端速度、解码速度各回答不同的问题；系统总吞吐不等于每个用户的速度。

常见误解：“取跑得最快的那一次，才代表机器的真实实力。”

测一小段确定性的代码时，最快的那次确实有意义：Python 的 timeit 文档就说，最小值给出了机器运行这段代码的速度下限。可推理服务的速度还取决于这次写了什么内容、草稿猜中了多少、缓存命中了多少。图 27-1 里最快的 97.4，只是三次里运气最好的一次。用户每天遇到的是中位数附近的速度，记住的是最慢的那几次。只报最快一次，是在挑对自己有利的数据。

深入一层：实验单位、代表性场景、配对比较与质量门

实验单位是一整套条件组合

至少记录：仓库版本（提交号）、可执行文件与构建参数、模型文件的哈希、量化方式、CPU 和 GPU 型号、内存通道和频率、驱动版本、上下文长度、输入 token 数、输出上限、KV 缓存模式、预填充分块大小、草稿设置、缓存冷热、并发定义、采样参数和随机种子。缺了一个关键变量，两组数字可能就不再可比。Strata 的详细文档在一张表里混用了不同引擎版本的格子，并另起一段补充了新内核的结果。[S03] 这份文档适合拿来练习“读性能表”，但不能把所有格子当成同一次统一实验，更不能当成本书的实测。

时钟边界逐个定义

端到端 TTFT：从发出请求到第一个输出 token。排队时间：从进入队列到获准执行。预填充时间：从开始处理新输入到所需的历史状态就绪。解码时间：按明确的起止点统计生成过程。完成时间：从发出请求到成功或失败的终态。两种解码速率 N ÷ 解码时长 和 (N − 1) ÷ (末 token 时间 − 首 token 时间) 都可以报告，但定义必须写清，不能在不同系统之间偷偷换。N = 1 时后者没有定义，应显示“没有定义”，而不是一个巨大的速率。

编程助手的三个代表性场景

冷仓库理解：长系统提示、工具定义、代码上下文和第一次回答，主要看冷预填充、TTFT 和内存峰值。增量修改：大段前缀可以复用，只新增报错和代码差异，看缓存是否有效、尾部处理多快。工具循环与分叉：短生成、工具输出、续写、另开分支，看状态恢复、取消和协议语义。输入长度可以取 1K、4K、16K、32K、64K、128K 和实际支持的近满窗口，并给输出预留明确的空间。不要把“最大上下文”全部用作提示，又要求额外生成。具体模型和配置的合法边界要从真实引擎核实：Strata 的服务端会直接拒绝“提示加输出上限超过上下文”的请求，返回 400，从不截断。[S15]

单流与多流分别回答问题

单流测试关注每个用户的即时体验。多流测试还要报告活动流数、总吞吐、每流 TTFT 和 token 间隔的 p50 / p95、失败率、排队和公平性。稀疏的到达和同步的高峰也不同：多流扩展测试应固定到达过程、请求长度分布和冷热状态，并保留每个请求的原始时间戳。把几个已经算好的速率取平均，通常不等于总 token 除以总时间。

配对、交替与区间

A/B 比较尽量配对：同一个提示在 A 和 B 上各跑一次，比较差值，而不是各自用不同的提示跑三次再比中位数。那份 RTX 3090 报告在比较不同的层切分点时就提醒：各次运行的提示是独立生成的，所以排名“不是配对比较”，看中位数要谨慎。上游报告 Strata 的文档也建议，做 A/B 时加上 --pcie-frac 0 等开关，让同一个提示每次得出相同的回答，否则回答不同，速度也跟着变。[S03] 样本很少时，p95 极不稳定，要同时给出样本数和原始记录；想给出置信区间，可以用自助法（bootstrap）对原始样本重抽样。删除离群值必须有事先写好的规则，并保留删除的原因。挑出最快的一次再报告，没有可推广的统计意义。

先过质量门，再比速度

投机解码、量化、KV 缓存格式、前缀缓存和 CPU / GPU 分派都可能改变执行路径。“快了 20%”，可回答少写了一半，或者失败的请求没被计入，就不是成功的优化。Strata 的文档在报告一个加速时，会同时报告它离 FP16 参照有多近（teacher forcing 下的 KL 散度）。[S03] 记录每次运行用 labs/benchmark_template.csv，A/B 流程和拒绝发布的条件见 labs/benchmark_protocol.md。没有真实硬件数据的格子保持空白，本书没有填入任何推测的显卡跑分。
