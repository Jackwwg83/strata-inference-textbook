一个零件全绿的故事

Strata 的模型里有一个查表模块，叫 PLE（第 11 章讲过）。开发者把它拆成几个零件：算哈希、从大表里读一行、做一小段计算。每个零件都写好了，也都通过了对照测试，分别对上了参考脚本、numpy 和 ggml 的结果。

然后，整个模型的一道验收没通过。原因写在源码注释里：这些零件从来没有被模型的主路径调用过。代码事实[S13] 每个零件都是对的，整台机器却少了一块。这一章是全书的最后一章，讲你的课程项目怎样避开这个坑。

一句话：做系统，先打通一条最细的“纵切”：让一个 token 从输入一路走到输出，并留下可以检查的证据；再一层层加功能。每做一个取舍，都写下换来了什么、付出了什么、怎样验证；交付时，给每个组件标明它的证据走到了哪一步。

28.1 模块全绿，系统却是错的

图 28-1 画出了 PLE 的处境。三个零件各自通过了对照测试，可模型的主路径从第 0 层走到第 47 层，一次也没有经过它们。单看任何一个零件的测试报告，都看不出问题。

这种错误有一个共同的根源：先把每一层“横着”做完，最后才把它们接起来。好比修一条从 A 城到 B 城的路，先把每一公里都铺到最终宽度，最后一天才发现中间有一段从来没连上。更稳的做法是先修一条窄路，从 A 一直通到 B，能走车了，再慢慢拓宽。

软件里，这条“窄路”叫纵切（vertical slice）：一个功能从入口一直贯穿到出口，每一层只做它必需的那一小部分，但整条链路是真的、能运行、能产出可以检查的结果。对推理引擎来说，第一条纵切就是：一句话进来，经过编码、逐层计算、选词，吐出一个 token，并把中间的关键数据打印出来，让人能核对。

纵切不等于随便写。它要求“细”，不要求“糙”：这一条链上的每一步都要有测试，第 26 章讲的参照答案和负例一样都不能少。它省掉的是广度，不是正确性。

28.2 系统设计，就是把取舍写下来

打通纵切之后，每加一个功能，都会遇到选择：用更多显存换速度，还是省显存；先求快，还是先求能调试。这些选择没有标准答案，但有标准的写法。

系统设计与工程取舍

系统设计回答的是：在给定的约束下，把一堆部件组织成一个能满足需求的整体。它和写一个算法不同：算法题通常有最优解，系统设计几乎总是在几个目标之间做取舍。速度、内存、正确性、可调试性、开发时间，往往此消彼长。

一次像样的取舍，至少写清五件事：

① 决定：选了什么，没选什么。② 换来：得到了什么好处，最好有数字。③ 代价：付出了什么，同样要有数字。④ 验证：怎样确认好处真的拿到了、代价真的只有这么多。⑤ 重议条件：出现什么情况时，应该推翻这个决定。

第 ⑤ 条最容易被忘掉。没有它，一个当初合理的决定，会在条件变了以后继续存在，变成没人敢动的“历史遗留”。工程界把这类越积越多、迟早要还的代价叫作技术债。

取舍还有一个常见的陷阱：只优化你能测到的那一项。比如只看平均速度，就可能牺牲了尾部延迟；只看单元测试，就可能漏掉组合错误。所以设计时就要想好，每个目标用什么指标衡量。

延伸阅读：维基百科：软件工程 · 维基百科：技术负债 · Wikipedia: Systems design · Wikipedia: Trade-off

Strata 的源码注释里，有很多这样写得清清楚楚的取舍。图 28-2 整理了其中一个：QSA 层的索引器负责挑出要读的历史位置，它的键用 FP32 存，而不是更省的 FP16。代码事实[S18]

再看几个例子，它们来自 session.hpp，都把“换来什么、付出什么”写在了一起 代码事实[S13]：

  • 每层一张 GPU 计算图。把一层的几十次内核启动录成一张图再回放，实测同样的工作从 2.393 毫秒降到 1.585 毫秒，快了 1.51 倍，因为引擎的瓶颈是“启动内核”的开销，而不是带宽。相关的代价也写在旁边：为了让每层的专家结果用本层的权重合并，每层还要再加一张图，CPU 能和 GPU 重叠工作的窗口因此只剩共享专家那一小段；注释直说“一个严格串行的残差链藏不住逐层的 CPU 计算”，这部分只能靠显存里的专家缓存去解决。
  • 调试开关做成运行时参数。“每层同步一次”能抓到别处看不见的错误，但会拖慢速度。它被做成一个运行时参数，而不是编译时选项：需要时打开，平时关掉。
  • 生成 token 时零内存分配。一个会话需要的所有状态，在开始时一次分配好。注释特别说明：如果在长序列的第一个 token 才去申请显存，现有的每个测试都会通过，唯独违反这条约束。

服务层也一样。Strata 的服务端默认一次只服务一个序列，请求先来先服务；提示加上输出上限超过上下文长度时，直接拒绝并返回 400，而不是悄悄截断。[S15] 前者用简单换来了状态不会串，后者用一次报错换来了用户不会拿到被截断却不自知的结果。v0.1.39 加了可选的“批槽位”，让几个请求一起解码。它的文档 docs/BATCHING.md 正好是一份把取舍写全的范例。换来的是等待时间：4 个请求同时到达时，最后一个看到第一个字的时间从 11.2 秒缩到 1.8 秒。代价是速度和显存：每个槽位占 0.56 GiB，在 12 GB 显卡上，单独一个请求也要慢 11%–24%。验证是逐个 token 对比单独运行时的输出。适用条件也写明了：只在专家大多放得进显存时，才推荐打开。上游报告

学过计算机的同学：工业界有一种做法叫“架构决策记录”（ADR）：每个重要决定写一页短文档，包括背景、决定、后果。你的课程报告里，每个设计选择都可以按图 28-2 的格式写一张小卡片。

28.3 三种项目，选一个

课程项目分三种，按你手头的条件选。三种的评分标准相同：看证据的质量、分析和工程的完整性，不看显卡的价格。

项目 A：没有显卡也能做的微型引擎。从本书随附的 labs/tiny_inference.py 出发。它用很小的固定随机权重和字符词表，把编码、归一化、递归层与注意力层、专家路由、输出和贪心选词接成一条完整的链。随机权重不会产生有意义的语言；这个项目的目标是理解运行机制，不是假装训练出了聊天模型。第 28.5 节给出分步路线。

项目 B：从一个可测的优化开始。选一个局部方向：量化块的解码、页表收集、缓存策略、分块大小、草稿窗口的控制，或者流式输出的分片解析。提交原理推导、基线、改动、负例、结果和局限。一次只改一个因素，不要同时改五个开关，最后只展示一个总耗时。没有显卡的同学做 CPU 参照实现和数学模拟；有显卡的同学可以在固定的 Strata 提交上做真实复现。

项目 C：多用户设计评审。提交一份“让多个序列同时运行”的设计，而不是在学期末强行做出一个生产服务。设计的第一步，是给每一块数据定好归属，见图 28-3。

设计文档要列出：哪些是只读共享对象，哪些是每个序列的状态，临时工作区归谁，调度和显存预算怎样分配，取消、恢复、观测和回滚怎么做。然后用第 25 章的并发验收场景去反驳自己的方案。加分项是一个能运行的小型调度或状态隔离原型。没有验证过的能力，必须写成“未实现”：界面上显示五个用户，不等于有五条真实在跑的推理流。写完自己的设计以后，可以拿上游 v0.1.41 的 docs/BATCHING.md 对照：它给每个槽位一份会话，写清了槽位的显存代价、逐 token 的一致性验收和目前的限制。先自己设计、再看参考，最能看出自己漏了什么。上游报告

学过计算机的同学：这和《操作系统》里的进程模型一模一样：多个进程共享只读的代码段，各自拥有私有的栈和堆。KV 缓存就是每个序列的“私有内存”，共享它而不加保护，就是两个进程互相改写对方的数据。

28.4 交付什么：给每个组件标明证据

项目报告最常见的问题，不是代码写错，而是把“写完了”说成“做完了”。为此，报告里的每个组件都要标明它的证据走到了哪一步：

状态含义可以拿出的证据
代码写完写了，测试过了，但还没接进主路径单元测试的输出
接进主路径主路径确实调用了它一次完整运行的日志，能看到它被调用
真实数据真实输入经过它，产出了完整的结果一条完整记录：输入、中间值、输出，字段齐全
模拟、空值或推算界面上能看到，但背后是假数据、空字段或估算必须明说，并标“教学推演”

一个组件完全可能“代码写完、也接进了主路径”，却还没有产出真实数据。这种状态必须照实写出来，不能用“完成”两个字盖过去。Strata 的源码里有一个很好的例子：CPU 和 GPU 本该重叠工作，可如果 CPU 拿到任务时 GPU 已经算完了这一层，整条流水线其实退化成了串行。这时每个 token 依然算得对，每层的耗时也看不出区别。所以作者专门加了一个计数器，统计 CPU 在 GPU 还在运行时拿到任务的层数，用来判断这个重叠机制是“真在干活”还是“只是摆设”。代码事实[S13]

报告本身按这个顺序写：先提出一个可以被实验推翻的问题，例如“在相同的输入和质量门下，增加显存里的热专家预算，能否减少 CPU 的计算时间？”然后依次给出理论、源码定位、方法、数据、解释和局限。所有图都要写单位、样本数和测量条件；源码链接指向固定的提交，而不是会变的 main 分支；原始数据和失败日志都要保留。评分按下表：

维度分值可检查的证据
原理与推导20公式、单位、依赖和前提正确
源码与契约20指向真实代码，分清当前代码和过时的注释
实现与测试25能运行，有独立的参照答案、负例和边界测试
实验与质量20配对或交替比较、原始数据、质量门、失败也计入
表达与可复现15写清环境、步骤和局限，别人能复验

有两条红线。把教学模拟写成硬件实测，“实验与质量”整项不计分；存在没有说明的状态串用，“实现与测试”整项不计分，性能做得再好也抵消不了正确性的缺陷。下面的自检表可以帮你在交之前先给自己打一遍分。

28.5 动手：先走通第一条纵切

以项目 A 为例。第一步不是写新功能，而是让现成的链路跑通一次，并看清它产出的每一个字段。在本书的仓库里运行：

python3 labs/tiny_inference.py --prompt "hello" --tokens 8

本书编写时实际运行的输出里，有这几样东西：模型几何（4 层、8 维、4 个专家选 2 个）、根据全部权重算出的模型指纹 model_id、提示的编号 [8, 5, 12, 12, 15]、生成的 8 个编号和对应的文字 "mzjsldhx"，以及 "draft_matches_greedy": true，说明草稿演示的结果和逐个生成完全一致。文字没有意义，因为权重是随机的；可每一个字段都是真算出来的。这就是你的第一份“真实数据”证据。

接下来按纵切的思路一段段往上加。每一段都先写一个会失败的测试，再写实现：

  1. 看清形状和归属。在每一层打印张量的形状，画出哪些是只读的权重、哪些是会变的状态。
  2. 保存与恢复、分段预填充。保存一个会话，恢复后继续生成，结果要和没中断时一样；把提示切成几段处理，结果要和一次处理一样。
  3. 草稿与验证。修改草稿演示的候选，在任意一个位置第一次被拒绝后丢掉后面的草稿，输出要和贪心生成一致。
  4. 测量。最后才测速度，并且按第 27 章的方法写成记录。注意：这个脚本的耗时不能当成 Strata 的性能。

labs/README.md 里的五个任务大致沿着这条路线。先别急着动手，用下面的规划器体会一下：同样的周数，横着铺和竖着切，截止那天手里各有什么。

规划器里的“一格一周”和“接口里藏着一个错误假设”都是教学假设，不是对任何真实项目的统计。它想让你看到的是结构上的差别：纵切让问题在第一个功能接线时就暴露出来，那时返工的范围最小。

28.6 教材也有版本

本书的每一个代码事实，都对照 Strata 的一个固定提交核实过：fb58e0dbc8399662c0e47c76578c6e878b14f6cf，也就是 Strata v0.1.41（提交日期 2026-10-08），研究日期 2026-10-09。Strata 还在快速迭代，新版本里的数字、默认值和接口都可能变。教材要升级时，按图 28-6 的顺序做。

为什么先比较“契约”？因为契约一变，依赖它的推导和实验就全部失效。Strata 自己就是这么看的：layout.hpp 里写着，模型几何的每一个字段都是某个内核依赖的数，改动它就是改动内核的契约，而不是调一个参数。代码事实[S04] 学期中可以维护两个版本：一个学期内不变的稳定版，一个跟踪上游的研究版。

本书自己就走过一遍这个流程。初稿固定在 v0.1.38，升级到 v0.1.39 时，变化最大的契约是调度：服务端从“只能一次服务一个请求”，变成“默认一次一个，可以选择打开批槽位”。所以第 25 章改写了开头、对照和小结，第 27、28 章里“一次只服务一个序列”的句子都补上了“默认”。反过来，README 测速表里的数字一个没变，上游也说明这一版没有重测，相关段落只需重新核对出处。再升级到 v0.1.40 时，上游发布说明写明四种量化给出的回答和 0.1.39 相同，默认行为基本没变。上游报告 改动集中在几处“目前还不能”的说法上：K8V4 格式的 KV 缓存现在也能流式存放（第 17 章），会话可以存成文件、跨重启保留（第 20 章）；此外，不少引用的行号移动了，要逐条重新对齐。再升级到 v0.1.40.2 时，上游发布说明写明，默认的回答和 0.1.40 逐字节相同。上游报告 新功能大多要手动打开。要改的集中在几处：Linux 上什么时候绕过文件缓存直读（第 6 章），多卡自动切分遇到平局时选哪一种（第 21 章），排队请求多久查一次取消（第 24 章），再加上第 22 章的几个计数和名单，以及不少行号。这一次还多了一件事：上游重写了整个 git 历史（#1276）。代码内容没变，每个提交却都换了编号，连版本标签也移到了新的提交上。本书原来固定的提交从此不属于任何分支，书里的每个源码链接都得换一遍。这给“固定到一个提交”补了一条教训：提交号只有在还有分支或标签能走到它时才可靠，这一次连标签都搬了家。所以固定版本时，最好把提交的 tree 哈希也记下来：内容相同，tree 哈希就相同，核对时比它更稳。再升级到 v0.1.41 时，发布说明写明两处默认值变了：一张 NVIDIA 卡读短提示时，CPU 默认分担一部分专家，数值的最后几位会变，回答可能略有不同（STRATA_PREFILL_CPU_SHARE=0 恢复原来的字节）；层切分加 --batch 时，默认每张卡处理一组请求，回答不变。上游报告 这是本书跟过的版本里第一次改动默认输出，“默认回答不变”这条契约被打破了。所以书里每一句讲“逐字节相同”“可以重复”的话，都要逐条重读，补上新的条件。

还有两件事要说清楚。第一，Strata 的代码以 MIT 许可证发布 [S19]，这个许可证管的是仓库里的代码，不能代替模型权重和其他第三方组件各自的许可。第二，本书是独立编写的教学材料，不代表原项目的背书；它是可以授课和自学的完整初版，还没有经过出版社或多位教师的外部审阅。公开发行前，建议请系统方向和模型数值方向的老师分别交叉审阅，再用试讲的反馈检查入门难度。

记住这三点

  1. 先打通一条纵切：一个 token 从输入走到输出，留下可以检查的真实数据，再一层层加功能。零件全绿，不等于系统接好了。
  2. 每个取舍写清五件事：决定、换来、代价、怎样验证、何时重议。数字要有单位和条件。
  3. 交付时给每个组件标明证据的阶段：代码写完、接进主路径、真实数据，还是模拟。别用“完成”两个字盖过任何一层。

常见误解：“先把每个模块都写完、测完，最后再拼起来，效率最高。”

分模块开发本身没错，错在“最后再拼”。模块之间的接口假设，只有在真正接起来时才会受到检验。Strata 的 PLE 模块就是这样：每个零件都通过了对照测试，可主路径从没调用过它们，直到整模型验收才暴露。[S13] 越晚接线，按错误假设写好的代码就越多，返工也越大。先接一条细线，再往上加，总的工作量往往更少。

深入一层：报告结构、可观测性与最后的理解检验

一份合格报告的结构

先提出一个你愿意被实验推翻的问题，然后依次写理论、源码定位、方法、数据、解释和局限。结论要标明自己属于哪一类：代码事实、实验结果，还是推测。所有图都要有单位、样本数和测量条件；来源链接使用固定的提交号，不只指向 main；性能的原始数据和失败日志都要保留；模型文件和依赖的哈希记在清单里。不要只交漂亮的截图。

评分表的红线怎样执行

把教学模拟冒充硬件实测，该项实验的结论一律不计分，即使其余部分做得很认真：读者已经无法分辨哪些数字可信。存在没有说明的状态串用，性能分不能抵消正确性的缺陷。两条红线的共同点是：它们破坏的是“证据可信”这件事本身。

可观测性：让“没在工作”的机制现形

Strata 的会话代码里有两个值得模仿的设计。一是“每层同步”调试模式：它能抓到“某个内核读了后面一层才会写的缓冲区”这类错误，平时看不见，代价是同步开销，所以做成运行时参数，按需打开。二是那个重叠计数器：CPU 和 GPU 的重叠如果退化成串行，返回值和每层耗时都看不出来，只有专门统计“CPU 在 GPU 仍在运行时拿到任务的层数”才能发现。[S13] 你的项目里，凡是声称“加速”“重叠”“缓存命中”的机制，都应该配一个能证明它真在工作的计数器。

约束要能被测试抓住

Strata 要求生成 token 时不做任何显存分配，所以会话的全部状态在开始时按最大长度一次算好、一次分配。注释点明了一个陷阱：如果某次分配发生在“更长序列的第一个 token”，现有的每个测试都会通过。[S13] 换句话说，一条约束如果没有专门的测试去检查它，它就只是一句愿望。写设计文档时，每条约束旁边都写上“哪个测试会在它被违反时失败”。

离开本书时的理解检验

你应该能用自己的话解释：为什么 40 GB 的模型文件不一定需要 40 GB 显存；为什么一次验证多个 token 不等于提前知道未来；为什么同一个指针可能指向不同层的数据；为什么固定的状态不等于可以任意回滚；为什么更多线程不等于能服务更多会话；为什么一个更快的数字必须带着完整的条件。这几句话可以迁移到任何一个推理引擎。Strata 是走进真实系统的入口，不是需要死记参数的终点。
