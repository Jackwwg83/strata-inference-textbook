换一批邻座

在你自己的电脑上，Strata 默认一次只回答一个请求，其他人排队（第 25 章）。你的问题独占整台机器。到了 DeepSeek 的集群上，情况反过来：你的问题和许多陌生人的问题挤进同一批，一起过每一张卡。这一步和 3 个人同批，下一步可能就和 300 个人同批。

按数学，邻座是谁，不该改变你的答案。可浮点数不听数学的。DeepInfer 的测试里有一条很硬的要求：64 个请求一起跑一遍，再一个一个单独跑一遍，每个 token 和它的对数概率都要完全相等（单独跑时强制写出同样的 token）。这一页讲它怎么做到，代价是什么；再看它怎样让模型只吐出合法的格式。

一句话：批大小一变，内核里求和的分组方式就可能变，浮点结果的最后几位跟着变，接近平手的 token 就会被换掉。DeepInfer 用 DEEPINFER_BATCH_INVARIANT=1 把求和顺序固定下来（只支持 NVIDIA）；再让每个请求带着自己的 seq_seed，采样用的随机数只看（种子, 位置），不看批。它的回归测试要求 PPL 逐位相等。结构化输出则在采样前给词表盖一层位掩码，只放行不破坏格式的 token。

5.1 同一个问题，换一批邻座，答案就变了

服务器的一步计算处理的是一整批请求：所有请求的 token 叠成一个大矩阵，一起过每一层。模型最后给每个候选 token 打的分数（logit），本质上是一长串乘积的和。GPU 上，这串和要分给许多计算单元去加。分几段、怎样合并，内核往往按矩阵的形状来定：批里请求少时，把一行拆成更多段，好让每个计算单元都有活干；请求多时，一行一段就够了。这是常见的内核设计思路，下面用一个玩具内核演示。教学推演

分组一变，结果就可能变。原因在第 26 章「浮点数的“相等”，要先定义」讲过：浮点加法不满足结合律，换一种分组，最后一两位就可能不同。这点差别平时无害，可两个候选 token 几乎打平时，它能决定谁赢（第 26 章「差一点点，就换了一个词」）。一个 token 换了，后面整段回答都跟着换。图 D5-1 是本页玩具内核算出的一个例子。

这里要分清两种“可复现”。第一种是确定性：同一批请求原样再跑一遍，结果相同。第二种是批次不变（batch-invariant）：不管和谁同批、批有多大，同一个请求的结果都相同。服务器上的批几乎从不重复，所以只有第二种才能让用户看到可复现的结果。第二种比第一种强得多。

对照 Strata：Strata 默认一条序列独占引擎，同批的“邻座”只有它自己（第 25 章）。它要逐字节重复，靠的是一份“关开关”的配方：关掉提示缓存、专家换入换出、按实测耗时分配的 CPU 份额等几项会改变计算顺序的设置（第 2 章末尾的「常见误解」和第 26 章）。到了集群上，你没法挑选同批的人，批的组成每一步都在变。所以 DeepInfer 不去关开关，而是把内核本身改成“结果不随批变”。

5.2 批次不变：把求和顺序钉死

README 对这个功能只有一句话：让模型结果在不同的批组成下保持相同，用 DEEPINFER_BATCH_INVARIANT=1 打开，只支持 NVIDIA。上游报告（README.md）这个开关默认关闭。代码事实（environ.py）在整个仓库里搜它，它改变行为的地方只有四处：代码事实

  1. 矩阵乘法库切到确定性算法。打开开关后，工作进程启动时调用 deep_gemm.use_deterministic_algorithms(True) 和 tile_kernels.use_deterministic_algorithms(True)。在昇腾 NPU 上，代码直接断言这个开关必须关着，却无条件打开这两个确定性算法，注释说是为了防止 CI 数值不稳定。（runtime_config.py）
  2. 解码注意力打开 FlashMLA 的批次不变选项。解码时的注意力函数 decode_mla_mqa_sparse 接收这个开关；走不融合的路径时，它原样传给 FlashMLA 的 flash_mla_with_kvcache(enable_batch_invariant=…)。走融合内核时，这个参数没有往下传。草稿模型的注意力调用也带着这个开关。（attention_backend.py、attn.py、草稿：attn.py）
  3. 预填充引擎少用一个融合内核。有一个内核把归一化、旋转位置编码、注意力和类型转换融在一起。不开开关时，预填充引擎里满足头数条件的注意力层都走它；打开后，稠密的 packed-KV 层改走不融合的路径。这条不融合的路径调用 FlashMLA 的 flash_mla_sparse_fwd，它不接收批次不变参数。解码引擎里，这类层本来就不走融合内核。（attn.py、attn.py、attention_backend.py）
  4. 专家通信少做一种合并。同时打开批次不变和专家重排时，创建 DeepEP 缓冲区要传 allow_multiple_reduction=False。（userbuffer.py）

这几个库（DeepGEMM、FlashMLA、DeepEP）的源码不在本次发布的仓库里，所以本页只知道开关的名字，不知道库内部怎么实现。从名字看，它们做的都是同一件事：让一次归约的分组和顺序不随批的形状变。教学推演 专家重排为什么牵涉进来，见宽专家并行那一页。

代价是速度。评测脚本给这个开关写的说明是：结果与批组成无关，“更慢”。代码事实（run_eval.py）慢多少，仓库里没有给数字。下面的玩具内核能看出慢在哪：段数固定以后，小批时有计算单元闲着。

学过并行计算的同学：这就是并行归约（reduction）的老问题。把一个长求和拆给多个线程块（矩阵乘法里叫 split-K），能让小批也吃满 GPU，可分组随形状变，结果的最后几位也随形状变。批次不变的做法是放弃“随形状选最快的分组”，换一个固定的分组。并行度少了，所以慢。

注意一点：批次不变换来的是可复现，不是更准。在图 D5-2 这一行里，固定 4 段的和恰好最接近双精度参考，可这是巧合：换一行数，最接近的可能是别的段数。批次不变只保证顺序固定，不挑最准的顺序。教学推演

5.3 确定性采样：随机数只看（种子, 位置）

模型结果不随批变以后，还剩采样这一步。第 2 章讲过，采样就是拿一个随机数 u 去累计概率上扎一针。要可重放，这个 u 也不能跟着批变。README 给的配方是三件事：DEEPINFER_BATCH_INVARIANT=1、DEEPINFER_ENABLE_MTP_VARLEN=0，再给 SamplingParams 传一个固定的 seq_seed；同样只支持 NVIDIA。做到了，相同的输入 token 和采样参数就得到相同的输出。上游报告（README.md）第二件事留到下一节，先看种子。

seq_seed 是每个请求自己带的 64 位种子。不传时，构造函数用 random.getrandbits(64) 现抽一个；SamplingParams 的温度默认是 1.0。所以不做任何设置时，DeepInfer 每次都按概率采样，种子每次都不同，两次运行本来就不一样。代码事实（sampling_params.py）调度器把种子逐个请求抄进采样内核的输入，位置用的是这个 token 在序列里的下标。代码事实（prepare_sample.cpp）

采样内核的说明写得很直接：结果只由（种子, 采样位置, 是否草稿预测）决定，与批大小和行的顺序无关。它的 PyTorch 参考实现把种子和 3 × 位置 + case 混在一起，过一遍 SplitMix64 哈希，得到 u。GPU 内核用的是 TileLang 自带的随机数生成器：用种子和 3 × 位置 + case 初始化（T.rng_init），再取数（T.rng_rand）。两种实现的随机数都只由这两个输入决定。代码事实（random_sampling.py、cuda/random_sampling.py）这就是第 2 章说的计数器式伪随机数：第 n 个随机数直接由（种子, n）算出，和之前抽过几次无关。图 D5-3 画出它的输入。

内核还多做了一步。按累计概率扎针，要先把概率一项项加起来，而这又是一个求和。DeepInfer 的采样内核先把每个 float32 概率转成定点整数（乘以 2³¹ 再取整），再用整数相加。代码事实（cuda/random_sampling.py）整数加法满足结合律，怎么分组都得同一个和，累计概率也就和分组无关。每一行由一个线程块单独处理，行与行之间不共享任何中间结果。代码事实（同一文件）对应的测试把一批行打乱顺序再采样，又把每一行单独拿出来采样，要求结果和整批时逐个相等。代码事实（random_sampling.py）

种子固定，也意味着另一面：同一个种子，永远写出同一段话。评测脚本要对每道题采样多次，就给每一次分一个不同的种子，注释原话是“相同的种子产生相同的输出，所以每个样本都要有自己的种子”。代码事实（run_eval.py）

对照 Strata：两边选的是同一类随机数。Strata 跑 Flash-Next 时用 Philox，第 t 个 token 的随机数只由（种子, 位置 t）决定（第 2 章「伪随机数与种子」）。默认行为也相似：v0.1.45 起，Strata 的服务层给没写采样参数的请求补上模型卡推荐的参数，按概率采样，没给种子就拿时钟当种子，所以两次回答本来就不同；直接用引擎、不写温度时，它仍然贪心解码（第 2 章 2.4 节）。DeepInfer 的 SamplingParams 默认温度 1.0、种子随机，和 Strata 的服务层一样“默认不可复现”。两边也都能固定种子、继续按概率采样：Strata 的请求同样可以带 seed，固定种子就能重放采样出的文字（第 18 章 18.5 节）。代码事实（server.py）真正的区别是：Strata 默认没有同批的邻座要防，DeepInfer 还得打开批次不变。

5.4 为什么要关掉可变长验证

DeepInfer 默认开着投机解码：草稿模型每一步先猜最多 5 个草稿 token，主模型一次验证。代码事实（environ.py）DEEPINFER_ENABLE_MTP_VARLEN=1 再打开“按置信度安排验证”：不是每个草稿都验，而是挑最可能被接受的那些去验。它默认关闭；评测脚本会把它打开。代码事实（run_eval.py）草稿怎么来、为什么能加速，见 DSpark 投机解码那一页。这里只问一件事：确定性采样为什么要求它关掉？

README 只写了“要关”，没写为什么。代码能说明下面三件事。

  1. 打开时，验证名额按整批分配。调度器把批里所有请求的草稿接受率估计放进同一个队列，从高到低排序；再用实测的前向耗时和采样耗时估算吞吐，决定这一步一共验几个草稿；最后按排名把名额分给各个请求。代码事实（mtp_varlen.hpp）开着零开销调度时，GPU 上还会按上一步的置信度再算一遍每个请求的长度。代码事实（worker.py）问答文档的说法一致：CPU 只定总预算，每个请求的长度在 GPU 上用全局排序重算。上游报告（inference_deployment_qa.md）
  2. 关掉时，每个请求只看自己。只有打开它，预热时才会测量那条“批大小—耗时”曲线；曲线是空的，调度器就给每个请求排 1 + 它自己的草稿数，不看别人。代码事实（base.py、mtp_varlen.hpp）
  3. 同一个位置，验不验，用的随机数不同。被验证的位置，先用 case 2 的随机数判定接不接受草稿，被拒了再用 case 1 的随机数从剩余概率里补抽；没被验证的位置，直接用 case 0 的随机数普通采样。代码事实（fused_sample.py）

三件事连起来，就是本页的解读：打开可变长验证后，你的请求在某个位置验不验草稿，取决于同批其他请求的置信度，还取决于实测耗时。验不验，决定这个位置用哪条随机数流；随机数流不同，种子再固定，抽到的 token 也可能不同。两种做法抽出的 token 服从的分布几乎相同，只是具体抽到哪个不一样。教学推演“几乎”是因为补抽时残差少减了一点点（草稿概率先乘一个略小于 1 的系数），残差就永远不会全为 0、抽不出东西；代码注释推导了输出分布和目标分布的偏差上界。代码事实（common.py）图 D5-4 画出这个过程。

对照 Strata：Strata 默认用的是“精确相等”验证：草稿 token 必须和目标模型自己抽到的 token 完全相同才留下。单看这条规则，验几个草稿都不改变写出的字（第 18 章 18.5 节）；Strata 里让回答随草稿变的，是别的机制：尾部跳过（第 26 章 26.5 节），以及 CPU 算一个 token 和一窗几个 token 时的舍入不同（第 2 章末尾的「常见误解」）。DeepInfer 用的是经典的“按概率接受、被拒补抽”，每个位置只保证分布（近似）不变。这种规则下，“验不验”本身就会改变抽到的字。所以在 DeepInfer 上，验证长度本身就必须固定。教学推演

反过来看，关掉可变长验证并不等于关掉投机解码。批次不变测试本身就开着 5 个草稿，验证长度固定，要求整批和单独跑的结果逐个相等。代码事实（test_batch_invariant.py）

5.5 上游怎么测：PPL 一位都不能差

DeepInfer 的离线回归测试只看一个数：每个样本输出的 decode_ppl，即输出 token 平均对数概率取负再取指数。代码事实（offline_inference.py）在 NVIDIA 上，测试打开批次不变，开 5 个草稿，用 4 张卡（EP4、CP2，于是有 2 个 DP rank）跑示例程序，再把每个 rank 的每个样本和基线文件比较。比较用的是 actual == expected，没有容差。代码事实（test_offline_inference.py）examples 的说明也写明：基线按平台和负载分组，每个 DP rank 一组样本，验证时逐个样本精确比较。上游报告（examples/README.md）

这些样本不是贪心生成的。每个样本的温度是 0.4，种子就是它的序号；rank r 拿到的是同样 5 道题重复 r + 1 遍。代码事实（_prompts.py）于是基线文件本身记下了“固定种子就能重放”这件事，见图 D5-5。

它不是批次不变的有力证据，原因有两个。第一，示例程序一批最多放 4 个请求，两个 rank 的前 4 个样本是在同样组成的批里开始的。代码事实（offline_inference.py）第二，昇腾上代码不许打开批次不变，可昇腾的基线也是同样的规律：rank 1 的前 5 个和 rank 0 逐位相同。代码事实（runtime_config.py、offline_decode_ppl.json）为什么在昇腾上也成立，代码没有说明，本页不做推测。

批次不变的直接证据是另一个测试。它造 64 个随机 token 组成的提示，用温度 1.0、top_p 0.7 整批生成 50 个 token；再把每个提示单独跑一遍，强制它写出整批时写出的那些 token，也就是第 26 章的 teacher forcing。整批和单独跑的 token、对数概率、前 5 名候选和它们的对数概率，都要用 == 相等。代码事实（test_batch_invariant.py）

对照 Strata：第 26 章教的是带容差的比较（「浮点比较的容差」），因为 Strata 的 CPU 和 GPU 用不同的顺序算同一个专家，两边本来就不该逐位相同。那一章也说了例外：同样的运算、同样的顺序，才要求逐位相同。DeepInfer 正是先用批次不变把顺序钉死，才敢用 ==。代价也写在仓库里。测试文件的注释说，基线和并行配置绑在一起，换了 EP、CP 就要重测。代码事实（test_offline_inference.py）examples 的说明说，任何数值变化都要先确认是预期的，再用脚本刷新基线。上游报告（examples/README.md）精确比较抓得住一切变化，也因此不区分“错了”和“只是换了个合法的顺序”。

5.6 结构化输出：每一步只放行合法的 token

最后一件事和随机数无关，却同样是“让输出可控”。结构化输出要求模型的输出严格符合一个格式：正则表达式、JSON schema 或 EBNF 文法。用法是给 SamplingParams 传 so_args={"schema_type": …, "schema": …}。上游报告（README.md）问答文档讲了流程：格式先编译成一个文法自动机；解码的每一步，自动机往前走一格，算出哪些 token 合法，生成掩码，作用在采样上。生产环境里，编译放在专门的机器上异步进行。上游报告（inference_deployment_qa.md）

正则表达式与有限自动机

正则表达式描述一类字符串。[A-Z]{2}-[0-9]{3} 的意思是：两个大写字母，一个连字符，三个数字，比如 QZ-345。

检查一个字符串符不符合正则，不必回头重读。可以把正则变成一台有限自动机：它有有限个状态，每读一个字符，就按规则跳到下一个状态；读完时停在“接受”状态，就算匹配。上面这个正则只需要 7 个状态：“已经写对了 0 到 6 个字符”。

自动机还能回答一个更有用的问题：在当前状态下，下一个字符可以是什么。结构化输出用的正是这一点，只是把“字符”换成了“token”，一个 token 可能包含好几个字符。JSON schema 和 EBNF 能描述嵌套结构（括号里套括号），要用带栈的自动机，道理相同。

延伸阅读：维基百科：正则表达式 · 维基百科：确定有限状态自动机 · 维基百科：扩展巴科斯范式 · OI Wiki：自动机 · MDN：正则表达式

在本次发布的代码里，编译交给开源库 xgrammar：三种格式分别调用它的 JSON schema、正则和文法编译器。编译在一个线程池里异步进行，请求等编译完成才进调度；超过 DEEPINFER_XGRAMMAR_TIMEOUT（默认 20 秒）就判这个请求失败。代码事实（compiler.py、matcher.py、so_matcher_builder.py、environ.py）离线版明确拒收“已序列化的文法”。代码事实 这和问答文档里“专门的编译机器”对得上：生产上大概是在别处编好、序列化后传进来。教学推演

掩码的形状很朴素：词表里每个 token 一位，32 个 token 挤进一个 int32；第 i 个 token 在第 i ÷ 32 个字的第 i mod 32 位。代码事实（matcher.py）GPU 内核读这串位，把为 0 的 token 的 logit 改成 −∞，然后才采样、才验证草稿。代码事实（structure_output.py、sampler.py）logit 为 −∞ 的 token 概率为 0，永远抽不到，所以输出一定合法。

上游的示例故意为难模型：提示词要它“随便续写一个很长的故事，不要写编号”，格式却要求 [A-Z]{2}-[0-9]{3}；要它“用自然语言胡思乱想，不要输出 JSON”，格式却是一个 JSON schema。测试要求输出完全匹配格式，并以正常的结束符收尾。代码事实（_structured_output.py）下面用一个只有 12 个 token 的玩具词表重演第一个例子：

学过编译原理的同学：这就是词法分析器的老本行，只是方向反过来：词法分析器拿自动机去认一串已有的字符，结构化输出拿自动机去限制下一个能写的字符。难点在于 token 和字符不对齐，一个 token 可能跨过好几个状态，所以每一步都要对整个词表逐个试走一遍；xgrammar 这类库的工作，就是把这一步做快。

投机解码让这件事多了一层。一步里不止要给真实位置算掩码，还要给每个草稿位置各算一张：匹配器先假装接受草稿 token，往前走，每走一格就填一张掩码，最后再退回去。代码事实（sampler.py）所以匹配器最多要能回退“草稿数 + 2”步。代码事实（matcher.py）这和第 18 章「事务的提交与回滚」是同一个思路。

对照 Strata：Strata 也接受 OpenAI 风格的 response_format（json_object、json_schema），做法却不同。它的文档写明，这是“先在提示里交代格式，再在服务端检查”，不是文法约束解码；生成一次，不合格就返回 502 错误。上游报告（DETAILS.md）它的状态接口也直接报告 "constrained_decoding": False。代码事实（server.py）一台机器服务一个人，失败了重问一次，代价不大。集群上请求量大，又常被程序调用，“保证合法”比“事后检查”值钱得多，于是 DeepInfer 把检查挪到了每一步采样之前。JSON 本身怎么读写，见第 23 章「JSON」。

记住这三点

  1. 同一个请求在不同的批里，结果可能不同：内核按批的形状选求和的分组，浮点加法不满足结合律，接近平手的 token 就会换掉。DEEPINFER_BATCH_INVARIANT=1 把分组固定下来，换来可复现，代价是慢。
  2. 确定性采样要三件事：批次不变、关掉可变长验证、固定 seq_seed。随机数只由（种子, 位置, 用途）决定，与批无关；可变长验证会让“这个位置验不验草稿”取决于整批，所以要关。
  3. 结构化输出把格式编译成自动机，每一步算出合法 token，打包成每 token 一位的掩码，把其余 logit 改成 −∞。它不改模型，只改“能从哪些 token 里挑”。

常见误解：“打开批次不变，结果就更准了。”

不会。批次不变只保证每次都按同一个顺序加，并不挑一个“更准”的顺序。图 D5-2 里固定 4 段的和恰好最接近双精度参考，但这只是这一行数的巧合；第 26 章 Strata 的实测也说明，不同的浮点顺序是同样好的近似。它买到的是可复现：同一个请求、同一个种子，不管和谁同批，都写出同一段话。这对调试、回归测试和“同一个问题给同一个答案”的产品承诺有用，对准确率没有帮助，还要付出速度。

采样内核：两级定点累计概率

random_sampling_tl 给每一行开一个线程块。词表不小于 8192 时，用 256 个线程，把一行折成 2048 条“车道”：第 k 条车道累加第 k、k + 2048、k + 4096……列的概率。概率先按 floor(p × 2³¹) 转成 uint32 定点数再相加。第一级在 2048 个车道和上找针落在哪条车道，第二级在这条车道的列里找具体的 token。代码事实（cuda/random_sampling.py）

取随机数那一步还有个细节：要在 [0, 总量) 里取一个整数，代码先算出总量的最大整数倍 limit，随机数落在 limit 以上就重抽，再取余。代码事实（同一文件）直接取余会让小的余数稍微多出现一点（取模偏差），重抽就没有这个偏差。重抽次数只取决于种子、位置和这一行的概率，所以不影响可重放。

投机验证用三条随机数流

参考实现把三种用途写得很清楚：普通采样用 3p + 0；判定是否接受草稿时，按 min(1, p_目标 ÷ p_草稿) 和一个用 3p + 2 生成的 u 比较；被拒后从残差 max(0, p_目标 − α × p_草稿) 里补抽，用 3p + 1。α = e−0.00005，比 1 小一点点，注释说是为了防止残差全为 0、采不出东西。代码事实（fused_sample.py）GPU 内核里的判定同样在 sample_positions * 3 + 2 上初始化随机数。（cuda/fused_sample.py）草稿模型自己抽草稿时，种子再加一个固定偏移 1000000007，和主模型的数列错开。（fused_sample.py）

温度 0 并不走单独的分支

文档说温度 0 表示贪心，可构造函数把小于 10⁻⁵ 的温度改成 10⁻⁵，同时把 top_p 设为 1、top_k 设为 −1，然后照常走采样内核。代码事实（sampling_params.py）除以这么小的温度，第一名的概率几乎是 1，效果上就是贪心。但不是严格的贪心：概率转成定点数时按 floor(p × 2³¹) 取整，第二名的权重只要不小于 2⁻³¹ 就不为 0。第二名和第一名的 logit 差 Δ 满足 e−Δ/10⁻⁵ ≥ 2⁻³¹，即 Δ ≤ 10⁻⁵ × ln 2³¹ ≈ 2.1 × 10⁻⁴ 时，它仍会按概率被抽中。教学推演（cuda/random_sampling.py）

可变长验证的调度细节

MTPVarlen::schedule 维护两个队列：一个用更早一轮的接受率估计总预算，一个用最近一轮的接受率分配每个请求的长度；注释说这样做是为了保证后面草稿的置信度不影响前面草稿验不验。排序按接受率从高到低，相同时按请求在批里的下标。总预算取“预期接受的 token 数 ÷ 估计耗时”最大的那个批大小，估计耗时 = 预热测得的基线 + 实测斜率 × 批大小 + 采样耗时的中位数。代码事实（mtp_varlen.hpp；耗时估计器在 L19–L131）实测耗时只在打开可变长验证时记录。（worker.py）“按下标打破平手”和“耗时进入公式”这两点，都让一个请求的验证长度依赖于整批，这是 5.4 节解读的依据。

结构化输出的触发词

so_args 还可以带 trigger_token_ids：这串 token 完整出现之前，模型自由生成；出现之后，文法才生效。匹配器用 KMP 算法增量地找这串 token。再加 bound_token_id，一旦写出这个 token，就不再允许自由生成，而是逐个 token 强制写完触发序列。代码事实（sampling_params.py、matcher.py）它适合“先说几句话，再写一个格式固定的工具调用”这类场景；代码里没有写明具体用在哪个产品功能上。匹配器出错时只判这一个请求失败，注释说明这样做是为了不让一个请求的问题拖垮整个引擎。（sampler.py）
