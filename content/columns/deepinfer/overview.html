换个方向看

这本书一直在做一件事：让一台普通电脑跑起一个大模型，服务一个人。Strata 的 README 开头就写着这个目标，显卡 12 GB 显存起步。上游报告[S01]

推理的另一端是 DeepSeek 的线上服务。按 DeepSeek 自己的说法，一个集群每天要处理 155 万亿个 token。上游报告（问答文档第 17 行）2026 年 10 月 20 日，DeepSeek 开源了撑起这个服务的推理框架 DeepInfer。这一页先回答三个问题：它是什么，开源了哪一块，和 Strata 差在哪。

一句话：DeepInfer 是 DeepSeek-V4.1-Flash 的集群推理引擎：预填充、解码、视觉编码分到不同的机器上，专家铺满几十张卡。这次开源的是引擎本体，能做离线推理；KV 缓存系统、把三段接起来的胶水和数据并行负载均衡器都不在仓库里。

1.1 另一端：同样的概念，换成上百张卡

DeepInfer 是一个推理框架，和 Strata 同属第 1 章说的“厨房”那一层（第 1 章）。README 第一句话说：它是撑起 DeepSeek 大规模线上服务的高性能推理框架，这次开源的版本提供离线推理，以及大规模服务需要的核心功能。上游报告（README 第 3 行）它目前只支持一个模型：DeepSeek-V4.1-Flash。

它和 Strata 讲的是同一套概念：MoE 专家、KV 缓存、预填充（prefill）和解码（decode）、投机解码、批处理。差别在规模。Strata 想办法把一个模型塞进一台电脑；DeepInfer 想办法让很多台机器一起服务很多人。DeepSeek 的问答文档写了这个系统从一开始就定下的三个目标：上游报告（问答第 7–13 行）

  1. 支持多家厂商的加速卡，并把每种平台的性能用足。
  2. 用普通硬件组织预填充和解码：预填充用普通的 8 卡机器，解码用普通的 64–128 卡超节点，也就是一组用高速互连连成一体的卡。
  3. KV 缓存保留 72 小时以上：老对话再来时，命中缓存就不用重新预填充。

先感受一下规模差。问答文档说，解码建议从 EP64 起步，预填充和解码的卡数大约 1:1，所以“最小的高效部署单元”是 64 张卡做预填充、64 张卡做解码。上游报告（问答第 65–67 行）EP 是专家并行（EP），第 2 页细讲。图 D1-1 把两端放在一起。

1.2 一个请求的旅程：生产系统地图

DeepSeek 在问答文档里画了一张参考架构图：系统由三段分离（E/P/D 分离）的计算节点和专门的存储节点组成。上游报告（问答第 41–43 行）E 是视觉编码器（VE），把图片变成向量；P 是预填充；D 是解码。分开部署的好处是每一段的资源可以单独配，首 token 延迟（TTFT）和逐 token 间隔（TBT）也能分开调。上游报告（问答第 27–31 行）

注意力部分用数据并行（DP），而且 DP 的份数等于 EP 的份数：每张卡各自服务一批请求的注意力，MoE 层再按专家并行协作。这么多副本要分活，所以 DeepSeek 做了四个负载均衡器：预填充、解码、VE 三个管数据并行副本之间的分配，专家负载均衡（EPLB）管专家在卡之间的分布。为了不重复预填充，还有一套 KV 缓存存储。上游报告（问答第 33 行）进出口还有一个 DeepSeek Recipe，负责在 API 协议和 token 序列之间转换。

下面的地图按那张架构图重画，并按仓库核对了每一块开没开源。点一个方块看它的说明；按走一步，跟着一个请求从进门走到出门。

这张图里最容易看漏的是 Entrypoint 前面那一步：它要先查 KV 存储，算出这个请求的前缀能命中多长，然后才能路由。问答文档特意说，这一步没法藏到别的工作后面。上游报告（问答第 157 行）命中越长，预填充要算的越少，所以“命中多长”决定了这个请求该分到多重的活。各段怎么配卡、KV 怎么存、怎么从 P 传到 D，都在第 3 页；四个负载均衡器的算法在第 2 页。

学过计算机的同学：这就是 Web 后端的经典分层：网关做协议转换（Recipe），负载均衡器把请求分给一群应用服务器（P 和 D），状态放进独立的存储集群（3FS）。不同的是，这里的一台“应用服务器”是几十张卡组成的一个通信域。见维基百科：负载均衡。

对照 Strata：Strata 把这张图压进了一台电脑：serve/server.py 管 HTTP 和排队，serve/frontend.py 套模板、解析输出（第 23 章）；引擎在同一张卡上先预填充、再解码（第 16 章）。默认配置下，一把锁让请求排成一队（第 25 章）。到了集群上，每一层都要拆成独立的服务，因为一台机器既装不下所有用户，也不能让所有用户排一条队。

1.3 开源边界：仓库里有什么，没有什么

README 把边界写得很清楚。这次开源的功能有：优化过的内核和模型、采样器运行时；注意力的数据并行和均衡的上下文并行（CP）、MoE 的专家并行加 EPLB；DSpark 和按置信度调度的验证；滑动窗口注意力（SWA）的有界重放（bounded replay）；异步调度，也就是零开销批调度器；批次不变（batch-invariant）推理；确定性采样；结构化输出。上游报告（README 第 9–18 行）

它也列了“完整的推理服务还需要、但这次没有包含”的三样：上游报告（README 第 38–42 行）

  • 一套 KV 缓存系统；
  • VE / 预填充 / 解码的拆分部署（README 补了一句：引擎需要的功能大部分已经实现）；
  • 预填充和解码在数据并行副本之间的负载均衡。

问答文档给了原因：KV 缓存管理和负载均衡跟 DeepSeek 内部的基础设施绑得太紧，暂时没有完整开源。上游报告（问答第 21 行）DeepSeek Recipe 则单独开源成了另一个仓库 deepseek-recipe。上游报告（问答第 19 行）

“大部分已经实现”这句话，能在代码里找到对应。引擎有三种类型：NORMAL 既做预填充也做解码，PROMPT 只做预填充，COMPLETION 只做解码。代码事实（engine_type.py，C++ 一侧同样定义在 scheduler.hpp）可主引擎类 LLMEngine 里有一段注释“这里开始都是虚函数”：初始化 PD 分离、预填充保存 KV、保存 KV、把算完的请求发给解码引擎，这几个函数只有一行说明，没有函数体。仓库里也没有别的类去实现它们。代码事实（llm_engine.py 第 800–858 行）图 D1-3 画出了这个边界。

还有一样容易误会的：仓库里有个目录叫 deepinfer/entrypoints/，可它不是图 D1-2 里的生产 Entrypoint。里面只有一个离线用的 LLM 类：在本进程里建好引擎，把一批提示词塞进去，循环调用 step() 直到全部做完。代码事实（llm.py）仓库里唯一的 HTTP 服务是一个默认关闭的性能采样接口 POST /profile，不接用户请求。代码事实（profile_server.py）

问答文档说生产上暂时不用张量并行（TP）和 CP，可 README 和例子都支持 CP（例子里有 --cp 8）。上游报告（问答第 53 行，examples/README 第 6–8 行）两者不矛盾：一个说线上怎么配，一个说代码能做什么。

1.5 谁能跑、要多少卡、坏了怎么办

先说门槛。硬件只有两种：NVIDIA SM100 GPU 和华为昇腾 950 NPU。软件要 Linux、GCC 13 以上、Python 3.12，NVIDIA 要 CUDA 13，昇腾要 CANN 9.2。上游报告（README 第 33–52 行）离线例子的默认参数是 --ep 8，也就是按一台 8 卡机器写的。代码事实（offline_inference.py）基准测试的规模由环境决定：ep_size = WORLD_SIZE × 可见卡数，WORLD_SIZE 是节点数。上游报告（examples/README 第 61 行）

所以本专栏的大多数读者跑不了 DeepInfer，本书也没有跑过。下面的每个数字都是 DeepSeek 自己报告的，本书没有复测。

两张性能图都是 README 说的基准：预填充用 4 张、解码用 64 张 SM100，各自在一个 scale-up 域里。上游报告（README 第 83 行）解码图的吞吐不是实测接受率，而是按假设的接受率折算的；第 4 页细讲这本账怎么记。

155 万亿 token 是什么量级？按一天 86,400 秒摊开：155 × 10¹² ÷ 86,400 ≈ 18 亿 token/s。Strata 在一张 RTX 5070 上写答案约 93 token/s（第 1 章），18 亿 ÷ 93 ≈ 1900 万。教学推演 这个比值只给数量级的直觉：问答文档没说这 155 万亿里有多少是输入、多少是缓存命中，而 Strata 的 93 只算输出。

弹性伸缩和容错。问答文档用一小节讲了线上怎样应对流量起伏和坏卡。上游报告（问答第 193–211 行）预填充按“没命中缓存的 token 数”决定要几台机器，解码按“正在跑的请求数”调整；每次调整都限速，也有上下限。解码引擎收到下线通知后有 1 分钟宽限期，没做完的请求连同 KV 缓存一次性转给别的解码引擎接着做。平时总留一些冗余：池子里有空着待命的机器，在线实例也比算出来的需求多；配额利用率高于 0.8 时禁止缩容。重启要几分钟，所以容错靠冗余和请求级的重新路由，不靠把单个引擎重启得更快。

宽专家并行有一个特别的弱点：一个实例的所有卡组成一个通信域，坏一张卡，整个实例就不能用。重启时，平台按当前健康的卡数重新决定 EP 大小。代码里有一处和它配套：冗余专家数会自动补到“专家总数能被 ep_size 整除”为止，所以 EP 大小不必是 384 的约数。代码事实（eplb/__init__.py）这和故障恢复的关系是本书的推断，问答文档没有这样说。教学推演

对照 Strata：Strata 只有一台机器，没有“别的卡”可以接手。它的生命周期问题是进程怎么启动、请求怎么取消（第 24 章「取消」），排队问题是一条队怎么排（第 25 章「排队论入门」）。到了集群上，坏卡是常态，所以“少一张卡还能不能接着服务”成了设计的一部分。

1.6 这个专栏怎么读

后面四页，各挑生产系统里的一块，讲清它的道理，再落到代码上。每页都先回到本书讲过的概念，再说集群上哪里不一样。图 D1-5 是路线图。

  • 第 2 页 宽专家并行：注意力按数据并行、专家按专家并行；为什么 EP64 比 EP8 吞吐高；EPLB 和三个数据并行负载均衡器怎么分活。先读第 10 章和第 21 章「流水线并行与张量并行」。
  • 第 3 页 三段分离与 72 小时 KV 缓存：VE、P、D 为什么分开；KV 缓存怎样存进 SSD 集群、命中后怎样只重算一小段。先读第 17 章「分页式管理」和第 20 章。
  • 第 4 页 DSpark 投机解码与零开销调度：草稿一次猜几个、按置信度决定验几个；CPU 排下一步时 GPU 不停。先读第 18 章和第 25 章「连续批处理」。
  • 第 5 页 批次不变、确定性采样与结构化输出：同样的输入为什么在服务器上会变，怎样把它变回相同；怎样让模型只输出合法的 JSON。先读第 26 章和第 2 章。

记住这三点

  1. DeepInfer 和 Strata 讲同一套概念，难题相反：Strata 要把模型塞进一台电脑，DeepInfer 要让上百张卡一起服务很多人。
  2. 生产系统由 Recipe、Entrypoint、三段分离的 VE / P / D、四个负载均衡器和一个 KV 存储集群组成。这次开源的是引擎本体和 EPLB，能做离线推理。
  3. KV 缓存系统、把三段接起来的胶水、数据并行负载均衡器都不在仓库里；引擎为它们留了类型和空钩子，要部署者自己补。

常见误解：“DeepInfer 开源了，拿来就能搭出 DeepSeek 那样的在线服务。”

这次的仓库只提供离线推理：一个进程收一批提示词，算完就退。没有接用户请求的 HTTP 服务，没有 KV 缓存系统，没有把预填充和解码接起来的胶水，也没有数据并行负载均衡器。README 列出的硬件只有 SM100 和昇腾 950，问答文档建议的最小高效单元是 128 张卡。它最大的价值，是让人看清一个生产级引擎内部怎么写。

深入一层：一次离线推理的调用链，以及怎样自己核对开源边界

从命令行到内核

以 python examples/offline_inference.py 为例，下面每一步都对照了固定提交 774ce244 的源码。

  1. 启动进程。例子默认 --ep 8（offline_inference.py 第 12–17 行）。examples/_launch.py 的 run_dp 按 RANK 和 WORLD_SIZE 给本节点负责的每个 DP rank 起一个子进程（第 26–40 行）。
  2. 建引擎。LLM.__init__ 用 offline_inference=True 构造 EngineArgs，再调 LLMEngine.from_engine_args（llm.py 第 70–84 行）。EngineArgs 的引擎类型默认是 NORMAL（arg_utils.py 第 41 行）。
  3. 零开销调度默认开。environ.py 里 DEEPINFER_ZERO_OVERHEAD_SCHEDULING 的原始默认值是关（第 179 行），但 EngineArgs.__post_init__ 会在用户没设时，按引擎类型把它设成开：NORMAL 和 COMPLETION 开，PROMPT 关（arg_utils.py 第 48–55 行，engine_type.py 第 15–17 行）。所以 README 说“默认开启”，和代码一致。
  4. 分词和提交。generate() 把每个提示词交给 _add_request；没给 token 编号时，用 Hugging Face 分词器编码（llm.py 第 144–166 行）。生产上这一步由 Recipe 做。
  5. 主循环。_run_engine 反复调 LLMEngine.step()，直到没有未完成的请求，再把在途的结果冲出来（第 168–195 行）。LLMEngine 从 C++ 扩展 deepinfer._C.engine 导入 Scheduler、BlockManager 等（llm_engine.py 第 19–31 行）。这个扩展由 setup.py 把 csrc/ 下的源文件编译而成，分成 cuda_utils、engine、graph_timer 三个子模块（pybind.cpp）。
  6. 每张卡上。Worker 驱动每一步的前向、后处理和采样（worker.py），ModelRunner 跑模型（model_runner.py）。模型由注册表找到：架构名 DeepseekV41ForCausalLM 对应 deepseek_vl.DeepseekVLForCausalLM（models/__init__.py 第 15–17 行），它继承自纯文本的 DeepseekForCausalLM（deepseek_vl.py 第 26 行）。
  7. 落到内核。平台类决定用哪一套 TileLang 算子：GPU 用 cuda，NPU 用 asc（platform.py 第 55–88 行）。其余算子来自表 D1-2 的内核库。

自己核对开源边界

本页关于“没有开源”的判断，可以在一份克隆里用三条命令复查：

  • git show 774ce244:deepinfer/engine/llm_engine.py | sed -n '800,858p'：看到“这里开始都是虚函数”和一串只有说明的函数。
  • git grep -n "def send_processed_prompts" 774ce244：只有 llm_engine.py 一处定义，没有子类实现它。
  • git grep -n -w "3FS" 774ce244 -- '*.py' '*.cpp' '*.hpp' 和 git grep -n "kvcache-store\|kvcache_store" 774ce244 -- '*.py' '*.cpp' '*.hpp'：都没有结果。3FS 和 kvcache-store 只出现在问答文档里。（别加 -i：不分大小写时，日志格式串里的 %.3fs 会被误匹配。）

本页没有核对的东西

vendor/ 下的 6 个子模块在本书使用的克隆里没有展开，所以本页只写 DeepInfer 怎样导入它们，不评价它们的实现。deepseek-recipe 是另一个仓库，本页对它的描述全部来自问答文档第 19、35 行和第 290–312 行。模型形状来自 Hugging Face 上提交 1bae0e10 的 config.json，它不受 DeepInfer 固定提交的约束。两张性能图的数值是本书从图上读的，精度约为刻度的一半。
