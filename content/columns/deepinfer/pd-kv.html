你可能注意到过

把一份长文档丢给聊天 AI，第一个问题要等一会儿才开始回答；接着追问，回答几乎马上就冒出来。第 20 章讲过 Strata 的办法：把读过的前缀存成检查点，放在本机内存里，下次只读新加的部分。

DeepSeek 的线上服务每天要接住数不清的这种追问。它把同一件事做成了一套集群系统：读题和写答案分到两组卡上，KV 缓存存进专门的 SSD 集群，保留 72 小时以上。这一页回答三个问题：为什么要分开，KV 缓存放在哪，命中以后怎么接上、差一点没命中时怎么少算。

一句话：预填充（prefill）吃算力，解码（decode）吃带宽，挤在同一组卡上会互相拖慢，所以 DeepSeek 把视觉编码器、预填充、解码分开部署。KV 缓存放在专用的 3FS 存储集群里，命中了就读回来；滑动窗口那一小块缺了，也只重算 128 个 token。开源的 DeepInfer 带了这些做法要用的引擎角色和缓存布局，KV 缓存系统和分离部署的衔接代码没有开源。

3.1 读题和写答案，为什么要分到两组卡上

第 16 章讲过，一次请求分两段。预填充（prefill）是读题：提示词的 token 全都已知，几千个一起算，权重读一遍供一整块共用，瓶颈是算力。解码（decode）是写答案：每一步每个请求只多出几个 token（DeepInfer 开着投机解码，测速图里平均每步约 3 个），却要把权重和 KV 缓存读一遍，瓶颈是带宽。两段在 roofline 上的位置不同，见第 5 章「roofline」和第 16 章「批处理」。

用户的体感也对应两个指标。首 token 延迟（TTFT）是从发出请求到看到第一个字的时间，主要花在预填充上。逐 token 间隔（TBT）是之后相邻两个 token 之间的时间，取决于解码每一步多快、会不会被打断。

麻烦出在两段挤在同一组卡上的时候。DeepInfer 的开源代码里就有这种“混合”引擎，看它怎么排班最清楚。代码事实引擎分三种角色：NORMAL 两段都做，PROMPT 只做预填充，COMPLETION 只做解码（engine_type.py）。NORMAL 引擎的每一步，要么全组做预填充，要么全组做解码：同一个数据并行（DP）组里的卡必须做同一种，靠一次投票统一（scheduler.hpp）。投票点默认每 70 步解码一次，所有 rank 都有预填充的活才一起做；另有每 100 步一次的保底点，任一 rank 有活就一起做（environ.py）。

这样排班，一步预填充做多久，这组卡上所有用户的解码就停多久。下面的时间线把两种部署放在一起。步长取自 DeepInfer README 的两张测速图：预填充一步 32,768 个 token 约 376 ms，解码一步约 13 ms。教学推演两张图的硬件配置不同，这里只借它们的量级，条件见文末“深入一层”。

图里能看出两件事。第一，混合部署时解码的步间隔偶尔会从 13 ms 跳到 389 ms，正在看回答的用户会觉得卡了一下。投机解码一步吐出约 3 个 token，所以平均每个 token 约 4 ms，它们是一阵一阵到的；这里拿步间隔代表 TBT。第二，为了少停几次，混合引擎把预填充攒起来做，新请求要等到下一个投票点，TTFT 反而变长。真实的混合引擎还会更糟一点：刚做完一步预填充，下一步又落在投票点上，各 rank 都还有活就接着做（scheduler.hpp）。代码事实

DeepSeek 的生产系统因此把视觉编码器（VE）、预填充、解码分开部署，各用各的卡，这叫三段分离（E/P/D 分离）。Q&A 文档的说法是：分开后每一段的资源单独配，TTFT 和 TBT 就能分别控制、分别优化（Q&A 文档）。上游报告开源代码里，PROMPT 引擎处理完的提示要“发送给 completion engine”，可这个函数是空的（llm_engine.py）。代码事实README 也写明，分离部署不在这次发布里，只是“需要的引擎功能大部分已经实现”（README）。上游报告

学过计算机的同学：这是操作系统课上交互式任务和批处理任务抢同一个 CPU 的老问题。长作业一占住处理器，短任务的响应就被拖长，第 25 章把这叫护航效应，并用 FIFO 和轮转演示过（第 25 章「调度算法」）。三段分离相当于给两类任务各配一台机器。学术界也有同样的论证，见 DistServe 论文。

对照 Strata：Strata 在一台电脑上跑，读题和写答案只能轮流用同一张卡。第 16 章那张测速表里，RTX 5070 读 32K 的提示词每秒 2,171 个 token，写答案每秒 81.8 个上游报告；服务端默认一次只跑一段对话（第 17 章）。一个人用，读题时没有别人在等解码，拆开没有意义。到了集群上，一次长提示的预填充会让同组几百个用户的解码一起停下来，所以要拆。

3.2 每一段配多少卡：8 卡机器和 64 卡超节点

分开以后，每一段可以按自己的瓶颈挑并行方式。Q&A 文档给的配置如下（目标、并行方式）。上游报告

阶段并行方式怎么取硬件
预填充专家并行（EP）2–8，数据并行（DP）2–8显存（HBM）够用就取最小普通 8 卡机器
解码EP64–128 / DP64–128，即宽专家并行（Wide-EP）卡够就取最大64–128 卡的超节点
视觉编码器（VE）一个实例一张卡推荐用便宜的卡—
张量并行（TP）、上下文并行（CP）暂不使用——

两头的取法正好相反。预填充一步本来就有上万个 token，每个专家分到的 token 已经够多，矩阵乘法跑得满，EP 小一些还能少一些跨卡通信。解码一步每个请求只有几个 token，要把很多请求的 token 汇到同一个专家上，才凑得出像样的批，所以 EP 越大越好。教学推演这笔账在宽专家并行那一页细算。超节点指 64–128 张卡用高速互连连成一个整体的系统。

最小能部署 1 个预填充实例加 1 个解码实例。实际 P 和 D 的卡数大约 1 : 1；解码推荐 EP64 以上，所以最小的高效单元是 64 张预填充卡加 64 张解码卡（Q&A 文档）。上游报告图 D3-2 把这个单元画出来。

P 和 D 能不能放在不同的数据中心？Q&A 文档说可以：V4.1 Flash 把 KV 缓存压得很小，跨数据中心传是可行的，每 8 张卡预留约 400 Gbps 的互连带宽。代价是可靠性：两个机房之间的光纤，施工时一铲子就可能挖断。DeepSeek 实际把推理节点放在不同但相邻的数据中心（Q&A 文档）。上游报告

表里写着生产上暂不用 CP，开源代码却带了它，README 的功能列表写着“balanced CP”（README）。两者不矛盾：代码支持，生产没开。上下文并行（CP）把一条长提示切成几段，交给几张卡一起算注意力；代码只让预填充用它（llm_engine.py）。代码事实“平衡”的切法见文末“深入一层”。

卡数也不是定死的。Q&A 文档说，预填充按“没命中缓存的 token 有多少”决定要几台机器，解码按“正在跑的请求有多少”调整（Q&A 文档）。上游报告也就是说，命中率直接决定要开多少台预填充机器。扩缩容和容错的其余细节见总览页。

3.3 KV 缓存放在哪：显存、本机内存、3FS

DeepSeek 给这套推理系统定的第三个目标是：KV 缓存保留 72 小时以上。窗口越长，用户隔天回来追问也能命中，省下重复的预填充；代价是要存很多、管很多（Q&A 文档）。上游报告这些 KV 分三处放，图 D3-3 按 Q&A 文档里的表画出（表格）。

为什么用一个专门的存储集群，而不是每台机器自己的内存加硬盘？Q&A 文档给了三条理由（Q&A 文档）。上游报告

  • 任何一台预填充机器都能命中任何前缀。负载均衡器只管哪台闲，不用顾忌“这个用户的缓存在哪台机器上”；预填充的负载均衡也因此不做前缀亲和路由（Q&A 文档）。
  • 存储节点和计算节点可以分别扩缩容。
  • 计算节点坏了，KV 缓存不丢。计算节点的故障率比存储节点高一个数量级以上。

解码时产生的 KV 也照样写盘，为的是提高命中率（Q&A 文档）。上游报告道理很简单：这一轮写出的回答，就是下一轮提示的前缀。

存储服务器的推荐配置是 20 块 30.73 TB 的 SSD；每台至少提供 40 GB/s 的读、5 GB/s 的写，总容量要够存 24 小时的数据，再按推理部署的规模加台数。按逻辑大小算，每张在线推理卡大约对应 14.4 TB 的存储，实际要的物理容量更多（Q&A 文档）。上游报告

拿这几个数粗算一下。一台存储服务器的原始容量是 20 × 30.73 ≈ 615 TB；10 + 2 纠删码让物理空间是逻辑数据的 1.2 倍，除以 1.2 约 512 TB，大约够 512 ÷ 14.4 ≈ 36 张在线卡的逻辑数据。这 36 张卡里预填充和解码约各一半；解码卡不从存储读前缀，它的 KV 由预填充卡传过来。所以真正来读的是约 18 张预填充卡，同时读时每张分到约 40 ÷ 18 ≈ 2.2 GB/s。教学推演这只是按容量配机器时的粗略下限：Q&A 文档没有给存储服务器和卡的比例，一次读也会分散到纠删组的多个节点上。3.5 节的交互图还会用到这个数。

3FS 是 DeepSeek 自己的分布式文件系统（3FS 的 GitHub 仓库）。它要在节点故障和网络抖动下，同时做到高可用和高性能。数据按 10 + 2 纠删码存，每个纠删组能同时坏两个节点。按 Q&A 原文，读的时候同时向组里 11 个节点发请求（一组共 10 + 2 = 12 块），任意 10 个回来就能解出数据。每个存储节点上跑一个回收进程（GC Worker），按最近最少使用（LRU）定期清掉旧缓存，让磁盘用量保持在水位线以下（Q&A 文档）。上游报告

纠删码：多存一点校验，坏几块也能拼回来

最简单的防丢办法是存三份副本，坏两份还剩一份，可空间要三倍。纠删码更省：把数据切成 k 块，再算出 m 块校验，一共存 k + m 块，分到不同的机器上。只要任意 k 块还在，就能把原数据算回来。

定义：(k + m) 纠删码能容忍任意 m 块同时丢失，空间开销是 (k + m) ÷ k 倍。常用的构造是里德-所罗门码，它把数据看成多项式的取值，丢掉的取值可以从剩下的点插值回来。

一个具体数字：3FS 存 KV 缓存用 10 + 2，空间只多 20%，任意坏两个节点都不丢数据。三副本要多 200%，也只能扛两个。代价是读写都要算编码，读的时候要凑够 10 块。

和本页的关系：KV 缓存坏了可以重算，看起来不必这么讲究。可它要扛 3 到 7 天、约 100 PiB，一次节点故障丢掉的是成千上万用户的命中。纠删码让这份“可以重算的数据”用较少的空间换来较高的可用性。

延伸阅读：维基百科：里德-所罗门码 · 维基百科：RAID · Wikipedia: Erasure code

kvcache-store 这一层没有过期逻辑，回收全靠 3FS 自己的 GC。3FS 给 KV 缓存提供约 100 PiB 的 SSD；保留期（TTL）是 Agent 流量 3 天、聊天流量 7 天。聊天流量的长尾更重，少量 KV 被反复读很多次；经验上 TTL 只给 3 天，聊天流量的命中率会少 0.5%–1%（Q&A 文档）。上游报告这正是第 12 章讲的命中率与工作集：多久以前的访问还算数，决定了缓存要多大（第 12 章「命中率」）。

学过计算机的同学：10 + 2 纠删码和 RAID 6 是一个思路：多存两份校验，任意坏两块都能恢复。“发 11 个请求、收到 10 个就解码”是冗余读：多发一个请求，取最先回来的 10 个，不等最慢的那一个，用来压长尾延迟。

对照 Strata：Strata 的 KV 缓存也分层：平时在显存；上下文超过 64K 时，完整的 KV 放在内存，显存只留常用的页（第 17 章「分页」）。前缀复用的检查点也在本机内存里，一个约 118 MB，最多留 6 个（第 20 章）。一台电脑只服务一个人，下次追问还落在这台机器上，本机内存就够了。DeepSeek 那边，一个用户的下一次请求可能落在任何一台预填充机器上，KV 还要留 3 到 7 天，只能放进一个人人都够得着的共享存储。

3.4 两种 KV：分页的块 KV，定长的 SWA 状态

V4.1 Flash 的注意力有两种记忆。一种和第 17 章一样，随对话变长而增长，用分页管理，叫块 KV；另一种只记最近的一小段，叫 SWA 状态。滑动窗口注意力（SWA）是注意力的一种简化：每个 token 只看自己前面最近的一段，窗口外的不看（注意力本身见第 8 章「注意力」）。V4.1 的窗口是 128 个 token（Q&A 文档）。上游报告窗口大小来自模型的配置文件（config.py），配置文件本身不在代码仓库里。

两种记忆，DeepInfer 用两个分配器分别管（llm_engine.py）。代码事实

  • 块 KV 按 128 个 token 一块，像第 17 章的分页那样用块表找（model_metadata_utils.py）。块 KV 里装主 KV 和索引器的 K（Q&A 文档）。一条 KV 记录是 512 个数加缩放系数：FP8 时 528 字节，FP4 时 288 字节（cache_common.py）。压缩层每 ratio 个 token 才存一条记录，一块 128 个 token 只占 128 ÷ ratio 条（cache_engine.py、同一文件）。
  • SWA 状态 不进分页的块。每个序列在状态缓存里占一个定长的槽位，叫 StateBlock。槽位按要不要存档分成两区：前面是要存档的 SWA，后面是不存档的部分，包括 YoCo 消费层的 SWA 和压缩状态（cache_engine.py）。每层是一个环形缓冲，装 128 + 6 = 134 个 token，多出的 6 个留给投机解码回退（cache_engine.py、environ.py）。默认设置下，位置 pos 的 token 写进第 pos mod 134 格，新 token 覆盖最旧的（prepare_tensor_input_v4.cpp）。

一个请求进来，分配器一次给它一张块表和一个槽位号（block_manager.hpp）。代码事实图 D3-4 画出这两样东西。

SWA 状态要存档的只有前一区。代码把这一区叫 to disk（“落盘”），可 SWA 并不进 3FS，而是存在本机内存里，见下文；本页统一叫“存档”。Q&A 文档算过它的大小：20 层 × 134 个 token × 528 字节 ＝ 1,415,040 字节，每个序列约 1.4 MB（Q&A 文档）。上游报告代码里的公式对得上：存档大小等于“要存档的层数 × 每层 134 个 token 的字节数（按 32 字节对齐）”（cache_engine.py）。代码事实134 × 528 ＝ 70,752 字节，正好是 32 的倍数，对齐不多占地方。教学推演“前 20 层存档”是 Q&A 给的数，代码按模型配置自己算层数。

这块状态只在 128 的整数倍处存档：代码里的存档粒度是 128，存档位置不是 128 的倍数就直接报错（cache_engine.py、同一文件）。代码事实按 Q&A 文档，解码时每跨过一个 128 的边界，就在显存里把当前窗口复制一份，请求结束时从最近一份存档（Q&A 文档）。上游报告开源代码里有复制函数，可决定“要不要复制”的 should_copy_state 恒返回 False（llm_engine.py）。代码事实预填充和解码各自怎么挑存档位置，见文末“深入一层”。

存到哪？SWA 状态不进 3FS，只留在产生它的那台机器的内存里。Entrypoint 机器上有一份内存目录，逻辑上是一份，物理上按键分散在各台 Entrypoint 机器上，记着哪台机器有哪段 SWA。命中时本机没有，就经 400G VLAN 从别的机器拉回来（Q&A 文档）。上游报告从预填充传到解码时，SWA 状态和块 KV 走同一条路。代码里，发给解码引擎的状态比存档的多：不存档那一区（消费层 SWA 和压缩状态）也一起发过去（cache_engine.py）。代码事实

开源代码里，存档和传输的接口都在，内容是空的。LLMEngine 里有一排“虚函数”：初始化分离部署、保存 KV、把处理完的提示发给解码引擎，默认什么都不做（llm_engine.py）。序列对象把“命中 token 数”“SWA 有效起点”等字段留给外部填，注释写着“外部注入命中数”（sequence.hpp）。代码事实我在这次发布里没有找到从外部存储查命中、再写进这些字段的代码，这和 README 一致（README）。

对照 Strata：第 20 章把两种记忆比作笔记本和白板：KV 缓存像笔记本，按位置往后写，退回去只要不看后面几行；GDN 的递推状态像白板，每个 token 整块改写，过去的样子只能靠事先拍照（第 20 章「快照与写时复制」）。DeepInfer 的块 KV 是笔记本，SWA 状态更像白板：定长的环形缓冲，新 token 覆盖最旧的。它不像 GDN 那样每步整块重写，一步只改一格；共同点是被覆盖的历史退不回去。所以它和 Strata 的 GDN 状态一样，只能在约定的位置拍照存档。Strata 的检查点约 118 MB，大头是那块白板；DeepInfer 每个序列只存约 1.4 MB 的 SWA，因为窗口只有 134 个 token。

3.5 命中了就读，SWA 缺了只重算 128 个：有界重放

一个长度为 L 的请求来了，能复用多少？Q&A 文档定的规则是：命中长度由块 KV 决定，最后一块要不要重算由 SWA 状态决定（Q&A 文档）。上游报告具体分三步：

  1. 命中长度最多是 L − 134：给窗口留 128 个 token，给投机解码回退留 6 个。
  2. 在这个上限内查块 KV，得到命中长度 L1，它是 128 的倍数。
  3. 再查 SWA 状态：在 L1 − 128 到 L1 之间有存档，命中长度就是 L1；没有，就退一块，命中 L1 − 128，退掉的这 128 个 token 重算。

退一块之后怎么重算？精确的做法是把 SWA 状态从头算回来，可滑动窗口一层层往前看，要追溯很远。DeepInfer 用的是有界重放（bounded replay）：只重算最近 128 个 token，并把窗口截在重放段之内。从位置 s 开始重放时，位置 i 的查询只看 max(s, i − 127) 到 i 的键，算出一份近似的 SWA 状态。要重放的 token 数就成了常数，和上下文多长无关；这 128 个 token 仍要走完每一层（Q&A 文档）。上游报告代码里，普通预填充的 SWA 可见范围左端取“窗口左端”和“SWA 有效起点”两者的最大值（prepare_tensor_input_v4.cpp）；有效起点之前的历史用零填上，注意力看不到它们（同一文件）。代码事实这就是 Q&A 里 max(s, i − 127) 的实现，s 就是有效起点。开着下面讲的截断时，另一个函数再多取一个“截断左端”，三者取最大（同一文件）。

同一招还用在另一处，而且每次预填充都能用。V4.1 Flash 的层分两半：前面是“编码器层”，后面是“解码器层”。解码器层的块 KV 不自己算，而是从最后一个编码器层的隐藏状态投影出来，每层只需要算自己的 SWA 状态。代码把这种结构叫 YoCo，同名论文《You Only Cache Once》描述过同类的“解码器-解码器”结构。要精确算出解码器层的 SWA，得让最后 2,560 个 token 走一遍 20 个解码器层；DeepInfer 只让提示的最后一小段走这 20 层，结果只给解码用，不进前缀缓存。Q&A 说这几乎把预填充的总计算量砍掉一半（Q&A 文档）。上游报告2,560 正好是 20 × 128：每过一层，滑动窗口就再往前看 128 个 token。教学推演

这一处的开关，README 和代码写得很具体。设 DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=compact、DEEPINFER_YOCO_PREFILL_KEEP_TOKENS=140 是 V4.1 的默认用法，保留的尾巴必须盖住窗口加最大回退长度（README）。上游报告代码要求 KEEP_TOKENS ≥ 窗口 + 回退，也就是至少 128 + 6 ＝ 134：加载模型时检查一次，每次准备输入时再查一次，不满足就报错（model_runner.py、prepare_tensor_input_v4.cpp；规则写在 environ.py 的说明里）。代码事实Q&A 说解码器层只重算“最后 128 个 token”，代码和 README 实际保留 KEEP_TOKENS 个，默认用法是 140 个；本页以代码为准。

命中以后，KV 怎么从 3FS 回到显存？Q&A 文档拆成三步（Q&A 文档）。上游报告匹配：Entrypoint 按哈希链比对前缀，只碰元数据，但命中长度要在路由前算出，这一步藏不住。取 KV：单独的进程异步把 KV 从 3FS 搬到主机共享内存。换入：引擎里的一个线程把它逐层拷进显存，和前向计算重叠；KV 块又小又碎，所以换入用 GDR，让 RDMA 网卡吃满 PCIe 带宽，不占 GPU 的计算单元。“一边搬一边算”的道理见第 14 章「同步与异步、双缓冲」。

那么，读回来到底比重算省多少？下面这笔账用 DeepSeek 报告的数做默认值：存储服务器每台至少 40 GB/s 读上游报告；预填充每卡每秒约 87,000 个没命中的 token，来自 README 测速图（4 张 SM100、EP4DP4、131,072 上下文）上游报告。每个 token 的 KV 有多大，本页没有核实，默认取 8 KiB，这是假设。还有一个假设：测速图里的 87,000 是平均吞吐，这里直接拿来算“长前缀之后的那截尾巴”；尾巴要对 11 万多个 token 做注意力，实际可能更慢。教学推演

算下来，读比算快得多：一个 128K 的请求命中 90%，预填充从约 1.5 秒降到约 0.18 秒。临界点是“读带宽 ÷ 预填充吞吐”：40 GB/s ÷ 87,000 token/s ≈ 449 KiB，每个 token 的 KV 只要小于它，读就比算快。可如果按 3.3 节的容量粗算，约 18 张预填充卡同时读一台存储服务器，每张只分到约 2.2 GB/s，临界点就掉到约 25 KiB，和假设的 8 KiB 只差 3 倍。教学推演所以存储的读带宽要跟着在线卡数一起配，否则命中省下的时间会被排队读吃掉。

记住这三点

  1. 预填充吃算力，解码吃带宽。挤在一组卡上，一步预填充就让所有人的解码停下来。DeepSeek 把视觉编码器、预填充、解码分开部署：预填充用 8 卡机器（EP2–8），解码用 64–128 卡超节点（EP64–128），最小高效单元是 64 + 64 张卡。
  2. 块 KV 按 128 个 token 分页，存进专用的 3FS 集群（10 + 2 纠删码，约 100 PiB，TTL 3–7 天）；SWA 状态每个序列一个定长槽位，只存约 1.4 MB，留在本机内存。
  3. 命中最多到 L − 134，按 128 取整；SWA 缺了就退一块，用有界重放只重算 128 个 token，代价是常数。开源版有引擎角色、缓存布局和有界重放，没有 KV 缓存系统和分离部署的衔接代码。

常见误解：“前缀命中只是省时间，算出来的结果和从头算一模一样。”

块 KV 是原样读回来的，这部分一样。可 SWA 状态缺了时，有界重放算出的是一份近似的 SWA：窗口被截在重放段里，看不到更早的 token（Q&A 文档）。解码器层的有界重放按 README 的默认用法开着时，每次预填充都截断，结果从一开始就和完整计算不同；examples/yoco 验证的是 mask 和 compact 两种截断彼此一致，不是和不截断一致。想要可重复的输出，看批次不变那一页。

深入一层：从环境变量到函数，一条条对上代码

引擎角色与混合引擎的投票

三种引擎角色定义在 engine_type.py：NORMAL 和 COMPLETION 默认开零开销调度，PROMPT 不开（异步调度见DSpark 与零开销调度那一页）。调度器按角色分派：PROMPT 只调 _schedule_prefill，COMPLETION 只调 _schedule_decode（scheduler.hpp）。NORMAL 的投票里，“想做预填充”的条件是显存里的 KV 用量不超过 90%，且有请求在排队（水位线、want）。ALL 点用 MIN 归约，全员想做才做；ANY 点任一 rank 想做就做。之后还有第二轮投票，确认真有 rank 排出了预填充；有的 rank 空手，就陪着跑一个空的预填充步，保持步型一致。间隔由 DEEPINFER_PREFILL_ATTEMPT_INTERVAL（默认 70）和 DEEPINFER_PREFILL_ANY_ATTEMPT_INTERVAL（默认 100）控制（environ.py）。非 NORMAL 的引擎在初始化时会调 init_pd_split（llm_engine.py）。另外，只有非 PROMPT 的引擎才用 CUDA Graph（model_runner.py）：解码步小而频繁，录图省下启动开销，这正是第 15 章「kernel 启动开销与算子融合」讲的事。

块表与状态槽

两个分配器都是 BlockManager：空闲块串成链表，块带引用计数，0 号块不用（block_manager.hpp）；块分配器按 num_gpu_blocks 管块，槽分配器按 num_state_seqs 管槽（llm_engine.py）。要的块数不少于总块数时返回 NEVER，直接报错；暂时不够返回 LATER，请求留在队里（block_manager.hpp）。try_allocate_seq 要块和槽同时够才分配（同一文件）。槽位数是 int(max_num_seqs × 1.2) + 1，比例由 DEEPINFER_NUM_STATE_SLOTS_RATIO 控制（cache_engine.py、environ.py）。启动时还检查：块能装下的 token 数乘 0.8，必须不小于模型的最大长度（llm_engine.py）。

SWA 状态的布局与存档

哪些层的 SWA 不存档，只看模型配置：层号不小于 n_prefill_layer 的是 YoCo 消费层（cache_engine.py）；n_prefill_layer 取第一个压缩比为 1 的层的序号（config.py）。开 DEEPINFER_PREFILL_STORE_EXTRA_STATE 时，存档用的环形缓冲再多存 DEEPINFER_PREFILL_STORE_EXTRA_SIZE（默认 128）个 token，截断开着时还要加 KEEP_TOKENS；注释的理由是“预填充时可能不会触发落盘，多存一段才能保证多轮命中”（cache_engine.py）。读出存档数据的是 select_state_slice_to_store：存档时要求位置是 128 的倍数；TO_CE=True 时构造发给解码引擎的完整状态，连不存档区一起（cache_engine.py）。反方向的 load_state_from_store_to_prefill_cache 把存档数据写回预填充的状态槽（同一文件）。

SWA 状态什么时候存

Q&A 文档给的规则（Q&A 文档）：上游报告预填充结束时，先在序列末尾留一个 token，再向下取整到 128 的倍数，不够一整段就这次不存；分段预填充只在最后一段存。解码时在显存里另开一个副本区，每跨过一个 128 边界就把当前窗口复制过去；请求结束时，从最近一次完整的副本存档，挂接点向下取整到 128。复制的位置最多越过边界 5 个 token，槽位比窗口多出的 6 个位置正好兜住。代码侧，复制由 do_copy_state 把 GPU 上的状态拷进 copy_state 缓冲，而“要不要复制”的判断 should_copy_state 在开源版里恒返回 False（llm_engine.py）。代码事实

有界重放的开关与检查

DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE 取 off、mask、compact，DEEPINFER_YOCO_PREFILL_KEEP_TOKENS 默认 0，开截断时必须显式设置（environ.py）。检查有两处：Python 侧在加载模型时（model_runner.py），C++ 侧在准备输入时（prepare_tensor_input_v4.cpp）。回退长度 DEEPINFER_MAX_BACKTRACKING_TOKENS 会被抬到至少“草稿数 + 1”，草稿数默认 5，所以至少 6（environ.py）。compact 模式下每个分段保留 [max(0, 总长 − KEEP_TOKENS), 总长) 与本段的交集；整段都在保留区之前时，仍留最后 1 个 token 占位（同一文件）。截断有两种模式：mask 保留全部查询，只把可见范围收窄；compact 在第一个消费层直接丢掉截断区的查询，真正省下计算（environ.py）。模型前向在第一个消费层把元数据换成 compact 视图（deepseek.py）。两种模式的可见范围是同一个公式（yoco.py）。截断开着时，提示词的逐 token 概率（prompt logprobs）被强制关掉：compact 模式下被截掉的行根本没算，mask 模式下矩形之前的行算出的概率没有意义（llm_engine.py）。调度器的代价模型也分开数消费层的行数，所以它知道截断省了多少（flops_estimator.hpp）。examples/yoco 有两级验证：L1 单卡几秒，只比元数据；L2 要 8 张卡和兼容的检查点，逐个比较 logprob 和 top-K，默认参数是 --keep-tokens 140 --window 128（examples/yoco/README.md）。

平衡 CP 的切法

README 把它写作“Attention DP / balanced CP”（README），解码引擎开 CP 会直接报错（llm_engine.py）。一条序列切成 2 × cp 段，第 r 张卡拿第 r 段和倒数第 r + 1 段，一前一后配成对（prepare_cp_mirror.py；截断时的补齐计算也按同样的配对，见 prepare_tensor_input_v4.cpp）。代码事实为什么这么配？因果注意力里越靠后的 token 要看的键越多。4 张卡顺着切，工作量约为 1 : 3 : 5 : 7，最忙那张是平均的 1.75 倍；一前一后配对后，四张卡一样多。教学推演调度时每条序列的长度对齐到 cp × 2（scheduler.hpp），每个 rank 的长度是各序列 ⌈长度 ÷ 2cp⌉ 之和再乘 2（prepare_tensor_input_base.cpp）。GPU 上的 kernel 按 blk = rank + half × (2cp − 1 − 2 × rank) 算出第 half 段对应的块号：half = 0 时是第 rank 块，half = 1 时是第 2cp − 1 − rank 块（prepare_cp_mirror.py）。工作量的推演：长度 N 切成 2cp 段，第 i 段里的 token 平均要看约 (i + 0.5) × N ÷ 2cp 个键，所以第 r 块和第 2cp − 1 − r 块加起来恒为 2cp 个单位，与 r 无关。教学推演

本页数字的条件

README 的两张测速图：预填充用 4 张 SM100，解码用 64 张，各自在一个 scale-up 域内（README）。预填充图的标题写着 EP4DP4、384 + 32 个专家、上下文 131,072、解码器有界重放 140 个 token；纵轴是每卡每秒处理的未命中 token。我按图读出的点是：每步 4,096 个 token 约 68 ms，8,192 约 114 ms，16,384 约 200 ms，32,768 约 376 ms，65,536 约 731 ms。上游报告（读图有误差）解码图的标题写着 EP64DP64、384 + 64 个专家、上下文 131,072、固定 nextn = 3、每个草稿 token 接受率 75%、τ = 3.25。每个 rank 64 个请求时，每个用户约每秒 246 个 token，所以解码一步约 3.25 ÷ 246 ≈ 13 ms。教学推演τ 的记账方式见DSpark 那一页。3.3 节的存储数字都来自 Q&A 文档，DeepSeek 没有公开 3FS 集群的实测读带宽分布。
