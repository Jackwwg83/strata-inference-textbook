从一个人到一桌人

第 18、19 章里，Strata 服务的是一个人。它的草稿层最多猜 3 个 token；要不要换成从上文里“抄”来的草稿，按一张实测的耗时表来定。

DeepInfer 的解码卡上，同一步里挤着几十个请求。DeepSeek 说生产工作点大约是每张卡 60 个。上游报告这时有两个新问题：一步里几百个草稿 token，哪些值得验？CPU 给下一步排队的那几毫秒，GPU 在干什么？

一句话：DeepInfer 的草稿模块一次前向猜 5 个 token，还给每个打一个“把握”分；打开变长验证后，调度器把验证名额先给把握最大的草稿，在一条实测的耗时曲线上找“每毫秒期望 token 最多”的总数。零开销批调度器让 CPU 提前一步排好下一批，GPU 不再停下来等。两者叠在一起时，CPU 只定总数，每个请求分几个，由 GPU 上的 kernel 现算。

4.1 草稿从哪来：一次前向猜 5 个，外加 5 个把握

先复习第 18 章「推测执行」讲的投机解码：便宜的草稿先猜几个 token，叫草稿 token；大模型把“上一个定下的 token ＋ 这几个草稿”排成一排，一次前向算完，再逐个验证，只留下连续的前缀。

DeepInfer 的草稿模块在 deepinfer/model_executor/models/mtp/dflash.py，类名叫 DFlash。README 和 DeepSeek 的部署问答把这套投机解码叫 DSpark，把调度验证的办法叫“按置信度调度验证”（confidence-scheduled verification）。上游报告（README.md）在代码里，DSpark 这个名字只出现在草稿模块的配置字段上，比如 dspark_target_layer_ids、dspark_noise_token_id、dspark_markov_rank。代码事实（dflash.py）代码和文档都没有解释这两个名字的来历，本页也不猜。

从代码看，这个草稿模块有三个特点。代码事实

  • 借主模型的特征。主模型前向时，草稿模块取主模型几层的隐藏状态，拼起来投影一次，写进自己的 KV 缓存。注释写明，这一步“在主模型前向里面跑”。（dflash.py）
  • 5 个位置一次算出。草稿的输入是一排 5 个位置：第 1 个是刚定下的 token，后 4 个都填一个固定的“噪声 token”。这一排过一遍草稿层，5 个位置的隐藏状态就同时有了。（dflash.py）之后逐个位置出 token，每个位置可以再加一个小修正项，它只看前一个 token：第 1 个位置看刚定下的 token，之后各看前一个位置刚抽出的草稿。（dflash.py）
  • 每个草稿附一个把握。置信度头（Confidence Head）是一个线性层加 sigmoid，给每个草稿估一个“会被接受的概率”。注释写着：“预测每个草稿 token 的接受概率。”（dflash.py）

猜几个由环境变量 DEEPINFER_USE_NEXTN_DECODE 决定，默认 5，设成 0 就关掉投机解码。代码事实（environ.py）问答说，生产上草稿模型也是一次出 5 个；内部版本的草稿模型新一些，但性能差别很小。上游报告（inference_deployment_qa.md）

验证用的是投机解码的经典规则：草稿按 min(1, p ÷ q) 的概率被接受，p 是主模型的概率，q 是草稿的概率；第一个被拒的位置，从两者之差的“残差分布”里补抽一个。随机数由请求的种子和位置算出。代码事实（sampler.py、fused_sample.py）种子怎样让结果可复现，见本专栏的“确定性”一页。图 D4-1 把一步解码串起来。

对照 Strata：Strata 的草稿来自模型自带的一层 MTP 层，最多猜 3 个；默认的验证规则是“草稿和目标的抽样结果完全相等才接受”，经典的 min(1, p ÷ q) 规则要另开开关（第 18 章 18.5 节）。DeepInfer 默认就用经典规则，一次猜 5 个，还多输出一列置信度。多出来的这列数，不是为了验证本身，是为了调度：一步里有几十个请求，得有个依据决定先验谁。

4.2 验几个最划算：把名额先给把握最大的草稿

最省事的做法是每个请求都把 5 个草稿全验。问答说，这样会把验证算力浪费在希望渺茫的草稿上，因为不同请求、不同位置的接受概率差得很多。上游报告（inference_deployment_qa.md）

账怎么算，第 19 章「期望值与几何级数」已经讲过：第 i 个草稿派上用场，要求前 i 个全被接受，概率是各位置条件接受率的连乘；一轮期望提交 1 ＋ c₁ ＋ c₂ ＋ … 个 token，该比的是“期望 token ÷ 一轮的时间”。DeepInfer 的代码把置信度头的输出当作每个位置的条件接受率，调度前先连乘。源码注释说：“modeling 返回的 confidence rate 是每个 token 独立的，使用前要做一个累乘。”代码事实（scheduler.hpp）

不同的是，一步里有很多请求，它们共用同一次前向。这一步的耗时，取决于整批一共验多少个 token。所以 DeepInfer 不再一个请求一个请求地挑，而是把整批当成一个预算问题来解。打开 DEEPINFER_ENABLE_MTP_VARLEN=1 后，MTPVarlen::schedule 这样做：代码事实（mtp_varlen.hpp）

  1. 把所有请求的所有草稿，按连乘后的概率从高到低排成一列。
  2. 从“每个请求只验主模型那 1 个 token”开始，按这一列逐个加名额。每加一个，期望 token 数加上它的概率。
  3. 每个总数 q 都查一次耗时：在启动时测好的耗时曲线上，取不小于 q 的那张 CUDA Graph 的耗时，再加上在线修正的斜率项和采样时间。
  4. 挑“期望 token ÷ 耗时”最大的那个 q，把前 q − N 个名额分给对应的请求，N 是请求数。这里其实排了两列：总数用再早一轮的置信度，分名额用最新一轮；不开 ZOS 也是这样。（mtp_varlen.hpp）

连乘的概率越往后越小，所以每个请求分到的名额，总是它前面连续的几个草稿。这和“只接受连续前缀”的规则对得上。问答的说法是：按期望接受率排序，选出让有效吞吐（每秒产出的 token 数）最大的那个前缀子集。上游报告

耗时曲线是实测的。引擎预热时，把每一张录好的 CUDA Graph 重放 5 次，去掉最快和最慢的一次取平均，再在专家并行（EP）的那组卡之间取平均。代码事实（model_runner.py）运行时，每个解码步实测的前向和采样耗时会喂回调度器，用滑动窗口的中位数修正这条曲线。（llm_engine.py、mtp_varlen.hpp）

这个开关默认是关的。代码事实（environ.py）只有开关打开、而且用上了 CUDA Graph 时，引擎才去测这条曲线；曲线为空时，每个请求固定验 1 ＋ 它手上的草稿数（通常是 5）个 token。（base.py、mtp_varlen.hpp）仓库里的评测脚本会把它设成 1。（run_eval.py）README 还写明，要做确定性采样，得把它关掉，原因见“确定性”一页。

贪心算法与边际收益

直觉：你有 10 张电影票要分给朋友，每个人去的可能性不同。想让到场的人最多，就把票先给最可能去的人，一张一张往下发。每一步都拿眼下收益最大的那一份，这就是贪心算法。

定义：贪心算法每一步做局部最好的选择，不回头。它不总是对的，但在“总收益是各份收益之和、各份互不影响”的问题里，它给出的就是最优解：任何一种别的分法，都能把一张票从收益低的人换给收益高的人，结果只会更好。这种证明方法叫“交换论证”。

一个例子：4 个草稿派上用场的概率是 0.9、0.7、0.4、0.1，只能验 2 个。贪心选 0.9 和 0.7，期望多拿 1.6 个 token；换成任何别的两个，都更少。

和本页的关系：名额数固定时，DeepInfer 按概率从高到低发名额，就是这个贪心。名额数本身不固定，于是调度器把每个总数都试一遍，比“期望 token ÷ 耗时”，取最大的那个。每多发一个名额，期望多出的那一点，就是它的边际收益。

延伸阅读：OI Wiki：贪心 · 维基百科：贪心算法 · Wikipedia: Greedy algorithm

第 3 步藏着一个台阶。耗时按“不小于 q 的那张图”查，图的大小是 1、2、4、8、16、24……每隔 8 一张。代码事实（mtp_varlen.hpp、cuda_graph_runner.py）所以同一张图里，多验几个、少验几个，估出的耗时完全一样。砍草稿只有在总数跌过一张图的边界时才省时间；期望 token 又随 q 只增不减，选出的总数总是落在某张图的大小上，或者干脆验全部草稿。教学推演

下面的模拟器把这个预算问题摊开。格子里的数就是连乘后的概率。耗时也按图的大小走台阶，但每级台阶的高度用一条直线代替真实曲线；总数和分名额只用一份置信度。这两点是教学简化。

算式是 吞吐 ＝ (N ＋ Σ 被验草稿的连乘概率) ÷ (10 ＋ t₁ × 图大小)，图大小是装得下这些 token 的最小那张 CUDA Graph。图 D4-2 里，固定做法是 10.71 ÷ 14.80 ≈ 0.724，按置信度是 9.84 ÷ 13.20 ≈ 0.745。教学推演

对照 Strata：Strata 的 MTP 窗口长度由启动参数 --spec 固定；只有设了 --spec-min-p，草稿的把握低于门槛时才不再往窗口里加。按实测耗时比“每毫秒期望提交几个 token”的 DraftPolicy，管的是提示词查找草稿（第 19 章 19.5 节）。这些都是为一个用户的一个窗口做决定。DeepInfer 要决定的是一整批几十个请求一共验几个、谁多谁少，门槛也不是固定的，而是由“多验一个值不值”当场算出来；比较的单位从“一个窗口”变成了“一张 CUDA Graph 的一次重放”。

4.3 上游的账：少验三成，吞吐多几个百分点

问答给了一张表，对比固定验 5 个和按置信度变长验证。条件是 EP64/DP64，也就是 64 张卡做专家并行，注意力按数据并行（DP）分成 64 份；表里的吞吐是用这套配置的基准数据推算的估计值，不是线上实测。上游报告（inference_deployment_qa.md）为什么要铺满 64 张卡，见“宽专家并行”一页。

问答的总结是：验证的草稿少了约 30%（5.00 降到 3.2–4.4），平均接受长度基本不变（3.29 对 3.20），在每卡约 60 条的生产工作点，吞吐多 4%–7%。上游报告 问答没写明“接受长度”里含不含主模型自己的那 1 个 token，本页不替它解释。

为什么并发低时不赚？一个合理的解释是：批小的时候，解码卡在搬权重上，多验几个 token 几乎不加时间，砍掉草稿省不下什么，却会丢掉一点接受长度（16 条时从 3.32 降到 3.24）。批大了，前向开始受算力限制，每个多验的 token 都实打实地花时间，砍掉低概率草稿才划算。教学推演 “卡在搬运还是卡在计算”的判断方法，见第 5 章「roofline」。上面的模拟器里，把 N 和 t₁ 一起调大，能看到同样的方向。

模拟器和真实系统还差一件事：模拟器里的置信度就是真实概率，按它分名额永远不亏。真实系统里，表里 16 条/卡那一行是 −1.5%。可能的原因之一是置信度估错，砍掉了本来能被接受的草稿；另外几种也说得通：耗时模型有误差，定总数用的是更早一轮的置信度，总数还要向上补到一张图的大小。教学推演 何况这张表本身也是用基准数据推算的估计。（inference_deployment_qa.md）

4.4 让 GPU 一刻不停：零开销批调度器

换一个角度看一步解码。问答把第 N 步拆成四段：schedule(N) → forward(N) → sample(N) → post-process(N)。调度和后处理都是纯 CPU 逻辑；后处理之前，CPU 要和 GPU 同步一次，才拿得到 sample(N) 的结果。于是在 post-process(N) 和 schedule(N+1) 这两段，GPU 闲着。上游报告（inference_deployment_qa.md）

异步调度要消灭的就是这段空闲。DeepInfer 把它的实现叫零开销批调度器（zero-overhead batch scheduler，代码里简称 ZOS）。问答说，它参照了 SGLang 和 NanoFlow 的做法：GPU 在跑 forward(N) → sample(N) 时，CPU 同时做 schedule(N+1) → 发射 forward(N+1) → post-process(N−1) → 发射 sample(N+1)。上游报告

代码里，这个顺序写在 Worker.execute_model_step 的注释里，每一步都走同样四件事：代码事实（worker.py）

  1. 发射本步的前向；
  2. 后处理上一步：先等上一步“采样完成”的事件，再处理输出；
  3. 发射本步的采样；
  4. 本步的后处理：预填充步和关掉 ZOS 时当场做；ZOS 下的解码步留到下一步，和下一步的前向重叠。

“上一步”只存在一个变量 prev_step_state 里，所以 CPU 最多领先 GPU 一步。第 2 件事里的等待，排在本步前向已经发射之后，所以 CPU 等的时候，GPU 手上有活。代码事实（worker.py）

README 说异步调度默认打开。上游报告（README.md）光看 environ.py，DEEPINFER_ZERO_OVERHEAD_SCHEDULING 的默认值是关；但创建引擎时，EngineArgs 会按引擎类型补一个默认值：既做预填充又做解码的 NORMAL 引擎、只做解码的 COMPLETION 引擎设成 1，只做预填充的 PROMPT 引擎设成 0。代码事实（environ.py、arg_utils.py、engine_type.py）所以凡是要解码的引擎，它确实默认开着，和 README 一致。

重叠很容易被一次意外的同步毁掉：只要发射代码里有一处要读 GPU 上的数，CPU 就得停下来等，GPU 的活一干完就又空了。DeepInfer 给前向和采样的发射各包了一层 forbid_cuda_sync()，函数注释用大写写着“这里不能有任何 CUDA 同步”，还有专门的单元测试。代码事实（model_runner.py、test_cuda_sync_guards.py）

拖一拖下面的时间线，看空档什么时候消失、什么时候回来。

稳态下，同步循环每步要 CPU ＋ GPU，异步循环只要 max(CPU, GPU)。默认参数下是 (4 ＋ 13) ÷ 13 ≈ 1.31 倍。教学推演 GPU 的 13 ms 是从 README 解码图读出来的：每卡 64 个请求时，每用户约 246 token/s，按图注的 τ ＝ 3.25 折算，每秒约 76 步，一步约 13 ms（4.6 节细讲这张图）。上游没有公布 CPU 每步花多久，4 ms 纯属假设。教学推演

异步不是白来的。CPU 排第 N+1 步时，还不知道第 N 步每个请求接受了几个 token，所以它先按最坏情况给每个在途请求预留 1 ＋ 5 个位置，等结果回来再改回实际值；位置表的上限也因此多留了 nextn ＋ 1 格。代码事实（预留：scheduler.hpp L726；先乐观推进：L927；再按实际接受数回填：L999；config.py）一个请求如果在途时被抢占，它那一步的输出整个作废。（scheduler.hpp）

学过计算机的同学：这就是一条两级的软件流水线：CPU 是第一级，GPU 是第二级，每级一次处理一步。和《计算机组成原理》里的指令流水线一样，流水线的节拍由最慢的那一级决定，所以 CPU 一旦比 GPU 慢，空档就会回来。流水线的基础见第 16 章「流水线」。

对照 Strata：Strata 的服务端默认是一把锁、一条队，一次只服务一条序列；打开 "parallel" 后，通常最多 8 个批槽位一起解码（第 25 章 25.1 节）。它也有重叠：验证窗口的提交可以不等图跑完就返回，让下一轮的草稿生成同时进行（第 14 章「同步与异步」）。DeepInfer 的解码卡上一步有几十个请求，CPU 每步要为整批做调度和后处理，这份活随批变大，不藏起来就直接吃掉 GPU 的时间。

4.5 两件事撞在一起：CPU 还不知道上一步接受了几个

把 4.2 和 4.4 放在一起，就撞上了一个难题。变长验证要按第 N 步刚出的置信度，决定第 N+1 步每个请求验几个；可是异步调度下，CPU 排第 N+1 步时，第 N 步还在 GPU 上跑，置信度还没出来。

问答给的解法是：CPU 调度时只定总预算；每个请求分几个，由 GPU 上的一个 TileLang kernel 重新算（连乘、全局排名取前 k、顺手把行号重映射），结果再写回一块锁页缓冲区。上游报告（inference_deployment_qa.md）代码和这段描述一一对得上：代码事实（worker.py）

  • CPU 先把本批请求和上一批对上号，做出一张重映射表 remap：本批第 i 个请求，是上一批的第几个；新来的记 −1。（zos.cpp）
  • GPU 上的 compute_seqlens_q_by_confidence_rates 读上一步留在显存（HBM）里的置信度，按 remap 取行、连乘，再在全批里排名，前 total_q − N 名各给对应请求加一个名额。新来的请求置信度记 0，排在最后。（schedule_mtp_varlen.py）
  • 每个请求的 KV 长度，也在 GPU 上按上一步实际接受的 token 数改好（worker.py 的 compute_seqlens_k_zos）；这一步的输入 token，直接从显存里上一步的采样结果里取。（prepare_tensor_input_zos.py）
  • 算好的每个请求长度拷回锁页内存，记一个事件。CPU 发射完前向、做完上一步的后处理，在发射采样前才等这个事件。（worker.py）

为什么总数非得在 CPU 上定？代码里至少有一个直接原因：CPU 要拿总 token 数去挑重放哪一张 CUDA Graph，这一步发生在发射之前。代码事实（worker.py、cuda_graph_runner.py）每张图的大小在录制时就定死了。而在 ZOS 下，图的输入缓冲直接放在显存里，GPU 上的 kernel 可以改写它，不用经过 CPU。（cuda_graph_runner.py、model_runner.py）

4.2 节说过，总数和分名额本来就用两份数据：总数用再早一轮的置信度，分名额用最新一轮，开不开 ZOS 都这样。源码注释写的是：总预算“永远用 N−2 轮的 accept_rate”，分配用 N−1 轮的；注释里的“第 N 轮”指正在排的那一步。代码事实（mtp_varlen.hpp）换成本节的记号：排第 N+1 步时，总数用第 N−1 步产出的置信度，分名额用第 N 步的。不开 ZOS 时，第 N 步已经后处理完，分名额在 CPU 上就能做；开了 ZOS，第 N 步的置信度还在 GPU 上，分名额就挪到 GPU 上做。

学过计算机的同学：这是流水线里的数据冒险：后一条指令要用前一条的结果，可前一条还没算完。CPU 的老办法有两个：停下来等（流水线停顿），或者把结果从执行单元直接“转发”给下一条指令，不绕回寄存器。DeepInfer 选的是转发：第 N 步的接受数和置信度不回 CPU，直接在显存里交给第 N+1 步。延伸阅读：维基百科：冒险（计算机系统结构） · Wikipedia: Operand forwarding

对照 Strata：第 15 章 15.5 节讲过，CUDA Graph 会把参数录死，所以 Strata 把每步都变的位置放进一块固定地址的显存，由主机每步拷一次新值进去。DeepInfer 在 ZOS 下又往前走了一步：每步变的长度和输入 token，连主机都不经手，直接由 GPU 用上一步的结果算出来。原则相同：图记住的是地址，内容每步重写。

4.6 读基准数字要小心：满接受口径

最后说一个读数时容易踩的坑。仓库自带的 benchmark.py 报的解码吞吐，是“满接受口径”：不管草稿实际被接受了多少，每个请求每步都按 1 ＋ nextn 个 token 记。算式是 avg_SPS × 请求数 × (1 ＋ nextn) ÷ CP 数，avg_SPS 是每秒走的步数。默认 64 个请求、nextn ＝ 5 时，一步记 384 个 token。上游报告（examples/README.md）代码里这条算式一模一样。代码事实（benchmark.py）

这样记有它的道理：关掉变长验证时，每步固定验 1 ＋ nextn 个 token，一步的耗时和接受率无关，测出的步速可以按任意接受率再折算。画图脚本就这么做：用 τ ＝ 1 ＋ nextn × a 把两条轴同乘 τ，a 是草稿被接受的比例；脚本还断言数据里没开变长验证，因为那时步速已经含了接受率，不能再乘。代码事实（plot_pareto.py）

README 里那张解码图，图注写着：EP64DP64，384＋64 个专家，上下文 131,072，nextn ＝ 3 固定，逐 token 接受率 75%，τ ＝ 3.25；测量用 64 张 SM100 卡，在同一个超节点内。上游报告（README.md、decode_pareto.png）读图：每卡 64 个请求时，约 15,700 token/s/卡，每用户约 246 token/s。上游报告（读图约数）要记住，这里的 75% 是画图时给定的输入，不是这次测出来的接受率。它也不是 4.2 节那种逐位置的条件接受率：画图脚本里的 a 是“被接受的草稿占全部草稿的比例”，τ ＝ 1 ＋ 3 × 0.75。代码事实（plot_pareto.py）如果每个位置的条件接受率都是 75%，按连乘算，一步期望只有 1 ＋ 0.75 ＋ 0.56 ＋ 0.42 ≈ 2.73 个。教学推演

折算一下：nextn ＝ 3 时，满接受口径比 a ＝ 75% 的口径多算 4 ÷ 3.25 − 1 ≈ 23%；nextn ＝ 5 时多算 6 ÷ 4.75 − 1 ≈ 26%。教学推演 4.3 节的基准估算里，固定验 5 个时平均接受长度约 3.3；无论它含不含主模型那 1 个 token，都远低于满接受口径的 6（只数草稿则是 5）。所以满接受口径的数，只能当上限看。

记住这三点

  1. DeepInfer 的草稿模块一次前向猜 5 个 token，还给每个打一个置信度。打开 DEEPINFER_ENABLE_MTP_VARLEN=1 后，调度器按连乘后的置信度从高到低发验证名额，在实测的耗时曲线上挑“每毫秒期望 token 最多”的总数。上游估算：生产工作点吞吐多 4%–7%，低并发时反而略亏。
  2. 零开销批调度器让 CPU 领先 GPU 一步：GPU 跑第 N 步时，CPU 已经在排第 N+1 步。稳态周期从 CPU ＋ GPU 变成 max(CPU, GPU)，前提是 CPU 每步的活不超过 GPU 一步。
  3. 两者叠加时，CPU 拿不到最新的置信度，于是只定总数（它要靠总数选 CUDA Graph），每个请求分几个由 GPU 上的 kernel 用最新置信度现算。读解码吞吐时，先看它是不是满接受口径。

常见误解：“零开销调度，就是 CPU 调度不花时间。”

CPU 的活一点没少，只是和 GPU 的活叠在了一起。CPU 每步比 GPU 慢时，异步循环的周期就是 CPU 的时间，GPU 照样空等，上面的时间线里把 CPU 拉过 GPU 就能看到。教学推演 DeepInfer 的调度器本体在 C++ 里（csrc/engine/scheduler.hpp），发射代码外面还套着禁止同步的守卫。代码事实

深入一层：一个解码步的完整调用链、预算算法的细节与相关开关

文件地图

  • csrc/engine/scheduler.hpp：C++ 调度器。解码调度在 L622–L660，最后调用 _mtp_varlen.schedule；草稿和置信度的记账在 process_MTPInfo（L1196–L1262）。
  • csrc/engine/mtp_varlen.hpp：变长验证的预算算法和两个估时器。
  • deepinfer/worker/worker.py：ZOS 的四步循环和 GPU 端修正。
  • csrc/engine/zos.cpp、deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py：ZOS 下的输入准备。
  • deepinfer/model_executor/layers/tilelang_ops/cuda/schedule_mtp_varlen.py：GPU 上分名额的 kernel；同名的上一级文件里有 PyTorch 参考实现和测试。
  • deepinfer/model_executor/models/mtp/dflash.py：草稿模块和置信度头。
  • csrc/graph_timer/、deepinfer/timer.py：CUDA Graph 内部的计时。

ZOS 打开时，一个解码步的顺序

  1. scheduler.schedule()：C++ 选出本批请求，按长度排序，MTPVarlen::schedule 给出每个请求的 seqlen_q 和总数；每个被调度的请求 schedule_cnt 加 1，并按 1 ＋ nextn 预留在途位置（scheduler.hpp L667–L736）。
  2. Worker._correct_seqlens_qk：和上一批对号，生成 remap；拷到显存；开变长时跑分名额 kernel；按上一步的接受数改 KV 长度；开变长时把新的 seqlen_q 拷回锁页内存并记事件（worker.py L191–L245）。注释写着：“H2D、修正、D2H 在当前流上有序；只有变长会改写这块锁页源。”
  3. execute_main_model：选图、发射前向，外面包着 forbid_cuda_sync() 和计时事件 device_forward。
  4. _post_process_step(prev)：等上一步的 sample_end_evt，刷新图内计时，处理输出；驱动进程里还会把上一步实测的前向和采样耗时交给 scheduler.update_mtp_runtime（llm_engine.py L984–L1015）。
  5. 等 D2H 事件，update_metadata_for_sampling_zos 把 CPU 侧的 seqlen_q 改成 GPU 算出的值；seqlen_k 不从 GPU 拷回，在 CPU 上按 seqlen_q ＋ 已缓存的 token 数重算（zos.cpp L279–L305）。
  6. execute_sample：验证上一步的草稿，再跑草稿模块出下一步的草稿和置信度；同样包着禁止同步的守卫。
  7. pre_sampler_sync 回调：释放上一轮延后释放的资源，处理 KV 落盘等。最后把本步状态存进 prev_step_state，留给下一步后处理。

预算算法的细节

  • 每个请求有两份接受率：accept_rates（最近一轮，已连乘）和 prev_accept_rates（再上一轮）。用 schedule_cnt 和 process_cnt 两个计数器判断“最近一轮”到底是 N−1 还是 N−2（sequence.hpp L118–L131）。
  • 还没有接受率时，有草稿的按 1.0 补，没草稿的按 0.0 补。
  • 排序按接受率降序，相同时请求下标小的在前；GPU kernel 用“有多少个元素比我大”的计数来排名，相同时扁平下标小的在前。这个 kernel 是并行计数，不是真的跑一次排序。
  • 候选总数从“只验主模型 token”开始；每个候选的耗时是：曲线上不小于它的那张图的基线耗时 ＋ 斜率 × 图大小 ＋ 采样耗时。比较用严格大于，所以吞吐相同时取较小的总数。同一张图里估出的耗时相同，所以选中的总数总是一张图的大小，或者全部草稿。
  • CUDA Graph 的大小按 token 数算：1、2、4，之后每隔 DEEPINFER_CUDAGRAPH_BATCH_SIZE_INTERVAL（默认 8）一张，最大是 max_num_seqs × (1 ＋ nextn)（cuda_graph_runner.py L41–L51、model_runner.py L72–L79）。

估时模型的在线修正

  • 启动曲线：每张图预热 1 次、计时 5 次，去掉最高最低各 1 次取平均，再在专家并行组内取平均；结果按模型和并行配置缓存到文件，有效期由 DEEPINFER_DECODE_PERF_CACHE_TTL_SEC 控制，默认 3600 秒。
  • 前向斜率：注释说启动曲线没考虑上下文长度，所以用 (实测前向 − 基线) ÷ 图大小 拟合一个斜率。保留最近 5000 步，每种图大小至少 10 个样本才算数，先按图大小取中位数，再对这些中位数取中位数；斜率小于 0 时按 0 算（mtp_varlen.hpp L44–L131）。
  • 采样耗时：没有启动曲线，按请求数分组，取最近 9 步的中位数，不足 5 个样本时退回全局的中位数。

置信度头

公式是 sigmoid(拼接[隐藏状态, 修正项嵌入] · w ÷ 温度)（tilelang_ops/dflash.py L10–L46）。温度来自 DEEPINFER_DFLASH_CONFIDENCE_HEAD_TEMPERATURE，默认 1.0，也可以按位置给 nextn 个值，用逗号分开（environ.py L134–L143）。注释说 Hugging Face 格式的 DFlash 固定带置信度头。草稿模块有几层，由模型配置里的 num_nextn_predict_layers 决定，本页没有核实这个值。

CUDA Graph 里怎么计时：graph_timer

变长验证的耗时反馈，用的是包在整次前向、整次采样外面的 CUDA 事件。另有一个 graph_timer，专门量图内部某几段（比如某一层的注意力、MLP）的耗时，供统计用。它在录图时插入“记录事件”的节点，录好后找出这些节点（graph_timer_cuda.cpp L48–L85）。每次重放前，它把这些节点换成另一组事件，两组轮流用（timer.py L78–L217）。ZOS 下，读上一步的计时时下一步的图已经在跑，两组事件轮流，读的就永远是跑完的那组，正在跑的那组不受影响。这就是第 14 章 14.4 节的双缓冲。
