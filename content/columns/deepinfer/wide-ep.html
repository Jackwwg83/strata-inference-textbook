从一台电脑到一个超节点

第 10 章算过一笔账：Strata 在一台电脑上生成一个 token，要读约 664 MB 的专家数据。显存装不下全部专家，就只缓存热门的那些，剩下的交给 CPU。那是“一个人、一台机器”的做法。

DeepSeek 的线上服务面对的是成千上万个同时在聊的人。它的解码不放在一张卡上，而是放在 64 到 128 张卡组成的超节点里：这些卡之间有高速互连，可以当成一个整体来用。上游报告（Q&A 第 11 行）这一页回答三个问题：几百个专家怎样摊到几十张卡上？为什么卡越多，解码反而越划算？热门专家扎堆在一张卡上时怎么办？

一句话：DeepInfer 解码时，注意力按数据并行（DP），每张卡管自己的一批请求；路由专家按专家并行（EP），摊到 64–128 张卡上，每张卡每层只放几个。卡越多，每张卡每步要读的专家权重越少，读一次服务的 token 越多。代价是每层两次全对全通信（all-to-all），而且最忙的那张卡决定整组的速度，所以要用专家负载均衡（EPLB）把热门专家复制、摊开。

2.1 两种切法叠在一起：注意力按请求切，专家按编号切

第 21 章讲过三种多卡分工：层切分、张量并行、请求并行，Strata 选了层切分。DeepInfer 只用了其中的数据并行（只用于注意力），再叠上第 21 章没讲的一种：专家并行。见图 D2-1。

  • 注意力用数据并行（DP）。每张卡有一份完整的注意力，各自处理不同的请求。上游说：和 DeepSeek-V3 / R1 一样，注意力的数据并行份数等于专家并行份数（#DP = #EP），目前不用张量并行（TP），也不用上下文并行（CP）。上游报告（Q&A 第 33–53 行）代码里有上下文并行，README 也列出了它，只是上游的部署配置不用。
  • MoE 用专家并行（EP）。每一层的路由专家按编号切成 EP 份，每张卡只放其中一份。路由器和共享专家每张卡各有一份完整的。代码事实（moe.py 第 24–67 行、第 77–110 行）

专家的个数要能被卡数整除。DeepInfer 区分三个数：模型定义的逻辑专家，路由器从中挑选；实际分配了权重的物理专家 = 逻辑专家 + 冗余副本；每张卡上的本地专家 = 物理专家 ÷ EP。代码要求物理专家数能被 EP 整除，否则直接报错。代码事实（moe.py 第 91–95 行）冗余副本是 2.4 节的主角。

因为每层 MoE 都要跨卡交换 token，一组卡里有人做预填充、有人做解码是不行的。在同时做预填充和解码的引擎里，调度器每到一个检查点就让全组投票，统一这一步的类型；组里有卡做预填充时，没活的卡也要陪着跑一个空的预填充步。代码事实（scheduler.hpp 第 295–340 行：“dp 内必须同型，靠投票统一”）

上游的部署里，两个阶段的宽度差得很远：预填充用 EP2–8，在显存（HBM）装得下的前提下越小越好；解码用 EP64–128，在卡够用的前提下越大越好，上游把它叫作宽专家并行（Wide-EP）。上游报告（Q&A 第 45–53 行）为什么两个阶段要分开部署，见第 3 页「三段分离与 72 小时 KV 缓存」。下一节解释解码为什么要铺宽。

学过计算机的同学：这就是并行计算里的“整体同步”模式：各自算一段，全体交换一次数据，再一起进入下一段。它好写、好推理，代价是每一段都要等最慢的那个人。

对照 Strata：Strata 有两张卡时按层切成前后两段（第 21 章），卡之间只在交界处传一次数据，因为家用电脑的卡之间通常只有 PCIe。DeepInfer 在超节点里有高速互连，才敢每层都让所有卡互相交换数据。互连的代价决定了切法。

2.2 卡越多越划算：每张卡每步要读的专家变少了

先回忆第 5 章的 roofline：解码时每一步都要把用到的权重读一遍，读权重的时间往往比计算还长。一份权重读一次，服务的 token 越多，越划算。

现在站在一张卡上看一个 MoE 层的一步解码。批次够大时，本卡负责的每个专家几乎都会被至少一个 token 选中，所以本卡要把自己的专家全读一遍。本卡放几个专家，就读几个专家的权重。教学推演

DeepSeek-V4.1-Flash 每层有多少个路由专家？DeepInfer 从 Hugging Face 上的模型 config.json 读这个数，仓库里没有这个文件，也没有写死这个数。代码事实（config.py 第 164–174 行）仓库里的对比图写着“384+64 experts”，Q&A 也说 EP64 时取整后每卡 7 个专家。上游报告（wide_ep_decode_pareto.png、Q&A 第 103 行）这两处对得上：384 ÷ 64 = 6，再加 1 个冗余，正好 7。本页就按 384 算。每个专家占多少字节、每个 token 选几个专家，仓库里查不到，本页不写具体数，只用 S 和 k 表示。

于是有一个很简单的式子：每卡每层专家数 = (384 + 冗余数) ÷ EP，每卡每步要读的专家权重 ≈ 这个数 × S。教学推演 按“每卡至少 1 个冗余”取整，EP8 是 49 个，EP64 是 7 个，EP128 是 4 个。从 EP8 到 EP64，每张卡每步读的专家权重降到约 1/7。

下面的推演器把三件事放在一起：每卡放几个专家，一份专家权重读一次平均服务多少 token，每卡每步要发出多少个隐藏向量。点 EP8、EP64、EP128，看哪个数在变、哪个几乎不动。每卡每步的 token 数 T 默认取 384：示例 benchmark 默认每卡 64 个请求，每个请求每步按 1 + 5 个 token 计。上游报告（examples/README 第 45 行）

省下来的不只是读的字节。批次固定为每卡 T 个 token 时，全组一步一共有 EP × T 个 token、EP × T × k 次专家选择。负载均匀时，每张卡分到 T × k 次，摊到本卡的专家上，每份权重服务 T × k ÷ 每卡专家数 个 token。教学推演 EP64 是 EP8 的 7 倍。这正是第 5 章说的“一桌人吃饭”：同一盘菜，吃的人越多越划算。

上游的实测图支持这个方向。上游报告 条件：DeepSeek-V4.1-Flash，上下文 131,072，草稿长度固定为 3，按每个草稿 token 75% 的接受率折算（图上写 τ = 3.25）；EP64DP64 用 384+64 个专家，EP8DP8 用 384+32 个；这张图没写卡的型号，README 给它的性能图写的条件是 SM100，每组卡都在一个 scale-up 域内（README 第 83 行）。每个 DP rank 跑 64 个请求时，从图上读：EP64 约每卡每秒 1.57 万个 token、每个用户每秒约 246 个；EP8 约 1.27 万、约 198 个。也就是吞吐和单用户速度同时更好。（Q&A 第 55–59 行）

读这张图要注意一点：仓库的 benchmark 脚本无条件设置 DEEPINFER_FORCE_LOAD_BALANCE=1，把每个 token 的路由分数换成随机数，专家负载天然均匀。代码事实（benchmark.py 第 158–168 行、input_metadata.py 第 48–50 行）所以这是“负载完全均衡”时的上限。上游说，线上的负载均衡大约能做到这个离线上限的 80%。上游报告（Q&A 第 125–127 行）

对照 Strata：Strata 一次只服务很少几段对话，一个 token 要读约 480 个专家（第 10 章）。它也按专家分组，可一份权重只能在一个验证窗口的几个 token 之间共享（第 16 章）。所以它的重点是让热门专家住进显存，少走慢路（第 12 章）。DeepInfer 反过来：让一张卡只管几个专家，再把成百上千个 token 攒成一批，让每份权重读一次就用满。

2.3 每层两次全对全：分发与合并

专家分散在不同的卡上，token 就得去找专家。每个 MoE 层，DeepInfer 做四件事：代码事实（mlp.py 第 565–616 行）

  1. 路由。本卡的路由器给本卡的每个 token 挑专家。路由器拿到一张“逻辑专家 → 物理副本”的映射表，选中的是逻辑专家，发往哪个副本由这张表决定。（第 359–401 行）在几个副本之间怎么选，写在内核库里，本书没有核实。
  2. 分发（dispatch）。每个 token 的隐藏向量发往它选中的专家所在的卡。这一步由 DeepEP 的 EPBuffer.dispatch 完成。它顺便给本卡每个专家累加“这一步收到多少 token”，这就是 2.4 节 EPLB 的原始数据。（第 461–490 行）
  3. 专家计算。本卡把收到的 token 按专家分组，做分组矩阵乘（第 16 章讲过“按专家分组”）。路由权重在这一步就乘进去了。（第 406–459 行）接着，本卡用共享专家算一遍本卡自己的 token。
  4. 合并（combine）。专家的结果送回 token 原来所在的卡，加在一起，再加上共享专家的结果。（第 493–511 行）

分发和合并都是全对全通信（all-to-all）：每张卡都要给其他每张卡发一份不同的数据。

集合通信：all-to-all

直觉：一个办公室有 4 个人，每人手里有一摞信，收件人是另外几个人。all-to-all 就是“所有人同时把信投到所有人的信箱里”，结束时每人手里只剩写给自己的信。

定义：一组 P 个进程，每个进程准备 P 份数据，第 j 份发给进程 j。它是集合通信的一种。别的常见操作还有广播（一人发给所有人）、all-reduce（所有人的数据加起来，人人拿到总和）、all-gather（每人一份，最后人人拿到全部）。

例子：4 张卡、每卡 8 个 token、每个 token 选 2 个专家，并且专家均匀分布。每张卡要发出 16 份向量，其中约 12 份发往别的卡（3/4）。卡数变成 64，发往别的卡的比例变成 63/64，总份数不变。所以变宽之后，每张卡的通信量几乎不涨，涨的是参与的卡数和“等最慢那张卡”的风险。

和 DeepInfer 的关系：每个 MoE 层一次分发、一次合并，各是一次 all-to-all。DeepInfer 统计负载时还用到了 all-reduce 和 all-gather（2.4 节）。

延伸阅读：维基百科：All-to-all (parallel pattern) · 维基百科：Collective operation · NCCL 文档：集合通信操作 · PyTorch 文档：torch.distributed

当整个 EP 组都在同一个高速互连域里时（NVIDIA 卡上就是同一个 NVLink 域），DeepInfer 走另一条路：Mega MoE。代码事实 这条路在 Python 侧只有一次调用：把路由结果、两组专家权重和一块对称显存交给 DeepGEMM 的 fp8_fp4_mega_moe（激活是 BF16 时换成 bf16_mega_moe，mlp.py 第 254–256 行），拿回这一层的输出，中间没有单独的分发、合并调用；共享专家也一起交进去。（mlp.py 第 184–188 行、第 528–563 行）上游说，在一个 scale-up 域里，不管 EP 多宽、批多大，Mega MoE 都明显快于不融合的做法。上游报告（Q&A 第 229–231 行）这个内核内部怎么把通信和计算叠在一起，DeepGEMM 的代码不在这次的仓库里，本书没有核实。

2.4 热门专家扎堆：EPLB 复制热门、重新摆放

全组每一步一起走，所以一步的耗时由最忙的那张卡决定。如果几个热门专家恰好都放在同一张卡上，这张卡要算的 token 是别人的好几倍，其他卡只能等。DeepInfer 用一个数衡量这件事：moe_lb = 最忙那张卡收到的 token ÷ 平均每卡收到的 token。代码事实（eplb/__init__.py 第 167–193 行、stats_logger.py 第 238–241 行）1.0 是完全均衡。

办法是专家负载均衡（EPLB）。物理槽位比逻辑专家多出几个，多出来的叫冗余专家，用来放热门专家的副本。上游的说法是：每张卡除了自己负责的专家，再放几个冗余专家。上游报告（Q&A 第 97 行）一个热门专家有了 3 份副本，它的 token 最多能分给 3 张卡；摆放时两份副本也可能落在同一张卡上。EPLB 的运行过程是这样的：代码事实（eplb/__init__.py 第 131–165 行、第 222–278 行）

  1. 统计。每一步，分发时给本卡每个专家累加收到的 token 数，存进一个滑动窗口。
  2. 定期重排。每隔 M 步，全组把窗口里的计数 all-reduce 加起来，交给重排策略。第一次重排提前到 M/4 步，尽早纠正冷启动时的不均。
  3. 复制热门。策略一轮给一个副本：每轮都给“多一份副本后，最大的单份负载下降最多”的那个专家。（policy.py 第 105–123 行）
  4. 重新摆放。所有副本按负载从大到小排队，逐个放到“放下之后，各步里最忙的卡加起来最不忙”的那张卡上，每张卡放满为止。（policy.py 第 12–70 行）这是贪心算法：每次只做眼下最好的选择，不保证全局最优，但快。
  5. 搬权重。按新旧映射在卡之间搬专家权重：GPU 并且在同一个 NVLink 域内，直接读对端卡上的镜像；否则用 torch.distributed 的点对点收发（NVIDIA 上是 NCCL，昇腾上不走镜像这条路）。（eplb/__init__.py 第 195–202 行）搬完再换映射表。（shuffle.py 第 1–6 行）

注意第 3、4 步的一个假设：一个专家有几份副本，它的负载就平均分成几份。代码事实（policy.py 第 31–37 行）下面的模拟器按同样的算法移植，规模缩小到 16 个专家、4 张卡。

代码里 EPLB 默认是关着的：重排间隔 DEEPINFER_EXPERT_REARRANGEMENT_STEP_INTERVAL 默认 0，表示不重排；冗余下限 DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS 默认 0；统计窗口默认 100 步。代码事实（environ.py 第 113–121 行）冗余下限是全组的总数，不是每卡的数，代码会把它向上取整到“384 + 冗余”能被 EP 整除。（eplb/__init__.py 第 21–28 行）上游公布的设置和实测如下。上游报告（Q&A 第 93–103 行）

对照 Strata：Strata 的专家缓存也在跟踪“谁最近热门”，每 4 轮按衰减计数把热门专家换进显存（第 12 章）。它要解决的是“在哪里算”：显存还是 CPU。EPLB 要解决的是“谁最忙”：热门专家多复制几份，摊给几张卡。两者都拿过去预测未来，也都先把权重拷完再切换映射。

2.5 请求怎么分到卡上：三个数据并行负载均衡器

EPLB 只管 MoE 部分。注意力部分的忙闲，取决于每张卡分到多少请求、这些请求的上下文有多长。这由 DP 层面的负载均衡器负责。它们和线上系统耦合很紧，这次没有开源：README 把预填充和解码的 DP 负载均衡列在“不包含”里，Q&A 说负载均衡组件和内部基础设施耦合紧，还没有完全开源，视觉编码器的负载均衡器也在其中。上游报告（README 第 38–42 行、Q&A 第 21 行）下面三条都只来自 Q&A 的描述。上游报告（Q&A 第 105–127 行）

  • 预填充负载均衡器。请求按总上下文长度分成四档：16K 以下、16–64K、64–256K、256K 以上。每档分到多少引擎，按上一轮各档的算力需求动态调整。引擎按剩余的算力额度主动来取活。因为任何引擎都能命中任何前缀（块 KV 缓存存在独立的 3FS 存储集群上，Q&A 第 141 行，见第 3 页），所以不按前缀亲和性分配。进了 DP 组，每个请求交给当前额度负载最低的 rank。
  • 解码负载均衡器。在所有解码实例的所有卡之间统一分配，同时平衡两个量：请求数（决定每步的批大小）和 KV 缓存总长度（决定注意力的开销）。经验做法是：短请求发给并发低、但 KV 总长大的卡，长请求发给 KV 总长小的卡。
  • 视觉编码器负载均衡器。预填充机器随机挑一台部署了视觉编码器（VE）的机器，再把图片交给这台机器上当前处理图块最少的卡。图块数直接按尺寸算：(宽 ÷ 图块边长) × (高 ÷ 图块边长)。

两层均衡缺一不可：DP 负载均衡器让每张卡的注意力差不多忙，EPLB 让每张卡的 MoE 差不多忙。上游说，整体能做到完全均衡的离线基准的大约 80%。上游报告

宽也有代价。一个解码实例的所有卡是一个通信域，坏一张卡，整个实例就不能用了。重启时，平台按当时健康的卡数重新决定 EP 宽度。上游报告（Q&A 第 209–211 行）扩缩容和其他容错手段，见第 1 页。

2.6 专家权重用 FP4：每步要读的字节再少一半

每卡每步要读的专家权重 = 专家个数 × 每个专家的字节数。2.2 节减少了前者，FP4 减少后者。上游说，路由专家的权重用 MXFP4：每 32 个权重共用一个 ue8m0 缩放系数。主 KV 和索引 KV 也用了 FP4，那是第 3 页的话题。上游报告（Q&A 第 213–221 行）

代码和这段描述一致：加载模型时，config.json 的量化配置必须写明专家用 FP4、缩放系数用 ue8m0，否则拒绝加载。代码事实（config.py 第 253–264 行）专家权重以 e2m1 格式两个一组塞进一个字节，缩放系数另存。（weights.py 第 281–288 行）矩阵乘时，激活用 FP8、专家权重用 FP4。（mlp.py 第 177–182 行、第 109–128 行）

算一下每个权重占几位：32 个权重 × 4 位，加 1 个 8 位的缩放系数，共 136 位，平均每个 4.25 位。教学推演 和 FP8 的 8 位比，每步要读的专家字节差不多减半。

对照 Strata：Strata 的 Q2_0 每个权重 2.25 位（第 4 章「量化」），目标是让 34 GB 的专家尽量多地住进 12 GB 显存，没住进去的由 CPU 算。DeepInfer 的专家全在卡上：一边把专家摊到几十张卡，一边用 4 位格式，两头一起减少每张卡每步要读的字节。

记住这三点

  1. 注意力按数据并行，每张卡管自己的请求；路由专家按专家并行，摊到 EP 张卡上。每层 MoE 都要分发、合并两次全对全，所以全组每一步一起走。
  2. 解码时卡越多，每张卡每层的专家越少（EP8 每卡 49 个，EP64 每卡 7 个），每步要读的专家权重越少，一份权重服务的 token 越多；每卡的通信量几乎不变。
  3. 最忙的那张卡决定整组的速度。EPLB 统计每个专家的负载，定期给热门专家加副本、重新摆放，再在卡之间搬权重；上游在解码上报告的 moe_lb 是 1.090。

常见误解：“EP 越宽越好，卡越多越快，可以一直加下去。”

加卡省下的读带宽越来越少：从 EP8 到 EP64，每卡专家从 49 个降到 7 个；再翻一倍到 EP128，只从 7 个降到 4 个。教学推演 EP 组超出 NVLink 域时还有普通的 DeepEP 路径可走，但 Mega MoE 和单机内的权重镜像搬运都只在域内使用；通信域越大，等最慢那张卡的风险越高，坏一张卡停掉的卡也越多。上游给的解码宽度是 EP64–128，对应一个 64–128 卡的超节点。上游报告

深入一层：EPLB 的代码路径、环境变量与 benchmark 口径

专家怎么编号

FusedExperts 的文档字符串定义了四个数：logical = n_routed_experts，路由器从中挑选；extra = n_redundant_experts，由 model_loader._configure_moe_redundancy 写入；physical = logical + extra，必须能被 ep_size 整除；local = physical // ep_size。（moe.py 第 1–8 行）取整由 resolve_num_extra_experts 完成：padding = -(num_routed_experts + min_num_extra_experts) % ep_size。（eplb/__init__.py 第 21–28 行、model_loader.py 第 83–106 行）初始布局是 [0 … n−1, 然后 0, 1, 2 … 的副本]，所有层用同一份。（第 31–39 行）加载权重时，每个 rank 按这份初始布局只读自己那几个专家，冗余副本复用同一份 HF 权重。（weights.py 第 248–272 行）权重形状相同的 MoE 层合成一组，每组一个 ExpertLoadBalancer。（deepseek.py 第 323–365 行）

每一步做什么

ExpertLoadBalancer.step 由采样阶段每步调用一次，EP 只有 1 时直接返回。它做三件事：把本步的 expert_count 存进窗口、需要时重排；累计负载统计；把 expert_count 清零。（第 131–165 行）NORMAL 引擎（同时做预填充和解码）默认跳过预填充步：这一步的计数不进窗口，也不推进重排计数；设 DEEPINFER_REARRANGE_AFTER_PREFILL_IN_NORMAL_ENGINE=1 后，预填充步的计数进窗口，下一个非预填充步立即重排。（第 83–84 行、第 146–165 行）负载统计每 DEEPINFER_MOE_LB_STAT_INTERVAL（默认 128）步做一次 all-gather，得到各卡 token 数的平均值和最大值，两者之比就是日志里的 moe_lb。（第 167–193 行）

策略的两段贪心

rebalance_experts_global 先复制、后摆放。复制阶段每轮对每个候选专家 j 算：“给 j 加一份副本后，每一步里最大的单份负载”，按步求和，取最小的那个 j。分数里加了 j × 1e-4，保证各专家的分数互不相同。（policy.py 第 73–140 行）摆放阶段的目标写在注释里：让“各步里最忙那张卡的负载”之和尽量小，同分时选编号小的卡。仓库的单元测试检查两张映射表互为逆、副本总数等于物理槽位数，以及同样输入两次结果完全相同。（test_eplb_policy.py 第 27–62 行）本页的模拟器把它简化成单层、双精度浮点，同分的处理可能和 PyTorch 的单精度版本略有不同。

权重怎么搬

第一次重排时先清空 PyTorch 的显存缓存，防止显存不够。EP 组在 NVLink 域内、并且是 GPU 时，建一块只装一层权重的对称显存镜像，逐层刷新；每张卡直接从配对的发送方镜像里拷贝缺的专家。否则走 torch.distributed 的批量点对点收发（NVIDIA 上是 NCCL），按 DEEPINFER_REARRANGE_P2P_GROUPS 分桶。同一个专家有多个发送方时，接收方按固定规则均分给发送方，收发两端用同一个函数配对，保证对得上。（eplb/__init__.py 第 195–220 行、shuffle.py 第 47–53 行、第 94–147 行）搬完权重，才用 copy_ 换上新的映射表。（第 261–278 行）

benchmark 口径

benchmark 的解码吞吐按“满接受”计：每个请求每步算 1 + nextn 个 token，不管草稿实际接受了几个。（examples/README 第 55 行）README 首页的解码图和宽度对比图用的是另一个口径：出图脚本把两根轴都乘以 τ = 1 + nextn × 接受率，副标题写着按 75% 接受率折算、τ = 3.25。（plot_pareto.py 第 58–67 行）所以 benchmark 直接打印的满接受吞吐，比图上的数要高。加上 DEEPINFER_FORCE_LOAD_BALANCE=1，这些图都是“负载完全均衡”下的数字。这些口径细节，第 4 页还会讲到。
