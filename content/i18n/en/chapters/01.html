Let's start with a puzzle

The first line of Strata's README says: run a 125-billion-parameter AI model on your own gaming PC. For the graphics card, it asks for at least 12 GB of VRAM. Upstream report[S01]

Do the common-sense math: 125 billion parameters, even at just 1 byte each, come to 125 GB. How can a 12 GB graphics card hold that? This book answers questions like this one: how does an AI model actually run inside your computer? Along the way, we will tie together the basics of computer organization, operating systems, algorithms and networking.

In one line: a chat AI generates only one token at a time. Generating that one token puts the GPU, RAM, CPU and SSD to work. Strata's trick is to arrange these four so that each one is just enough.

1.1 What happens after you press Enter

You type a sentence into the chat box and press Enter. A few seconds later the answer appears, word by word. In between, your words go through six transformations, shown in Figure 1-1.

The figure has a few new words. Here they are in plain language.

A token is the smallest unit a model reads and writes. It may be one Chinese character, one word, half an English word or one punctuation mark. The model does not read letters directly; it only knows token IDs. The tokenizer is the program that cuts text into tokens and turns them into IDs, as Figure 1-2 shows.

Sampling is step ⑤. The model does not "say" the next word directly. Instead it gives a probability for every candidate token, and sampling picks one according to those probabilities. Chapter 2 covers it in detail.

Look at the dashed line in Figure 1-1. The model generates only one token per round: to write a 300-token answer, steps ④ to ⑥ repeat 300 times. That is why "generation speed" is usually measured in tokens per second, written token/s.

If you studied CS: the whole generation process is one loop: while not done: probs = model(tokens); t = sample(probs); tokens.append(t). Each round's input includes the previous round's output. A model that "feeds on its own output" like this is called an autoregressive model.

1.2 Why the first word is always a bit slow

You may have noticed: after you send a question, you wait a moment before the first word appears; after that, the words come quickly. The reason is that an answer has two phases, shown in Figure 1-3.

The first phase is called prefill ("reading the prompt"): the model reads your whole question in one go. Every token in the question is already known, so they can all be computed together. The second phase is called decode ("writing the answer"): each new token depends on the one before it, so they can only come one at a time.

Strata's upstream measurements show that on the same machine, prefill handles about 1,299 tokens per second and decode about 93. Upstream report[S03] So the longer the question, the longer you wait for the first word. The README also warns that the first message of a conversation must be read in full, at roughly 1 minute per 30,000 tokens; later follow-ups read only the new part and start answering within seconds. [S01]

1.3 Model, engine, app: three roles people often mix up

Think of a restaurant, as in Figure 1-4. Strata's own docs use a kitchen analogy too. [S02]

  • The model is the recipe. It is a huge pile of trained numbers (called "parameters" or "weights"), plus a fixed set of computation rules. Qwen3.8-Flash-Next is a model.
  • The inference engine is the kitchen and the chefs. It does the computation on your hardware, following the recipe. Strata is an inference engine; so are llama.cpp and vLLM.
  • The app is the front desk. It greets you, tidies up your words and hands them to the kitchen, then brings the finished dish back to you. Strata's built-in web chat page, and the coding tools that connect through its API, all live in this layer. [S01]

Keep these three layers apart, and you will not look in the wrong place when something breaks. However fast the engine is, it cannot make the model smarter: same recipe, different kitchen, and the dish should taste the same. In the other direction, if answer quality drops, the cause may be the recipe (a different model, or one compressed too hard), the kitchen (an engine bug that computes something wrong), or the front desk (a template or protocol that passes your words on incorrectly).

1.4 Three layers of "storage" in one computer

How fast a kitchen works depends a lot on where things are kept. A computer is the same. Three layers of storage matter for inference, shown in Figure 1-5.

The graphics card (GPU) computes fastest, but its VRAM is the smallest: common gaming cards have only 12–24 GB. RAM is much bigger, but it sits far from the GPU, and data must travel over a bus called PCIe to get there. The SSD is the biggest and also the slowest.

Strata divides the work like this Upstream report[S02]:

  1. The parts every token needs, plus the few thousand most often used "experts", go in VRAM.
  2. All the experts go in RAM. The ones not on the GPU are computed by the CPU right there in RAM, working at the same time as the GPU.
  3. The SSD holds a 28.8 GB lookup table, and each token reads only a few of its rows.

Chapter 10 is all about what an "expert" is. For now you only need to know that experts are the key to running a big model on a small graphics card.

The memory hierarchy

A computer's storage devices always trade off among "fast", "big" and "cheap": the faster ones are smaller and pricier, and the bigger ones are slower. So a computer stacks them into a pyramid: the most used data goes on the fastest level, less used data goes lower, and data moves up when it is needed. This is the memory hierarchy.

Two measures describe "fast". Bandwidth is how many bytes per second you can move, like how thick a water pipe is. Latency is how long you wait from sending a request to getting the first byte, like the time water takes to flow from the tap into the glass. An inference engine reads a huge number of parameters for every token, so it cares most about bandwidth. Figure 1-6 shows the theoretical bandwidth of each level on the upstream test machine.

All of Strata's design can be seen as placing data on this pyramid: hot experts in VRAM, all experts in RAM, the big lookup table on the SSD. Later chapters come back to this picture again and again.

Further reading: Wikipedia: Locality of reference · Wikipedia: Memory hierarchy · Computer Systems: A Programmer's Perspective (CS:APP), Chapter 6

If you studied CS: this is the memory hierarchy from computer organization, with one extra level: VRAM. To the CPU, VRAM is memory on another device. The CPU cannot read and write it directly the way it uses its own RAM; data has to be moved over PCIe (Chapter 14 covers DMA).

1.5 Doing the math: 24,576 and 480

The README says this model is made of 24,576 "experts", and each word it writes needs only 10 of them. [S01] That sentence is simplified to make it easy to read. Let's check it against the source code.

The source code defines the model as 48 layers with 512 experts per layer Code fact[S04]; every token picks 10 experts in each layer Code fact[S13]. Figure 1-7 draws this structure.

  • 48 × 512 = 24,576: this is the total number of experts.
  • One token passes through 48 layers and picks 10 in each, for 48 × 10 = 480 expert picks in total.

"10" is per layer, not for the whole model. If you read it as "the whole model uses only 10 experts", your estimates of compute and data movement will be 48 times too small. This is a habit the book keeps stressing: a number must carry its unit and its scope.

1.6 How to read this book: every number has a source

Every conclusion in this book is marked with the kind of evidence behind it:

  • Code factRead directly from the source code at a fixed version. For example, "48 layers".
  • Upstream reportAn explanation or a measurement from Strata's author in the docs; this book has not measured it again. For example, "94 tokens per second on an RTX 5070". [S01]
  • Teaching estimateA result this book works out with a simplified model, to help you build intuition; not a measurement. All the interactive experiments in your browser belong here.
  • Basic principles: general rules of math or computing that do not depend on Strata. These get no tag.

Why be so fussy? Because numbers in the AI world are very easy to carry to the wrong place. A speed from someone else's graphics card, the VRAM use of one particular setup, a simplified claim in a marketing picture: once cut off from their conditions, they can mislead. Learning to ask "under what conditions was this number measured?" is worth more than memorizing any single number.

The source code reading in this book is pinned to one commit from 2026-10-03; its hash is in the page footer. Strata is still changing fast, so the numbers in newer versions may already differ.

Hands-on: open this chapter's interactive lab, "The journey of one token". It breaks the path of Figure 1-1 into stages you can inspect one by one, so you can see the input and output of every step. Try to think of a "what goes wrong if…" example for one of the arrows: say, the template changed, or the tokenizer does not match the model. All the numbers in the lab are teaching estimates, not measurements on your computer.

Remember these three

  1. The model is the recipe, the inference engine is the kitchen, the app is the front desk. Each one owns its own stretch.
  2. Prefill first, then decode: prefill computes the whole question together, decode can only produce one token per round.
  3. For every number, ask: is it a code fact, an upstream report or an estimate? What are its unit and scope?

Common misconception: "You need as much VRAM as the model file is big."

Not necessarily. The file size only tells you how many bytes the weights take on disk. At run time, some weights can stay in RAM, computed by the CPU or sent to the GPU on demand; VRAM also has to hold the chat history and temporary data. Strata downloads a model of about 70 GB, yet runs on a 12 GB graphics card. [S01]

The real boundary between the server layer and the engine

In Strata's server code, what the app layer hands to the engine is not an HTTP request, and not raw JSON either, but a list of token IDs. The interface is Engine.generate(ids, max_new, sampling, cancel), and it returns an iterator that yields token IDs one by one. Code fact[S15] Template rendering, tokenizing and protocol parsing all happen outside this boundary. So when you debug, the first step is to decide which side of the boundary the error is on.

The same file also says that the server handles only one sequence at a time, and requests queue first come, first served (FIFO). [S15] "Supports an OpenAI-compatible API" does not mean "supports many users at once"; Chapter 25 discusses what it takes to extend it to many users.

Different kinds of "cache" are not the same thing

The CPU's hardware cache keeps recently accessed memory lines. Strata's expert cache puts some of the weights in VRAM. The KV cache keeps intermediate results of the chat history. The session cache keeps whole sequence states that can be restored. The lookup table's row cache keeps table rows read from the SSD. What they cache, how long it lives and when it becomes invalid are all completely different. "Add a cache" means something only once you say what is cached, how you confirm it is still the same object, and when it becomes invalid.

A comment is not a fact

Source comments can be stuck at an old stage of development. For example, the top of expert_source.hpp says "Phase 2 has no cache (hit rate h = 0)" and explains that Phase 3 will replace this object with a VRAM cache. [S06] Yet the current engine does have an expert cache. [S02][S05] When you meet a contradiction like this, do not decide based on one comment; trace the current call chain, the default configuration and the tests. The source tour in this book reviews the listed windows of key files; it is not a line-by-line audit of the whole repository.

Class activity: draw responsibility boundaries for one token

Draw five boxes on paper: server layer, sequence state, weight storage, compute kernels, hardware. For each box, write one input, one output and one condition that must always hold, for example "a sequence state belongs only to its own conversation". Then place three failures in the boxes where they could come from: "the answer is right but slow", "the answer changes randomly every time", "the second half of the text is garbled". The goal is not to guess right at once, but to learn to design experiments that tell these hypotheses apart.
