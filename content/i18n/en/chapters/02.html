You may have noticed

Ask a chat AI the same question twice, and you often get two different answers. But it is a computer: how can the same input give different outputs?

The answer hides in step ⑤ of Chapter 1's six steps. The model never "says" the next word directly. It only produces a probability table, and then, like rolling dice, picks one entry from it. This chapter explains, step by step, where that table comes from, how the dice are rolled, and what filtering happens before the roll.

In one line: at each step the model answers just one multiple-choice question: given the text so far, it scores every token in the vocabulary; softmax turns the scores into probabilities, and a random number picks one token by probability. Temperature, top-k and top-p all change this probability table before the pick.

2.1 The model reads numbers, not letters

As Chapter 1 said, the tokenizer cuts text into tokens and turns them into integer IDs. Strata's tokenizer has 248,320 tokens, and its method is called byte-level BPE: first split the text into its smallest units, bytes, then keep merging pieces that often sit next to each other in the training text into a single token. Common words end up as one token; rare characters are split into several pieces. Code factstrata_tokenizer.py

Because the lowest level is bytes, any text can be represented, and "unknown character" never happens. The tokenizer's notes also name the check it cares about most: encode a piece of text and decode it again, and you must get back the original, byte for byte. Emoji, multi-byte Chinese characters and runs of spaces are all covered by this check.

So a token is not the same as a word. Strata's README says "a token is about ¾ of an English word". [S01] That is a rule of thumb for English; Chinese, code and tables all have different ratios. The only reliable way to count the tokens in a piece of text is to actually run this tokenizer on it.

One more thing is easy to miss: the sentence you type is not all the model reads. The chat template in step ② adds role tags, a system prompt and tool descriptions around it, as Figure 2-1 shows.

Strata's server layer renders the model's own Jinja template, and it requires the result to match what Hugging Face produces exactly; this is checked against 10 standard examples, including thinking mode and tool calls. Code fact[S16] Before rendering, the server layer also drops the empty assistant turns from the history, that is, those with no text, no images and no tool calls (the last message is kept), so the model does not take "answering nothing" as an example to follow. This is a default behavior added in v0.1.40; set STRATA_KEEP_EMPTY_TURNS=1 to restore the old behavior. [S16] The "thinking level" you choose in the interface is also passed to the template as a parameter: when you choose high, the value actually passed is xhigh; when you choose none, it passes "thinking off". [S16] All of these change the final list of IDs.

The interface between the server layer and the engine is Engine.generate(ids, max_new, sampling, cancel): a list of IDs goes in, and token IDs come back one by one. [S15] Text exists only outside this boundary.

2.2 Guess only the next one: the chain rule

Your phone keyboard guesses the next word as you type. A large model does the same thing, just far more accurately. At each step it answers only one question: given all the tokens so far, what comes next? The answer is not one word but a probability table: every token in the vocabulary gets a probability, and they add up to 1.

The probability of a whole sentence is the product of the probabilities from each step of guessing, as Figure 2-2 shows. This rule is called the chain rule.

Conditional probability and the chain rule

Start with an intuition: the chance that a random person on the street carries an umbrella is not high; but if you know "it is raining outside", that chance is much higher. "The probability of A, given that B happened" is called a conditional probability, written P(A | B), and defined as P(A | B) = P(A and B) ÷ P(B).

Rearrange the definition and you get the multiplication rule: P(A and B) = P(B) × P(A | B). Apply it again and again, and the joint probability of a long run of events breaks into a product of conditional probabilities: P(x₁, x₂, x₃) = P(x₁) × P(x₂ | x₁) × P(x₃ | x₁, x₂). This is the chain rule. It needs no assumptions; it holds for every probability distribution.

Language models are built on exactly this formula: at each step the model learns only one thing, P(next token | all previous tokens). In Figure 2-2, the probability 0.012 of "I love you" is three conditional probabilities multiplied together. Note that the condition is all previous tokens, so changing one word in the prefix can change the probability table at every later step.

Further reading: Wikipedia: Conditional probability · Wikipedia: Independence (probability theory) · Wikipedia: Chain rule (probability)

If you studied CS: this is the multiplication rule from probability theory. Unlike a Markov chain, the condition here is the whole history, not just the previous state. Because the condition includes the whole history, the engine must store that history and reuse it again and again (the KV cache in Chapter 17).

While we are here, let's clear up a common mix-up: during generation, not a single model parameter changes; only the history of "tokens so far" changes. Parameters change only during training. The expert cache in Chapter 10 does adjust as the conversation goes on, but it adjusts where the parameters are kept, not what they are, so that is not "the model learning" either.

2.3 From scores to probabilities: softmax and temperature

The model's last layer does not output probabilities. It outputs a list of scores, called logits in the jargon: one number per token in the vocabulary, positive or negative, and they do not add up to 1. To turn them into probabilities, they go through a function called softmax: first take the exponential ez of every score, which makes it positive; then divide by the sum of all the exponentials, so they add up to 1.

Before taking the exponential, you can also divide every score by a number T, called the temperature. With T below 1, the gaps between scores grow: high scores get relatively higher, the distribution gets "sharper", and the answers get more conservative. With T above 1, the gaps shrink: the distribution gets "flatter", unpopular words get more of a chance, and the answers wander more. Figure 2-3 shows the same scores at three temperatures.

The softmax formula contains an exponential, and exponentials grow extremely fast. Inside a computer that causes trouble. The primer below explains why, and the one trick that fixes it.

Softmax and floating-point overflow

Computers store fractional numbers as floating-point numbers. They have a limited number of bits, so the largest value they can represent is limited too. The most common 32-bit float (FP32) tops out at about 3.4 × 10³⁸. That sounds huge, but e89 already exceeds it. A result above the limit becomes "infinity" (∞); this is called overflow. Once both the numerator and the denominator are ∞, ∞ ÷ ∞ in floating point is NaN (Not a Number), and the whole probability table is ruined.

The fix takes one line: before taking the exponentials, subtract the largest score m from every score. Since ez−m = ez ÷ em, the numerator and the denominator are both divided by the same em, and the ratio does not change at all. But after the subtraction the largest number becomes 0, e0 = 1, and all the others are below 1, so nothing can overflow any more. Mathematically identical, numerically safe: this is called a numerically stable way to write it.

An example: take the exponentials of the scores [1000, 999] directly, and both come out as ∞. Subtract 1000 first to get [0, −1]; the exponentials are [1, 0.3679] and the probabilities are [0.7311, 0.2689]. Strata's sampling kernel does exactly this: it subtracts the maximum from every entry, then computes the exponentials and cumulative probabilities in double precision. Code factsampler.cu

Further reading: Wikipedia: LogSumExp (the same max-subtraction trick) · Python docs: Floating-point arithmetic: issues and limitations · Wikipedia: Softmax function

2.4 Rolling the dice: picking one by probability

With the probability table in hand, how do you "pick by probability"? Picture a ruler of length 1. Lay each candidate's probability along it in turn: cat takes the first 0.62, dog the next 0.23, and so on, until the ruler is exactly covered. Then drop a needle at random; whichever segment it lands in, that word is picked, as Figure 2-4 shows. A high-probability segment is long, so it has a bigger chance of being hit.

This method is called inverse transform sampling: first compute the cumulative probabilities (0.62, 0.85, 0.94, …), then find the first position greater than u. Strata's sampling kernel picks exactly this way: it adds up the cumulative probability entry by entry, and the first entry that goes past u is the result. Code fact[S07]

The other approach is greedy decoding: roll no dice, always pick the most probable token. Greedy output is fully deterministic, which suits cases that need a stable answer, such as solving exercises or testing. Strata's sampling parameters say that a temperature of 0 or below means greedy, and the server layer notes that when a request gives no temperature, the engine also defaults to greedy. Code factsampler.hpp · server.py

One question remains: how does a computer drop the needle "at random"? It actually computes a number that only looks random.

Pseudorandom numbers and seeds

A computer is a deterministic machine: the same input always gives the same output. The "random numbers" it produces are really a sequence computed by a formula that just looks patternless; these are called pseudorandom numbers. The formula's starting point is called the seed: same seed, same whole sequence. That is a good thing: when something goes wrong, you can replay the exact scene with the same seed.

Common generators are sequential: each number is computed from the previous one, so to get the 1000th you must first compute the 999 before it. There is also a counter-based kind: the n-th number is computed directly from (seed, n), no matter how many came before, as Figure 2-5 shows.

Strata's sampling uses a counter-based generator called Philox: the random number for the t-th token is determined only by (seed, position t). A source comment states the reason for this choice: a batch of tokens can be sampled in any order, and the results can still be reproduced. The generated u takes 24 bits, so it falls strictly inside [0, 1) and is never rounded up to 1. Code factsampler.cu

Further reading: Wikipedia: Random number generation · Python docs: the random module · Wikipedia: Pseudorandom number generator · Wikipedia: Counter-based RNG

If you studied CS: inverse transform sampling is a lookup on the cumulative distribution function (CDF): it maps the uniform distribution on [0, 1) to any discrete distribution. With many candidates, the cumulative array is sorted, so binary search brings one draw down to O(log n).

2.5 The sampling chain: order matters too

Before rolling the dice, a real engine first "trims" the probability table several times. Strata's sampling chain has six steps in a fixed order, shown in Figure 2-6. Code fact[S07]

  • Repetition penalty: tokens that appeared recently get lower scores, so the model does not keep repeating itself in circles.
  • top-k: keep only the k highest-scoring tokens. Strata's default sampling parameter is 20; the server layer limits top-k to 1–64, because the engine's sampling path keeps at most 64 candidates. Code factserver.py
  • top-p: add up probabilities from highest to lowest, stop once the sum reaches p, and cut everything after. The default is p = 0.95.
  • min-p: drop candidates whose probability is below min_p times the top one's. The default is 0, which means off.
  • Temperature and the pick: covered above.

Why does the order matter? Look at where temperature sits: after the cuts. So the top-p cut is made using the probabilities at temperature 1. However high you set the temperature, it cannot bring back a candidate that was already cut. The other way around, if you moved temperature to the front, the same parameters would cut a different set of candidates.

Strata itself fell into this trap. A source comment records a fix: an earlier version applied the repetition penalty twice (once more after temperature) and also put min-p in front of top-p. The comment puts it bluntly: every one of these orders produces a "valid" token, so you cannot spot the problem by looking at the output; you have to compare, entry by entry, at the level of the probability distribution, against an independently computed result. Code factsampler.cu

This gives us an important habit: to judge whether two sampling implementations agree, compare the probability tables, not just the final text. The text can be identical while the distributions differ; and distributions that differ only slightly can make the text fork at some step.

2.6 Hands-on: look at the "distribution" and the "draw" separately

Open this chapter's interactive lab, "From logits to probabilities". It uses only three scores and turns temperature and the random number u into two independent knobs.

  1. Fix u, change only the temperature. You will see the probability bars change length, and the picked token may change with them. Temperature changes the distribution.
  2. Fix the temperature, change only u. The probability bars do not move at all; only where the needle lands changes. u changes which sample is drawn from the distribution.
  3. Add up the three probabilities. The numbers on screen are rounded, so they may add up to 0.999 or 1.001. That is not a bug: checking "adds up to 1" must allow a tiny floating-point error.

The lab and the two interactive figures on this page are all teaching estimates: the scores are assumed, and the random numbers come from a simple hash function, not Strata's Philox.

Remember these three

  1. At each step the model outputs only one probability table for the "next token"; the probability of a whole sentence is the product of the conditional probabilities at each step (the chain rule).
  2. Softmax turns scores into probabilities. Subtracting the maximum first leaves the result unchanged and prevents floating-point overflow. Temperature only changes how sharp or flat the distribution is.
  3. Sampling = using one pseudorandom number to pick by cumulative probability. The order of the sampling chain is part of its meaning: a different order gives a different probability table.

Common misconception: "Set the temperature to 0, and the answer to the same question will always be word-for-word identical."

Temperature 0 only guarantees "pick the highest score at every step". But the highest score itself comes out of floating-point arithmetic: change the order of a sum, and the last few decimal places may differ. When two candidates' scores are extremely close, that tiny difference can swap a token, and everything after it forks. Strata's docs record exactly this: with the IQ-series models, the CPU uses different kernels for one token at a time and for several tokens at once, the rounding differs slightly, and the same prompt at temperature 0 may get another (equally reasonable) answer. To get byte-identical output you also have to turn off several settings, including the prompt cache, expert swapping and PCIe offloading. Upstream measurement (IQ3_XXS, a prompt of about 3,600 tokens, repeated 4 times): with all those switches set, the 4 runs gave only 1 distinct answer; with the default settings they gave 2. Upstream report[S03]

The chain rule written out in full

For a sequence x₁…xₙ, the chain rule gives:

P(x₁…xₙ) = ∏ₜ P(xₜ | x₁…xₜ₋₁)

Each round of the inference loop computes one conditional distribution. The "history" is not optional background; it is an input of the function. Change one earlier token, and every later conditional distribution may change. This also explains why cached results for earlier text (the session cache in Chapter 20) can be reused only when the prefix is exactly the same.

Softmax and one draw, by hand

Take z = [2, 1, 0] and T = 1. Subtract the maximum 2 to get [0, −1, −2]; the exponentials are about [1, 0.3679, 0.1353], the sum is 1.5032, and normalizing gives [0.6652, 0.2447, 0.0900]. The cumulative probabilities are about [0.6652, 0.9100, 1]. If u = 0.8, the first cumulative value above it is 0.9100, so the second entry is picked; u = 0.5 picks the first entry; u = 0.95 picks the third. Greedy always picks the first.

Temperature approaching 0 is not the same as greedy

Mathematically, as T approaches 0, softmax approaches "the top-scoring entry has probability 1". But a program cannot actually compute z ÷ 0, so real implementations write greedy as a separate branch. Another detail is ties: when two scores are exactly equal, there must be a fixed rule for who wins. Strata's greedy kernel says the smaller ID wins, the parallel version keeps the same rule, and the comment calls it "the core of the whole correctness argument". Code factsampler.cu

The sign trap in the repetition penalty

The repetition penalty "lowers the score", which sounds like dividing by a number greater than 1. But a score can be negative, and a negative number divided by 1.1 actually gets bigger. Strata copies llama.cpp's rule: divide by the penalty when the score is positive, multiply by it when the score is 0 or below. The comment warns that dividing unconditionally is the most natural thing to write after reading the paper, yet it turns the penalty into a reward on half the vocabulary. Another detail: the presence penalty only looks at whether a token appeared at all; it is a 0/1 switch and ignores how many times. sampler.cu

Same seed does not mean same output

Suppose candidate A had the top score, but it was repeated many times in the history. Doing top-k first and then the penalty, or the penalty first and then top-k, can give completely different candidate sets. So "same seed" is far from enough to prove "same output". You must also fix the history, the sampling parameters, the processing order, and the numerical path that computed the logits. Strata's coupled-draft interface writes all this into the contract: row t of the verification window draws with Philox(seed, pos₀ + t), and a draft is accepted only if it equals that row's draw. So the output is a function of the seed alone, and the drafts decide only how many tokens one round produces. This mode is off by default. Code fact[S07]

The server layer's contract: reject, never silently truncate

When you read serve/frontend.py, first see how ChatTemplate.render passes in messages, tools and the generation prompt, then see how effort_kwargs normalizes the many ways of writing a "thinking level" into the four levels the template knows. [S16] Then read the header of serve/server.py: when the prompt plus the maximum output length exceeds the context, the request is rejected with a 400, never truncated; leaving the maximum output empty, or setting it to 0 or −1, all mean "write as much as the remaining context allows". [S15] The accounting also keeps a margin of CTX_SLACK = 8 positions, matching the check on the engine side. [S15] Those 8 positions are not a mathematical constant of the model; they are an agreement between the front end and the back end.

How to accept a sampling implementation

In the lab, drag the temperature and watch the probabilities, not just the token that gets picked. For acceptance, compare distributions: given the same logits and the same parameters, the two implementations' probability tables must agree within a floating-point tolerance. Do not require the rounded numbers on screen to add up to exactly 1.
