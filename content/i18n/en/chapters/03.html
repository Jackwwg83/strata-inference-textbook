Let's start with a puzzle

Strata's source code has a comment devoted to one spot that is "deliberately different from the reference implementation": the reference implementation stores a block of state data in (S, S, H) order, while Strata's kernel insists on (S, H, S). The comment also warns that both orders use the same three sizes, so mixing them up raises no error. Code fact[S17]

Same numbers, just stored in a different order: why make such a fuss? Because to a computer, "which row and column is this number in" and "which memory cell is this number in" are two different questions. This chapter first works out matrix multiplication, then shows how a table gets flattened onto the single line that is memory.

In one line: almost all of a model's computation is "multiply a row of weights by a column of inputs and add up"; and a tensor = a run of numbers + a rule for "turning coordinates into an address". The shape says which coordinates exist; the strides say how many cells each coordinate steps over.

3.1 A model is full of tables of numbers

Open a model file and you find almost nothing but numbers, arranged into tables by purpose. A single column is a vector; rows and columns make a matrix; stack several tables and you get a three-dimensional array. All of these are called tensors: piles of numbers with coordinates. The length of every axis, taken together, is the tensor's shape, as Figure 3-1 shows.

In the model Strata runs, the data one token passes from layer to layer is a vector of 2560 numbers. Code fact[S04] Each expert from Chapter 10 holds three matrices inside: they squeeze 2560 numbers down to 640, then expand them back to 2560. [S04] Nearly all of the model's computation is multiplying vectors by matrices like these.

3.2 One matrix-vector product, by hand

Start with an example small enough to do with a pencil. W has 2 rows and 3 columns, and x has 3 numbers:

There is only one rule: take a row of W, multiply it pair by pair with x, and add everything up to get one output. Repeat once for every row of W. This "multiply pairs and add" is called the dot product, and the whole operation is a matrix-vector product, written GEMV in the jargon.

Shapes follow a rule too: a (2 × 3) matrix can only multiply a vector of 3 numbers, and the result has 2 numbers. The 3 in the middle must match, and then it "cancels out". One GEMV in a real model might have shape (640 × 2560): 2560 numbers go in, and 640 come out.

Dot products and matrix multiplication

Intuition: you buy 3 items at the store, with unit prices [5, 2, 8] dollars and quantities [1, 3, 2]. The total is 5×1 + 2×3 + 8×2 = 27 dollars. "Two lists of the same length, multiplied pair by pair and added up" is the dot product. It is a weighted sum: one list is the weights, the other the data.

A matrix-vector product is the same data x taking one dot product with each row of W. If W has m rows and d columns, that is m dot products and m × d multiply-adds. If you have b inputs, line them up side by side as a d × b matrix X and compute WX: that is a matrix-matrix product (GEMM). Mathematically it is just b GEMVs placed side by side; in engineering the difference is huge: W is read once and can be reused for all b inputs in turn, as Figure 3-3 shows.

As Chapter 1 said, decode produces only one token per round, so every layer's computation is a GEMV; prefill computes a long question all at once, so it becomes a GEMM. That is what the difference in Figure 3-3 looks like in a real system.

3.3 Memory is a single line: row-major order and strides

A matrix is two-dimensional, but memory is just one long line of cells, each with a number called its address. To put a table into it, you must first agree on "what comes first".

Array memory layout: row-major, column-major and strides

Imagine copying a seating chart into a long, narrow notebook. One way is row by row: first copy every seat in row 0, then row 1. This is called row-major order. The other way is column by column, called column-major order. Both are fine, as long as the reader knows how it was copied, as Figure 3-4 shows.

In row-major order, the address of (i, j) is i × (number of columns) + j. In other words: each time j grows by 1, the address grows by 1; each time i grows by 1, the address grows by a whole row's length. "How many cells the address jumps when one coordinate grows by 1" is called that axis's stride. The table above has strides (3, 1) in row-major order and (1, 2) in column-major order.

In any number of dimensions: address = each coordinate times its stride, all added up. The fastest-changing axis has stride 1, and each axis before it has a stride equal to the product of the lengths of all the axes after it. So to describe a tensor, a shape is not enough; you also need the strides.

Further reading: Wikipedia: Row- and column-major order · PyTorch docs: Tensor.stride · Computer Systems: A Programmer's Perspective (CS:APP), Chapters 3 and 6

If you studied CS: two-dimensional arrays in C are row-major; Fortran and MATLAB are column-major. NumPy and PyTorch tensors carry a set of strides, and a transpose is often just a swap of two strides, with not a single byte moved. That is exactly why two tensors with "the same shape" can be laid out completely differently in memory.

3.4 An example with three axes: one element, two addresses

Let's shrink the state from the opening. Call the three axes i, h and j, with lengths 2, 3 and 2: 12 numbers in all. In (i, h, j) order, j is fastest; in (i, j, h) order, h is fastest. Below you can click any element and see where it lives under each order:

Work out the highlighted element (i=1, h=2, j=0) by hand. In (i, h, j) order the strides are (6, 2, 1), so the address = 1×6 + 2×2 + 0×1 = 10. In (i, j, h) order the strides are (6, 1, 3): i steps 6, j steps 3, h steps 1, so the address = 1×6 + 0×3 + 2×1 = 8.

Both addresses are in the valid range. That means: if the writer uses one order and the reader uses the other, the program does not crash and does not go out of bounds; it just quietly reads the wrong numbers. The final result is finite and looks normal, but it is wrong. Errors like this are the hardest to track down.

3.5 Why Strata deliberately switches the order

Back to the comment from the opening. The model Strata runs has 36 layers called GDN layers, and each has a block of state: a three-dimensional array with two axes of length 128 and one of length 48. Code fact[S04] The reference implementation stores it as (S, S, H) = (i, j, h); Strata's kernel changes this to (S, H, S) = (i, h, j), making j the fastest axis. Code fact[S17]

The reason is in the comment: with i fixed, a group of threads on the GPU reads down along j, one after another. If j is fastest, the group reads one contiguous stretch of memory; if not, the threads must read one number every 48, as Figure 3-6 shows. When a GPU reads contiguous memory, it can merge a group of threads' requests into a few large reads, which is called memory coalescing; reads that jump around cannot be merged (Chapter 15 has the details).

The comment goes on: this state is a buffer built at run time, not weights from the model file, so choosing either layout costs nothing extra; but the choice must be written down, because the two layouts "index the same three sizes, and mixing them up is silent". [S17] Let's work out its size while we are here: 128 × 48 × 128 = 786,432 numbers, at 4 bytes each in FP32, is exactly 3 MiB; all 36 layers come to 108 MiB. Teaching estimate

The attention layers' KV cache has a similar agreement. The source writes its layout as [page][KV head][position in page][head dimension], with the last axis fastest, and requires that code outside the header file must not assume this mapping on its own. The tests run with page sizes of 1, 4 and 512 and with a shuffled page table, and require the attention output to be exactly the same each time. Code fact[S18] The "layout" is treated as part of the interface contract.

3.6 Check shapes at load time, then try it yourself

Since a wrong layout or a wrong shape will not raise an error on its own, you have to check actively. Strata's layout.hpp writes every size the kernels depend on into a struct, ModelGeometry: width 2560, 48 layers, one attention layer every 4 layers, 512 experts per layer, and so on. Then check_layer and check_all check the shape of every tensor in the model file, one by one. Code fact[S04]

The comment at the top of the file spells out why: a mismatch must be reported at load time, naming the tensor, its actual shape and the required shape, instead of turning into one wrong number in a GEMV at token 4000. The comment also records a real lesson: in one round of development a cache size was computed 4 times too large, because "the number of query heads" was mistaken for "the number of key heads"; and that bug survived an extra round, because it made the VRAM budget tighter and so looked even "safer". [S04]

Another check lives in layer.cpp: a quantized tensor is made of three blocks (codes, scales and offsets), and the program requires the byte counts of the three blocks to add up to exactly the whole tensor; the offset flag and the presence of the offset block must also agree. If they do not match, the tensor is rejected rather than guessed at. Code fact[S14] What these "three blocks" are is covered in Chapter 4.

Hands-on: open this chapter's interactive lab, "Work out a matrix multiplication". First predict the result on paper, then change one input element and see which outputs change with it. Then try the two interactive figures on this page: in the matrix-vector product, set x to [0, 1, 0]; in the stride experiment, click the same element and switch layouts. Finally, a small exercise: fill each element of the matrix with a number that shows its coordinates (for example, 12 for row 1, column 2), then deliberately write the strides the wrong way round and see which number in the output "ended up in the wrong place".

Remember these three

  1. Matrix-vector product = one dot product of x with each row of W. Compute several inputs side by side (GEMM) and one copy of the weights gets used several times.
  2. Memory is a single line. Tensor = a run of numbers + a shape + strides; address = each coordinate times its stride, added up.
  3. A wrong layout raises no error; it just quietly computes the wrong thing. So the layout belongs in the interface, and shapes must be checked at load time.

Common misconception: "Two tensors with the same shape can simply stand in for each other."

The shape only says which coordinates exist, not which memory cell each coordinate maps to. Strata's GDN state has the same shape in the reference implementation and in the kernel, but a different layout; hand one to the other directly and you get finite but wrong numbers. Code fact[S17] You also have to check the strides, what each axis means, and what state the data is in (for example, whether it is already normalized).

Go deeper: the address formula, head mapping and interface contracts

The general address formula

For a tensor with any number of dimensions, offset = Σ index[a] × stride[a]. The shape tells you which coordinates are valid; the strides tell you how many elements one step along each coordinate skips. State the unit of the strides clearly: "elements" or "bytes". They differ by a factor of the element size, and mixing them up is another common kind of bug.

Worked example: locating a 3-D element

Take S = 2 and H = 3, with the contiguous (i, h, j) layout where j is fastest. Element (1, 2, 0) has offset (1 × 3 + 2) × 2 + 0 = 10. If you wrongly read it as (i, j, h), the same mathematical element has offset (1 × 2 + 0) × 3 + 2 = 8. Both addresses are in the valid range, so a bounds check cannot catch it. More generally, memory safety is not numerical correctness: valid addresses, no NaN and a fluent final sentence prove nothing about whether the tensor layouts agree.

Head mapping: modulo or integer division

"Which head pairs with which head" is also an indexing rule, and both common ways of writing it produce results of the right shape. A GDN layer has 48 value heads and 16 key heads; Strata says value head h pairs with key head h mod 16 (modulo), not h ÷ 3 (integer division). [S17] An attention layer has 24 query heads and 2 KV heads, and the rule is exactly the opposite: query head q pairs with KV head q ÷ 12 (integer division), not q mod 2. Code fact[S18] For example: value head 17 pairs with key head 1 by modulo, but key head 5 by integer division; query head 1 pairs with KV head 0 by integer division, but KV head 1 by modulo. Write them the wrong way round and the program still runs. That is why the source comments say both the reference implementation and the tests "pin down" these two rules.

The paged address of the KV cache

The attention layers store their KV cache in pages. The row for logical position t and head h lives at: page = table[t / page_size], row = (page × n_head_kv + h) × page_size + (t mod page_size). In other words, consecutive positions of the same head sit next to each other inside a page, which is exactly the property attention wants most. [S18] The tests use three page sizes and a shuffled page table and require identical output: the choice of layout must not leak into the result.

The second job of a type system

C++'s float* only says "this points to some floating-point numbers". It does not say whether these are activations before or after normalization, which layer produced them, whether an expert's result has already been multiplied by the routing weight, or even whether they live in CPU memory or VRAM. Strata's sampling interface has a whole paragraph of warnings in capital letters about this: logits and out are VRAM pointers, and neither the parameter names nor the types show it; pass the wrong one and the error surfaces in the next synchronizing call, pointing at some unrelated buffer. sampler.hpp

You can add semantic types in the design, such as NormalizedActivation or ExpertOutputUnweighted. Even without changing the types, the interface comments and the tests should state five things clearly: shape, layout (strides), whether it is normalized, whether the routing weight has been applied, and who owns the buffer and for how long. The contracts of expert_source.hpp in Chapter 10's "Go deeper" are examples of exactly these five things.

GEMV and GEMM: same transform, different reuse

A GEMV in inference multiplies a matrix by one vector; stack several inputs into X and it becomes a GEMM. Both perform the same linear transform, but their chances to reuse the weights are completely different, so you cannot compare their speed by "total floating-point operations" alone. Chapter 5 puts numbers on this with the roofline model.

Test with small, asymmetric samples

Implement the product with W = [[1, 2, 3], [4, 5, 6]] and x = [1, 0, −1]; then stack a few x's into two columns and compute them together, and require each column's result to equal the GEMV on its own. Then deliberately swap the strides and confirm the test fails. Every position in W is different and nothing is symmetric, so errors like a transpose or swapped rows and columns are hard to hide behind a coincidence.
