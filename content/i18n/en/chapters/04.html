Let's do the math first

125 billion parameters, stored at the common 16 bits each, take 250 GB. Yet Strata's installer downloads a model file of only about 70 GB. Upstream report[S01] This chapter works out why: in its expert part, each parameter takes only 2.25 bits on average.

When a number shrinks from 16 bits to just over 2, where does the lost information go? And how can the model still work? This chapter starts from "how a computer stores one number", moves on to "how a whole block of numbers shares one ruler", and ends with Strata's real formats.

In one line: quantization approximates a large block of fractional numbers with just a few integer levels: each block shares one scale s, and each number stores only "how many s it is". Fewer bits mean coarser levels and bigger errors; the error is accepted on purpose, so it must be measured.

4.1 How many bits does one number take?

Inside a computer everything is 0s and 1s. One bit can show only two states; 8 bits make 1 byte, which can show 256. The more bits a parameter uses, the finer the numbers it can represent, and the more space it takes. Figure 4-1 puts the total size of 125 billion parameters at different bit widths side by side.

The formula is simple: bytes = number of parameters × bits ÷ 8. 125 billion × 2.25 ÷ 8 ≈ 35.2 billion bytes, about 35 GB. Teaching estimate This is only the average size per parameter in the expert part; some more sensitive parts of the model use more bits.

Before we talk about "how to squeeze", let's look at how everyday numbers with a decimal point are stored in a computer.

Binary and floating point: FP32, FP16, BF16

Scientific notation writes 123000 as 1.23 × 10⁵: a "significant part" times a power of 10. Computers do the same thing, only with base 2: any nonzero number can be written as 1.xxx × 2ᵉ. It is stored in three fields: the sign bit (positive or negative), the exponent bits (what e is, which sets the range) and the mantissa bits (the xxx after the 1, which sets the precision). This way of storing numbers is called floating point, and the standard is IEEE 754.

Three common formats split the bits differently, as Figure 4-2 shows. FP32 uses 1 + 8 + 23 bits. FP16 uses 1 + 5 + 10 bits; with only 5 exponent bits, its largest value is 65504. BF16 uses 1 + 8 + 7 bits: its exponent is as wide as FP32's, so its range is almost the same, but the price is a mantissa of only 7 bits, which makes it 8 times coarser.

BF16 has a neat property: it is just FP32 with the last 16 bits cut off. So converting BF16 back to FP32 only means adding 16 zeros, with no loss at all; converting FP32 to BF16 must round off the cut-off part. Strata's conversion function copies ggml's approach: "round to nearest, ties to even", and it checks for a tie by looking at bit 16. The comment specifically warns that using bit 15 by mistake goes wrong only on "exact ties", which almost never show up in real data, so no end-to-end test would catch it. Code factbf16_bits.hpp The same comment also stresses that FP16 and BF16 are not two spellings of the same thing: use a conversion function written for one on the other, and you get "reasonable-looking" wrong numbers.

The most common traps in model inference are exactly these details: FP16 overflow, precision lost in subnormals, and how "round to nearest even" and "round half away from zero" differ on ties.

4.2 Quantization: one ruler for a whole block of numbers

In floating point, every number carries its own exponent. That is flexible, but it takes space. Quantization takes a different approach: a whole block of numbers shares one ruler. The spacing between the ruler's marks is called the scale s, and each number only records "about how many s it is". That integer is called the code.

Integer quantization and error

Intuition: measure people's heights with a ruler marked only in whole centimeters, and everyone is recorded as "the nearest whole centimeter", off by half a centimeter at most. Quantization works the same way: first choose the mark spacing s, then round each number to the nearest mark. Denser marks mean smaller errors, but more levels to record, so more bits per number.

The simplest kind is symmetric uniform quantization. With b-bit codes, take Q = 2b−1 − 1 (Q = 7 for 4 bits). Find the largest absolute value a in the block and set s = a ÷ Q. Each number x is encoded as q = round(x ÷ s) and restored as x̂ = s × q. That way the largest number lands exactly on level ±Q, and all the others fall in between.

The difference between the restored value and the original is the quantization error. A common summary of a block's error is the mean squared error (MSE): square each error, then average. In the example above, MSE ≈ 0.00087. Without clipping, no number's error exceeds s ÷ 2.

Further reading: Wikipedia: Mean squared error · Wikipedia: Quantization (signal processing) · Hugging Face docs: Quantization

Note that each number stores only a small integer, but the block must also store an s. That s takes space too. The bigger the block, the less of s each number has to carry; the smaller the block, the more "expensive" s becomes. The next section shows that this trade-off cannot be avoided.

4.3 Outliers: one big number drags down a whole block

Sharing one ruler has a weak spot: the ruler's marks are set by the largest number in the block. If most numbers in a block are within ±0.5 but one of them is −2.8, s gets stretched several times over, the marks get coarser, and the small numbers all snap to level 0. A number that stands out like this is called an outlier, as Figure 4-4 shows.

One fix is to make the blocks smaller: an outlier can only drag down its own small group. The price is more values of s. With g numbers per group, b bits per number and one 16-bit s per group, each number really takes b + 16 ÷ g bits. 4-bit codes in groups of 32 really cost 4.5 bits; in groups of 4 they cost 8 bits, which throws away half the compression.

So "4-bit quantization" names only the nominal bit width. The real cost must include the scales (and, in some formats, offsets). Rotations, non-uniform codebooks and giving sensitive layers a few more bits are other ways to deal with outliers, but each has its own decoding cost, and they must be weighed together.

4.5 Same formula, different decimals

The error quantization brings in is "on purpose". There is another kind of error that is "by accident": floating-point addition is not associative. See Figure 4-6.

This happens in inference engines every day. In Strata, the same expert is computed on the GPU when it hits the GPU cache and on the CPU when it misses. The source records one real reconciliation: the CPU side stored its activation scales in FP32, while the GPU side stored them in FP16 as the format says, and the two differed by about 4.761 × 10⁻⁴ (relative error) on every one of 80 data blocks. A version that lets the GPU use the CPU's scales was added for exactly this reason. Code factquantize_act.hpp The same file also notes that multiplying FP16 activations directly with quantized weights is off from the reference answer by 0.6%–0.9%, which is 6 to 9 times the allowed error.

Rounding rules are the same story. Strata writes the rounding of 8-bit activations as "round to nearest, ties to even", not the "ties away from zero" of C's roundf. The two differ only on exact ties, which almost never occur in real data, so the wrong one would still pass every end-to-end test. Its comparison test therefore builds ties on purpose. quantize_act.hpp

The chat history can be quantized too. By default Strata stores the KV cache in 8 bits; the optional 4-bit KV, available since engine 0.1.8, halves that memory and runs about 4% faster at a 128K context, but it gets noticeably less accurate on long documents: perplexity (a measure of how "surprised" the model is; lower is better) rises by 8%–12%, while the "needle in a haystack" test still passes. Upstream report[S03] Half the memory in exchange for a measurable loss of quality: that is the typical trade-off of quantization.

4.6 Hands-on: keep books on the error

Open this chapter's interactive lab, "Bits and quantization error". It uses the symmetric uniform quantization from this chapter, not Q2_0 or any IQ format.

  2. Add an outlier and do it again. See how much sharing one scale costs.
  3. Compare two changes: "one more bit" and "groups half as big". Compare them at the same total storage, counting the bits of the scales; do not compare only the nominal bit widths.

The arrays in the lab are fixed, so you can check every result with a pencil.

Remember these three

  1. Floating point = sign + exponent + mantissa. The exponent sets the range and the mantissa sets the precision; FP16 has a small range, BF16 has coarse precision.
  2. Quantization lets a whole block of numbers share one scale s, and each number stores only how many s it is. Real bits = code bits + each number's share of the scale's bits.
  3. There are two kinds of error: the one quantization brings in on purpose, and the one from the order of floating-point operations. Both must be measured; "it did not crash" is not enough.

Common misconception: "Quantization is like zipping a file: unzip it and it is exactly the same as before."

zip is lossless compression: after unzipping, not a single byte differs. Quantization is lossy: the code remembers only "the nearest mark", and the original fraction is gone for good. Good quantization can make the loss so small that you hardly notice it, but "hardly" has to be measured. Strata's 4-bit KV cache is an example: it saves half the memory, and perplexity on long documents rises by 8%–12%. Upstream report[S03]

Go deeper: nominal bits, error bounds and two real lessons

Nominal bits are not real bits

Take a block of g = 32 weights, each with a 4-bit code, plus one 16-bit scale. The codes take 16 bytes and the scale takes 2 bytes, 18 bytes in all, which really comes to 4.5 bits per weight. Add offsets, alignment padding or indexes, and the cost changes again. So you cannot mechanically announce a VRAM need as "parameters × 4 ÷ 8": the on-disk representation, the width of the scales after loading and the GPU's temporary unpacking buffers may all differ. The per-block byte counts recorded in the source are more trustworthy than a file-name suffix. [S14]

An error bound covers one block, not the whole model

Without clipping and with round-to-nearest, no single element's error exceeds s ÷ 2. That is only a quantization error bound for one block, not a guarantee of task quality for the whole model. Nonlinearities, selection boundaries such as top-k (Chapter 10), and dozens of stacked layers all change how errors spread. So acceptance has three levels: does the format decode according to its contract; is the tensor error within budget for fixed inputs; is the quality on real tasks acceptable. "It did not crash" does not even prove the first level.

Lesson one: what was overlooked was the "width" of the scales

layer.cpp contains a comment written in capital letters. An earlier function worked out the sizes of the three blocks of a quantized tensor on its own, assuming every scale took 4 bytes. But 90 of the 303 quantized tensors store FP16 scales (all 58 Q2_0 expert tensors, plus Q4_0, Q5_0, Q8_0 and IQ4_NL), so the computed scale block was twice too big, and the three blocks did not add up to the whole tensor. The first suspicion was "the group size is wrong"; a check of all 303 tensors found not one wrong group size. The input nobody checked was the width of the scales, not the number of groups. The current approach: at load time, widen FP16 scales to FP32 and record the real size; all other code only checks, never works it out. Code fact[S14]

Lesson two: two tools agreeing does not make them right

The same file records another story: both packing tools looked for a data block named mins, but its real name was offsets. As a result, the offset blocks of 54 Q4_K/Q5_K tensors were left out, the memory regions were sized without them, and the bytes were never copied in: 136 MiB short. The comment's conclusion is worth remembering: two tools agreeing counts as evidence only if they do not share the same wrong assumption. What finally caught the bug was exactly the check that "rejects on mismatch and never guesses". [S14]

The format follows the type, not the name

During development there was an assumption that "the name decides the format": for example, that attn_qkv is always one particular K-series quantization. In fact one name is spread across many formats in different layers. Among the attn_qkv tensors of the 36 GDN layers, 13 are IQ4_XS, 18 are Q3_K, 1 is Q2_0 and 4 are Q4_K. So the rule was changed to go by type: 2-bit codes pair with Q8_0 activations, and other quantized formats pair with Q8_K. Pair them wrongly and the GEMV result is off by 0.6%–1.4%: a "reasonable-looking" vector, not an obviously broken one. [S14]

Details in 8-bit activation quantization that "look like bugs but are not"

Q8_K activation quantization copies ggml's reference implementation, including two spots that look like typos: the scale uses −127 ÷ max rather than −128 ÷ max; and max is "the signed value of the element with the largest absolute value", so a positive maximum is mapped to −127. The comment says that writing −128 instead of −127 brings a 0.79% scale error, the same order of magnitude as the quantization step, and so produces an activation that "looks usable". quantize_act.hpp
