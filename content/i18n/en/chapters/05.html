You might have noticed

Graphics cards advertise trillions of operations per second. Yet running a large language model on the same card produces only dozens of tokens per second. By operation count, generating one token shouldn't take nearly that long. Where is the time going?

A comment in Strata's source code states plainly that the engine is "bottlenecked by launch overhead, not bandwidth". Another says that GEMV accounts for only about 16% of a token, so optimizing it by a few percentage points "won't move the needle on the total". Code fact[S13][S14] This chapter teaches you three ways to measure where the time goes: bandwidth vs. latency, the roofline model, and Amdahl's law.

In one line: the time to run a computation is at least the longer of "arithmetic time" and "data transfer time"; when writing answers, data is large and arithmetic is small, so you stall on data transfer. Before optimizing, measure how much each part costs: if one part is only 16% of the total, even making it infinitely fast speeds up the whole system by only 19%.

5.1 The GPU is so fast—why do tokens still come slowly?

Imagine a chef with lightning-fast hands. But the ingredients have to be carried up from the warehouse downstairs, trip after trip. As long as supplies lag behind, the chef must wait, no matter how sharp the knife. A GPU's arithmetic units are the chef; VRAM and RAM are the warehouse; the number of bytes per second a channel can carry decides whether the chef can stay busy.

When writing answers, generating each token requires reading the weights for that step once. Chapter 10 calculated that the expert data alone is about 664 MB. Strata's source records a measurement: on that test machine, reading experts from main memory reaches 44.14 GB/s. Code factexpert_source.hpp If every token reads all 663.6 MB of expert data from RAM, just that transfer takes 663.6 MB ÷ 44.14 GB/s ≈ 15 ms, capping the output at 66 tokens per second, before any arithmetic. Teaching estimate

This is why Strata puts hot experts in VRAM (much faster reads) and lets the CPU compute experts in RAM in-place (data never crosses PCIe). Real-world testing shows output speed of about 93 tokens per second (RTX 5070 with 12 GB, Q2_0, 4K context, engine 0.1.26, speculative decoding enabled), above the "read everything from RAM" ceiling just calculated. The reasons are two: many experts never get read from RAM at all; speculative decoding can produce more than one token per step (Chapter 18). Upstream report[S03]

Bandwidth and latency

Chapter 1's storage hierarchy sidebar mentioned these two terms; here they become a formula. Latency is "how long to wait for the first byte after the request"—like how long a package takes to ship. Bandwidth is "how many bytes per second after it starts moving"—like a truck's cargo capacity. The time to transfer a batch of data is roughly:

Transfer time ≈ latency + data size ÷ bandwidth

Which term dominates depends on data size, as Figure 5-1 shows. Small packages are almost pure latency: transferring 1 KB and 2 KB take nearly the same time. Large packages are almost pure bandwidth: 664 MB is determined entirely by bandwidth. So to optimize small, frequent operations, find a way to reduce the count; to optimize large transfers, raise bandwidth or move less data.

5.2 Two ceilings: the roofline model

Put "arithmetic" and "data movement" in the same picture. Say a computation does F floating-point operations, moving D bytes through some storage level; the hardware can do at most P operations per second and move at most B bytes per second through that level. Ignoring other overhead, time is at least:

T ≥ max(F ÷ P, D ÷ B)

The larger of the two terms wins. Now define arithmetic intensity I = F ÷ D: how many operations per byte moved. The speed you can achieve is pinned by two "ceilings": operations per second ≤ min(P, B × I). Plot this and it looks like a roof shape, called the roofline model, shown in Figure 5-2.

Compute and roofline

Compute throughput is how many floating-point operations per second, measured in FLOPS; 1 TFLOPS is one trillion per second. The roofline model says: how fast you run depends on which ceiling it sits under. The two ceilings meet at a point called the ridge, located at I = P ÷ B. Below the ridge, you are bandwidth-limited: no amount of compute power helps while waiting for data; above it, you are compute-limited: data is plentiful, arithmetic is the bottleneck.

Take a matrix-vector product to compute I. Each weight multiplies each input once, adds the result once—2 operations per weight; if weights are FP16, that is 2 bytes per weight. Computing 1 token at a time, I = 2 ÷ 2 = 1. Assume P = 50 TFLOPS (teaching assumption) and B = 672 GB/s; the ridge is around 74. At I = 1, you can achieve at most 0.672 TFLOPS, under 2% of the limit. Teaching estimate

Two cautions. First, D must specify which storage level the bytes cross: VRAM, RAM, PCIe, or disk. Using VRAM bandwidth to compute transfer time through RAM is like applying a highway speed limit to a country road. Second, this is a lower bound, not a prediction: real time is extended by kernel launch overhead, synchronization, irregular access patterns, insufficient parallelism, page faults, and serial dependencies.

5.3 One person eating, a table of people eating

One dish is served. Whether one person eats it or the whole table, the person serving exerts the same effort. But the number fed differs by ten times. Weights work the same way: read them once, feed them to 1 token, or to 32 tokens, and the transfer cost barely changes.

A concrete example: Teaching estimate suppose a linear layer has about 8 million weights, 2 bytes each, about 16 MB total. Computing 1 input: about 16 million operations, I ≈ 1. Computing 32 inputs at once—same weights read once—about 512 million operations, weight traffic still about 16 MB, I ≈ 32. Inputs and outputs add their own traffic, so this is approximate; the scale doesn't change.

This is the root cause of Chapter 1's "prefill is fast, decode is slow". During prefill, a long prompt is computed in one pass, and one set of weights is shared by thousands of tokens; during decode, each step computes just 1 token. Upstream measured on the same machine: a 4K context takes 1,299 tokens per second to prefill but only 93.0 per second to decode (RTX 5070 with 12 GB, Q2_0, engine 0.1.26). Upstream report[S03] Do not expect both modes to follow the same "time per token" rule.

Quantization also raises I: the same weights fit in fewer bytes, so the same bandwidth feeds more arithmetic. The Q2_0 from Chapter 4 shrinks each weight to 0.28125 bytes, raising I from 1 to about 7 for 1 token. The cost: each weight must be unpacked before use, extra arithmetic the roofline ceilings don't include.

If you studied CS: this is the "memory-intensive" versus "compute-intensive" distinction from computer architecture, and blocking (or tiling) to improve cache reuse is the same idea: make every byte read participate in more operations.

5.4 Dependency chains: some work just cannot be parallelized

Your home has both a washer and a dryer, but one load of laundry must finish washing before it can dry. More machines don't speed it up. A chain of "this must wait for that" forms a graph; the longest path from start to finish is the critical path: total time is at least its length.

Each layer in Strata has such a chain. One layer's output must be merged before the next layer can receive correct input; layers serialize strictly. The source code comment is clear: the CPU compute for unmatched experts "cannot be hidden in a strictly serial residual chain". While that CPU time runs, the GPU can only parallelize the shared experts, because everything downstream depends on the expert result. Code fact[S13] See Figure 5-3.

For two parallel paths A and B, time for this phase is roughly max(TA, TB) plus merge time; for serial steps, it is TA + TB. To address the CPU part, Strata's answer is not "hide it better" but "put more experts in VRAM cache so the CPU has less to compute" (Chapters 10 and 12). The comment says exactly: for the CPU item, the answer is VRAM caching in phase 3, not overlap in the pipeline. [S13]

Beware one illusion: "both started at the same time" does not mean "they really overlap". Strata added a diagnostic counter just for this—it counts whether the CPU begins while the GPU is still running, or after the GPU finishes. Both cases yield correct tokens and identical per-layer time; only this counter reveals whether overlap actually happened. Code fact[S13]

5.5 Optimizing one part—how much faster is the whole?

Suppose you speed up the part that takes 20% of total time by 2×. How much faster is the system? Not 2×, not 1.2×. New time = 80% + 20% ÷ 2 = 90%, so the whole thing is 1.11× faster. The interactive plot below lets you try any two numbers:

Amdahl's law and critical path

Speed up the fraction f of total time by s×, leaving the rest unchanged. Overall speedup is:

S = 1 ÷ [(1 − f) + f ÷ s]

This is Amdahl's law. Let s go to infinity: S approaches 1 ÷ (1 − f). When f = 16%, the limit is 1.19×; when f = 50%, it is 2×; when f = 90%, it is 10×. The lesson is simple: the return on optimization depends on "what fraction does this part occupy", not "how many times faster did we make it".

Critical path is its partner. Amdahl says "optimizing small parts yields little"; critical path says "optimizing parts not on the longest chain yields nothing"—it has no effect, because total time is set by the longest chain, and faster side chains just finish waiting earlier. So the first step of performance analysis is always: measure the timeline, find which steps sit on the critical path, and measure each.

Further reading: Wikipedia: Amdahl's law · Wikipedia: Critical path method · CUDA C++ Best Practices Guide (includes Amdahl's law section)

Strata's source has a textbook example. Developers found that changing thread count from 32 to 64 per line raised bandwidth—seeming "free speedup". Yet measurements showed: with experts, 64 threads gave 11.75 tokens/s, 32 threads gave 11.99; without experts, 20.19 vs. 20.26, noise-level difference, even slightly worse. The comment explains by Amdahl's law: GEMV is about 16% of a token; a few percentage points there move the needle zero. Code fact[S14] Note: these token/s numbers are from early development and cannot be directly compared to today's speeds.

The same code measured the real heavyweight: launch overhead. A tiny kernel that processes only 48 numbers still takes about 0.028 ms, because that is the cost to launch a kernel on this machine. One layer of GDN launches about 19 kernels; a block runs about 45. Record 43 nodes from one block as a CUDA Graph and replay it: time drops from 2.393 ms to 1.585 ms, 1.51× faster, all overhead gone. 5.6 Match metrics to experience, then optimize

Last, clarify terms often mixed up. Time to first token (TTFT) is the span from request to seeing the first token—includes queueing, templating, tokenization, prefill, and first-step generation. Output speed is generated tokens divided by generation time, not "final character count ÷ total wall time". When many users share a system, there is also overall throughput: tokens per second across all users. One system can have high throughput but make each user wait long; it can be fast on short requests but queue long ones indefinitely. So Chapters 25 and 27 cover queueing and percentiles—a single token/s number is never the whole story.

Hands-on: open this chapter's interactive lab "Compute or bandwidth?".

  1. Enter the operation count, data size, compute throughput, and bandwidth; watch the bottleneck shift from data to compute.
  2. Add "unavoidable launch time"; see how it raises the lower bound.
  3. Speed up one phase 2×; observe why the end-to-end time does not speed up 2×.

When reporting results, write all assumptions and units before the numbers; title it "theoretical lower bound" or "teaching estimate". Numbers from plugging a card's peak throughput into the formula are not "measured on that GPU".

Remember these three

  1. Time is at least max(arithmetic ÷ compute throughput, bytes ÷ bandwidth); specify which storage level the bytes cross. During decode, intensity is small, so data transfer dominates.
  2. Computing many tokens at once reuses the same weights multiple times, raising intensity, until you hit the compute ceiling. That is why prefill is ten-plus times faster than decode.
  3. Before optimizing, measure the timeline: parts not on the critical path help zero, parts that are small help little (Amdahl's law).

Common misconception: "Double the GPU compute, double the generation speed."

During decode, speed is constrained by data transfer and the dependency chain, not compute. Doubling compute just leaves it more idle. For Strata, VRAM size matters more than GPU speed: upstream says larger VRAM beats a faster card; more VRAM holds more experts, each expert held in VRAM means the CPU computes one fewer. Go deeper: lower bounds, overlap, and how to report performance

Lower bound is not prediction

The roofline bound T ≥ max(F ÷ P, D ÷ B) is just that: a lower bound. Real T is extended by kernel launch overhead, synchronization, irregular access, insufficient parallelism, page faults, and serial dependencies. Even when one cost is zero, you cannot hit all peak values at once. D must specify the storage level: VRAM, RAM, PCIe, or disk. Different storage levels mean different I for the same code.

Example: same weight matrix, single batch and large batch

Teaching scenario: a linear layer with about 8 million weights, 2 bytes each, about 16 MB. One input vector: about 16 million operations, I ≈ 1. Thirty-two inputs at once, same weights read once: about 512 million operations, weight traffic still 16 MB, theoretical I ≈ 32. Activations and outputs add traffic, so this is a simplification; the order of magnitude holds. It explains why decode's GEMV and prefill's GEMM should not be judged by the same token/s metric.

Overlap must be proven with a timeline

For two parallel paths A and B, time for this segment is roughly max(TA, TB) + Tmerge; for serial steps, TA + TB. Saying "they launched together" instead of measuring actual overlap is a common performance analysis error. Strata's session code shows how to detect it: if the host reads "this layer is done" at the same time the GPU event query shows completion, then that layer finished long ago—the CPU started while the GPU was idle, so the "pipeline" is really serial. This shows in no return value and no per-layer timing; a separate counter is needed. [S13]

Amdahl's two numbers

If GEMV is 20% and sped up 2×, total time becomes 0.8 + 0.2 ÷ 2 = 0.9, overall speedup only 1.111×; even at infinite speed, the ceiling is 1.25×. True optimization depends on "what fraction of the target workload's critical path"—not how pretty the microbenchmark looks.

Metric definitions must be complete

TTFT may include queueing, templating, tokenization, prefill, first-step generation, and network transit. Report fully which are included. Output speed: is it generated tokens ÷ generation time, or something else? Upstream speed tables spelled it out: hardware and specs, model and quantization, context length, engine version, how many runs, mean or median. [S03] And note: speculative decoding speed varies with text content; one prompt's different answers can differ by a few percent. [S03]
