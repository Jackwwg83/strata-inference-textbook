You may have noticed

The same big file takes a while to open the first time, yet the second time it opens almost instantly. Here is something stranger: "open" a 30 GB model file with mmap and the call returns in the blink of an eye, even though not one byte has been read from the SSD yet.

A model file is one big block of bytes. The engine wants tensors, each with the right shape and the right type. This chapter covers the road in between: what the file holds, why "opening" and "reading into memory" are two different things, and how the engine proves that the bytes it read are exactly the bytes it thinks they are.

In one line: a model file must pass three gates before it becomes usable tensors: understand the directory, prove each tensor lies entirely inside the file, and get the bytes actually into RAM. A mistake at any gate can be silent, so Strata checks actively at every gate. It would rather refuse to start than compute with the wrong bytes.

6.1 What is inside a model file

Think of a model file as a book. The cover gives the title and the edition; next comes a table of contents that tells you on which page each chapter starts; the body text comes last. Strata reads the GGUF format, the common model file format of the llama.cpp ecosystem, and it is built exactly like that. See Figure 6-1.

Metadata is "data about data", such as which architecture the model uses and how many layers it has. The tensor directory records five things for each tensor: its name, its number of dimensions, the length of each dimension, the data type it is stored in, and the byte in the data section where it starts.

Strata's GGUF reader starts checking the moment it opens the file. Code fact The first 4 bytes must be "GGUF" and the version must be 3. In the metadata, the architecture must be qwen4exp, and the layer count 48, the width 2560, the 24 attention heads and the 2 KV heads must all match. If any item is off, the reader names the exact key, the expected value and the actual value, then refuses to run (gguf_reader.hpp lines 423–427 and 573–603). This engine is written for one model only, and "it more or less runs" is more dangerous than an outright error.

Once you know the shape and the type, you can work out how many bytes a tensor takes. Strata's main format, Q2_0, packs 64 numbers into 18 bytes, which is 2.25 bits per number. Code fact (gguf_reader.hpp lines 120–121 and 213–216) A 2560 × 640 expert matrix has 1,638,400 numbers, that is 25,600 blocks, which take 25,600 × 18 = 460,800 bytes. An expert has three such matrices, 1,382,400 bytes in total, exactly the expert size hard-coded in the source. Teaching estimate[S06]

6.2 "Opened" is not "read in": mmap and the page cache

There are two ways to read a file. The first is "make a photocopy": call read, and the operating system copies the bytes you asked for into memory you prepared. The second is "get a library card": call mmap, and the operating system hands you a range of addresses and says "these addresses stand for that file". When the bytes really move up from the SSD is decided later, when you use them.

Files, memory mapping and the page cache

A file is a named run of bytes on the SSD. A program cannot do arithmetic on the SSD directly; the data must first come into RAM. The operating system manages memory in units called pages, commonly 4 KiB each.

Memory mapping (mmap) "hangs" a file onto the process's address space: address base + i corresponds to byte i of the file. When the mapping is set up, the operating system only records this correspondence; it reads no data. The first time the program touches a page, the hardware finds the page is not in RAM yet and raises a page fault. The operating system takes over, reads that page in from the SSD, and lets the program carry on. The program never notices the pause at all; that one access is simply slower.

Pages that were read in are not thrown away at once; they stay in the page cache. When the same file is accessed again, the data comes straight from RAM. That is why "the second open is much faster". When RAM runs short, the operating system reclaims clean pages that have not been used for a while, and reads them from the SSD again if they are needed later. Figure 6-2, after this primer, draws these three layers.

How this ties into the chapter: Strata uses mmap to read the GGUF file header, and it generally uses mmap to read experts in low-memory mode too (see Section 6.3 for the exception). So "the mapping succeeded" only means the addresses are ready. It does not mean the data is in RAM, much less that later accesses will not stall on the SSD.

Further reading: Wikipedia: Memory-mapped file · Wikipedia: Page fault · Wikipedia: Page cache · Linux manual: mmap(2) · OSTEP Chapter 21: Beyond Physical Memory

On Linux, Strata's GGUF reader uses mmap to map the whole file read-only; on Windows it uses the matching MapViewOfFile. It then parses the file header at the mapped address. Code fact (gguf_reader.hpp lines 376–408)

If you studied CS: this is demand paging from your operating systems course. mmap turns "file I/O" into "memory access", and the page fault handler does the read for you. Chapter 14 goes into virtual memory and page tables.

The page cache is a good helper, but it decides by its own rules what to keep and what to drop. What happens when those rules do not match the way you access data? Strata's source records a real lesson. Code fact An early version gave the operating system a "random access" hint when it opened the expert file on Windows. This hint makes the system turn off read-ahead and drop pages it has read as soon as it can, on the theory that "in a big file read at random, what was read will not be read again". The expert file is the exact opposite: the experts each token picks look random, but the bytes read for one token are almost all read again for the next. The result: speed fell to 1.93 GB/s, each token took 344 ms, and after 25 tokens it still had not warmed up, because pages were evicted as fast as they came in. The comment's conclusion: the right hint is no hint; what matters is whether the pages stay (expert_source.cpp lines 819–829).

6.3 Where Strata puts the bytes: copy, map, direct read

The same engine stores different data in three completely different ways; see Figure 6-4. The choice comes down to two questions: is this data read again and again for every token? And does it fit in RAM?

Normal mode: copy it in, lock it. With enough RAM, all the experts (23–50 GB, depending on the quantized version) are copied into RAM and their pages are locked. Upstream report[S03] Locking a page tells the operating system: these pages may not be swapped out to disk. Once they are locked, the GPU can fetch data straight from this memory by DMA, with no CPU hand-off in between. [S06] The platform layer's lock function calls mlock on Linux and VirtualLock on Windows. When only part of the memory gets locked, it reports that honestly instead of pretending to succeed. Code fact (platform/memory.hpp lines 1–24)

Low-memory mode: map it, let the page cache manage it. When RAM cannot hold all the experts (engine 0.1.26 and later), the installer maps experts.bin in the model folder instead. Experts the GPU does not cache are managed by the operating system's file cache and can be handed back when RAM runs short. When a memory budget is set (--resident-budget-gib), the hottest experts are copied into RAM and the rest are read from the file. If the memory left cannot even keep the bytes that must be read, the engine stops using the mapping and instead bypasses the page cache and reads the experts straight from the drive. The Windows rule is that the page cache must be able to keep all the bytes to be read. Since v0.1.40, Linux also reads directly like this, using O_DIRECT, but with a much looser condition: if the page cache can keep only about 1/20 of them (at least 1.5 GiB), it keeps using the mapping. The reason is that these reads are very skewed: the hottest experts are already in the GPU and RAM, and among the remaining reads the same small group of experts keeps coming back, so caching a small part catches most of the repeated reads. Set STRATA_UNBUFFERED_LOAD=1 or 0 to force one side. Code fact (expert_source.cpp lines 419–423 and 439–443; platform/memory.hpp lines 35–54) Upstream reports that for the Coder version, the engine's committed memory fell from 36 GB to about 13 GB with identical answers; but with a small GPU, most experts must be read from the SSD, which is much slower. Upstream report[S03]

The n-gram table: keep it out of RAM, read the SSD directly. The default table has 320,001,536 rows at 90 bytes per row in the IQ4_NL format, about 28.8 GB (26.8 GiB) in total. Code fact Since v0.1.40, the reader also accepts tables in Q4_0, Q5_1, Q8_0, BF16 and other formats, at 90 to 320 bytes per row (ngram.hpp lines 44–58). The reader is designed to never take up RAM, not even page cache: every row is fetched straight from the SSD with an unbuffered 4 KiB read. Each token reads 16 rows, spread over 16 different pages (ple_reader.hpp lines 1–5). The low-level direct-read module states why: a memory mapping cannot keep the promise "stay out of the page cache", while an unbuffered read can. The price is that the offset, the length and the buffer address must all be multiples of 4096 (direct_file.hpp lines 3–9). Chapter 11 explains what this table is for.

6.4 Every tensor goes through a security check

The directory says "tensor X starts at offset o and is n bytes long". Can the engine trust that? The file may have been cut off halfway through the download, corrupted by some other tool, or be a file for another model altogether. Before the engine reads a tensor, it must first prove that the range [o, o+n) lies entirely inside the file.

The most natural way to write it is o + n ≤ F (F is the length of the data section). But integers in a computer have a fixed number of bits. When the result of an unsigned integer computation goes past the maximum, it quietly "wraps around" to a small number. This is called overflow. If the o in the directory is corrupted into a huge number, o + n wraps around to a small number, and the check is fooled.

Strata uses a form that cannot overflow: first confirm o ≤ F, then confirm n ≤ F − o. The first step guarantees the subtraction cannot go negative, and the second step does no addition at all. Code fact (gguf_reader.hpp lines 530–536) The simulator below shrinks the integers to 8 bits so you can see the overflow:

If you studied CS: in C/C++, unsigned integer overflow is "well defined": it wraps modulo 264, with no error and no crash. It is dangerous precisely because it is quiet. Signed integer overflow, on the other hand, is undefined behavior, and the compiler may even optimize your check away.

The multiplication that computes the byte count can overflow too. A tensor's element count is the product of its dimension lengths, and four dimensions multiplied together can easily exceed 64 bits. Before Strata multiplies by each dimension d, it checks "current product ≤ maximum ÷ d". If that fails, it returns 0, meaning "this shape has no valid size". Code fact (gguf_reader.hpp lines 475–488)

That is only part of the security check. The same reader also rejects files where: two tensors share a name (otherwise a lookup lets whichever comes first win, and the wrong tensor gets used silently); the number of dimensions is 0 or more than 4; a metadata array is longer than 224; or the data section starts past the end of the file. Code fact (gguf_reader.hpp lines 326, 437–446 and 458) Before mapping the expert file, the engine also checks that the file size is exactly the byte count the expert layout requires. Off by a single byte, and it refuses (expert_source.cpp lines 874–884).

The byte range being right is not enough; the shape must be right too. layout.hpp checks the shape of every tensor, layer by layer, at load time: is the tensor behind this name really the shape the kernel expects? The header states its goal: report the tensor name, the actual shape and the required shape at load time, instead of turning into one wrong number inside a matrix multiplication at token 4000. Code fact[S04]

6.5 Are the bytes right? Checksums and hashes

The range check answers "are the bytes inside the file?" There is one question it cannot answer: are these the original bytes? If one byte got corrupted during the download, the file size stays the same and the range check still passes. To answer that question, you need to compute a "fingerprint" of the data.

Checksums and hashes

The intuition: you ship a big box of books. How do you know nothing was lost or swapped on the way? You can count the total pages first and write the number on the box, then count again on arrival. That "total pages" is the simplest kind of checksum: one very short number that sums up a big block of data, so comparing the two sides tells you whether anything changed.

The simplest checksum adds up all the bytes. It catches "one byte changed", but not "two bytes swapped places", because addition does not care about order. Better check algorithms such as the CRC (cyclic redundancy check) are sensitive to order and are widely used to catch random errors in transfer and storage.

A cryptographic hash such as SHA-256 goes a step further. It turns data of any length into a 256-bit digest and has two properties. Change one bit of the input, and about half the bits of the digest change (the avalanche effect). And deliberately building two different files with the same digest is out of reach of today's computing power. So it catches not only accidental damage but also deliberate substitution. Figure 6-6, after this primer, is a small example.

How this ties into the chapter: for a model file of tens of GB, the file name and size only prove "there is a file of about the right size". Computing a hash over it is what proves "it is that very file".

Further reading: Wikipedia: Checksum · Wikipedia: Hash function · Wikipedia: SHA-2 · Wikipedia: Cyclic redundancy check · MDN: computing SHA-256 in the browser · OSTEP Chapter 45: Data Integrity and Protection

Strata's install script runs a full hash check on two kinds of Unsloth model files: the experimental UD-Q4_K_XL (4 shards), and UD-IQ4_XS (3 shards), which became a regular option in v0.1.39. Code fact The byte count and the SHA-256 of every shard are hard-coded in the script. After the download, it compares the byte count first and stops with an error on a mismatch. Then it reads the whole file in 16 MiB chunks and computes the SHA-256. On a mismatch it deletes the file and asks you to download it again. Hashing the 111 GB UD-Q4_K_XL once takes about 5 minutes, so the result is recorded in a "done marker" file and not recomputed on the next start (setup.py lines 235–255, 300 and 1490–1512). The other model files are not hashed; the install script reads through their tensor directories to check them instead (the comment on lines 235–236).

The hash covers "is the file right?" Once the bytes move from RAM to VRAM, they need to be confirmed once more. The expert cache has a verify_slot function: it reads back the bytes of a slot in VRAM and compares them byte by byte with the original in RAM. The comment calls it "the only thing that proves the cache holds the expert it claims to", because a right slot number with wrong bytes produces a plausible-looking wrong token. [S05] And it really did catch a problem: the first version of the startup fill used asynchronous copies that were not in the same execution order as the read-back check, and the check rejected the whole run with "slot 0 differs from the arena at byte 0". The comment's verdict: this is exactly the check doing its job. Code fact[S05]

6.6 Hands-on: practice the loader without downloading a model

This chapter has no separate lab page; the two interactive figures above are the lab. Try them in this order:

  1. In the "Page cache simulator", first set C ≥ W and run 10 tokens, then set C to W − 1. Write down both hit rates, and explain in one sentence why one missing slot drops the rate from nearly 100% to 0%.
  2. In the "Range check", fix n at 100 and drag o up from 150. Find the first o value that fools check A, and confirm your answer with o + n − 256.

Advanced exercise: design a fake 128-byte GGUF file whose directory lists three tensors. Test, in turn: a valid range, a range ending exactly at the end of the file, a range 1 byte out of bounds, a huge offset, an overflowing product of dimensions, and two tensors with the same name. The pass criterion is not "a bad file crashes". It is a human-readable reason for the rejection, before any computation starts.

Remember these three

  1. mmap only sets up the "address ↔ file" correspondence. Bytes come in from the SSD through a page fault on first access, then stay in the page cache. A successful mapping does not mean the data is in RAM.
  2. Strata chooses where to hold data by how it is accessed: experts that are read over and over and fit are copied into RAM and locked; when they do not fit, the page cache takes over; the 28.8 GB n-gram table bypasses the page cache and reads the SSD directly.
  3. Every tensor goes through a security check: the range check must be written as o ≤ F and n ≤ F − o to be safe from overflow; shapes are checked at load time; and the file as a whole is proven to be "that very file" with a hash such as SHA-256.

Common misconception: "Once mmap succeeds, the model is already in RAM."

When mmap returns, the operating system has only recorded the correspondence, and possibly not one page has been read. The real reading happens on first access, and pages read in can still be reclaimed when RAM runs short, to be read from the SSD again next time. Strata's source records exactly this: when pages are evicted as fast as they come in, speed drops to SSD level.

Go deeper: agreement is not correctness, ownership and lifetime, and whom to trust when docs and code disagree

Two tools can agree and still both be wrong

layer.cpp keeps two very valuable failure records. [S14] The first: a function re-derived on its own the sizes of a quantized tensor's three data blocks (the codes, the scale factors and the offsets), assuming each scale factor takes 4 bytes. But 90 of the 303 quantized tensors have 2-byte fp16 scale factors, including all 58 Q2_0 expert tensors. So the computed scale block came out twice too big, and the three blocks no longer added up to the tensor's total size. The first suspicion was that the group size in the manifest was wrong; an audit of all 303 tensors showed the group size was fine. The input that went unchecked was the width of the scale factors.

The second: two packing tools both looked for a data block named mins, but the real key is offsets. The two tools "agreed" in missing the offset blocks of 54 Q4_K/Q5_K tensors: the memory budget came out 136 MiB short, and those bytes were never copied in. The comment's conclusion: two tools agreeing counts as evidence only if they do not share the same wrong assumption. Today's plane_ptrs no longer derives anything itself. It only checks that the three block sizes the loader recorded add up to the tensor's total bytes, and that the "has an offset block" flag matches the offset block size, and it refuses on any mismatch. Code fact[S14]

The lesson for test design: two oracles (reference implementations that judge right from wrong) must be truly independent. One parses in order, following the format spec; the other uses hand-built fixed samples checked byte by byte. Do not let them share the same layout-deriving function and then treat "same result" as strong evidence.

One addition in the header cursor

Cursor::need, used to read the file header, is written as pos_ + n > size_ (gguf_reader.hpp lines 240–242): exactly the addition form from Section 6.4. The fixed-length fields of the header are small, so this is fine; but the string length n is read from the file. Exercise: if n is tampered with to be close to 264, can this comparison be fooled by wrap-around? Hint: even if it is fooled, the next line builds a std::string from n, and a length over the limit throws an exception. The file is still rejected; only the error message is no longer the precise "unexpected end of file". Security often rests on several layers of defense, but every layer is worth writing correctly.

What RAII can manage, and what it cannot

C++ RAII (Resource Acquisition Is Initialization) lets an object release its resources automatically in its destructor: when the GGUF reader fails partway through construction, it first unmaps and closes the file, then lets the exception out (gguf_reader.hpp lines 342–345 and 410–419). But the resources in an inference engine are not just memory and file handles. There are also VRAM, pinned memory, CUDA streams and events. A smart pointer knows only the ownership it was told about, and it will not wait for an asynchronous copy to finish on your behalf.

So an interface contract should say "the caller holds this buffer until the copy-done event is confirmed", not "pass in an address". expert_source.hpp spells out pointer lifetimes clearly. A pointer returned by a plain source is only guaranteed to live until the next blob() call. A caching source must return a pointer into the cache itself, never into a scratch area that gets reused; otherwise, while the CPU computes this expert, it may already be reading the next expert's bytes. A "temporary" expert block assembled on the fly from GGUF shards is valid only for the current layer and the one or two layers after it; to keep it longer, you must make a copy with copy_blob. [S06] Before freeing session memory, session_release must also revoke external pointers that other modules registered (such as the angle table for rotary position encoding), so that a new session does not compute with an address that was already freed. [S13]

When the docs and the code disagree, whom to trust

Strata's documentation says the n-gram table "reads a few rows through the operating system cache" (docs/HOW_IT_WORKS.md line 31), while the reader's header says "never enters RAM; every row uses an unbuffered 4 KiB read" (ple_reader.hpp lines 3–4). This book describes the source at a fixed commit and points out such disagreements as they are. When you read an open-source project, the docs are the author's intent and the code is the actual behavior. When the two disagree, go with the side you can run and test, and write down the disagreement; do not smooth it over for either side.

Why "the async call returned" does not mean "the copy is done"

When an asynchronous copy function returns, it only means the job is in the queue; the DMA engine may not have read the source buffer yet. If you reuse or free the source buffer at that moment, what gets copied may be half old bytes and half new ones. The real permission to reuse is a completion event on the same stream, or a synchronization point written into the contract. The "slot 0 differs" failure in expert_cache.hpp was, at heart, two execution orders that were not lined up. [S05]
