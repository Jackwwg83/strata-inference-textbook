An analogy first

There are two ways to take notes in a meeting. One is the stenographer: write down every sentence, the notebook gets thicker and thicker, and to find something you flip back through it. The other is the whiteboard: there is only one board of fixed size, and when new content comes in, you erase a bit of the old and rewrite a bit. The board always stays the same size.

The attention of Chapter 8 is the stenographer. This chapter is about the whiteboard: 36 of the 48 layers in Strata's model use GDN (Gated DeltaNet), and each head in each layer has just one 128 × 128 "whiteboard" that never grows, however long the conversation. With a few small examples you can work by hand, we will see clearly how this whiteboard is erased, written and read.

In one line: GDN compresses the history into a fixed-size state matrix. For each new token, it first decays the whole state, then uses the current key to read out the old value, and writes back only the difference "target value minus old value" with one outer product. The state does not grow with the context, but it is lossy, and one step in the wrong order quietly changes the result.

9.1 Two kinds of memory: flip through notes, or erase and rewrite a whiteboard

Attention keeps a key and a value for every history position and looks back when needed. The upside is that nothing is lost; the price is that the longer the context, the more it stores and the slower it looks things up (Chapter 8). GDN takes another road: it keeps no record per item, but maintains a fixed-size state and updates it once for every token. See Figure 9-1.

Recurrent neural networks and "state"

The intuition: when you count sheep, you keep just one number in your head, "how many have I counted so far". Each time you see a sheep, you add one. You do not need to remember what every sheep looked like to report the total at any moment. This "thing kept in your head" is the state.

The definition: a system updates itself at every step by "old state + new input → new state", written hₜ = f(hₜ₋₁, xₜ). A counter in a digital circuit and a finite-state machine from compiler theory both have this shape. Replace f with a trainable neural network and you get a recurrent neural network (RNN).

Two key properties. First, the state has a fixed size, so the work per step does not depend on how many steps have gone by: it is O(1). Reading a text of n words is O(n), cheaper than attention's O(n²). Second, a fixed size means lossy: the "sheep counter" can tell you the total, but not the color of sheep number 17. The classic trouble with old-style RNNs is exactly "forgetting things from long ago". Newer models like GDN ease it with a bigger matrix state and a smarter write rule, but they are still lossy.

There is also an engineering consequence: the state only moves forward. Given the state at step t, you generally cannot work back to step t − 2, because writing has already erased part of the old information. To roll back, you must save a snapshot in advance, or replay from the start.

How this ties into the chapter: each of Strata's 36 GDN layers has its own state, pushed forward one token after another.

In Strata, 36 of the 48 layers are GDN. Code fact[S04] The session state keeps a separate recurrent state and convolution history for each GDN layer. The temporary buffers for intermediate computation are one set shared by all 36 layers, but the state must be one per layer, because "recurrent" is the whole point. [S13] A GDN layer does not even have a "position" parameter: its input for each token is only that row of numbers, and what moves forward from token to token is this state (layer.hpp lines 535–537).

If you studied CS: think of a GDN layer as a state machine. The state is 48 floating-point matrices of 128 × 128, the input is the current token's vector, and the transition function is this chapter's recurrence. It is the same abstraction as a sequential circuit in digital logic: combinational logic computes the next state, and registers hold the current one.

9.2 The outer product: rewriting a whole table at once

The whiteboard is a matrix. How do you write the relation "key k → value v" into it? The answer is the outer product.

The outer product and the rank-one update

The dot product from Chapter 3 turns two vectors into one number: q · k = Σ qᵢkᵢ. The outer product does the reverse and turns two vectors into a table: row i, column j of k vᵀ is kᵢ × vⱼ. If k has 3 numbers and v has 2, the outer product is a 3 × 2 table; see Figure 9-2 after this primer.

This table has one special feature: every row is a multiple of v (row i = kᵢ × v). All the rows "point the same way"; in linear algebra we say its rank is 1. So adding an outer product to a matrix is called a rank-one update: S ← S + k vᵀ.

Why is a rank-one update good for memory? Because "reading" with the same k gets exactly v back. You read with Sᵀk: dot each column with k. If S = k vᵀ and k has length 1, then Sᵀk = v × (k · k) = v. If different keys are perpendicular to each other (dot product 0), what each one writes does not interfere with the others; if they overlap, their contents bleed into each other.

The cost is just as plain to see: one rank-one update touches every cell of the table, S × S multiply-adds; but it depends only on the current pair k and v, with no need to look back at any history.

How this ties into the chapter: for every token, GDN does one rank-one update per value head, on a 128 × 128 whiteboard each.

9.3 The Delta rule: read the old value first, write only the difference

The plainest way to write is to add one k vᵀ each time. The trouble is that if the same key is written twice, the two values pile up. Try it on a 2 × 2 whiteboard: first write "apple" (key [1, 0]) → [2, 3], then change apple to [5, 1]. After plain addition, the first row of the board is [2, 3] + [5, 1] = [7, 4], and reading it back gives [7, 4], which is neither value.

The Delta rule fixes this: before writing, read with this key to see what the board already holds (written v̂), then write only the difference "target minus old value", δ = v − v̂. On the second apple write, v̂ = [2, 3] and δ = [5, 1] − [2, 3] = [3, −2]; after adding it, the first row becomes [5, 1], and reading back gives exactly the new value. See Figure 9-3.

Real GDN has one more knob: the write strength β. The difference is multiplied by β before it is written, δ = β(v − v̂). β = 1 means "change it completely to the new value"; β = 0.25 means "move only a quarter of the way toward the new value". β must lie between 0 and 1, so the layer first passes it through sigmoid; the kernel is not responsible for this step (Chapter 7 covered this contract). [S17]

A 2 × 2 whiteboard has only 4 numbers. The more keys you write, and the more they overlap, the worse they interfere with each other: in the simulator above, write apple and banana and then orange, and orange reads back accurately while apple and banana have changed. The real whiteboard is 128 × 128, with far less interference, but the principle "fixed size = lossy" is the same.

9.4 Gated decay: one step out of order changes the result

The whiteboard also needs to "forget". When each token arrives, GDN first multiplies the whole whiteboard by a decay factor α, then does the Delta write. With α close to 1, old memories barely fade; with α close to 0, it almost starts from a blank board. Each value head has its own α, computed fresh from the current token: α = egate. [S17]

gate is computed as softplus(…) × ssm_a (layer.hpp line 14). The output of softplus is never below 0, and ssm_a is a coefficient in the model for each value head. As long as ssm_a is negative, gate is never above 0, and α lies between 0 and 1: in effect "the old memory is discounted at every step".

Here is one full step of one value head written out, where the state S is a "key dim × value dim" matrix Code fact[S17]:

  1. Decay: S̄ = α S
  2. Read the old value: v̂ = S̄ᵀ k
  3. Compute the difference: δ = β (v − v̂)
  4. Write: S′ = S̄ + k δᵀ
  5. Output: o = S′ᵀ q

The GDN header stresses that the decay must come before the rank-one update, and a test pins this down on purpose. [S17] Why does the order matter so much? Shrink the matrix to a single number and work it by hand. Take the old state S = 2, α = 0.5, k = 1, v = 3, β = 0.25 and q = 1:

  • Decay, then write (the contract): S̄ = 1; v̂ = 1; δ = 0.25 × (3 − 1) = 0.5; S′ = 1.5; output 1.5.
  • Write, then decay (wrong): v̂ = 2; δ = 0.25 × (3 − 2) = 0.25; after the write it is 2.25; multiplied by 0.5 that gives 1.125.

Both results are reasonable, finite and in range, but only one matches the model. The wrong order also discounts the new information that was just written, as if "partly forgetting something the moment you note it down". Three edge cases each check one thing: with α = 0, the old memory is cleared completely; with β = 0, nothing is written; with k = 0, no key is rewritten. Across these three cases the two orders agree in some and differ in others, which makes them a good check on whether an implementation has quietly swapped the order.

9.5 Why it can run in parallel, and why it cannot

Look back at the five-step formula and you will notice something easy to miss: for a fixed value head h and value dimension j, each step touches only the numbers in column j of the whiteboard. Reading the old value sums along the key dimension i, and the write changes only column j. Different columns never interact at all. Code fact[S17] So one thread can own one column and compute it from start to finish, with not a single synchronization barrier in the whole recurrence. See Figure 9-5.

To keep parallel threads in step when they read memory, Strata changed the storage order of the state from the reference implementation's (key dim, value dim, head) to (key dim, head, value dim), so neighboring threads read neighboring addresses. The state is a runtime buffer, not a weight, so its layout can be chosen freely; but the header warns that both layouts index the same three numbers, and mixing them up raises no error. [S17]

But "columns can run in parallel" does not mean "tokens can run in parallel". The state at step t + 1 depends on step t, so along the time direction it is still a chain. What runs in parallel is the work within one step, not the steps themselves.

The pairing of heads also matters. GDN has 16 key/query heads and 48 value heads, and value head h is paired with key head h % 16 (the remainder). [S17] Chapter 8's GQA, however, uses integer division. The two modules use exactly opposite conventions, so writing one "general multi-head mapping function" and reusing it everywhere would actually cause bugs.

Finally, the bill. The main state of each GDN layer is 128 × 128 × 48 FP32 numbers, which is 3,145,728 bytes, exactly 3 MiB; the 36 layers come to 108 MiB. Add the convolution history (10,240 channels × 3 columns × 4 bytes = 120 KiB per layer), and the total is about 112.2 MiB. Teaching estimate (sizes from [S04]; the float count per layer is in session.cpp lines 41–44) This number stays the same from the first token to token 262,144. But it is not all of the model's state: the KV cache of the QSA layers still grows with the context.

A side note: the description at the top of the GDN header says "48 layers are GDN and 12 are QSA". That adds up to 60 layers, which does not match the real 36 + 12 = 48. [S17] This book goes by the executable geometry definition and the session's state allocation, and does not treat an outdated comment as a model fact. [S04][S13]

9.6 Hands-on: a one-dimensional GDN, and how hard "rolling back" is

Open this chapter's interactive lab, "One recurrent update". It shrinks GDN to a scalar state and shows the correct and the wrong update order side by side. Three things to try:

  1. Set α = 0, β = 0 and k = 0, and verify the three edge-case properties from Section 9.4 one by one.
  2. Find a set of parameters for which the two orders give the same result; then explain why they differ in general.
  3. Go back to this chapter's "Order really matters" and drag α to 1. Do the two orders still differ? Explain why with the formula.

The fact that the state only moves forward becomes a real problem in speculative decoding (Chapters 18 and 19). The engine first guesses a few words the cheap way (Strata uses the model's built-in MTP layer), then lets the full 48 layers check them all at once, and wrong guesses must be rolled back. [S02] The KV cache is easy: the keys and values at wrongly guessed positions can just stay there, and they are overwritten the next time those positions are processed. The GDN state, however, has already been rewritten by the wrong words, and you cannot simply "roll back the counter". Strata's approach: the verify window does not touch the GDN state; once it is settled that the first n words are accepted, the inputs saved in the window are used to replay those n words, pushing the convolution history and the recurrent state forward. Code fact[S08] See Figure 9-6. One kind of window is the exception: a window with no draft and only 1 token. Its result is always accepted, so there is nothing to "take back". So since v0.1.40, on CUDA the graph of such a window advances the GDN state directly, which saves the commit that would follow (verify.cpp lines 156–158).

Remember these three

  1. GDN remembers the history in a fixed-size state matrix: 128 × 128 per value head per layer, about 112 MiB across the 36 layers, and it does not grow with the context. The price is that it is lossy and can only move forward.
  2. One step per token: first decay S̄ = αS, then read the old value v̂ = S̄ᵀk, compute the difference δ = β(v − v̂), and write it with an outer product S′ = S̄ + kδᵀ. Decay before write is the contract; the reverse also discounts the new information.
  3. Within one step, the columns of the whiteboard are independent, so they can run in parallel, one thread per column; from token to token it is still a serial chain.

Common misconception: "The GDN state has a fixed size, so the whole model's memory does not grow with the context, and it can roll back freely."

Only the state of the 36 GDN layers is fixed. The KV cache of the 12 QSA layers still grows with the context. A fixed size does not mean "reversible" either: writing has already partly erased old information, so the only ways back to an earlier state are a snapshot saved in advance or a replay from a known state.

Go deeper: the full tensor shapes, a few contracts that are easy to misread, and how to test a recurrence

One GDN recurrence step written out in full

gdn.hpp describes one step in these six lines (the state written with the reference implementation's indices as st[i, j, h]) [S17]:

  • dec = exp(gate), one number per value head; st = state × dec
  • sk[h, j] = Σᵢ st[i, j, h] × k[idx[h]][i] (read the old value)
  • d[h, j] = (v[h, j] − sk[h, j]) × beta[h] (the difference)
  • st[i, j, h] += k[idx[h]][i] × d[h, j] (rank-one write)
  • o[h, j] = Σᵢ st[i, j, h] × q[idx[h]][i] (read out)

Here idx[h] = h % h_k, with h_k = 16, h_v = 48 and S = 128. Every line touches only the column (j, h); that is the basis for "one thread per column, no barrier needed". [S17]

Four input contracts that are easy to misread

  • q and k have already been L2-normalized, and q has already been multiplied by 1/√S. The two llama.cpp paths apply this factor in different places, so the caller is responsible for it. [S17] The ε of L2 normalization is added to the sum of squares and must not be divided by the width; otherwise the result is off by √128 ≈ 11.3 (Chapter 7). [S17]
  • gate is the value before the exponential. dec = exp(gate) is computed inside the kernel. [S17]
  • The layer passes beta through sigmoid first. The kernel's contract is d = (v − sk) × beta, and what it receives must already be a fraction. Pass in the raw projection value and the write strength becomes unbounded and can take either sign. [S17]
  • v is not normalized. Only q and k are (layer.hpp line 23).

The layer's last step is y = rms_norm(o) × ssm_norm × sigmoid(z), with a separate RMS normalization per head. It is sigmoid here, not the SiLU that qwen3.5 used. [S17]

The convolution history: one more small piece of state

Before the recurrence, the 10,240 channels first pass through a short convolution of length 4. It must remember the previous 3 columns of input, ordered "oldest first": coefficient 0 of the kernel multiplies the oldest column, and the new input lands in the last column. The weights are stored in GGML's native layout, where the tap is the fastest-changing dimension, unlike the reference implementation's row-major order. [S17] These 3 columns of history, like the recurrent state, are per-layer state that moves forward with each token, and they must be handled on rollback too. [S08]

How to test a recurrence

The first kind is edge-case tests: α = 0 checks forgetting, β = 0 checks writing nothing, k = 0 checks a keyless update, plus an order test for "decay before write" (GDN's reference implementation has a property dedicated to pinning it down). [S17]

The second kind is snapshot-and-replay tests: process a fixed sequence, save the state at step t, go on for two more steps, then restore the snapshot and replay those two steps, and require the result to match an uninterrupted run bit for bit. The commit logic of speculative decoding depends on exactly this property. [S08]

The third kind is head-mapping tests: both the remainder pairing and the integer-division pairing produce correctly shaped outputs, so the tests must use data that tells the two apart, or a mix-up will never be found. [S17]

Do not try to "work back" from the final state to an earlier one. The decay may shrink some directions close to 0, and the Delta write overwrites old values; without the necessary information saved, this inverse generally does not exist.
