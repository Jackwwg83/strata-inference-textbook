You may have noticed

Your phone keyboard is good at finishing your sentences: type "the weather today" and it offers "is nice" or "looks bad" right away. It does not understand weather at all. It has simply remembered which words tend to show up next to each other.

The model Strata runs has a "phrase memory" like this too, and it is frighteningly large: a 28.8 GB table that lives on the SSD. Upstream report[S02] For every token the model generates, it fetches 16 rows from that table. This chapter answers three questions: how the row numbers are computed, how to fetch rows from the SSD quickly and cheaply, and how to keep rows you have already fetched for next time.

In one line: the model hashes the last 2 and the last 3 tokens to get 16 row numbers. Each row is only 90 bytes, yet the SSD is read in 4 KiB pages. Rows already read go into an 8-way set-associative row cache; when a set is full, a rotating pointer picks which row to replace.

11.1 The model's "phrase memory"

First, what does the table store? It is indexed by n-gram: "n tokens in a row". The last 2 tokens form a bigram, and the last 3 tokens form a trigram. If the context is "I like cats", the bigram is "like cats" and the trigram is "I like cats".

In the Strata source, the module that uses this table is called PLE, and it works in layer 1 of the model (counting from 0). Code fact[S13] Figure 11-1 shows the flow for each token. The bigram and the trigram each have 8 "heads", and each head computes one row number, 16 in total. Each row holds 160 numbers, so 16 rows joined together give exactly 2560 numbers, the model's main width. Code fact (include/strata/kernels/ngram.hpp)

The table itself is part of the model's parameters. It is named per_layer_token_embd and has 320,001,536 rows. At 90 bytes per row, the whole table is 28.8 GB (26.8 GiB). Code fact (ple_reader.hpp) That is far bigger than 12 GB of VRAM, and it is not loaded into RAM either. It just stays on the SSD.

n-gram language models

The simplest way to guess the next word is to "look at the last few words". If, in your text collection, "I like" is followed by "cats" 30% of the time and by "you" 20% of the time, you guess in those proportions. Guessing the n-th word from only the n−1 words before it is an n-gram language model. With n = 2 it is a bigram model; with n = 3, a trigram model.

The trouble is the number of combinations. With a vocabulary of V tokens, there are V³ possible trigrams. With V = 100,000, that is 10¹⁵ trigrams. Most of them will never appear even once in your lifetime, and you cannot store an entry for each one.

The model Strata runs borrows the n-gram idea but does it differently. It does not store "the probability of the next word". Instead, it stores a short run of trained numbers for each n-gram and hands them to the neural network. It also does not give every combination its own row: it uses hashing to squeeze an astronomical number of combinations into 320 million rows (next section). So this table is more like a notebook of phrases than a complete language model.

Further reading: Wikipedia: N-gram · Wikipedia: Word n-gram language model

11.2 How three tokens become 16 row numbers

The table does not contain the words "I like cats", only row numbers. The step from tokens to row numbers is a hash: it stirs any input into a number that looks random but comes out the same every time. Strata's hash has three steps: Code fact (ngram.hpp, src/kernels/ngram.cpp)

  1. Multiply: multiply each token ID by a large fixed constant, a different constant for each of the three positions.
  2. XOR: combine the products bit by bit with "exclusive or" (same bits give 0, different bits give 1). The result is a mixed value. The bigram mixes two numbers; the trigram mixes three.
  3. Take the remainder: each head divides the mixed value by its own modulus, keeps the remainder, and adds the head's starting row in the big table. Every head's modulus is around 20 million, and none is a power of 2: for example 20000003, 20000023 and 20000033.

Two details are worth remembering. First, a position with no earlier text is recorded as −1, and an "end of conversation" token cuts off all the history before it. The two history tokens are part of the sequence state and are stored "oldest first". Code fact[S13] Second, this hash runs on the CPU. It needs 64-bit integer multiplication and XOR, and a source comment quotes the reference implementation: the GPU compute framework ggml has neither operation. Code fact (ngram.hpp)

The simulator below replays the three steps with small numbers: the multipliers become 31, 17 and 7, the moduli range from 11 to 37, and each kind of n-gram has only 4 heads. The rules are the same as Strata's; the numbers are small enough to work out by hand.

Hashing has one consequence you cannot avoid: a collision, where two different n-grams produce the same row number. Do the math. This model's token IDs go up to at least 248,046 (the end-of-conversation token uses that ID) Code fact (src/program/generate.cpp), so there are more than 248,046² ≈ 61.5 billion possible bigrams, while one head has only about 20 million rows. On average, every row must "take in" more than 3,000 different bigrams. Teaching estimate Collisions are accepted by design.

Then why does it still work? One reasonable reading: every head uses a different modulus, so when two n-grams collide on one head, they most likely go separate ways on the other heads, and the 16 rows the model receives will not all be the same. Teaching estimate Try a few more contexts in the simulator and you can see this for yourself.

Hash tables and hash functions

A library has a million books. Searching by title one book at a time is too slow. Try something else: set up ten thousand shelves, "stir" each title into a number from 0 to 9999, and put the book on that shelf. To find a book, stir its title the same way and walk straight to that shelf. The stirring rule is a hash function, the structure that stores things in slots this way is a hash table, and each slot is a bucket.

A good hash function meets two requirements: the same input always gives the same bucket, and different inputs spread out as evenly as possible. The most common form is "stir, then take the remainder": bucket = h(key) mod buckets. If the number of buckets is a prime, every bit of the key affects the remainder. If it is a power of 2, the remainder looks only at the lowest few bits, and any difference in the high bits is thrown away.

When there are fewer slots than keys, two keys must land in the same bucket. This is a hash collision (the pigeonhole principle: put 10 pigeons into 9 holes and at least one hole has more than one). An ordinary hash table also stores the keys, so on a collision it compares them one by one or moves one elsewhere, and lookups stay exact. Strata's n-gram table does not store keys. It lets collisions happen and relies on the many heads to make up for each other. This idea of "store only values, no keys, and use several hash functions" is much like the count-min sketch from data structures.

One more small trap: why mix with XOR and not addition? A source comment spells it out: for two equal products, XOR gives 0 and addition gives double, a completely different result, yet both versions produce row numbers that "look valid". Code fact (ngram.hpp)

11.3 A row is 90 bytes, so why read 4 KiB?

With the row numbers in hand, the next job is to fetch the rows from the SSD. Here is the catch: the SSD is not read byte by byte but page by page. Strata reads this table with "direct reads" that bypass the operating system's cache, and every read's start, length and memory address must be a whole multiple of 4096 bytes. Code fact (include/strata/platform/direct_file.hpp) To get one 90-byte row, you must read the entire 4096-byte page it sits in. See Figure 11-3.

In the source, every read request has one of only two lengths: one page, or two pages (when the row crosses a page boundary). Code fact[S11] You can work out the share of crossing rows by hand: 4096 = 45 × 90 + 46, so any row that starts in the last 89 bytes of a page reaches into the next page. Row starts are spread roughly evenly within a page, so about 89 ÷ 4096 ≈ 2.2% of rows need two pages. Teaching estimate

A token's 16 rows land on 16 different pages. Code fact (ple_reader.hpp) With no cache, that means reading 16 × 4 KiB = 64 KiB, of which only 1,440 bytes are useful: a read amplification of about 45×. Teaching estimate When reading a long prompt, many rows may share a page. Strata merges requests for the same page into one, and sorts them by file position before reading, so the SSD sees something close to a sequential read. Code fact (src/ngram/ple_reader.cpp)

64 KiB does not sound like much. The real trouble is latency: 16 small random reads, each one waiting for the SSD to respond. A source comment records a set of measurements from development (the comment does not name the hardware). An early version used memory mapping, so the 16 rows became 16 "page faults" waited on one after another, costing 2.10–2.61 milliseconds per token. After switching to direct reads with all 16 requests sent at once, it took about 311 microseconds. Upstream report (comment in ngram.hpp) The same comment warns that if something else in the process still maps the file, direct reads slow down to 1,575 microseconds per token.

11.4 Keep a copy of rows you have read: the 8-way set-associative row cache

The same row is often needed again and again. A pair like "I like" may show up many times in one conversation. Upstream measured this on a fixed text collection: a cache of 1 million rows (the comment says about 95 MB) could save up to about 82% of the reads, and even within one long prompt, 20%–34% of the rows repeat. Upstream report (comment in ple_reader.hpp)

So Strata keeps a row cache in RAM, 1,048,576 rows by default, about 94 MB at 90 bytes per row. Code fact (ngram.hpp) All byte counts in this chapter use the default IQ4_NL table. Since v0.1.40, the engine can also read tables in Q4_0, Q5_1, Q8_0, BF16 and other formats, at 90 to 320 bytes per row. The row count stays the same and each row gets wider, so the same 1,048,576-row cache gets bigger: about 335 MB for a BF16 table. Code fact (ngram.hpp) The row cache is 8-way set associative: Code fact[S11]

  • The cache is split into many sets, each with 8 slots (8 ways). At the default size there are 1,048,576 ÷ 8 = 131,072 sets.
  • A row number is first stirred once (multiplied by a large fixed odd number, then a shift-and-XOR), then taken modulo the number of sets to decide which set it belongs to. It can live only in that set's 8 slots.
  • A lookup compares only that set's 8 slots.
  • If the row is not there, it is read from the SSD and written into the slot that the set's replacement pointer points at. The pointer then moves on by one, and after the 8th slot it wraps back to the 1st.

This "rotating pointer" is cheap: each set needs only a small counter, and nobody has to track which row was used most recently. The price is that it ignores how often a row is used; whatever the pointer reaches gets replaced. When does that hurt? The simulator below shows a worst case.

This example is built on purpose. Real row numbers are stirred before they are assigned to a set, so they rarely crowd into one set this neatly. The "hot spot" trace in the simulator also shows that when accesses concentrate on a few rows, rotation and LRU reach about the same hit rate. The simplest policy buys you a lookup that checks only 8 slots and a memory footprint that never grows. That is a good deal. Teaching estimate

If you studied CS: this is the set-associative structure of a CPU cache from computer architecture. "Row number → set number" matches the set-index bits of an address, and comparing 8 slots matches comparing 8 tags. The difference: this one is built in software, it caches rows of a table on the SSD, and each slot holds 90 bytes.

Direct-mapped, set-associative, fully associative

A cache has far fewer slots than there are things to cache, so first you need a rule: which slots may a given item go into? There are three answers, shown in Figure 11-5.

  • Direct-mapped: each item has exactly one fixed slot. Lookup is the fastest, since you check only one slot. But when two popular items fight over the same slot, they keep kicking each other out.
  • Fully associative: an item can go in any slot. This is the most flexible, but every lookup must compare against every slot, which gets too slow when there are many slots.
  • Set associative: the compromise. A rule first assigns the item to a set, and within the set it may use any slot. With W slots per set, it is called W-way set associative.

The three structures go with three kinds of miss. An item seen for the first time cannot be there: a compulsory miss. The cache is simply too small for everything: a capacity miss. Everything would fit in total, but one set is too crowded: a conflict miss. The example in Figure 11-4 is a pure conflict miss.

11.5 Do not keep the model waiting: send requests early, let another thread collect

One problem is left. Even at 311 microseconds, the model does not want to stop and wait. Luckily, the 16 row numbers depend only on the token itself, so they can be computed as soon as the token is known, and the 16 rows are not needed until layer 1. Two pieces of work sit in between: turning the token into a vector (the embedding), and the computation of layer 0. That is the window in which the reading time can be "hidden". Code fact (ple_reader.hpp)

So the read interface is split in two. As soon as a token comes out, the code calls issue (send the requests), which returns right away. Just before layer 1 needs the rows, it calls collect (get the results), and only then might it have to wait. See Figure 11-6.

Who deals with the SSD? By default, a dedicated I/O thread. It submits the read requests and collects the "read done" notices; the side that calls issue only puts requests into a queue and wakes the thread up. According to a source comment, this keeps the roughly 11-microsecond system-call cost of each file read off the main loop. A mutex protects the queue and the state. Code fact[S11] By default at most 256 read requests can be in flight at once. During generation each token needs only 16; the limit is reached only when reading a large chunk of prompt. Code fact (ngram.hpp)

One more detail may make you smile. Some SSDs drop into a power-saving state after about 250 milliseconds of idle time, and the next read then waits an extra 50–150 milliseconds. If generation hits the row cache for several rounds in a row, the SSD may "fall asleep". So the reader has a "stay awake" feature: when no read request has arrived for a while, it reads some page of the table just to keep the SSD awake. The generation program turns it on by default. Code fact (ple_reader.hpp) This "send it now, collect it later" asynchronous style is covered in depth in Chapter 14.

11.6 Hands-on: cause a collision yourself

The two simulators in this chapter do different jobs. "n-gram hash" shows where row numbers come from and how collisions happen. "Row cache" shows how set associativity and the replacement pointer work. Start with a run of "conflict" in "Row cache", note the two hit rates, then switch to "hot spot" and compare.

Then open this chapter's lab, "Cache traces and conflicts". With 16 slots and 9 odd keys that land in the same set, compare "fully associative LRU" with "8-way rotation". You can also write your own access traces: guess the hit rate first, then run it to check. Note that both the lab and the simulators assign sets by "row number mod sets" so that conflicts are easy to cause; Strata actually stirs the row number before assigning a set, so rows do not crowd together this easily.

When you are done, think about one question: if the 8 ways become 1 way (direct-mapped), how does the hit rate change for the same "hot spot" trace?

Remember these three

  1. For each token, the last 2 and the last 3 tokens are hashed (multiply, XOR, take the remainder) into 16 row numbers. The 16 rows fetched from the 28.8 GB table are joined into 2560 numbers. The table stores no keys, and collisions are allowed.
  2. The SSD is read in 4 KiB pages: even a 90-byte row costs a whole page, and a row that crosses a page boundary costs two. The hard part is the latency of 16 random reads, not bandwidth.
  3. Rows already read go into an 8-way set-associative row cache, and a full set replaces whatever its rotating pointer points at. Even when total capacity is enough, rows crowded into one set can cause conflict misses.

Common misconception: "With a 28.8 GB table on the SSD, SSD bandwidth must be the bottleneck."

Each token uses only 1,440 bytes. Even if none of the 16 rows is cached and each costs a whole page, generating 90 tokens per second reads only 64 KiB × 90 ≈ 5.9 MB per second. Common SSDs read several GB per second sequentially, three orders of magnitude more. Teaching estimate What you really have to deal with is latency: how long 16 small reads take, and whether they can overlap with computing. A source comment says it plainly: this is a latency problem, not a bandwidth problem. Code fact (ngram.hpp)

Go deeper: three kinds of "lookup", where docs and code disagree, hashing traps and what to measure

Three lookups that must not be drawn as one box

Strata has at least three things with "lookup" or "cache" in their names, and their correctness conditions are completely different. The n-gram table lookup is part of the model's numerical computation: it depends on the sequence history and reads trained table rows, so fetching a wrong row means computing a wrong answer. The prompt lookup draft guesses the next few tokens (at most 5) from text that already appeared earlier, and the big model still has to verify whether the guess is right. Upstream report[S02] The expert cache, in the default configuration, only decides whether an expert's weights are in VRAM right now; it does not change what is computed (Chapter 12). The names are similar, but a bug has very different effects: in the first, the output becomes wrong; in the second, things only get slower; in the third, the output may "look right but be wrong".

The two history tokens that PLE uses are part of the sequence state, along with a convolution-style history buffer. Code fact[S13] They must be saved and restored with the conversation; they are not a log you can throw away.

Where comments, docs and code disagree

The comment at the top of ple_reader.hpp says the row cache uses "clock eviction", but ple_reader.cpp has one rotating pointer per set and none of the "recently used" bits that the clock algorithm needs. Code fact[S11] Clock without those bits degrades into plain rotation, so the two behave the same, but when you read the code, the implementation is what counts.

Another one: the upstream docs say this table is "read through the operating system's cache". Upstream report[S02] Yet the current code's default mode is direct reading, and the comments explicitly require that this table take up no RAM, including the operating system's file cache. Memory mapping is kept only as a comparison baseline, and there is a separate option that locks the whole table into RAM. Code fact (ngram.hpp, direct_file.hpp) Docs often lag behind the code. When you hit a mismatch like this, trace it to the default configuration and the call path to confirm.

Every bug in the hash "looks right"

The comments in ngram.hpp list a string of traps: using addition instead of XOR; using "AND with a power of 2 minus 1" instead of the remainder (the moduli are not powers of 2, so these are different functions); the end-of-conversation cut must propagate to earlier positions; missing history is −1, while ID 0 is a real token; when the current token is itself the end token, it does not cut its own context; the history array is "oldest first", and reading it in the wrong direction still produces valid row numbers. Code fact (ngram.hpp, src/kernels/ngram.cpp) Every one of these mistakes yields row numbers inside the valid range, so a range check cannot catch them. The only way is to compare item by item against a "reference answer" from an independent implementation.

There is also an offset trap: the table's data does not start at byte 0 of the file, because a file header comes first. Reading from 0 gives you "header + misaligned rows", which still decode into plausible-looking numbers. So the reader takes the offset from the file header it actually parsed, and checks that the table exactly fills the rest of the file. Code fact (ngram.hpp)

A new thread does not mean faster

Moving the system calls to an I/O thread shortens the "submit time" in the main loop, but the request itself is not necessarily faster. If the model needs the row right away, the waiting just moves somewhere else. Look at a timeline of three things: when a request is submitted, when it completes and when it is consumed. There is a real gain only if independent work can be done between submitting and consuming.

What numbers to check

The reader's statistics include: rows requested, row cache hits, rows merged into the same page, read requests sent, bytes read, time collect spent blocked, and the latency of each read (the last 65,536 reads are kept, for computing percentiles). Code fact (ple_reader.hpp) To evaluate a change, report at least: the row hit rate, the pages read, the ratio of useful bytes to bytes actually read, and the p50 and p95 of the wait time per token. Sequential read bandwidth alone cannot explain the performance of sparse random table lookups. The reader also supports fault injection that "deliberately delays every read", to verify that on a slow SSD the system waits, rather than quietly using data that has not finished reading.
