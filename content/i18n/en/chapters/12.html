Picking up where Chapter 10 left off

Chapter 10 said that Strata keeps the most often picked experts in VRAM, leaves the rest in RAM for the CPU to compute in place, and swaps the experts in VRAM when the topic changes. That sounds smooth. But once you sit down to write the code, the questions pile up. Whom do you load at the start? VRAM has a few thousand slots in total; how do you split them across 48 layers? When do you swap, and whom? And what if, halfway through a swap, a token needs exactly that expert?

These are all old cache problems. This chapter uses Strata's expert cache to work through them one by one.

In one line: the expert cache starts full, filled by historical frequency, with a range of slots for each layer. After that, every 4 rounds it swaps cold experts out and hot ones in by "decayed count". During a swap it first removes the table entry, waits for the bytes to finish copying, and only then registers the new expert, so the GPU never reads a slot that is half new and half old.

12.1 Hit rate: first, name the denominator

The first number to look at for any cache is the hit rate: what share of the things you need are already in the cache. For the expert cache, a "hit" means the picked expert is already in VRAM and the GPU computes it directly. A "miss" means the CPU has to read that expert's 1.38 MB from RAM and compute it there.

Upstream measured this while building the cache. With 4,105 experts in VRAM, the per-expert hit rate was 0.6447, and ten-fold held-out evaluation gave a range from 0.6110 to 0.6750. Upstream report[S05] The same comment records another number: the share of layers where all 10 experts hit is only 0.0456. Upstream report[S05] Both numbers are called "hit rate", yet they differ by more than ten times, because their denominators differ. See Figure 12-1.

This shapes the design directly. If a fast path works only when the whole layer hits, a 64.5% per-expert hit rate does not help: such layers are only 4.6% of the total. The upstream comment draws the conclusion: do not design GPU kernels that group work by "whole layer"; let some experts of a layer run on the GPU and others on the CPU. Code fact[S05]

Hit rate and working set

Hit rate = hits ÷ accesses. It looks simple. The hard part is how to count "one access": per token, per "layer × token", per expert call, per distinct expert, or per byte? Change the denominator and the number can move by an order of magnitude. When you report a hit rate, also state the cache size, whether it was a cold start or warmed up, and what data you measured on.

A useful idea is the working set: the set of things actually used over a recent stretch of time. Say that over the last 100 tokens, layer 7 picked 60 different experts in total. Those 60 are layer 7's working set right now. If the cache can hold the working set, the hit rate is high. If it cannot, items get pushed out right after they come in, and the cache keeps moving data back and forth. This is called thrashing.

The working set drifts over time. The experts busy while you write code are not the ones busy while you write prose. So a cache has to answer two questions: who is in the working set now (statistics), and how to keep up as it changes (the replacement policy, see 12.4).

12.2 Whom to load first: a list ranked by past frequency

The laziest start is "first come, first served": once the run begins, the first few thousand distinct experts that get picked take the slots in turn, and once the slots are full nothing changes. The problem is that who shows up first depends entirely on the first prompt of this conversation. Upstream measured a hit rate of only 0.4864 this way. Upstream report[S05]

Strata prepares an expert profile in advance instead. It counts how often each (layer, expert) pair is picked over a long access trace, ranks them from most to least frequent, and fills VRAM from that list at startup. With the same 4,105 slots, the held-out hit rate is 0.6447. Upstream report[S05] See Figure 12-2.

The comment stresses one point: the list is read from a file, so you can "build the list from this prompt and score it on another prompt", and only then do you know whether it generalizes. Code fact[S05] Using the same trace both to build the list and to score it is an open-book exam, and the score comes out too high. The comment notes that the README once published 0.6573, a number measured "in sample"; 0.6447 is the held-out result. Upstream report[S05]

If you studied machine learning: this is the rule that training and test sets must be kept apart. "Counting what is popular" in a cache policy is also a kind of fitting, and it can overfit too.

12.3 Don't let the first layers grab everything: a range of slots per layer

How should the slots be split across 48 layers? Upstream fell into a trap here that teaches a lot. The early admission rule was: all layers share one counter, slots are handed out in order of arrival, and when they run out, they run out. A token walks from layer 0 onward and picks 10 experts in each layer, so 256 slots are gone by about layer 26. The later layers never get a slot, and for the whole run the cache helps only the first few layers. Code fact[S05]

The numbers in the comment are striking. With 256 slots, the run had 1,781 hits out of 60,000 accesses, a hit rate of 2.97%. On the same routing trace, an estimate gives 21.4% with 8 slots per layer and 70.4% with 64 per layer. The comment's conclusion: the cache was never short of capacity; it was short of fair allocation. Upstream report[S05]

The fix is direct. With per-layer admission on, layer l may use only slots l·q up to (l+1)·q, where q is the total number of slots divided by the number of layers, and the last layer takes the remainder. Code fact[S05] The fix changes only "who may use which slot" and nothing else. The lesson matters more than the fix: a low hit rate does not always mean the cache is too small. First check whether the allocation has got tangled up with the order of access.

12.4 Hot experts change: LRU, LFU and decayed counts

The list only covers the start. As the chat goes on, the topic changes, and so do the hot experts. To keep up, the cache must decide "whom to push out". This is called the replacement policy. First, a few classic ones.

Cache replacement policies: LRU, LFU and others

The cache is full and something new must come in, so something old has to leave. Which one?

  • OPT (the optimal policy): evict the item whose next use is furthest in the future. It is the best score possible in theory, but it needs to know the future, so it serves only as a reference.
  • FIFO (first in, first out): evict whatever came in earliest. It is simple, but it also throws out old items that are still used a lot. The rotating pointer in Chapter 11 is one FIFO per set.
  • LRU (least recently used): evict the item unused for the longest time. The reasoning: "what was used recently will probably be used again soon". It reacts fast, but it fears a "one-time scan": a run of cold items used once each can push out every hot one.
  • LFU (least frequently used): evict the item with the lowest total count. It shrugs off the odd cold item, but its memory is too good: an old favorite that built up a big count keeps its seat even after the topic has changed.
  • CLOCK (second chance): give each slot a "recently used" bit. A pointer sweeps around; when it meets a slot with the bit set, it clears the bit and lets that slot stay; only a slot without the bit gets replaced. It approximates LRU at very low cost, and operating systems often use it for paging.

LFU's flaw has a classic patch: let the counts decay over time, for example by multiplying every count by 0.7 at regular intervals. Old credit then fades slowly, and a new favorite gets a chance to overtake an old one. This kind of trick is often called "aging".

Further reading: Wikipedia: Page replacement algorithm · Wikipedia: Cache replacement policies · OSTEP Chapter 22: Swapping policies

Strata's expert cache uses exactly this "decayed count". The rules live in the generation program, and all the numbers check out: Code fact (src/program/generate.cpp, src/core/expert_source.cpp)

  1. Count: every time a layer picks an expert, that expert's count goes up by 1, whether or not it is in VRAM.
  2. Adjust on a schedule: by default, adjust once every 4 rounds. One round is one forward pass of the big model, which verifies a batch of drafts and produces one or more tokens.
  3. Swap only when it is worth it: within one layer, an expert outside VRAM is a candidate only if its count is at least 2. A candidate must lead the coldest expert in VRAM by more than 1.5 before an actual swap happens. One adjustment swaps at most 96 experts.
  4. Everyone fades: after the adjustment, every count is multiplied by 0.7.

What does multiplying by 0.7 mean? If an expert stops being picked, its count halves about every 2 adjustments (0.7² ≈ 0.49). Turned around, a single "pick", counting all the fading that follows, contributes 1 + 0.7 + 0.49 + … = 1 ÷ (1 − 0.7) ≈ 3.3 in total. The source comment uses exactly this sum to describe accumulated "heat". Teaching estimate Figure 12-4 draws the fading.

So how does this rule beat LRU and LFU? The simulator below shrinks one layer to 24 experts, with 4 picked per token and room for only 6 in VRAM, and runs all three policies on the same routing sequence. From token 30 on, the topic changes; you can also insert a "cold burst".

The simulator has only one layer and 24 experts, so its numbers do not carry over to Strata directly. What it wants you to see is personality. LRU is sharp but easily thrown off by cold data; LFU is steady but will not forget; decayed count strikes a balance between them with "scheduled adjustment + thresholds + fading". Why adjust only once every 4 rounds instead of swapping on every miss? Each swap moves 1.38 MB over PCIe, so swapping in and out often has a cost of its own. The two thresholds (a count of 2, a lead of 1.5) are there for the same reason: do not move data over a tiny difference. Teaching estimate

The long-context KV page cache (covered in Chapter 17) keeps some of the pages in VRAM. At each step, one thread block on the GPU runs a CLOCK sweep to pick the slots to replace, then copies the missing pages in from pinned memory. 12.5 During the swap: copy first, register after

Once you have decided whom to swap, you still have to actually swap. This step is where "looks fine" bugs breed most easily. The expert cache has two things: a residency table that records which slot each (layer, expert) pair is in, or that it is not in VRAM; and the real bytes inside the slots. The GPU looks only at the table: if the table says #112 is in slot 5, the GPU reads slot 5.

The copy is asynchronous: the function that starts the copy returns at once while the bytes are still travelling over PCIe (covered in Chapter 14). If you first write "#112 is in slot 5" in the table and only then start the copy, and a token picks #112 in between, the GPU reads bytes that are half new and half old. Strata's adaptive cache does exactly this. As soon as a swap starts, the outgoing expert is marked "not in VRAM" in the table; the source comment says "evicted from this moment: the CPU computes it in the meantime". The incoming expert first goes on a "pending" list, and it is written into the table only when the completion event recorded after the copy arrives. Code fact (src/program/generate.cpp)

There is a sneakier version of this bug. Upstream once used a non-blocking "has the copy finished yet?" query to decide whether to register: if finished, register; if not, try again next time. As a result, the same expert might be computed by the GPU in one round and by the CPU in the next, depending only on how fast the copy went. The GPU and the CPU round differently, so the same prompt could give different answers on two runs. The default now waits for the copy to land before the next round starts. Code fact (src/program/generate.cpp) The upstream docs also warn that to get byte-for-byte identical repeat results, you must turn off a few switches, adaptive swapping among them. Upstream report[S03]

The low-RAM "resident" mode adds one more constraint: RAM holds only the experts the graphics card does not have. So the bytes of the outgoing expert must first be copied from VRAM back to RAM, into the space the incoming expert frees up. Only then does the RAM copy keep "exactly filling in" what the GPU is missing. Upstream report[S03] The interface has a function just for this. Code fact[S06]

If you studied operating systems: this is the same idea as paging, where you "mark the page table entry invalid first, and reuse the page frame only after the write-back finishes". Every change to a mapping must wait until the data it depends on is really in place.

How do you prove that a slot holds the expert the table claims? The cache provides a byte-by-byte comparison function: read the slot back to the host and compare it with the original in RAM, one byte at a time. The comment calls this "the only thing that proves the cache holds the expert it claims". If the table index is right but the bytes are wrong, the result is a plausible-looking token, and that is exactly the kind of bug this project has paid for most. Code fact[S05]

12.6 Hands-on: race the three policies

First, in "Three replacement policies race", run all 60 tokens and note what the three strips of hit cells look like after token 30. Then turn on "cold burst" and run again, and see whose slots get scrambled. Next, in "One swap in and out", walk through the wrong order once and feel why "right label, wrong bytes" is the most dangerous case.

Finally, open this chapter's lab, "Cache traces and conflicts". Compare LRU, LFU, FIFO and 8-way rotation on the same access sequence. The policies in the lab are textbook versions, not Strata's decayed count. What they let you practise is this: with the same capacity, how far apart can different policies' hit rates be, and how do you build an access sequence that makes one particular policy lose?

Remember these three

  1. Name the denominator of a hit rate first: counted per expert it is 64.5%, counted as "the whole layer hits" it is only 4.6%. Evaluate a list on a trace it has never seen.
  2. Start full from a frequency list, with a range of slots for each layer. Global first come, first served lets the first layers grab every slot, and the hit rate drops to 3%.
  3. After that, swap by decayed count every 4 rounds (a count of 2, a lead of 1.5, everything × 0.7). During a swap, remove the table entry first, and register only after the copy has finished.

Common misconception: "A low hit rate means the cache is too small; just add VRAM."

Not necessarily. An early upstream version hit only 2.97% with 256 slots, while on the same access trace, 8 slots per layer would reach 21.4%. Upstream report[S05] The capacity barely changed; what changed was "who gets the slots". When the hit rate is low, first check whether the allocation is fair, whether the policy is tangled up with the access order and whether you are counting the right thing. Talk about more capacity after that.

Go deeper: historical comments, correctness invariants and how to evaluate

How "the cache never evicts" and "the cache swaps" can both be true

The top of expert_cache.hpp says that this file is only slot storage plus a residency table and does no computing yet, so turning the cache on can only make things slower. Code fact[S05] Its admission function also says plainly that it "never evicts", because the eviction policy must be chosen from measurements, and a placeholder policy would lead every downstream design to plan around the wrong hit rate. Code fact[S05] These comments were written early in development. Today's engine really does swap experts, but the swapping does not happen in this class: the generation program picks swap pairs by decayed count, copies the new expert's bytes straight into the old expert's slot, and then updates the residency table. When reading the code, keep "what this class does not do" apart from "what the whole system does not do".

Conditions every swap must keep

  • Every valid entry in the table points to a slot that is already completely filled.
  • A slot that a computation is reading must not be overwritten.
  • After a swap-out, the old mapping is invalid at once; the swap-in mapping takes effect only after the bytes have landed.
  • Expert blocks of different sizes (some quantization formats differ per layer) must not cross slot boundaries; once slots are sized for one layer, they are never handed to another layer. Code fact[S05]
  • In resident mode, the outgoing expert's bytes are copied back to RAM first, so the RAM copy keeps "exactly filling in" what the GPU is missing.

Sync or async: why the startup fill blocks

Normal fills are asynchronous, because the copy and the kernel that later reads it sit on the same stream, so the order holds naturally. The startup fill from the list has no such guarantee: the source data sits in ordinary RAM, and the byte-by-byte check reads it back on a separate "legacy stream", which has no ordering with the non-blocking streams. The first version used an asynchronous fill, and the check reported "slot 0 differs from the original at byte 0" and refused to run. The comment says: that is the check doing its job. So a dedicated blocking fill was added. Code fact[S05]

The list can be saved

The upstream docs say that from engine 0.1.36 on there is an optional feature: save the ranking the adaptive cache has learned as a new list, and start from it next time. The order is: experts in VRAM right now come first, then by the heat accumulated in this run, then by position in the original list. Code fact[S05] The file is first written to a temporary file and then renamed over the old one, so even a process crash leaves no half-written file behind. Code fact[S05]

How to compare policies fairly

When you report a cache policy, state at least: the total cache capacity and the per-layer split, the denominator of the hit rate, cold start versus warmed up, where the access trace came from, whether the list and the evaluation used different traces, how long recovery takes after a topic shift, and how many bytes per second are swapped in and out. A bare "70% hit rate" can neither be reproduced nor used to estimate a VRAM budget.
