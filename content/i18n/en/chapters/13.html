Something that defies intuition

Strata keeps the graphics card and the processor busy at the same time. That sounds like hiring two workers, so it should be a lot faster. Yet the upstream development notes record this story: they cut the CPU's expert work per token from 18.2 milliseconds to 10.2 milliseconds, so the CPU really did almost half as much. And the result? The total time to generate a token did not move at all. Upstream report (comment in include/strata/core/hit_hook.hpp)

Where did the 8 saved milliseconds go? This chapter starts with the personalities of the CPU and the GPU, moves on to "who waits for whom", and lands on one term: the critical path.

In one line: computing an expert is mostly reading bytes, so the CPU computes the experts in RAM right where they are. Within one layer, hit experts go to the GPU and missed ones to the CPU, and both sides compute at the same time. But each layer depends on the data of the one before, so layers must wait in line. The CPU's work cannot hide; the only fix is a cache that makes it smaller.

13.1 Two processors, two personalities

A CPU is like a few all-round master craftsmen; a GPU is like an assembly-line workshop with over a thousand workers. The craftsmen are few, but each one can handle complex work alone, deciding the next move as they go. The workshop has many hands, and it is best at "everyone doing the same simple motion at once". Figure 13-1 is a sketch.

CPU and GPU: SIMD and SIMT

A CPU (central processing unit) has few cores; the Ryzen 5 7600 in the upstream test machine has 6. Upstream report[S03] Each core is "smart": it has large caches, predicts branches and executes out of order, so it suits programs with complex control flow. A CPU can also compute several numbers at once: one SIMD (single instruction, multiple data) instruction applies the same operation to a whole row of numbers. An AVX-512 register is 512 bits wide and holds 16 32-bit floats, that is, 16 "lanes". Strata's CPU expert kernels are written with AVX-512 or AVX2. Upstream report[S02]

A GPU (graphics processing unit) spends its chip area on a huge number of simple compute units; an ordinary gaming graphics card has thousands. Its way of running is called SIMT (single instruction, multiple threads): an NVIDIA GPU groups 32 threads together (one warp), and the whole group runs the same instruction at the same time, each thread on its own data. [R01] It also comes with far more memory bandwidth: the VRAM of an RTX 5070 delivers about 672 GB/s, while dual-channel DDR5-5200 RAM delivers about 83 GB/s (Chapter 1 compares them).

What the two have in common: they show their strength only when they do many copies of the same work, each independent of the others. If every step must wait for the result of the step before, no number of lanes helps; the work moves one cell at a time. The simulator below lets you see this for yourself.

Further reading: Wikipedia: Single instruction, multiple data · Wikipedia: Single instruction, multiple threads · NVIDIA CUDA Programming Guide

If you studied CS: SIMD is simply vector instructions (SSE and AVX on x86, NEON on ARM). You can think of the GPU's SIMT as "hardware that automatically packs a group of threads into one wide vector and runs it". When threads in a group take different branches, the group has to run them in separate batches.

13.2 Why a CPU can compute experts too: it is mostly reading bytes

The GPU computes so much faster, so why does Strata dare to let the CPU compute experts? Because the hard part of computing an expert is not the math, it is the reading. One expert is 1.38 MB, and each parameter is used in only one or two multiply-adds, so the compute units spend most of their time waiting for data to arrive from RAM. The comment on the upstream CPU expert pool says it bluntly: the expert kernels are limited by memory bandwidth, 6 cores measured about 42.55 GB/s, and the speed grows almost in proportion to the number of cores. Code fact (include/strata/kernels/cpu/pool.hpp)

If the bottleneck is reading bytes, then make the bytes travel less. Chapter 10 worked it out: moving the missed experts to the graphics card over PCIe costs more than 10 milliseconds per token for the moving alone. Turn it around and send the "work" to where the data lives, and far less has to travel. See Figure 13-3.

The interface works like this: in every layer, the GPU hands the CPU side the normalized input, the IDs of the 10 chosen experts and their weights, then waits for 10 × 2560 numbers to come back. Code fact[S06] At 4 bytes per number, the input is about 10 KB and the results about 100 KB, more than a hundred times smaller than 13.8 MB. Teaching estimate

The CPU side is an expert pool: one worker thread per physical core, with the first core kept for the main loop. Each layer's 10 experts are shared out among these threads and computed at the same time. The host must collect all 10 results and add them up before the next layer can start, so every layer is a "barrier". Code fact (pool.hpp)

If you studied CS: the threads are pinned to physical cores, not to logical processors. The two hyperthreads of one physical core share the same execution units and caches; squeeze two memory-reading threads onto one core and the bandwidth halves. The source comment also records a measurement: when the main-loop thread was not pinned to its own core, the expert pool fell from 36.32 GB/s to 26.9 GB/s. Upstream report (comment in pool.hpp)

According to upstream measurements during development, before the expert cache existed the CPU had to read 663.6 MB of expert data per token. At about 40 GB/s that takes 16.2 milliseconds, while a whole token took about 53 milliseconds at the time. Upstream report[S05] The CPU's share was the single biggest cost on the whole machine.

13.3 Within one layer: hits to the GPU, misses to the CPU, both at once

With the expert cache in place, the 10 experts of a layer split into three groups: Code fact (src/core/expert_source.cpp, src/program/generate.cpp)

  1. Those in VRAM (hits): the GPU computes them directly.
  2. Of the misses, a share is picked out by a fixed ratio, and the GPU reads them over PCIe from pinned memory and computes them. The default ratio is 0.2 for Q2_0 models and 0.55 for other native formats.
  3. The remaining misses: the CPU computes them in place.

The order matters: the GPU's share is decided and published first, so the GPU gets moving first, and only then does the CPU start its own share. Code fact (comment in expert_source.cpp) The upstream docs mention that setting the PCIe share to 0 sends every miss back to the CPU, and generation gets slower. Upstream report[S03]

The simulator below draws one layer as a timeline. The numbers are a teaching estimate: each expert is 1.38 MB; the CPU reads at 40 GB/s, VRAM at 672 GB/s and PCIe at 63 GB/s; attention plus routing is assumed to take 0.25 milliseconds and the merge 0.05 milliseconds.

The first upstream version tripped over exactly this "who goes first". Back then, the GPU step that computes the hits was placed after the CPU expert pool. The CPU's work really did shrink by half (from 18.2 to 10.2 milliseconds), but the GPU's half merely moved from "beside" to "behind", and the path got no shorter at all. The fix split it into two steps: the GPU first starts computing the hit experts into a separate buffer while the CPU computes the misses; once the CPU's results reach the GPU, the two are added together. One extra buffer and one extra addition bought back real parallelism. Upstream report (comment in hit_hook.hpp) You can turn off "both sides at once" in the simulator and replay this story.

13.4 Between layers: dependence blocks parallelism

If a layer can run in parallel inside, can the GPU start layer l + 1 while the CPU is still computing layer l? No. The input of layer l + 1 is exactly the result of layer l after its 10 experts are merged. The chain hangs together link by link, as Figure 13-5 shows.

Data dependence and the critical path

When one computation uses the result of another, there is a data dependence between them (more precisely, a "read after write" dependence). Two dependent steps can only run one after the other; only steps with no dependence can possibly run at the same time.

Draw every computation as a graph: each computation is a node, each dependence an arrow. The longest chain of arrows from start to finish is the critical path. The whole job takes at least that long, however many workers you have. There are only two ways to go faster: shorten a step on the critical path, or move a step off the critical path so it runs in parallel with other steps.

The flip side: shortening a step that is not on the critical path does nothing at all. That is exactly the story from the opening: the CPU did 8 milliseconds less work, but once those 8 milliseconds were gone, the GPU's share moved up to fill the gap, and the critical path stayed just as long. It is the same idea as Amdahl's law in Chapter 5: optimize only one part, and the overall gain is capped by the rest.

Further reading: Wikipedia: Analysis of parallel algorithms (work, span and the critical path) · Wikipedia: Data dependency · Wikipedia: Critical path method

Strata's source code writes this down as a conclusion. Each layer is split into two GPU compute graphs. The first runs from attention through routing and the shared expert. The second merges the expert results and writes them back to the residual stream; it has to wait for the CPU to hand its results back before it can start, so that layer l's expert results are paired with layer l's own routing weights. The price: the only time left for the CPU and GPU to overlap is the short stretch of the shared expert. The comment says that a once-per-layer CPU expert pool cannot hide behind a strictly serial residual chain. Code fact[S13]

The cache's comment gives the numbers: the pipeline at the time hid only 1.055 milliseconds of 19.035 milliseconds of CPU work, so 96% stayed exposed on the critical path, "because the residual chain is strictly serial". So the only way out is to read fewer bytes: put some experts in VRAM, and let the CPU read only the misses. Upstream report[S05] That is why the expert cache of Chapter 12 exists.

13.5 How to prove it really runs in parallel

"The CPU and the GPU are both busy" is not the same as "they are busy at the same time". In the two cases of Figure 13-6, each side is busy for the same total time, yet the total time is very different.

Strata's session code counts exactly this. In every layer, when the host sees the "doorbell" (the GPU's signal that "routing is chosen"), it checks whether the GPU compute graph is still running. If it is, the CPU has a window that overlaps the GPU; if it has already finished, the CPU is working while the GPU sits idle, and the whole pipeline is effectively serial. This counter is called rings_mid_graph, and the comment calls it the diagnostic that "tells whether the doorbell is just for show". Code fact[S13]

The comment also spells out why it is needed: both cases produce the correct token, and each layer takes the same time; the only difference is that "the overlap hid nothing". Another counter records the milliseconds from launching the graph to seeing the doorbell, and the window the CPU can use is "the layer's duration minus that". Code fact[S13] "Overlap enabled" in a config file is only an intention; the event timeline is the behavior.

13.6 Hands-on: find the balance point

Start with this chapter's "within one layer" simulator: drag the hit rate to 0%, then to 65%, and see where the critical path moves from the CPU; turn off "both sides at once" to replay the lesson of the first upstream version; press "Set best share" and watch the two branches become equally long. Then go to "16 at a time" and run all three algorithms.

Next, open this chapter's lab, "Splitting work between CPU and GPU". It has just two branches: the CPU, and "handed to the GPU over PCIe". Change the effective rate of each side and the split ratio, and find the ratio with the shortest total time. Lab task: halve the effective rate of the PCIe branch and explain why the best split is no longer "half each". Note that both the lab and the simulator assume the two branches do not compete for resources; on a real machine, the CPU reading experts and PCIe reading pinned memory use the same memory bandwidth.

Remember these three

  1. Computing an expert is mostly reading bytes. Let the CPU compute the experts in RAM in place, and only 10 KB of input and 100 KB of results cross PCIe.
  2. Within one layer, hit experts go to the GPU, some misses go to the GPU over PCIe, and the rest go to the CPU. Both sides compute at once, and the join waits for the slower side.
  3. Layers depend on each other's data, so the 48 layers form one critical path. The CPU's work cannot hide; only the cache can shrink it. Optimizing a step that is not on the critical path does nothing.

Common misconception: "If the CPU and GPU compute together, speed doubles; if the CPU does half the work, the total time drops a lot."

Total time gets shorter only if the part you saved is on the critical path. Upstream cut the CPU's work from 18.2 milliseconds to 10.2 milliseconds and the token got no faster at all, because the GPU's share was queued behind the CPU. Upstream report Likewise, "100% GPU utilization" proves nothing: the GPU may be spinning while it waits, or computing a share that could have run in parallel. What you need to look at is the critical path and the event timeline.

Go deeper: the split formula, why it is off, and the traps of concurrency

The split formula for two branches

Let D be the expert data still to be computed. A fraction f goes to "the GPU branch over PCIe" and the rest to the CPU. Express the sustained throughput of the CPU branch as Bc bytes per second and that of the PCIe branch as Bp bytes per second, and assume the two do not affect each other:

T(f) ≈ max((1 − f)·D / Bc, f·D / Bp) + Tmerge

It is fastest when the two branches are equally long, which gives f = Bp ÷ (Bc + Bp). With Bc = 40 and Bp = 20, f = 1/3, not "half each". Teaching estimate Here Bp is not the nominal PCIe bandwidth; it is the effective rate that includes every cost of that branch.

Why the real optimum is not here

The formula assumes each branch uses its own resources, but on a real machine they compete: the CPU reading experts and the GPU reading pinned memory over PCIe go through the same memory channels; PCIe may also be carrying KV pages for a long context at the same time; and expert size, how many tokens in one verification window reuse the same expert, GPU launch overhead and how host threads are pinned to cores all change each side's effective rate. So Strata's default shares (0.2 for Q2_0, 0.55 for other native formats) come from measurement, not from this formula. Code fact (generate.cpp) The formula is good for forming a hypothesis; tuning needs a record of each branch's finish time, bytes moved and total time, then a re-check on a different set of tasks.

Is the result right? The timing adds up, but the answer is wrong

hit_hook.hpp records a textbook concurrency bug. In the first version, the "GPU computes hits first" step read the hit list that is decided inside the expert pool's callback, but that callback ran after it. So it read the previous layer's list and computed the previous layer's experts into this layer's slots. The program kept producing tokens, the timing looked normal, but compared with the reference answer, the mean KL divergence rose from 9.69×10⁻² to 1.03, and agreement on the most likely token fell from 0.867 to 0.333. The fix was to have this step take the IDs published by this layer's router directly. Code fact (hit_hook.hpp)

A race inside the thread pool

When the CPU expert pool waited for a batch of tasks, it first waited only for "done count = task count". But on a card with lots of VRAM, most experts hit, so the worker threads were often asleep; if a batch was small enough, it finished before the sleeping threads woke up. A thread that woke late could grab a task from the next batch and do the same task twice, or bump the count after the host had reset it, so "done count = task count" never became true and the GPU waited forever. The fix tags every task claim with a batch number: the task pointer is one 64-bit word holding "batch | task count | index", and a claim uses compare-and-swap that succeeds only if the batch matches, so a late thread simply cannot claim anything. Code fact (pool.hpp) The upstream docs record this hang as issue #29, fixed in engine 0.1.12.

Where a comment and the design disagree

In the second half of session.hpp there is an older comment that says "the overlap comes from a one-layer delay: the expert pool's results are consumed by the next layer". Code fact (session.hpp) The earlier comment about the two compute graphs says the exact opposite: to avoid pairing layer l's experts with layer l + 1's routing weights, the merge must stay in the same layer. Code fact[S13] When you hit a contradiction like this, trust the current call order and the tests.

The GPU and the CPU may differ in the last few digits for the same expert

The GPU and CPU kernels round differently. Which processor computes which expert depends on the cache state and the PCIe share, so running the same prompt again may not give a byte-for-byte identical answer. The upstream docs say that if you want repeatable results you can set a few switches, such as a PCIe share of 0, at the cost of slower generation. Upstream report[S03]
