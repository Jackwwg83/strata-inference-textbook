You may have run into this

The first time you start Strata, your computer can freeze up for a minute or two, and even the mouse lags. The README warns you ahead of time: at startup the model reads 35–55 GB into RAM and "locks" part of it for the graphics card. If the computer slows down or even stops responding during this time, that is normal; just wait. Upstream report[S01]

Why does memory need to be "locked"? What can the GPU do once it is locked, and what goes wrong if it is not? This chapter starts from the most basic trick an operating system plays: the memory addresses your program sees are actually "fake".

In one line: the operating system can move memory pages at any time, but the GPU's DMA engine only trusts the physical addresses it got when the job started, so memory to be copied must be pinned first. Copies are asynchronous: a function returning does not mean the data has arrived, so you wait for a completion signal. Two buffers taking turns, "copy one while computing the other", hide the copy time, as long as you wait for the "done using it" signal before every overwrite.

14.1 The memory addresses you see are "fake"

A pointer in a program, such as 0x7f3a_0000_1000, is not a real location on the memory stick. It is a virtual address. The operating system and the CPU work together to translate the virtual address into a physical address, and only then is the RAM actually read. This layer of translation lets every program believe it owns a large, contiguous stretch of memory, and it lets the operating system rearrange things freely behind the scenes.

Virtual memory and paging

The operating system cuts memory into fixed-size blocks called pages; 4 KiB is the most common size. A program's virtual address space is cut into pages, and physical memory is cut into page frames of the same size. Each program has a page table that records "virtual page → physical page frame". Every time the CPU touches memory, it looks up this table first; see Figure 14-1.

This brings three benefits: programs are isolated from each other; when memory runs short, rarely used pages can be swapped out to disk and read back when needed; and physical memory can be handed out in scattered bits while the program still sees contiguous addresses. The price: which frame a virtual page sits in right now is up to the operating system, and it can change at any moment.

Looking up the page table on every access is too slow, so the CPU has a small part that caches translations, called the TLB (translation lookaside buffer). It holds only a few thousand entries. Strata's source code does the math: 33.97 GB of expert weights cut into 4 KB pages is 8.3 million pages, more than any TLB can hold, so reading each expert keeps hitting the page table. With 2 MB huge pages it needs only a little over 16,000 pages. Code fact(include/strata/core/pinned.hpp) Sadly, on Windows an ordinary user account has no permission to use huge pages by default, so normal pages are the common case, and the engine reports at startup which kind it got. Code fact(pinned.hpp)

If you studied operating systems: this is the familiar "page table + TLB + page fault" package. This chapter cares about one side effect: the page table can change at any time, and external devices are not told.

14.2 Let the GPU do the moving: DMA and pinning

Sending data from RAM to the GPU does not need the CPU to carry it byte by byte. The GPU has dedicated copy engines. The CPU only tells one "copy from here, this much, to there", and the engine pulls the data across the PCIe bus by itself. This way of letting "a device read and write memory directly" is called DMA (direct memory access).

DMA: devices access memory directly

Without DMA, the CPU has to read every byte out of memory itself and write it to the device, and it can do nothing else meanwhile. With DMA, the CPU only issues a "work order"; the device's DMA engine carries it out and tells the CPU when it is done. Disks, network cards and GPUs all rely on it.

The key point: the DMA engine does not go through the CPU's page table. It only understands physical addresses. Before the job starts, the driver translates the virtual addresses and hands it a list of physical frame numbers. If the operating system moves a page halfway through, the DMA engine has no idea; it keeps reading the old frame, which may now hold another program's data.

So memory used for DMA must first be pinned (also called "page-locked"): you tell the operating system that these pages may not be moved or swapped out until they are unpinned. In CUDA you can allocate pinned memory directly, or "register" an existing block of memory as pinned. When you copy from ordinary (pageable) memory, the driver usually has to copy the data into its own pinned staging area first and then let DMA move it, which adds one extra copy. [R01]

14.3 "Submitted" does not mean "done"

Once the copy engine is told to move data, should the CPU stand by and wait until it finishes? It can wait or not. These are two ways of calling.

Synchronous and asynchronous

A synchronous call: when the function returns, the work is done. Like going to a service counter and standing there until it is handled. An asynchronous call: the function only "submits" the work and returns at once, while the work goes on in the background. Like ordering online: once you place the order you go do other things, and you get a notice when the parcel arrives.

The benefit of asynchrony is that you do not sit idle; see Figure 14-4. The price: when the function returns, you cannot assume the work is done. To use the result, you must wait for an explicit completion signal. In CUDA, work submitted on the same stream runs in order. Across streams, or when the host wants to read a result, you rely on an event: record an event on the stream, and once the event "completes", all the work submitted before it is done. [R01]

Further reading: Wikipedia: Asynchronous I/O · Wikipedia: Producer–consumer problem · OSTEP Chapter 30: Condition variables (producers and consumers)

Strata's source code is full of "returned does not mean done" reminders:

  • Filling the expert cache is usually asynchronous, because the copy and the computation that later reads it sit on the same stream, so the order holds naturally. Filling the cache from a list at startup has no such guarantee. The first version used the asynchronous fill, and the byte-by-byte check failed at once: "slot 0 differs at byte 0". So a dedicated blocking version was added. Code fact[S05]
  • Committing a verify window can return before the compute graph finishes, so drafting the next step can run at the same time. But any code that reads or writes the session state from another stream or from the host (a new request, a save, a snapshot and so on) must first call wait_commit(). Code fact[S08]
  • The per-layer main loop does not call a function that "waits for the whole stream to finish"; it queries an event instead. A source comment also records a trap: a pinned buffer was freed once per token, and freeing pinned memory implicitly synchronizes the whole device, so every token ended with an extra full-device wait. The fix was to allocate once at the start of the session and reuse it. Code fact(include/strata/core/session.hpp)

The SSD reads in Chapter 11 follow the same idea: as soon as a token is decided, 16 read requests are submitted, and the results are collected only right before layer 1 needs them.

14.4 Double buffering: copy while you compute

The most common use of asynchronous copies is to overlap copying with computing. Suppose you have a series of data chunks to process: each chunk is first copied to the GPU (3 milliseconds) and then computed (5 milliseconds). With only one buffer you can only "copy, then compute, then copy again". With two, one buffer can be computed while the other is being filled with the next chunk. This is called double buffering.

Let's do the math. For 4 chunks, running everything in series takes 4 × (3 + 5) = 32 milliseconds. With double buffering, the first chunk's copy and the last chunk's compute cannot overlap with anything, and every step in between costs whichever part is slower: 3 + (4 − 1) × max(3, 5) + 5 = 23 milliseconds. This formula holds only if the copy engine and the compute units really are two independent resources.

What the simulator most wants you to see is the moment of "overwrite without waiting for the signal". The correctness of double buffering does not come from "allocating two blocks of memory"; it comes from two signals: read only after the copy is done, and write only after it has been used. Each buffer is a small state machine; see Figure 14-6.

Strata uses exactly this kind of ring buffer when it reads a long prompt: experts not in VRAM go up to the GPU through a ring of pinned slots, on a separate copy stream. Code fact[S12] Each slot has two events, one meaning "copy done" and one meaning "done using it". Code fact(prefill.cpp) The helper copy threads mentioned earlier follow the same rule: job j writes into pinned buffer j mod 16 (16 buffers by default), and before writing it must wait until the DMA that job j − 16 issued from this buffer has finished. Code fact(prefill.cpp)

The size of the ring matters too. A source comment records one measurement (Q2_0, 8192 tokens per chunk): raising the ring from 96 slots to 384 lifted prompt reading from 1,153 to 1,294 tokens per second, because the next layer's experts can arrive while this layer's attention is computing. But when many experts need host copies, a big ring is actually slower, because the bottleneck is the host copy and the extra slots only take up cache space. Upstream report(prefill.cpp comment) When layers are split across several GPUs, each stage also has two pinned handoff buffers: while the next stage reads chunk c, this stage is already working on chunk c + 1. Code fact[S12] That is double buffering.

14.5 Pinning is not free

If pinning is so good, why not pin all the memory? Because pinned pages can no longer be moved, swapped out or reclaimed by the operating system when memory is tight. The more you pin, the less slack is left for the system, other programs and the file cache. [R02]

Strata is careful about this. The low-memory "resident" mode leaves 4 GiB of free memory for the system. Upstream report[S03] If you set a memory budget for it with --resident-budget-gib, then on Windows that budget is also limited by the "commit limit" (the memory the system can promise to provide). When the budget exceeds it, the engine lowers the budget and prints a message. Code fact(src/core/expert_source.cpp) On Windows, pinned memory mapped for the GPU also counts against a "shared GPU memory" budget. The source records a 63 GB machine that pinned piece by piece until the driver refused, ended up with 28 GiB pinned, filled that budget, and then every later VRAM allocation failed with "out of memory". So the engine offers an optional cap. It is not the default, though, because on a 64 GB machine pinning more caused no trouble in testing, and the cap makes prompt reading about 20% slower. Code fact(pinned.cu) There is no answer that fits every case; you have to measure on each machine.

There is also a fun parallel: the KV page cache for long contexts (mentioned in Chapter 12) keeps the full KV data in pinned memory mapped for the GPU, keeps only some of the pages in VRAM, and uses a "page number → VRAM slot" table to record which pages are in VRAM. Code fact(include/strata/kernels/kv_stream.hpp) That is almost a tiny virtual memory system: page table, page faults and replacement, all done by the GPU itself.

14.6 Hands-on: make the race show up every time

This chapter has no separate interactive lab; the two simulators are your workbench. In "Double buffering", play once each with 1, 2 and 3 buffers and note the total time. Then go back to 2 buffers, turn on "overwrite without waiting", and see which chunks are marked ✗. Next make the copy slower and the compute faster and try again: why did nothing go wrong "by luck" this time? Errors that are "sometimes right, sometimes wrong" are the hardest to track down.

In "DMA and pinning", walk through once with pinning off and once with it on, and compare the page table with the frame numbers DMA holds at steps 4 and 5.

Finally, a paper experiment: simulate double buffering with two arrays and write a test that deliberately lets the producer overwrite an array before the consumer has finished reading it; confirm the test fails. Then add the "used" signal and confirm it passes. Last, artificially delay the "done" event by a few steps and confirm the system waits instead of quietly reading half-new, half-old data.

Remember these three

  1. Program addresses are virtual, and the operating system can move pages at any time. DMA only understands physical addresses, so memory it uses must be pinned. Strata pins its whole expert arena and maps it for the GPU.
  2. An asynchronous call "returning" does not mean "done". To use the result, wait for the completion event; to reuse a buffer, wait for the "used" event.
  3. Double buffering hides copying behind computing: total time ≈ first copy + (chunks − 1) × the slower part + last compute. Pinning has a cost, so leave headroom for the system.

Common misconception: "Once the async copy function returns, the data has arrived, and I can change the source buffer right away."

The function returning only says the work has been submitted; the copy may not even have started. If you overwrite the source buffer now, the GPU may receive a mix of old and new data; if you free it, the copy may well read memory someone else now owns. Whether you can reuse a buffer depends only on the completion signal. Adding "wait 0.1 seconds" in between is not a fix either: it still fails on a slower machine and wastes time on a faster one.

Go deeper: the producer–consumer protocol, stream ordering boundaries and memory budgets

A minimal producer–consumer protocol

The producer fills in the bytes first and then publishes "ready". The consumer reads after it sees "ready" and publishes "used" when it is done. Only when the producer sees "used" may it overwrite. The teaching state machine is: free → filling → ready → reading → free. You may not jump from "ready" straight back to "free", and you may not use a plain variable or volatile in place of the ordering guarantees that cross-device work needs. Which fences, events and stream semantics to use depends on the rules of the target platform. [R01]

Stream order holds only where it is guaranteed

Operations submitted in order on the same stream are naturally ordered. Between different streams, or between a host read and the default stream, you cannot just assume an order. The startup fill of the expert cache tripped right here: the data was copied on a non-blocking stream and the check read it on the legacy stream; the two had no ordering, so the check read slots that had not finished copying. Code fact[S05] The asynchronous commit of a verify window is the same: the caller can skip the wait only if later work is on the same stream and drafting does not read what the commit writes. As soon as another stream or the host needs to read the session state, it must wait first. Code fact[S08]

The same concurrency lesson, used twice

When helper copy threads take jobs, they use an atomic variable packed as "batch number | job count | index". A thread gets a job only if the batch matches, so a late thread cannot grab a job from the next batch. A source comment says this is the lesson from the CPU expert pool hang (issue #29). Code fact(prefill.cpp) Chapter 13 tells the whole story of that hang.

Do not count the memory budget twice

A sound memory budget separates several quantities: reserved (address space taken, not yet really allocated), committed (the system promises it can provide), resident (in physical memory right now), locked (may not be swapped out), and those that also have a copy on the GPU. These quantities can point at the same physical pages, so simply adding them up counts things twice. First work out whether they overlap, then do the totals. [R02] The host also runs service processes and needs file cache, page tables, input buffers and recoverable session state; you cannot give all physical memory to the experts.

Acceptance: make rare errors show up every time

Tests must not only walk the happy path. Build these cases on purpose: the consumer is slow to answer "used" — does the producer come around and overwrite? The completion event is artificially delayed — does the system wait, or read a half-finished result? Each round's data carries an increasing generation number, and the generation the consumer reads must match the one it expects. After a timeout, that buffer must not be reused. The SSD reader in Chapter 11 has built-in fault injection that "artificially delays every read", exactly for this kind of acceptance test.
