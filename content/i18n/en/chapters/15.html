A strange measurement

A comment in Strata's source code records something odd. A tiny GPU program called gdn_gate handles only 48 numbers in total, yet every run takes 28 microseconds. The author's verdict: a kernel this small cannot really be executing for 28 microseconds. Code fact[S13]

The GPU finishes 48 numbers in the blink of an eye. So where does the extra time go? The answer is "check-in": every time the CPU asks the GPU to run a small program, it first has to go through a submission routine. Submit them one at a time, and one token needs about two thousand submissions. This chapter covers how the GPU splits up work, where the check-in fee comes from, and how Strata cuts two thousand check-ins down to a few dozen, or even one.

In one line: a small program on the GPU is called a kernel, and every launch carries a fixed overhead of tens of microseconds. Strata saves it in two ways: it fuses several kernels into one, and it records a whole layer's kernels as a CUDA Graph that is submitted in one go. The price is that a graph freezes its arguments, so the "position", which changes every step, must live in a block of VRAM at a fixed address.

15.1 How the GPU splits up work: threads, thread blocks and warps

Picture a huge exam-grading hall. There are tens of thousands of papers, and each teacher grades one. The teachers are split into many rooms, and inside each room they sit in rows of 32. A whole row follows the same call: "turn the page", "look at question one", "give a score". The call is the same; the paper in each pair of hands is different.

That is how a GPU works. A small program the CPU hands to the GPU is called a kernel. Launch a kernel once, and the GPU starts thousands upon thousands of threads. Every thread runs the same code; only the index of the data it handles differs. The threads are first grouped into thread blocks. The threads in one block run on the same compute unit and can share a small piece of fast storage. Inside a block, the threads are lined up in groups of 32 called warps: the 32 threads of one warp execute the same instruction at the same time. [R01] Figure 15-1 draws these three levels together.

Strata is full of this pattern. Take the KV paging of Chapter 17: the source says it "uses one 1,024-thread block to scan the selected indices". Code fact Or take the recurrence in the GDN layers: a source comment notes that each line of the formula touches only one column of the state, and the columns do not depend on each other, so "one thread can own a whole column, and no thread ever waits for another during the step". [S17]

The GPU programming model: threads, thread blocks and warps

Intuition: a CPU is like a few all-round professors, each able to handle complex branches and decisions. A GPU is like thousands of teaching assistants, each of whom only does simple things on command, but there are a lot of them. To make a GPU fast, you have to split the work into thousands upon thousands of small tasks that do not depend on each other.

Definition: the programmer writes a kernel function and, at launch, says "how many thread blocks, and how many threads per block". In CUDA you write vecAdd<<<4, 256>>>(A, B, C): 4 blocks of 256 threads, 1,024 threads in total, and each one uses threadIdx.x + blockDim.x × blockIdx.x to work out which element it is responsible for. On current NVIDIA GPUs, a thread block holds at most 1,024 threads, and the threads in a block form warps of 32. [R01]

A concrete number: when a warp reads VRAM and its 32 threads read neighboring addresses, the hardware can merge them into very few memory transactions. This is called coalesced access. If the addresses are far apart from each other, the read splits into many transactions, and each one uses only a small part of the bytes it fetches. The Strata example in the next section shows how big the gap is.

How this ties into the chapter: a kernel is the smallest unit of work the CPU hands to the GPU. The smaller and more numerous the kernels, the more the cost of the "handover" itself stands out.

Further reading: NVIDIA CUDA Programming Guide: Programming model · NVIDIA: Intro to CUDA C++ (with the vecAdd example) · Wikipedia: CUDA · Wikipedia: Thread block

If you studied CS: a warp is the execution unit of SIMT (single instruction, multiple threads). One instruction drives 32 threads, like a SIMD vector instruction; but each thread has its own registers and program counter and can take a different branch, at the cost of the two sides of the branch running in turn. Chapter 13 covers the difference between SIMD and SIMT in detail.

15.2 Neighboring threads read neighboring addresses: data layout matters

Same math, different data layout, and the speed can differ several times over. Figure 15-2 compares two ways of reading.

Strata's GDN layers learned this the hard way. A comment in the fused kernel explains: the original code had one warp own one column of the state, with 32 threads walking down the 128 rows. But the state is stored as "row, head, column", so two neighboring threads read data about 24.5 KB apart. As a result, each 32-byte sector fetched delivered only 4 useful bytes, and each layer took 47.6 microseconds just to move 6.3 MB of state. Code fact

After the rewrite, one thread block owns a whole head, and its 512 threads are laid out as "row group, column". The 128 columns of a row become exactly one contiguous 512-byte read. Code fact The idea is the same as in Figure 15-2: make neighboring threads read neighboring addresses. GDN's basic kernel follows the same rule: the state is stored as (i, h, j) with j changing fastest, so for a fixed i, a warp reading along j touches contiguous memory. [S17]

Data layout is a "free" choice: the state is a runtime buffer, not model weights, so you can lay it out any way you like. But the source warns that the two layouts index the same three numbers. Once the reader and the writer disagree on the layout, the program still runs, and the results go silently wrong. [S17]

15.3 Every kernel launch pays a "check-in fee"

Back to the strange measurement at the start. For the CPU to make the GPU run a kernel, it goes through the driver: check the arguments, pack the command, put it in the submission queue. This paperwork runs on the CPU and takes time. It is called launch overhead. If the kernel itself computes for only a few microseconds while the paperwork takes ten or twenty, the GPU finishes one kernel and then sits idle waiting for the next. Figure 15-3 draws this "waiting".

This is not hypothetical. A Strata comment states the conclusion outright: "this engine is launch-bound, not bandwidth-bound." Every kernel in the GDN layers measured about 0.028 ms, even gdn_gate, which handles only 48 numbers; that is exactly the cost of one ordinary launch on that machine. One GDN layer makes about 19 launches, and a full layer block about 45. Code fact[S13] The comment does not say which GPU or driver version was used, so treat the numbers below only as a sense of scale.

Let us do the math. Another comment says that launching kernel by kernel, one token needs about 2,000 launches, and each driver call measured 10–22 microseconds. Code fact The "check-in" alone costs each token anywhere from 2,000 × 10 µs = 20 ms to 2,000 × 22 µs ≈ 44 ms. In terms of speed, even if the GPU computed nothing at all, you would get at most 23–50 tokens per second. Teaching estimate

Kernel launch overhead and kernel fusion

Intuition: at a hospital, you queue to check in. If every small test needed a fresh check-in, the whole morning would vanish at the check-in window. There are two fixes: merge several tests into one (kernel fusion), or have the doctor write the whole set of test orders at once and let the nurse work through the list (CUDA Graph).

Definition: launch overhead is the fixed cost for the CPU to prepare and submit a kernel, and it hardly depends on how much the kernel computes. Say a kernel computes for w microseconds and a submission takes L microseconds. Submit n kernels one by one: if w < L, the total is about n × L + w, and the GPU spends most of its time waiting; if w ≥ L, the total is about L + n × w, and the submissions hide behind the computation. Teaching estimate

Fusion does more than save check-ins. Once several operators become one kernel, intermediate results can stay in registers or on-chip storage instead of being written back to VRAM and read out again. The price is a more complex kernel, which may use more registers and so let fewer threads run on the GPU at once. CUDA Graph, on the other hand, does not change the kernels at all: it records a chain of operations and their dependencies, then submits and replays the whole chain in one go. What it saves is the cost of submitting on the CPU side. [R01]

How this ties into the chapter: Strata uses both. The next section looks at the actual numbers.

15.4 Two ways to save: fusion and CUDA Graph

Figure 15-4 puts the two side by side: fusion changes what runs on the GPU, and a graph changes how the CPU submits.

Fusion. Strata has a set of kernels whose file names start with fused_. For example, the single kernel fused_gdn_conv_l2 replaces three launches: the old "convolution plus SiLU" and two L2 norms. fused_gdn_ab replaces two matrix-vector products and two element-wise kernels. Code fact Reading the hybrid residual used to take six kernels each time, 96 times per token; after fusion it takes two kernels. Code fact

CUDA Graph. Strata records each layer's kernels as a graph. A comment gives the measurement: the same layer block of 43 nodes takes 2.393 ms launched one by one, but only 1.585 ms as a recorded graph replay. That is 1.51× faster, and the savings are "all launch overhead". Code fact[S13] Another comment puts it even more plainly: replay does exactly the same arithmetic as launching one by one; the only difference is that "about 2,000 kernel launches become 48 graph launches". Code fact

Can it go further? Yes. Under the Windows display driver model, each graph launch itself also costs about 0.3–0.4 ms. The per-layer loop launches 96 graphs per token, and a token measured 48.6 ms, of which the real kernels on the GPU took only 12 ms. So Strata wrote another version, "one graph per token", that packs all 48 layers into a single graph. Code fact Figure 15-5 lines up the three stages.

Why not record the whole token from the start? Because in the middle of every layer, the GPU has to hand over to the CPU expert pool: only when the GPU reaches the routing step does the CPU know which experts to compute. Strata first used "one layer" as the unit of a graph precisely so the host could step in between layers, and so the CPU expert pool could start working while the GPU ran the next stretch. [S13] The whole-token graph instead uses a single-thread kernel on the GPU that waits, on the device, for the host to set a flag, so the host no longer calls the driver. Code fact

15.5 A graph freezes its arguments: the frozen position

CUDA Graph has a quirk: during capture, a kernel's arguments are copied into the graph as they are, and every later replay uses that copy. Strata wrote a small experiment just to confirm this: on replay, the graph rereads the data in its input buffers, but it does not reread kernel arguments. Code fact

The trouble is that some arguments change with every token. The classic one is the position: which token this is. If the position is passed as an argument to the kernel that writes the KV cache, it is 0 when the graph is captured, and it stays 0 on every replay after that. The simulator below slows this down. Strata's qsa.hpp spells out the damage this bug does. Once the position is frozen, every token writes to slot 0, scoring and selection look at just 1 slot, and attention only ever sees one slot of history. The comment calls it "worse than a crash": the output is finite, plausible-looking numbers, and the symptom looks exactly like "the model cannot use its context". People would suspect the KV cache, the selection algorithm or the weights, and never think of the graph. Code fact[S18]

Its fix is "one block of VRAM, not six changed function signatures": put the four numbers that change every step into a tiny step buffer:

  • step[0] = pos: the position of the new token;
  • step[1] = n_kv = pos + 1: how many slots the cache holds;
  • step[2] = n_bid: how many 4-slot blocks are already full;
  • step[3] = width: how many slots this step selects, equal to min(n_kv, 2051). [S18]

Each kernel reads the numbers it needs from this block of VRAM, the argument lists stay exactly the same from token to token, and the whole QSA path can be captured as a graph. Each step, the host does just one small copy to rewrite the content of that VRAM block. Code fact[S18] The four numbers depend on each other. Keeping them in one place, computed by one piece of code, rules out "changed pos, forgot n_kv".

If you studied CS: this is exactly the difference between "pass by value" and "pass by pointer" in C. If the graph records a value, it is that value forever; if it records a pointer, every dereference reads the new content. The catch is that the memory the pointer points to must stay valid the whole time, and the graph cannot check that for itself.

The same reasoning applies to sampling. Parameters such as temperature and top-p can differ for every request, so Strata keeps sampling outside the captured graph; otherwise those parameters would be "permanently baked into the graph". Code fact[S08]

15.6 Hands-on: find the bottleneck and the freeze yourself

Both interactive figures in this chapter work as small experiments.

  1. Launch overhead timeline (Figure 15-3): first play it with the default settings, and note the total time and the GPU busy share for all three ways. Then slowly drag each kernel's compute time w from 5 µs to 40 µs, and find the point where "the graph is no longer clearly faster". You will find it sits roughly where w gets close to L: once a kernel runs longer than a submission, the submission cost hides on its own.
  2. The frozen position (Figure 15-6): run 4 tokens with each way of writing it. Compare the KV slots and "how many slots attention can see". Then think: if you only checked "did the program report an error, and is the output a finite number", could you catch the wrong version?

To check this on a real GPU, write a tiny graph that only does state[pos] = token, replay it with pos = 0, 1 and 2, and check that all three positions were written. Looking only at a final return value of "success" is not enough.

Remember these three

  1. A GPU works with thousands upon thousands of threads: threads are grouped into thread blocks, and every 32 threads in a block form a warp. Make neighboring threads read neighboring addresses, and no data movement is wasted.
  2. Every kernel launch has a fixed overhead. Strata originally needed about 2,000 launches per token. It cuts the number of kernels with fusion, and uses CUDA Graph to bring submissions down to one per layer, then one per token.
  3. A graph freezes kernel arguments. Values that change every step (the position, n_kv, the selection width) must live in a fixed-address VRAM buffer that the kernel reads each time.

Common misconception: "CUDA Graph merges many kernels into one big kernel."

It does not. A graph only records a chain of operations and their dependencies. On replay, each node is still a separate kernel, and intermediate results are still written back to VRAM. What it saves is the cost of submitting on the CPU side. Truly merging computation into one kernel is kernel fusion, and that means rewriting the kernel. The two solve different problems, and Strata uses both. [R01]

Go deeper: the cost of fusion, three duties of graph capture, and how to verify

Fusion is not free

Writing several operators into one kernel means fewer launches and fewer writes and reads of intermediate results. The price: more variables are alive at once inside the kernel, so each thread needs more registers. The total number of registers is fixed, so the more each thread takes, the fewer threads can reside at once, and the GPU has fewer "spare threads" to hide memory waits. This is called lower occupancy. The code is also more complex and harder to test. So fusion should be decided by measurement. For example, Strata's fused hybrid-residual read has several variants. On each card, the engine first runs them with random weights and adopts only the newest variant that matches the baseline bit for bit. Code fact

A teaching example: a layer with 20 launches at 5 µs of host overhead each spends about 100 µs on launches alone. For small operators that compute for only a few microseconds, that is a lot; if each kernel computes for several milliseconds, the same 100 µs is a rounding error. These are all assumed values, meant for judging "is this worth optimizing", not measurements. Teaching estimate

Three duties of graph capture

graph.hpp writes three things down as preconditions of the interface, and each one comes from a dedicated small experiment. Code fact

  1. Waiting must call the driver, not just read memory. Under the Windows display driver model, command submission is batched. A spin loop that only read memory, without calling the driver, spun 5,907,703 times in 500 ms while the kernel never even started; the data flipped only once some code called the driver. So the wait was changed to poll an event repeatedly. Each poll costs about 0.021 ms, and it is a "query", not a "synchronize".
  2. A graph rereads input buffers, not kernel arguments. Over 8 replays, each with a fresh pinned input, the results kept up every time; but arguments are copied into the nodes during capture and never read again. Every value that changes per step (position, page-table base, token ID) must be data in VRAM, not an argument.
  3. Fixed addresses are the caller's job. The graph holds the graph, not the memory. Every buffer the captured code uses must be allocated before capture and must never be reallocated afterward.

Two more defenses are worth learning. A capture that yields 0 nodes is an error right away, because "a graph that does nothing" would replay quietly forever, producing neither errors nor output. And if a CUDA error is left inside the capture body, the capture is abandoned instead of instantiating a broken graph. Code fact

Do not take one execution path for the whole engine

Strata has several kinds of graph at the same time: SessionGraphs with one or two per layer (one stretch before routing, one after the experts are combined) [S13], the multi-token graph for the speculative decoding verification window (Chapter 18) [S08], the whole-token TokenGraph, and prefix graphs used for timing stage by stage. If one header says "one graph per layer", you cannot conclude from it that the engine never captures a bigger graph. Source code often keeps a reference path, a debug path, a fast path and implementations chosen by device capability side by side; the calling context and the conditions that enable a path are part of any conclusion. This is the same thing as "one function with several specialized versions" from a compilers course.

Verification: addresses, values and state

A graph optimization must verify at least three things: the values that change per step are updated correctly on every round; the captured addresses stay valid across all replays; and the state after a replay matches the reference path that does not use a graph. A typical lifetime trap: a buffer is freed when a request ends, but the graph object is kept for the next request, so the next replay reads and writes freed memory.

The tests must also be able to "see" the bug. Repeating the same prompt at the same temperature proves nothing about switching parameters correctly. A better way: fix the logits, run two requests in a row, one greedy and one at high temperature (or with different fixed random numbers), and compare the parameters actually used and the results against the reference implementation without a graph. The second request must take a branch that differs from the first and can be predicted.

Only advanced GPU work needs a profiler: record launch time, kernel time, register use and replay time, then use an end-to-end A/B comparison to judge whether a local optimization really shortened the critical path. Strata's comments contain a counterexample: in one round, stage timings measured in non-graph mode came out 4× higher than the real cost of the same work once captured as a graph, and nearly sent the optimization in the wrong direction.
