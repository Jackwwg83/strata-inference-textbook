Same computer, two speeds

Strata's upstream speed table has two columns of numbers. On the same computer with an RTX 5070, reading a 32K-token prompt runs at 2,171 tokens per second; writing the answer runs at only 81.8 tokens per second. Upstream report[S03]

Same model, same 48 layers, same graphics card. Why is "reading" more than twenty times faster than "writing"? The secret fits in one word: batching. This chapter explains why computing together beats computing one at a time, how big a chunk should be, and how to make moving data and computing happen at the same time.

In one line: during decode the model can compute only one token at a time, so each read of the weights is used once. During prefill the whole prompt is already known, so thousands of tokens can be computed as one chunk, and each read of the weights is shared by the whole chunk. Strata reads at most 8,192 tokens per chunk, and starts moving the next layer's experts while the current layer is still computing.

16.1 Why reading the prompt is over twenty times faster than writing the answer

Start with the numbers. Figure 16-1 shows the two speeds that upstream measured on one computer.

The upstream docs list the test setup: an RTX 5070 12 GB graphics card, a Ryzen 5 7600 CPU, 64 GB of DDR5-5200 RAM, Windows, engine 0.1.26, the Q2_0 model, and speculative decoding switched on while writing the answer. Upstream report[S03]

The gap comes from a basic difference between the two phases. During decode ("writing the answer"), the next token is unknown until the previous one has been chosen, so tokens can only come one at a time. During prefill ("reading the prompt"), every token of the prompt is already there, so a big block of them can go into the model together. Note that "computing together" does not mean "peeking at each other": the 5th token still sees only the first 4. The model's causal rule does not change at all; only the way the computation is organized changes.

16.2 Why computing together is faster: matrix × vector vs matrix × matrix

Picture a teacher grading multiple-choice tests. For each test, the teacher takes the answer key out of a cabinet, checks the test, and puts the key back. If tests arrive one at a time, most of the time goes into fetching and returning the key. If 50 arrive at once, the teacher fetches the key once, checks all 50, and puts it back; spread over 50 tests, the fetching costs almost nothing.

In a model, the "answer key" is the weights. For every layer, that layer's weights must be read from VRAM into the compute units. Figure 16-2 draws the two cases side by side.

Batching: matrix × vector vs matrix × matrix

Intuition: moving data and computing are two separate bills. If you compute token by token, you move the whole set of weights every time, and moving becomes the main cost. If you compute a batch of tokens together, you pay for the move once while the compute stays the same, so the "compute done per byte moved" goes up. Chapter 5 called this ratio arithmetic intensity; it decides whether a program is limited by bandwidth or by compute.

Definition: a layer's weights form an m × n matrix W. One token's input is a vector x of length n. Computing W·x is a matrix-vector multiplication (GEMV): it reads m × n weights and does about 2mn multiply-adds. Line up C tokens' vectors into an n × C matrix X, and computing W·X is a matrix-matrix multiplication (GEMM): it still reads m × n weights, but the compute grows to about 2mnC. The arithmetic intensity rises to about C times the original.

A concrete number: Strata's speculative decoding controller has a default table of "how many times longer does the dense part take for n tokens at once than for one token". For 2 tokens it is 1.05×, for 4 it is 1.45×, for 8 it is 3.0×. Code fact In other words, with 8 tokens together each one costs on average 3.0 ÷ 8 ≈ 38% of computing it alone. Teaching estimate

How it ties to this chapter: during prefill C can be in the thousands, which is why prefill is so much faster. Batching has a price too: it needs more temporary storage for the whole chunk's intermediate results, and each chunk takes longer to finish.

Further reading: Wikipedia: Matrix (mathematics) · Wikipedia: Matrix multiplication · Wikipedia: BLAS (where GEMV and GEMM come from)

Strata uses the same trick elsewhere. The verification window of speculative decoding sends in several tokens at once, and the source code describes this window's cost as "the dense weights are read only once and shared by T tokens". [S08] The fused read of the hybrid residual also has a multi-token version where up to 8 tokens share the weights, and "the weights are read only once for all of them". Code fact

If you studied CS: this is "locality of memory access" from Computer Architecture and the BLAS levels from numerical linear algebra. BLAS-2 (matrix × vector) is limited by bandwidth; only BLAS-3 (matrix × matrix) can keep the compute units fully busy. Prefill turns a string of BLAS-2 calls into BLAS-3.

16.3 Batching the experts: group by expert

The dense part is easy: every token uses the same weights. The expert part is trickier: each token picks 10 experts per layer, and different tokens pick different ones. Strata first groups by expert: it gathers the tokens that picked the same expert, reads that expert's weights once, and computes the whole group. [S12] Figure 16-4 shows a scaled-down sketch.

Scale it up to real size: a chunk of 8,192 tokens, each picking 10 experts per layer, makes 81,920 expert calls in one layer, yet each layer has only 512 experts. On average each expert is shared by 81,920 ÷ 512 = 160 tokens. Teaching estimate A source comment also says that once a chunk reaches 1,024 tokens or more, "almost all" of each layer's 512 experts get picked. Code fact

After grouping, where do the experts come from? Hot experts cached in VRAM are read directly. The rest travel from the expert area in RAM through a pinned-memory "ring buffer" and onto the GPU on a separate copy stream. [S12] After the computation, the results must go back in the original token order and then be added up by each token's routing weights. Put one result in the wrong place, and it gets added to some other token.

Note how this differs from decode. During decode, missed experts are mostly computed in place by the CPU in RAM (Chapter 10). During prefill each expert is shared by hundreds or thousands of tokens, so moving it to the GPU and computing them together pays off. There is one exception: for a chunk of fewer than 1,024 tokens (for example, the short output an agent reads back after a tool call), the engine hands the non-resident experts chosen by only a few tokens to the CPU expert pool, which is idle at that moment; the rest are moved over PCIe as usual. Since v0.1.41, this CPU share is on by default on a single NVIDIA card (the CUDA build, without --batch); it is still off by default with a layer split, with batch slots, and in the AMD (HIP) build. The price is that the CPU uses its own activation format, so its results are not bit-for-bit identical to the GPU's. Set STRATA_PREFILL_CPU_SHARE=0 to turn it off, and the output goes back to the bytes of 0.1.40.x. Code fact (src/prefill/prefill.cpp)[S12] Upstream tested it on three NVIDIA cards: for prompts of 512 and 1,000 tokens, the time to read the prompt fell by 20% to 34%; the KL divergence of the first token averaged about 0.004. Upstream report Note that the comment on set_cpu_pool in prefill.hpp still says "if it is not set, nothing is shared", while the comment and code of arm_cpu_share right next to it have changed to on by default. When the two disagree, go with the code. Code fact[S12]

16.4 How big should a chunk be? Is bigger always better?

The prompt is cut into chunks and read one chunk at a time; each chunk goes through all 48 layers before the next one starts. [S12] The bigger the chunk, the more tokens share the weights and the experts. But bigger is not always better. The teaching model below draws the trade-off:

How does the real Strata pick a chunk size? Upstream's explanation: long text is read in big chunks of at most 8,192 tokens each, which is why long documents read at over 1,000 tokens per second. [S02] With --prefill auto, the engine looks for the largest chunk that fits within the borrowing limit. The default maximum is 8,192, and the user can explicitly raise it to 16,384 or 32,768. Code fact How it looks was changed once in v0.1.39. Before, the engine took the first fit from a fixed table of candidates (32,768, 16,384, 8,192, 6,144, and so on). That table is too coarse: a machine that could hold about 8,700 tokens got only 8,192. Now the engine does a binary search on a grid of 256 tokens. A bigger chunk can only borrow more VRAM, never less, so "the largest chunk that fits" can be found by bisection. Code fact To estimate "how long will prefill take", the server also assumes at most 32,768 tokens per chunk. [S15]

The price of a big chunk is temporary VRAM. The intermediate results of an 8,192-token chunk take a lot of space. Strata's answer is to "borrow" from the expert cache: during prefill it lends some slots at the end of the cache to the chunk buffer, and after prefill it fills the original experts back in. Each request borrows only the size its own prompt needs. [S12] Figure 16-6 shows a set of measurements from a source comment.

The speedup is 973 ÷ 791 ≈ 1.23×. Teaching estimate Even bigger chunks can be a bit faster still: the comment records an RTX 5090 reading a 32K prompt at 5,624 tokens per second with 8,192-token chunks, and 6,465 tokens per second with the whole prompt as one chunk (32,768). But that needs a lot of VRAM, so it is off by default. Code fact

Chunks cannot be too small either. A source comment notes that below about 1,000 tokens per chunk the engine switches to a different set of kernels, and the Q2_0 output changes, so the "move every expert" mode has a floor of 1,024. When STRATA_PREFILL_CPU_SHARE_MAX=3072 extends the CPU share to larger chunks, this floor is raised to 3,072 as well. Code fact Also, the engine checks "should I stop?" only before each chunk starts, so the bigger the chunk, the longer a cancelled request has to wait. [S12]

16.5 Pipelining: this layer computes while the next one is on its way

Once the prompt is cut, each chunk still has to go through 48 layers. Every layer does two things: move the experts it needs onto the GPU, then compute. If the two take turns, the copy channel sits idle while the GPU computes, and the GPU sits idle while data moves. Strata overlaps them: while the current layer computes attention, the next layer's experts are already crossing PCIe. [S02]

Pipelining: several stages working at once

Intuition: doing laundry has two steps, "wash" and "dry". With one washer and one dryer, the smart move is to put the second load in the washer while the first load is in the dryer. Each load takes as long as before, but the whole pile finishes much sooner.

Definition: split a job into several stages in sequence, each done by a different unit. While job i is in stage 2, job i+1 has already started stage 1. This is a pipeline. Once it is running steadily, the total time is set by the slowest stage, not by the sum of all stages. Figure 16-7 shows an example with two stages and four layers.

A pipeline needs two things: the stages must use different units (here, the copy engine and the compute units), and a buffer between them must hold what "has arrived but is not computed yet". If the buffer is too small, the moving stops and waits.

Further reading: Wikipedia: Pipeline (computing) · Wikipedia: Instruction pipelining · Wikipedia: Multiple buffering (the buffer between stages)

In Strata, the buffer is that pinned-memory ring buffer. A source comment records how much its size matters: reading Q2_0 with 8,192-token chunks, a ring of 96 slots reads 1,153 tokens per second, and 384 slots reach 1,294, because "the next layer's experts can arrive during this layer's attention phase". Code fact

The ring buffer and the chunk buffer borrow from the same VRAM, so v0.1.39 budgets the two together. The size of the ring is now fixed in bytes: one slot holds one whole expert, so a model with bigger experts gets fewer slots. When auto mode picks a chunk, it looks for the largest chunk that still leaves the ring full. A source comment records the reason: reading a 120K prompt on a 4-GPU machine, one more ring slot is worth about 0.53 tokens per second, and one more chunk token only about 0.05, so the ring is protected first and the chunk grows after that. A prompt that fits the chunk of the old rule keeps the old ring, and its results are bit-for-bit unchanged. Code fact For longer prompts, the split of experts between "computed in the cache" and "moved up and computed" changes, so the bits change too; upstream tested it against the FP16 prompt path, and the quality stays in its old range. Upstream report

With several graphics cards, the pipeline gains another level: each card owns a span of layers, and as soon as the earlier span hands a chunk's intermediate results to the later span, it starts reading the next chunk. In the words of the interface comment, while the later span reads chunk c, the earlier span is already reading chunk c+1. [S12]

Finally, do not forget the handoff. When a chunk is done, the engine must leave the session state exactly as it "would be after reading token by token up to here": the GDN recurrent state and convolution history, the QSA KV cache and indexer, the PLE history. Not one can be missing, so that decode can pick up seamlessly from the next token. [S12]

16.6 Hands-on: find a chunk that is fast and still fits

  1. First play with the interactive figure above (Figure 16-5). Drag C from 1 to 8192 and watch where the bars change from "rising" to "plateau". Then switch the pipeline off, play once with it on and once with it off at C = 1024, and compare the "time per chunk".
  2. Open this book's lab, "Chunking and the space trade-off". Under an explicitly given reuse curve, it computes both the speed of each chunk size and the space it needs. First find the absolute fastest chunk, then rule out the ones over the VRAM budget, and compare how far the "best feasible" is from the "absolute best". The reuse curve and per-token space in the lab are made-up parameters, not Strata's allocator.
  3. Think about it: if the same prompt is read with C = 1 and with C = 8192, should the final state be the same? Answer after reading "Go deeper".

Remember these three

  1. Decode is matrix × vector: one read of the weights serves one token. Prefill is matrix × matrix: one read of the weights serves a whole chunk. On the same computer, prefill can be more than twenty times faster than decode.
  2. The expert part is batched by grouping by expert: tokens that picked the same expert go together, and its weights are read only once. Bigger chunks mean more reuse, but they borrow more VRAM and make cancelling slower. Strata's default is at most 8,192 tokens per chunk.
  3. Pipelining overlaps moving and computing: while the current layer computes, the next layer's experts are already on their way. The total time is set by the slowest stage.

Common misconception: "During prefill all the tokens are known, so they can see each other and the causal rule no longer matters."

Wrong. Batching only changes how the computation is organized; it does not change the model's rules. Token i can still see only the tokens before it. Prefill still uses the causal mask, and the recurrent layers still walk through the chunk in order. An input being "known" and being allowed to "see the future" are two different things.

Go deeper: state handoff, rounding differences and when borrowing VRAM is safe

The handoff is more than the last vector

When a chunk is done, the state to hand off includes the GDN recurrent state and convolution state, the QSA KV and indexer, the PLE history, and the state related to the draft layers. [S12][S13] If you keep only the last row of logits and drop these states, the next decode step is no longer working on the same history.

A strong test: read the same token string with different chunkings, such as C = 1, C = 7 and C = 32, then compare the state at chunk boundaries and the output that follows under a fixed history. The samples most likely to break: a length that just crosses a chunk boundary, a last chunk that is not full, a very short prompt, a cancel halfway through prefill, and decode starting right after prefill.

Batching changes rounding, but "floating point" is not an excuse for everything

Batched and one-by-one computation can take different rounding paths. The upstream docs give an example: with IQ-family models, the CPU computes one token's experts with ggml's dot product, but several tokens with Strata's own multi-token kernel, and the two round slightly differently. So even at temperature 0, the same prompt can produce another, equally reasonable answer because the drafts differ. Upstream added a switch that makes every group use the multi-token kernel. [S03] Since v0.1.41 the default path has one such example: when a single NVIDIA card reads a chunk of fewer than 1,024 tokens, the experts that the CPU takes over are computed in the CPU's own activation format (Section 16.3). Upstream compared the share on and off with prompts of 500 and 1,000 tokens: about half of the 32-token greedy answers were exactly the same, and the rest forked at about the 23rd token, at a point where two candidates were almost tied. Upstream report

So when C = 1 and a large C do not give word-for-word identical output, you cannot conclude right away that one side has a bug, and you cannot wave it off with "it's just floating point" either. Compare on the same fixed history: the intermediate tensors, the chosen experts and index numbers, and the layer where the error starts to grow. Then judge by tolerances and quality gates set in advance. The "non-numeric contracts", such as state positions, the causal mask and index numbers, must be checked separately and exactly.

When borrowing VRAM is safe

The chunk buffer borrows slots from the expert cache, which raises two problems. First, while slots are lent out, the experts that used to live there are gone, so the routing table must stop treating them as "hits". In the source code, those experts are moved from RAM during prefill and filled back in afterwards. [S12] Second, only after the refill has finished may the engine announce again which expert lives in each slot. Showing that "the budgets add up to less than VRAM" does not prove that borrowing is safe. What you must prove is that "at every moment, the label matches the bytes in the slot".

The several chunk sizes in the docs

Different chunk sizes appear in different places upstream: the readme says "at most 8,192 tokens" [S02]; the paragraph in the details doc that explains the internals still said 2,048 in v0.1.38 and was changed to "at most 8,192; 32,768 must be turned on by hand" only in v0.1.39, while the history paragraph about the 0.1.13 change still records "it used to be 2,048"; the server uses 32,768 as the upper bound to estimate wait time [S15]; the engine's auto mode defaults to a maximum of 8,192 and can be explicitly raised to 32,768. Code fact These numbers do not contradict each other; they answer different questions (default, historical value, upper bound). In formulas, this book always writes the chunk size as the variable C.

The limits of the teaching cost formula

This chapter's interactive figures and the "Chunking and the space trade-off" lab use a simplified cost formula of the form T ≈ N ÷ r(C) + ⌈N ÷ C⌉ × fixed cost per chunk, where r(C) is an explicitly set reuse curve. It can show two things, "the fixed cost gets spread thin" and "space is limited", but it cannot predict Strata's real throughput. Real speed also depends on the expert hit rate, PCIe bandwidth, the CPU copy threads, the attention compute that grows with context length, and more.

In advanced GPU experiments, change only C each time, keep everything else fixed (quantization, KV format, drafts, input, cache state), and then explain the changes in speed and quality.
