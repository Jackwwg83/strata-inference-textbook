A small slip in the source code

Strata's qsa.hpp has a comment that works out how big the KV cache is for a 32K context: 12 layers × 2 heads × 256 dimensions × 2 (K and V) × 2 bytes × 32,768 = "805 MiB". [S18]

Punch it into a calculator: the result is 805,306,368 bytes. That is 805 MB, and it is also 768 MiB, but it is not 805 MiB. Even the experts who write inference engines slip on units. This chapter answers two questions: how many bytes a model needs to "remember" a conversation, and where those bytes live.

In one line: in Strata only 12 attention layers need a KV cache that grows with the conversation. Stored in FP16, each token takes 24,576 bytes, and a 128K context is exactly 3 GiB. When you count capacity, keep GB (10⁹ bytes) and GiB (2³⁰ bytes) apart; they differ by 7.4%. Strata cuts the KV into pages of 4 tokens and manages them with a page table. Above a 64K context, VRAM keeps only the pages that are used often, and the full history lives in RAM.

17.1 Where the model's "memory" lives: the KV cache

You chat with an AI for an hour, and it still remembers what you said at the start. The model does not reread the whole conversation from the beginning for every word it writes; that would be far too slow. Instead, for every token it has read, each attention layer stores two things it computed: K (the key, used to be "found") and V (the value, the content you take out once it is found). This archive is called the KV cache. Chapter 8 showed how attention matches Q against K and then takes V by weight; here we care about just one thing: every time the conversation grows by one token, the KV cache of every attention layer grows by one cell.

The model Strata runs has 48 layers, but not every layer has a KV cache. In every group of 4 layers, only the 4th is a QSA attention layer, 12 in total. The other 36 are GDN layers, which remember the history in a recurrent state of fixed size that does not grow with the conversation. [S04] Figure 17-1 lays them out side by side.

How big is a GDN layer's state? With the sizes in the source code, each layer holds a 128 × 48 × 128 recurrent state plus a 10,240 × 3 convolution history, all as 4-byte floats: 3,268,608 bytes in total. The 36 layers come to about 118 million bytes, or 112.2 MiB. Code fact Whether the conversation is 1K or 256K tokens long, that number does not change. Only the KV of the 12 QSA layers "grows as you chat".

17.2 Doing the math: how many bytes per token

One token stores one K and one V in each QSA layer. Each layer has 2 KV heads, and each head has 256 dimensions. [S04] Stored as 16-bit floats (FP16, 2 bytes per number), the KV of one token is:

12 layers × 2 heads × 256 dimensions × 2 (K, V) × 2 bytes = 24,576 bytes = 24 KiB

Multiply by the context length and you get the KV of one conversation. A 128K context is 131,072 tokens: 24,576 × 131,072 = 3,221,225,472 bytes, exactly 3 GiB. Teaching estimate

By default, Strata does not store KV in FP16. Above a 4K context, it stores KV as 8-bit integers (INT8) by default; 4-bit (Q4_0) and "8-bit K, 4-bit V" (K8V4) are options. [S03] Lower bit widths must also store scale factors (Chapter 4 covered these), so the byte count does not simply halve. Figure 17-2 shows the results worked out from the formats in the source code.

Each of these numbers can be matched in the source code. The INT8 format pairs every 64 numbers with one FP16 scale factor, so one token in one layer is 1,024 bytes of codes plus 32 bytes of scales. Across 12 layers that is 12,672 bytes, and the comment says "instead of 24,576 for FP16". Q4_0 packs every 32 numbers into 18 bytes, 144 bytes per head. Code fact K8V4 simply stores K as INT8 and V as Q4_0. That works out 22.7% smaller than INT8, which matches the upstream docs' "23% less than 8-bit". [S03]

The saved bytes are not free: with 4-bit KV, perplexity (lower is better) rises by 8–12% on long documents, so upstream keeps 8-bit as the default. [S03] Changing only where data is stored without touching its values, and quantizing, which does change the values, are two different kinds of "saving".

17.3 GB or GiB: the 7% unit trap

Once you have the byte count, converting it to "so many G" walks you straight into the trap from the opening.

GB vs GiB: the decimal and the binary "thousand"

Intuition: in daily life a "thousand" is 1,000. But computers address memory in binary, where 2¹⁰ = 1,024 is the handier number, so early on 1,024 bytes was also called "1 KB". Mixing the two "thousands" compounds at every step: by the G level the gap is already 7.4%.

Definition: the international standards now keep the two kinds of prefix apart. The decimal kB, MB and GB are 10³, 10⁶ and 10⁹ bytes. The binary KiB, MiB and GiB are 2¹⁰ = 1,024, 2²⁰ = 1,048,576 and 2³⁰ = 1,073,741,824 bytes. So 1 GiB ≈ 1.074 GB, and 1 GB ≈ 0.931 GiB.

A concrete example: 805,306,368 bytes = 805.3 MB = 768 MiB. Drive makers and network speeds usually use decimal units. Operating systems showing memory, and the logs of many programs, often use binary units yet still write "GB". Even NVIDIA's CUDA docs have to point out that "KB" in their tables means 1,024 bytes, that is, KiB. [R01]

Why it matters here: when you budget VRAM, first make the units match. A 7% gap sounds small, but on 12 GB it is nearly 0.9 GB, and the upstream docs say each extra 1 GB of VRAM holds about 700 more experts. [S02]

Further reading: Wikipedia: Binary prefix · Wikipedia: Gigabyte · Wikipedia: Binary number · NVIDIA: Compute capabilities (where KB means KiB)

You can find several examples of this in Strata's source code. The KV comment from the opening writes 805 MB as 805 MiB. The "1.6 GiB at FP32" on the same line is really 1.61 GB, that is, 1.5 GiB. The indexer comment says a 32K context needs "50 MiB"; at the 1.5 KiB per token it gives, that is 48 MiB, or 50.3 MB. [S18] The INT8 file, on the other hand, says "3.3 GB at 262K instead of 6.4": 12,672 × 262,144 ≈ 3.32 × 10⁹ bytes, which is decimal GB, used consistently. Code fact When you read someone else's numbers, ask first: which kind of G is this?

"K" has the same problem. Upstream says the model's full context is "262K", meaning 262,144 tokens, that is, 256 × 1,024. Teaching estimate When this book's figures say "256K", they mean the same number.

17.4 Paging: cutting the history into pages of 4 tokens

The KV cache is not one big contiguous array. Strata cuts it into small blocks, each called a page, and keeps a page table that records "which physical location holds page number such-and-such". It is exactly how an operating system manages memory.

The KV cache and paged management

Intuition: a library shelves its books by number. To find "book 37", you first check the catalog card, which tells you which shelf and which slot it is in. A book can move; as long as the card is updated, readers still find it. A book whose card says "sent to the branch library" has to be brought back before you can borrow it.

Definition: paging cuts data that is logically contiguous into pages of equal size; a page table translates "logical page number" into "physical location". A program accesses data only by logical number, and the page table decides where the data really is. Operating systems use this to build virtual memory: a page can be in RAM or swapped out to disk, and when an access finds it missing, it is loaded first; this is called a page fault. A page table also makes "logically contiguous, physically scattered" possible, so you do not have to reserve one contiguous region for the worst case.

A concrete number: one page in Strata is 4 tokens, exactly one block of the attention indexer. In INT8 format, one page holds K and V for 4 tokens and 2 heads, 4,224 bytes in total. Code fact The physical row of token c is found by first looking up page = table[c ÷ page size] and then adding the offset inside the page. [S18]

Why it matters here: with a page table, part of the KV can sit in VRAM and part in RAM, without changing the attention code. The next section does exactly that.

Further reading: OSTEP: Paging: Introduction (PDF) · Wikipedia: Memory paging · Wikipedia: Page table · Paper: vLLM's PagedAttention

Why are Strata's pages as small as 4 tokens, and why not smaller still? The source code explains: this engine serves only a few conversations at once, not hundreds or thousands, so a coarser grain buys little, and a finer one would add an extra indirection for every token. [S18] Page size must not affect the result either: the tests use page sizes of 1, 4 and 512, shuffle the order of the page table, and require the attention output to be exactly the same. [S18] In other words, the page table decides only "where it is", never "what you read".

If you studied CS: this is the paging and page-fault handling from an operating systems course, with "RAM / disk" replaced by "VRAM / RAM" and "process address space" replaced by "one conversation's KV". vLLM's PagedAttention uses the same idea to serve many concurrent requests; Strata has little concurrency, so its pages are mainly for "partial residency".

17.5 VRAM keeps only the pages in use: KV streaming

QSA attention does not read the whole history at each step. It picks only the roughly 2,000 most relevant positions to compute with (Chapter 8). Since each step reads only a part, there is no need to keep the whole history in VRAM. From a 64K context on, Strata by default keeps the full KV in RAM, and VRAM holds only the part attention reads most often, 32,768 positions by default. [S02][S03]

It works in three steps, all on the GPU, inside the recorded graph:

  1. One thread block of 1,024 threads scans the blocks selected in this step. Blocks already in VRAM get a "used this step" mark; blocks that are not go onto a list of misses.
  2. The same thread block picks a slot for each miss using the CLOCK algorithm (also called "second chance"): a hand sweeps around the slots, lets each recently used slot off once, and never picks a slot that this step is using. Then it updates the page table: the old block is marked "absent", and the new block points to this slot.
  3. A copy kernel reads the missing blocks from RAM over PCIe into their slots. Code fact

The most important rule in this design is "there is only one authoritative copy". The K and V of a new token are always written to the copy in RAM; only when the block they belong to happens to live in VRAM are they also written to that slot. So a slot is never stale, and nothing ever needs to be invalidated: not when speculative decoding rejects a draft (Chapter 18), and not when a parked conversation is resumed. Code fact Parking a conversation also saves the authoritative copy in RAM, not the replaceable VRAM slots. [S10]

Where does the saved VRAM go? To experts. Upstream measured: with KV streaming on at a 262K context, the experts in VRAM went from 1,589 to 3,872, and generation speed rose from 50.9 to 62.6 tokens per second; the cost is about 13.7 KB of RAM per context token. [S03] Figure 17-7 estimates this trade with the INT8 format.

The K8V4 format can stream too. Since v0.1.40, the upstream docs state that it streams the KV cache like the other formats (--kv-resident N): on an 8 GB RTX 2060 SUPER at a 128K context with 20,480 resident cells, it gains 780 more expert slots than K8V4 without streaming. [S03] The engine of the previous version, v0.1.39, would simply refuse this combination. Whether two "save memory" switches can stack depends on the version; you cannot assume it.

Remember these three

  1. In Strata only the KV of the 12 QSA layers grows with the conversation: 24,576 bytes per token in FP16, 12,672 bytes in INT8. The state of the 36 GDN layers stays fixed at about 112 MiB.
  2. GB is 10⁹ bytes, GiB is 2³⁰ bytes, and they differ by 7.4%. 805,306,368 bytes is 805 MB, and also 768 MiB; pairing the number of one unit with the name of the other is the most common mistake.
  3. KV is managed in pages of 4 tokens through a page table. Above 64K, the full KV is in RAM and VRAM holds only the pages in use; on a miss, CLOCK swaps the page in. The history is not deleted, only moved.

Common misconception: "VRAM keeps only 32K of KV, so the model remembers only the last 32K tokens."

Wrong. "Kept in VRAM" and "kept at all" are two different things. The full history stays in RAM the whole time. Whichever block attention selects, the page table swaps it into VRAM and then reads it, and the values read are exactly the same as when everything sits in VRAM. [S03] How much stays in VRAM affects only speed, not what the model can see. The only way history really gets lost is going past the context limit, and Strata's server rejects such a request outright; it never quietly truncates. [S15]

Go deeper: every factor in the capacity formula, peak budgets and switches that do not stack

Ask about every letter in the formula

For general grouped-query attention (GQA), the raw KV payload is M = L × T × Hkv × d × (bK + bV) bytes. L is the number of layers that need KV, 12 here, not 48. T is the number of positions; say whether it is the number actually used or the number allocated in advance. Hkv is the number of KV heads (2), not the number of query heads (24). d is the dimension per head (256). bK and bV are the bytes per element; for a quantized format, spread the scale factors into them. [S04][S18]

Count 48 layers instead of 12 and the result is 4 times too big. Someone will say "it is a conservative estimate, so it does not matter". Wrong: a false attribution makes people misjudge the bottleneck, buy the wrong hardware or switch off features that actually help. Erring on the safe side is not the same as having the right model. Margin should be listed as its own item, not hidden inside a structural error. The source code has a lesson of this kind: an early round counted indexer key storage by the number of query heads (4), while the cached keys really have only 1 shared head, so the figure was 4 times too big. The error survived a whole round precisely because it made the budget "tighter" and so looked safer. [S04]

What else there is besides the main KV

The main KV is only one line on the bill. QSA also stores the indexer keys: in FP32, one per 4 tokens, 1.5 KiB per token across the 12 layers. [S18] Another comment in the source says that FP16 KV plus FP32 indexer keys makes the engine actually allocate about 29 KB per token, 7.65 GB at 262K, which a 12 GB graphics card cannot hold; that is exactly why it switched to INT8. Code fact A complete budget also includes at least: the resident non-expert weights, the hot experts, the GDN state, the convolution and PLE state, the draft layer, scratch buffers, CUDA Graph and framework overhead, and reserved space. On the RAM side there are all the experts, the master copy of streamed KV, parked conversations and the headroom the operating system needs. [S03][S06]

A budget must look at the peak, not just the sum

Prefill and decode need memory differently, so draw up a separate bill for each. As Chapter 16 showed, the chunk buffer during prefill is borrowed from the expert cache: the same block of VRAM must not be counted as two uses. But if two lifetimes really do overlap, you also cannot optimistically take only the larger one. The budget formula must match the real allocations, and you check it against the peaks at startup and while running.

Memory-saving switches do not stack freely

Whether K8V4 and KV streaming can both take effect depends on the version: the v0.1.39 engine refuses this combination, and since v0.1.40 the two can stack. [S03] A table that assumes the two effects multiply, without testing that configuration, gives false capacity and speed numbers.

Likewise, 4-bit quantization changes values and needs a quality evaluation (upstream measured perplexity rising by 8–12%). Changing only where data lives (streaming, paging) keeps the values the same, and what it needs is checks that the mapping and the copies are correct. [S03] You cannot cover both kinds of "saving" with one blanket "lossless" label.

Budgeting for several conversations

Read-only model weights can be shared; sequence state is usually one copy per conversation. A teaching approximation: total ≈ shared weights + Σ state of each conversation + scratch buffers + reserve. If several requests share an exactly identical prefix, sharing physical pages plus copy-on-write can save space. But that needs strict identity checks, reference counting and isolation on write; that is the topic of Chapter 20, and you cannot reuse state just because two pieces of text look alike. Strata's parking, for example, reuses state only when the token prefix is exactly equal, the image identities match and the guidance mode is the same. [S10]

When you report capacity, keep four numbers apart: the configured limit, the actual token length, the allocated capacity and the working set currently resident. "5 conversations of up to 128K" and "5 conversations that really fill 128K" are two different things.

Acceptance

When a request goes over budget, the system must refuse it clearly or pick a supported fallback; it must never quietly shorten the context or drop history. Strata's server answers a request whose "prompt plus maximum generation length exceeds the context" with a 400 error and never truncates. [S15] At acceptance, measure the peak RAM and the peak VRAM together, rather than taking one screenshot of VRAM while idle.
