A speed-up that "cheats"

Strata's docs describe one of its speed tricks like this: a small, fast helper first guesses the next few words, the big model checks all those guesses in one go, keeps the ones it agrees with, and then writes the next word itself. "The helper only guesses; the big model decides every word, so the answer quality stays the same, just 1.6–1.8 times faster." Upstream report[S02]

How can guessing make the computation faster without changing the answer? What happens when a guess is wrong? And how do you "take back" work that was already computed on top of a wrong guess? This chapter answers these three questions with Strata's verify window.

In one line: the draft layer guesses up to 3 tokens. The target model puts them in one window and computes them all at once, compares them from left to right, and accepts them up to the first mismatch; everything after that is thrown away. At the mismatch, the target gives its own pick, so every round moves forward at least 1 token. This is the same idea as a CPU's speculative execution, or a database's "write tentatively, then commit, roll back on error".

18.1 Guess first, check later: a wrong guess costs little

Chapter 16 showed that computing several tokens at once is much cheaper than computing them one by one, because the weights are read only once. When writing the answer, though, you only know the next token after the previous one has been picked, so you cannot batch. Speculative decoding works around this: first guess the next few tokens with a cheap method, then hand "the last result + these guesses" to the big model as one batch and compute it in one go. At every position the big model says "here is what I would write", and comparing that with the guesses shows which guesses were right.

The part that guesses is called the draft; the big model that has the final say is called the target model. Strata's drafts come from an MTP (multi-token prediction) layer that ships with the model, and it guesses at most 3 tokens. If the answer repeats earlier text (for example when editing code or quoting the source), Strata can also "copy" up to 5 tokens from the earlier text; this is called prompt lookup. One verification runs through all 48 layers, and each round moves forward 2.4–3.2 tokens on average. [S02] Figure 18-1 compares the two.

Why does checking a few more tokens per round cost so little? The source code does the accounting: one window costs "read the dense weights once, shared by T tokens", plus computing on the CPU the union of the experts that each of the T tokens missed. From real decode logs, the missed experts the CPU has to compute come to 1.75 times a single token's at T = 2, 2.4 times at T = 3 and 3.05 times at T = 4. [S08] The marginal cost of verifying one more token is far smaller than running another round.

How well the draft guesses decides how much you gain. A source comment records that the MTP layer matches the greedy result 0.89, 0.86 and 0.85 of the time at steps 1, 2 and 3. Code fact The upstream docs also warn that output speed depends on the text: the more drafts get accepted, the faster it goes, and the same prompt with a different answer can differ in speed by several percent. [S03] How many tokens to guess each time, and whether guessing pays at all, is the topic of Chapter 19.

18.2 Accept only the unbroken prefix

The comparison has one rule: go from left to right and accept up to the first mismatch. Say row 0 of the window is the token x fixed in the last round, followed by drafts d₁, d₂, d₃. The target model works out "after x I would write a", "after x, d₁ I would write b", and so on. Then it compares in order:

  • After x the target picks a, and draft d₁ = a: accept;
  • After x, a the target picks b, and draft d₂ = b: accept;
  • After x, a, b the target picks e, but draft d₃ ≠ e: stop. d₃ is thrown away and replaced by the target's own e.

In Strata's generation loop this rule is one line of code: while (a < T - 1 && window[a + 1] == outv[a]) ++a;, followed right away by ver.commit(a + 1). Code fact Here outv[t] is the target's pick after row t of the window, and a is the number of accepted drafts. The target's own token at the mismatch is output too, so every round moves forward a + 1 tokens, at least 1. The comment in the draft controller says the same: "the verify pass always commits one token." [S09]

Why are all drafts after the first mismatch thrown away, even one that "looks right"? Because it was guessed on top of a wrong token, so its premise no longer holds. The simulator below is built to show exactly this case; press Step through round 2 and see:

If you studied CS: you can prove this rule correct by mathematical induction. Assume the committed history H equals the greedy result. If d₁ equals the target's pick after H, then H + d₁ still equals the greedy result; and so on, up to the first mismatch. The drafts after a mismatch rest on a wrong history, the chain of induction is broken, and there is no reason to accept them. Correctness holds as a chain along the prefix; it is not a tick for each position of the window on its own.

With greedy decoding (take the most probable token at each step), Strata's verify window gives an even stronger guarantee: the result of row t in the window is bit-for-bit identical to what plain one-by-one generation gives at that position, because every kernel in the window either is the single-token kernel, or does exactly the same arithmetic per token as the single-token version. So "the draft was accepted" means exactly "plain generation would also have written it". [S08]

18.3 Speculative execution: CPUs did it first

"Guess and keep going, take it back if the guess was wrong" was not invented for language models. Modern CPUs do it billions of times a second.

Speculative execution and branch prediction

Intuition: you are in the cafeteria line. The person in front of you has not yet decided between noodles and rice, but the cook has already started the noodles, because that is what this person usually orders. If the guess is right, the wait is saved; if it is wrong, the noodles go aside and the cook starts over. At worst some work is wasted; the wrong dish is never served.

Definition: a CPU runs instructions in a pipeline (Chapter 16 covered pipelines). When it reaches a branch such as an if, the condition is not computed yet, so it does not know which instruction to fetch next. The branch predictor guesses a direction from history, and the CPU keeps executing in the guessed direction. This is called speculative execution. The key point: the results of speculative execution first go somewhere temporary and are not written to the official state. Once the condition is known, a right guess lets the results "retire" (commit); a wrong guess flushes those instructions from the pipeline, and the CPU restarts in the right direction.

A concrete number: on modern processors, branch prediction is usually right more than 90% of the time, so "occasionally wasting a little work" is far cheaper than "stopping to wait every time". The cost of a wrong guess grows with the pipeline: the longer the pipeline, the more work is wasted.

How it connects to this chapter: the draft is the branch prediction, the verify window is the speculative execution, and commit(a + 1) is the retirement. Both follow the same discipline: a guessed result must not take effect before it has been checked.

Further reading: Wikipedia: Speculative execution · Wikipedia: Branch predictor · Wikipedia: Instruction pipelining

18.4 Write tentatively, then commit: transaction-style state management

The hard part is "taking it back". While the verify window computes T rows, all kinds of model state may change: the KV cache gains T slots, the GDN recurrent state moves forward, the indexer gains a few keys. If only the first 2 rows are accepted, the later changes must look as if they never happened. This is exactly the problem a database "transaction" solves.

Committing and rolling back a transaction

Intuition: a bank transfer has two steps: take 100 from account A, add 100 to account B. What if the power fails after the first step? The bank wraps both steps in one transaction: either all of it takes effect, or it is as if nothing happened.

Definition: during a transaction, changes are first recorded somewhere temporary (a log or a copy), where the outside world cannot see them. When every check passes, a commit makes all the changes take effect at once; if something goes wrong midway, a rollback discards the temporary changes and returns to the state before the transaction began. There are two common ways to implement rollback: save a snapshot first and restore it on error, or record the inputs and redo the work from them after confirmation. File-system "journaling" uses the same ideas.

A concrete example: Strata's commit(n) is not "commit the whole window or roll it all back"; it is "commit only the first n rows". That is finer-grained than a textbook transaction: within one window, the prefix takes effect and the suffix rolls back.

How it connects to this chapter: different states are taken back in different ways. We go through them one by one below.

Further reading: Wikipedia: Database transaction · Wikipedia: Rollback (data management) · OSTEP: Crash Consistency: FSCK and Journaling (PDF)

Strata's verify window spells this out clearly. While the window runs, it appends K/V and indexer keys for all T positions, but it does not touch the GDN state. commit(n) then makes the first n tokens take effect, and each kind of state has its own method: [S08]

  • GDN recurrent state: the window does not change it at all; it only saves the input of each row. At commit, the saved inputs of the first n tokens are replayed, and the state moves forward to the right place. This is "record the inputs, redo after confirmation".
  • Indexer keys: first restore the snapshot saved before the window, then append the accepted keys again. A comment explains why: a rejected key may sit in a slot that the current block still needs. This is "snapshot + redo".
  • PLE history: set it directly to the snapshot taken after token n−1.
  • KV cache: the extra slots need nothing at all. Those positions are processed again in the next round, and the new values overwrite them before any query reads them. [S08] The KV streaming of Chapter 17 follows the same rule: a new token is always written to the authoritative copy in RAM, so "rejecting a draft" never requires invalidating any VRAM slot. Code fact

There is one exception. A window with no draft (T = 1) has only row 0, and it is always accepted, so nothing needs to be taken back. So since v0.1.40, on CUDA the graph of such a window advances the GDN state directly, and commit no longer launches a commit graph, which saves one graph launch; set STRATA_ONE_TOKEN_COMMIT=0 to turn this off. A multi-row window that may be rejected still follows the rules above. Code fact

Note that the window's "row count" and the "accepted draft count" differ by 1: row 0 of the window is the token fixed in the last round, and it too is written into the state during this round. So when a drafts are accepted, a + 1 rows are committed. A comment in the generation loop says: "the first a + 1 window tokens are now in the session; the last output is not yet: it is the next round's row 0." Code fact The draft layer's position counter uses the same offset: after a window at position p accepts a drafts, the next window starts at p + a + 1. [S07]

If you studied CS: every new kind of sequence state must answer four questions. Does the window write it while running? How does commit(n) keep only the prefix? How is the rejected part invalidated? Who confirms that asynchronous reads and writes have finished? It is the same as adding a new table to a database: you have to think through its logging and recovery.

18.5 Verifying under sampling: an exact match with the target's sample

With greedy decoding the comparison is simple: is the draft the target's most probable token for this row? But chat often runs with temperature sampling, where each step "draws one by probability". The draw itself is random, so what do you compare against?

Strata makes the target model's draw reproducible: the random number for row t of the window is set by the "seed" and that row's absolute position, and then goes through the full sampling chain (repetition penalty, top-k, top-p, min-p, temperature, and finally one draw by the cumulative distribution). A draft is accepted only if it is exactly equal to that row's sampled result. So the output depends only on the seed, not on what the drafts were; the drafts only decide how many steps a round can move forward. [S07] The repetition penalty for each row is also prepared separately, from "the history that should come before this row", counted the same way as in plain one-by-one generation. [S08]

How should the draft guess so that it more often "hits" the target's draw? Strata has a "coupled draft" mode, off by default: instead of proposing the token it is most sure of, the draft layer runs the target's sampling chain and draws with the same random number the target is about to use. When the two distributions are close, drawing from the cumulative distribution with the same random number gives the same result far more often than "trying to hit a random sample with the most likely token". The target's draw does not change, so the output text does not change either. [S07] Figure 18-5 sketches the idea.

Note that this is not the method of the classic speculative decoding paper. The classic method accepts a draft with probability min(1, p ÷ q), and on rejection draws a replacement from a corrected distribution, which guarantees that the output distribution matches the target's exactly. [R04] The Strata code this book read uses "an exact match with the target's sampled result", not that formula. The two methods differ in their distribution argument, in how they organize random numbers and in what they need from the implementation, so do not mix them up.

What the draft can guess also has a practical limit: the MTP draft layer can only propose tokens from a subset of the vocabulary. Since engine 0.1.27 this subset includes all Chinese, Japanese and Korean tokens, and upstream measured answers in these languages getting 15–38% faster as a result (Q2_0, RTX 5070). [S03] Part of the speed-up Chinese users see comes from here.

Remember these three

  1. The draft guesses; the target decides. Compare from left to right and accept up to the first mismatch; drafts after the mismatch are thrown away even if they happen to be right. Each round moves forward a + 1 tokens, at least 1.
  2. This is the same discipline as a CPU's speculative execution: a guessed result must not take effect before it is checked. Strata uses commit(a + 1) to make only the prefix of the window take effect.
  3. Taking things back is designed state by state: GDN replays the saved inputs, the indexer restores a snapshot and appends again, PLE restores the matching snapshot, and the extra KV slots wait to be overwritten. Just decrementing the position is not enough.

Common misconception: "The draft layer is small and inaccurate, so using it makes the answers worse."

It does not. The draft only proposes; every token stays only if it exactly equals the target model's own pick (or its reproducible sampled result). Bad guesses only mean fewer tokens per round and lower speed; they never change the words written. [S02][S07] Upstream also records one exception worth knowing: with IQ-series models, the CPU uses two different sets of kernels for experts when computing one token versus several tokens, and their rounding differs slightly. So at temperature 0, the same prompt may get a different but equally reasonable answer depending on the drafts. Turning on a switch that makes every group use the multi-token kernels removes the dependence on the drafts. [S03]

Go deeper: offsets, asynchronous commit and an acceptance checklist

Keep the window's counts apart

Say the committed length is 100. Row 0 of the window is the token x at position 100, and drafts d₁, d₂, d₃ take positions 101–103. If only d₁ is accepted (a = 1), 2 rows are committed (positions 100 and 101), the target's pick after position 101 becomes row 0 of the next window, and the next window starts at position 102. [S07] Mathematically you can say "each round contributes at least one target step, plus the number of accepted drafts". In engineering terms, though, you must check the window start, the row index, the next position and the meaning of commit(n_keep) one by one; never treat "accepted drafts" and "committed rows" as the same variable. The random-number counter of coupled drafting follows the same offset: a draft made in MTP slot c is verified by the row with counter c + 1. [S07]

Penalty history for each row

The repetition penalty has to count "which tokens appeared before this row". The history before row t of the window is the committed content plus drafts 1 to t. Strata prepares a separate history for each row of the window; before 0.1.19 it prepared one only for row 0, and the draft rows read slots that had never been written. [S08] A bug like this does not crash the program; it just quietly makes the results differ from plain generation when the penalty is on.

Asynchronous commit

With a single GPU, commit() by default returns without waiting for its graph to finish: the next window queues behind it on the same stream, and the draft layer does not read what it writes, so the commit can overlap with the next round's drafting. Anyone who reads or writes the session from another stream or from the host (a new request, a checkpoint, a snapshot, the prefill path, the end of a run) must first call wait_commit(). [S08] This is one more example of Chapter 14's "synchronous versus asynchronous": the fast path saves the wait, and the price is that every side reader must remember to wait on its own.

Why the draft layer's "shortcuts" do not affect the output

The MTP draft layer takes several shortcuts in its implementation: the big projection is quantized to Q8_0, attention is computed densely over every slot it has seen, and all 512 experts stay resident in VRAM (708 MB). The source code is explicit: these choices affect only the quality of the drafts, never the output, because every output token is decided by the verify window. Speculatively written slots also never touch the indexer state; they are simply overwritten when the position is processed again. Code fact

Acceptance checklist

To test speculative decoding, the average acceptance rate is not enough. Cover at least: all rejected, all accepted, rejection midway, close to the context limit, hitting the end token, cancellation midway, repetition penalty on, and sampling parameters switched between requests. Compare against "the reference result without speculation under the same fixed history": the logits, the state after commit and the final tokens must all match. Whenever you add any sequence state, answer the four questions of Section 18.4 one by one and add the matching tests.
