You may have noticed

When you watch Strata write, it sometimes seems to burst out a whole string of words at once instead of squeezing them out one at a time. The README explains it like this: a small helper first guesses the next few words, and the big model checks all those guesses in one go, so the same answer arrives 1.6–1.8 times faster. Upstream report[S01]

The upstream docs also say the model's built-in guessing layer guesses at most 3 tokens at a time. Upstream report[S02] Here is the puzzle: a correct guess is a free token, so why not guess 10 at once? This chapter answers two questions: how many guesses pay off best, and how the engine changes its mind on the fly when the acceptance rate keeps shifting.

In one line: each extra guessed token adds less and less to the expected gain, shrinking like a geometric series, while the time to verify a round keeps growing. Strata compares "expected tokens committed per millisecond" and updates its acceptance rates on the fly with an exponential moving average.

19.1 Guess once, check once: how many tokens does a round give?

First a quick review of Chapter 18's speculative decoding: guess cheaply first, then let the big model grade the guesses. The guesser is the model's built-in MTP layer (multi-token prediction), and the candidates it guesses are called drafts. Upstream report[S02]

The big model lines up "the last confirmed token + k drafts" in a row and runs through its 48 layers just once. That single pass tells it, for every position at once, "here is what I think belongs here". This row is the verify window, and it is k + 1 long. Figure 19-1 walks through an example with k = 3.

The rule is simple: compare from left to right and stop at the first mismatch. Every matching draft before it is accepted, plus the big model's own answer where it stopped. So if a drafts are accepted, the round commits a + 1 tokens. Strata's generation loop counts exactly this way: it compares each draft in the window with the big model's output, then calls commit(a + 1). Code fact

Even if no guess is right, the round still gets the big model's own 1 token, the same as with no guessing at all. Wrong guesses cannot make the answer worse, because the big model has the final say on every word. Upstream report[S02] A wrong guess costs only one thing: this round's verification computed a few extra positions for nothing.

19.2 How many per round on average? Enter the expected value

You cannot know in advance how many drafts a round will accept. What we can compute is how many it gets on average, which is the expected value.

Let the conditional acceptance rate of the i-th draft be pᵢ: the probability that draft i is accepted, given that the i − 1 drafts before it were all accepted. The word "given" matters: once an earlier draft is rejected, the later ones never even get compared.

Draft i is useful only if the first i are all accepted, which has probability p₁ × p₂ × … × pᵢ. Add up every position's "probability of being useful" and you get the expected number of tokens committed per round:

E = 1 + p₁ + p₁p₂ + … + p₁p₂…pₖ

The leading 1 is the big model's own token, which every round gets for sure. Strata's source code multiplies and adds the terms one by one in exactly this way. Code fact[S09] If every position has the same acceptance rate p, this sum is the first k + 1 terms of a geometric sequence. The primer below shows why adding more terms "runs out of steam".

Expected value and geometric series

Intuition: the expected value is "the average result after you do something many, many times". A fair die can land on anything from 1 to 6 on a single roll, but on average it gives 3.5. The expected value is defined as: multiply each outcome by its probability, then add them all up.

To count "tokens per round" there is a handier route: add up each position's "probability of being used". Position 1 is always used, probability 1; position 2 is used with probability p; position 3 with p²… so E = 1 + p + p² + … + pᵏ. A sum where each term is the previous one times the same number is a geometric series, and it has a ready-made formula: E = (1 − pᵏ⁺¹) ÷ (1 − p).

So the gain from guessing more keeps shrinking: with p = 0.86, the 8th draft contributes only 0.86⁸ ≈ 0.30 tokens. A geometric series also has a ceiling: as the number of terms goes to infinity, the sum approaches 1 ÷ (1 − p). With p = 0.86, even infinitely many guesses average only about 7.1 tokens per round.

Further reading: Wikipedia: Expected value · Wikipedia: Geometric series · Wikipedia: Geometric distribution

If you studied CS: call "tokens committed in a round" the random variable N. The method above is the tail-sum formula from probability, E[N] = Σ P(N ≥ i). It holds for any distribution, so the derivation does not need the positions to be independent; it only chains conditional probabilities.

Now plug in Strata's numbers. The source code starts every MTP position at an acceptance rate of 0.86, and a comment says this was measured on the same model. Code fact[S09] With 3 guesses, E = 1 + 0.86 + 0.74 + 0.64 ≈ 3.24. The upstream docs report that in practice one verify pass commits 2.4–3.2 tokens on average. Upstream report[S02] The two are in the same range, so 0.86 is a reasonable starting point. The real acceptance rate shifts with the text, which Section 19.4 covers in detail. Teaching estimate

19.3 The other half of the bill: wider windows cost more to verify

If verification were free, more guesses would always be better. But verification takes time. Strata's cost model step_ms splits one round's time into four parts: Code fact[S09]

  • Dense part: attention and everything else every token must compute. The wider the window, the slower this part; the source uses a table of multipliers indexed by window length.
  • CPU experts: experts not cached on the GPU are computed by the CPU (see Chapter 10). The more tokens in the window, the more distinct experts are used and the busier the CPU gets.
  • Sync: a fixed coordination overhead per round.
  • Drafting: the MTP layer also needs time to guess each draft.

The defaults for these parts are in the header file: dense part 11 ms, all 480 experts on the CPU 15.8 ms, VRAM hit rate 55%, sync 2.4 ms, and 1.2 ms per MTP draft. A comment says defaults such as the multiplier table come from measurements on September 23, and that 11 ms is the target from the plan and should be replaced with a measured value inside the engine. Code fact Figure 19-3 plugs these defaults into the formula to show how the four parts grow as the window widens.

Look at the CPU part. If 9 tokens each used a completely different set of experts, the CPU would have 9 times the work of 1 token. Yet the multiplier table in the source tops out at 5.2 times, and a comment says the table comes from measured routing traces. Code fact Tokens in the same window often pick the same experts; this is Chapter 10's "hot experts" at work.

With the numerator and the denominator in hand, the goal is clear: speed = expected tokens committed per round ÷ time per round. The controller computes this for every k and picks the fastest. Code fact[S09] The interactive figure below lays the calculation out for you.

The numbers in this figure come from plugging the source defaults into the formula, not from measurements: with no guessing, a round takes 20.5 ms, or 48.8 tokens per second; with 3 guesses, a round takes 44.4 ms, yields 3.24 tokens on average, and runs at 72.8 per second. Teaching estimate What it shows is the shape: the curve has a peak, and where the peak sits depends on the acceptance rate and the costs.

There is one more threshold. The best window must beat no guessing by more than 5%, or the controller will not use it and simply does not guess. Code fact[S09] The header comment describes this 5% as a setting from the plan. Code fact The benefit: the acceptance estimate itself has error, so a "gain" of one or two percent may well be an illusion created by that error.

19.4 Acceptance rates change: learning on the fly

0.86 is only a starting point. When you write code, what comes next can often be guessed from what came before; when you write a brand-new poem, it is much harder. The upstream docs also note that the same prompt with a different answer can change the output speed by several percent, because the number of accepted drafts changed. Upstream report[S03] So the acceptance rate has to be estimated on the fly. Strata's tool for that is the exponential moving average.

Exponential moving average (EMA)

Intuition: you want to know the recent average temperature, but you do not want to keep every day's record. The trick is to keep just one number, the "estimate", and every time a new temperature arrives, nudge the estimate a small step toward it:

new estimate = old estimate + α × (new data − old estimate)

This is the exponential moving average, and α (between 0 and 1) is the update weight. Expand it and the newest data point has weight α, the one before has α(1 − α), the one before that α(1 − α)²… Older data gets less weight, decaying exponentially, hence the name. It needs the memory of a single number, and each update costs one multiplication and two additions or subtractions.

α sets the trade-off. A large α tracks quickly but is easily thrown off by one or two chance results; a small α is steady but takes a long time to react when things change. A handy measure is the half-life: how many updates it takes for old data's weight to drop by half, which is ln 0.5 ÷ ln(1 − α). With α = 0.05 that is about 13.5 updates; with α = 0.3 it is under 2.

Strata's controller uses exactly this formula to update each position's acceptance rate: an acceptance counts as 1, a rejection as 0. Code fact[S09] The default α in the header file is 0.05. Code fact

Further reading: Wikipedia: Moving average · Wikipedia: Exponential smoothing · RFC 6298: Computing TCP's retransmission timer

If you studied CS: in computer networks, TCP estimates the round-trip time (RTT) with an EMA: SRTT ← (1 − 1/8) × SRTT + 1/8 × the new RTT sample, as in RFC 6298. Estimating an acceptance rate and estimating network delay are the same kind of problem: the data is noisy, the environment changes, and memory is tight.

There is a trap in the bookkeeping. Say this round guessed 3 and the 1st was rejected right away. How should drafts 2 and 3 be recorded? They were never compared at all. They are unobserved, not "failures". Statistics calls this situation, where the outcome was never seen, censoring.

Strata's observe updates only the accepted positions plus the first rejected one; it leaves every later position alone. Code fact[S09] There is also the opposite case: when every guess in a round is accepted, positions beyond the window were never tried either. If they were never updated, the window could never grow. The source handles this by nudging those positions' estimates a small step toward the estimate of the deepest observed position. Code fact[S09]

The tracker below lets you feel both effects yourself: the α trade-off and the effect of the bookkeeping rule.

The deeper the position, the fewer chances it gets to be compared: draft 3 gets a record only when the first two are both accepted. So deep positions update more slowly than shallow ones. That is why, in the tracker, the p₃ curve reacts noticeably more sluggishly than p₁ after the topic changes. Teaching estimate

19.5 Which one does Strata actually run?

The controller described so far lives in src/spec/controller.cpp. It is compiled into the strata_spec library and has its own unit test, controller_test. Code fact But open the main generation program, generate.cpp (the source of the strata executable), and it includes a different header, draft_policy.hpp; the generation loop calls DraftPolicy. In the engine source this book checked, we found no call to Controller. Code fact Figure 19-7 puts the two side by side.

Start with the MTP side. In the generation loop, the MTP window length comes from the launch option --spec and stays fixed every round except the first. It only gets shorter when --spec-min-p is set: once the draft layer's confidence in a draft falls below that threshold, no more drafts are added to the window. Code fact The upstream docs say MTP guesses at most 3 at a time. Upstream report[S02]

DraftPolicy handles something else: prompt lookup. If the text being written repeats a passage from the context, say, copying a few existing lines while editing code, then whatever followed that passage last time will probably follow it again, and can be used directly as a draft. Lookup drafts are at most 5 long, and they are used only when the measured acceptance rate and cost both say it pays. Upstream reports 6–11% faster code editing and no change on ordinary text. Upstream report[S02] The generation loop has one more precondition: when MTP is on, the first token of the lookup draft must match MTP's own first draft before DraftPolicy is asked to decide. Code fact

DraftPolicy still uses this chapter's formula: on the lookup side E(k) = 1 + q + q² + … + qᵏ, where q is an acceptance rate tracked in buckets by "how long the match was"; on the MTP side it uses the measured average yield per round directly. The denominator is no longer a formula but the measured time per round for each window length, smoothed by an EMA with α = 0.1; for lengths it has not measured, it converts from measured ones with a preset shape curve. A lookup window must beat the MTP window by more than 3% to be chosen. Code fact

That is a great engineering lesson: however detailed your cost model, it cannot beat measuring directly. Round times change with the machine and with the context length; measured values follow the machine automatically.

19.6 Hands-on: find the best window yourself

Open this chapter's lab, "How long a draft is worth guessing". It uses a simpler cost formula: a baseline time plus a fixed verify and drafting cost per draft, with the same acceptance rate p for every position. It compares the expected tokens, time and net gain for k = 0 to 5.

  1. Set p to 0: every k has an expected value of 1, and drafts only add time. The best answer should be k = 0.
  2. Set p to 1: the expected value is exactly k + 1. See whether the longest window always wins now.
  3. Keep p fixed and raise the draft cost: find the point where the best k drops back to 0.

Afterwards, compare with this chapter's two interactive figures. The lab's cost is a straight line; in Strata's cost model, shared experts make the CPU part grow slower than a straight line, while the dense multiplier jumps sharply once the window reaches 5 tokens. A different cost curve moves the peak.

Remember these three

  1. Expected tokens per round E = 1 + p₁ + p₁p₂ + …: each extra guess multiplies its contribution by another acceptance rate, so returns diminish. With p = 0.86, even infinitely many guesses cannot pass 7.1.
  2. What to optimize is speed = E ÷ time per round. Wider windows cost more to verify, so the speed curve has a peak; drafting must also beat no drafting by a clear margin to be worth it.
  3. Estimate acceptance rates on the fly with an EMA: a large α reacts fast but jitters, a small α is steady but slow. Positions never compared are "unseen" and must not be counted as failures.

Common misconception: "A higher acceptance rate always means more speed."

The acceptance rate is only part of the numerator. Suppose a smarter but slower drafting method raises the expected yield per round from 2 to 2.5 tokens, but the round time goes from 10 ms to 15 ms: speed drops from 200 tokens per second to about 167. Teaching estimate To judge a drafting method, look at tokens committed per millisecond, not just how many guesses were right.

Go deeper: conditional probability, censoring, exploration and acceptance criteria

The expectation formula needs no independence assumption

pᵢ is defined as "the conditional probability that draft i is accepted, given the first i − 1 were all accepted". Draft i contributes if and only if the first i are all accepted, and the multiplication rule for conditional probability gives that probability directly as p₁p₂…pᵢ, with no claim that positions are independent. Example: p = [0.8, 0.6, 0.5] gives E = 1 + 0.8 + 0.48 + 0.24 = 2.52. If drafting plus verifying takes 18 ms per round, speed is about 140 tokens/s; with no guessing a round takes 8 ms, 125 tokens/s, so the net gain is about 12%. These are teaching exercises, not Strata benchmarks. Teaching estimate

The source's expected is used in two ways: MTP passes a per-position array; lookup drafts use the same q for every position, which is a geometric series. Code fact[S09]

The cost model, term by term

In step_ms(k), n = k + 1, clamped to between 1 and K_MAX + 1. Dense part = dense_ms × dense_ratio[n−1]. CPU part = (1 − hit rate) × cpu_all_miss_ms × U × (1 + extra_use_cost × (n ÷ U − 1)), where U is how many times more distinct experts the window uses compared with a single token, and n ÷ U is how many tokens use each expert on average. Drafting part = k × time per draft. Code fact[S09] Defaults from the header file: K_MAX = 8; extra_use_cost = 0.25, meaning each extra token using the same expert costs only 25% of one read; lookup drafts cost 0.01 ms each, nearly free. Code fact

Applying the ideal "weights are read only once" to every draft unconditionally overestimates the gain; ignoring expert reuse completely underestimates it. The actual value of U depends on routing and must be measured.

Priors are not physical constants

MTP's initial acceptance rate of 0.86 and the lookup prior bucketed by match length, {0.35, 0.6, 0.8, 0.92}, are only starting points. The comments say the former was measured on the same model and the latter comes from offline replay, and both are then learned per session. Code fact[S09] Change the language, the quantization or the task, and both draft quality and expert reuse change. DraftPolicy has its own lookup prior: {0.75, 0.88, 0.93, 0.96}, each worth 4 observations, so a few rounds of real data override it; old observations decay by a factor of 0.97 per round. Code fact

Censoring, positions beyond the window, and "exploration"

After the first draft is rejected, later positions are no longer under the condition "every earlier draft accepted", so they are unobserved. Recording them as 0 creates a self-reinforcing loop: the shorter the window, the worse deep positions look, and the less willing the controller is to try a long window again. When everything is accepted, the opposite happens: positions beyond the window were never tested, and the source pulls them toward the estimate of the deepest observed position, or the window could never grow. Code fact[S09]

Looking at Controller's two functions alone, there is another boundary worth noting: once "no drafting" is chosen, observe returns right away and the estimates stop updating. Code fact[S09] If noise ever pushes the estimate below the threshold, these two functions alone can never learn their way back, and the caller must explore separately. (One test in this chapter's module demonstrates exactly this.) DraftPolicy explores explicitly: a lookup window whose time has never been measured gets tried directly for its first 3 uses, as long as its acceptance estimate is at least 0.85. The comment says verification guarantees the output does not change; the only thing at stake is this round's speed. Code fact v0.1.40.2 added one more case: a lookup window that has been measured, but not measured again for more than 300 rounds, is also tried again when its acceptance estimate is at least 0.85. The comment gives the reason: its time may have been measured during an especially slow stretch, and at that price it can never be chosen, so it is never measured again. Code fact

Can drafts change the output?

In principle, no: every committed token is the big model's own choice. But the upstream docs point out a floating-point exception: with IQ-quantized models, the CPU uses different kernels to compute an expert for one token and for several tokens, and their rounding differs slightly; how many tokens share an expert depends on the drafts in the verify window. So even at temperature 0, the same prompt can produce a different but equally reasonable answer. Setting STRATA_IQ_MT_MIN=1 makes every group use the multi-token kernel, and the answer no longer depends on the drafts. Upstream report[S03]

Acceptance criteria

To test a window controller, boundaries are more convincing than a pretty curve:

  • When drafts are very expensive, it falls back to k = 0.
  • With p = 0, extra drafts produce no fake gain.
  • With p = 1, E equals exactly k + 1.
  • Unobserved positions are not counted as failures; when everything is accepted, positions beyond the window can be pulled up.
  • If it beats no drafting by less than the threshold, it stays with no drafting.

The computation module behind this chapter's interactive figures has tests for these boundaries, and its cost function was checked term by term against the source defaults. Upstream's own controller_test tests the same kind of properties: with the priors it picks 2 to 5 drafts, it turns speculation off after sustained rejections, and the window widens after sustained full acceptance.
