You may have noticed

Hand a long document to a chat AI and the first question takes a good while before any answer appears. Ask a follow-up and the answer pops out almost at once. Strata's docs say the same thing: after the first message it keeps hold of the conversation and reads only the newly added part, so a follow-up can start within seconds. Upstream report[S02]

What exactly does the engine "keep hold of"? If two requests differ by a single word or swap one image, does it still dare to reuse anything? If two conversations start the same and then branch, can they share one copy? This chapter covers prefix reuse, snapshots and copy-on-write.

In one line: Strata saves a prefix it has read as a checkpoint (a kind of snapshot). When a new request's tokens, images and steering mode match the checkpoint exactly, it resumes from the checkpoint and reads only the new tail. A snapshot must hold the entire running state; saving just the KV cache is not enough.

20.1 Why follow-ups are fast: do not reread what was already read

Multi-turn chat has one quirk: every request sends the whole history again. The request for turn 5 starts with everything from turns 1 to 4 and only then has your new question. The new content is often a short stretch; the long part before it is the prefix, the part identical to the start of the previous request.

If the engine read from the first token every time, long chats would get slower and slower. The smart way is like a bookmark: start reading where you stopped last time. This is called prefix reuse, and engines often call it the prompt cache.

How much does it save? Strata reads long text at more than 1,000 tokens per second. Upstream report[S02] A comment in the source does the math too: a 30,000-token system prompt read at about 1,000 per second takes about 30 seconds. Upstream report Figure 20-1 compares the two approaches.

Resuming from a checkpoint has its own cost: the checkpoint lives in RAM and must be moved back to the GPU. A checkpoint is about 118 MB (the next sections explain why). At the PCIe 5.0 theoretical bandwidth of about 63 GB/s used in Chapter 10, that is 118 ÷ 63 ≈ 2 milliseconds. Teaching estimate Next to 30 seconds, it is negligible.

The upstream docs also warn of a side effect: the prompt cache makes a repeated request read only its tail, which takes a different computation path from reading it all, so the answer may not be exactly the same as a full read. If you need byte-identical output, turn it off with options such as --prompt-cache 0. Upstream report[S03]

20.2 What counts as "the same prefix"?

Reuse requires that the history a checkpoint stands for is exactly the same as the start of the new request. "Looks about the same" does not count. Change one token and the result at every later position changes with it.

Strata makes this call with a function called conversation_prefix, plus one extra check when the conversation cache picks an entry. Code fact[S10] Together they make four rules:

  1. Same steering mode. Steering is an optional "control vector" that, when turned on, changes the intermediate results of many layers. If the two sides use different modes, the state in the checkpoint was computed a different way, so it is skipped.
  2. The checkpoint is shorter than the request. The request's last token must really be read, because it starts the next verify round. So a checkpoint exactly as long as the request cannot be used.
  3. Every token ID in the prefix is the same.
  4. Every image in the prefix has the same identity. In the token sequence an image is just a run of placeholders, and identical placeholders can stand for completely different pictures. So the engine records a separate identity for each image: its start position plus a content hash. Code fact[S10]

If you studied data structures: deciding "is this checkpoint a prefix of the request?" is a string prefix comparison, and finding the longest matching prefix among many checkpoints is exactly what tries and radix trees are good at. Strata's source comments compare it directly to a radix tree; see Section 20.4.

20.3 What goes into a snapshot: a notebook can flip back, a whiteboard cannot

A checkpoint is a kind of snapshot: a picture of the whole state at one moment, so you can return to that moment later, like a game save. What to save depends on how the model "remembers" history. The model Strata runs has two kinds of layers among its 48, and they remember history in completely different ways. Code fact[S04]

  • The 12 attention layers (QSA) use a KV cache. For each token read, they write one more row by position, like a notebook. To go back to a prefix, ignore the later rows: the verifier's notes say plainly that rejected positions are simply overwritten when they are processed again, before any query reads them. Code fact[S08]
  • The 36 GDN layers use a recurrent state. For each token read, they rewrite a fixed-size block of state in place, like a whiteboard. Code fact[S17] Once token 5 is read, what the board looked like at token 4 is erased and can never be computed back.

How big is the whiteboard? Each GDN layer's state is 128 × 48 × 128 32-bit floats, so the 36 layers total 36 × 128 × 48 × 128 × 4 bytes ≈ 113 MB. Teaching estimate[S04][S17] However long the conversation, this whiteboard stays the same size. The KV notebook keeps getting thicker: stored at 2 bytes per number, the 12 layers take 12 × 2 × 2 × 256 × 2 bytes ≈ 24.6 KB per token, or about 737 MB for 30,000 tokens. Teaching estimate

So Strata's checkpoints mostly store the whiteboard: the GDN recurrent state, plus a few small pieces such as the PLE (per-layer embedding) history and the attention indexer's tails, along with the token IDs and image identities of that prefix. Code fact[S10] The upstream docs say one checkpoint is about 118 MB, Upstream report which matches the 113 MB whiteboard: it is the bulk of it.

20.4 A chain of checkpoints: pin the root, rotate the rest

When does the engine take a photo? The upstream docs say: one at the start of each new assistant turn, plus one more every 16K tokens while reading a long prompt, with at most 6 kept in RAM. Upstream report

These checkpoints have a special shape. The KV cache on the GPU has only one region, so it can hold only one history branch at a time. Every checkpoint kept must therefore be a prefix of the current history; sorted by length, each is a prefix of the next, forming a chain. A source comment compares it to a radix tree: a tree flattened down to the single branch the session can hold. Code fact

When the chain is full, who gets evicted? The early approach was first in, first out: the oldest checkpoint went first. But the oldest one is usually the end of the system prompt, the very spot every new chat from the same client passes through. Throw it away and every new chat must reread the system prompt from scratch. Code fact

The current rule is: pin the root, rotate the rest by least recently used (LRU). The eviction function in the source is only a few lines: if the capacity is below 2, turn off pinning and evict the oldest; otherwise skip entry 0 and pick the least recently used among the rest. Code fact The upstream docs add one more rule: for a prompt read from the start, if the system prompt has 2,048 tokens or more, a photo is also taken at the end of the system prompt so that a root exists (from engine 0.1.20). Upstream report Chapter 12 covers cache replacement policies like LRU in detail.

20.5 Two conversations, one shared opening: copy-on-write

Now a harder case: conversations A and B start exactly the same (say, the same system prompt plus the same document), then each asks its own question. Can they share the prefix and pay only for the parts that differ? Operating systems and databases found a classic answer to this long ago.

Snapshots and copy-on-write

The clumsiest way to take a snapshot of some data is to copy all of it. 1 GB of data means copying 1 GB: slow, and it takes double the space. Yet most of the time, the snapshot and the original later differ in only a few places.

Copy-on-write (COW) takes another route: copy nothing at first. Both sides share the same data, and each block carries a reference count, meaning "how many users it has". Whoever wants to write into a shared block copies that block first and changes their own copy. A block nobody changes only ever exists once. Figure 20-5 shows a three-page example.

The most famous example is Linux's fork(): creating a child process copies only the page table. Parent and child share all physical memory pages, marked read-only. Whoever writes a page first triggers a page fault, and only then does the kernel copy that page. That is why forking a process that uses several GB of memory finishes almost instantly. File system snapshots and the multiversion concurrency control (MVCC) in databases use the same idea.

Back to this chapter: the shared prefix of two conversations is exactly the "pages nobody changes". As long as the prefix's KV pages are only read and never written, they can safely be shared. The simulator below lets you try it yourself.

Further reading: Wikipedia: Copy-on-write · Linux manual: fork(2) · OSTEP (free operating systems textbook, the virtual memory chapters) · Wikipedia: Multiversion concurrency control

The simulator reveals two things. First, KV pages can be shared, but the last page of the prefix, if not full, gets written by both sides and must be copied. Second, the recurrent state (the whiteboard) can never be shared: every token rewrites it whole, so at a fork it can only be copied in full.

So what does Strata itself do? It does not share pages between two conversations. The source says so right on the buffer that holds snapshot data: a snapshot and the buffers it keeps have exactly one owner, so no sharing and no copy-on-write are needed. Code fact As noted earlier, the KV region on the GPU holds only one history branch at a time, so a single chain is enough. Copy-on-write here is our teaching extension, not Strata's implementation.

Strata does have a similar money-saving trick, though. It can "park" several conversations in RAM (this feature is off by default and must be turned on by hand), with a full snapshot for each parked conversation: running state, checkpoints, the KV pages in use and the draft layer's KV. Upstream report After a conversation is restored, its unchanged KV pages can be kept and reused directly the next time it is parked, with no fresh copy; when the conversation grows, new pages are only appended and existing pages are not moved; only pages rewritten by a rollback are copied again. Upstream report That is the same spirit as copy-on-write: do not copy what has not changed.

20.6 Hands-on: save, switch, restore, then compare

Restoring a snapshot has one iron rule: either restore it completely, or refuse it clearly. Half-restored state is the most dangerous kind: the model will happily generate text that reads smoothly and is completely wrong. Strata first validates every layer and every checkpoint, and starts writing only when all of them pass; a snapshot that fails validation is rejected before any GPU operation. If something goes wrong in the middle of moving data, the interface requires that the caller must not keep using that session for inference. Code fact

If you studied databases: this is the atomicity of a transaction: either it all takes effect, or it is as if nothing happened. Chapter 18 described "commit only the accepted prefix" in speculative decoding; here the same idea is applied to restoring a session.

Open this chapter's lab, "Commit only the accepted prefix". It uses a toy recurrence s ← 0.5s + t to show why the candidate state differs from the committed state, and why rolling back only the counter leaves a wrong state behind. Set the second draft to be rejected and find the position where "the counter rolled back but the state did not". That is exactly why a whiteboard cannot be rolled back by "pretending nothing was written".

To go further, design your own test that needs no GPU: run conversation A with the same toy recurrence and save a snapshot; switch to conversation B; then restore A and continue. Finally compare bit for bit with the result of "A never left". The two must be exactly the same.

Remember these three

  1. Prefix reuse accepts only an exact match: the token IDs, image identities and steering mode must all be the same, and the checkpoint must also be shorter than the request before reading can resume.
  2. The KV cache is like a notebook: to roll back, ignore the later rows. The recurrent state is like a whiteboard, rewritten whole for every token, so it can only roll back to a checkpoint photographed in advance. The bulk of a Strata checkpoint is the GDN state of about 113 MB.
  3. Copy-on-write lets several branches share pages nobody changes and copies only the page being written. Strata uses a checkpoint chain with "root pinned, the rest rotated by LRU"; parked conversations each own their buffers outright, with no copy-on-write.

Common misconception: "Saving the KV cache is the same as saving the whole conversation."

For the model Strata runs, that is far from enough. 36 of its 48 layers remember history in a recurrent state, which is not in the KV cache. On top of that come the PLE history, the attention indexer's tails, the draft layer's KV, and the token IDs and image identities of the prefix. Code fact[S10] Leave out any one of them and the restored conversation will quietly compute the wrong thing.

Go deeper: matching rules, the snapshot inventory, capacity accounting and the restore contract

Source details of the matching rules

conversation_prefix first requires that the checkpoint is not empty, that its length is strictly less than the request's, and that the first n token IDs are equal one by one; otherwise it returns 0. Then it walks the request's images: images whose start position is outside the prefix are skipped; those inside must equal the checkpoint's recorded images in order (both start position and hash); finally, the checkpoint's recorded images must be used up exactly. One image too many, one too few, or one swapped, and it returns 0. Code fact[S10]

When the conversation cache picks a checkpoint, it searches back from the most recently parked entry and skips entries with a different steering mode outright; for each entry it considers both the current state and each of its checkpoints, and takes the longest match. On equal length it prefers the most recently parked branch, and the caller prefers the state it already holds at the same length. Code fact[S10]

Identity checklist: what upstream checks, and what this book suggests

Upstream checks tokens, image identities and the steering mode. The snapshot also has an 18-integer geometry array, and a source comment states clearly that it is used only for a runtime compatibility check; it is not the identity of the model weights, nor a disk format. Code fact[S10] Two models with the same shapes and completely different weights have the same geometry.

If you extend this mechanism to production (snapshots on disk, shared across processes, many users), this book suggests the identity key should at least add: the model weight version, the tokenizer and chat template, the RoPE settings, the quantization format, the device numeric mode, and the authorization scope (whose conversation may be used by whom). This is a teaching extension list, not checks upstream already does.

The full inventory of a snapshot

A checkpoint (ConversationCheckpoint) contains: token IDs, image identities, the GDN state, the PLE history, the indexer tails, dead, block_pos and other byte blocks, plus the per-device sub-checkpoints stage_parts of the layer-split runtime. The KV part (ConversationKv) has a format ID, the cell count, the head count, the head dimension, the page size, the indexer row count, and K, V, their quantization scale factors and the pooled index rows. A whole-conversation snapshot (SavedConversation) adds the geometry, the layer range layer_lo / layer_hi, the current state, the list of checkpoints, the KV of the main layers plus the draft layer, and the steering flag. Code fact[S10]

Note the multi-GPU boundary: a source comment says ordinary layer-split checkpoints keep each device's running state, but parking a whole session currently supports only a single GPU and rejects those sub-checkpoints. Code fact[S10] The upstream docs also say that turning on parking together with --layer-split is rejected before the model loads. Upstream report You cannot go from "supports multiple GPUs" to "every cache and restore combination supports multiple GPUs".

Capacity accounting: count capacity, guard against underflow

A snapshot's byte count adds up each vector's capacity(), not its size(): space already allocated but not yet filled counts too. Code fact[S10] The check for whether a new snapshot fits is written as held <= budget_ && incoming <= budget_ - held && …, confirming before each subtraction that it cannot go negative. An unsigned integer that goes below zero wraps around to a huge positive number, and the budget check becomes meaningless. KV kept for reuse counts toward the same budget. Code fact[S10]

To make room, it first drops the KV kept for reuse, then evicts the oldest entries in parking order. Code fact The upstream docs also require a margin of free physical memory of at least --conversation-cache-min-free-mib (default 2560), checked once before allocating and again after the photo is taken; if memory data cannot be read, nothing is parked. Upstream report The corresponding check function clearly separates "could not read" from "read 0": with no data, it refuses outright. Code fact The default budget is 0, meaning the feature is off; the docs' example uses 8 GiB and 4 slots and says this is a ceiling, not a recommendation. Upstream report

The restore contract and persistence

The snapshot interface sorts restore results into three kinds: success, invalid snapshot, and transfer failure. An invalid snapshot is rejected before any CUDA call or write; a transfer failure may leave half a state behind, and the caller must not keep using that session for inference. Code fact The upstream docs say a transfer or sync failure is treated as fatal, and snapshots do not survive a restart. Upstream report

To store snapshots on disk, a common safe approach is: write a temporary file first; once it is written, flushed to disk and has passed its checksum, "publish" it with one atomic rename, and record a format version in the file. The exact durability guarantees also depend on the file system. [R02] This is a teaching extension; Strata does not currently persist snapshots.

The limits of KV page reuse

The snapshot interface has an easily missed comment: identical token IDs do not prove the KV bytes are unchanged. "Number of unchanged tokens" is valid only for storage that was really restored into this session from the snapshot and has had every later rewrite subtracted. Code fact The matching function in the conversation cache shrinks the "unchanged length" down to the first dirtied position each time it meets a rewrite, and drops the whole block once it reaches 0. Code fact[S10]

The buffer holding snapshot data is made of 16 MiB segments; appending never moves existing data, and only the small segment directory may move. Code fact This is what underpins "growth only appends, existing pages are not copied".

Worked example: why a fork from a shared prefix needs write isolation

Sessions A and B share their first 1000 tokens. Then A writes token a and B writes b. The read-only shared prefix need not be copied, but position 1001 and the mutable recurrent state must be separate for each. If both sessions pointed straight at the same writable state, one request would quietly corrupt the other. A teaching design can use "immutable prefix pages + reference counts + copy-on-write"; the GDN recurrent state must be copied in full at the fork point.
