Two cards, but not twice as fast

Strata's README has one line on this: two or three graphics cards can run the model together. Upstream report[S01] The upstream docs give one set of measurements: an RTX 5080 plus an RTX 3090 reads long prompts about 20% faster, yet generates answers at about the same speed as the 5080 alone.

You added a whole 24 GB graphics card and the answers did not get faster. Where did the money go? This chapter explains three things: how two cards split the work, why a single token cannot get faster, and how much data really has to travel between the two cards.

In one line: Strata cuts the 48 layers into a front half and a back half, one per card. A token still has to pass the first card and then the second, so a single token does not get faster. The real gains are that two cards can cache twice as many experts, and that while reading a prompt the two cards work at the same time like a pipeline.

21.1 How can two cards split the work?

Picture two people moving house. One can carry the bedroom while the other carries the living room; both can lift the same big sofa together; or each can move a different house. All three count as "two people working together", yet the amount of coordinating is completely different. Multiple GPUs are the same: there are three common ways to split, shown in Figure 21-1.

Strata uses the first one: a layer split, which cuts the model's layers in order into a few segments, each card handling one consecutive segment. The upstream docs put it plainly: this is pipeline (by-layer) parallelism, not tensor parallelism; a token crosses from one card to the next once per verify window, not twice per layer. Upstream report

In the code, this lands in a function called set_stage. Each stage (the segment of layers on one card) runs only the layers [layer_begin, layer_end): a stage that does not start at layer 0 takes over the data from the segment before it; a stage that ends before the last layer hands its data on and carries no output head. Code fact[S08]

Pipeline parallelism and tensor parallelism

When a big model does not fit on one card, there are two basic ways to cut it. Cut it horizontally, into segments of layers, and you get pipeline parallelism: like a factory line, the first station finishes and passes the work to the second. Cut it vertically, splitting one layer's big matrix into pieces, and you get tensor parallelism: like two people lifting a sofa together, they must shout "one, two, three" at every step to stay in sync.

The two cuts pay their costs in different places. A pipeline passes data only once at each boundary between segments, but one piece of data must finish the earlier segment before it can enter the next, so the wait for a single piece of data cannot be saved. Tensor parallelism really lets two cards compute the same layer at once, but after every layer the two halves must be combined. In the classic Megatron-LM approach, each Transformer layer's forward pass does this combining twice. With 48 layers, that is 96 times.

There is a third way, data parallelism (here called request parallelism): each card holds a whole copy of the model and handles different requests. It needs almost no cross-card talk, provided one card can hold the entire model.

Strata's problem is that "the model does not fit on one card", and the graphics cards in a home PC are usually connected only through PCIe, with no dedicated high-speed link. So it chose the layer split, which needs the least communication.

Further reading: Wikipedia: Pipeline (computing) · Wikipedia: Parallel computing · PyTorch docs: Pipeline Parallelism · Hugging Face: comparing multi-GPU parallelism · The Megatron-LM paper

21.2 One token still has to queue layer by layer

While generating an answer, every token must travel from layer 0 to layer 47. Layer 19 needs layer 18's result, and layer 18 needs layer 17's. This dependency chain cannot be broken. So while the first card computes the front half, the second can only wait; while the second computes the back half, the first sits idle. See Figure 21-2.

The upstream measurements confirm this: with an RTX 5080 plus an RTX 3090, generation speed is about the same as the 5080 alone, and slightly faster when writing code. Upstream report (Coder model, 32K context, Ryzen 9 9950X3D CPU; one card writes stories at 83–87 tokens per second and the best two-card split at 84; for code the figures are 88–105 and 110. The docs do not state the engine version; the results folder is dated 2026-09-29.)

So what is the second card for? Capacity. Chapter 10 explained that experts not in VRAM go to the CPU, which computes them in RAM, slowly. After a layer split, each card caches experts only for its own layers, so together the two cards can cache about twice as many experts as one. The upstream docs say that for the Coder model, a 16 GB card plus a 24 GB card can hold almost every expert, and "that is where the speed comes from": during generation the CPU is barely needed. Upstream report Figure 21-3 shows what sits on each card.

Mind the cost: by default, every card needs its own copy of the dense weights, plus its own session state and prompt buffer. That is why upstream advises against bringing in cards with less than 8 GB of VRAM. Upstream report v0.1.39 added an optional switch, STRATA_STAGE_TRIM=1: each card loads only the dense weights of its own layers, and the VRAM saved goes to the expert cache. Upstream ran the Coder model on two 16 GB MI50 cards: the experts in VRAM grew from 8,819 to 10,626, and generation went from 39.2 to 41.7 tokens per second. For now you must turn this switch on by hand; the experts sit in different places, so the output may differ slightly. Upstream report In v0.1.39 it worked only when you wrote the split point by hand. Since v0.1.40, the later cards can also trim under automatic splitting. The first card still trims only with a hand-written split point, because its VRAM is divided up before the split point is computed. Code fact

By default, this is how the two cards take turns while generating. v0.1.40 added an optional switch, --pipeline-windows 2, that keeps both cards busy during generation too: while the later card is still verifying window K, the earlier card has already started on window K+1. Code fact Window K+1 is a guess: the guess is that window K will be accepted whole, and that the next token is the one the draft layer predicted. If the guess is right, the next window is already half done. If it is wrong, the earlier card puts back the recurrent state it saved beforehand and recomputes from the real token. This is the same "guess first, then verify" idea as speculative decoding in Chapter 18, only used between two cards. On an RTX 4060 Ti plus an RTX 5080, upstream measured the average generation speed going from 72.4 to 84.0 tokens per second (+16%). The price is 160 MiB less expert cache on each card. It can be turned on only with two cards, in server mode, with a draft layer, and it is off by default. Upstream report The dependency chain is not broken: the same token still goes through the earlier card first and then the later card. What keeps both cards busy at the same time is two different windows.

21.3 Reading the prompt is when the pipeline starts turning

Reading a prompt is a different story. A long prompt is fully known before reading starts, and Strata cuts it into many chunks and reads them one by one (Chapter 16 covered chunking). Now the two cards can stagger: while the second card reads chunk c, the first is already reading chunk c+1. The comment on the prefill interface says exactly this: a stage that is not the last copies its data into two pinned memory buffers and launches the next stage on another thread, "so the next stage reads chunk c while this stage reads chunk c+1". Code fact[S12]

Laundry is a good analogy. The washer takes 4 minutes per load and the dryer 5 minutes per load. With a single load, you need 9 minutes no matter what. With 8 loads, the second load goes into the washer as soon as the first goes into the dryer. The dryer sets the beat: one load comes out every 5 minutes. The total is the first 4 minutes plus 8 dryer runs of 40 minutes, 44 minutes in all. Doing everything one after another would take 8 × 9 = 72 minutes.

The stretch at the start where "the dryer waits for the first load" and the stretch at the end where "the washer has nothing left to wash" are called bubbles: times when a station on the pipeline sits idle. The simulator below draws the two cards as a timeline. Change each segment's time, the number of chunks and the transfer time, and see where the bubbles are:

Check the simulator's conclusion against the upstream measurements: with the same 5080 plus 3090, reading a 16K prompt goes from 1,726–2,017 tokens per second on one card to 2,039, and a 28K prompt from 1,970 to 2,357. The docs explain it as "each card reads its own layers while the other card reads the next chunk", a speedup of about 18%–20%. Upstream report (Same conditions as the previous section.)

If you studied CS: this is the same thing as the instruction pipeline in computer organization. A 5-stage pipeline does not make a single instruction faster; it makes an instruction finish every cycle. Throughput is set by the slowest stage, and the fill at the start and the stalls on dependencies are the bubbles. In a layer split, a "stage" is a segment of layers and an "instruction" is a prompt chunk.

21.4 How big is the parcel, and how wide is the road?

What exactly passes between the two cards at a handoff? Intuitively, what flows from layer to layer for one token is a 2560-dimensional vector, that is, 2560 numbers. Strata's handoff is bigger. verify.hpp specifies that the handoff buffer holds three things per token: the residual R (hc × n_embd numbers), one vector the previous layer has not written back yet (n_embd numbers), and hc injection coefficients. Code fact[S08] Plug in the model geometry hc = 4 and n_embd = 2560 [S04]:

4 × 2560 + 2560 + 4 = 12,804 floats = 51,216 bytes / token

Why not just pass 2560 numbers? Because this model's residual is itself 4 vectors of 2560 dimensions, and one write-back from the last layer is postponed to the start of the next layer. For the next stage to carry on "as if nothing had been split", it needs all of it. A code comment says this split is bit-exact: split or not, the numbers computed are exactly the same. Code fact[S08]

When reading a prompt, the handoff carries the residual part: 4 × 2560 floats per token, 40,960 bytes. A chunk holds 2048 tokens by default, so that is 2048 × 40,960 = 83,886,080 bytes, about 84 MB. Code fact (src/prefill/prefill.cpp) Teaching estimate When generating, the docs say there is one handoff per verify window, "a few hundred KB, relayed through pinned memory". Upstream report At 51,216 bytes per token, a 5-token window is about 256 KB, which matches.

Now that we know the size of the parcel, we need the width of the road. The primer below covers the roads between two cards.

Interconnect bandwidth: PCIe and NVLink

A graphics card plugs into a PCIe slot on the motherboard. PCIe is a serial bus made of several lanes side by side, like a highway with several lanes: "×16" means 16 lanes and "×4" means 4. Each PCIe generation doubles the speed of a single lane.

At theoretical peak, per direction: PCIe 3.0 ×16 is about 15.8 GB/s, PCIe 4.0 ×16 about 31.5 GB/s, and PCIe 5.0 ×16 about 63 GB/s. In a ×4 slot you get only a quarter of that.

NVLink is NVIDIA's dedicated high-speed link between graphics cards. A data-center H100 has 18 NVLink 4.0 links, 900 GB/s in both directions combined, about 450 GB/s per direction: more than ten times PCIe 4.0 ×16. Home dual-GPU setups usually do not have it and must go over PCIe. Figure 21-5 compares these roads.

Besides bandwidth there is latency: even a single byte pays a fixed startup and sync overhead. Send one big parcel and you pay the latency once; send 96 small parcels and you pay it 96 times. Chapter 5 covers bandwidth and latency in detail, and the "memory hierarchy" primer in Chapter 1 compares the bandwidth of each level.

Further reading: Wikipedia: PCI Express · Wikipedia: NVLink · NVIDIA NCCL docs: multi-GPU communication overview

21.5 Each card minds only its own layers

After the layers are split, each card still needs its own "memory": every layer's KV cache or recurrent state. The early approach had every stage allocate state for all 48 layers, even though it ran only one segment. A comment in session.hpp calls this "the old whole-model-sized buffer problem". Now each session owns only the state of the layers [layer_lo, layer_hi). Code fact[S13]

There is an easy-to-miss detail here. Layers in the code are still numbered by their global index, but the arrays hold only this segment's rows. So to fetch the state of the g-th GDN layer, you first subtract the index of the segment's first GDN layer, gdn_ord0. Get the subtraction wrong and you read another layer's state, with no error reported. If a segment has no QSA layer at all, the code still allocates one "primary" QSA state for it, because whole-model shared things such as the rotary position embedding table are read from there. Code fact[S13]

Where to cut also matters. The function that computes how many bytes a segment of layers takes, session_bytes, is pure arithmetic, so it can "quote a price" for a candidate split before any memory is allocated. Code fact[S13] The upstream docs say the default auto mode tries every split for two to four cards (four cards were added in v0.1.40) and picks the one that lets the card caches hold the most "hot experts". The startup log prints the choice, for example "K = 19, the cache can hold 11,767 of 12,288 profile entries". Upstream report

Last, saving. Chapter 20 covered session snapshots. While reading a prompt, the first card is often a chunk or more ahead of the second. If you simply stitch the two cards' states together at some moment, you get a monster that is "front half at chunk 3, back half at chunk 2". See Figure 21-7.

Strata gives each stage a callback, on_stage_chunk, which is called whenever a card finishes a chunk and its own state sits exactly at the end of that chunk. The comment notes that by the time the last stage reports, the earlier stages "are already a chunk or more ahead", so a save in the middle of a prompt must take each stage's part here. Code fact[S12]

21.6 Hands-on: find the bubbles, and think about whether to add a card

This chapter has no separate lab page; the two interactive figures are the workbench. Try this:

  1. In "two-card pipeline", fix a = 4 and b = 5, drag the chunk count from 1 to 8, write down each total, and check 5N + 4. Then set the transfer time to 1 ms and look at "just one token": see why two cards end up slower than one.
  2. Make a and b very unbalanced (say 2 and 8) and see how long the fast card sits idle. That is why upstream advises "put the fastest card first and let the auto split assign layers by cache capacity". Upstream report
  3. In "how long one handoff takes", switch between links and change the latency, and see whether the gap between tensor parallelism and the layer split comes mainly from bytes or from the number of crossings.

The upstream docs also give a few practical lessons you can understand through the simulator's conclusions. Upstream report

  • Do not add a much slower card just to make up numbers. Adding an RTX 2080 Ti to the 5080 plus 3090 actually dropped generation to 68 (stories) and 90 (code) tokens per second. Every extra card adds another round of handoff and waiting to each window.
  • If one card can hold it, do not split. Version 0.1.31 added an optional switch: when the first card can hold all the profiled experts and the context, use only that card. Running the Coder model on an R9700 32 GB plus an RX 9070 XT, turning it on raised a 4K prompt from 1,244 to 1,776 tokens per second and generation from about 51 to about 60; a 16K prompt got about 5% slower.
  • Old cards need an experimental path. The multi-GPU doc still says: every card needs compute capability 7.5 or higher (RTX 20 series and newer). v0.1.39 also added an experimental CUDA 12 engine for old cards such as Pascal and Volta; the doc about old cards adds that when a V100 shares a model with an RTX 30 or 40 card, both cards run this engine. That doc also says the maintainers do not own these cards and have checked only that the code compiles and the unit tests pass. But the v0.1.40 release notes say the maintainers now have a P100 (sm_60), and it gave 10/10 matching results on 3 quantizations; there is still no real Volta card. The docs disagree, so "which cards are supported" also depends on the version and the source.

Remember these three

  1. There are three ways to split across cards: layer split (pipeline parallelism), tensor parallelism and request parallelism. Strata uses the layer split because it needs the least cross-card talk, and home PCIe is enough.
  2. One token's layers must be computed one after another, so a layer split does not make it faster. Two cards bring twice the cacheable experts, and staggered work while reading prompts: total time = a + b + (N − 1) × max(a, b).
  3. The handoff carries the complete mathematical state: 51,216 bytes per token while generating, about 84 MB per chunk while reading a prompt. Few bytes, few crossings, so the communication cost is small; saves must line up on the moment each card finishes the same chunk.

Common misconception: "Plug in two graphics cards and generation doubles in speed."

One token's layers depend on each other in order, so the two cards can only take turns. In upstream measurements, a 5080 plus a 3090 generates at about the same speed as the 5080 alone, and adding a 2080 Ti makes it slower. Where two cards do speed things up, it is because the extra VRAM lets the CPU compute fewer experts and because long prompts are read as a pipeline, not because "two cards' compute adds up". Upstream report

Go deeper: the handoff contract, the double-buffer protocol and how to evaluate a two-card gain

Why the handoff must be 12,804 numbers

The comment on Verifier::set_stage spells it out: each token in the handoff carries the residual R (hc × n_embd), the last layer's vector bo that has not been written back yet (n_embd), and inject (hc); the next stage "folds in" this write-back when it reads its first layer, exactly as an unsplit window would, so the split is bit-exact. Both pointers must be device-visible memory (mapped pinned memory, which must also be portable when the two stages are on two cards). Code fact[S08] The number of handoff floats comes from handoff_floats, and the formula is exactly hc*n_embd + n_embd + hc. [S08]

Passing only the 2560-dimensional "hidden state" would drop the other three residual copies and the postponed write-back. Nothing would crash; it would just compute the wrong thing silently. The lesson: a cross-device communication format must reflect the complete mathematical contract, and you cannot trim it casually because "the hidden size is 2560". Upstream also offers a checking mode: --layer-split K --split-device 0 runs both stages on the same card, solely to verify that the handoff is bit-exact; it is not a speed mode. Upstream report

The double-buffer handoff protocol

In prefill.cpp, the earlier stage allocates two blocks of pinned memory at init with cudaHostAlloc(..., cudaHostAllocPortable), each big enough for one whole prompt chunk's residual rows (chunk × D × 4 bytes, D = 4 × 2560). Code fact After each chunk, it does four things in order:

  1. Copy the residual rows from VRAM into the current handoff buffer and wait for the copy to finish;
  2. Call on_stage_chunk, while this stage's state sits exactly at the end of the chunk;
  3. Wait for the next stage to finish the previous chunk (so it will no longer read the buffer about to be overwritten);
  4. Launch the next stage on another thread to read this chunk, then switch to the other buffer and go on to the next chunk.

Let the earlier stage take a′ per chunk (including the copy out) and the later stage b′ per chunk (including the copy in). Step 3 means the moment the earlier stage starts chunk c+1 equals the moment the later stage starts chunk c. From this it follows that the later stage starts consecutive chunks max(a′, b′) apart, starts the first chunk at a′, and finishes the last chunk b′ after starting it, so total time = a′ + b′ + (N − 1) × max(a′, b′). With a′ = 4, b′ = 5 and N = 8 that is 44 ms, versus 72 ms one chunk after another. Teaching estimate This chapter's simulator uses exactly this model, and tests/viz-21.test.cjs checks the dependencies and buffer rules chunk by chunk.

With three or more cards, v0.1.39 changed how step 3 waits. Before, after the next stage finished reading a chunk, it still had to wait for its own next stage, and the wait passed on down the chain to the last card. Now each stage waits only for its direct successor: a middle stage hands the chunk over and returns, and everything is collected once at the end of the prompt. Code fact[S12] Upstream measured prompt reading 10%–28% faster on 4 RTX 3060 cards. Upstream report With two cards there is no middle stage, so the pipeline is the same as before.

If each chunk's transfer also occupies a critical resource, it belongs in a′ or b′; you cannot pretend it does not exist. Whether PCIe lets the two cards access each other directly, whether data must detour through RAM, the motherboard topology and crossing NUMA nodes all change this number. Strata chose the most conservative road: relay everything through RAM and never rely on GPU-to-GPU access.

Global indices and "a segment with no QSA layer"

The session state comments explain: qsa_states and gdn_state keep global indices and the arrays simply have fewer rows, so each per-layer user must subtract gdn_ord0; the whole-model uses that used to read qsa_states[0] (the shared RoPE table, the prefill staging identity, the rope MTP borrows) now read qsa_states[primary]; a segment with no QSA layer still allocates one primary state. The default full-range allocation is byte-identical to the old whole-model allocation. Code fact[S13] Tests must specifically cover edge cases such as "a segment with no QSA layer" and "a split point near layer 1".

A save must belong to a single boundary

The contract of on_stage_chunk: it is called when a stage finishes a chunk, its own stream has synced, and its state sits at the end of that chunk; the last stage calls it before on_chunk; it runs on that stage's own thread, with that stage's card as the current device. Code fact[S12] The upstream docs add that a session save stores and restores every card's state, and a save in the middle of a prompt has each card store its own part when it finishes that chunk. Upstream report Put the other way round: if you wait for the last card to report completion and then grab the earlier card's "current state", you get some later chunk, and the save is inconsistent.

How to tell where a two-card speedup comes from

"Two cards are faster than one" does not by itself show "the pipeline is very efficient". The extra VRAM raises the expert hit rate and cuts CPU work, and that may well be the main gain. Measure separately: each card's expert hit rate, the CPU pool's workload, the handoff time, and each stage's time. Upstream's auto split itself shows where the focus is: it picks the split that "lets the cache hold the most hot experts", and on a tie it leaves the most room on the fullest card. Upstream report

Cases not covered yet, or covered with conditions

  • Under the WDDM driver on Windows and WSL2, only an 8 GiB expert region is pinned, and the rest streams through a pinned staging ring; the Linux driver has no such cap. Upstream report
  • By default, every card must hold a copy of the dense weights (since v0.1.39, STRATA_STAGE_TRIM=1 can load only the layers of its own stage) and its own prompt buffer (about 1.5 GB each with the default 2048-token chunks), so cards under 8 GB are not recommended; mixing NVIDIA and AMD cards is not supported. Upstream report
  • For a prompt that fits in one chunk, the two stages can only read one after the other, so one card is always idle. v0.1.39 added the optional STRATA_PREFILL_HELP=1: the idle card moves some of the experts over its own PCIe link, computes them, and sends the results back. Upstream measured it on two RTX 3090 cards: a 1.1K prompt went from 496 to 723 tokens per second; from about 3.3K tokens it stops sharing, because by then the two stages already overlap. Its rounding differs from the default path and the output is not bit-for-bit the same, so you must turn it on by hand. Upstream report
  • Strata has another two-card mode, --peer-device: the second card acts only as an expert cache, with activations and results going back and forth over NVLink or another GPU-to-GPU path; it is mutually exclusive with --layer-split, so you can pick only one. Upstream report
  • Acceptance cannot rest on one successful run on an ideal two-card topology. Also test cancelled requests, a very short last chunk, an error on the second card and unavailable GPU-to-GPU access, then compare the results byte for byte with a single card.
