When you download open-source software, the release page often lists a whole row of files: windows-x64, linux-x64, macos-arm64… It is the same program, so why prepare so many copies?

Strata's README opens with: NVIDIA or AMD graphics cards, Windows or Linux. Upstream report[S01] Its design notes put it even more bluntly: on NVIDIA (CUDA) and AMD (HIP) cards it runs the same engine, just compiled once for each. [S02] This chapter answers two questions: how does one source tree become programs that run on different machines? And how much does "it runs" actually prove?

In one line: every chip understands only its own instructions. Strata keeps one source tree and uses build switches, conditional compilation and a CUDA→HIP "renaming table" to build two engines, one for NVIDIA and one for AMD; on the CPU side it first asks the CPU which instructions it knows at startup, then picks an AVX-512 or AVX2 kernel. Compiles, tests pass, runs on a real card, and maintainer verified are four different levels of evidence.

22.1 One recipe, three kitchens

Imagine you wrote a recipe and are mailing it to three restaurants. One cooks on gas, one on induction, and one only has an oven. "Stir-fry for three minutes" has to be translated by each into what its own equipment can do.

Programs work the same way. Programmers write source code: text people can read. What a chip actually runs is machine code: a string of binary instructions. Which instructions a chip can run, and how each is encoded, is set by its instruction set, which is like "the list of appliances in this kitchen". Translating source code into machine code for one instruction set is the job of the compiler.

The sm_120 and gfx1100 in the figure are GPU architecture codes, like the model number of a kitchen. Strata's build script requires NVIDIA cards to have compute capability 7.5 or higher, that is, RTX 20 series and newer; on the AMD side it accepts only an explicit list, and any architecture not on the list is an error. Code fact v0.1.39 opens two more experimental paths: a CUDA 12 engine for old Pascal and Volta cards, and a separate build for gfx906. Section 22.3 covers them. Upstream report

Compilers, instruction sets and conditional compilation

An instruction set is a contract between hardware and software: the chip promises "I know these instructions", and software may speak only in those instructions. Chips in the same family keep adding new instructions. The x86 CPU family, for example, first got AVX2 and later added the wider AVX-512. When an old chip meets an instruction it does not know, it reports an "illegal instruction" and the program crashes.

A compiler translates source code into machine code. Compiling C and C++ happens in two stages: first the preprocessor edits the text, then the compiler proper does the translation. The preprocessor does three things: it pastes in #included files verbatim; it replaces macros defined with #define by name, like find-and-replace; and it keeps only one branch of each #if condition, deleting the other branches entirely. That last trick is called conditional compilation.

This is exactly how Strata writes the "four-byte dot product" on AMD cards: RDNA3 and RDNA4 cards (since v0.1.40, also the RDNA3.5 gfx1150 and gfx1151) use one sudot4 instruction; RDNA2 lacks it and uses the older sdot4 instead; the RDNA1 gfx1012 has not even sdot4, so it uses a short piece of assembly that builds the same result from 4 multiplications and 2 three-way additions; everything else (including the RDNA1 gfx1010 and gfx1011 and the RDNA3 integrated GPU gfx1103, all new in v0.1.40.2) falls back to a loop that multiplies byte by byte and adds up. All four paths compute exactly the same integer, at different speeds. Code fact Section 22.3 compiles it hands-on.

Further reading: Wikipedia: Compiler · Wikipedia: Instruction set architecture · Wikipedia: C preprocessor · cppreference: conditional inclusion

If you studied CS: a compilers course follows the main line of lexical analysis, parsing and code generation; preprocessing happens before all of that and is pure text editing that knows no grammar. That is why errors from macro replacement often point at strange places: what the compiler sees is the code after replacement.

22.2 CPU: ask which instructions it knows, then pick a kernel

Chapter 10 explained that experts the GPU has not cached are computed by the CPU right in RAM. The upstream docs summarize it this way: these computations use AVX-512 or AVX2 kernels, and models in i-quant formats use ggml's kernels. Upstream report[S02] The source splits it more finely: i-quant formats also switch to Strata's own multi-token kernel when a group holds several tokens. Code fact A kernel here means a piece of core computation code written specifically to run very fast.

AVX2 and AVX-512 are both SIMD instructions: one instruction processes a whole row of numbers at once (Chapter 13 covers this in detail). The difference is how wide the row is. AVX2 registers are 256 bits and AVX-512 registers are 512 bits; see Figure 22-3.

The trouble: if the whole program were compiled for AVX-512, the compiler could insert AVX-512 instructions anywhere, and the program would crash on an old CPU. Strata's build script adds AVX-512 or AVX2 compile switches only to a few kernel source files (options like -mavx512f for GCC, /arch:AVX512 for MSVC). The file that "probes the CPU" gets no such switch, so it runs safely on any x86-64 CPU. Code fact

The probe relies on CPUID: an instruction that makes the CPU "introduce itself", returning a string of bits where each bit stands for one feature. Strata checks that all five AVX-512 sub-features (F, BW, VL, VNNI, VBMI) are present, and also that the operating system saves this set of big registers when it switches threads. If anything is missing, it treats the CPU as having no AVX-512. Code fact Then it picks a kernel in this order:

If you studied CS: this is "runtime dispatch", the same idea as virtual functions in object-oriented programming: the call site stays the same, and which code really runs is decided only at run time. The difference is that the deciding factor here is not the object's type but the feature bits CPUID returns.

22.3 GPU: one CUDA-style source, two engines for NVIDIA and AMD

On the CPU side, one program file carries two sets of kernels and picks at run time. The GPU side goes further: NVIDIA and AMD cards have completely different instructions, even different programming platforms, so the only option is to build a separate engine for each vendor.

CUDA and HIP

CUDA is NVIDIA's GPU programming platform: a set of C++ syntax extensions, a runtime function library, and the nvcc compiler. Programmers use it to write functions that run in parallel on the GPU, then call functions such as cudaMalloc and cudaMemcpy to allocate VRAM and move data. CUDA can only produce machine code for NVIDIA cards.

HIP is AMD's counterpart on the ROCm platform. It is deliberately modeled on CUDA: most function names just swap the prefix cuda for hip, so cudaMalloc becomes hipMalloc, with essentially the same meaning. So a piece of CUDA code can often compile on AMD cards after nothing more than "renaming". AMD even provides an official tool, HIPIFY, that does the renaming automatically.

Beyond renaming, some differences cannot be renamed away. A GPU bundles a group of threads that execute in lockstep; NVIDIA calls it a warp and AMD a wavefront (wave for short). On NVIDIA a group is always 32 threads; older AMD architectures use 64, and the RDNA series can use 32. Code that relies on "a group of 32" goes wrong on a 64-wide machine. Strata's HIP backend supports only wave32 and checks again at startup. Code fact v0.1.39 added a separate build, turned on by hand, for gfx906, which is wave64: it uses a different compatibility layer that maps one CUDA warp to half of a 64-thread wavefront, and you can choose only one of it and the HIP backend. Upstream report Chapter 15 covers threads, warps and related ideas in detail.

How this ties to the chapter: Strata does not use a tool to rewrite its source. Instead it slips a "renaming table" into every source file automatically at compile time. We look at how right below.

Further reading: ROCm docs: What is HIP · ROCm docs: porting from CUDA to HIP · NVIDIA: CUDA Programming Guide · Wikipedia: CUDA · Wikipedia: ROCm

Strata's GPU code is written CUDA-style in .cu files, 56 of them under the src directory. One of them, new in v0.1.40, is a matrix-core kernel for RDNA3 cards, compiled only in the AMD build. Turning on the HIP build switch does three things: Code fact

  1. The build script marks every .cu file as HIP language and hands it to AMD's compiler.
  2. The compile flags gain -include hip_compat/cuda_runtime.h, which forces this shim header onto the very top of every source file. A shim here means a thin layer of code wedged between two layers, existing only to smooth over their differences.
  3. The shim holds 91 macros of the form #define cudaMalloc hipMalloc; a few of the names have two spellings, chosen by HIP version or platform, and each compile keeps only one. Another cublas_v2.h shim handles the matrix library names: 17 lines for the new hipBLAS, and for the old 0.x versions another 15 lines that switch straight to the names of the lower-level rocBLAS. Once the preprocessor substitutes them, the CUDA names have become HIP names.

The build script also rules that the CUDA and HIP switches cannot both be on: one build compiles only one backend. Code fact

Renaming alone is not enough. Some CUDA GPU built-in functions have no ready-made HIP equivalent on RDNA cards, so the shim has to implement them itself. Take the four-byte dot product __dp4a: split each of two 32-bit integers into 4 signed bytes, multiply the matching pairs, and add the results into an accumulator. The shim splits this four ways by GPU architecture (see the primer in Section 22.1). Or take __shfl_xor_sync, which swaps data within a warp: the shim first checks "are all 32 lanes taking part", and if not, it aborts immediately instead of quietly dropping that part of the meaning. Code fact

Suppose your GPU architecture is on the list and the engine compiled. Is that "supported"? Strata's own build script gives a very fine-grained answer. It sorts AMD architectures into three tiers, and CMake reacts differently to each tier at configure time: Code fact

Intel graphics cards take a third road that does not go through the CUDA→HIP shim above. The sycl/ directory in the repository ports Strata's engine to SYCL (the C++ programming model used by Intel oneAPI). The second trap is numbers. The dp4a in Figure 22-5 is integer math, so every path matches bit for bit. Floating point is different: change the order of additions and the last few digits may differ (Chapter 4 covered floating-point rounding). Strata's AMD docs say outright that the two backends are not promised to give bit-identical answers. Upstream report This happens on a single machine too. With IQ-series models, the CPU uses ggml's dot product when it computes one token alone and Strata's multi-token kernel when it computes a group, and the two round slightly differently; how many tokens a group holds depends on the drafts. So even at temperature 0, the same prompt can get a different but equally reasonable answer. From engine 0.1.30 you can set STRATA_IQ_MT_MIN=1 to remove this difference; the cost, measured upstream on a Ryzen 7600 (AVX-512), is IQ3_S decoding 1–3% slower. The CPU uses its own activation format, so the rows it computes are not bit-identical to the card's; set STRATA_PREFILL_CPU_SHARE=0 to turn it off. Remember these three

  1. A chip understands only its own instruction set. The same source must be compiled once for each target; conditional compilation lets one source keep only the branch that matches the target in each compile.
  2. On the CPU, Strata dispatches at run time: it first asks via CPUID whether AVX-512 and AVX2 are present, then picks a kernel. On the GPU, it dispatches at compile time: a CUDA→HIP renaming table plus a few hand-written built-in functions build two engines, one for NVIDIA and one for AMD.
  3. Compiles, tests pass, runs on a real card, and maintainer verified are four different levels of evidence. Floating-point results are not guaranteed bit-identical across backends either, so record build configurations and environment variables as experimental conditions.

Common misconception: "If the code compiles on my graphics card, my card is supported."

Compiling only shows that the compiler recognizes the code. Strata's build script has a ready-made counterexample: gfx1011 compiles, and the upstream docs say it builds with 0 errors, but nobody has run it on a real card, so configuring still prints a "not verified" warning. gfx1102 has gone further: it passes the built-in tests and one user has run a complete model, yet it is still marked "not verified", because there is only one report and the maintainers have not reproduced it. Real support comes from running a real model on a real card, getting results that check out, and someone being able to reproduce it.

Go deeper: compile time vs run time, the limits of the shim, and support statements

Why the AVX-512 switch is added only to single files

The build script's comment gives the reason: in a source file compiled with /arch:AVX512, the compiler may use AVX-512 instructions anywhere, including in the scalar code you thought was the "fallback". If the scalar fallback and the AVX-512 kernel sat in the same file, the fallback would no longer be a fallback and would crash on old CPUs just the same. So Strata adds the switch only to kernel files, and the CPU-probing function lives in a file without the switch, guaranteeing that the "just asking" step is safe on any x86-64 CPU. Code fact

The probe itself also uses conditional compilation: the same CPUID code uses __cpuidex and _xgetbv under MSVC, and __cpuid_count plus inline-assembly xgetbv under GCC/Clang. Checking the XCR0 register confirms that the operating system saves AVX-512's big registers on thread switches; if the CPU supports it but the OS does not save them, it still cannot be used. Code fact

The limits of the shim: abort rather than quietly change the meaning

CUDA's warp shuffle functions take a mask argument saying "which lanes take part". The matching HIP functions have no such argument. The shim's approach: the current kernels only use the full mask, so any call without a full mask aborts immediately (__builtin_trap) instead of dropping the mask and carrying on. __nanosleep counts clock cycles in CUDA, while AMD's sleep instruction accepts only 0 to 15, so the shim simply always uses the minimum, 1, because here it is treated only as a hint to "wait a moment". Code fact

The four dp4a paths each have their subtleties too. RDNA3/RDNA4's sudot4 instruction lets you say separately whether each operand is signed, and the shim marks both as signed so that it matches the meaning of CUDA's __dp4a. RDNA2's sdot4 is already "signed × signed, accumulated modulo 2³²", the same meaning. The RDNA1 assembly first sign-extends each byte and multiplies (v_mul_i32_i24), then uses v_add3_u32 to add two products into the accumulator at a time; 32-bit unsigned addition is already modulo 2³². This code is adapted from llama.cpp; with the compile switch STRATA_GFX1012_PORTABLE_DOT on, gfx1012 uses the portable loop instead, which makes comparison easy. The portable loop accumulates in an unsigned 32-bit integer and then reads it as signed, which is likewise modulo 2³². This chapter's simulator test file checks one by one that the RDNA1 assembly, the portable loop and the vmad form for old NVIDIA cards match the reference bit for bit even at the overflow boundaries.

The name does not decide the format: dispatch by type

The same tensor name may use different quantization formats in different layers. A comment in layer.cpp records a lesson: early code assumed "the name decides the format", for example that attn_qkv is always some K-quant; in the actual model pack, the attn_qkv of the 36 GDN layers comes in four formats: IQ4_XS, Q3_K, Q2_0 and Q4_K. So the rule changed to dispatch by type: 2-bit codes go through Q8_0 activations, other quantization formats through Q8_K. Get it wrong and the matrix-vector product is off by 0.6%–1.4%: what comes out is a "plausible-looking" vector rather than an obviously broken one, which is the hardest kind to catch. Code fact[S14]

Pin the dependencies too

Strata's CPU experts use ggml-cpu's dot product, and the build pulls ggml from the llama.cpp repository. It pulls not "the latest" but a commit hard-coded in third_party/ggml/VERSION.txt. Code fact The reason is the same as this book pinning Strata's commit: when a dependency changes, the numerical path may change.

A minimal support statement

When writing a support statement for a new backend, state at least:

  • The source commit; the compiler and its version; the list of target architectures; every compile switch; the versions of dependency libraries; the runtime environment variables.
  • The devices, drivers, model packs, quantization formats and KV formats tested, both the prefill and decode paths, and the range of context lengths.
  • Evidence listed by level: compiles, built-in tests pass, tensor-level comparison (error against a reference implementation), end-to-end quality, stability, performance.
  • Untested combinations listed explicitly as "untested"; never write "fully supported".

Two binaries built from the same commit may take different code paths if their compile switches differ. The startup log should say which backend, which CPU path and whether a fallback was actually used; when Strata starts on a CPU without AVX-512, it prints whether it switched to AVX2 or ggml. Code fact Users should not have to guess from the file name.

The tail of vectorization

When a vector's length is not divisible by the number of lanes, the leftover "tail" must be handled with a mask or a separate scalar path. Reading a few extra bytes to save effort may read the next expert's data: it does not necessarily crash, but the result is wrong. When Strata loads native experts, it first checks that each expert's size is a whole multiple of the format's block size, and refuses it otherwise. Code fact
