You may have noticed

In a chat web page, the answer pops out one word at a time. Skip the web page and call your local Strata's API from the command line, and you see something else: line after line of data: {…}, a blank line between each, and a last line that reads data: [DONE].

These lines are SSE (Server-Sent Events). They leave the server as a stream of bytes, and before they reach you, the network cuts them into chunks of any size it likes. One Chinese character can be cut in half; one message can arrive in two pieces. This chapter explains how to put those pieces back together into a complete sentence with no garbled text.

In one line: between a token the model emits and the text on your screen there are three gates: bytes become characters (UTF-8), characters become events (the SSE blank line), and events become structure (JSON). At each gate, collect a complete unit first, then process it.

23.1 Between the model and your app sits a serving layer

The inference engine understands only token IDs: give it a list of IDs and it emits new IDs one after another. Your app speaks another language: it sends a chat message in JSON and expects pieces of text back. The translator in the middle is the serving layer. Figure 23-1 shows Strata's serving layer.

serve/server.py states its job right at the top: on top of "any engine that maps token IDs to tokens", it offers APIs in two styles, OpenAI and Anthropic. The endpoints include POST /v1/chat/completions (OpenAI style, streaming and non-streaming), POST /v1/messages (Anthropic style), GET /v1/models, GET /health and more. Code fact[S15] v0.1.39 also added OpenAI's Responses API, POST /v1/responses, for the Codex CLI. It is stateless: the server stores no answers, and the client sends the whole conversation every time. The endpoint list at the top of the file does not mention it yet: a comment lagging behind the code. Code fact

Its contract with the engine is a single function: Engine.generate(prompt_ids, max_new, sampling, cancel), which returns an iterator that yields token IDs one by one. The real StrataEngine keeps one strata --serve process running and talks to it over standard input and output; MockEngine emits tokens from a script, so every API path can be tested on a machine with no GPU. [S15]

The first sentence of serve/frontend.py reads: "Everything here is text: no model, no GPU." It does three things. It turns the OpenAI and Anthropic request formats into the one message list the chat template wants. It renders the prompt with the model's own Jinja template, checked against Hugging Face's output on 10 samples. And it splits the streamed output, piece by piece, into thinking, text and tool calls, and never sends half a tag. Code fact[S16]

If you studied CS: this is a pocket version of the layering idea from Computer Networks: each layer talks only to the layer above and the layer below, and as long as the interface is agreed, the inside of a layer can be swapped freely. MockEngine can stand in for the real engine precisely because the boundary is just one function, generate.

23.2 How an answer can be sent while it is being written

An ordinary web request is one question, one answer: the browser sends a request, the server prepares the whole response and sends it back in one go. For a large model, that means waiting tens of seconds before you see the first word. A streaming response works differently: the same answer is split into many small pieces, and each piece goes out as soon as it is written. Figure 23-2 compares the two.

HTTP and streaming (SSE)

HTTP is the set of rules browsers and servers use to talk. One exchange has two halves: the client sends a request (which path to visit, what data to bring), and the server returns a response (a status code, such as 200 for success, 400 for a bad request, 401 for failed authentication; plus some headers and a body). The Content-Type header tells the other side what format the body is in.

A normal response writes its body in one go. SSE instead sets the response's Content-Type to text/event-stream and keeps the connection open; the server writes a piece whenever it has one, and each piece is called an event. The format is very plain:

  • each event is made of a few lines, and lines starting with data: carry the data;
  • a blank line ends the event;
  • a line starting with a colon is a comment, and the client simply ignores it;
  • an optional event: line gives the event a name.

An example: the server writes data: hello, a newline, then a blank line, and the client receives one event whose content is "hello". The standard also requires: the event stream must be UTF-8; a line may end with LF, CR or CRLF; several data lines in one event are joined with newlines; and if the stream breaks in the middle of an event, that half event is thrown away, never delivered as if it were complete. [R05]

How this relates to Strata: add "stream": true to /v1/chat/completions and the answer comes back as SSE; leave it out, and you get one JSON object after generation ends.

Further reading: MDN: An overview of HTTP · MDN: Using server-sent events · HTML Standard: Server-sent events · Wikipedia: HTTP

Strata's SSE code is short. It first returns status 200 with the headers Content-Type: text/event-stream and Cache-Control: no-cache, plus X-Accel-Buffering: no, which asks reverse proxies such as nginx not to hold events back but to forward each one the moment it arrives. Code fact After that, each piece of the answer is written as data: plus a piece of JSON plus a blank line; when everything is done it writes data: [DONE]. Figure 23-3 takes that byte stream apart.

Note the : keep-alive line in the middle. While it reads a very long prompt, the engine may not emit a token for several minutes. During that time Strata produces a "heartbeat" every 10 seconds, and the HTTP layer writes it as an SSE comment. Code fact The client ignores comments, but because bytes keep coming in, it does not decide the connection is dead; and when the server writes, it also finds out whether the other side has already left (Chapter 24 covers this in detail). The Responses API of v0.1.39 goes one step further: the Codex CLI counts only real events as "still working" and ignores comments, so while a long prompt is read, the server sends an extra response.in_progress event every 15 seconds. 23.3 One Chinese character, three bytes

The network knows bytes, not characters. Take a simplified event, data: {"delta":"你好"} ("hello" in Chinese). With the blank line at the end it is 26 bytes on the wire, and the two characters 你 and 好 take 3 bytes each. Here is the problem: how big each "chunk" is that a TCP connection hands to the program is decided by the network and the operating system, and it has nothing to do with character boundaries. The 3 bytes of one Chinese character can easily end up with the first byte in this chunk and the other two in the next.

UTF-8: how many bytes a character takes

Every character in a computer has a number, called its code point; for example, the Chinese character 中 ("middle") is U+4E2D. UTF-8 is a set of rules for writing code points as bytes: common characters such as English letters take just 1 byte, exactly as in old ASCII; most Chinese characters take 3 bytes; emoji take 4.

The clever part is that every byte "carries its own ID", as Figure 23-4 shows. The number of 1s at the start of the first byte tells you how many bytes the character takes; every following byte starts with 10 and is called a continuation byte. So when a decoder reads E4 (binary 1110 0100) it knows two continuation bytes should follow. If the chunk ends right there, the right move is to hold on to E4 and join it with the next chunk when that arrives.

Python's codecs.getincrementaldecoder and the browser's TextDecoder (with stream: true) are both such incremental decoders. If instead you decode each chunk on its own, half a character turns into the replacement character �, and it can never be put back together.

Further reading: Wikipedia: UTF-8 · MDN: TextDecoder · Python docs: codecs · RFC 3629: UTF-8

Strata itself has to deal with this, and at an earlier point: one token of the model is not always one whole character. The Detokenizer in serve/server.py feeds each token's bytes into an incremental UTF-8 decoder; complete characters go out at once, and half a character that spans tokens is held until later tokens complete it. Code fact A code comment also keeps the books: the old approach decoded all generated IDs again for every new token, which cost an extra 2 milliseconds per token by the time the answer reached 8K tokens, and 4 milliseconds at 16K; incremental decoding costs a constant amount per token.

Once the server writes the bytes out, the client has to solve the same problem again, with one more layer on top: events get cut apart too. The slicer below cuts a 126-byte SSE stream into random chunks and lets two clients receive it side by side:

23.4 JSON: what an event carries is structure

SSE only cuts out events; it does not care what is inside them. After data:, Strata puts a piece of JSON.

JSON: a data format both people and programs can read

JSON describes structured data with very few rules: curly braces {} hold a set of "name: value" pairs, square brackets [] hold a list, and a value can be a string, a number, true/false, null, or another nested level. For example, {"delta":{"content":"hello"}} means: the content inside delta is "hello".

Parsing JSON has one hard requirement: the text must be complete. Miss one closing brace or half a quote and the parser reports an error. That is exactly why you first cut out a complete event at the blank line, and only then parse it.

A non-ASCII character in a JSON string can be written two ways: as raw UTF-8 bytes, or as an escape like \u4e2d. Both mean the same thing, but the byte counts differ; see Figure 23-6.

Further reading: Wikipedia: JSON · MDN: JSON · Python docs: json (including ensure_ascii) · RFC 8259

When Strata writes a streaming event it calls json.dumps(c, ensure_ascii=False), so Chinese goes out as raw UTF-8. Code fact If it switched to escapes, the wire would carry only ASCII bytes and there would be no more "half characters"; but Chinese text would double in size, the SSE standard already requires UTF-8 decoding, and events would still be cut apart. So the right direction is for the client to do honest incremental decoding, not to dodge the problem with escapes.

Chain the three gates together, and the order cannot change:

  1. Bytes → characters: incremental UTF-8 decoding, holding incomplete bytes;
  2. Characters → events: collect text in a buffer, cut out a complete event only at a blank line, drop comments;
  3. Events → structure: parse the complete data as JSON and take out the text.

If you studied CS: this follows the same idea as the "character stream → lexer → parser" pipeline in Compilers: each stage works only after the stage before it hands over a complete unit. TCP guarantees only the order of bytes, never the completeness of any higher-level unit.

23.5 The model's output must also be "collected before sent"

The same trouble shows up once more inside the server. This model "thinks" before it answers: its thinking goes between <think> and </think>; when it needs a tool, it writes tags like <tool_call><function=name><parameter=param>value</parameter>…. These tags are meant for programs and should never appear on your screen.

The trouble is that tags can be cut apart too: one step emits </th, and only the next step emits ink>. The OutputParser in frontend.py exists for exactly this: it holds a tag that has been cut apart until it is complete, then handles it. So the client never sees half tags like <tool_ or </thi. Code fact[S16]

The real OutputParser does two things this widget leaves out. First, it reports tool-call progress while the call is being written: a start event as soon as the tool name appears, and the arguments piece by piece, so the client does not sit idle for minutes while the model writes a large file. Code fact Second, it treats the newlines around tags with care, so that streamed output and one-shot output come out exactly the same.

Tool calls also touch on security. A model writing a function name does not mean the system allows that function to run: model output is untrusted input, and you must check the arguments and the permissions before you execute anything. Strata offers MCP tools only to requests that explicitly ask for them (with "strata_mcp": true); every other client sees exactly the same API as before. 23.6 Hands-on: cut the same stream into any size

Open this chapter's lab, "Byte chunks are not events". It cuts an SSE stream containing Chinese text into fixed-size chunks from 1 to 32 bytes, then restores it with the three correct gates. Try three things in order:

  1. Go from 1 byte all the way to 32 bytes: for every chunk size, the restored text must be exactly the same. If even one size gives a different result, the parser has a bug.
  2. Turn on CRLF line endings: SSE allows three kinds of line endings, and the parser must accept all of them.
  3. Watch the "unfinished" buffer: when the stream breaks in the middle of an event, that half event must stay pending or raise an error; it must not pretend to be complete.

Then go back to this chapter's two interactive figures and run the chunk size at 1 byte and at 64 bytes. You will see it more directly: the smaller the chunks, the more obviously the careless approach fails; the bigger the chunks, the deeper the bug hides.

Remember these three

  1. Strata's serving layer turns the app's JSON request into token IDs, turns the tokens the engine emits back into text, and sends it back as an SSE event stream. Between it and the engine there is only one interface, Engine.generate.
  2. Getting from bytes to text takes three gates: incremental UTF-8 decoding, cutting events at blank lines, and parsing complete JSON. Network chunk boundaries have nothing to do with any of these three boundaries, so collect a complete unit before each gate.
  3. Tags in the model's output get cut apart too. Strata's OutputParser holds any tail that might start a tag and never sends half a tag; a tool call counts only once it is fully written.

Common misconception: "Count the SSE events and you know how many tokens the model generated."

The two have no fixed relation. Strata's first event only announces "the assistant starts speaking" and holds no token; keep-alive comments appear while a long prompt is being read; when a token brings only half a Chinese character, that step has no text to send; and while a tag is being held, nothing may go out for a moment. The other way round, the text in one event can come from several tokens. To count tokens, read the usage field at the end of the response; do not count events.

Go deeper: the exact rules at the three boundaries, what "compatible" covers, and how to test

The three boundaries, as the standard spells them out

The SSE standard's requirements for a parser come down to a few rules [R05]: decode the event stream as UTF-8; a line may end with CRLF, a lone LF or a lone CR; a blank line dispatches one event; several data lines in one event are joined with LF; a line starting with a colon is a comment; and when the stream ends, a half event that did not end with a blank line is thrown away.

That gives the order of implementation: incremental byte decoding → accumulate text and frame it at event boundaries → parse the data payload. Calling JSON.parse on every chunk you read gets bitten by both character splits and event splits. This book's lab implements only a data-only subset, supports LF and CRLF, and does not implement EventSource's automatic reconnection or the id and retry fields, so it is not a complete SSE client.

Worked example: one Chinese character across three chunks

The three bytes of 中, E4 B8 AD, land in three network chunks. Decoding each chunk as complete text gives three replacement characters. An incremental decoder reading E4 knows two bytes are still missing and holds it; after B8, one is still missing; only after AD does it output 中. In the same way, the two newlines after data: {"delta":"中"} can be cut at any point: at the colon, at a quote, or between the two newlines. The number of network chunks and the number of tokens have no fixed relation.

"OpenAI-compatible" means a subset of the API

Read "compatible" in terms of which endpoints, which fields and which semantics are implemented; a path that looks like /v1/... does not prove full compatibility. This book describes only the endpoints and boundaries listed at the top of serve/server.py [S15] and has not audited every protocol field one by one. The /v1/responses endpoint added in v0.1.39 is not in that list. Each of its streaming events carries an event: line with a name, starting with response.created and ending with response.completed (or incomplete, or failed). This book has not audited it either. Upstream report A few details the source confirms: the first event's delta is {"role":"assistant","content":""}; thinking goes in the reasoning_content field; and an end caused by cancellation is reported to the client as stop.

What if an error shows up after the stream has started?

The HTTP status code lives in the response headers, and once the headers are sent they cannot change. So Strata catches what it can before the stream starts: if the prompt length plus the maximum output length exceeds the context, it rejects the request with 400 and never silently truncates. [S15] If the engine reports an error only after the stream has started (for example, the engine process exits unexpectedly), the status is already 200, so Strata writes an event with an error field into the stream, then writes data: [DONE] to end it normally; the Anthropic-style API writes an event: error event instead. Code fact Clients must check the content of events, not just the status code.

The template sandbox covers only the template layer

frontend.py renders the chat template with Jinja's ImmutableSandboxedEnvironment. [S16] That is a concrete defense at the template layer that limits what template code can do; it does not automatically prove that tool execution, fetching image URLs or reading local files are safe too. Each kind of resource access needs its own threat model. Strata has one more check for MCP tools: only Strata's own web page (or an origin the config explicitly trusts), sending JSON, can let the model use these tools, because the tools run with your permissions on this computer. Code fact

How to test it, and the limits of the evidence

Testing the SSE parser: cut two JSON events containing Chinese into chunks of 1 to 32 bytes and require every chunk size to restore exactly the same result; add CRLF, multi-line data and a truncated final event as test cases; a truncated event must stay unfinished or raise an error, never fake success.

MockEngine can verify streaming and non-streaming responses, cancellation, tool arguments and the closing events on error, but it cannot prove the quality or real performance of GPU inference. [S15] That is the benefit of layered testing, and also the limit of its evidence.
