You may have noticed

Chat web pages have a "Stop" button. Click it, and the text freezes at once. But did the graphics card (GPU) really stop?

Strata's source has a very candid comment (issues #430 and #431): it used to be that after a client hung up, the request kept the engine busy until the answer was finished, or until the whole prompt had been read. The screen had long since stopped, and the GPU was still working for someone who had already left. This chapter covers three things: how a request is born and how it ends; how "stop" travels layer by layer down to the GPU; and who is allowed to put your GPU to work.

In one line: a request passes through four layers: the browser, the HTTP connection, the server process and the engine process. "Stop" is a signal that must be passed down and confirmed at every layer; "authentication" decides who can send a request in at all.

24.1 You clicked "Stop". What actually stopped?

Between your click and the moment the GPU stops computing for this request lie several layers. Each layer means something different by "stopped"; see Figure 24-1.

To make this precise, first draw a state machine for the request: at any moment the request is in exactly one state, and only certain events can move it to another. Here is this book's teaching version:

  • Queued: the request has arrived, but the engine is serving someone else. By default, Strata serves one sequence at a time, and later arrivals wait in a FIFO (first in, first out) queue. [S15] v0.1.39 added a "parallel": N that you must turn on by hand: up to N conversations decode together in the engine, and extra requests wait for a free slot. Upstream report[S01] This chapter covers only the default single-sequence path.
  • Prefill: the engine reads your prompt chunk by chunk (the prefill, "reading the prompt", from Chapter 1).
  • Decode: it writes the answer one token at a time (decode, "writing the answer").
  • Done / Cancelled / Failed: three end states. Every request must end in one of them; none may be left hanging.
  • Cancelling: "stop" has been called, but the engine has not yet confirmed that it stopped. This in-between state is the easiest one to overlook.

These state names are this book's abstraction, not an enum in the upstream code. What Strata actually records is whether a request is "queued" or "generating", plus a short phase note such as "reading the prompt" or "answering". Code fact The simulator below slows the whole process down:

24.2 Processes and threads: who is actually doing the work

To know where "stop" must go, you first need to know who is doing the work.

The life cycle of processes and threads

A process is a running program. The operating system gives it its own separate block of memory, plus resources such as open files and network connections. By default two processes cannot see each other's memory; they can only pass messages through channels such as pipes or the network. When a process ends, the operating system takes back all the RAM and VRAM it held.

A thread is one line of execution inside a process. A process can have several threads; they share the same memory, which makes exchanging data easy but also makes it easy for them to step on each other's toes.

Both have a life cycle: created, running, waiting (for network data, say) and ended. There are two ways to end: finish on your own, or be ended by someone else. On Unix-like systems one process can send another a signal: SIGTERM means "please exit", and the receiver gets a chance to tidy up first; SIGKILL means "end right now", and the receiver gets no chance to clean up at all.

How this relates to Strata: the server and the engine are two processes that pass text line by line through pipes; inside the server, several threads split the work, as Figure 24-3 shows.

Further reading: Wikipedia: Process (computing) · Wikipedia: Thread (computing) · OSTEP: The Abstraction: The Process · Python docs: subprocess · man 7 signal

The server starts strata --serve with Python's subprocess.Popen and connects both its standard input and its standard output to pipes. Code fact Once the engine has loaded its weights, it first writes a few INFO lines, then a READY line with the context length; if that line also carries stop, this engine version supports stopping midway. Only when the server reads READY does it treat the engine as "alive". After that, the server writes a GEN line to submit a request, and the engine answers with T (one token), PP (prefill progress), DONE (finished) or ERR (error).

A dedicated reader thread puts every line of engine output into a queue. That way, the thread handling a request can wait for the next line "with a timeout": if nothing comes, it can send a heartbeat and check the cancel flag first, instead of waiting blindly forever. Code fact

The engine process can also die unexpectedly. The code has a dedicated EngineDied exception, and its comment names the most common cause: on Linux, being killed by the OOM killer when memory runs out. [S15] When that happens, the current request ends with an error, and when the next request arrives, the server restarts the engine with the same command. Since v0.1.39, if the new process exits before it says READY, the server waits 15 seconds and tries again, up to 3 times: the VRAM of the engine that just died may take a while to come back. Code fact

Shutting the engine down normally also takes care. The server goes in three steps, waiting at most 20 seconds at each; see Figure 24-4.

A comment explains why the first step is QUIT: the engine frees its memory itself, and unlocking tens of GB of pinned memory takes a while. Code fact If all three steps fail, the server raises EngineStuck and keeps its record of the process; it does not claim that the process's VRAM and RAM have been returned. Also, on Windows the server puts the engine into a job object set to "kill on close". That way, even if you simply close the console window, the engine ends with it and does not become an orphan process nobody looks after. Code fact

24.3 Cancellation: passing "stop" down layer by layer

Cancellation: why you can only say "please stop"

The most direct way to cancel is to cut off the working thread from outside. But that is dangerous: it might be holding a lock, be halfway through writing a data structure, or be borrowing a block of VRAM. Cut it off, and the lock is never released, the data is half new and half old, and everyone after it goes wrong.

So most real systems use cooperative cancellation: the outside only sets a cancel flag, and the worker glances at the flag at agreed checkpoints; when it sees the flag, it cleans up and exits on its own. Python's threading.Event, Go's context and C#'s CancellationToken all follow this idea.

Two rules follow. First, cancellation is not instant; in the worst case you wait until the next checkpoint. Second, the farther apart the checkpoints, the slower the cancellation. So "called stop" and "really stopped" are two different things, and the stretch between them is the "Cancelling" state in Figure 24-2.

Further reading: Python docs: threading (Event objects) · OSTEP: Concurrency: An Introduction · Wikipedia: Multithreading

Strata's cancellation is cooperative. At the start of each request, the server creates a threading.Event as the cancel flag. Two paths can set it:

  • A write fails: an error while the server writes an SSE event to the connection means the client has left, so the flag is set at once. The comment says: "Client went away: stop the engine." Code fact
  • A watcher thread: a failed write alone is not enough. While a long prompt is being read, the server writes a keep-alive comment only once in a long while, and the first write after a hang-up usually still "succeeds". So each request gets its own watcher thread that checks the connection every 0.5 seconds: if the connection shows "readable" but yields no data, the other side has closed it, and the flag is set. Code fact This is exactly the fix for #430 and #431 mentioned at the start.

Once the flag is set, it takes effect through checkpoints; see Figure 24-5.

Where is the checkpoint in step ⑤? During decode, the loop glances at the flag every time it produces a token. During prefill, the engine reads chunk by chunk: should_stop in prefill.hpp is checked once before each chunk starts, and if it returns true the prefill ends early with the error message "cancelled". Code fact[S12] The server's comment also says so: a STOP sent during prefill is seen only after the current chunk has been read. One chunk can hold up to 32768 tokens. [S15] The "worst-case wait" in the interactive figure is computed from this.

Step ⑥ matters just as much. After sending STOP, the server keeps reading the engine's output until it gets this request's own DONE, and holds the FIFO lock the whole time. The comment explains why: if it let go early, a leftover DONE from the previous request would still sit in the engine queue, and the next request would take it as its own end signal. Code fact This step also has a time limit: the wait for the STOP echo is never unbounded, because the FIFO stays taken during the wait and everyone behind is queuing.

The MockEngine used in tests follows the same contract: before emitting each token, it glances at the cancel flag. [S15] So the cancellation logic can be tested on a machine with no GPU.

24.4 What if it hangs? The watchdog

Cancellation relies on the engine "cooperating". What if the engine freezes and says nothing at all? The server needs a watchdog: after a period with no sign of life, it decides something has gone wrong.

The hard part is "how long is too long". During decode, the engine writes a line for every token, so it is chatty; while reading a very long prompt, it may stay silent for minutes. A one-size-fits-all watchdog either kills an engine that is busy reading a prompt, or waits forever on one that is truly frozen. Strata gives a different limit for each phase [S15]:

  • Base limit, 300 seconds: while a request is in progress, if the engine produces no output at all for longer than this, it is declared lost. The config can change this; 0 means wait forever.
  • First prefill chunk: on top of the 300 seconds, add the time this chunk would take on "the slowest computer, reading only 50 tokens per second".
  • After a chunk is read: the next chunk may take up to 3 times the time the last chunk actually took, but no less than 300 seconds.

The numbers in the figure come from plugging in the code's constants. Teaching estimate First chunk: 300 + 32768 ÷ 50 ≈ 955 seconds. A fast computer, at the upstream measured rate of 2171 tokens per second, reads a 32768-token chunk in about 15.1 seconds; 3 times that is 45.3 seconds, under 300, so the limit stays at 300 seconds. A slow computer at 100 tokens per second needs 327.7 seconds per chunk, and 3 times that is about 983 seconds.

What happens after a timeout? The comment calls it "the two sides out of step": the engine's main thread is waiting for the next command, while the server is waiting for this request to end. The server ends the engine process, the request ends with an error, and the engine restarts when the next request arrives. [S15] Ending the process is crude, but it has one advantage: the VRAM and RAM are sure to come back with it.

The same idea shows up at a lower level too. The Verifier that checks draft tokens has a release_gpu_waits: when a batch of GPU work is stuck and cannot finish normally, it forcibly releases every wait flag on the GPU so the batch drains out. But from then on, this Verifier refuses to run any new compute window, because that batch finished under untrusted conditions. Code fact[S08] A forced drain is not a normal finish; you cannot pretend nothing happened and keep serving the next request.

24.5 Who may use your GPU: authentication and API keys

So far: "how to stop". This section: "who may start". If anyone can send requests to your Strata, your GPU becomes a public resource.

Authentication and API keys

Authentication answers "who are you"; authorization answers "what may you do". The simplest form of authentication is an API key: the server and the client share a long random string in advance, and the client puts it in an HTTP header on every request, usually written as Authorization: Bearer your-key. If it matches, the server lets the request in; if not, it returns 401.

An API key is like a shared door key: whoever holds it can open the door, so it must stay secret. Never put it in web page source code or commit it to a public repository. Send it over HTTPS whenever you can; otherwise anyone along the way can read it.

The comparison itself needs care. An ordinary string comparison returns as soon as it hits a differing character, so the longer the correctly guessed prefix, the longer the comparison takes. By measuring the time, an attacker can guess the key one character at a time. Attacks that leak information through "side products" such as time or power use are called side-channel attacks, and this one is a timing attack. The defense is a constant-time comparison: wherever the strings first differ, it compares the whole string before returning.

Further reading: Wikipedia: API key · Wikipedia: Side-channel attack · MDN: Authorization header · Python docs: hmac.compare_digest · RFC 6750: Bearer tokens

Strata's first line of defense is listening only to this computer by default: the server listens on 127.0.0.1 by default, so other devices cannot connect at all. Code fact In that case the README says any API key will do in your app. [S01] To reach it from a phone or another computer, you change it to listen on 0.0.0.0, and the README says plainly to "always set a key". [S01] If you change the listen address but set no key, the server prints a warning at startup: there is no API key, so anyone on the network can use this model. Code fact

Once a key is set, requests to /v1/* must carry it: as Authorization: Bearer …, or in the x-api-key header (which Anthropic-style clients use). The comparison uses hmac.compare_digest, which a code comment calls "constant-time"; a mismatch returns 401 with the type authentication_error. Code fact Figure 24-7 shows the whole decision.

Why must it be constant-time? The simulator below lets you play the attacker:

In the real world each comparison differs by only a few nanoseconds, while network jitter is several milliseconds, so a real attack has to measure the same guess thousands upon thousands of times and dig out the difference with statistics. That is hard, but not impossible. Using hmac.compare_digest takes one line of code, so there is no reason to take the risk.

Strata also defends against a sneakier attack: DNS rebinding. A malicious web page you open can briefly point its own domain name at 127.0.0.1, then reach the service on your computer while posing as "its own site". So when no key is set, the server answers only requests whose Host header is a name it knows, such as localhost or an IP address; POST requests from an unknown web page origin are also refused. Once a key is set, the key decides, because someone else's web page cannot get your key. Upstream report

If you studied CS: this section touches several basics from Computer Networks and Information Security: the difference between authentication and authorization, a minimal attack surface (listening only on the loopback address by default), and side-channel attacks. Security measures stack in layers, and each layer guards only against what it is meant to guard against.

  2. After pressing Cancel, press "Engine lost" while in "Cancelling". See how the server wraps up, and why the wait for the STOP echo must also have a time limit.
  3. In the timing attack simulator, crack the key once with each comparison method, and count how many tries each takes.

If you can write Python, you can use Strata's built-in MockEngine (python -m serve.server --engine mock) to start a server on a machine with no GPU, send a streaming request with curl, press Ctrl+C partway through to disconnect, and then check the request's outcome in the server window. [S15]

Remember these three

  1. A request passes through the browser, the HTTP connection, the server process, the engine process and the GPU. Each layer means something different by "stopped"; the cancel signal must be passed down layer by layer, and confirmed.
  2. Strata's cancellation is cooperative: a watcher thread checks the connection every 0.5 seconds and sets the cancel flag; the engine stops at a checkpoint, and the server releases the FIFO only after reading this request's own DONE. During prefill the checkpoints are far apart, so cancellation is slow.
  3. Strata listens only to this computer by default. When you open it to the network you must set an API key, and the comparison uses the constant-time hmac.compare_digest to prevent timing attacks.

Common misconception: "Close the web page and the GPU stops."

Closing the web page stops only the top layer. The server first has to notice the connection is gone, then tell the engine, and the engine still has to reach its next checkpoint before it stops. Before Strata fixed #430 and #431, there were cases where the client had long since left while the engine kept computing. "Stopped" must be confirmed at each layer separately.

Go deeper: the linearization point of cancellation, late stale replies and trust boundaries

From which moment does cancellation "take effect"?

You can define cancellation like this: from some confirmed boundary on, no new token is committed to the user, and the related resources eventually stop being used. That boundary is the linearization point of the cancellation. If a flag has only been set and the prefill chunk loop or the decode loop has not yet seen it, the cancellation is not complete.

From this book's reading of serve/server.py, a request still in the queue checks the cancel flag only after it gets the FIFO lock and sends the GEN command to the engine, inside the loop that waits for engine output: when the first token or prefill progress line arrives, or after 10 seconds with no output. Code fact This means a queued request whose client hung up long ago still makes the engine start reading its prompt, and only then receives STOP. A worthwhile extension exercise: check the flag once after getting the lock and before sending the command.

Worked example: a stale reply after a timeout

Request A times out, and the service starts on request B. If A's late results still get written into the shared output queue, B may receive A's tokens, or take A's DONE as its own end. The fix is to check who each output belongs to, and not to reuse the same mutable state until the old execution is confirmed finished.

Strata does the latter: after sending STOP, it keeps reading until this request's own DONE, holding the FIFO lock the whole time; and when it records usage, it counts only the DONE that arrives during this request, because otherwise a failed or disconnected request would book the previous request's decode numbers as its own. Code fact This book has not audited every output-ownership path upstream; in class you can build this risk with a deliberately delayed mock engine, then verify the fix.

A watchdog must understand phases of work

Treating every "no text output for a while" as a deadlock kills healthy requests that are reading long prompts; waiting forever blocks the whole FIFO. A sound diagnosis must tell apart: queuing, a legitimate long computation, slow I/O, a lost child process and a protocol out of step, and it must report the state and the last progress instead of a vague "timeout". Strata adjusts its limit per prefill chunk and writes the reason for the loss into the error message, which is exactly this idea. [S15]

In the same way, "explicit model control" (load, unload) must not interrupt requests that are running or queued: the code defines ModelBusy for exactly this. [S15] The upstream docs say the control API returns 409 in that case. Upstream report

Tools, image URLs and local files are all trust boundaries

Model output is untrusted input. Tool arguments need schema validation and permission checks; fetching remote URLs involves outbound access and resource limits; reading local paths involves file permissions and path scope. Strata's image input supports three sources: base64 data, http(s) URLs and local file paths. [S15] v0.1.40 added three checks to these entry points: a network path that points to another computer is never read; an image read from a URL is capped at 32 MiB; and a web page from another site cannot make the server read a local file as an image. Code fact(server.py) Upstream also patched one entry point at a time: a community fix missed the /v1/responses entry point, and the maintainer added it at merge time. Upstream report This book has not audited whether the step where the server fetches an http(s) URL prevents SSRF. Security has to be audited entry point by entry point; you cannot declare the whole system safe because one place uses a safe library.

frontend.py renders templates in a sandboxed Jinja environment. [S16] That is a concrete choice at the template layer; it does not automatically prove that tool execution, URL fetching and file access are all safe. Each kind of resource needs its own threat model.

A checklist for "cancellation complete"

Inject these cases into the mock engine: cancel during prefill, output cut off, duplicate cancel, an unresponsive engine, late stale results, and a new request after recovery. Pass conditions: no new user-visible token is committed; every task that reads or writes the related buffers has stopped or finished; the queue and state are not misused by the next request; late stale output is recognized and dropped; resources are released exactly once; and the client gets a clear "cancelled" or "failed", not "success".
