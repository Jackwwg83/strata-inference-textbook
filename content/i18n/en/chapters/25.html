Picture this first

You have Strata running on your computer at home, and your roommates and classmates want to use it too. Five people open the web page and ask questions at the same time. Strata's README says it plainly: by default it answers one request at a time and the others queue; to answer several at once, you must turn on "parallel" in the config, and on a 12 GB graphics card that makes every answer slower. Upstream report[S01] So with the default setup, how long does the fifth person wait? And if one of them asks for a long essay, do the other four just sit there?

This chapter is a design class. In its default setup, upstream Strata serves one sequence behind a single first-in, first-out queue. v0.1.39 added a "batch slots" feature, off by default, that decodes several conversations together, normally up to 8. First we use scheduling algorithms and queueing theory to work out "how long the wait is", then we look at what has to change to turn one sequence into many, and last we compare with upstream's approach.

In one line: who goes first, how long people wait, and whether requests can be computed together are three different questions, answered by the scheduling policy, queueing theory and batching respectively; and before you change anything, every sequence's state must be cleanly isolated.

25.1 Where things stand: one lock, one queue

The top of serve/server.py says: "One sequence at a time, behind a FIFO." Code fact[S15] The implementation is simple: the serving layer has one lock, self.fifo = threading.Lock(). In the default setup, whichever request holds the lock has the engine to itself; the other requests queue outside the lock, and the "queued" count on the status page goes up by one. Code fact But that opening comment is now behind the code: later in the same file there is a "parallel" option, and when it is on, requests no longer take this lock but go to the engine's batch slots. Code fact(server.py) When a comment and the code disagree, trust the code.

On the other hand, the HTTP server is Python's ThreadingHTTPServer, with one thread per connection, so five people can all connect at the same time. Connected is not the same as served; see Figure 25-1.

Upstream does have one feature that touches on "multiple sessions": you can turn on a size-limited session parking area that keeps the state of a few conversations in RAM, so requests that take turns do not have to re-read their prompts from scratch every time. But the docs say clearly that it does not run requests concurrently. Upstream report The code that manages these parked sessions is also strict about reuse: the tokens must match exactly, the image identity must match, and the guidance mode must match; all three are required. Code fact[S10]

Real concurrency was added only in v0.1.39: write "parallel": N in the model config, and the engine opens one batch slot for each of N conversations and decodes them together. N is normally at most 8, because one batch window holds at most 8 rows; with the optional --batch-mtp added in v0.1.40, more than 8 slots can take turns entering an 8-row window. Code fact(server.py) It is off by default. The README also warns that on a 12 GB graphics card it makes every answer slower. At the end of Sections 25.4 and 25.5, we compare with upstream's implementation.

25.2 Who goes first: FIFO, SJF, round-robin

Scheduling algorithms: FIFO, SJF and round-robin

When there is one server and a crowd of customers, "whom to serve first" is the scheduling problem. An operating system giving processes CPU time, a printer ordering print jobs, and an inference service ordering requests are all the same problem. The three classic policies:

  • FIFO (first in, first out, also called FCFS, first come, first served): in order of arrival, one finishes before the next starts. Simple and fair, but one long job blocks every short job behind it; this is the convoy effect.
  • SJF (shortest job first): always do the shortest job next. You can prove that when all jobs arrive together, it gives the shortest average waiting time. It has two costs: you must know each job's length in advance, and a long job may be pushed back forever by a steady stream of short ones; this is starvation.
  • Round-robin (RR): everyone takes turns running a short stretch, called a time slice, and goes to the back of the line if not finished. Everyone gets started quickly, but switching back and forth costs something, and the average completion time is not necessarily shorter.

There is more than one yardstick, too: waiting time (finish time − arrival time − own length), first response (how soon service starts; for chat, how soon you see the first word) and throughput (how much gets done per unit of time). Each policy wins on some measures and loses on others.

Further reading: OSTEP: Scheduling: Introduction · Wikipedia: Scheduling (computing) · Wikipedia: Resource starvation · Wikipedia: Round-robin scheduling

Start with the smallest example: three requests arrive together, with answers 8, 3 and 5 tokens long. Assume each token takes 1 time unit to generate and switching takes no time. Teaching estimate

Work out FIFO: A finishes at 8, B at 11, C at 16; the waits are 0, 8 and 11, about 6.33 on average. SJF does B (3) first, then C (5), and A (8) last; the waits are 8, 0 and 3, about 3.67 on average, the shortest. Round-robin gives each one 1 unit in turn, so the first words appear at 1, 2 and 3, and everyone gets a quick response; but all three are dragged out until late, and the average wait is 7, the longest of all.

If every switch also has to save and restore a big block of sequence state (such as the GDN recurrent state from Chapter 9), a slice that is too small lets the switching cost eat up a lot of time. Fairness is not free; you have to look at first-word time, completion time, throughput and how much state gets moved, all together.

If you studied CS: this is the CPU scheduling chapter from Operating Systems, with "process" replaced by "generation request" and "CPU time slice" by "token step". There is one key difference: when an operating system switches processes, it saves only a little context such as registers; when an inference engine switches sequences, behind it sit big blocks of data such as the KV cache and recurrent state.

25.3 Queueing theory basics: at 80% busy, things start to jam

Scheduling decides who goes first, but there is a more basic question: how densely do requests arrive? However clever the scheduling policy, if work arrives faster than it gets done, the queue grows without limit.

Queueing theory basics: Little's law and M/M/1

Queueing theory studies systems of "arrive, queue, get served". It describes a system with a few quantities: the arrival rate λ (how many arrive per unit of time), the service rate μ (how many can be served per unit of time), and the utilization ρ = λ ÷ μ (the fraction of time the server is busy).

The most useful result is Little's law: L = λ × W. The average number of customers in the system, L, equals the arrival rate times the average time each one stays, W. It needs almost no assumptions, and it applies to a bubble tea shop, a highway and an inference service alike. For example, if 3 requests arrive per minute and each stays 20 seconds (1/3 minute) on average, there is 1 request in the system on average.

The simplest queueing model is called M/M/1: arrivals are random (the gaps between arrivals follow an exponential distribution), service times are random too, and there is only one server. Its average time in the system is W = 1 ÷ (μ − λ). This formula tells us something counterintuitive: the closer utilization gets to 100%, the more steeply the waiting time grows. At ρ = 50%, W is 2 times the service time; at 80%, 5 times; at 95%, 20 times.

Further reading: Wikipedia: Little's law · Wikipedia: M/M/1 queue · Wikipedia: Queueing theory

Apply it to Strata. Teaching estimate Suppose an answer takes 10 seconds on average (say 500 tokens at 50 per second); then one Strata can serve at most μ = 6 requests per minute. If 3 arrive per minute on average (ρ = 50%), the average stay is 1 ÷ (6 − 3) minutes = 20 seconds; at 4.8 per minute (ρ = 80%), it is 1 ÷ 1.2 minutes = 50 seconds; at 5.7 per minute (ρ = 95%), it becomes 200 seconds. Requests went up by less than double, but the wait went up tenfold.

M/M/1 is only a rough model: the lengths of large-model answers do not follow an exponential distribution, and prefill and decode take very different amounts of time. But its qualitative conclusion is very robust: as soon as you get close to full load, waiting gets out of hand. In a real system this means you either add machines, limit the rate (when the queue is too long, tell the user "please try again later" right away), or find a way to raise μ, which is the batching of the next section.

25.4 Continuous batching: letting several sequences move together

The two sections above assumed the engine serves one sequence at a time. One way to raise μ is to let several sequences advance together in the same computation.

Continuous batching

To generate one token, the engine has to read the relevant weights from VRAM once. Serving one sequence, one read of the weights yields only one token; serving 8 sequences at once, one read yields 8 tokens. That is the payoff of batching: it turns matrix-times-vector into matrix-times-matrix, so the weights are read once and used many times (Chapter 16 covers this in detail).

Naive static batching groups a few sequences into a batch that starts together and ends together. The problem is that answers vary in length: the short ones finish early, their places can only sit empty, and the next batch cannot start until the longest one is done.

Continuous batching (also called iteration-level scheduling) shrinks the unit of scheduling from "a batch of requests" to "one generation step": after every token, it checks whether any sequence has finished, and if so, a waiting sequence takes its place right away. The Orca system was one of the first to lay this idea out systematically; later, inference frameworks such as vLLM adopted it widely, together with paged KV cache management (Chapter 17).

Further reading: The vLLM / PagedAttention paper (arXiv) · Wikipedia: Batch processing

For an MoE model like the one Strata runs, batching has one special twist. Each sequence picks 10 experts in every layer (Chapter 10), and different sequences often pick different experts. The more sequences in a batch, the bigger the union of experts a layer has to wake up; see Figure 25-5. Teaching estimate

This estimate assumes experts are picked uniformly; real routing has hot and cold experts, so the union is smaller. But the direction is certain: in an architecture where "experts live in RAM and the CPU computes the missed ones", you cannot simply carry over what you know about batching dense models; you have to measure.

The batch slots in upstream v0.1.39 give a measurement. On an RTX 5070 (12 GB) running Q2_0, when 4 conversations decode together, the CPU has to compute 24 experts per layer, against about 8 for a single one, so one batch window takes about as long as computing 4 tokens one by one. Upstream report(BATCHING.md) 24 against 8 is 3 times, smaller than the 3.9 times of the uniform assumption in Figure 25-5; this is exactly the effect of hot and cold experts. On this card, batching buys waiting time, not speed. In the other direction, on a layer split across four 16 GB graphics cards, each card's VRAM holds most of the experts, and 8 requests together reach 360 tokens per second in total, against 120 for one request; the author of PR #559 measured these numbers. 25.5 Going multi-sequence: isolate state first, then talk speed

Suppose you decide to do it and make Strata serve two sequences at once. The first step is not writing a scheduler but making a clear list: what is shared, and what belongs to each sequence alone.

The upstream code gives a great place to start reading. SessionState in session.hpp has a comment calling it "everything one sequence needs except the weights": each layer's state, scratch space for chunk computation, and the hand-off area between the GPU and CPU expert pools. Code fact[S13] In other words, in the upstream design one sequence corresponds to one SessionState.

More important are these two lines in the comment. The 36 GDN layers share one set of scratch space, while their state is one per layer; the 12 QSA layers also share one set of scratch space, and the reason is in parentheses: "they never run at the same time". Code fact[S13] Under the premise of one sequence, layers run in order, this sharing is completely correct and also saves VRAM. But once two sequences run at the same time, the premise "never run at the same time" no longer holds: both sides write to the shared scratch space at once, and the two sequences' data get mixed into each other.

If you studied CS: this is the most classic trap in concurrent programming: code that was correct only because of a hidden assumption that "there is only one executor". When you go multi-threaded, you have to dig out every such assumption one by one and either prove mutual exclusion again or give each executor its own copy, not just put one global lock around the outside and call it done.

Next comes the VRAM budget. Upstream allocates every layer's state for the maximum context all at once when the session starts, and the comment explains that this is because it requires zero allocation on the path that generates each token: a single temporary cudaMalloc can pass every other test and still fail this one. Code fact[S13] With multiple sequences, the same principle means: before you admit a new sequence, reserve all of its state space first. Figure 25-6 works out the budget with a set of teaching numbers.

These numbers are teaching assumptions: 20 GiB of shared weights and cache, 2 GiB of state per sequence, 2 GiB of scratch space and 2 GiB of reserve. Teaching estimate Five active sequences need 20 + 5 × 2 + 2 + 2 = 34 GiB. Note two things: sequences with different context lengths have different state sizes; and if the five sequences really compute at the same time, the scratch space must also be recomputed by the level of concurrency and can no longer be one shared copy.

This gives the principle of admission control: before a sequence is promised "active", reserve its whole budget atomically; if the budget is not enough, let it queue or reject it clearly. You must not take in every request first and then hope the VRAM allocator does not fail.

The batch slots added in upstream v0.1.39 can be compared with this section's checklist. It does not let two sequences run separately; it puts S sequences into one verify window, one per row, and moves them forward layer by layer together. Row s reads and writes only the state of slot s: the GDN recurrent state, the QSA K/V and indexer, and the PLE history. This state lives in a separate session, carved the same way as the verifier's own session. Code fact[S08] The budget is also computed first and accepted after. Each slot's session takes 0.56 GiB of VRAM at a 32K context with 8-bit KV, taken from the expert cache. At startup the engine opens as many slots as the VRAM can hold, 8 at most by default; if not even two fit, it falls back to one request at a time. Upstream report(BATCHING.md) The limits are also stated clearly: by default, a request in a slot carries no MTP draft, so each window yields one token; the repetition penalty has no effect in a batch window. Upstream report(BATCHING.md) v0.1.40 added the optional --batch-mtp: each slot also verifies one MTP draft in every window, so one slot takes two rows, one 8-row window holds at most 4 slots, and the extra slots take turns entering the window. Code fact(generate.cpp) This is one more trade: it spends VRAM and rows in the window to win back the speed the drafts bring. For now it supports only a single card, and each slot needs some extra VRAM for the draft state. Users of an RTX PRO 5000 measured 31%–39% higher total throughput with 2–4 clients; this book has not re-measured it. Upstream report(BATCHING.md)

25.6 Hands-on: why the short request keeps waiting

Open this chapter's lab, "Why short requests keep waiting". It compares FIFO and round-robin on first-word time, completion time and switching cost. All requests are ready at time 0, 1 token takes 1 millisecond, and it does not model batching or prefill on a real GPU. Try these in order:

  1. With the default requests, compare FIFO and round-robin on first-word time: round-robin lets the short request start sooner.
  2. Turn up the switching cost: round-robin's total time grows, and the price of fairness becomes visible.
  3. Make the time slice bigger, until round-robin gives exactly the same result as FIFO.

Then go back to this chapter's two interactive figures: in the scheduling comparison, try "short requests keep coming" and watch SJF starve the long request; on the queueing curve, push utilization to 95% and run the simulation several times. The lab's numbers are only for discussing scheduling trade-offs; they are not benchmarks of any real system.

Remember these three

  1. In the default setup, upstream Strata serves one sequence at a time, and the other requests queue at the FIFO lock; v0.1.39 added batch slots, off by default. Scheduling policy and admission control are this chapter's design exercises. Count connections, queued requests and active sequences separately.
  2. FIFO is simple but gets blocked by long requests; SJF has the shortest average wait but starves long requests; round-robin lets everyone see a first word sooner but pays a switching cost. The closer utilization gets to 100%, the more steeply waiting grows.
  3. To go multi-sequence, first find every hidden "only one executor" assumption, such as the shared scratch space; then budget by "weights once, state once per sequence", and reserve atomically before admitting a new sequence.

Common misconception: "Strata's HTTP server is multi-threaded, so it can serve several users at the same time."

Multi-threading only lets several people connect at once. In the default setup, in front of the engine that does the real work there is a FIFO lock, and only one sequence generates at any moment. Connection concurrency, thread concurrency and sequence concurrency are three different levels; seeing ThreadingHTTPServer does not mean the engine supports continuous batching. Whether the engine can compute together depends on the engine's own settings, such as "parallel", available since v0.1.39, and not on the HTTP layer.

Go deeper: four counts, budget details, switching cost and concurrency tests

First, separate what exists from what is designed

The comment at the top of the pinned upstream serving file still says: one sequence at a time behind a FIFO. [S15] That holds in the default setup; with "parallel" on it no longer holds, because the comment did not keep up with the code. Upstream's own multi-concurrency implementation is written up in docs/BATCHING.md; this chapter only quotes its design and upstream's measurements, and this book has not re-measured them. Upstream report The person who started this book has mentioned a modified Strata branch that supports multiple concurrent requests, but that branch's source is outside the scope of this review. This chapter proposes a design and a test method for a multi-user extension; it does not claim to have audited or implemented that branch.

Count four numbers separately: concurrent HTTP connections, queued requests, sequences generating, and sequences processed in the same kernel computation. They can be completely different. Opening more threads does not automatically solve the isolation of the KV cache, GDN state, PLE state, random numbers and scratch buffers.

List who owns each piece of mutable state

Read-only weights and read-only cache contents can be shared, with proper synchronization. Each sequence's token history, KV page map, GDN state, PLE state, sampling parameters, random-number counter and cancel flag must have a clear owner. Upstream's SessionState is a good place to start reading about "sequence state other than the weights" [S13]; note that the PLE history and token window are also explicitly called "sequence state" in the comments.

Whether shared scratch space is safe depends on whether scheduling guarantees mutual exclusion. Scratch space that assumed "layers never run concurrently" breaks at once when two sessions use it at the same time, even though the code was correct before. When adding concurrency, list every single-sequence assumption instead of only looking for one global mutex.

Budget details

The 34 GiB in the main text is only a starting point. If the five sequences need their own scratch space, those 2 GiB must be recomputed by the actual concurrency; sequences with different context lengths also have different state sizes. Admission control must reserve the budget atomically before a sequence is promised active. The session parking area (an optional upstream feature) uses host RAM, which must be counted in the budget too. Upstream report Upstream's batch slots do the same: with KV streaming on, each slot's whole KV cache also takes pinned memory, 1.6 GB at a 128K context. Upstream report(BATCHING.md)

The real cost of round-robin

The teaching simulation assumes switching costs nothing, or a fixed constant. When a real engine switches sequences, if it has to move one sequence's KV cache and recurrent state out of VRAM and move another's in, a slice that is too small lets the moving cost overwhelm the computing. So a "fairness" evaluation must look at first-word time, completion time, throughput and the amount of state moved, all together. SJF has one more practical problem: an answer's length is unknown until it is fully generated, so it can only be estimated; to prevent starvation, a common approach is to give requests a higher priority the longer they wait, which is called aging.

Worked example: the last slot, two requests at the same moment

Test assertions: exactly one request gets a valid budget and becomes active, and the other queues or is clearly rejected; nothing is reserved twice, and a client retry must not create two sessions. After completion or cancellation, the budget is released exactly once; an old request must not keep writing into the state of a new slot.

Concurrency tests must hit the "state leaking across" risk

Design two fixed requests, A and B, in different languages or tasks. First run each alone and record the reference outputs; then run them interleaved or in parallel. Cover these cases: A is cancelled while B continues; A is in a long prefill while B is decoding; the same prefix with different images; session restore; and two requests racing for the last slot of budget.

Upstream's acceptance test for batch slots follows the same idea: run the same batch of conversations alone first, then run them together in slots, and compare token by token. It covers cases such as a long prompt being read while two others decode, a long prompt giving way to a short one and then continuing, and the next turn continuing from its slot. To make the comparison bit-for-bit identical, you must also turn off a few rounding choices that change with the window, such as setting STRATA_IQ_MT_MIN=1 and adding --pcie-frac 0. Upstream report(BATCHING.md)

Minimum pass conditions: state isolation is correct, no promise exceeds the budget, nothing ends twice, no output from an old request leaks in, and no long request starves. A system whose total throughput went up but that occasionally mixes up contexts is not an acceptable concurrent inference service.

The limits of the simulators' evidence

This chapter's two interactive figures and its lab are discrete teaching simulations: every token takes a fixed time, and there is no real prefill, draft verification, prefix hit, GPU kernel or cache contention. They are only for discussing scheduling trade-offs; the ratios they show must not be used to advertise the performance of any real system.
