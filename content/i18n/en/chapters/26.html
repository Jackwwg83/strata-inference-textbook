It starts with a startup warning

Strata used to print a warning every time it started. Roughly: the expert computation on the graphics card is "not correct", and no output it produces can be trusted. Later, issue #23 asked a blunt question: if I turn on the expert cache, do the answers get worse? Upstream report

The author ran an experiment: the same text, once with the cache on and once with it off, comparing the model's prediction position by position. The result is a little counter-intuitive. At 2%–5% of the positions, the two runs picked a different "most likely next word"; yet overall, neither was more accurate than the other. Different, and both right. That is where this chapter begins: how do you test a system when you cannot even pin down a single "correct answer"?

In one line: test an inference engine in layers. Small functions are checked against exact answers, single kernels against an independent reference implementation, and the whole model by feeding both sides the same text and comparing position by position. The last few digits of a float change with the order of computation, so "equal" must first be defined as a comparison with a tolerance. And a good test must also prove that it really catches a bug you plant on purpose.

26.1 Why "looks right" is the most dangerous case

A program can go wrong in two ways. One is a crash: an error, an exit, a screen of garbage. That kind of bug is easy to find; the first run exposes it. The other kind is nastier: the program runs as usual, prints a normal-looking number, and the sentence it generates reads smoothly, but the content is already wrong. Figure 26-1 puts the two side by side.

Inference engines are especially prone to the right-hand kind. The reason is simple: the model outputs a list of probabilities, so when the math is a little off, the word it picks is still a "reasonable-looking word". In Strata's source comments, the author wrote these traps down one by one Code fact:

  • Caching by address. The input each layer sends to its experts lives in the same block of memory. The address never changes; the contents differ in every layer. Cache it by address and you reuse layer 0's data in the next 47 layers, getting "a finite, plausible-looking, completely wrong token". [S06]
  • Weights applied twice. The expert pool does not multiply by the routing weights; the merge step does. If both sides multiply, you can barely see it in one layer, but over 48 layers the error keeps growing. [S06]
  • The rule for pairing heads. In a GDN layer, 48 value heads must be paired with 16 key heads, and the correct rule is the modulo (h % 16). The comment points out that another rule, "grouping in blocks", also produces perfectly well-formed output. [S17]
  • The wrong activation format. Which activation format a quantized matrix needs depends on its data type, not its name. Pick the wrong one and the matrix product is off by 0.6%–1.4%. In the comment's own words, you get "a plausible vector, not a broken one". [S14]

So testing an inference engine needs one thing: a reference answer, also called a test oracle. It is an independent source that tells you "what the correct result should be". It can be a number worked out by hand, another implementation you trust, or a rule that must always hold. Without a reference answer, a test can only check "the program did not crash".

26.2 The layers of testing: from one formula to a whole session

Testing a whole inference engine in one go is not realistic. Engineers split the job into layers. Bottom-layer tests are small and fast, and when one fails it points at the exact line. Top-layer tests are slow, but they come closest to what users actually see. Figure 26-2 is a "test ladder" built from Strata's own tests.

Let us look at a few rungs and how Strata handles them.

The bottom rung is pure functions. Converting a 32-bit float to the 16-bit BF16 format has only 2³² possible inputs, about 4.3 billion. Strata's test simply tries every one of them, comparing each against the conversion rule of ggml (the compute library behind llama.cpp), and finishes in a few seconds. This test caught a real bug: the old rounding code carried a bit when it met a NaN ("not a number"), turning the NaN into −0 or infinity, so a NaN coming from upstream was quietly hidden. Code fact (bf16_bits_test.cpp)

The second rung is single kernels. Every GPU kernel has a comparison test that checks it against a trusted reference implementation. A comment in the build script puts it plainly: the reference itself was first checked against ggml, and "comparing a kernel against another copy of itself proves nothing". Code fact (CMakeLists.txt)

The third rung is composition and contracts. layout.hpp checks, when the model loads, whether every tensor's shape matches what the kernels assume. If one does not, it reports the tensor's name, its actual shape and the required shape. The comment says the point is to fail at load time, not to become a wrong number inside a matrix product at token 4000. [S04] The same comment records a real lesson: in one round of development, the indexer's key cache was sized for "4 heads" when there is really only 1 shared head, so it was 4 times too big. The bug survived a whole round in the code because it made the budget more conservative, and nobody felt anything was off. [S04]

The top two rungs run the whole model. Section 26.4 covers them.

No rung of the ladder can be skipped. Strata has a ready-made cautionary tale. The model has a module called PLE (the lookup module from Chapter 11). Every one of its parts was written, and each passed its own comparison test, yet no model code ever called it. As a result, one whole-model acceptance gate (code-named C1) failed. Code fact[S13] Every part green, and the system still wrong.

The levels of software testing

Tests for a large system usually come in layers. A unit test tests just one function or one class: give it an input, check the output, done in milliseconds. An integration test wires a few modules together and checks that both sides keep the "interface contract" between them. A system test (also called an end-to-end test) enters through the user's front door and checks the final result. One more kind cuts across all layers: the regression test. Each time you fix a bug, you keep a test that reproduces it, so it can never sneak back.

A common rule of thumb is the "test pyramid": many fast unit tests at the bottom, a few slow end-to-end tests at the top. The reason is cost. When an end-to-end test fails, you still have to spend time finding which layer broke; when a unit test fails, it usually points straight at a few lines of code.

Another common tool is the test double: a fake object whose behavior you control, standing in for a real but expensive part. Strata's serving layer ships a MockEngine that emits tokens from a script, so every API path can be tested on a machine with no GPU. Code fact[S15] It can prove that "the HTTP protocol layer is written correctly", but it cannot prove that the real engine computes correctly. Each layer of tests answers only for the layer it covers.

Further reading: Wikipedia: Software testing · Wikipedia: Unit testing · Wikipedia: Regression testing · Python docs: unittest, the unit testing framework

If you studied CS: this is the test pyramid and the V-model from Software Engineering. What is special about an inference engine is an extra layer in the middle, "compare against a reference implementation": the correct answer for most kernels cannot be worked out by hand, so you have to find an independent, trusted implementation to compare against.

26.3 For floats, "equal" needs a definition first

Back to the experiment from the start. The graphics card and the CPU compute the same quantized expert from byte-for-byte identical data, yet the results differ in the last few decimal places. The author's explanation: the two sides do their floating-point operations in a different order, and both are equally good approximations of the model. Upstream report (cache-parity report)

Why would order change the result? Because a float in a computer has a limited number of digits, and every addition has to round once. Take an extreme case. In 32-bit floats (FP32), neighboring representable numbers near 100 million are 8 apart. So 100 million plus 1 is still 100 million; the 1 gets "swallowed". Add the same four numbers in a different order and you get a different answer, as Figure 26-3 shows.

This example is an extreme case picked on purpose. In real inference the difference is usually just the last digit or two, a difference of one or two ULPs (unit in the last place, one step in the last digit). But that is already enough to make a test like a == b fail.

The engineering fix is to compare with a tolerance: if two numbers are close enough, they count as equal. There are two ways to measure "close enough". A relative tolerance scales with the size of the numbers, for example allowing a difference of one part in ten thousand. An absolute tolerance is a fixed threshold, for example anything within 10⁻⁶ counts as equal. The two are usually used together. The primer below explains why.

Tolerance in float comparison

Start with intuition. Compare 100 million with 100,000,008: a gap of 8 is the smallest difference FP32 can tell apart there, so they should count as equal. Compare 0.000001 with 0.000009: the gap is under 0.00001, yet one is 9 times the other, so they clearly should not count as equal. So "how far apart still counts as equal" has to be tied to the size of the numbers themselves. That is the relative tolerance.

But the relative tolerance breaks down near 0. Say a result should be 0 in theory; one side computes 2×10⁻⁸ and the other gets exactly 0. The relative gap is 100%, yet in practice there is no difference between them. That is when you need an absolute tolerance as a floor. Python's standard library function math.isclose combines the two:

|a − b| ≤ max(rtol × max(|a|, |b|), atol)

Its defaults are rtol = 10⁻⁹ and atol = 0. The docs warn specifically: when comparing with 0, the default settings always say "not equal", so you must supply a positive atol yourself. Also, NaN is not "close" to anything, not even itself. Figure 26-4, below this primer, draws the rule: the horizontal axis is the size of the number, the vertical axis is the allowed error.

How big should the tolerance be? There is no universal answer. It depends on the data type (FP32 has about 7 significant digits, FP16 just over 3), on how long the chain of computation is, and on how sensitive the downstream steps are to error. One reliable approach: first measure the typical difference between two implementations that are both correct, then set the tolerance above that and below the differences that are clearly wrong.

One more point is often missed: a tolerance can only let through legitimate differences such as "a different order". It cannot rescue an algorithm that itself loses information. In Figure 26-3 both paths are wrong; widen the tolerance until they count as "equal" and the test no longer tests anything.

Further reading: Python docs: math.isclose · MDN: Number.EPSILON (machine epsilon) · Wikipedia: IEEE 754 · Wikipedia: Unit in the last place

So when should you insist on bit-for-bit equality? When both sides do exactly the same operations in exactly the same order. For example, moving quantized data from one storage format to another only rearranges bytes, so the decoded values must match to the last bit. Strata's canonical_xcheck.py demands exactly that. Code fact (canonical_xcheck.py) On the other hand, even compiler optimizations can change the order. On AMD graphics cards, Strata deliberately turns off "fused multiply-add" (FMA) for two files: fusing a multiply and an add into one instruction rounds only once, which changes which way a value "exactly halfway" goes. Code fact (CMakeLists.txt)

If you studied CS: Numerical Analysis teaches that floating-point addition is commutative but not associative: (a + b) + c and a + (b + c) can differ. On a GPU, thousands of threads do a reduction, and the thread layout decides how the sum is grouped. So you should never expect "the same formula" to match bit for bit on a CPU and a GPU in the first place.

26.4 A tiny difference, and the word changes

Can a tiny numerical difference have a visible effect? Yes, and it happens right at the step that picks the word. At the end, the model gives every candidate word a score, called a logit, and the word with the highest score is picked. If the first and second place have almost the same score, a tiny numerical error can swap them.

Here is an example. The reference engine scores two candidate words [1.00000, 0.99999] and picks the first. The engine under test computes [0.99998, 1.00001] and picks the second. The largest difference between them is only 0.00002, yet the chosen word has changed. Conversely, if the scores are [10, 0], an error ten times larger still would not change the word. So "the largest error is tiny" and "the same word is picked" are two separate things, and you must check them separately.

Comparing two engines has one more snag. Let each one generate freely, and as soon as one word differs, the "context" that follows differs too, so no later step can be compared. The fix is called teacher forcing (fixed history): do not let the engines continue on their own; feed both sides the same reference text and, at every position, compare their predictions for "the next word". Figure 26-5 contrasts the two approaches.

This is how Strata answered "does the cache make the output worse?". The engine has a switch that runs through a reference text one token at a time and writes out all the logits at every position. With the cache off, the CPU computes every expert; with the cache on, the 5,130 most-used experts sit on the graphics card. Test conditions: Q2_0 quantization, an RTX 5070, and the first 512 or 1,024 tokens of three fixed texts. Upstream report

Perplexity in the table measures how "surprised" the model is by this real text; lower means better predictions. The report draws three conclusions. The cache changes "which of two nearly tied candidates wins" at 2%–5% of positions, and most flips happen where the top two scores are less than 0.5 apart. The two perplexities are the same within 1 standard error, so neither side is more accurate. The graphics card and the CPU compute the same expert with different floating-point orders, and both are equally good approximations. Upstream report (cache-parity report)

This table shows how a good comparison is done: it looks at the discrete decision (is the top word the same), at the continuous quality (perplexity), and it also says where the flips happen. Report only "96% of words are the same" and readers will think the other 4% are errors; report only "the perplexity is the same" and you may hide a bug that breaks only a few positions.

26.5 Make the test fail once: reference answers and negative cases

A test passed. What does that tell you? If the test would also pass on a program with a real bug, then its "pass" means nothing at all. The way to check a test is plain: plant a bug in the code on purpose and see whether the test catches it. This is called mutation testing, and each broken version is a "mutant".

The experiment below shows this with a 48-layer toy model. It has 4 versions of the implementation and 5 tests. Take a guess first: which tests can catch the "weights applied twice" bug?

Two cells in the table deserve a closer look. First, the "weak unit test" missed "weights applied twice": it happened to use a weight of 1.0, and 1.0 squared is still 1.0. A test whose inputs are too "tidy" is born blind to some kinds of bugs. Second, "stale input per layer" fooled both unit tests: the bug is not inside the function under test but in the loop that chains the functions together. This is exactly the "every part green, and the system still wrong" from Section 26.2.

The strongest bug-catcher in the table is the differential test: feed the same inputs to the implementation under test and to an independent reference implementation, then compare the outputs. The primer below is all about it.

Differential testing and metamorphic testing

Many computations have no answer you can work out by hand: nobody can check a 2560-dimensional matrix product on paper. The idea of a differential test is to find an independently built version to serve as the reference, give both sides the same input, and compare the outputs. The reference can be slow, even clumsy, as long as it is trustworthy. Strata's comparison tests work this way: a GPU kernel is checked against a scalar reference path that has already been verified, and that reference path itself was first checked against ggml.

The key to a reference is that it is independent. Strata's layer.cpp records a lesson. Two packing tools both looked for the offset plane of a certain kind of quantized data under the field name mins, but the plane's real name is offsets. The two tools "agreed", and so together they dropped the offsets of 54 tensors, 136 MiB in all. The comment's conclusion: two tools agreeing counts as evidence only if they do not share the same wrong assumption. Code fact[S14]

When even a reference is hard to find, you can use a metamorphic test. You do not know what the correct answer is, but you do know "if the input changes like this, the output should change like that". For example, Strata's KV cache is stored in pages. A test stores the same data with 1, 4 and 512 slots per page, shuffles the page table, and requires the attention output to be exactly the same. [S18] Another example is the verification window in speculative decoding: by design, the word picked at every position must be bit-for-bit identical to what token-by-token generation would pick. [S08] These "should not change" rules are references that need no correct answer.

Further reading: Wikipedia: Differential testing · Wikipedia: Metamorphic testing · Wikipedia: Test oracle · Wikipedia: Mutation testing

Differential testing has caught real bugs in Strata too. In the Q2_0 quantization format, the 2-bit codes 0–3 must have 1 subtracted when decoded, so the representable values are {−d, 0, d, 2d}, not {0, d, 2d, 3d}. Forget that minus 1 and most values look right, but every one is off by one step. So the conversion tool copies ggml's decoding expression word for word, then compares bit by bit. Code fact (canonical_xcheck.py) The same file records a real slip in the Q8_0 format: the codes were once stored as signed numbers, which agreed perfectly with their own decoder. Only when a real model was packed did it turn out that two tensors decoded 128 codes off across the board, while the other 12 types were fine.

If you studied CS: Compilers courses have a classic technique for this: give the same program to two compilers and compare the results when you run them. In ACM-style contests, people write a brute-force solution and run it side by side with the optimized one on random inputs. Same idea.

26.6 Hands-on: write tests for a tiny engine

This book ships a tiny inference engine in pure Python, labs/tiny_inference.py: 4 layers, 8 dimensions, and in every layer 2 of 4 experts are picked. The weights are fixed random numbers, and no graphics card is needed. It is not a Strata-compatible implementation, and its output means nothing as language, but the whole chain "encode → compute layer by layer → pick a word → save and restore" is real. Its 10 tests all pass in this book's environment.

  1. Read the tests first. Open labs/test_tiny_inference.py and find the one that says "processing in chunks equals processing in one go". It uses exact equality. Think about it: why is exact equality right here? (Hint: both paths do exactly the same operations in the same order.)
  2. Plant a bug. Follow task 3 in labs/README.md and swap the order "decay first, then update" in the recurrent layer. Which tests fail? If none fails, add one that does.
  3. Rewrite the comparison rule. Suppose you replace token-by-token prefill with one matrix multiplication over the whole chunk, so the order of operations changes. Turn that exact-equality test into a tolerance comparison, and explain how you chose the tolerance.

Both interactive experiments in this chapter compute for real in your browser; their numbers are teaching estimates. The lab bench's tolerance formula matches Python's math.isclose; the mutation test uses a toy model, not Strata's kernels.

Remember these three

  1. The most dangerous bugs in an inference engine are the ones that "look normal". Tests need an independent reference answer; checking that the program did not crash is not enough.
  2. Floating-point results change with the order of computation. Demand bit-for-bit equality only for the same operations in the same order; otherwise compare with a relative plus an absolute tolerance, and check the chosen word separately.
  3. Tests themselves must be tested: plant a bug on purpose and see whether they fail. A reference implementation must be independent; it must not share a wrong assumption with the code under test.

Common misconception: "The CPU and the graphics card give different numbers, so one of them has a bug."

Not necessarily. The two sides do their floating-point operations in a different order, so the last few digits will differ anyway, and Strata's measurements show the two are equally accurate. But you cannot wave everything through either. That startup warning, "the GPU path is not correct", started from a real fault: back then, the output diverged from token 0. The fault was later fixed and covered by the expert comparison tests, and only from version 0.1.8 on was the warning replaced with an accurate note. Upstream report Tell the two apart by the pattern: a legitimate difference flips only at near-ties and leaves perplexity unchanged; a real bug often diverges from the very start, or makes quality metrics systematically worse.

Go deeper: five layers of evidence, metric traps, and the limits of "bit-for-bit"

The five-rung evidence ladder

Rung one is pure functions: address offsets, capacities, top-k, expected lengths. Rung two is single kernels: same input, compare outputs and errors. Rung three is composition: the order of normalization, gating, expert weighting and state updates. Rung four is the whole model's distribution under a fixed history. Rung five is real tasks and long-session behavior. Passing a lower rung does not imply passing a higher one. The notes "the expert pool does not multiply by the routing weights" and on GDN's β and state axis both show that composition errors can hide between modules that each pass their own tests. [S06][S17]

Which metrics to record under teacher forcing

You can record the largest absolute error, the relative error, the mean squared error, the KL divergence, whether the top word changed, and whether the experts the router picked and the positions the indexer picked changed. Every metric has a trap. Relative error is distorted when the reference value is near 0. KL divergence needs a note on how the probabilities are normalized and how zero probabilities are handled. The share of matching top words must be read together with the distribution of the "gap between the top two". Strata's QSA indexer simply requires the picked positions to be exactly the same, with no tolerance, because picking a different slot changes the input to attention. That is why it stores the indexer's keys in FP32 rather than FP16: FP16 would perturb each score by about 2⁻¹¹ relative, right on the selection boundary. The cost is small: at a 32K context, these FP32 keys come to about 50 MiB in total. [S18]

Metamorphic relations you can use directly

Apply the same permutation to the page table and the data, and the logical attention result should not change. Split the same input into different chunks, and the state handed over between chunks should be equivalent. Save, restore and continue, and it should be as if you never left. Turn off the draft, and the result should match the corresponding target path in meaning. [S08][S18] These relations generate lots of strong tests, but you must write down the tolerance and the numerical path. Across CPU and GPU, with a different matrix-multiply implementation, or with a different quantization path, bit-for-bit equality is not guaranteed. You can neither wave every difference through nor ignore the known rounding boundaries.

The "bit-for-bit" promise has limits

Strata's verification window promises in its header file that the word picked at every position is bit-for-bit identical to one-at-a-time generation. [S08] Yet the upstream docs also record this: with the IQ family of quantizations, the CPU uses two kernels with slightly different rounding for one token and for many tokens. So the same prompt at temperature 0 can produce a different, equally good answer depending on the draft, the cache state or session restore (issue #152). With STRATA_IQ_MT_MIN=1, every case takes the many-token kernel, and the answer no longer depends on the draft. To make a server byte-for-byte repeatable you also need --prompt-cache 0 --adapt-swaps 0 --pcie-frac 0. The author measured it (IQ3_XXS, a 3.6K-token prompt, 4 repeats): with all three switches, the 4 runs gave just 1 answer; without --pcie-frac 0, 2 answers (the first run differed); with all defaults, also 2. Upstream report[S03] The header file states the design goal and the docs state the measured limits; read both.

A checklist of negative cases to plant

Plant these errors in your tests on purpose: change the head mapping from modulo to integer division; use RMS normalization instead of L2 normalization; decide the per-layer activation cache by pointer alone; multiply the routing weights twice; freeze the position counter; forget PLE's history when restoring a session. The tests should fail reliably and point to the earliest contract that was broken. If a test still passes after a bug is planted, it most likely checks only "the process did not crash". A reference implementation must not share a wrong assumption with the code under test; the case in layer.cpp where both tools looked for the wrong field name makes a good classroom discussion. [S14]

Which tests the public repository can run

A comment in Strata's CMakeLists.txt states that the full test suite and the microbenchmarks live in tests/ and bench/micro/, which the public source does not include, so the switch that builds the tests is off by default. Code fact (CMakeLists.txt) Likewise, the reference implementation ref/gdn.py mentioned in the comments of gdn.hpp is nowhere to be found in the public repository's ref/ directory, which holds only load.py. The comparison tests and measurements this chapter cites come from public source comments, test files and reports; this book did not rerun them on a GPU.

What this book's own tests prove

The tests for labs/tiny_inference.py check chunked processing, save and restore, reference replay and controlled draft acceptance. They prove this book's teaching code, not the upstream Strata GPU implementation. Strata's dispatch, quantization, asynchronous execution and real weights must be verified separately in the matching environment.
