Start with three numbers

Strata's README says that on an RTX 5070, the Q2_0 version writes 94 tokens per second. Upstream report[S01] That number looks very certain.

Now look at a test a community member sent in: one RTX 3090, running the Coder model with a 32K-long prompt, the same settings three times in a row, all within 30 seconds. The three output speeds were 52.7, 66.8 and 97.4 tokens per second. Upstream report The fastest is almost twice the slowest. So how fast is this machine, really? This chapter is about how to measure so that a speed number survives tough questions.

In one line: a performance number means something only when it carries its conditions, its sample count and its statistical method. Warm up first, then repeat; report the median and the spread; list the first run on its own; and state which formula you used to compute "speed".

27.1 One machine, three speeds in 30 seconds

First, the raw records of those three runs. They come from a community test report in the Strata repository: engine version 0.1.26, one RTX 3090, the Coder model, a 32K-long prompt. Upstream report (RTX 3090 test report)

Why such a big gap? The raw records hold clues Upstream report:

  • The outputs were too short. The three runs generated only 48, 26 and 45 tokens; the model finished early and stopped. Each decode phase took less than 1 second (911, 389 and 462 milliseconds). Over such short times, any small wobble gets magnified.
  • Each run wrote different text. The three answers all started differently. Strata speeds things up with speculative decoding: guess a few tokens first, then verify them in one go. The more guesses land, the faster it goes. The three runs accepted 31 of 38 drafts, 12 of 21, and 33 of 37. Run 2 guessed worst, yet its speed came out in the middle, so more than one factor drives speed.
  • The input drifted too. All three were nominally "32K prompts", but their real lengths were 28,317, 31,630 and 31,601 tokens. The report recorded the real lengths on purpose, because "nominal length labels drift".

The report's own conclusion is restrained: run each cell three times, report the median, and also list the first run's value; and mark the whole set of results as "preliminary". That is exactly the habit this chapter teaches.

First, two words. Throughput is how much work gets done per unit of time; here it is how many tokens come out per second, written token/s, and bigger is better. Latency is how long you wait for one thing to finish, such as the time from sending a request to seeing the first word, and smaller is better. People often mix the two up, but they answer different questions.

27.2 A number must carry its conditions

Where does the "94 token/s" in the README come from? The v0.1.39 README adds a line under the table: the Q2_0 row used engine 0.1.36, and the other rows used 0.1.26. Upstream report[S01] In the detailed documentation, the 0.1.36 section says that for Q2_0, the output at 4K went from 89 to 93.5 tokens per second, and the 32K prompt reading from 2,170 to 2,653. But the main table is from 0.1.26, where the same cells are 93.0 and 2,171. Upstream report[S03] The README writes 2,650 for prompt reading, which matches 0.1.36 and does not match the main table. From the number "94" alone you cannot tell which version it came from; you have to read the release notes. The conditions of the main table are written at the start of the document; see Figure 27-2.

The document has a few more details worth learning from Upstream report[S03]:

  • It flags mixed versions. Most of the table is from 0.1.26, but a few cells in the 262K column were not retested; they reuse numbers from 0.1.22 or 0.1.14 and are marked with a separate symbol. Numbers that share a table did not necessarily come from the same experiment.
  • It says the numbers change with the content. Output speed also depends on the text itself: the more guesses speculative decoding lands, the faster it goes. So the same prompt with a different answer can differ in speed by several percent.
  • It runs comparisons back to back. When the document compares 0.1.14 with 0.1.12, it runs them back to back on the same 4K prompt and gets 88.5 and 85.7 token/s.

Back to the 3090 from the start. The README estimates that an RTX 3090 "can write roughly 100–140 tokens per second". [S01] The community report measured less than that, but the two sets of conditions are far apart. The report used a virtual machine; both graphics cards on the test machine had their power manually capped at 280 W; the tester generated the prompts from the source code; and several requests ended early. The report itself says that until it gets the upstream prompts and test method, every comparison with upstream is "for reference only". Upstream report Neither number is wrong. They just cannot be compared directly.

If you studied CS: this is the first rule of performance evaluation in Computer Architecture: describe the test environment, and change only one variable at a time. In science it is called "controlling variables". A benchmark score without conditions is as useless as a physical quantity without units.

27.3 One slow request drags the average away

You measured the same thing several times and got a list of numbers. Which number should stand for it? The most common answer is the average, but it has a big flaw. The primer below explains.

Mean, percentiles and variance

Take the times of a batch of requests: 8, 9, 10, 11 and 100 milliseconds. The first four are normal; the last one may have run into another program grabbing resources.

The mean adds everything up and divides by the count: (8 + 9 + 10 + 11 + 100) ÷ 5 = 27.6 milliseconds. Yet none of the five runs is anywhere near 27.6; the 100 dragged it away. The median is the number right in the middle once the list is sorted, here 10 milliseconds. Even if the 100 became 10,000, the median would not move. This "not bothered by a few extreme values" property is called robustness.

A percentile answers "how slow are most requests". p95 means: 95% of requests are no slower than this. User experience is often set by the slow end: the slowest 1 out of every 20 requests is the one users remember best. There are several conventions for computing p95. This book uses the simplest, the "nearest rank" method: sort from small to large and take item number ⌈0.95 × n⌉. Note: with fewer than 20 samples, p95 is simply the maximum. If you run only 5 times and report p95, you are really reporting "the slowest run".

Variance and standard deviation measure how spread out the data are. Sample standard deviation = √( Σ(xᵢ − mean)² ÷ (n − 1) ). For the numbers above it is about 40.5 milliseconds, bigger than the typical value itself. That is a warning: the data contain an outlier, and the mean cannot be trusted.

Further reading: Wikipedia: Median · Wikipedia: Percentile · Wikipedia: Standard deviation · Python docs: statistics (including the two methods of quantiles)

Look back at the three runs in Figure 27-1: median 66.8, mean 72.3, and the "p95" is the fastest run, 97.4. (Here bigger is better, so to see the slow end you must look at the minimum, 52.7.) Taken alone, none of the three numbers is complete. The upstream report gives the median, then attaches the first run's value along with the raw records.

If you studied CS: in Probability and Statistics, the median's "breakdown point" is 50%: as long as fewer than half of the data points become arbitrary values, the median cannot run off to infinity. The mean's breakdown point is 0: a single bad data point can drag it away. And performance data are exactly where a few extreme values show up most easily.

27.4 The first run is always slow: warm-up and repetition

Many systems run slower the first time than later. In Strata, several things "warm up" with use:

  • The expert cache. Which experts sit in VRAM adjusts with the conversation, fitting the current content better the more you use it. Upstream report[S02]
  • The draft controller. It starts with an estimate of "how many draft tokens will land", then learns as it goes within each session. Code fact[S09]
  • The compute graph. The GPU compute graph of the verification window is recorded only on first use. Code fact[S08]
  • The operating system's file cache. A file you just read stays in RAM, and the second read is much faster.

Some things work the other way and make later runs "unrealistically fast". Strata keeps the conversation and, on a follow-up, reads only the new part. [S02] If a speed test keeps sending the same prompt, from the second run on prefill costs almost nothing, and what you measure is no longer the speed of "reading a 32K prompt". That is why every request in that 3090 report uses a different ID and never reuses a conversation. Upstream report

Another community report writes up its method more fully; see Figure 27-4. It tests the IQ2_XS quantization on an RTX 5090 with engine 0.1.29. First it sends a very short warm-up request, not counted in the results. Then, on the same loaded engine, it runs each length three times in a row, in the order 4K, 32K, 128K. Every request reads its full prompt, with 0 reused tokens, and each table cell reads "median [min–max]". Upstream report (RTX 5090 test report)

Note that warm-up request: its prompt had only 19 tokens, and it output only 2. A request that short could not warm everything up. The first counted 4K run had about 0.2 seconds more time to first token and decoded about 10% slower. The report did not quietly drop that run; it says "the slower first 4K run is kept in the range". Upstream report That is more honest than deleting it, and it leaves readers the material to judge for themselves.

Warm-up and benchmarking method

A benchmark runs the same task over and over under controlled conditions to measure its performance. To make the results trustworthy, a few basics matter:

Warm-up. Before the timed runs, run a few times so the caches, compute graphs and file cache settle into a steady state; these runs do not count. Decide in advance how many warm-up runs and what content to use, and write it in the report. If what you care about is precisely the cold start (say, a user opening the app for the first time), measure the cold start on its own; do not mix it with the warm state.

Repetition. One run is one sample. Only by repeating can you see how big the wobble is. Fix the number of repetitions in advance; do not "run until you like the result".

Interleaving. When comparing A and B, do not finish all of A and then run B. Alternate: A, B, A, B. Otherwise changes in how warm the machine is, its temperature and its background tasks all land on one side.

Keep the raw data. Report the median and the range, and attach the raw record of every run, including the failed and abnormal ones.

There is one case where you may look only at the fastest run: timing a small piece of deterministic code. The Python timeit docs recommend looking at the minimum, because slower results are usually caused by interference from other processes, and the minimum gives the lower bound for how fast the machine runs that code. But the speed of an inference service also depends on the input text, how many draft tokens land and how many cache hits occur. These are not "interference"; they are what real users will actually run into.

Further reading: Wikipedia: Software performance testing · Python docs: timeit · Wikipedia: Benchmark (computing)

What does each of warm-up, repetition and interleaving fix? The experiment below lets you design the measurement yourself. Its advantage is that it "knows the truth": B really is 5% faster than A, so you can see directly whether your plan measures it correctly.

27.5 Define the clock first: TTFT and "tokens per second"

Even with a sound method, the word "speed" itself can be computed in several ways. After a user sends a request, several stretches of time pass: queueing, prefill ("reading the prompt"), the first token appearing, the later tokens arriving one by one, and the end. Where you start the stopwatch and where you stop it give completely different numbers; see Figure 27-6.

TTFT (time to first token) is the time from sending a request to the first token appearing. It includes queueing and prefill, and it decides how long the user "waits before seeing anything happen". The RTX 5090 report defines it precisely: start the clock just before sending the HTTP request, stop at the first non-empty piece of text, and ignore empty role messages and keep-alive messages. Upstream report

Output speed has even more formulas. Speeds ② and ③ in the figure above differ by just a "minus 1", but for short outputs the gap is not small: with only 26 output tokens, the two differ by 26 ÷ 25 − 1 = 4%. Teaching estimate With only 1 output token, speed ③ is not defined at all; forcing it means dividing by 0.

A "live speedometer" has its own subtleties. A comment in Strata's server source says the live speed shown in the interface is a rate over a time window, not "the average since the first token". The latter is about 1 ÷ elapsed time right after the first token appears; it once showed a five-digit number on the monitoring screen, then read too low for the following second. The window in the code is 2 seconds; when less than 0.25 seconds have passed, it counts as 0.25 seconds. Code fact[S15]

When several users share the system, two more things must be kept apart. System throughput is how many tokens per second all requests together produce; per-stream speed is the speed each user sees. Five users at a combined 100 tokens per second does not mean 100 tokens per second each. In the default setup, Strata's server handles one sequence at a time, and requests queue first come, first served. [S15] So "five people at once" means the last four are waiting in line: their TTFT grows, while their decode speed stays the same. Chapter 25 covered the cost of this kind of queueing. v0.1.39 can turn on "parallel" in the config to decode several requests together, and the result turns out the other way round. Upstream measured on an RTX 5070: when 4 requests arrive together, the first token of the last one comes at 1.8 seconds instead of 11.2; but the total throughput falls from 70.7 to 63.1 tokens per second, and the speed of each stream falls from 79.6 to 16.9 tokens per second. Upstream report(BATCHING.md) In this mode, the server's live speed tok_s is the sum of all the requests' rates, that is, the system throughput. Code fact(server.py) Each slot's own speed is listed separately in live.slots of /metrics. Upstream report(BATCHING.md) Which of the two setups is "faster" depends on whether you ask about TTFT, total throughput or single-stream speed.

27.6 Hands-on: write one measurement up as a checkable record

This book ships a measurement protocol, labs/benchmark_protocol.md, and a record template, labs/benchmark_template.csv. The template has 31 columns, from the repository version, build flags and model-file hash to queueing, TTFT, decode time, peak VRAM and whether quality passed; each run fills one row. The template contains not a single real benchmark result: a cell that was never measured on real hardware should stay empty.

  1. Play with this chapter's two experiments first. In the measurement experiment, find a plan that reliably measures the 5%, and note the repetitions, warm-ups and run order you used. In "three speeds", drag the output length to 1 and see which formulas break.
  2. Then open the interactive experiment "Why short requests keep waiting" in Chapter 25. It compares, under first-come-first-served and round-robin scheduling, each request's time to first token and its completion time. Notice: total throughput barely changes, yet each person's experience differs a lot. That is exactly why "per-stream" and "total throughput" must be reported separately.
  3. Finally, write a record. If you have a computer that can run Strata, follow the protocol and run one A/B: change one setting at a time, alternate A and B, repeat each group at least 5 times after warm-up, and put every run's raw data into the template. If you do not have such a computer, practice on the upstream RTX 3090 report: copy each run's numbers out of its raw JSON, recompute the median yourself, and list which template columns the report is missing.

The times in both of this chapter's interactive experiments are teaching assumptions, not Strata measurements. They demonstrate a measurement method, not the speed of any graphics card.

Remember these three

  1. A performance number must carry its conditions: hardware, model and quantization, engine version, input and output lengths, cold or warm caches, and concurrency. Numbers from different conditions cannot be compared directly.
  2. Warm up first, then repeat, and alternate A and B. Report the median and the range, list the first run on its own, and keep the raw data and the failed runs.
  3. Define the clock before talking about "speed": TTFT, end-to-end speed and decode speed each answer a different question, and system throughput is not each user's speed.

Common misconception: "Only the fastest run shows what the machine can really do."

When you time a small piece of deterministic code, the fastest run does mean something: the Python timeit docs say the minimum gives a lower bound on how fast the machine runs that code. But an inference service's speed also depends on what text it wrote this time, how many draft tokens landed and how many cache hits occurred. The fastest value in Figure 27-1, 97.4, was just the luckiest of three runs. Every day, users experience speeds near the median and remember the slowest few. Reporting only the fastest run is cherry-picking the data that flatter you.

Go deeper: experimental units, representative scenarios, paired comparison and quality gates

An experimental unit is a full set of conditions

Record at least: repository version (commit hash), executable and build flags, model-file hash, quantization, CPU and GPU models, RAM channels and frequency, driver version, context length, input token count, output cap, KV cache mode, prefill chunk size, draft settings, cold or warm caches, the definition of concurrency, sampling parameters and the random seed. Miss one key variable and two sets of numbers may no longer be comparable. Strata's detailed documentation mixes cells from different engine versions in one table, and adds the results of a new kernel in a separate paragraph. [S03] That document is good for practicing "reading a performance table", but you cannot treat all its cells as one unified experiment, let alone as this book's own measurements.

Define each clock boundary

End-to-end TTFT: from sending the request to the first output token. Queue time: from entering the queue to being allowed to run. Prefill time: from starting to process new input to the needed history state being ready. Decode time: the generation process, counted between clearly defined start and end points. Completion time: from sending the request to the final success or failure state. Both decode rates, N ÷ decode time and (N − 1) ÷ (last token time − first token time), may be reported, but the definition must be written down and never quietly swapped between systems. At N = 1 the latter is undefined, and should be shown as "undefined", not as a huge rate.

Three representative scenarios for a coding assistant

Understanding a cold repository: a long system prompt, tool definitions, code context and the first answer; mainly look at cold prefill, TTFT and peak memory. Incremental edits: a large prefix can be reused, with only new error messages and code diffs added; look at whether the cache works and how fast the tail is processed. Tool loops and branching: short generations, tool output, continuation and opening a new branch; look at state restore, cancellation and protocol semantics. Input lengths can be 1K, 4K, 16K, 32K, 64K, 128K and a near-full window that is actually supported, with explicit room left for output. Do not use the whole "maximum context" for the prompt and then ask for extra generation. Check the legal limits for a specific model and configuration against the real engine: Strata's server flatly rejects a request whose "prompt plus output cap exceeds the context", returning 400, and never truncates. [S15]

Single-stream and multi-stream tests answer different questions

A single-stream test looks at each user's immediate experience. A multi-stream test must also report the number of active streams, total throughput, per-stream TTFT and token-gap p50 / p95, failure rate, queueing and fairness. Sparse arrivals and synchronized peaks also differ: a multi-stream scaling test should fix the arrival process, the distribution of request lengths and the cold or warm state, and keep the raw timestamps of every request. Averaging several already computed rates usually does not equal total tokens divided by total time.

Pairing, alternation and intervals

Pair your A/B comparisons when you can: run the same prompt once on A and once on B and compare the difference, rather than running three different prompts on each and comparing medians. When comparing different layer split points, that RTX 3090 report warns that the prompts of each run were generated independently, so the ranking is "not a paired comparison" and the medians should be read with care. Upstream report Strata's documentation also suggests adding switches such as --pcie-frac 0 for A/B tests, so that the same prompt gives the same answer every time; otherwise the answer changes, and the speed changes with it. [S03] With very few samples, p95 is highly unstable, so always give the sample count and the raw records. To give a confidence interval, you can resample the raw samples with the bootstrap. Removing outliers needs a rule written down in advance, and the reason for each removal must be kept. Picking the fastest run and reporting it has no generalizable statistical meaning.

Pass the quality gate first, then compare speed

Speculative decoding, quantization, KV cache formats, prefix caching and CPU / GPU dispatch can all change the execution path. "20% faster" is not a successful optimization if the answers got half as long, or if failed requests were left out of the count. When Strata's documentation reports a speed-up, it also reports how close the result stays to the FP16 reference (the KL divergence under teacher forcing). [S03] Record each run with labs/benchmark_template.csv; the A/B procedure and the conditions for refusing a release are in labs/benchmark_protocol.md. Cells with no real hardware data stay blank; this book has not filled in any guessed GPU benchmark scores.
