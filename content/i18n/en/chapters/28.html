A story where every part was green

Strata's model has a lookup module called PLE (covered in Chapter 11). The developers split it into a few parts: compute a hash, read one row from a big table, run a small computation. Every part was written, and every part passed its comparison test, matching the results of a reference script, numpy and ggml respectively.

Then the whole model failed an acceptance check. The reason is written in a source comment: these parts had never been called by the model's main path. Code fact[S13] Every part was correct, yet the machine as a whole was missing a piece. This is the book's last chapter, and it is about how your course project can avoid that trap.

In one line: when you build a system, first open up one thin "vertical slice": let one token travel all the way from input to output and leave evidence you can check; then add features layer by layer. For every trade-off, write down what it bought, what it cost and how you verify it. When you deliver, label each component with how far its evidence has come.

28.1 Every module green, the system still wrong

Figure 28-1 draws PLE's situation. Each of the three parts passed its comparison test, yet the model's main path, from layer 0 to layer 47, never once went through them. Look at any one part's test report alone and you would see no problem.

Bugs like this share one root cause: finish each layer "horizontally" first and connect them only at the end. It is like building a road from city A to city B by paving every kilometer to its final width, only to find on the last day that one stretch in the middle was never connected. The safer way is to build a narrow road first, all the way from A to B. Once cars can drive on it, widen it bit by bit.

In software, this "narrow road" is called a vertical slice: one feature runs straight through from entrance to exit. Each layer does only the small part it must, but the whole chain is real, runs, and produces results you can check. For an inference engine, the first vertical slice is: a sentence comes in, goes through encoding, layer-by-layer computation and word picking, comes out as one token, and the key intermediate data are printed so a person can check them.

A vertical slice is not sloppy code. It must be "thin", not "rough": every step in the chain needs tests, and the reference answers and negative cases from Chapter 26 are just as necessary. What it saves is breadth, not correctness.

28.2 System design is writing your trade-offs down

Once the vertical slice works, every new feature brings choices: trade more VRAM for speed, or save VRAM; aim for speed first, or for debuggability first. These choices have no standard answer, but they do have a standard way to be written down.

System design and engineering trade-offs

System design answers this: under given constraints, how do you organize a pile of parts into a whole that meets the requirements? It differs from writing an algorithm. An algorithm problem usually has an optimal solution; system design is almost always a trade-off among several goals. Speed, memory, correctness, debuggability and development time often pull against each other.

A decent trade-off writes down at least five things:

① Decision: what you chose, and what you did not. ② Gain: what benefit you got, ideally with numbers. ③ Cost: what you paid, again with numbers. ④ Verification: how you confirm the benefit is real and the cost is no bigger than stated. ⑤ Conditions to revisit: what would make you overturn this decision.

Item ⑤ is the easiest to forget. Without it, a decision that was reasonable at the time lives on after the conditions change and turns into "legacy" nobody dares to touch. Engineers call this kind of cost, which piles up and must be repaid sooner or later, technical debt.

Trade-offs have another common trap: optimizing only the thing you can measure. Look only at average speed and you may sacrifice tail latency; look only at unit tests and you may miss composition errors. So decide at design time which metric measures each goal.

Further reading: Wikipedia: Software engineering · Wikipedia: Technical debt · Wikipedia: Systems design · Wikipedia: Trade-off

Strata's source comments contain many trade-offs written out this clearly. Figure 28-2 lays out one of them: the indexer in the QSA layer picks which history positions to read, and its keys are stored in FP32 rather than the smaller FP16. Code fact[S18]

A few more examples come from session.hpp, each writing "what it buys" and "what it costs" side by side Code fact[S13]:

  • One GPU compute graph per layer. Recording a layer's dozens of kernel launches into one graph and replaying it took the same work from 2.393 milliseconds down to 1.585 milliseconds in measurement, 1.51 times faster, because the engine's bottleneck is the overhead of "launching kernels", not bandwidth. The related cost is written right next to it. To merge each layer's expert results with that layer's own weights, every layer needs one more graph, so the window in which the CPU can work alongside the GPU shrinks to just the shared-expert stretch. The comment says it plainly: "a strictly serial residual chain cannot hide per-layer CPU work". That part can only be solved by the expert cache in VRAM.
  • The debug switch is a runtime parameter. "Synchronize after every layer" catches bugs you cannot see any other way, but it slows things down. So it is a runtime parameter, not a compile-time option: on when you need it, off the rest of the time.
  • Zero memory allocation while generating tokens. Every piece of state a session needs is allocated once, at the start. The comment points out specifically: if VRAM were requested only at the first token of a long sequence, every existing test would still pass, and only this constraint would be broken.

The serving layer is the same. By default, Strata's server serves one sequence at a time, first come, first served. When the prompt plus the output cap exceeds the context length, it rejects the request outright with a 400 instead of silently truncating it. [S15] The first choice trades simplicity for state that never gets mixed up; the second trades one error message for users never receiving a truncated result without knowing it. v0.1.39 added optional "batch slots" that decode several requests together. Its document docs/BATCHING.md is a good example of a trade-off written out in full. What you get is waiting time: when 4 requests arrive together, the time for the last one to see its first word drops from 11.2 seconds to 1.8. The price is speed and VRAM: each slot takes 0.56 GiB, and on a 12 GB graphics card even a single request runs 11%–24% slower. The check is token-by-token comparison with the output of a run alone. The conditions of use are stated too: it is recommended only when most experts fit in VRAM. Upstream report

If you studied CS: industry has a practice called the "architecture decision record" (ADR): each important decision gets a short one-page document with its context, the decision and its consequences. In your course report, you can write each design choice as a small card in the format of Figure 28-2.

28.3 Three kinds of project: pick one

Course projects come in three kinds; pick one based on what you have at hand. All three are graded by the same standard: the quality of the evidence and the completeness of the analysis and engineering, not the price of your graphics card.

Project A: a tiny engine that needs no graphics card. Start from labs/tiny_inference.py, which ships with this book. With tiny fixed random weights and a character vocabulary, it chains encoding, normalization, recurrent and attention layers, expert routing, the output and greedy word picking into one complete line. Random weights produce no meaningful language; the goal of this project is to understand how the machinery runs, not to pretend you trained a chat model. Section 28.5 gives a step-by-step route.

Project B: start from one measurable optimization. Pick one local direction: decoding quantized blocks, page-table gathers, the cache policy, chunk size, draft-window control, or chunked parsing of streamed output. Submit the derivation, a baseline, the change, negative cases, the results and the limitations. Change one factor at a time; do not flip five switches at once and then show only one total time. Students without a graphics card build a CPU reference implementation and a mathematical simulation; students with one can do a real reproduction on a fixed Strata commit.

Project C: a multi-user design review. Submit a design for "running several sequences at once", rather than forcing out a production service at the end of the term. The first step of the design is to decide who owns each piece of data; see Figure 28-3.

The design document must list: which objects are shared read-only, which are per-sequence state, who owns the scratch area, how scheduling and the VRAM budget are divided, and how cancellation, restore, observability and rollback work. Then use the concurrency acceptance scenarios from Chapter 25 to try to refute your own design. Extra credit goes to a small runnable prototype of the scheduler or of state isolation. Any capability you have not verified must be written as "not implemented": an interface showing five users is not the same as five inference streams really running. After you write your own design, you can compare it with upstream v0.1.40's docs/BATCHING.md: it gives each slot its own session, and it spells out the VRAM cost of a slot, the token-by-token consistency check and the current limits. Design first, then read the reference: that shows best what you missed. Upstream report

If you studied CS: this is exactly the process model from Operating Systems: several processes share a read-only code segment, and each has its own private stack and heap. The KV cache is each sequence's "private memory". Sharing it without protection is two processes overwriting each other's data.

28.4 What to deliver: label each component with its evidence

The most common problem in project reports is not wrong code; it is calling "written" "done". So every component in the report must state how far its evidence has come:

StatusMeaningEvidence you can show
Code writtenWritten and tested, but not yet wired into the main pathUnit test output
On the main pathThe main path really calls itThe log of one complete run that shows it being called
Real dataReal input went through it and produced a complete resultOne complete record: input, intermediate values and output, every field filled in
Simulated, empty or estimatedVisible in the interface, but backed by fake data, empty fields or estimatesMust be said plainly and labeled "Teaching estimate"

A component can easily be "code written and on the main path" without having produced any real data yet. That state must be written down as it is, not papered over with the word "done". Strata's source has a good example. The CPU and the GPU are supposed to overlap their work, but if the GPU has already finished a layer by the time the CPU gets its task, the whole pipeline has really degraded into serial execution. Every token is still computed correctly, and the time per layer shows no difference. So the author added a counter that tracks in how many layers the CPU got its task while the GPU was still running. It tells you whether the overlap mechanism is "really working" or "just for show". Code fact[S13]

The report itself follows this order. First pose a question that an experiment could refute, for example: "with the same input and quality gate, does raising the budget for hot experts in VRAM reduce the CPU's compute time?" Then give, in turn, the theory, where it lives in the source, the method, the data, the interpretation and the limitations. Every figure states its units, sample count and measurement conditions; source links point to a fixed commit, not to the ever-changing main branch; raw data and failure logs are all kept. Grading follows this table:

DimensionPointsCheckable evidence
Theory and derivation20Formulas, units, dependencies and assumptions are correct
Source and contracts20Points to real code; tells current code apart from outdated comments
Code and tests25Runs; has an independent reference answer, negative cases and edge-case tests
Experiments and quality20Paired or alternating comparison, raw data, a quality gate, failures counted too
Writing and replication15States the environment, steps and limitations so others can re-check

There are two red lines. Present a teaching simulation as a hardware measurement and the whole "Experiments and quality" dimension scores zero. Leave a state leak unexplained and the whole "Code and tests" dimension scores zero; no amount of performance can make up for a correctness defect. The self-check below lets you grade yourself before you hand it in.

28.5 Hands-on: get the first vertical slice through

Take Project A as the example. The first step is not writing a new feature; it is running the existing chain once and looking closely at every field it produces. In this book's repository, run:

python3 labs/tiny_inference.py --prompt "hello" --tokens 8

The output from an actual run while this book was being written contains these things: the model geometry (4 layers, 8 dimensions, 2 of 4 experts picked); a model fingerprint model_id computed from all the weights; the prompt's IDs [8, 5, 12, 12, 15]; the 8 generated IDs and their text "mzjsldhx"; and "draft_matches_greedy": true, which shows that the draft demo's result matches one-at-a-time generation exactly. The text means nothing, because the weights are random; but every field was really computed. This is your first piece of "real data" evidence.

Next, add one stretch at a time, in the spirit of the vertical slice. For each stretch, first write a test that fails, then write the implementation:

  1. See the shapes and ownership. Print each tensor's shape in every layer, and map out which parts are read-only weights and which are changing state.
  2. Save and restore, chunked prefill. Save a session, restore it and keep generating; the result must match an uninterrupted run. Split the prompt into several chunks; the result must match processing it in one go.
  3. Draft and verify. Change the draft demo's candidates. Once a draft token is rejected at any position, throw away the rest of the draft; the output must match greedy generation.
  4. Measure. Measure speed only at the end, and write it up as a record using Chapter 27's method. Note: this script's timings cannot stand in for Strata's performance.

The five tasks in labs/README.md roughly follow this route. Before you dive in, get a feel for it with the planner below: with the same number of weeks, what do you have on deadline day if you build horizontally versus slice vertically?

The planner's "one cell per week" and "a wrong assumption hidden in the interface" are teaching assumptions, not statistics about any real project. What it wants you to see is a structural difference: a vertical slice exposes problems as soon as the first feature is wired in, when the scope of rework is smallest.

28.6 Textbooks have versions too

Every code fact in this book was checked against one fixed Strata commit: 1735d6471df29b42c26170efaac1f1446a58640f, which is Strata v0.1.40 (commit date 2026-10-06), researched on 2026-10-06. Strata is still iterating fast, and the numbers, defaults and interfaces may change in new versions. When the book needs an upgrade, follow the order in Figure 28-6.

Why compare the "contracts" first? Because once a contract changes, every derivation and experiment that depends on it is invalid. Strata itself sees it this way: layout.hpp says that every field of the model geometry is a number some kernel depends on, so changing it changes a kernel's contract; it is not tuning a parameter. Code fact[S04] During a term you can maintain two versions: a stable one that stays fixed for the term, and a research one that tracks upstream.

This book went through the process itself. The first draft was pinned to v0.1.38. When it moved to v0.1.39, the contract that changed most was scheduling: the server went from "can serve only one request at a time" to "one at a time by default, with optional batch slots". So Chapter 25 rewrote its opening, its comparison and its summary, and in Chapters 27 and 28 the sentences about "one sequence at a time" gained the word "by default". On the other hand, not one number in the README speed table changed, and upstream says this version did not re-measure it, so the related paragraphs only needed their sources checked again. When it moved again to v0.1.40, the upstream release notes said the four quantizations gave the same answers as 0.1.39, so the default behavior is basically unchanged. Upstream report The changes cluster in a few "not yet possible" claims: the K8V4 KV cache can now also be streamed (Chapter 17), and a conversation can be saved to a file and kept across restarts (Chapter 20). Also, many cited line numbers moved, and each one has to be realigned.

Remember these three

  1. Get one vertical slice through first: one token travels from input to output and leaves real data you can check; then add features layer by layer. Every part green does not mean the system is wired up.
  2. Write down five things for every trade-off: the decision, the gain, the cost, how you verify it, and when to revisit it. Numbers need units and conditions.
  3. When you deliver, label each component's evidence stage: code written, on the main path, real data, or simulated. Never let the word "done" paper over any layer.

Common misconception: "It is most efficient to finish and test every module first, then put them together at the end."

Building in modules is fine; the mistake is "put them together at the end". The interface assumptions between modules are only tested when the modules are really connected. That is what happened to Strata's PLE module: every part passed its comparison test, yet the main path never called them, and nobody found out until the whole-model acceptance check. [S13] The later you wire things up, the more code gets written on a wrong assumption, and the bigger the rework. Wire up one thin line first and build on it; the total work is often smaller.

Go deeper: report structure, observability, and a final check of your understanding

The structure of a solid report

First pose a question you are willing to have an experiment refute; then write, in turn, the theory, where it lives in the source, the method, the data, the interpretation and the limitations. Each conclusion must say which kind it is: a code fact, an experimental result, or a guess. Every figure needs units, sample counts and measurement conditions; source links use a fixed commit hash, not just main; raw performance data and failure logs are all kept; the hashes of the model file and dependencies go into a manifest. Do not hand in just pretty screenshots.

How the rubric's red lines are enforced

Pass a teaching simulation off as a hardware measurement and none of that experiment's conclusions earn points, however careful the rest of the work is: readers can no longer tell which numbers to trust. If there is an unexplained state leak, performance points cannot offset the correctness defect. What the two red lines have in common is that they break "the evidence can be trusted" itself.

Observability: expose the mechanism that is "not actually working"

Strata's session code has two designs worth copying. One is the "synchronize every layer" debug mode. It catches bugs such as "a kernel read a buffer that only a later layer writes", which are normally invisible; its price is the synchronization overhead, so it is a runtime parameter, turned on when needed. The other is that overlap counter. If the CPU–GPU overlap degrades into serial execution, neither the return values nor the per-layer times reveal it; only a dedicated count of "layers in which the CPU got its task while the GPU was still running" can catch it. [S13] In your project, every mechanism that claims "speed-up", "overlap" or "cache hits" should come with a counter that proves it is really working.

Constraints must be catchable by tests

Strata requires no VRAM allocation while generating tokens, so all of a session's state is sized for the maximum length and allocated once, at the start. The comment points out a trap: if one allocation happened at "the first token of a longer sequence", every existing test would still pass. [S13] In other words, a constraint without a dedicated test to check it is only a wish. When you write the design document, put next to every constraint "which test fails if this is broken".

A check of your understanding as you leave this book

You should be able to explain in your own words: why a 40 GB model file does not necessarily need 40 GB of VRAM; why verifying several tokens at once is not knowing the future in advance; why the same pointer can point to different layers' data; why a fixed-size state does not mean you can roll back to anywhere; why more threads do not mean more sessions can be served; and why a faster number must carry its full conditions. These ideas carry over to any inference engine. Strata is a door into real systems, not a destination whose parameters you must memorize.
