New batch neighbors

On your own computer, Strata answers one request at a time by default. Everyone else waits in line (Chapter 25). Your question has the whole machine to itself. On a DeepSeek cluster, the situation is the opposite. Your question is squeezed into one batch with many strangers' questions, and the batch passes through every card together. This step you share a batch with 3 people. The next step, you may share it with 300.

In math, who sits next to you should not change your answer. But floating-point numbers do not obey math. DeepInfer's tests include one very strict requirement. Run 64 requests together, then run them one by one. Every token and its log-probability must be exactly equal (the single runs are forced to write the same tokens). This page explains how DeepInfer does it and what it costs. Then it shows how DeepInfer makes the model emit only a legal format.

In one line: When the batch size changes, the way the kernel groups its sums can change. The last digits of the float result then change too, and a token that was almost tied gets swapped. DeepInfer fixes the summation order with DEEPINFER_BATCH_INVARIANT=1 (NVIDIA only). Each request also carries its own seq_seed, and the random number used for sampling depends only on (seed, position), never on the batch. Its regression test requires PPL to be bit-for-bit equal. Structured outputs put a bitmask over the vocabulary before sampling, and let through only the tokens that keep the format valid.

5.1 Same question, different batch neighbors, different answer

One server step handles a whole batch of requests. The tokens of all requests are stacked into one big matrix, and the matrix passes through every layer together. The final score the model gives each candidate token (the logit) is, at heart, the sum of a long list of products. On a GPU, this sum is split across many compute units. How many segments to use, and how to merge them, is usually decided by the kernel from the shape of the matrix. When the batch has few requests, the kernel splits one row into more segments, so that every compute unit has work. When the batch has many requests, one segment per row is enough. This is a common kernel design. The toy kernel below demonstrates it. Teaching estimate

When the grouping changes, the result can change. The reason was explained in Chapter 26, “For floats, ‘equal’ needs a definition first”: floating-point addition is not associative, so with a different grouping the last digit or two can differ. This difference is usually harmless. But when two candidate tokens are almost tied, it can decide the winner (Chapter 26, “A tiny difference, and the word changes”). Once one token changes, the whole rest of the answer changes with it. Figure D5-1 is one example computed by this page's toy kernel.

Here we must separate two kinds of “reproducible”. The first is determinism: run the same batch of requests again unchanged, and the results are the same. The second is batch-invariant: whoever shares the batch and however large the batch is, the result of one request is the same. On a server, a batch almost never repeats. So only the second kind lets users see reproducible results. The second kind is much stronger than the first.

Compared with Strata: By default, Strata gives the engine to one sequence, so the only “neighbor” in the batch is the sequence itself (Chapter 25). To repeat a run byte for byte, it uses a “switch-off” recipe. You turn off the prompt cache, expert swapping, the CPU share assigned by measured time, and a few other settings that change the computation order (the “Common misconception” at the end of Chapter 2, and Chapter 26). On a cluster, you cannot choose who shares the batch, and the batch changes at every step. So DeepInfer does not turn switches off. It changes the kernels themselves, so that the result does not depend on the batch.

5.2 Batch-invariant: pin down the summation order

The README describes this feature in one sentence: keep model results the same under different batch compositions; switch it on with DEEPINFER_BATCH_INVARIANT=1; NVIDIA only. Upstream report (README.md) The switch is off by default. Code fact (environ.py) Searching the whole repository for it, we find only four places where it changes behavior: Code fact

  1. The matrix-multiplication libraries switch to deterministic algorithms. With the switch on, the worker process calls deep_gemm.use_deterministic_algorithms(True) and tile_kernels.use_deterministic_algorithms(True) at startup. On Ascend NPUs, the code asserts that the switch must be off, but it switches on both deterministic algorithms without any condition. A comment says this prevents numerical instability in CI. (runtime_config.py)
  2. Decode attention turns on FlashMLA's batch-invariant option. The decode attention function decode_mla_mqa_sparse takes this switch. On the unfused path, it passes the switch unchanged to FlashMLA's flash_mla_with_kvcache(enable_batch_invariant=…). On the fused-kernel path, the parameter is not passed down. The attention call of the draft model also carries the switch. (attention_backend.py, attn.py, draft: attn.py)
  3. The prefill engine uses one fewer fused kernel. One kernel fuses normalization, rotary position embedding, attention and type conversion. With the switch off, every attention layer in the prefill engine that meets the head-count condition uses it. With the switch on, the dense packed-KV layers take the unfused path instead. That unfused path calls FlashMLA's flash_mla_sparse_fwd, which does not accept a batch-invariant parameter. In the decode engine, layers of this kind never used the fused kernel anyway. (attn.py, attn.py, attention_backend.py)
  4. Expert communication skips one kind of merge. When batch-invariant and expert rebalancing are both on, the DeepEP buffer is created with allow_multiple_reduction=False. (userbuffer.py)

The source code of these libraries (DeepGEMM, FlashMLA, DeepEP) is not in the repository of this release. So this page knows the names of the switches, but not how the libraries implement them. From the names, they all do the same thing: they keep the grouping and order of one reduction independent of the batch shape. Teaching estimate For why expert rebalancing is involved, see the page on wide expert parallelism.

The cost is speed. The evaluation script describes this switch as: results do not depend on the batch composition, “slower”. Code fact (run_eval.py) The repository gives no number for how much slower. The toy kernel below shows where the slowdown comes from: once the number of segments is fixed, some compute units sit idle in small batches.

If you studied parallel computing: This is the old problem of parallel reduction. Split one long sum across several thread blocks (called split-K in matrix multiplication), and even a small batch can fill the GPU. But the grouping changes with the shape, so the last digits of the result change with the shape too. The batch-invariant approach gives up “pick the fastest grouping for this shape” and uses one fixed grouping instead. There is less parallelism, so it is slower.

Note one point: batch-invariant buys reproducibility, not accuracy. In the row of Figure D5-2, the sum with 4 fixed segments happens to be closest to the double-precision reference. But this is a coincidence. With another row of numbers, a different segment count may be closest. Batch-invariant only fixes the order. It does not choose the most accurate order. Teaching estimate

5.3 Deterministic sampling: the random number depends only on (seed, position)

Once the model result no longer depends on the batch, one step remains: sampling. Chapter 2 explained that sampling means taking a random number u and sticking a pin into the cumulative probabilities. To make a run replayable, u must not depend on the batch either. The README gives a recipe with three parts: DEEPINFER_BATCH_INVARIANT=1, DEEPINFER_ENABLE_MTP_VARLEN=0, and a fixed seq_seed passed to SamplingParams. Again, NVIDIA only. If you do all three, the same input tokens and sampling parameters give the same output. Upstream report (README.md) The second part is covered in the next section. First, the seed.

seq_seed is a 64-bit seed that each request carries. If you do not pass one, the constructor draws one with random.getrandbits(64). The default temperature of SamplingParams is 1.0. So with no settings at all, DeepInfer samples by probability every time, with a different seed every time, and two runs differ by design. Code fact (sampling_params.py) The scheduler copies the seeds, request by request, into the input of the sampling kernel. The position is the index of this token in the sequence. Code fact (prepare_sample.cpp)

The sampling kernel's documentation is direct: the result is decided only by (seed, sampling position, whether it is a draft prediction), and does not depend on the batch size or the row order. Its PyTorch reference implementation mixes the seed with 3 × position + case, and runs the result through the SplitMix64 hash to get u. The GPU kernel uses the random number generator built into TileLang. It initializes the generator with the seed and 3 × position + case (T.rng_init), and then draws a number (T.rng_rand). In both implementations, the random number depends only on these two inputs. Code fact (random_sampling.py, cuda/random_sampling.py) This is the counter-based pseudorandom number from Chapter 2: the n-th random number is computed directly from (seed, n), and does not depend on how many numbers were drawn before. Figure D5-3 shows its inputs.

The kernel does one more thing. To stick the pin into the cumulative probabilities, it must first add the probabilities one by one, and that is also a sum. DeepInfer's sampling kernel first converts each float32 probability into a fixed-point integer (multiply by 2³¹ and round down), and then adds the integers. Code fact (cuda/random_sampling.py) Integer addition is associative: any grouping gives the same sum, so the cumulative probability does not depend on the grouping. Each row is handled by one thread block alone, and rows share no intermediate results. Code fact (same file) The matching test shuffles the rows of a batch and samples again. It also samples each row alone. The results must equal the whole-batch results, one by one. Code fact (random_sampling.py)

A fixed seed has another side: the same seed always writes the same text. The evaluation script samples each question several times, so it gives each sample a different seed. The comment says: “the same seed produces the same output, so each sample needs its own seed”. Code fact (run_eval.py)

Compared with Strata: Both sides choose the same kind of random number. When Strata runs Flash-Next, it uses Philox, and the random number of the t-th token depends only on (seed, position t) (Chapter 2, “Pseudorandom numbers and seeds”). The default behavior is also similar. Since v0.1.45, the Strata serving layer fills in the parameters recommended by the model card for requests that give no sampling parameters. It samples by probability, and if no seed is given it uses the clock as the seed, so two answers differ by design. When you use the engine directly and give no temperature, it still decodes greedily (Chapter 2, Section 2.4). The SamplingParams of DeepInfer has a default temperature of 1.0 and a random seed. Like the Strata serving layer, it is “not reproducible by default”. Both sides can also fix the seed and keep sampling by probability. A Strata request can also carry a seed, and a fixed seed replays the sampled text (Chapter 18, Section 18.5). Code fact (server.py) The real difference is this: by default Strata has no batch neighbors to guard against, while DeepInfer must also switch on batch-invariant.

5.4 Why variable-length verification must be off

DeepInfer turns on speculative decoding by default. At each step, the draft model first guesses up to 5 draft tokens, and the main model does one verification. Code fact (environ.py) DEEPINFER_ENABLE_MTP_VARLEN=1 adds “schedule verification by confidence”. It does not verify every draft. It picks the drafts most likely to be accepted, and verifies those. It is off by default, and the evaluation script switches it on. Code fact (run_eval.py) For how drafts are produced and why they speed things up, see the page on DSpark speculative decoding. Here we ask only one thing: why does deterministic sampling require it to be off?

The README says only “turn it off”. It does not say why. The code shows the following three things.

  1. When it is on, verification slots are assigned across the whole batch. The scheduler puts the draft acceptance-rate estimates of all requests in the batch into one queue and sorts them from high to low. It then estimates the throughput from the measured forward time and sampling time, and decides how many drafts to verify in total at this step. Finally, it hands out the slots to the requests by rank. Code fact (mtp_varlen.hpp) When zero-overhead scheduling is on, the GPU also recomputes the length of each request from the confidence of the previous step. Code fact (worker.py) The Q&A document says the same: the CPU decides only the total budget, and the length of each request is recomputed on the GPU with a global sort. Upstream report (inference_deployment_qa.md)
  2. When it is off, each request looks only at itself. The “batch size to time” curve is measured during warm-up only when this switch is on. If the curve is empty, the scheduler gives every request 1 + its own number of drafts, and does not look at others. Code fact (base.py, mtp_varlen.hpp)
  3. For the same position, the random numbers differ between “verified” and “not verified”. At a verified position, a case 2 random number first decides whether to accept the draft. If the draft is rejected, a case 1 random number draws a replacement from the remaining probability. At a position that is not verified, a case 0 random number does ordinary sampling directly. Code fact (fused_sample.py)

Put the three together and you get this page's reading. With variable-length verification on, whether your request verifies drafts at some position depends on the confidence of the other requests in the batch, and on the measured time. Whether it verifies decides which random-number stream that position uses. With a different stream, even a fixed seed can draw a different token. The tokens drawn by the two methods follow almost the same distribution. Only the specific token drawn differs. Teaching estimate “Almost” is there because the resample subtracts a little too little from the residual: the draft probability is first multiplied by a factor slightly below 1, so the residual is never all zero and always has something to draw. A code comment derives an upper bound for the gap between the output distribution and the target distribution. Code fact (common.py) Figure D5-4 draws this process.

Compared with Strata: By default, Strata uses “exact equality” verification: a draft token is kept only if it is exactly the same as the token the target model draws by itself. Looking at this rule alone, however many drafts you verify, the written text does not change (Chapter 18, Section 18.5). In Strata, other mechanisms make the answer change with the drafts: tail skip (Chapter 26, Section 26.5), and the different rounding when the CPU computes one token versus a window of several tokens (the “Common misconception” at the end of Chapter 2). DeepInfer uses the classic rule “accept by probability, resample on rejection”, and each position guarantees only that the distribution stays (approximately) the same. Under this rule, “verify or not” itself changes the token drawn. So on DeepInfer, the verification length itself must be fixed. Teaching estimate

Seen from the other side, turning off variable-length verification does not turn off speculative decoding. The batch-invariant test itself runs with 5 drafts, a fixed verification length, and requires the whole-batch results and the single-run results to be equal one by one. Code fact (test_batch_invariant.py)

5.5 How upstream tests it: not one bit of PPL may differ

DeepInfer's offline regression test looks at one number only: the decode_ppl of each sample output, that is, the negative average log-probability of the output tokens, passed through the exponential. Code fact (offline_inference.py) On NVIDIA, the test turns on batch-invariant and 5 drafts, and runs the example program on 4 cards (EP4, CP2, so there are 2 DP ranks). It then compares every sample of every rank with a baseline file. The comparison is actual == expected, with no tolerance. Code fact (test_offline_inference.py) The examples README says the same: baselines are grouped by platform and workload, one group of samples per DP rank, and verification compares each sample exactly. Upstream report (examples/README.md)

These samples are not generated greedily. The temperature of each sample is 0.4, and its seed is its index. Rank r gets the same 5 questions, repeated r + 1 times. Code fact (_prompts.py) So the baseline file itself records the fact that “a fixed seed replays”. See Figure D5-5.

It is not strong evidence for batch-invariance, for two reasons. First, the example program puts at most 4 requests in a batch, so the first 4 samples of the two ranks start in batches of the same composition. Code fact (offline_inference.py) Second, the code does not allow batch-invariant to be switched on for Ascend, yet the Ascend baseline shows the same pattern: the first 5 samples of rank 1 are bit-for-bit equal to rank 0. Code fact (runtime_config.py, offline_decode_ppl.json) The code does not explain why this holds on Ascend too, and this page does not guess.

The direct evidence for batch-invariance is another test. It builds prompts of 64 random tokens, and generates 50 tokens as a whole batch with temperature 1.0 and top_p 0.7. Then it runs each prompt alone and forces it to write the tokens that were written in the whole batch. This is the teacher forcing of Chapter 26. The tokens, the log-probabilities, the top 5 candidates and their log-probabilities of the whole-batch run and the single run must all be equal with ==. Code fact (test_batch_invariant.py)

Compared with Strata: Chapter 26 teaches comparison with a tolerance (“Tolerance in float comparison”), because the CPU and the GPU of Strata compute the same expert in different orders, so the two sides should not be bit-for-bit equal. That chapter also names the exception: only the same operations in the same order must be bit-for-bit equal. DeepInfer first pins the order with batch-invariant, and only then dares to use ==. The cost is also written in the repository. A comment in the test file says that the baseline is tied to the parallel configuration, so changing EP or CP means measuring again. Code fact (test_offline_inference.py) The examples README says that any numeric change must first be confirmed as expected, and then the baseline is refreshed with a script. Upstream report (examples/README.md) An exact comparison catches every change. For the same reason, it cannot tell “wrong” from “just a different valid order”.

5.6 Structured outputs: let only legal tokens through at every step

The last topic has nothing to do with random numbers, but it is also about “keeping the output under control”. Structured outputs require the model output to follow a format strictly: a regular expression, a JSON schema or an EBNF grammar. To use it, pass so_args={"schema_type": …, "schema": …} to SamplingParams. Upstream report (README.md) The Q&A document describes the flow. The format is first compiled into a grammar automaton. At every decoding step, the automaton moves forward one step, works out which tokens are legal, produces a mask, and applies it to sampling. In production, the compilation runs asynchronously on dedicated machines. Upstream report (inference_deployment_qa.md)

Regular expressions and finite automata

A regular expression describes a class of strings. [A-Z]{2}-[0-9]{3} means: two uppercase letters, one hyphen, three digits, for example QZ-345.

To check whether a string matches a regular expression, you do not need to read back. You can turn the expression into a finite automaton. It has a finite number of states. For each character it reads, it jumps to the next state by a rule. If it stops in an “accept” state when the input ends, the string matches. The expression above needs only 7 states: “0 to 6 characters written correctly so far”.

An automaton can also answer a more useful question: in the current state, what may the next character be? Structured outputs use exactly this, except that “character” becomes “token”, and one token may contain several characters. JSON schema and EBNF can describe nested structures (brackets inside brackets). They need an automaton with a stack, but the idea is the same.

Further reading: Wikipedia: Regular expression · Wikipedia: Deterministic finite automaton · Wikipedia: Extended Backus–Naur form · OI Wiki: Automaton · MDN: Regular expressions

In the code of this release, compilation goes to the open-source library xgrammar. The three formats call its JSON-schema, regex and grammar compilers. Compilation runs asynchronously in a thread pool. A request enters the scheduler only after compilation finishes. If compilation takes longer than DEEPINFER_XGRAMMAR_TIMEOUT (20 seconds by default), the request fails. Code fact (compiler.py, matcher.py, so_matcher_builder.py, environ.py) The offline version explicitly rejects a “serialized grammar”. Code fact This matches the “dedicated compile machines” in the Q&A document: in production, the grammar is probably compiled elsewhere, serialized, and sent in. Teaching estimate

The shape of the mask is plain: one bit per token in the vocabulary, with 32 tokens packed into one int32. Token i sits at bit (i mod 32) of word i ÷ 32. Code fact (matcher.py) The GPU kernel reads these bits and changes the logit of every token whose bit is 0 to −∞. Only then does it sample and verify drafts. Code fact (structure_output.py, sampler.py) A token with logit −∞ has probability 0 and can never be drawn, so the output is always legal.

The upstream example makes things hard for the model on purpose. The prompt asks it to “continue a very long story freely, and do not write any ID”, but the format is [A-Z]{2}-[0-9]{3}. Another prompt asks it to “daydream in natural language, and do not output JSON”, but the format is a JSON schema. The test requires the output to match the format completely and to end with a normal end token. Code fact (_structured_output.py) Below, a toy vocabulary of only 12 tokens replays the first example:

If you studied compilers: This is the old job of a lexer, with the direction reversed. A lexer uses an automaton to recognize a string that already exists. Structured outputs use an automaton to limit the next character that may be written. The hard part is that tokens and characters do not line up. One token may cross several states, so at every step the whole vocabulary must be tried one token at a time. Libraries such as xgrammar exist to make this step fast.

Speculative decoding adds one more layer. In one step, the matcher must compute a mask for the real position and also one for each draft position. It first pretends to accept the draft tokens and moves forward, filling in one mask per step, and finally rolls back. Code fact (sampler.py) So the matcher must be able to roll back at most “number of drafts + 2” steps. Code fact (matcher.py) This is the same idea as Chapter 18, “Committing and rolling back a transaction”.

Compared with Strata: Strata also accepts the OpenAI-style response_format (json_object, json_schema), but works differently. Its documentation says this is “state the format in the prompt first, then check on the server”. It is not grammar-constrained decoding. It generates once, and if the result is not valid, it returns a 502 error. Upstream report (DETAILS.md) Its status endpoint also reports "constrained_decoding": False directly. Code fact (server.py) One machine serves one person, so asking again after a failure costs little. On a cluster, the request volume is large and programs often make the calls. “Guaranteed legal” is worth much more than “checked afterwards”. So DeepInfer moves the check to before every sampling step. For how JSON itself is read and written, see Chapter 23, “JSON”.

Remember these three

  1. The same request can give different results in different batches. The kernel chooses the summation grouping from the batch shape, floating-point addition is not associative, and a token that is almost tied gets swapped. DEEPINFER_BATCH_INVARIANT=1 fixes the grouping. This buys reproducibility, and the cost is speed.
  2. Deterministic sampling needs three things: batch-invariant, variable-length verification off, and a fixed seq_seed. The random number depends only on (seed, position, use) and not on the batch. Variable-length verification makes “whether this position verifies a draft” depend on the whole batch, so it must be off.
  3. Structured outputs compile the format into an automaton. At every step, they work out the legal tokens, pack them into a mask with one bit per token, and change the other logits to −∞. They do not change the model. They change only “which tokens you may choose from”.

Common misconception: “With batch-invariant on, the result is more accurate.”

No. Batch-invariant only guarantees that the numbers are always added in the same order. It does not choose a “more accurate” order. In Figure D5-2, the sum with 4 fixed segments happens to be closest to the double-precision reference, but this is only a coincidence of this row of numbers. The measurements for Strata in Chapter 26 also show that different floating-point orders are equally good approximations. What batch-invariant buys is reproducibility: the same request with the same seed writes the same text, whoever shares its batch. This helps debugging, regression tests, and a product promise of “the same question gets the same answer”. It does not help accuracy, and it costs speed.

The sampling kernel: two-level fixed-point cumulative probability

random_sampling_tl starts one thread block per row. When the vocabulary is at least 8192, it uses 256 threads and folds one row into 2048 “lanes”: lane k adds up the probabilities of columns k, k + 2048, k + 4096 and so on. A probability is first converted to a uint32 fixed-point number with floor(p × 2³¹), and then added. The first level finds which lane the pin lands in, using the sums over the 2048 lanes. The second level finds the exact token among the columns of that lane. Code fact (cuda/random_sampling.py)

The step that draws the random number has one more detail. To draw an integer in [0, total), the code first computes the largest multiple of the total, limit. If the random number falls at or above limit, it draws again, and then takes the remainder. Code fact (same file) Taking the remainder directly would make small remainders appear slightly more often (modulo bias). Drawing again removes this bias. The number of redraws depends only on the seed, the position and the probabilities of this row, so replay is not affected.

Speculative verification uses three random-number streams

The reference implementation states the three uses clearly. Ordinary sampling uses 3p + 0. To decide whether to accept a draft, it compares min(1, p_target ÷ p_draft) with a u generated at 3p + 2. After a rejection, it draws again from the residual max(0, p_target − α × p_draft), using 3p + 1. Here α = e−0.00005, a little below 1. A comment says this prevents the residual from being all zero, which would leave nothing to draw. Code fact (fused_sample.py) In the GPU kernel, the decision also initializes its random number at sample_positions * 3 + 2. (cuda/fused_sample.py) When the draft model draws its own drafts, the seed gets a fixed offset of 1000000007, so that it stays apart from the sequence of the main model. (fused_sample.py)

Temperature 0 does not take a separate branch

The documentation says temperature 0 means greedy. But the constructor changes any temperature below 10⁻⁵ to 10⁻⁵, sets top_p to 1 and top_k to −1, and then goes through the sampling kernel as usual. Code fact (sampling_params.py) After division by such a small temperature, the probability of the top token is almost 1, so in effect it is greedy. But it is not strictly greedy. When a probability is converted to fixed point, it is rounded down with floor(p × 2³¹), so the weight of the second token is not 0 as long as it is at least 2⁻³¹. Let Δ be the logit gap between the second and the first token. If e−Δ/10⁻⁵ ≥ 2⁻³¹, that is, Δ ≤ 10⁻⁵ × ln 2³¹ ≈ 2.1 × 10⁻⁴, it can still be drawn by probability. Teaching estimate (cuda/random_sampling.py)

Scheduling details of variable-length verification

MTPVarlen::schedule keeps two queues. One uses the acceptance-rate estimate of an earlier round to estimate the total budget. The other uses the acceptance rate of the latest round to assign the length of each request. A comment says this keeps the confidence of later drafts from affecting whether earlier drafts are verified. The sort is by acceptance rate from high to low, and ties are broken by the request's index in the batch. The total budget is the batch size with the largest “expected number of accepted tokens ÷ estimated time”. The estimated time = the baseline measured at warm-up + the measured slope × batch size + the median of the sampling time. Code fact (mtp_varlen.hpp; the time estimator is at L19–L131) The measured times are recorded only when variable-length verification is on. (worker.py) Two points, “ties broken by index” and “time enters the formula”, both make the verification length of one request depend on the whole batch. This is the basis of the reading in Section 5.4.

Trigger tokens of structured outputs

so_args can also carry trigger_token_ids. Until this token sequence appears in full, the model generates freely. After it appears, the grammar takes effect. The matcher finds the sequence incrementally with the KMP algorithm. With bound_token_id added, once the model writes this token, free generation is no longer allowed. The trigger sequence is then forced out token by token. Code fact (sampling_params.py, matcher.py) It suits cases such as “say a few words first, then write a tool call with a fixed format”. The code does not say which product feature uses it. When the matcher fails, only this one request fails. A comment says this keeps one request's problem from bringing down the whole engine. (sampler.py)
