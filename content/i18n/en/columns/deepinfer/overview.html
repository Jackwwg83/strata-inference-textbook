A different view

This book has been doing one thing all along: making an ordinary computer run a large model for one person. Strata's README states this goal in its first lines: a graphics card with at least 12 GB of VRAM. Upstream report[S01]

The other end of inference is DeepSeek's online service. By DeepSeek's own account, one cluster handles 155 trillion tokens a day. Upstream report (Q&A doc, line 17) On October 20, 2026, DeepSeek open-sourced DeepInfer, the inference framework behind this service. This page answers three questions: what it is, which part was open-sourced, and how it differs from Strata.

In one line: DeepInfer is the cluster inference engine for DeepSeek-V4.1-Flash: prefill, decode and vision encoding run on different machines, and the experts spread across dozens of cards. What was open-sourced is the engine itself, which can do offline inference. The KV cache system, the glue that connects the three stages, and the data-parallel load balancers are not in the repository.

1.1 The other end: the same ideas, spread over hundreds of cards

DeepInfer is an inference framework. It sits on the same layer as Strata, the "kitchen" of Chapter 1 (Chapter 1). The first sentence of the README says it is a high-performance inference framework that powers DeepSeek's large-scale online service, and that this release provides offline inference plus the core features that large-scale serving needs. Upstream report (README, line 3) For now it supports only one model: DeepSeek-V4.1-Flash.

It uses the same set of concepts as Strata: MoE experts, the KV cache, prefill and decode, speculative decoding, batching. The difference is scale. Strata finds ways to squeeze one model into one computer; DeepInfer finds ways for many machines to serve many people together. DeepSeek's Q&A doc states the three goals that were set for this system from the start: Upstream report (Q&A, lines 7–13)

  1. Support accelerator cards from several vendors, and get the most out of each platform.
  2. Build prefill and decode from ordinary hardware: prefill on ordinary 8-card machines, decode on ordinary 64–128-card supernodes, that is, groups of cards joined into one unit by a high-speed interconnect.
  3. Keep the KV cache for more than 72 hours: when an old conversation comes back, a cache hit means no new prefill.

To feel the scale gap: the Q&A doc says decode should start from EP64, and the ratio of prefill cards to decode cards is about 1:1, so the "smallest efficient deployment unit" is 64 cards for prefill plus 64 cards for decode. Upstream report (Q&A, lines 65–67) EP is expert parallelism (EP), covered in detail on page 2. Figure D1-1 puts the two ends side by side.

Compared with Strata: Strata's problem is "it does not fit": a 12 GB card cannot hold 34 GB of experts, so it stores them in tiers and lets the CPU help (Chapter 10). 1.2 One request's journey: a map of the production system

In its Q&A doc, DeepSeek draws a reference architecture diagram: the system is made of compute nodes with E/P/D disaggregation plus dedicated storage nodes. Upstream report (Q&A, lines 41–43) E is the vision encoder (VE), which turns images into vectors; P is prefill; D is decode. Deploying them separately lets each stage get its own resources, and lets time to first token (TTFT) and time between tokens (TBT) be tuned separately. Upstream report (Q&A, lines 27–31)

Attention uses data parallelism (DP), and the number of DP copies equals the number of EP copies: each card serves the attention of its own batch of requests, and the MoE layers then cooperate through expert parallelism. With so many replicas, the work has to be handed out, so DeepSeek built four load balancers: the prefill, decode and VE balancers handle assignment among data-parallel replicas, and expert load balancing (EPLB) handles how experts are spread across cards. To avoid repeating prefill, there is also a KV cache storage system. Upstream report (Q&A, line 33) At the entrance and exit there is also a DeepSeek Recipe, which converts between API protocols and token sequences.

The map below redraws that architecture diagram and checks against the repository whether each block is open source. Click a block to read its description; press Step to follow one request from the door to the exit.

The easiest step to miss in this diagram is the one Entrypoint takes first: it queries KV storage to work out how long a prefix of this request can hit, and only then can it route. The Q&A doc stresses that this step cannot be hidden behind other work. Upstream report (Q&A, line 157) The longer the hit, the less prefill has to compute, so "how long the hit is" decides how heavy a job this request is. How to size the cards of each stage, how KV is stored, and how it moves from P to D are all on page 3; the algorithms of the four load balancers are on page 2.

If you studied CS: This is the classic layering of a web backend: a gateway does protocol conversion (Recipe), a load balancer hands requests to a group of application servers (P and D), and state lives in a separate storage cluster (3FS). The difference is that one "application server" here is a communication domain made of dozens of cards. See Wikipedia: Load balancing.

Compared with Strata: Strata squeezes this diagram into one computer: serve/server.py handles HTTP and queueing, and serve/frontend.py applies templates and parses the output (Chapter 23); the engine prefills first and then decodes on the same card (Chapter 16). With the default configuration, one lock lines the requests up in a single queue (Chapter 25). On a cluster, every layer must become its own service, because one machine can neither hold all the users nor make all of them wait in one line.

1.3 The open-source boundary: what is in the repository and what is not

The README states the boundary clearly. The features open-sourced this time are: optimized kernels and models, and the sampler runtime; data parallelism for attention with balanced context parallelism (CP), and expert parallelism for MoE plus EPLB; DSpark and confidence-scheduled verification; bounded replay for sliding-window attention (SWA); asynchronous scheduling, that is, the zero-overhead batch scheduler; batch-invariant inference; deterministic sampling; and structured outputs. Upstream report (README, lines 9–18)

It also lists three things that a complete inference service needs but that are not included this time: Upstream report (README, lines 38–42)

  • a KV cache system;
  • disaggregated deployment of VE / prefill / decode (the README adds that most of the functionality the engine needs is already implemented);
  • load balancing between data-parallel replicas for prefill and decode.

The Q&A doc gives the reason: KV cache management and load balancing are tied too closely to DeepSeek's internal infrastructure, so they are not fully open-sourced for now. Upstream report (Q&A, line 21) DeepSeek Recipe was open-sourced separately, as another repository, deepseek-recipe. Upstream report (Q&A, line 19)

The claim that "most of it is already implemented" has a counterpart in the code. The engine has three types: NORMAL does both prefill and decode, PROMPT does only prefill, and COMPLETION does only decode. Code fact (engine_type.py; the C++ side defines the same thing in scheduler.hpp) But the main engine class LLMEngine has a comment saying "everything from here on is virtual functions": initializing PD disaggregation, saving KV after prefill, saving KV, and sending finished requests to the decode engine. These functions have only a one-line description and no body. No other class in the repository implements them. Code fact (llm_engine.py, lines 800–858) Figure D1-3 draws this boundary.

One more easy mistake: the repository has a directory called deepinfer/entrypoints/, but it is not the production Entrypoint of Figure D1-2. It holds only one offline LLM class: it builds the engine in the current process, feeds in a batch of prompts, and calls step() in a loop until all are done. Code fact (llm.py) The only HTTP server in the repository is a performance-profiling endpoint, POST /profile, which is off by default and does not take user requests. Code fact (profile_server.py)

The Q&A doc says production does not use tensor parallelism (TP) or CP for now, yet the README and the examples both support CP (the examples have --cp 8). Upstream report (Q&A, line 53, examples/README, lines 6–8) The two do not conflict: one says how the live system is configured, the other says what the code can do.

If you studied CS: This is the very common "scripting layer plus native core" structure. Databases and browsers are often layered like this too.

1.5 Who can run it, how many cards it takes, and what happens when something breaks

First, the bar to entry. There are only two kinds of hardware: NVIDIA SM100 GPUs and Huawei Ascend 950 NPUs. The software needs Linux, GCC 13 or later, and Python 3.12; NVIDIA needs CUDA 13, and Ascend needs CANN 9.2. Upstream report (README, lines 33–52) The default argument of the offline example is --ep 8, that is, it is written for one 8-card machine. Code fact (offline_inference.py) The size of the benchmark is set by the environment: ep_size = WORLD_SIZE × visible cards, where WORLD_SIZE is the number of nodes. Upstream report (examples/README, line 61)

So most readers of this column cannot run DeepInfer, and this book has not run it either. Every number below was reported by DeepSeek itself, and this book has not re-measured any of them.

Upstream report (README, line 83) The decode chart's throughput is not a measured acceptance rate; it is scaled by an assumed acceptance rate. Page 4 explains in detail how this accounting works.

What scale is 155 trillion tokens? Spread over the 86,400 seconds of a day: 155 × 10¹² ÷ 86,400 ≈ 1.8 billion token/s. Strata writes an answer at about 93 token/s on one RTX 5070 (Chapter 1), and 1.8 billion ÷ 93 ≈ 19 million. Teaching estimate This ratio only gives a feel for the order of magnitude: the Q&A doc does not say how many of the 155 trillion are input and how many are cache hits, while Strata's 93 counts only output.

Autoscaling and fault tolerance. The Q&A doc has one section on how the live system copes with traffic swings and bad cards. Upstream report (Q&A, lines 193–211) Prefill decides how many machines it needs by "the number of tokens that missed the cache", and decode adjusts by "the number of requests that are running"; every adjustment is rate-limited, with upper and lower bounds. After a decode engine receives a take-offline notice, it has a 1-minute grace period, and the requests it has not finished are handed over, together with their KV cache, to another decode engine in one go to continue. Some redundancy is always kept: the pool has idle machines on standby, and there are more online instances than the computed demand; when quota utilization is above 0.8, scaling in is forbidden. A restart takes minutes, so fault tolerance relies on redundancy and request-level re-routing, not on restarting a single engine faster.

Wide expert parallelism has one particular weakness: all the cards of an instance form one communication domain, and when one card breaks, the whole instance cannot be used. On restart, the platform decides the EP size again from the number of healthy cards. The code has a matching piece: the number of redundant experts is padded automatically until "the total number of experts is divisible by ep_size", so the EP size need not be a divisor of 384. Code fact (eplb/__init__.py) The link between this and failure recovery is this book's inference; the Q&A doc does not say it. Teaching estimate

Compared with Strata: Strata has only one machine, with no "other card" to take over. Its lifecycle question is how the process starts and how a request is cancelled (Chapter 24 "Cancellation"), and its queueing question is how one line is organized (Chapter 25 "Queueing theory basics"). On a cluster, bad cards are the normal case, so "can we keep serving with one card fewer" becomes part of the design.

1.6 How to read this column

Each of the next four pages picks one piece of the production system, explains its logic, and then lands on the code. Every page first returns to a concept this book has covered, then says where the cluster differs. Figure D1-5 is the roadmap.

  • Page 2 Wide expert parallelism: attention uses data parallelism and experts use expert parallelism; why EP64 has higher throughput than EP8; how EPLB and the three data-parallel load balancers split the work. Read Chapter 10 and Chapter 21 "Pipeline parallelism and tensor parallelism" first.
  • Page 3 E/P/D disaggregation and the 72-hour KV cache: why VE, P and D are separated; how the KV cache is stored in an SSD cluster, and how only a small segment is recomputed after a hit. Read Chapter 17 "Paging" and Chapter 20 first.
  • Page 4 DSpark speculative decoding and zero-overhead scheduling: how many tokens the draft guesses at once, and how confidence decides how many to verify; the GPU keeps running while the CPU plans the next step. Read Chapter 18 and Chapter 25 "Continuous batching" first.
  • Page 5 Batch invariance, deterministic sampling and structured outputs: why the same input gives different output on a server and how to make it the same again; how to make the model output only valid JSON. Read Chapter 26 and Chapter 2 first.

Remember these three

  1. DeepInfer and Strata use the same set of concepts, but their hard problems are opposite: Strata must squeeze a model into one computer, while DeepInfer must have hundreds of cards serve many people together.
  2. The production system is made of Recipe, Entrypoint, the E/P/D-disaggregated VE / P / D, four load balancers and a KV storage cluster. What was open-sourced this time is the engine itself and EPLB, which can do offline inference.
  3. The KV cache system, the glue that connects the three stages, and the data-parallel load balancers are not in the repository; the engine leaves types and empty hooks for them, and whoever deploys it must fill them in.

Common misconception: "DeepInfer is open source, so I can take it and build an online service like DeepSeek's."

This repository provides only offline inference: one process takes a batch of prompts and exits when it is done. There is no HTTP service that accepts user requests, no KV cache system, no glue that connects prefill and decode, and no data-parallel load balancer. The only hardware the README lists is SM100 and Ascend 950, and the smallest efficient unit the Q&A doc suggests is 128 cards. Its greatest value is that it lets people see how a production-grade engine is written inside.

Go deeper: the call chain of one offline inference run, and how to check the open-source boundary yourself

From the command line to the kernels

Take python examples/offline_inference.py as the example. Every step below was checked against the source at the pinned commit 774ce244.

  1. Start the process. The example defaults to --ep 8 (offline_inference.py, lines 12–17). run_dp in examples/_launch.py starts one child process for each DP rank that this node is responsible for, according to RANK and WORLD_SIZE (lines 26–40).
  2. Build the engine. LLM.__init__ constructs EngineArgs with offline_inference=True, then calls LLMEngine.from_engine_args (llm.py, lines 70–84). The engine type in EngineArgs defaults to NORMAL (arg_utils.py, line 41).
  3. Zero-overhead scheduling is on by default. The raw default of DEEPINFER_ZERO_OVERHEAD_SCHEDULING in environ.py is off (line 179), but when the user has not set it, EngineArgs.__post_init__ turns it on by engine type: on for NORMAL and COMPLETION, off for PROMPT (arg_utils.py, lines 48–55, engine_type.py, lines 15–17). So the README's "enabled by default" matches the code.
  4. Tokenize and submit. generate() hands each prompt to _add_request; when no token ids are given, it encodes the prompt with the Hugging Face tokenizer (llm.py, lines 144–166). In production, Recipe does this step.
  5. Main loop. _run_engine calls LLMEngine.step() again and again until no unfinished request remains, then flushes the in-flight results (lines 168–195). LLMEngine imports Scheduler, BlockManager and others from the C++ extension deepinfer._C.engine (llm_engine.py, lines 19–31). setup.py builds this extension from the source files under csrc/, split into three submodules: cuda_utils, engine and graph_timer (pybind.cpp).
  6. On each card. Worker drives the forward pass, post-processing and sampling of every step (worker.py), and ModelRunner runs the model (model_runner.py). The model is found through a registry: the architecture name DeepseekV41ForCausalLM maps to deepseek_vl.DeepseekVLForCausalLM (models/__init__.py, lines 15–17), which inherits from the text-only DeepseekForCausalLM (deepseek_vl.py, line 26).
  7. Down to the kernels. The platform class decides which set of TileLang operators to use: cuda for GPUs and asc for NPUs (platform.py, lines 55–88). The other operators come from the kernel libraries in Table D1-2.

Check the open-source boundary yourself

The claims on this page about what is "not open-sourced" can be re-checked in a clone with three commands:

  • git show 774ce244:deepinfer/engine/llm_engine.py | sed -n '800,858p': you see "everything from here on is virtual functions" and a run of functions that have only descriptions.
  • git grep -n "def send_processed_prompts" 774ce244: there is only one definition, in llm_engine.py, and no subclass implements it.
  • git grep -n -w "3FS" 774ce244 -- '*.py' '*.cpp' '*.hpp' and git grep -n "kvcache-store\|kvcache_store" 774ce244 -- '*.py' '*.cpp' '*.hpp': both return nothing. 3FS and kvcache-store appear only in the Q&A doc. (Do not add -i: with case-insensitive matching, %.3fs in a log format string would be a false match.)

What this page did not check

The 6 submodules under vendor/ are not expanded in the clone this book used, so this page only says how DeepInfer imports them and does not judge their implementation. deepseek-recipe is another repository, and everything this page says about it comes from Q&A lines 19 and 35 and lines 290–312. The model shapes come from config.json at commit 1bae0e10 on Hugging Face, which is not bound by DeepInfer's pinned commit. The numbers in the two performance charts were read off the charts by this book, with a precision of about half a grid step.
