You may have noticed

Drop a long document into a chat AI and the first question takes a while to start answering. Ask a follow-up, and the answer appears almost at once. Chapter 20 explained Strata’s way: save the prefix it has already read as a checkpoint in the computer’s own RAM, and next time read only the new part.

DeepSeek’s online service catches countless follow-ups like this every day. It turned the same idea into a cluster system: reading the prompt and writing the answer run on two separate groups of GPUs, and the KV cache goes into a dedicated SSD cluster that keeps it for 72 hours or more. This page answers three questions. Why split the two phases? Where does the KV cache live? After a hit, how does the engine pick up where it left off, and how does a near miss cost less recomputation?

In one line: Prefill is limited by compute and decode is limited by bandwidth, and they slow each other down on the same group of GPUs. So DeepSeek deploys the vision encoder, prefill and decode separately. The KV cache sits in a dedicated 3FS storage cluster and is read back on a hit. If the small sliding-window part is missing, the engine recomputes only 128 tokens. The open-source DeepInfer ships the engine roles and cache layout these steps need. It does not ship the code that joins the KV cache system to the disaggregated deployment.

3.1 Reading the prompt and writing the answer: why they need two groups of GPUs

Chapter 16 explained that a request has two phases. Prefill is “reading the prompt”: every prompt token is already known, thousands of them are computed together, the weights are read once for the whole block, and the bottleneck is compute. Decode is “writing the answer”: each step adds only a few tokens per request (DeepInfer runs speculative decoding; in the benchmark charts it averages about 3 tokens per step), yet each step must read the weights and the KV cache once, so the bottleneck is bandwidth. The two phases sit at different places on the roofline. See Chapter 5 “Compute and roofline” and Chapter 16 “Batching”.

Users feel two metrics, too. Time to first token (TTFT) is the time from sending the request to seeing the first word. It is mostly spent in prefill. Time between tokens (TBT) is the gap between two neighboring tokens after that. It depends on how fast each decode step is and whether something interrupts it.

Trouble starts when the two phases share one group of GPUs. DeepInfer’s open-source code has exactly this “mixed” engine, and its scheduling is the clearest way to see the problem. Code fact The engine has three roles: NORMAL does both phases, PROMPT does only prefill, and COMPLETION does only decode (engine_type.py). In every step, a NORMAL engine either runs prefill on the whole group or runs decode on the whole group. The GPUs in one data parallelism (DP) group must do the same kind of work, and one vote makes them agree (scheduler.hpp). By default, a vote point comes once every 70 decode steps, and prefill runs only if every rank has prefill work. There is also a fallback point every 100 steps, where prefill runs if any rank has work (environ.py).

With this schedule, while one prefill step runs, decode for every user on the group stops for as long as that step takes. The timeline below puts the two deployments side by side. The step times come from two benchmark charts in the DeepInfer README: one prefill step of 32,768 tokens takes about 376 ms, and one decode step takes about 13 ms. Teaching estimate The two charts use different hardware, so we borrow only their order of magnitude. See “Go deeper” at the end for the conditions.

Two things show up in the figure. First, with mixed deployment the gap between decode steps sometimes jumps from 13 ms to 389 ms, and a user who is reading the answer feels a hiccup. Speculative decoding emits about 3 tokens per step, so the average is about 4 ms per token, and the tokens arrive in bursts. Here we use the step gap to stand for TBT. Second, to stop fewer times, the mixed engine saves up prefill work, so a new request waits for the next vote point and TTFT gets longer. The real mixed engine is a little worse: right after one prefill step, the next step may land on a vote point, and if every rank still has work, prefill continues (scheduler.hpp). Code fact

So DeepSeek’s production system deploys the vision encoder (VE), prefill and decode separately, each on its own GPUs. This is called E/P/D disaggregation. The Q&A document says that after the split each phase gets its own resources, so TTFT and TBT can be controlled and tuned separately (Q&A document). Upstream report In the open-source code, a PROMPT engine must “send” the finished prompt “to the completion engine”, but that function is empty (llm_engine.py). Code fact The README also says that disaggregated deployment is not part of this release, and only that “most of the engine features it needs are already implemented” (README). Upstream report

If you studied CS: This is the old operating-systems problem of interactive jobs and batch jobs fighting for the same CPU. Once a long job holds the processor, the response time of short tasks stretches. Chapter 25 calls this the convoy effect and showed it with FIFO and round-robin (Chapter 25 “Scheduling algorithms”). Disaggregation is like giving each kind of task its own machine. Academia makes the same argument; see the DistServe paper.

Compared with Strata: Strata runs on one computer, so reading the prompt and writing the answer must take turns on the same GPU. In the benchmark table of Chapter 16, the RTX 5070 reads a 32K prompt at 2,171 tokens per second and writes the answer at 81.8 tokens per second Upstream report. By default the server runs only one conversation at a time (Chapter 17). With one user, nobody is waiting for decode while the prompt is read, so splitting makes no sense. On a cluster, one long prompt’s prefill would stop decode for hundreds of users in the same group, so it must be split.

After the split, each phase can choose its parallelism by its own bottleneck. The Q&A document gives this setup (goal, parallelism). Upstream report

The two ends choose in opposite ways. One prefill step already holds tens of thousands of tokens, so each expert gets enough tokens to keep the matrix multiplications busy, and a smaller EP also means less cross-GPU communication. A decode step has only a few tokens per request, so the tokens of many requests must gather on the same expert to form a decent batch. That is why a larger EP is better. Teaching estimate The Wide-EP page works out this calculation in detail. A supernode is a system of 64–128 GPUs joined by a fast interconnect so that they act as one unit.

The smallest possible deployment is 1 prefill instance plus 1 decode instance. In practice P and D GPU counts are about 1 : 1. Decode recommends EP64 or more, so the smallest efficient unit is 64 prefill GPUs plus 64 decode GPUs (Q&A document). Upstream report Figure D3-2 draws this unit.

Can P and D sit in different data centers? The Q&A document says yes. V4.1 Flash compresses the KV cache so small that sending it across data centers is feasible, and about 400 Gbps of interconnect bandwidth is reserved for every 8 GPUs. The price is reliability: a fiber between two sites can be cut by one shovel during construction. DeepSeek in fact puts the inference nodes in different but neighboring data centers (Q&A document). Upstream report

The table says CP is not used in production, yet the open-source code includes it, and the README feature list says “balanced CP” (README). There is no contradiction: the code supports it, and production does not turn it on. Context parallelism (CP) cuts one long prompt into pieces and lets several GPUs compute attention together. The code lets only prefill use it (llm_engine.py). Code fact The “balanced” way of cutting is explained in “Go deeper” at the end.

The number of GPUs is not fixed either. The Q&A document says prefill decides how many machines it needs from “how many tokens missed the cache”, and decode adjusts to “how many requests are running” (Q&A document). Upstream report In other words, the hit rate directly decides how many prefill machines to run. The rest of the details on scaling and fault tolerance are on the overview page.

3.3 Where the KV cache lives: GPU memory, local RAM, 3FS

The third goal DeepSeek set for this inference system is to keep the KV cache for 72 hours or more. A longer window means a user who comes back the next day and asks a follow-up still gets a hit, which saves a repeated prefill. The price is a lot to store and a lot to manage (Q&A document). Upstream report The KV sits in three places. Figure D3-3 draws them from the table in the Q&A document (table).

Why use a dedicated storage cluster, instead of each machine’s own RAM plus disk? The Q&A document gives three reasons (Q&A document). Upstream report

  • Any prefill machine can hit any prefix. The load balancer only cares which machine is idle, and does not need to worry about “which machine holds this user’s cache”. For this reason prefill load balancing also does no prefix-affinity routing (Q&A document).
  • Storage nodes and compute nodes can scale separately.
  • If a compute node breaks, the KV cache is not lost. Compute nodes fail more than ten times as often as storage nodes.

The KV produced during decode is also written to disk, to raise the hit rate (Q&A document). Upstream report The reason is simple: the answer written in this round is the prefix of the next round’s prompt.

The recommended storage server has 20 SSDs of 30.73 TB each. Each server must give at least 40 GB/s of reads and 5 GB/s of writes, the total capacity must hold 24 hours of data, and the number of servers grows with the size of the inference deployment. In logical size, each online inference GPU corresponds to about 14.4 TB of storage, and the physical capacity needed is larger (Q&A document). Upstream report

Let us do a rough calculation with these numbers. The raw capacity of one storage server is 20 × 30.73 ≈ 615 TB. The 10 + 2 erasure code makes physical space 1.2 times the logical data, so dividing by 1.2 gives about 512 TB, which holds the logical data of about 512 ÷ 14.4 ≈ 36 online GPUs. Of these 36 GPUs, about half do prefill and half do decode. Decode GPUs do not read prefixes from storage, because prefill GPUs send their KV over. So the ones that really read are about 18 prefill GPUs, and when they read at the same time each gets about 40 ÷ 18 ≈ 2.2 GB/s. Teaching estimate This is only a rough lower bound for sizing machines by capacity. The Q&A document does not give a ratio of storage servers to GPUs, and one read is spread over many nodes of an erasure group. The interactive figure in Section 3.5 uses this number again.

3FS is DeepSeek’s own distributed file system (the 3FS GitHub repository). It must stay highly available and fast under node failures and network jitter. Data is stored with a 10 + 2 erasure code, so each erasure group can lose two nodes at once. According to the Q&A text, a read sends requests to 11 nodes of the group at the same time (a group has 10 + 2 = 12 blocks), and any 10 replies are enough to decode the data. Each storage node runs a garbage-collection process (GC Worker) that periodically clears old cache in least-recently-used (LRU) order, keeping disk usage below a watermark (Q&A document). Upstream report

Erasure code: store a few extra check blocks, and the data comes back even after a few blocks are lost

The simplest way to avoid loss is three copies. If two copies fail, one is left, but it costs three times the space. An erasure code is cheaper: it cuts the data into k blocks, computes m check blocks, and stores k + m blocks on different machines. As long as any k blocks survive, the original data can be computed back.

Definition: a (k + m) erasure code tolerates the loss of any m blocks at the same time, and its space overhead is (k + m) ÷ k times. A common construction is the Reed–Solomon code. It treats the data as values of a polynomial, and lost values can be interpolated back from the remaining points.

A concrete number: 3FS stores the KV cache with 10 + 2. It uses only 20% more space, and losing any two nodes loses no data. Three copies cost 200% more and can also survive only two failures. The price is that reads and writes must compute the code, and a read must collect 10 blocks.

How it relates to this page: a broken KV cache can be recomputed, so it may seem not worth this care. But it must last 3 to 7 days and about 100 PiB, and one node failure would lose the hits of thousands upon thousands of users. The erasure code lets this “recomputable data” buy higher availability with less space.

Further reading: Wikipedia: Reed–Solomon error correction · Wikipedia: RAID · Wikipedia: Erasure code

The kvcache-store layer has no expiry logic; reclamation relies entirely on 3FS’s own GC. 3FS provides about 100 PiB of SSD for the KV cache. The retention time (TTL) is 3 days for agent traffic and 7 days for chat traffic. Chat traffic has a heavier long tail, with a small amount of KV read many times. From experience, giving chat traffic only a 3-day TTL would lower its hit rate by 0.5%–1% (Q&A document). Upstream report This is exactly the hit rate and working set from Chapter 12: how long ago an access still counts decides how large the cache must be (Chapter 12 “Hit rate and working set”).

If you studied CS: A 10 + 2 erasure code follows the same idea as RAID 6: store two extra check blocks, and any two lost blocks can be recovered. “Send 11 requests and decode once 10 arrive” is a redundant read: send one extra request, take the first 10 that come back, and do not wait for the slowest one. This cuts the long-tail latency.

Compared with Strata: Strata’s KV cache is also tiered: it normally sits in GPU memory, and when the context goes beyond 64K, the full KV goes to RAM and GPU memory keeps only the hot pages (Chapter 17 “The KV cache and paged management”). The checkpoints for prefix reuse also sit in local RAM, about 118 MB each, with at most 6 kept (Chapter 20). One computer serves one person, and the next follow-up lands on the same machine again, so local RAM is enough. At DeepSeek, a user’s next request can land on any prefill machine, and the KV must be kept for 3 to 7 days. So it can only go into a shared storage that everyone can reach.

3.4 Two kinds of KV: paged block KV and fixed-size SWA state

The attention in V4.1 Flash has two kinds of memory. One grows as the conversation grows, as in Chapter 17, and is managed with paging. It is called block KV. The other remembers only the most recent short stretch, and is called SWA state. Sliding-window attention (SWA) is a simplified form of attention: each token looks only at a recent stretch before it, and does not look outside the window (for attention itself see Chapter 8 “The attention mechanism”). The window in V4.1 is 128 tokens (Q&A document). Upstream report The window size comes from the model’s config file (config.py), and the config file itself is not in the code repository.

DeepInfer manages the two kinds of memory with two allocators (llm_engine.py). Code fact

  • Block KV uses blocks of 128 tokens and is found through a block table, like the paging in Chapter 17 (model_metadata_utils.py). Block KV holds the main KV and the indexer’s K (Q&A document). One KV record is 512 numbers plus scale factors: 528 bytes in FP8 and 288 bytes in FP4 (cache_common.py). A compressed layer stores one record only for every ratio tokens, so one block of 128 tokens takes only 128 ÷ ratio records (cache_engine.py, same file).
  • SWA state does not go into paged blocks. Each sequence takes one fixed-size slot in the state cache, called a StateBlock. The slot is divided into two zones by whether it is archived: the front part is the SWA that is archived, and the rear part is what is not archived, including the SWA of the YoCo consumer layers and the compressed state (cache_engine.py). Each layer is a ring buffer holding 128 + 6 = 134 tokens, and the extra 6 are kept for speculative decoding rollback (cache_engine.py, environ.py). With default settings, the token at position pos is written to cell pos mod 134, and a new token overwrites the oldest (prepare_tensor_input_v4.cpp).

When a request arrives, the allocator gives it one block table and one slot number at once (block_manager.hpp). Code fact Figure D3-4 draws these two things.

Only the front zone of the SWA state needs to be archived. The code calls this zone “to disk”, but the SWA does not go into 3FS. It sits in local RAM, as explained below, and this page calls it “archive” throughout. The Q&A document computes its size: 20 layers × 134 tokens × 528 bytes = 1,415,040 bytes, about 1.4 MB per sequence (Q&A document). Upstream report The formula in the code matches: the archive size equals “the number of archived layers × the bytes of 134 tokens per layer (aligned to 32 bytes)” (cache_engine.py). Code fact 134 × 528 = 70,752 bytes, which is exactly a multiple of 32, so alignment wastes no space. Teaching estimate “The first 20 layers are archived” is a number given by the Q&A document; the code works out the layer count itself from the model config.

This state is archived only at integer multiples of 128. The archive granularity in the code is 128, and an archive position that is not a multiple of 128 raises an error right away (cache_engine.py, same file). Code fact According to the Q&A document, during decode, every time the position crosses a 128 boundary, a copy of the current window is made in GPU memory, and when the request ends, the archive is taken from the most recent copy (Q&A document). Upstream report The open-source code has the copy function, but should_copy_state, which decides whether to copy, always returns False (llm_engine.py). Code fact How prefill and decode each pick the archive position is in “Go deeper” at the end.

Where is it stored? The SWA state does not go into 3FS. It stays only in the RAM of the machine that produced it. The Entrypoint machines hold an in-memory directory. Logically it is one directory, but physically it is spread by key over the Entrypoint machines, and it records which machine has which SWA segment. On a hit, if the local machine does not have it, the state is pulled from another machine over the 400G VLAN (Q&A document). Upstream report When prefill hands off to decode, the SWA state travels the same way as the block KV. In the code, the state sent to the decode engine is larger than what is archived: the non-archived zone (the consumer-layer SWA and the compressed state) is sent along too (cache_engine.py). Code fact

In the open-source code, the interfaces for archiving and transfer exist, and their bodies are empty. LLMEngine has a row of “virtual functions” that initialize disaggregated deployment, save KV, and send a finished prompt to the decode engine, and by default they do nothing (llm_engine.py). The sequence object leaves fields such as “hit token count” and “SWA valid start” for outside code to fill, and a comment says “hit count injected from outside” (sequence.hpp). Code fact I did not find, in this release, any code that looks up hits in external storage and writes them into these fields. This agrees with the README (README).

Compared with Strata: Chapter 20 compares the two kinds of memory to a notebook and a whiteboard. The KV cache is like a notebook: you write forward by position, and to go back you just ignore the last few lines. The recurrent state of GDN is like a whiteboard: every token rewrites the whole board, and the past can only be recovered from a photo taken earlier (Chapter 20 “Snapshots and copy-on-write”). DeepInfer’s block KV is the notebook, and the SWA state is closer to the whiteboard: a fixed-size ring buffer where a new token overwrites the oldest. It does not rewrite the whole board at every step like GDN. One step changes one cell. What they share is that overwritten history cannot be brought back. So, like Strata’s GDN state, it can only be archived by taking a photo at agreed positions. Strata’s checkpoint is about 118 MB, and most of it is that whiteboard. DeepInfer archives only about 1.4 MB of SWA per sequence, because the window is only 134 tokens.

3.5 Read on a hit, recompute only 128 tokens if SWA is missing: bounded replay

A request of length L arrives. How much can be reused? The rule in the Q&A document: the hit length is decided by the block KV, and whether the last block must be recomputed is decided by the SWA state (Q&A document). Upstream report There are three steps:

  1. The hit length is at most L − 134: 128 tokens are kept for the window, and 6 for speculative decoding rollback.
  2. Look up the block KV within this limit to get the hit length L1, which is a multiple of 128.
  3. Then look up the SWA state. If there is an archive between L1 − 128 and L1, the hit length is L1. If not, step back one block, so the hit is L1 − 128, and the 128 tokens given up are recomputed.

After stepping back one block, how is the recomputation done? The exact way is to rebuild the SWA state from the very beginning, but the sliding window looks back layer by layer and would have to trace very far. DeepInfer uses bounded replay: it recomputes only the latest 128 tokens, and cuts the window inside the replay segment. When replay starts at position s, the query at position i sees only the keys from max(s, i − 127) to i, which yields an approximate SWA state. The number of tokens to replay becomes a constant, independent of how long the context is, although these 128 tokens still go through every layer (Q&A document). Upstream report In the code, for ordinary prefill, the left end of the SWA visible range is the larger of the “window left end” and the “SWA valid start” (prepare_tensor_input_v4.cpp). History before the valid start is filled with zeros, and attention cannot see it (same file). Code fact This is the implementation of max(s, i − 127) in the Q&A, where s is the valid start. When the truncation described below is on, another function takes one more value, the “truncation left end”, and uses the largest of the three (same file).

The same trick is used in another place, and it applies to every prefill. The layers of V4.1 Flash split into two halves: the front are “encoder layers” and the rear are “decoder layers”. The block KV of the decoder layers is not computed by those layers. It is projected from the hidden state of the last encoder layer, and each layer only needs to compute its own SWA state. The code calls this structure YoCo, and the paper of the same name, “You Only Cache Once”, describes a similar “decoder-decoder” structure. To compute the decoder layers’ SWA exactly, the last 2,560 tokens must run through the 20 decoder layers. DeepInfer lets only a short tail of the prompt go through these 20 layers, and the result is used for decode only and does not enter the prefix cache. The Q&A says this cuts the total compute of prefill almost in half (Q&A document). Upstream report 2,560 is exactly 20 × 128: with each layer, the sliding window looks another 128 tokens further back. Teaching estimate

The switches for this part are described very concretely in the README and the code. Setting DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=compact and DEEPINFER_YOCO_PREFILL_KEEP_TOKENS=140 is the default usage for V4.1, and the tail that is kept must cover the window plus the maximum rollback length (README). Upstream report The code requires KEEP_TOKENS ≥ window + rollback, that is, at least 128 + 6 = 134. It is checked once when the model loads and once more each time the input is prepared, and it raises an error if not met (model_runner.py, prepare_tensor_input_v4.cpp; the rule is written in the notes of environ.py). Code fact The Q&A says decoder layers recompute only the “last 128 tokens”, but the code and README actually keep KEEP_TOKENS of them, and the default usage is 140. This page follows the code.

After a hit, how does the KV get from 3FS back into GPU memory? The Q&A document breaks it into three steps (Q&A document). Upstream report Match: the Entrypoint compares prefixes along a hash chain. It touches only metadata, but the hit length must be known before routing, so this step cannot be hidden. Fetch KV: a separate process asynchronously moves the KV from 3FS to host shared memory. Swap in: a thread in the engine copies it layer by layer into GPU memory, overlapping with the forward computation. KV blocks are small and scattered, so the swap-in uses GDR, which lets the RDMA NIC fill the PCIe bandwidth and uses none of the GPU’s compute units. For the idea of “moving while computing”, see Chapter 14 “Synchronous and asynchronous”.

So how much does reading back save compared with recomputing? The calculation below uses numbers reported by DeepSeek as defaults. Each storage server reads at least 40 GB/s Upstream report. Prefill handles about 87,000 missed tokens per GPU per second, from a README benchmark chart (4 SM100 GPUs, EP4DP4, 131,072 context) Upstream report. How large the KV of one token is, this page has not verified, so the default is 8 KiB, which is an assumption. There is one more assumption: the 87,000 in the chart is an average throughput, and here we use it directly for “the tail after a long prefix”. The tail must run attention over more than 110,000 tokens, so it may actually be slower. Teaching estimate

The result: reading is much faster than computing. For a 128K request with a 90% hit, prefill drops from about 1.5 seconds to about 0.18 seconds. The break-even point is “read bandwidth ÷ prefill throughput”: 40 GB/s ÷ 87,000 tokens/s ≈ 449 KiB. If the KV per token is smaller than that, reading is faster than computing. But with the capacity estimate of Section 3.3, about 18 prefill GPUs read from one storage server at the same time, and each gets only about 2.2 GB/s, so the break-even point falls to about 25 KiB, only 3 times above the assumed 8 KiB. Teaching estimate So the read bandwidth of storage must be sized together with the number of online GPUs. Otherwise the time saved by a hit is eaten by queueing for reads.

Remember these three

  1. Prefill is limited by compute and decode by bandwidth. On one group of GPUs, a single prefill step stops everyone’s decode. DeepSeek deploys the vision encoder, prefill and decode separately: prefill on 8-GPU machines (EP2–8), decode on supernodes of 64–128 GPUs (EP64–128), and the smallest efficient unit is 64 + 64 GPUs.
  2. Block KV is paged in blocks of 128 tokens and stored in a dedicated 3FS cluster (10 + 2 erasure code, about 100 PiB, TTL 3–7 days). SWA state is one fixed-size slot per sequence, only about 1.4 MB is archived, and it stays in local RAM.
  3. A hit goes at most to L − 134, rounded to a multiple of 128. If SWA is missing, step back one block and recompute only 128 tokens with bounded replay, so the cost is constant. The open-source release has the engine roles, the cache layout and bounded replay. It does not have the code that joins the KV cache system to the disaggregated deployment.

Common misconception: “A prefix hit only saves time, and the result is exactly the same as computing from scratch.”

Block KV is read back as is, so that part is identical. But when the SWA state is missing, bounded replay produces an approximate SWA: the window is cut inside the replay segment and cannot see earlier tokens (Q&A document). When bounded replay for decoder layers is on, as in the README’s default usage, every prefill is truncated, so the result differs from the full computation from the start. What examples/yoco verifies is that the two truncation modes, mask and compact, agree with each other, not that they agree with no truncation. If you want reproducible output, read the batch-invariant page.

Go deeper: from environment variables to functions, matching the code one by one

Engine roles and the vote in the mixed engine

The three engine roles are defined in engine_type.py: NORMAL and COMPLETION turn on zero-overhead scheduling by default, and PROMPT does not (for asynchronous scheduling see the page on DSpark and zero-overhead scheduling). The scheduler dispatches by role: PROMPT calls only _schedule_prefill, and COMPLETION calls only _schedule_decode (scheduler.hpp). In the NORMAL vote, “wants to do prefill” means the KV usage in GPU memory is at most 90% and some request is waiting (watermark, want). The ALL point reduces with MIN, so prefill runs only if everyone wants it; at the ANY point, prefill runs if any rank wants it. After that there is a second round of voting to confirm that some rank really scheduled prefill work. A rank with nothing to do joins in by running an empty prefill step, so all ranks keep the same step shape. The intervals are controlled by DEEPINFER_PREFILL_ATTEMPT_INTERVAL (default 70) and DEEPINFER_PREFILL_ANY_ATTEMPT_INTERVAL (default 100) (environ.py). A non-NORMAL engine calls init_pd_split when it initializes (llm_engine.py). Also, only non-PROMPT engines use CUDA Graph (model_runner.py): decode steps are small and frequent, so recording a graph saves the launch overhead, which is exactly what Chapter 15 “Kernel launch overhead and kernel fusion” covers.

Block table and state slots

Both allocators are a BlockManager: free blocks are chained into a linked list, blocks carry a reference count, and block 0 is not used (block_manager.hpp). The block allocator manages blocks by num_gpu_blocks, and the slot allocator manages slots by num_state_seqs (llm_engine.py). When the number of blocks requested is not less than the total number of blocks, it returns NEVER and raises an error at once. When there are temporarily not enough, it returns LATER and the request stays in the queue (block_manager.hpp). try_allocate_seq allocates only if both blocks and a slot are available (same file). The number of slots is int(max_num_seqs × 1.2) + 1, and the ratio is controlled by DEEPINFER_NUM_STATE_SLOTS_RATIO (cache_engine.py, environ.py). At startup there is one more check: the number of tokens the blocks can hold, times 0.8, must be at least the model’s maximum length (llm_engine.py).

Layout and archiving of the SWA state

Which layers’ SWA is not archived depends only on the model config: layers whose index is not less than n_prefill_layer are YoCo consumer layers (cache_engine.py). n_prefill_layer is the index of the first layer whose compression ratio is 1 (config.py). When DEEPINFER_PREFILL_STORE_EXTRA_STATE is on, the ring buffer used for archiving stores DEEPINFER_PREFILL_STORE_EXTRA_SIZE (default 128) more tokens, and KEEP_TOKENS is added when truncation is on. The comment gives this reason: “prefill may not trigger a write to disk, so storing an extra stretch is what guarantees a hit across several turns” (cache_engine.py). What reads out the archive data is select_state_slice_to_store: when archiving, it requires the position to be a multiple of 128. With TO_CE=True, it builds the complete state to send to the decode engine, including the non-archived zone (cache_engine.py). The opposite direction, load_state_from_store_to_prefill_cache, writes archive data back to the prefill state slot (same file).

When the SWA state is stored

The rule given by the Q&A document (Q&A document): Upstream report when prefill ends, first leave one token at the end of the sequence, then round down to a multiple of 128. If there is not a whole segment, nothing is stored this time. With chunked prefill, only the last chunk stores. During decode, a separate copy zone is opened in GPU memory, and each time a 128 boundary is crossed, the current window is copied there. When the request ends, the archive is taken from the most recent complete copy, and the attach point is rounded down to 128. A copy position can pass the boundary by at most 5 tokens, and the 6 extra positions of the slot over the window cover exactly that. On the code side, the copy is done by do_copy_state, which copies the state on the GPU into the copy_state buffer, while should_copy_state, which decides whether to copy, always returns False in the open-source release (llm_engine.py). Switches and checks for bounded replay

DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE takes off, mask or compact. DEEPINFER_YOCO_PREFILL_KEEP_TOKENS defaults to 0 and must be set explicitly when truncation is on (environ.py). There are two checks: the Python side at model load (model_runner.py) and the C++ side when preparing the input (prepare_tensor_input_v4.cpp). The rollback length DEEPINFER_MAX_BACKTRACKING_TOKENS is raised to at least “number of drafts + 1”; the default number of drafts is 5, so it is at least 6 (environ.py). In compact mode, each chunk keeps the intersection of [max(0, total length − KEEP_TOKENS), total length) with the chunk. If the whole chunk is before the kept zone, one last token is still left as a placeholder (same file). Truncation has two modes: mask keeps all queries and only narrows the visible range; compact drops the queries of the truncated zone at the first consumer layer, which really saves compute (environ.py). In the model forward, the metadata is switched to the compact view at the first consumer layer (deepseek.py). The visible range of both modes is the same formula (yoco.py). When truncation is on, per-token probabilities of the prompt (prompt logprobs) are forced off: in compact mode the truncated rows were never computed, and in mask mode the probabilities of rows before the rectangle have no meaning (llm_engine.py). The scheduler’s cost model also counts the consumer-layer rows separately, so it knows how much truncation saves (flops_estimator.hpp). examples/yoco has two levels of verification: L1 takes a few seconds on one GPU and compares only metadata; L2 needs 8 GPUs and a compatible checkpoint, and compares logprob and top-K one by one. The default parameters are --keep-tokens 140 --window 128 (examples/yoco/README.md).

How balanced CP cuts the sequence

The README writes it as “Attention DP / balanced CP” (README), and turning on CP in a decode engine raises an error at once (llm_engine.py). A sequence is cut into 2 × cp segments, and GPU r takes segment r and the (r + 1)-th segment from the end, one front and one back paired together (prepare_cp_mirror.py; the padding computation under truncation uses the same pairing, see prepare_tensor_input_v4.cpp). Code fact Why pair them this way? In causal attention, the later a token is, the more keys it must look at. If 4 GPUs cut the sequence straight through, the workload is about 1 : 3 : 5 : 7, and the busiest GPU has 1.75 times the average. With one front and one back paired together, all four GPUs have the same amount. Teaching estimate At scheduling time, each sequence length is aligned to cp × 2 (scheduler.hpp), and the length of each rank is the sum over sequences of ⌈length ÷ 2cp⌉, times 2 (prepare_tensor_input_base.cpp). The kernel on the GPU computes the block number of segment half as blk = rank + half × (2cp − 1 − 2 × rank): when half = 0 it is block rank, and when half = 1 it is block 2cp − 1 − rank (prepare_cp_mirror.py). The workload reasoning: a length N is cut into 2cp segments, and a token in segment i looks at about (i + 0.5) × N ÷ 2cp keys on average, so block r and block 2cp − 1 − r always add up to 2cp units, independent of r. The conditions behind the numbers on this page

The two benchmark charts in the README: prefill uses 4 SM100 GPUs and decode uses 64, each inside one scale-up domain (README). The title of the prefill chart says EP4DP4, 384 + 32 experts, context 131,072, and decoder bounded replay of 140 tokens. The vertical axis is the missed tokens processed per GPU per second.
