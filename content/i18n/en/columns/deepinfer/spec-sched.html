From one person to a whole table

In Chapters 18 and 19, Strata serves one person. Its draft layer guesses at most 3 tokens. Whether to swap in drafts "copied" from the context is decided by a measured timing table.

On a DeepInfer decode GPU, dozens of requests share the same step. DeepSeek says the production operating point is about 60 per GPU.Upstream report That raises two new questions. Among several hundred draft tokens in one step, which ones are worth verifying? And what is the GPU doing during the few milliseconds the CPU spends queuing the next step?

In one line: DeepInfer's draft module guesses 5 tokens in one forward pass and gives each one a confidence score. With variable-length verification on, the scheduler hands verification slots to the most confident drafts first. It searches a measured timing curve for the total that gives the most expected tokens per millisecond. The zero-overhead batch scheduler lets the CPU prepare the next batch one step ahead, so the GPU no longer stops to wait. When both are on, the CPU only fixes the total. A kernel on the GPU works out the share for each request on the spot.

4.1 Where drafts come from: 5 guesses in one pass, plus 5 confidence scores

First, a quick review of the speculative decoding from Chapter 18, "Speculative execution and branch prediction". A cheap draft guesses a few tokens first. They are called draft tokens. The big model lines up "the last settled token + these drafts" in one row and computes them in one forward pass. Then it verifies them one by one and keeps only the unbroken prefix.

DeepInfer's draft module lives in deepinfer/model_executor/models/mtp/dflash.py, in a class called DFlash. The README and DeepSeek's deployment Q&A call this speculative decoding setup DSpark. They call the way it schedules verification "confidence-scheduled verification".Upstream report (README.md) In the code, the name DSpark appears only in config fields of the draft module, such as dspark_target_layer_ids, dspark_noise_token_id and dspark_markov_rank.Code fact (dflash.py) Neither the code nor the docs explain where these two names come from, and this page does not guess.

From the code, this draft module has three features.Code fact

  • It borrows features from the main model. During the main model's forward pass, the draft module takes the hidden states of a few layers, concatenates them, projects them once, and writes the result into its own KV cache. A comment says this step "runs inside the main model's forward pass". (dflash.py)
  • 5 positions in one pass. The draft input is a row of 5 positions. The first is the token that was just settled. The other 4 are all filled with one fixed "noise token". The row goes through the draft layers once, and the hidden states of all 5 positions come out together. (dflash.py) After that, tokens come out position by position. Each position can add a small correction term that looks only at the previous token. Position 1 looks at the token just settled. Each later position looks at the draft just drawn at the position before it. (dflash.py)
  • Each draft carries a confidence. The confidence head is one linear layer plus a sigmoid. It estimates, for every draft, "the probability that it will be accepted". The comment reads: "Predict the acceptance probability of each draft token." (dflash.py)

The environment variable DEEPINFER_USE_NEXTN_DECODE sets how many tokens to guess. The default is 5, and 0 turns speculative decoding off.Code fact (environ.py) The Q&A says that in production the draft model also produces 5 at a time. The internal draft model is newer, but the performance difference is small.Upstream report (inference_deployment_qa.md)

Verification uses the classic speculative decoding rule. A draft is accepted with probability min(1, p ÷ q), where p is the main model's probability and q is the draft's probability. At the first rejected position, one token is drawn again from the "residual distribution", the difference between the two. The random numbers come from the request's seed and the position.Code fact (sampler.py, fused_sample.py) For how the seed makes results reproducible, see the "Determinism" page of this column. Figure D4-1 strings one decode step together.

Compared with Strata: Strata's drafts come from one MTP layer built into the model, and it guesses at most 3. By default a draft is accepted only if the draft and the target sample exactly the same token. The classic min(1, p ÷ q) rule needs its own switch (Chapter 18, section 18.5). DeepInfer uses the classic rule by default, guesses 5 at a time, and outputs one more column: confidence. The extra column is not for verification itself. It is for scheduling. With dozens of requests in one step, the scheduler needs a basis for deciding whom to verify first.

4.2 How many to verify: give slots to the most confident drafts first

The simplest way is to verify all 5 drafts of every request. The Q&A says this wastes verification compute on drafts with little hope, because acceptance probabilities differ a lot across requests and positions.Upstream report (inference_deployment_qa.md)

Chapter 19, "Expected value and geometric series", already explained the math. Draft i is useful only if the first i drafts are all accepted. That probability is the product of the conditional acceptance rates of those positions. One round commits 1 + c₁ + c₂ + … tokens in expectation, and the quantity to compare is "expected tokens ÷ time per round". DeepInfer's code treats the output of the confidence head as the conditional acceptance rate of each position, and takes the cumulative product before scheduling. A source comment says: "the confidence rate returned by modeling is independent per token; take a cumulative product before use."Code fact (scheduler.hpp)

The difference is that one step holds many requests, and they share one forward pass. The time of the step depends on how many tokens the whole batch verifies together. So DeepInfer no longer picks request by request. It solves the whole batch as one budget problem. With DEEPINFER_ENABLE_MTP_VARLEN=1 on, MTPVarlen::schedule does this:Code fact (mtp_varlen.hpp)

  1. Sort all drafts of all requests by their cumulative-product probability, from high to low, into one list.
  2. Start from "each request verifies only its 1 main-model token". Walk down the list and add one slot at a time. Each added slot raises the expected token count by its probability.
  3. Look up the time for every total q. On the timing curve measured at startup, take the time of the CUDA Graph whose size is at least q. Then add an online-corrected slope term and the sampling time.
  4. Pick the q with the largest "expected tokens ÷ time". Give the first q − N slots to the matching requests, where N is the number of requests. Two lists are in fact ranked here: the total uses the confidence from an even earlier round, and the slot assignment uses the latest round. This is so with or without ZOS. (mtp_varlen.hpp)

The cumulative probability shrinks as you go further, so the slots a request gets are always its first few consecutive drafts. This matches the rule "only an unbroken prefix is accepted". The Q&A puts it this way: sort by expected acceptance rate, and choose the prefix subset that maximizes the effective throughput (tokens produced per second).Upstream report

The timing curve is measured. During engine warm-up, every recorded CUDA Graph is replayed 5 times. The fastest and the slowest run are dropped and the rest are averaged. Then the result is averaged across the GPUs of one expert parallelism (EP) group.Code fact (model_runner.py) At run time, the measured forward and sampling time of every decode step is fed back to the scheduler, which corrects this curve with a sliding-window median. (llm_engine.py, mtp_varlen.hpp)

This switch is off by default.Code fact (environ.py) The engine measures the curve only when the switch is on and CUDA Graphs are in use. When the curve is empty, each request verifies a fixed 1 + (the drafts it holds, usually 5) tokens. (base.py, mtp_varlen.hpp) The evaluation script in the repository sets it to 1. (run_eval.py) The README also states that deterministic sampling requires turning it off. The reason is on the "Determinism" page.

Greedy algorithms and marginal gain

Intuition: you have 10 movie tickets to give to friends, and each friend is more or less likely to show up. To get the most people in the seats, give the tickets to the likeliest people first, one at a time. At every step you take the share with the best immediate gain. This is a greedy algorithm.

Definition: a greedy algorithm makes the locally best choice at every step and never goes back. It is not always right. But when the total gain is the sum of the gains of the parts and the parts do not affect each other, it gives the optimal answer. Any other split can be improved by moving one ticket from a person with a lower gain to a person with a higher gain. This proof method is called an "exchange argument".

An example: 4 drafts would be useful with probabilities 0.9, 0.7, 0.4 and 0.1, and you can verify only 2. Greedy picks 0.9 and 0.7, which adds 1.6 expected tokens. Any other pair gives less.

How this relates to this page: when the number of slots is fixed, DeepInfer hands out slots by probability from high to low, which is exactly this greedy rule. The number of slots is not fixed, so the scheduler tries every total, compares "expected tokens ÷ time", and takes the largest. The extra expected tokens from each added slot is its marginal gain.

Further reading: OI Wiki: Greedy algorithms · Wikipedia: Greedy algorithm

Step 3 hides a staircase. The time is looked up by "the graph of size at least q", and the graph sizes are 1, 2, 4, 8, 16, 24 … one every 8. Code fact (mtp_varlen.hpp, cuda_graph_runner.py) So inside one graph, verifying a few more or a few fewer tokens gives exactly the same estimated time. Cutting drafts saves time only when the total drops across a graph boundary. The expected token count never decreases as q grows, so the chosen total always lands on some graph size, or simply verifies all the drafts.Teaching estimate

The simulator below lays this budget problem out. The numbers in the cells are the cumulative-product probabilities. The time also follows the graph-size staircase, but each step of the staircase has the same height, so a straight line stands in for the real curve. The total and the slot assignment use only one set of confidence scores. These two points are teaching simplifications.

The formula is throughput = (N + Σ cumulative probability of verified drafts) ÷ (10 + t₁ × graph size), where the graph size is the smallest CUDA Graph that holds these tokens. In Figure D4-2, the fixed method gives 10.71 ÷ 14.80 ≈ 0.724, and confidence scheduling gives 9.84 ÷ 13.20 ≈ 0.745.Teaching estimate

Compared with Strata: Strata's MTP window length is fixed by the startup flag --spec. Only if you set --spec-min-p does it stop adding drafts to the window once a draft's confidence falls below the threshold. The DraftPolicy that compares "expected committed tokens per millisecond" using measured times manages prompt-lookup drafts (Chapter 19, section 19.5). All of these decide for one window of one user. DeepInfer has to decide, for a whole batch of dozens of requests, how many to verify in total and who gets more or fewer. The threshold is not fixed either. It is computed on the spot from "is one more verification worth it". The unit of comparison changes from "one window" to "one replay of one CUDA Graph".

4.3 The upstream numbers: about 30% fewer verified, a few points more throughput

The Q&A gives a table that compares fixed verification of 5 with confidence-based variable-length verification. The setup is EP64/DP64: 64 GPUs do expert parallelism, and attention is split into 64 shares by data parallelism (DP). The throughput in the table is an estimate computed from benchmark data for this configuration, not a measurement from live traffic.Upstream report (inference_deployment_qa.md) For why it spreads across all 64 GPUs, see the "Wide expert parallelism" page.

The Q&A sums it up this way: about 30% fewer drafts are verified (5.00 drops to 3.2–4.4), the mean accepted length barely changes (3.29 versus 3.20), and at the production operating point of about 60 requests per GPU, throughput rises by 4%–7%.Upstream report The Q&A does not say whether the "accepted length" includes the main model's own 1 token, and this page does not explain it on its behalf.

Why is there no gain at low concurrency? A reasonable explanation: when the batch is small, decode is stuck on moving weights, so verifying a few more tokens adds almost no time. Cutting drafts saves little and loses a bit of accepted length (from 3.32 to 3.24 at 16 requests). When the batch is large, the forward pass becomes compute-bound. Every extra verified token really costs time, so cutting low-probability drafts pays off.Teaching estimate For how to tell "stuck on moving data" from "stuck on compute", see Chapter 5, "Compute and roofline". In the simulator above, raise N and t₁ together to see the same direction.

The simulator differs from a real system in one more way. In the simulator, the confidence is the true probability, so assigning slots by it never loses. In the real system, the 16-per-GPU row of the table is −1.5%. One possible reason is that the confidence is wrong, and drafts that would have been accepted get cut. Several others also make sense: the timing model has errors, the total is set from an even earlier round of confidence, and the total is rounded up to a graph size.Teaching estimate Besides, the table itself is an estimate computed from benchmark data. (inference_deployment_qa.md)

4.4 Keep the GPU running: the zero-overhead batch scheduler

Look at one decode step from another angle. The Q&A splits step N into four parts: schedule(N) → forward(N) → sample(N) → post-process(N). Scheduling and post-processing are pure CPU logic. Before post-processing, the CPU must synchronize with the GPU once to get the result of sample(N). So between post-process(N) and schedule(N+1), the GPU sits idle.Upstream report (inference_deployment_qa.md)

Asynchronous scheduling exists to remove this idle time. DeepInfer calls its implementation the zero-overhead batch scheduler (ZOS in the code). The Q&A says it follows SGLang and NanoFlow. While the GPU runs forward(N) → sample(N), the CPU at the same time does schedule(N+1) → launch forward(N+1) → post-process(N−1) → launch sample(N+1).Upstream report

In the code, this order is written in a comment of Worker.execute_model_step. Every step does the same four things:Code fact (worker.py)

  1. Launch this step's forward pass.
  2. Post-process the previous step: first wait for the previous step's "sampling done" event, then handle the output.
  3. Launch this step's sampling.
  4. Post-process this step: a prefill step, or any step with ZOS off, does it right away. A decode step under ZOS leaves it to the next step, to overlap with the next step's forward pass.

The "previous step" lives in one variable, prev_step_state, so the CPU can be at most one step ahead of the GPU. The wait in item 2 comes after this step's forward pass is already launched, so while the CPU waits, the GPU has work.Code fact (worker.py)

The README says asynchronous scheduling is on by default.Upstream report (README.md) Looking at environ.py alone, the default of DEEPINFER_ZERO_OVERHEAD_SCHEDULING is off. But when the engine is created, EngineArgs fills in a default by engine type: 1 for the NORMAL engine (which does both prefill and decode) and the COMPLETION engine (decode only), and 0 for the PROMPT engine (prefill only).Code fact (environ.py, arg_utils.py, engine_type.py) So every engine that decodes does have it on by default, which agrees with the README.

An accidental synchronization can easily ruin the overlap. If the launch code reads one number on the GPU anywhere, the CPU has to stop and wait, and as soon as the GPU finishes its work it is idle again. DeepInfer wraps both the forward launch and the sampling launch in forbid_cuda_sync(). The function comment says in capital letters that no CUDA synchronization is allowed here, and a dedicated unit test covers it.Code fact (model_runner.py, test_cuda_sync_guards.py)

Drag the timeline below to see when the gap disappears and when it comes back.

In steady state, the synchronous loop takes CPU + GPU per step, and the asynchronous loop takes only max(CPU, GPU). With the default numbers that is (4 + 13) ÷ 13 ≈ 1.31 times.Teaching estimate The GPU's 13 ms is read from the README decode chart: at 64 requests per GPU, each user gets about 246 token/s. Converted with the caption's τ = 3.25, that is about 76 steps per second, so one step takes about 13 ms (Section 4.6 goes into this chart). Upstream does not publish how long the CPU takes per step, so 4 ms is purely an assumption.Teaching estimate

Asynchrony is not free. When the CPU schedules step N+1, it does not yet know how many tokens each request accepted in step N. So it first reserves 1 + 5 positions for each in-flight request, the worst case, and corrects them to the real values when the results come back. The upper limit of the position table also keeps nextn + 1 extra cells for this reason.Code fact (reserve: scheduler.hpp L726; advance optimistically first: L927; then fill back by the real accepted count: L999; config.py) If a request is preempted while in flight, the whole output of that step is discarded. (scheduler.hpp)

If you studied CS: This is a two-stage software pipeline. The CPU is stage one, the GPU is stage two, and each stage handles one step at a time. As with the instruction pipeline in a computer organization course, the slowest stage sets the beat of the pipeline. So once the CPU is slower than the GPU, the gap comes back. For the basics of pipelines, see Chapter 16, "Pipelining: several stages working at once".

Compared with Strata: Strata's server by default has one lock and one queue, and serves one sequence at a time. With "parallel" on, usually at most 8 batch slots decode together (Chapter 25, section 25.1). It has overlap too: the commit of a verification window can return without waiting for the graph to finish, so the next round's draft generation runs at the same time (Chapter 14, "Synchronous and asynchronous"). On a DeepInfer decode GPU, one step holds dozens of requests. The CPU has to schedule and post-process the whole batch every step, and this work grows with the batch. If it is not hidden, it eats the GPU's time directly.

4.5 Two things collide: the CPU does not yet know how many were accepted last step

Put 4.2 and 4.4 together and you hit a hard problem. Variable-length verification must use the confidence just produced by step N to decide how many each request verifies in step N+1. But under asynchronous scheduling, when the CPU schedules step N+1, step N is still running on the GPU, and the confidence has not come out yet.

The Q&A's solution: when the CPU schedules, it fixes only the total budget. How many each request gets is recomputed by a TileLang kernel on the GPU (cumulative product, global ranking to take the top k, and remapping row indices on the way). The result is written back to a pinned buffer.Upstream report (inference_deployment_qa.md) The code matches this description point by point:Code fact (worker.py)

  • The CPU first matches this batch's requests to the previous batch and builds a remap table, remap: for the i-th request of this batch, which request of the previous batch it was. New arrivals are marked −1. (zos.cpp)
  • On the GPU, compute_seqlens_q_by_confidence_rates reads the confidence left in GPU memory (HBM) by the previous step. It picks rows by remap, takes the cumulative product, and ranks across the whole batch. Each of the top total_q − N entries adds one slot to its request. A new request gets confidence 0 and ranks last. (schedule_mtp_varlen.py)
  • The KV length of every request is also corrected on the GPU, by the number of tokens the previous step actually accepted (compute_seqlens_k_zos in worker.py). The input tokens of this step are taken straight from the previous step's sampling result in GPU memory. (prepare_tensor_input_zos.py)
  • The computed length of each request is copied back to pinned memory, and an event is recorded. After the CPU has launched the forward pass and finished the previous step's post-processing, it waits for this event, right before launching sampling. (worker.py)

Why must the total be fixed on the CPU? The code gives at least one direct reason: the CPU needs the total token count to choose which CUDA Graph to replay, and this happens before launch.Code fact (worker.py, cuda_graph_runner.py) The size of each graph is fixed when it is recorded. Under ZOS, the input buffer of the graph sits in GPU memory, so a kernel on the GPU can rewrite it without going through the CPU. (cuda_graph_runner.py, model_runner.py)

Section 4.2 already said that the total and the slot assignment use two different data sets: the total uses the confidence from an even earlier round, and the assignment uses the latest round, with ZOS or without. The source comment says that the total budget "always uses the accept_rate of round N−2", and the assignment uses round N−1. In the comment, "round N" means the step being scheduled.Code fact (mtp_varlen.hpp) In this section's notation: when scheduling step N+1, the total uses the confidence produced by step N−1, and the assignment uses that of step N. With ZOS off, step N has already been post-processed, so the assignment can be done on the CPU. With ZOS on, step N's confidence is still on the GPU, so the assignment moves to the GPU.

If you studied CS: This is a data hazard in a pipeline: a later instruction needs the result of an earlier one, but the earlier one has not finished. A CPU has two classic answers. One is to stop and wait (a pipeline stall). The other is to "forward" the result from the execution unit straight to the next instruction, without a trip through the registers. DeepInfer chooses forwarding: the accepted counts and confidence of step N do not go back to the CPU. They are handed to step N+1 directly in GPU memory. Further reading: Wikipedia: Hazard (computer architecture) · Wikipedia: Operand forwarding

Compared with Strata: Chapter 15, section 15.5, explained that a CUDA Graph records its parameters as fixed, so Strata puts the positions that change every step into a block of GPU memory at a fixed address, and the host copies new values in once per step. Under ZOS, DeepInfer goes one step further: the lengths and input tokens that change every step do not even pass through the host. The GPU computes them from the previous step's results. The principle is the same: the graph remembers addresses, and the contents are rewritten every step.

4.6 Read benchmark numbers with care: the full-acceptance basis

One last trap that is easy to step in when reading numbers. The decode throughput reported by the repository's own benchmark.py uses a "full-acceptance basis": however many drafts were actually accepted, every request counts 1 + nextn tokens per step. The formula is avg_SPS × number of requests × (1 + nextn) ÷ number of CP ranks, where avg_SPS is steps per second. With the defaults, 64 requests and nextn = 5, one step counts 384 tokens.Upstream report (examples/README.md) The code has exactly the same formula.Code fact (benchmark.py)

There is a reason for counting this way. With variable-length verification off, every step verifies a fixed 1 + nextn tokens, so the time of a step does not depend on the acceptance rate. The measured step rate can then be converted to any acceptance rate. The plotting script does exactly this. It uses τ = 1 + nextn × a to scale both axes by τ, where a is the fraction of drafts accepted. The script also asserts that variable-length verification was off in the data, because otherwise the step rate already contains the acceptance rate and cannot be multiplied again.Code fact (plot_pareto.py)

The caption of the README decode chart says: EP64DP64, 384+64 experts, context 131,072, nextn = 3 fixed, per-token acceptance rate 75%, τ = 3.25. The measurement used 64 SM100 GPUs inside one supernode.Upstream report (README.md, decode_pareto.png) Reading the chart: at 64 requests per GPU, about 15,700 token/s per GPU and about 246 token/s per user.Upstream report (approximate, read from the chart) Remember that the 75% here is an input given when drawing the chart, not an acceptance rate measured in this run. It is also not the per-position conditional acceptance rate of Section 4.2. The a in the plotting script is "accepted drafts as a fraction of all drafts", and τ = 1 + 3 × 0.75.Code fact (plot_pareto.py) If the conditional acceptance rate at every position were 75%, the cumulative product would give an expectation of only 1 + 0.75 + 0.56 + 0.42 ≈ 2.73 per step.Teaching estimate

Converting: with nextn = 3, the full-acceptance basis counts 4 ÷ 3.25 − 1 ≈ 23% more than the a = 75% basis. With nextn = 5, it counts 6 ÷ 4.75 − 1 ≈ 26% more.Teaching estimate In the benchmark estimate of Section 4.3, fixed verification of 5 gives a mean accepted length of about 3.3. Whether or not it includes the main model's 1 token, it is far below the full-acceptance 6 (or 5, counting drafts only). So a number on the full-acceptance basis can only be read as an upper bound.

Remember these three

  1. DeepInfer's draft module guesses 5 tokens in one forward pass and gives each one a confidence. With DEEPINFER_ENABLE_MTP_VARLEN=1 on, the scheduler hands out verification slots by cumulative-product confidence from high to low, and picks the total with the most expected tokens per millisecond on the measured timing curve. Upstream estimate: throughput up 4%–7% at the production operating point, slightly worse at low concurrency.
  2. The zero-overhead batch scheduler keeps the CPU one step ahead of the GPU: while the GPU runs step N, the CPU is already preparing step N+1. The steady-state cycle changes from CPU + GPU to max(CPU, GPU), provided the CPU's work per step does not exceed one GPU step.
  3. When the two are combined, the CPU cannot get the latest confidence. So it fixes only the total (it needs the total to choose a CUDA Graph), and a kernel on the GPU splits it across requests with the latest confidence. When you read decode throughput, first check whether it is on the full-acceptance basis.

Common misconception: "Zero-overhead scheduling means CPU scheduling takes no time."

The CPU's work is not reduced at all. It is only overlapped with the GPU's work. When the CPU is slower than the GPU in every step, the cycle of the asynchronous loop is the CPU's time and the GPU still waits. Drag the CPU past the GPU in the timeline above to see it.Teaching estimate DeepInfer's scheduler itself is in C++ (csrc/engine/scheduler.hpp), and the launch code is wrapped in a guard that forbids synchronization.Code fact

Go deeper: the full call chain of one decode step, the details of the budget algorithm, and related switches

File map

  • deepinfer/engine/llm_engine.py: LLMEngine.step(), the entry point of one step (L860–L959).
  • csrc/engine/scheduler.hpp: the C++ scheduler. Decode scheduling is at L622–L660 and ends by calling _mtp_varlen.schedule. The bookkeeping of drafts and confidence is in process_MTPInfo (L1196–L1262).
  • csrc/engine/mtp_varlen.hpp: the budget algorithm of variable-length verification and the two time estimators.
  • deepinfer/worker/worker.py: the four-step ZOS loop and the GPU-side correction.
  • csrc/engine/zos.cpp, deepinfer/model_executor/input_metadata/prepare_tensor_input_zos.py: input preparation under ZOS.
  • deepinfer/model_executor/layers/tilelang_ops/cuda/schedule_mtp_varlen.py: the GPU kernel that assigns slots. The file of the same name one level up holds a PyTorch reference implementation and tests.
  • deepinfer/model_executor/models/mtp/dflash.py: the draft module and the confidence head.
  • csrc/graph_timer/, deepinfer/timer.py: timing inside a CUDA Graph.

The order of one decode step with ZOS on

  1. scheduler.schedule(): C++ picks this batch of requests and sorts them by length. MTPVarlen::schedule gives each request's seqlen_q and the total. Each scheduled request gets schedule_cnt + 1, and in-flight positions are reserved as 1 + nextn (scheduler.hpp L667–L736).
  2. Worker._correct_seqlens_qk: match against the previous batch and build the remap. Copy it to GPU memory. With variable length on, run the slot-assignment kernel. Correct the KV lengths by the previous step's accepted counts. With variable length on, copy the new seqlen_q back to pinned memory and record an event (worker.py L191–L245). A comment says: "H2D, correction and D2H are ordered on the current stream; only variable length rewrites this pinned source."
  3. execute_main_model: pick the graph and launch the forward pass, wrapped in forbid_cuda_sync() and the timing event device_forward.
  4. _post_process_step(prev): wait for the previous step's sample_end_evt, refresh the in-graph timing, and handle the output. In the driver process it also hands the previous step's measured forward and sampling time to scheduler.update_mtp_runtime (llm_engine.py L984–L1015).
  5. Wait for the D2H event. update_metadata_for_sampling_zos changes the CPU-side seqlen_q to the value computed on the GPU. seqlen_k is not copied back from the GPU. It is recomputed on the CPU as seqlen_q + the number of cached tokens (zos.cpp L279–L305).
  6. execute_sample: verify the previous step's drafts, then run the draft module to produce the next step's drafts and confidence. It is wrapped in the same guard that forbids synchronization.
  7. The pre_sampler_sync callback: release resources whose release was deferred from the last round, handle KV spill to disk, and so on. Finally, store this step's state in prev_step_state for the next step to post-process.

Details of the budget algorithm

  • Each request has two acceptance rates: accept_rates (the latest round, already multiplied) and prev_accept_rates (the round before). Two counters, schedule_cnt and process_cnt, tell whether the "latest round" is N−1 or N−2 (sequence.hpp L118–L131).
  • When there is no acceptance rate yet, a request with drafts is filled with 1.0 and a request without drafts with 0.0.
  • Sorting is by acceptance rate descending, and on ties the request with the smaller index comes first. The GPU kernel ranks by counting "how many elements are larger than me", and on ties the smaller flat index comes first. This kernel counts in parallel. It does not really run a sort.
  • Candidate totals start from "verify only the main-model tokens". The time of each candidate is: the baseline time of the graph on the curve that is not smaller than it + slope × graph size + sampling time. The comparison uses strictly greater, so when throughput is equal the smaller total wins. Inside one graph the estimated time is the same, so the chosen total is always a graph size, or all the drafts.
  • CUDA Graph sizes are counted in tokens: 1, 2, 4, then one every DEEPINFER_CUDAGRAPH_BATCH_SIZE_INTERVAL (default 8), up to max_num_seqs × (1 + nextn) (cuda_graph_runner.py L41–L51, model_runner.py L72–L79).

Online correction of the timing model

  • Startup curve: each graph is warmed up once and timed 5 times. The highest and lowest run are dropped and the rest averaged, then averaged again inside the expert-parallel group. The result is cached in a file by model and parallel configuration. The validity period is set by DEEPINFER_DECODE_PERF_CACHE_TTL_SEC, 3600 seconds by default.
  • Forward slope: a comment says the startup curve does not account for context length, so a slope is fitted from (measured forward − baseline) ÷ graph size. It keeps the last 5000 steps, and each graph size needs at least 10 samples to count. It takes the median per graph size first, then the median of those medians. A slope below 0 is treated as 0 (mtp_varlen.hpp L44–L131).
  • Sampling time: there is no startup curve. It is grouped by number of requests, takes the median of the last 9 steps, and falls back to the global median when there are fewer than 5 samples.

The confidence head

The formula is sigmoid(concat[hidden state, correction embedding] · w ÷ temperature) (tilelang_ops/dflash.py L10–L46). The temperature comes from DEEPINFER_DFLASH_CONFIDENCE_HEAD_TEMPERATURE, 1.0 by default. You can also give nextn values, one per position, separated by commas (environ.py L134–L143). A comment says the Hugging Face format of DFlash always carries a confidence head. The number of layers in the draft module is set by num_nextn_predict_layers in the model config. This page did not verify that value.

Timing inside a CUDA Graph: graph_timer

The time feedback for variable-length verification uses CUDA events wrapped around the whole forward pass and the whole sampling. There is also a graph_timer that measures a few segments inside the graph (for example the attention or the MLP of one layer), for statistics. It inserts "record event" nodes while the graph is recorded, then finds those nodes after recording (graph_timer_cuda.cpp L48–L85). Before every replay, it swaps these nodes for another set of events, and the two sets are used in turn (timer.py L78–L217). Under ZOS, when the previous step's timing is read, the next step's graph is already running. Because the two sets alternate, what is read is always the set that has finished, and the running set is not disturbed. This is the double buffering of Chapter 14, section 14.4.
