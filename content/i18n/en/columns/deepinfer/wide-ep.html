From one computer to one supernode

Chapter 10 did a calculation. When Strata generates one token on one computer, it reads about 664 MB of expert data. VRAM cannot hold all the experts. So Strata caches only the popular ones and leaves the rest to the CPU. That is a “one person, one machine” design.

DeepSeek’s online service faces thousands of people who chat at the same time. Its decode does not run on one GPU. It runs on a supernode of 64 to 128 GPUs. These GPUs have a fast interconnect, so you can treat them as one unit. Upstream report (Q&A line 11) This page answers three questions. How do hundreds of experts spread over dozens of GPUs? Why does decode get cheaper as you add GPUs? What happens when popular experts crowd onto one GPU?

In one line: In DeepInfer decode, attention uses data parallelism (DP): each GPU handles its own batch of requests. The routed experts use expert parallelism (EP): they spread over 64–128 GPUs, and each GPU holds only a few per layer. With more GPUs, each GPU reads fewer expert weights per step, and one read serves more tokens. The cost is two all-to-all communications per layer. Also, the busiest GPU sets the speed of the whole group. So expert load balancing (EPLB) copies the popular experts and spreads them out.

2.1 Two cuts stacked together: attention splits by request, experts split by number

Chapter 21 described three ways to share work across GPUs: layer split, tensor parallelism and request parallelism. Strata chose layer split. DeepInfer uses only one of them, data parallelism, and only for attention. On top of it, DeepInfer adds one that Chapter 21 did not cover: expert parallelism. See Figure D2-1.

  • Attention uses data parallelism (DP). Each GPU holds a full copy of attention and handles different requests. Upstream says: as in DeepSeek-V3 / R1, the number of attention DP replicas equals the number of EP replicas (#DP = #EP). For now it uses no tensor parallelism (TP) and no context parallelism (CP). Upstream report (Q&A lines 33–53) The code has context parallelism, and the README lists it. Only the upstream deployment config does not use it.
  • MoE uses expert parallelism (EP). The routed experts of each layer are cut by number into EP parts, and each GPU holds only one part. Every GPU holds a full copy of the router and the shared experts. Code fact (moe.py lines 24–67, lines 77–110)

The number of experts must divide evenly by the number of GPUs. DeepInfer distinguishes three counts. The logical experts are the ones the model defines, and the router picks from them. The physical experts are the ones that have weights assigned = logical experts + redundant copies. The local experts on each GPU = physical experts ÷ EP. The code requires the physical expert count to divide evenly by EP, and raises an error otherwise. Code fact (moe.py lines 91–95) The redundant copies are the main topic of Section 2.4.

Every MoE layer exchanges tokens across GPUs. So in one group of GPUs, some GPUs cannot do prefill while others do decode. In an engine that does both prefill and decode, the scheduler makes the whole group vote at each checkpoint, so all agree on the type of this step. If any GPU in the group does prefill, the GPUs with no work must also run an empty prefill step. Code fact (scheduler.hpp lines 295–340: “within a DP group the type must be the same, unified by voting”)

In the upstream deployment, the two phases use very different widths. Prefill uses EP2–8: as small as possible, as long as the model fits in GPU memory (HBM). Decode uses EP64–128: as large as possible, as long as there are enough GPUs. Upstream calls this wide expert parallelism (Wide-EP). Upstream report (Q&A lines 45–53) For why the two phases deploy separately, see page 3, “E/P/D disaggregation and the 72-hour KV cache”. The next section explains why decode should be spread wide.

If you studied CS: This is the “bulk synchronous” pattern from parallel computing. Each worker computes a segment, everyone exchanges data once, and then all enter the next segment together. It is easy to write and easy to reason about. The cost is that every segment waits for the slowest worker.

Compared with Strata: With two GPUs, Strata splits the model by layers into a front part and a back part (Chapter 21). The GPUs pass data only once, at the boundary, because the GPUs in a home PC usually connect only over PCIe. DeepInfer has a fast interconnect inside a supernode. That is why it dares to make all GPUs exchange data in every layer. The cost of the interconnect decides how you cut the model.

2.2 More GPUs, better value: each GPU reads fewer experts per step

Recall the Roofline model in Chapter 5. In decode, every step reads all the weights it uses, and reading weights often takes longer than computing. If one read of the weights serves more tokens, the read is a better deal.

Now stand on one GPU and watch one decode step of one MoE layer. With a large enough batch, almost every expert on this GPU gets chosen by at least one token. So this GPU must read all of its experts. The number of experts on this GPU is the number of expert weight sets it reads. Teaching estimate

How many routed experts does each layer of DeepSeek-V4.1-Flash have? DeepInfer reads this number from the model’s config.json on Hugging Face. The repository has no such file and does not hard-code the number. Code fact (config.py lines 164–174) The comparison chart in the repository says “384+64 experts”, and the Q&A says that at EP64, after rounding, each GPU holds 7 experts. Upstream report (wide_ep_decode_pareto.png, Q&A line 103) These two agree: 384 ÷ 64 = 6, plus 1 redundant expert, makes exactly 7. This page uses 384. The repository does not tell us how many bytes one expert takes or how many experts each token picks. So this page gives no concrete numbers for them. It uses S and k.

This gives a simple formula: experts per GPU per layer = (384 + redundant) ÷ EP. The expert weights each GPU reads per step ≈ this number × S. Teaching estimate Rounded with “at least 1 redundant expert per GPU”, EP8 gives 49, EP64 gives 7, and EP128 gives 4. From EP8 to EP64, the expert weights each GPU reads per step drop to about 1/7.

The explorer below puts three things together: how many experts one GPU holds, how many tokens one read of an expert’s weights serves on average, and how many hidden vectors one GPU sends per step. Click EP8, EP64 and EP128. See which number changes and which barely moves. The number of tokens per GPU per step, T, defaults to 384. The example benchmark defaults to 64 requests per GPU, and each request counts as 1 + 5 tokens per step. Upstream report (examples/README line 45)

The saving is not only in the bytes read. With a fixed batch of T tokens per GPU, the whole group has EP × T tokens and EP × T × k expert selections in one step. With an even load, each GPU gets T × k of them. Spread over the experts on this GPU, each set of weights serves T × k ÷ (experts per GPU) tokens. Teaching estimate EP64 is 7 times EP8. This is exactly the “shared dinner table” idea of Chapter 5: for the same dish, the more people eat it, the better the deal.

Upstream’s measured chart supports this direction. Upstream report Conditions: DeepSeek-V4.1-Flash, context 131,072, draft length fixed at 3, scaled by a 75% acceptance rate per draft token (the chart says τ = 3.25). EP64DP64 uses 384+64 experts. EP8DP8 uses 384+32. The chart does not name the GPU model. The README states for its performance charts: SM100, with every group of GPUs inside one scale-up domain (README line 83). With 64 requests per DP rank, reading from the chart: EP64 reaches about 15,700 tokens per second per GPU and about 246 tokens per second per user. EP8 reaches about 12,700 and about 198. So throughput and per-user speed both improve. (Q&A lines 55–59)

One point matters when you read this chart. The repository’s benchmark script sets DEEPINFER_FORCE_LOAD_BALANCE=1 unconditionally. It replaces each token’s routing scores with random numbers, so the expert load is even by construction. Code fact (benchmark.py lines 158–168, input_metadata.py lines 48–50) So this is the upper limit under “perfectly balanced load”. Upstream says that online load balancing reaches about 80% of this offline limit. Upstream report (Q&A lines 125–127)

Compared with Strata: Strata serves only a few conversations at a time, and one token reads about 480 experts (Chapter 10). It also groups by expert, but one set of weights can be shared only among the few tokens of one verification window (Chapter 16). So its focus is to keep popular experts in VRAM and avoid the slow path (Chapter 12). DeepInfer does the opposite: one GPU handles only a few experts, and hundreds or thousands of tokens are gathered into one batch, so each read of the weights is fully used.

2.3 Two all-to-alls per layer: dispatch and combine

The experts sit on different GPUs, so tokens must go and find them. In every MoE layer, DeepInfer does four things: Code fact (mlp.py lines 565–616)

  1. Route. The router on this GPU picks experts for each token on this GPU. The router gets a map from “logical expert → physical copy”. It picks logical experts, and the map decides which copy receives the token. (lines 359–401) How it chooses among several copies is written inside a kernel library. This book has not verified it.
  2. Dispatch. The hidden vector of each token goes to the GPU that holds its chosen expert. DeepEP’s EPBuffer.dispatch does this step. As a side effect, it adds up “how many tokens each local expert received in this step”. This is the raw data for EPLB in Section 2.4. (lines 461–490)
  3. Expert compute. This GPU groups the tokens it received by expert and runs a grouped matrix multiplication (Chapter 16 covered “grouping by expert”). The routing weights are multiplied in at this step. (lines 406–459) Then this GPU uses the shared expert to process its own tokens.
  4. Combine. The expert outputs go back to the GPU where each token came from. They are added up, and then the shared expert’s output is added. (lines 493–511)

Dispatch and combine are both all-to-all communication: every GPU sends a different piece of data to every other GPU.

Collective communication: all-to-all

Intuition: an office has 4 people. Each holds a stack of letters addressed to the others. All-to-all means “everyone drops letters into everyone’s mailbox at the same time”. At the end, each person holds only the letters addressed to them.

Definition: a group of P processes. Each process prepares P pieces of data, and piece j goes to process j. It is one kind of collective communication. Other common operations are broadcast (one sends to all), all-reduce (everyone’s data is summed, and everyone gets the sum) and all-gather (everyone has one piece, and in the end everyone gets all pieces).

Example: 4 GPUs, 8 tokens per GPU, 2 experts per token, with experts spread evenly. Each GPU sends out 16 vectors, and about 12 of them (3/4) go to other GPUs. With 64 GPUs, the share that goes to other GPUs becomes 63/64, and the total count stays the same. So when the group gets wider, the traffic of each GPU barely grows. What grows is the number of GPUs involved and the risk of “waiting for the slowest GPU”.

Link to DeepInfer: each MoE layer has one dispatch and one combine, and each is one all-to-all. DeepInfer also uses all-reduce and all-gather when it counts the load (Section 2.4).

Further reading: Wikipedia: All-to-all (parallel pattern) · Wikipedia: Collective operation · NCCL docs: collective operations · PyTorch docs: torch.distributed

When the whole EP group sits in one fast interconnect domain (on NVIDIA GPUs, one NVLink domain), DeepInfer takes another path: Mega MoE. Code fact On the Python side, this path makes a single call. It hands the routing result, two sets of expert weights and a block of symmetric VRAM to DeepGEMM’s fp8_fp4_mega_moe (it uses bf16_mega_moe when the activations are BF16, mlp.py lines 254–256), and gets back the output of this layer. There are no separate dispatch and combine calls in between. The shared expert is handed in too. (mlp.py lines 184–188, lines 528–563) Upstream says that inside one scale-up domain, Mega MoE is clearly faster than the unfused way, however wide EP is and however large the batch is. Upstream report (Q&A lines 229–231) How the kernel overlaps communication with compute inside, this book has not verified: the DeepGEMM code is not in this repository checkout.

2.4 Popular experts crowd together: EPLB copies the popular ones and places them again

The whole group steps together, so the time of a step is set by the busiest GPU. Suppose several popular experts sit on the same GPU. That GPU must compute several times as many tokens as the others, and the other GPUs have to wait. DeepInfer measures this with one number: moe_lb = tokens received by the busiest GPU ÷ average tokens received per GPU. Code fact (eplb/__init__.py lines 167–193, stats_logger.py lines 238–241) A value of 1.0 means perfect balance.

The fix is expert load balancing (EPLB). There are more physical slots than logical experts. The extra slots are called redundant experts, and they hold copies of popular experts. Upstream puts it this way: besides the experts a GPU is responsible for, each GPU also holds a few redundant experts. Upstream report (Q&A line 97) A popular expert with 3 copies can spread its tokens over at most 3 GPUs. When copies are placed, two of them may also land on the same GPU. EPLB runs like this: Code fact (eplb/__init__.py lines 131–165, lines 222–278)

  1. Count. At every step, dispatch adds up the tokens received by each local expert and stores them in a sliding window.
  2. Rearrange periodically. Every M steps, the whole group sums the counts in the window with an all-reduce and hands them to the rearrangement policy. The first rearrangement comes early, at M/4 steps, to correct the imbalance of the cold start as soon as possible.
  3. Copy the popular ones. The policy gives out one copy per round. Each round, the copy goes to the expert for which one more copy lowers the largest single-copy load the most. (policy.py lines 105–123)
  4. Place again. All copies line up from the largest load to the smallest. One by one, each goes to the GPU where, after placing it, the sum over steps of the busiest GPU’s load is the lowest. Each GPU is filled until full. (policy.py lines 12–70) This is a greedy algorithm: each time it makes only the best choice for now. It does not guarantee a global optimum, but it is fast.
  5. Move the weights. Move expert weights between GPUs by the old and new maps. If the devices are GPUs in the same NVLink domain, read the mirror on the peer GPU directly. Otherwise use point-to-point send and receive from torch.distributed (NCCL on NVIDIA; on Ascend this mirror path is not used). (eplb/__init__.py lines 195–202) Only after the move does it swap the map. (shuffle.py lines 1–6)

Note an assumption in steps 3 and 4: if an expert has several copies, its load splits evenly among them. Code fact (policy.py lines 31–37) The simulator below ports the same algorithm, scaled down to 16 experts and 4 GPUs.

In the code, EPLB is off by default. The rearrangement interval DEEPINFER_EXPERT_REARRANGEMENT_STEP_INTERVAL defaults to 0, which means no rearrangement. The redundancy floor DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS defaults to 0. The statistics window defaults to 100 steps. Code fact (environ.py lines 113–121) The redundancy floor is a total for the whole group, not a count per GPU. The code rounds it up so that “384 + redundant” divides evenly by EP. (eplb/__init__.py lines 21–28) The settings and measurements that upstream published are below. Upstream report (Q&A lines 93–103)

Compared with Strata: Strata’s expert cache also tracks “who was popular lately”. Every 4 rounds, it swaps the popular experts into VRAM by decayed counts (Chapter 12). The problem it solves is “where to compute”: VRAM or CPU. The problem EPLB solves is “who is busiest”: copy the popular experts a few more times and spread them over several GPUs. Both use the past to predict the future. Both also finish copying the weights before they switch the map.

2.5 How requests reach GPUs: three data-parallel load balancers

EPLB handles only the MoE part. How busy the attention part is depends on how many requests each GPU gets and how long their contexts are. A load balancer at the DP level handles that. These balancers are tightly coupled to the online system, and they are not open source this time. The README lists the DP load balancing of prefill and decode under “not included”. The Q&A says the load-balancing components are tightly coupled to internal infrastructure and not fully open source yet, and the vision encoder load balancer is among them. Upstream report (README lines 38–42, Q&A line 21) The three items below come only from the Q&A description. Upstream report (Q&A lines 105–127)

  • Prefill load balancer. Requests fall into four bands by total context length: under 16K, 16–64K, 64–256K and over 256K. How many engines each band gets adjusts dynamically by each band’s compute demand in the last round. Engines pull work by themselves according to their remaining compute quota. Any engine can hit any prefix (the block KV cache lives on a separate 3FS storage cluster, Q&A line 141, see page 3), so the balancer does not assign by prefix affinity. Inside a DP group, each request goes to the rank with the lowest current quota load.
  • Decode load balancer. It assigns across all GPUs of all decode instances in one pool, and it balances two quantities at once: the number of requests (which sets the batch size per step) and the total KV cache length (which sets the attention cost). The rule of thumb: send short requests to GPUs with low concurrency but a large total KV length, and send long requests to GPUs with a small total KV length.
  • Vision encoder load balancer. A prefill machine picks at random a machine that has a vision encoder (VE) deployed, and then hands the image to the GPU on that machine that currently handles the fewest tiles. It computes the tile count directly from the size: (width ÷ tile side) × (height ÷ tile side).

You need both layers of balancing. The DP load balancer keeps the attention of every GPU about equally busy, and EPLB keeps the MoE of every GPU about equally busy. Upstream says the whole system reaches about 80% of the perfectly balanced offline benchmark. Upstream report

Width also has a cost. All GPUs of one decode instance form one communication domain. If one GPU fails, the whole instance becomes unusable. On restart, the platform decides the EP width again from the number of healthy GPUs at that time. Upstream report (Q&A lines 209–211) For scaling up and down and other fault-tolerance measures, see page 1.

2.6 FP4 for expert weights: half the bytes per step, again

The expert weights each GPU reads per step = number of experts × bytes per expert. Section 2.2 reduced the first factor. FP4 reduces the second. Upstream says the routed experts’ weights use MXFP4: every 32 weights share one ue8m0 scale. The main KV and the index KV also use FP4, but that is a topic for page 3. Upstream report (Q&A lines 213–221)

The code agrees with this description. When it loads the model, the quantization config in config.json must state FP4 for the experts and ue8m0 for the scale, or loading is refused. Code fact (config.py lines 253–264) Expert weights are packed two at a time into one byte in e2m1 format, and the scales are stored separately. (weights.py lines 281–288) In the matrix multiplication, activations use FP8 and expert weights use FP4. (mlp.py lines 177–182, lines 109–128)

Count the bits per weight: 32 weights × 4 bits, plus one 8-bit scale, make 136 bits, or 4.25 bits per weight on average. Teaching estimate Compared with the 8 bits of FP8, the expert bytes read per step drop by about half.

Compared with Strata: Strata’s Q2_0 takes 2.25 bits per weight (Chapter 4, “Quantization”). Its goal is to fit as many of the 34 GB of experts as possible into 12 GB of VRAM, and the CPU computes those that do not fit. All DeepInfer experts stay on GPUs. It spreads experts over dozens of GPUs on one side and uses a 4-bit format on the other, and together these cut the bytes each GPU reads per step.

Remember these three

  1. Attention uses data parallelism, and each GPU handles its own requests. Routed experts use expert parallelism and spread over EP GPUs. Every MoE layer does two all-to-alls, dispatch and combine, so the whole group moves together at every step.
  2. In decode, more GPUs mean fewer experts per GPU per layer (EP8 has 49 per GPU, EP64 has 7). Each step reads fewer expert weights, and one set of weights serves more tokens. The communication per GPU barely changes.
  3. The busiest GPU sets the speed of the whole group. EPLB counts the load of each expert, adds copies of popular experts at regular intervals, places them again, and then moves weights between GPUs. For decode, upstream reports a moe_lb of 1.090.

Common misconception: “The wider EP is, the better. More GPUs are always faster, so keep adding them.”

The read bandwidth you save shrinks with each addition. From EP8 to EP64, experts per GPU fall from 49 to 7. Doubling again to EP128 takes it only from 7 to 4. Teaching estimate When the EP group exceeds the NVLink domain, the standard DeepEP path still works. But Mega MoE and the weight-mirror transfer inside one machine are used only inside a domain. The larger the communication domain, the higher the risk of waiting for the slowest GPU, and the more GPUs stop when one fails. Upstream’s decode width is EP64–128, which matches a supernode of 64–128 GPUs. Upstream report

How experts are numbered

The docstring of FusedExperts defines four counts. logical = n_routed_experts, which the router picks from. extra = n_redundant_experts, written by model_loader._configure_moe_redundancy. physical = logical + extra, which must divide evenly by ep_size. local = physical // ep_size. (moe.py lines 1–8) resolve_num_extra_experts does the rounding: padding = -(num_routed_experts + min_num_extra_experts) % ep_size. (eplb/__init__.py lines 21–28, model_loader.py lines 83–106) The initial layout is [0 … n−1, then copies of 0, 1, 2 …], the same for all layers. (lines 31–39) When it loads weights, each rank reads only its own few experts by this initial layout, and the redundant copies reuse the same HF weights. (weights.py lines 248–272) MoE layers with the same weight shape form one group, and each group has one ExpertLoadBalancer. (deepseek.py lines 323–365)

What happens at each step

ExpertLoadBalancer.step is called once per step by the sampling stage. It returns at once when EP is 1. It does three things: it stores this step’s expert_count in the window and rearranges if needed; it accumulates load statistics; it resets expert_count to zero. (lines 131–165) The NORMAL engine (which does both prefill and decode) skips prefill steps by default. The counts of such a step do not enter the window and do not advance the rearrangement count. After you set DEEPINFER_REARRANGE_AFTER_PREFILL_IN_NORMAL_ENGINE=1, the counts of prefill steps enter the window, and the next non-prefill step rearranges at once. (lines 83–84, lines 146–165) Every DEEPINFER_MOE_LB_STAT_INTERVAL steps (default 128), the load statistics run one all-gather. It gives the average and the maximum of the token counts of all GPUs, and their ratio is the moe_lb in the log. (lines 167–193)

The policy: two greedy stages

rebalance_experts_global copies first and places after. In each round of the copy stage, it computes for each candidate expert j: “the largest single-copy load in each step after adding one copy to j”. It sums over the steps and takes the j with the smallest sum. It adds j × 1e-4 to the score so that the scores of all experts differ. (policy.py lines 73–140) The goal of the placement stage is written in a comment: make the sum of “the load of the busiest GPU in each step” as small as possible, and on a tie pick the GPU with the smaller number. The repository’s unit tests check that the two maps are inverses of each other, that the total number of copies equals the number of physical slots, and that the same input gives exactly the same result twice. (test_eplb_policy.py lines 27–62) The simulator on this page simplifies it to a single layer with double-precision floats. Its tie handling may differ slightly from the PyTorch single-precision version.

How weights move

At the first rearrangement, it first empties PyTorch’s VRAM cache, so memory does not run out. When the EP group is inside an NVLink domain and uses GPUs, it builds a symmetric VRAM mirror that holds the weights of only one layer and refreshes it layer by layer. Each GPU copies the missing experts directly from the paired sender’s mirror. Otherwise it uses batched point-to-point send and receive from torch.distributed (NCCL on NVIDIA), split into buckets by DEEPINFER_REARRANGE_P2P_GROUPS. When an expert has several senders, the receivers split evenly among the senders by a fixed rule. The sender and the receiver use the same function to pair up, so the pairs always match. (eplb/__init__.py lines 195–220, shuffle.py lines 47–53, lines 94–147) Only after the weights have moved does it swap in the new map with copy_. (lines 261–278)
