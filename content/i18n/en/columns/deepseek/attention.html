A different engine

Chapter 8 described attention as “looking back through the book with a question”: every new token scores all the earlier text, so the longer the context, the more pages to turn. Strata’s Qwen path saves effort in two ways: 24 query heads share 2 sets of keys and values, and each token picks at most 2051 positions out of all of them.

DeepSeek-V4.1-Flash in strata-dsv41 takes another route. The last 128 tokens are kept row for row. Older tokens are blended into one row per group of R (in V4.1, layers 20 to 39 have R = 1: no blending, and space is saved only by FP4 and by sharing a source layer). A small scorer then picks at most 512 rows from these. Grow the context from 8K to 1M and the number of rows each token attends to, in each layer, still has the same cap. This page answers three questions: which rows does one token read; why are those rows so small; and which state must the engine store so that a conversation can be rolled back and parked?

In one line: in every layer, each token reads three things: the last 128 rows (the window ring, overwriting), at most 512 rows that the indexer picks from the compressed rows (append-only), and one learned sink number per head that is added to the softmax denominator. All 64 heads share the same K = V row (512 dims) and the same pick list. The number of rows attended to is therefore capped, and the cache keeps only compressed rows (one row per R positions). The cost moves to the indexer: source layers, and indexer layers that do not use the pre-filter, scan all compressed rows at every step, and reading a prompt takes a quadratic amount of scoring.

3.1 What a token looks back at: 128 rows, 512 picked rows and a sink

The header of ds4_model.cu writes down how one attention layer computes, as a recipe. For token p, the layer does five things in order. Upstream report (ds4_model.cu lines 8–10, ds4_model.hpp lines 6–10)

  1. The hidden state goes through two low-rank projections, wq_a and wq_b, and becomes q: 64 heads of 512 dims each.
  2. A separate projection makes this token’s own K = V row, 512 dims. It is rounded to FP8 and written into this layer’s window ring.
  3. The layer reads three things: the latest 128 rows in the window ring; at most 512 rows that the indexer picks from the compressed rows (only layers with a compression ratio above 0 have them); and one learned sink per head.
  4. Each head scores these rows with q, applies softmax and takes the weighted sum. All 64 heads read the same rows.
  5. The rotated part of the output is rotated back, rounded to FP8 and projected by the grouped wo_a and wo_b.

Keep the sources of the numbers apart. 128, 512 and 64 heads come from the file header and from the comments of the lab program Upstream report (ds4_lab.cu lines 1–4). The engine itself reads sliding_window, index_topk and num_attention_heads from the pack’s ds4.txt Code fact (ds4_model.cu lines 519–522). Four geometry checks are hard-coded: head_dim must be 512, index_head_dim must be 128, experts per token must not exceed 8, and hc must not exceed 8. If any check fails, the pack does not load Code fact (lines 2166–2169).

K = V means two copies merged into one. In Chapter 8, every position stores a key k and a value v: k decides “where to look” and v decides “what is seen”. Here the same row is first used for the dot product and then for the weighted sum, and the GPU kernel uses one set of row pointers for both Code fact (ds4_kernels.cu lines 892–903, lines 934–941). The 64 heads then share that one row. This is called multi-query attention (MQA). It goes one step further than the GQA of Chapter 8: GQA splits 24 heads into 2 groups, MQA puts all heads in one group. For background, see Shazeer’s original paper.

The sink is one learned number per head. It enters only the softmax denominator and has no value row: output = weighted sum of the rows ÷ (sum of the row weights + e^(sink − max score)) Code fact (lines 946–949; the sink is loaded at ds4_model.cu line 4308). When a head finds every row irrelevant, it hands its weight to the sink and the output shrinks toward 0. The sink is a single number and takes no cache row. Why softmax needs such an exit is analyzed in the StreamingLLM paper.

Compared with the Qwen path: a Qwen layer in Chapter 8 has 24 query heads and 2 sets of keys and values, K and V are two separate copies, and each step picks at most 2051 positions out of all of them (Chapter 8 “The attention mechanism: Q, K, V”). The 64 heads of a DeepSeek layer share 1 row, and K and V are the same row. The Qwen result is also multiplied by a sigmoid output gate; here, the way to make a head “speak less” is the sink in the denominator.

3.2 The 128-row ring: no recent token is ever lost

The window ring is a fixed-size cache of 128 rows per layer. The row for position p goes into slot p mod 128, and the new row overwrites the one from 128 tokens ago Code fact (ds4_kernels.cu lines 1297–1331). Each row has 512 dims, stored as FP8 codes, with one power-of-two scale per 32 values Code fact (ds4_kernels.cuh lines 22–33). For what FP8 is, see Chapter 4 “Binary and floating point: FP32, FP16, BF16”.

You can compute the bytes per row directly: 512 codes plus 512 ÷ 32 = 16 scales make 528 bytes, which is already a multiple of 16, so no padding is needed Code fact (ds4_model.cu lines 3209–3213). One layer’s ring is 128 × 528 = 67,584 bytes. DeepSeek-V4.1-Flash has 40 layers Upstream report (DEEPSEEK41.md line 3), so 40 layers take 2,703,360 bytes, about 2.58 MiB Teaching estimate. This part does not depend on context length. The cluster page worked out the same 528 independently (DeepInfer page 3).

From position 127 on, the window a token sees is exactly 128 rows, itself included; earlier tokens see only p + 1 rows. The engine first decodes the ring rows into BF16 working rows, appends the new row, and then takes the latest 128 positions. The oldest ring row is left out and is overwritten right after Code fact (ds4_model.cu lines 10090–10118). Why keep exactly 128 tokens? Upstream gives no motive, so this is inference: Teaching estimate nearby tokens matter most, and half a sentence or a variable that was just defined sits in these rows. Keeping them exactly has a fixed cost. Earlier tokens go to the compressed rows of Section 3.3.

The ring overwrites, and what is overwritten cannot be brought back. When speculative decoding verifies a batch of draft tokens, each layer first backs up the rows that are about to be overwritten, at most 16 rows, and writes them back if the drafts are rejected Code fact (ds4_model.cu lines 4357–4360, ds4_kernels.cuh lines 175–176). The ring backup area is 16 × 528 = 8,448 bytes per layer Teaching estimate. A source layer with R > 1 also keeps a group buffer and a snapshot of the new compressed rows Code fact (ds4_model.cu lines 4357–4361). The backup area is allocated only for packs that have a draft model. How drafts are verified belongs to the page DSpark and conversation parking.

If you studied CS: the window ring is a ring buffer (circular queue): fixed capacity, a write pointer that goes around, new data overwriting the oldest, and no more memory allocation. A NIC receive queue and the Linux kernel’s kfifo are the same structure. The slot number is the position mod 128, so reading the row of position p moves no data. See Wikipedia: Circular buffer.

3.3 Compressed rows: blending R positions into one row

For positions older than 128 tokens, the raw rows have already been overwritten by the ring. They survive as compressed rows: one row per R positions. R is the compression ratio, one number per layer, taken from the pack’s compress_ratios list Code fact (ds4_model.cu line 531). A layer with R = 0 has no compressed rows and does window attention only; the blocks of the DSpark draft model must be such layers Code fact (lines 2383–2384).

How are R positions blended into one row? Each position is first projected into a pair of 512-dim vectors, kv and score, and written into slot p mod R. When position p satisfies (p + 1) mod R = 0, the group is full. For each dimension, the engine runs one softmax over the R scores, uses the resulting weights to sum the kv vectors, and finishes with RMSNorm Code fact (ds4_kernels.cu lines 570–604). The result gets rotary position encoding and is rounded to FP4: E2M1 codes with one E4M3 scale per 16 values. One row is 256 + 32 = 288 bytes Code fact (ds4_model.cu lines 10223–10232, ds4_kernels.cuh lines 22–33). A group that is not full waits in an FP32 buffer: R × 512 floats each for kv and score Code fact (ds4_model.cu lines 4329–4331).

With R = 1 nothing is blended: each position gets one compressed row, but it comes from its own projection (compressor.wkv plus normalization), not from a copy of the window row Code fact (ds4_model.cu lines 10129–10135, ref.py lines 250–251).

Not every layer stores its own compressed rows. Only the source layers listed in kv_source_layer_ids carry a compressor and own a compressed cache; later layers with the same compression ratio read from them directly Code fact (ds4_model.cu lines 2393–2412). A check runs at load time: before any layer with a ratio above 0, a source layer with the same ratio must already exist, or loading fails. The code comments say that in V4.1 layer 20 is the first layer with ratio 1, and layers 20 to 39 all read its compressed rows and index keys Upstream report (lines 9261–9262, lines 9304–9306). The ratios of the source layers among the first 20 layers are set by the pack’s ds4.txt. Their values are not in the pinned repository, so this page writes them all as R. The cluster page calls the layers that read earlier layers’ caches YoCo consumer layers (DeepInfer page 3); the Strata code also uses the name yoco.

The capacity of the compressed cache is fixed at load time by the context limit: ⌈max_context ÷ R⌉ + 1 rows per source layer Code fact (line 2401). Each row holds 288 bytes of compressed KV plus an 80-byte index key: 128 dims of FP4 are 64 bytes of codes plus a 4-byte scale, padded to a multiple of 16, which gives 80 Code fact (ds4_kernels.cuh lines 29–33, ds4_model.cu lines 3211–3213).

The rotary position encoding has two frequency tables as well: layers with a compression ratio above 0 use the table with long-context scaling, and window layers use the unscaled table Code fact (ds4_model.cu lines 2171–2172, lines 544–565, line 9969). Only a layer that looks far back uses the scaled table.

Compared with the Qwen path: the Qwen index key in Chapter 8 is the average of 4 raw keys, then normalized and rotated, and used only for scoring; the real attention still runs over all the raw keys and values (Chapter 8). A DeepSeek compressed row is a learned weighted average, and it is itself the row that attention reads. For old positions outside the window, the raw rows are gone, and from then on they can be read only through the compressed rows.

3.4 The indexer: picking 512 rows out of all compressed rows

The indexer is a very small scorer. For token p, the score of compressed row i is Σ_h relu(q_h · k_i) × w_h Code fact (ds4_kernels.cuh lines 131–134, ds4_kernels.cu lines 626–689). q_h is the indexer’s own query: a set of heads, 128 dims each, projected from the low-rank latent of the attention q. The kernel supports at most 32 heads Code fact (ds4_kernels.cu lines 2356–2362), and the lab comments give exactly 32 heads Upstream report. k_i is the index key of row i: 128 dims, FP4. w_h is the weight of each head, projected from this token’s hidden state Code fact (ds4_model.cu lines 10156–10187). The Qwen indexer in Chapter 8 also uses relu and a sum, with no softmax; DeepSeek adds this set of content-dependent head weights.

The min(512, n) positions with the highest scores are selected, where n = ⌊(p + 1) ÷ R⌋ is the number of compressed rows that exist at this moment. When n is at most 512, all rows are selected Code fact (ds4_model.cu lines 10151–10155). The result is a list of positions, one list per token, shared by all 64 heads Code fact (ds4_kernels.cu line 840: the kernel takes the list per token, not per head).

Not every layer has an indexer. Only the layers listed in index_source_layer_ids score the compressed rows and update the list; the other layers reuse the most recent list Code fact (ds4_model.cu lines 9582–9594). Index keys are made only in source layers that own a compressed cache: a key is the compressed row (before rotation) after one more projection, normalization, rotation and rounding to FP4 Code fact (lines 10156–10170).

The list of a source layer can also go through a pre-filter first, called candidate blocks. The layer named by candidate_source_layer_id (layer 20 in the test fixture) first groups the compressed rows into blocks of candidate_block_size, takes the highest score inside each block, and picks the candidate_topk_blocks blocks with the top scores; the block that holds the newest position is always chosen Code fact (ds4_kernels.cu lines 798–812). Later indexer layers use this result and score only the positions inside those blocks. When the number of blocks is at most candidate_topk_blocks, the pre-filter has no effect Code fact (ds4_model.cu lines 10188–10215). In one test fixture of the converter, the block size is 8 and the block count is 2048 (test_pack_gguf_engram.py lines 173–177). If a real pack uses the same two values, the pre-filter starts to matter only when there are more than 8 × 2048 = 16,384 compressed rows Teaching estimate.

The interactive figure below lets you choose a context length and see which rows one decoding token reads at this step: the 128 rows in the window ring, plus the at most 512 compressed rows that the indexer picks. The static figure shows the default: context 8,192, a layer with R = 1.

Attention has a cap on the rows it reads; the indexer’s scan has no common cap. During decoding, a source layer and any indexer layer that does not use the pre-filter score all n rows at every step; a layer with the pre-filter scores only the positions inside the candidate blocks (see above). A layer that scores everything reads n × 80 bytes of index keys and does n × 32 × 128 multiply-adds (head count taken from the comments) Teaching estimate. n grows linearly with context. Reading a prompt means scoring each position once: a prompt of L tokens costs L(L + 1) ÷ 2 pairs on one indexer layer with R = 1, and in general L²/(2R). At L = 8,192 that is about 3.4 × 10⁷ pairs, at L = 262,144 about 3.4 × 10¹⁰, and at L = 1,048,576 about 5.5 × 10¹¹ Teaching estimate. The 262,144 row is exactly the number of full-attention pairs worked out in Chapter 8 (about 34.4 billion, Chapter 8 “Computational complexity and O(n²)”). What is saved is the cost of each pair: full attention with 64 heads × 512 dims takes 2 × 32,768 multiply-adds per pair (the dot product plus the weighted sum), while the indexer takes only 32 × 128 = 4,096 per pair and has no softmax, about 16 times cheaper by a rough count Teaching estimate. The documentation says the same: with a very long prompt, reading is slow “because the indexer’s work grows with the square of the length”, and the first reply at 512K or 1M takes many minutes Upstream report (DEEPSEEK41.md lines 98–100).

If you studied CS: this is the two-stage “recall, then rerank” of a search system: recall is cheap but scans the whole collection; rerank is expensive and looks only at candidates. Here recall is the indexer scanning all compressed rows, and rerank is real attention over 640 rows. The candidate-block pre-filter is like one more coarse index in front of recall, which drops most of the blocks first.

Compared with DeepInfer: the cluster puts the main compressed KV and the indexer keys into the same kind of paged block KV: 128 tokens per block, found through a block table (DeepInfer page 3). Strata has no block table: for each source layer, the compressed rows and the index keys each form one array laid out contiguously by position, and row i sits at i × row bytes Code fact (ds4_model.cu line 10230). Teaching estimate One computer serves one conversation, so it has no need to split memory into blocks for sharing between requests, swapping out or prefix hits.

3.5 What a token leaves behind: three kinds of state, two ways to roll back

When a token has gone through all layers, it leaves four things in the engine: the window ring of each layer; the compressor’s group that is not yet full; the compressed rows and index keys of the source layers, append-only; and the Engram n-gram history, which belongs to the Engram page. Code fact (ds4_model.hpp lines 8–11) The first three decide whether a conversation can be rolled back and whether it can be parked.

Chapter 20 uses a notebook and a whiteboard as the picture of two kinds of memory. The compressed rows are the notebook: written only forward and ordered by position, so rolling back means only turning down the number “written up to page …”, and the part beyond it gets rewritten later Code fact (ds4_model.cu lines 5691–5692). The ring and the unfilled group buffer are whiteboards, and so is the GDN state of Chapter 9 (Chapter 9 “Recurrent neural networks and ‘state’”): new content covers old content, and the only way back is to take a photo in advance. A checkpoint is that photo. It copies only these two; up to 4 are kept at once: the end of the previous turn’s prompt, one position before it, an anchor, and a shared prefix Code fact (lines 1104–1110, lines 5751–5755). Each one is at least 2.58 MiB Teaching estimate. Why a whiteboard needs a photo is explained in Chapter 20 “Snapshots and copy-on-write”.

When another request pushes a conversation out of the model, the engine does one conversation parking: it writes out all the state. The content is the tokens, each layer’s ring and group buffer, the compressed rows and index keys of every source layer (0 to pos ÷ R rows), and the checkpoints Code fact (ds4_model.cu lines 5788–5806). There is a ready formula for the size: a header plus 4 × pos bytes of tokens; plus, per layer, 16 + 67,584 bytes and the group buffer (2 × R × 512 × 4 bytes, only in source layers with R > 1); plus ⌊pos ÷ R⌋ × (288 + 80) bytes for each source layer; plus the checkpoints. The documentation gives about 17 MB per 6.5K tokens Upstream report (DEEPSEEK41.md line 116). A rough estimate from the formula: rings 2.70 MB, at most 4 checkpoints at least 10.8 MB, one source layer with R = 1 at 6,500 × 368 ≈ 2.4 MB, about 15.9 MB in total, and then the group buffers and the other source layers on top, which is the same order as the documentation Teaching estimate. R is missing for the first 20 layers, so this sum can only be estimated to the order of magnitude. The parking procedure belongs to the page DSpark and conversation parking.

These caches live in VRAM and compete with the experts for space. At load time the engine first allocates the ring and the compressed cache of each source layer by max_context, and then puts experts into the remaining VRAM Code fact (ds4_model.cu lines 2696–2698, line 3042, lines 4600–4620). The documentation is direct about it: every extra position means a few fewer experts Upstream report (DEEPSEEK41.md lines 99–100). The default context is 8,192; --context accepts 8K to 1M; upstream has not tested anything above 256K Upstream report (line 93, lines 96–98). When the context is full, the engine reports “the context is full” Code fact (ds4_model.cu line 9295). A comment at line 795 of setup.py still says “(4096 and 8192; 64K is not tried yet)”, which is out of date: the check at lines 8533–8536 of the same file accepts 8,192 to 1,048,576 Code fact (setup.py line 795, lines 8533–8536).

Compared with the Qwen path: Chapter 17 pages the KV cache with 4 tokens per page; beyond 64K of context, most pages go to RAM and VRAM keeps only the frequently used ones (Chapter 17 “The KV cache and paged management”). dsv41 has no such layer: the compressed cache is an array laid out contiguously by position, allocated once in VRAM by the context limit, and a longer context means giving up room that experts would use. In Chapter 8, the 12 QSA layers of Qwen need 768 MiB in total at a 32K context (FP16, Chapter 8); here one source layer with R = 1 needs 11.5 MiB at the same length (FP4). That is 12 layers against 1, and also FP16 against FP4, so the bases differ. The totals of the two models cannot be compared directly, because the DeepSeek side lacks the R of the first 20 layers.
Compared with DeepInfer: the ring on the cluster holds 134 tokens: 128 plus 6, where the extra 6 are kept for speculative-decoding rollback; for each sequence only the ring of the first 20 layers is archived, about 1.4 MB (DeepInfer page 3). The Strata ring is 128 rows, and rollback relies on a separate 16-row backup area; parking saves the whole state, compressed rows included. Both sides follow the same logic: once the ring is overwritten there is no way back, so both take a photo at agreed positions.

3.6 Attention is not the bottleneck: the decode bill and the long-prompt shortcut

First, how much a decode step reads from the cache. Each layer reads at most 128 ring rows (528 bytes each) and 512 compressed rows (288 bytes each): 128 × 528 + 512 × 288 = 215,040 bytes. If all 40 layers have compressed rows, the cap is 8,601,600 bytes, about 8.2 MiB Teaching estimate. Now the experts: the placement table in the documentation gives 18.8 MB per expert for UD-Q8_K_XL Upstream report (DEEPSEEK41.md line 15); each token uses 6 per layer, which is 240 over 40 layers, about 4.5 GB Teaching estimate. The cache that attention reads is only about 0.2% of what the experts read. The indexer scan is counted separately: every full-scoring indexer layer reads n × 80 bytes per step, which at n = 1,048,576 is 80 MiB, already more than these 8.2 MiB Teaching estimate. So the 0.2% holds only for the attention part and for short contexts. And 0.2% compares bytes touched, not time: some experts sit in VRAM, some in RAM and some on SSD, and the slow ones are the latter.

A measurement in the code comments backs this up. The engine has a split-KV attention kernel that is 2.9 times faster for a single query on an A4000; but on a machine with 4 × R9700, decoding is 21.8 against 21.9 tok/s, with no measurable gain, so it is off by default and you turn it on with DS4_ATTN_SPLIT=1 Upstream report (ds4_kernels.cu lines 2027–2031, lines 2442–2445). Decoding is slow elsewhere: in the experts and the SSD, see the experts page.

The long-prompt bill is different. When a prompt is read, every position goes through all layers. But layers 20 to 39 have a shortcut: for earlier positions they read only through the compressed rows and index keys of layer 20, and their window looks back only 127 tokens Upstream report (ds4_model.cu lines 9304–9306). So for the front part of a long prompt there is no need to run the attention and experts of layers 20 to 39; it is enough to compute the compressed rows and index keys of layer 20 (the code calls this kv_only, and the comment says “no experts”) Code fact (lines 8538–8542, lines 3937–3938). Only the last stretch needs all layers: each extra layer pushes the dependency range back by 127 more tokens, so 20 layers keep (40 − 20) × 127 + 128 = 2,668 rows Teaching estimate (test_prompt_skip.py lines 26–30, ds4_model.cu lines 9315–9317). It is worth doing only when at least 1,024 rows can be skipped Code fact (line 963, line 9318). With 2,668 + 1,024, the shortcut is used only when one fed-in prompt has about 3,692 tokens or more Teaching estimate. The shortcut is enabled only on the one-GPU path that reads the prompt in chunks, and DS4_YOCO=0 turns it off Code fact (lines 9275–9283).

A rough estimate for a prompt of 32,768 tokens: 2,668 ÷ 32,768 is about 8%, so layers 20 to 39 process only about 8% of the rows Teaching estimate. Why does the answer not change? The comment’s argument: of what these layers do for early positions, only the compressed rows and index keys are read later, and everything else affects only each layer’s own ring, which keeps just the last 128 rows. Upstream has a test script that compares the shortcut with the full computation and requires the KL to stay within “the noise of the expert summation order” Upstream report (test_prompt_skip.py lines 1–11).

Compared with DeepInfer: after a cache hit, DeepSeek’s own service replays only the last 128 tokens and cuts the window to stay inside the replayed span; this is called bounded replay (DeepInfer page 3). The Strata code leaves a switch for this rule: DS4_YOCO=2 means “keep only the last 128 rows”, which is faster and changes the answer slightly; the default, 1, keeps 2,668 rows and matches the full computation except for the expert summation order Upstream report (ds4_model.cu lines 9263–9266).

Remember these three

  1. In every layer, each token reads a capped number of rows: the last 128 rows in the window ring (FP8, 528 bytes per row, overwriting), plus at most 512 rows that the indexer picks from the compressed rows (FP4, 288 bytes per row), plus one sink number per head. The 64 heads share the same K = V row and the same pick list.
  2. Positions older than 128 tokens survive only as compressed rows: one row per R positions, a learned weighted average, append-only. A source layer with R = 1 takes 368 bytes per position (compressed row plus index key); the rings of 40 layers are fixed at about 2.58 MiB.
  3. A cap is not free. The indexer scans all compressed rows (or the candidates after the pre-filter) at every step, and reading a prompt takes quadratic scoring; the caches live in VRAM and push out experts; there are two ways to roll back: truncate the position for compressed rows, and copy first for the ring and the group buffer.

Common misconception: “Each token reads only 640 rows, so a long context costs next to nothing.”

The rows read are capped, but the cost is not only there. The indexer has to score all compressed rows: n rows at every decode step, and L²/(2R) pairs to read the prompt. All compressed rows and index keys must be kept, which takes VRAM and pushes out experts. Upstream’s advice is direct: start at 256K or less, because the first reply at 512K or 1M takes many minutes Upstream report (DEEPSEEK41.md lines 98–100).

Go deeper: the call chain of one decode step, and what could not be checked

What one decoding token does inside layer(), in order

The entry point is layer() Code fact (ds4_model.cu line 9961). Below is the order of the attention part; all line numbers are in the same file.

  1. q: wq_b acts on the low-rank latent, then the rotation is applied (lines 10080–10087).
  2. Window: ring_to_ext decodes the ring into BF16 working rows; the new K = V row is normalized, rotated, rounded to FP8 and appended; ext_to_ring writes it into slot p mod 128 (lines 10094–10104).
  3. The window range of each token is written into AttnRows: 128 rows starting from max(win − p0, t + 1) (lines 10107–10119).
  4. Compressor: with R = 1 it normalizes directly, with R > 1 it calls compress_win; the row of a full group is rotated, rounded to FP4 and written at g_first × row bytes (lines 10129–10148, lines 10223–10232).
  5. Indexer: a source layer first computes the new index key, then q and the head weights, and calls index_score and topk (lines 10156–10215).
  6. sparse_attn: scale factor 1 ÷ √512, with the sink passed in (lines 10261–10263). The output is rotated back, rounded to FP8 and passed through wo_a and wo_b (lines 10265–10279).
