Guess, verify, park

The earlier pages answered "how does a model this big fit into one computer?" This page answers "once it fits, how do we make it a bit faster, and how do several conversations take turns using it?" There are four parts. The DSpark draft model guesses 5 tokens at a time (the block size of 5 comes from comments next to the shipped pack), and the main model checks them all in one row. Inside the verify window, the experts that the CPU helps compute run through a mailbox, in parallel with the GPU. When another conversation pushes yours out, its state is parked in RAM and on disk, and the engine reads it back when you return. The serving layer writes the thinking effort as one number, and translates the model's tool-call format into a shape clients understand. After reading, you can answer three questions: how the engine decides how many drafts to verify; why the verify window is set to synchronous on Strix Halo; and what the engine reads when a conversation comes back after several days.

In one line: DSpark gives 5 drafts and 5 confidences in one block forward pass (the block size is 5, according to comments next to the shipped pack). The engine trims the window with two gates (a floor for each draft, and a running product of confidences), then lets the backbone line up [last token + kept drafts] in one row and verify them all at once. It keeps the consecutive prefix, judged by "the probability that the backbone would write this token itself", and rolls back the rest. Inside the verify window, experts on the CPU lane go through a host-mapped mailbox, in parallel with the GPU. This path is slower on Strix Halo, so setup switches it to synchronous. Conversation parking puts the whole conversation state in RAM first (up to 4 conversations), then spills it to a folder on disk. The serving layer sets 2 GiB and turns it on. The one-week cleanup is the engine's own default. Every speed number comes with its machine and its conditions.

5.1 How DSpark guesses: one block forward pass, five drafts, five confidences

First, recall the idea. Speculative decoding means "guess first, verify later": a cheap draft model guesses a few tokens, the big model lines them up and checks them in one pass, and only the consecutive correct prefix is kept. Chapter 18, “Speculative decoding: guess boldly, commit strictly” covers this idea. This page covers only what is different on the DeepSeek-V4.1-Flash path.

What the draft model is. DSpark is a draft model made by Unsloth. It uses the Q8_0 format, takes about 8 GB, and all three file sets (1.75, 2.00 and 2.25 bpw) share one copy. Upstream report (DEEPSEEK41.md line 30, DEEPSEEK41.md line 40) The size accounting for the whole disk was done on page 1. In the engine, the draft model is a few blocks at the end of the checkpoint. Its geometry (block size, noise token, Markov rank, number of experts, how many are picked, which backbone layers it attaches to) is read from the pack's config keys. Code fact (ds4_model.cu lines 533–536)

Its internal structure. The engine's own check script compares line by line against DeepSeek's checkpoint, and it states that the draft model has three blocks. Each block is windowed attention plus a small MoE with 128 experts and 3 picked per token. The input comes from the backbone's layer 37 to 39 states. Upstream report (dspark_ref.py lines 10–14) The draft model does not store its own history. The engine keeps a window ring for each block, and the ring holds a projection of the backbone's KV. Each time the backbone keeps a batch of rows, the engine uses those rows' states at those three layers to "seed" the ring. Code fact (ds4_model.cu lines 7677–7681)

The input of one drafting round. To draft, the engine gives the draft model one block. Row 0 is the token that was just decided and has not yet been fed to the backbone (call it y). Every other row holds the same fixed "noise token". The number of rows equals dspark_block_size in the pack. Code fact (ds4_model.cu lines 7761–7766, pack_gguf.py line 222) This number is not written in the engine code. Three comments all say it is 5. The check script writes the block as "[y, noise x 4]". The engine comment says "the drafter's fixed T=5". The comment in setup says "6-row verify window" (5 drafts plus y). Upstream report (dspark_ref.py lines 10–14, ds4_model.cu lines 9620–9625, test_dsv41_async_t.py lines 3–5) The header comment of the kernel file ds4_attn_split.cuh still says "DSpark verify T = 2..5", which does not match 6 rows. Upstream report (ds4_attn_split.cuh lines 3–4) This page follows T = n + 1 in verify, and treats that header as an old comment that was never updated.

How the five drafts come out. The block passes through the three blocks and yields 5 rows of hidden states. Each row then goes through the backbone's output head, gets one Markov bias term added, and takes the argmax. That is the draft for the row. The bias looks only at the previous token: row 0 looks at y, and each later row looks at the draft that the row before it just produced. So the 5 drafts come from one block forward pass plus five tiny chained steps, not five full forward passes. Code fact (ds4_model.cu lines 7877–7886) By default a draft takes the argmax. Only the environment variable DS4_DSPARK_SAMPLE=1 switches to sampling from the draft model's distribution, and that is a test switch. Code fact (ds4_model.hpp lines 128–134, ds4_model.cu line 1052)

How the five confidences are computed. Each row also yields one confidence. Take the block's output row, append the Markov embedding row of the previous token, take a dot product with a learned weight vector, and apply a sigmoid. Code fact (ds4_kernels.cuh line 278) The engine's author treats it as "the probability that this draft is kept". A comment in main.cpp says a draft is worth verifying because the probability that it is kept together with all the drafts before it is still high enough. Upstream report (ds4_main.cpp lines 169–175) That is how the author uses it. This page has no data on whether the confidence is actually calibrated, so it draws no conclusion.

Drafting is not free. A comment in the engine records one set of timings. The output head of the draft block (fixed T=5) dropped from 4.55 ms to 2.83 ms, and the whole round dropped from 14.49 ms to 13.46 ms. The machine is not named. Upstream report (ds4_model.cu lines 9620–9625) Decode speeds across machines range from 4.7 to 80 tokens/s, which converts to 12.5 to 213 ms per token. Upstream report (DEEPSEEK41.md line 63, DEEPSEEK41.md lines 64–65) Teaching estimate (1000 ÷ 80 = 12.5 ms; 1000 ÷ 4.7 ≈ 213 ms) These two sets of numbers come from different machines and different measurement setups, so you cannot compare them directly. All we can say is that one drafting round costs more than ten milliseconds. So "guessing accurately" is not enough; the guess must also be "worth it". The two gates below exist for that purpose.

Compared with the Qwen path: The draft on the main line, Qwen3.8-Flash-Next, comes from the model's own single MTP layer. Setup defaults to --spec 4: a 4-row window that guesses at most 3 tokens at a time. --spec sets the upper limit of the window, and DraftPolicy can still adjust the real length from measured timings (Chapter 19, section 19.5). DSpark yields 5 drafts in one forward pass and adds a column of confidences. That column is the raw material for the two gates in the next section.
Compared with DeepInfer: DeepInfer's draft module also guesses 5 tokens in one forward pass, its input is also [the token just decided, noise token × 4], and it also carries a column of confidences. Upstream report (see DeepInfer's spec-sched page; that column was checked at a679bb86) A comment in the Strata engine calls the cumulative gate "DeepInfer's cumulative rule" outright. The use differs: a cluster uses the confidences to split verification slots among dozens of requests, while one computer has a single request, so the confidences only trim one window.

5.2 Whether to load it, and how many to verify: --dspark and the two confidence gates

Four values. --dspark accepts on, off, none and auto. Code fact (ds4_main.cpp lines 1332–1337) on and auto load the draft model and use it. off loads it but does not use it. none does not load it at all. off has a trap: the draft model's experts take about 7 GB, so loading them takes VRAM. That is why the setup launch script passes auto and never passes off. Upstream report (DEEPSEEK41.md lines 77–78)

The arithmetic behind auto. At load time, the engine compares the total bytes of all routed experts with the available VRAM on all GPUs (after the reserve is subtracted). If the experts are more than 1.5 times the VRAM, the engine does not load the draft model. Code fact (ds4_model.cu lines 2343–2347) The comment gives two reasons. On such a machine, one verify round reads 3.3 times the bytes of one token, and measurement shows it is no faster than decoding token by token. The draft model's 7 GB of experts would also push out the hottest experts of the backbone. Upstream report (ds4_model.hpp lines 46–49) Take a graphics card with 12 GB: Teaching estimate (1.5 × 12 GB = 18 GB, while the model shards of the 2.00 file set total 138 GB, not counting the 111 GB Engram table and the 8 GB draft model (DEEPSEEK41.md line 37)) The experts make up most of the model. This page has no exact figure for them, but it is far above 18 GB, so auto will never load the draft model on this kind of card. On a Mac it is even simpler: Metal has no kernel for the quantized Markov bias head, and measurement shows no speedup, so auto never loads it, and forcing on prints a warning that it will "most likely stop at the Markov bias step". Code fact (ds4_model.cu lines 2326–2336)

Actual results on each machine, each with its conditions.

  • RTX 3060 (12 GB VRAM, 46 GB RAM): off by default. Turning on --dspark by hand adds 2–13% on top of the release defaults. An earlier release note said 6.1–6.7 rose to 8.2–8.7 tokens/s. That compared against forced-on, and it was later corrected. Upstream report (DEEPSEEK41.md line 64, release-notes-0.2.4.1.md line 9)
  • RTX 5070 (12 GB) + Ryzen 5 7600 (6 cores): turning it on gains nothing. Code answers run at 4.64 tokens/s (off) versus 4.33 (on, the best setting); the agent task runs at 3.41 versus 2.86–3.21. The release note gives the reason: "the CPU spent on checking drafts is about equal to the value of the tokens saved". Upstream report (release-notes-0.2.4.md line 42)
  • 4× Radeon AI PRO R9700 (0.2.4, 2.00 set): about 31 tokens/s, and 55–69 with DSpark on. Upstream report (MODELS.md line 104) These are old numbers from before the "speed tier" existed. Their conditions differ from the 48 tokens/s on page 1, so do not compare them with each other.
  • RTX 4090 (48 GB) + 128 GB RAM (self-reported by a user, one report from one machine): auto decides "off", and the speed is only 16–22 tokens/s. With --dspark on --dspark-conf 0.65 set by hand, the median of five 64-token answers is 40.2 tokens/s. The document also says auto is still the default. The manual command also contains --ssd-cache 108, and the document does not give the other settings of the two runs in full. So the rise from 16–22 to 40.2 cannot be credited to DSpark alone. Upstream report (DEEPSEEK41.md lines 69–71)
  • Strix Halo 128 GB, 2.25 set: the experts are too large, so this machine runs without the draft model. Upstream report (STRIX_HALO.md lines 79–84)
  • Mac: off, same answers, no speedup. Upstream report (DEEPSEEK_MAC.md line 74)

These results point to one rule: the experts in the verify window are either in VRAM, or must be read from RAM or SSD. At Full quality, each row picks 6 experts, so a 6-row window makes at most 36 picks. The Faster mode, the default on a 12 GB card, picks 5 per row, at most 30. Teaching estimate (6 rows × 6 = 36; 6 rows × 5 = 30) Upstream report (DEEPSEEK41.md line 130) The more distinct experts a layer touches, the more bytes it has to move. On a machine whose VRAM holds most of the experts, verifying more rows adds almost no cost. On a machine where they do not fit, every extra row may read a few more experts. The window path reads each expert only once, which already saves part of the cost. Code fact (ds4_model.cu line 10365) It cannot save everything, so the window must be "trimmed" below.

The first gate: a floor for each draft. dspark_conf defaults to 0.5. You can change it with --dspark-conf, or with the dspark_conf key in a request. If a draft's confidence is below it, drafting stops there. Code fact (ds4_model.hpp lines 52–55, ds4_main.cpp lines 281–286) The second gate: the running product. Multiply the confidences of the drafts so far, and stop when the product drops below the gate. On most machines the default is 0, which means off. RDNA4 is the exception; see the next paragraph. In the engine this is one loop: count from draft 1, stop at the first draft that fails, and drop the whole tail after it. The reason is simple: for draft 3 to be useful, drafts 1 and 2 must both be accepted. The loop also has two hard caps: the smaller of the tokens this request can still generate and the context headroom, minus 1; and --dspark-depth (default 64, never reached in practice). Code fact (ds4_main.cpp lines 238–244, ds4_main.cpp line 165) When that smaller value leaves only 1 token, the engine does not draft at all. Code fact (ds4_main.cpp lines 223–224)

The default of the product gate follows the hardware. RDNA4 graphics cards (gfx1200, gfx1201: R9700, RX 9000) default to 0.5, and all others to 0. The environment variable STRATA_DS4_DSPARK_CUM wins on any machine, and DS4_DEFAULTS=026 falls back to the 0.2.6 value of 0. Code fact (ds4_experts_rule.hpp lines 197–201, experts_rule_test.cpp lines 283–287) A comment records why only RDNA4 is turned on: 4× R9700, 2.25 bpw, 6 decodes of 128 tokens per group, the same batch of ids, 71.7 → 76.9 tokens/s (median). Project Maya measured +6.5% on a Radeon 8065S (Strix Halo), but that is one data point from one machine. On CUDA the measurement came out flat. So Strix and CUDA stay at 0. Upstream report (ds4_main.cpp lines 169–175) The floor is not 0.5 everywhere either: the Strix Halo Windows document writes the launch arguments as --dspark auto --dspark-conf 0.65, and when the tuner tries the "force on" setting, it also passes 0.65. Upstream report (STRIX_HALO_WINDOWS.md line 78, tune.py lines 121–122)

Try it. The simulator below uses a set of teaching numbers and lets you drag three quantities: drafts per round (1 to 5), the acceptance rate (the size of the conditional probability that each draft is kept), and the confidence gates (the floor and the running product). It shows how many tokens one verify window finally yields per round. The formula is E = 1 + c₁ + c₁c₂ + … + c₁…ck, where k is the number of drafts that pass the gates and cᵢ is the confidence. Teaching estimate (E = 1 + Σᵢ₌₁..k ∏ⱼ₌₁..i cⱼ; the derivation of the expected value is in Chapter 19, section 19.2) Treating confidence as the conditional acceptance rate is this page's teaching assumption, not a fact the engine has measured.

What to look at in this example. The five drafts have confidences 0.80, 0.62, 0.45, 0.35 and 0.28. The running products are 0.800, 0.496, 0.223, 0.078 and 0.022. Teaching estimate (0.80 × 0.62 = 0.496; 0.496 × 0.45 ≈ 0.223; 0.223 × 0.35 ≈ 0.078; 0.078 × 0.28 ≈ 0.022) With only the 0.5 floor, draft 3 (0.45) is blocked, so 2 are verified. Add the 0.5 product gate, and draft 2 has a product of 0.496, which misses by a hair and is also blocked, so only 1 is verified. The three approaches give expected yields of 2.62, 2.30 and 1.80 tokens, with windows of 6, 3 and 2 rows. Teaching estimate (1 + 0.800 + 0.496 + 0.223 + 0.078 + 0.022 ≈ 2.62; 1 + 0.800 + 0.496 ≈ 2.30; 1 + 0.800 = 1.80) The question becomes: is the cost saved on the rows we skip worth the 0.3 to 0.8 tokens we give up? The answer depends on the machine. On RDNA4 it pays off, and on CUDA it is flat, so the defaults differ. The upstream measurements give only the final tokens/s, not the tokens per round.

There is one more capping knob. --dspark-block N caps the drafts per round at N, and the pack's block size is the upper limit. Code fact (ds4_model.cu line 2350) The tuner tries N = 3, and keeps that setting only if it is more than 5% faster than the standard setting. Upstream report (DEEPSEEK41.md lines 137–140) So "5" is the factory cap, not the best value for every machine.

After one wasted round of drafting, the next round rests. If no draft in a round passes both gates, the engine takes an ordinary decode step as usual and makes the next round skip drafting. A different case does not count: if drafts were sent to verification and all were rejected, the next round drafts as usual. Code fact (ds4_main.cpp lines 988–1000) Drafting has already spent the time, and this rule stops the waste from repeating. A request can also carry three keys of its own: spec, dspark_conf and dspark_cum. The tuner uses them to measure both "on" and "off" while it benchmarks speed. Code fact (ds4_main.cpp lines 281–286)

Compared with the Qwen path: The main line also has a floor: once --spec-min-p is set, the draft layer stops adding a draft to the window when its confidence in that draft is below the gate (Chapter 19, section 19.5). dsv41 adds a second gate: the running product of confidences. The main line also has a controller that updates the acceptance rate with an exponential moving average (section 19.4) and a DraftPolicy that picks the window from measured timings (section 19.5). This page found nothing equivalent in ds4_main.cpp: the only "adaptivity" in dsv41 is the auto decision above, the two gates, and resting one round after a wasted one.

5.3 The verify window: check a whole row at once, roll back on error

How the window is laid out. The k drafts that pass the gates, plus y, form a window of k + 1 rows, and the window goes through all layers of the backbone in one pass. Code fact (ds4_model.cu lines 7952–7958) The largest k is the block size 5, so the window has at most 6 rows. Each row writes state for itself: the new row in the window ring, the partial group of the compressor, the compressed KV and the indexer keys.

How to compare. Verification has two modes, depending on the request's temperature. At temperature 0 or below (greedy), each row takes the backbone's argmax, and we count from row 0 how many consecutive rows equal the draft; call that m. Code fact (ds4_model.cu lines 7967–7978) At temperature above 0 (sampling), it uses the classic rule of speculative sampling: draft d is kept with probability min(1, p(d) ÷ q(d)), where q is the draft's distribution. If it is rejected, one replacement token is drawn from the residual distribution max(0, p − q). This guarantees that each token has the same distribution as if the backbone had sampled it itself. Code fact (ds4_model.cu lines 7945–7950, sampler.cu lines 184–186)

q is a single point, so the rule simplifies. The draft takes the argmax, so q is a point mass sitting on d, with probability 1. The engine simply fills q with 1 here. Code fact (ds4_model.cu lines 7979–7992) The keep probability becomes min(1, p(d) ÷ 1) = p(d): whatever probability the backbone gives this token (after the sampling chain of top-k, top-p, min-p and temperature), the draft is kept with that same probability. Teaching estimate (q(d) = 1 → min(1, p(d) ÷ 1) = p(d)) When a draft falls outside the cut of the sampling chain, p(d) = 0, and it is never kept. Code fact (ds4_model.cu lines 7979–7992) The serving layer's default request is a sampling request (temperature 1.0, top_p 1.0), so everyday use takes this path. Upstream report (DEEPSEEK41.md line 115, test_dsv41.py line 419)

Confidence does not appear here. It decides only which drafts enter the window, and plays no part in "keep or not". Code fact (ds4_main.cpp lines 238–244) Whether to keep a draft depends only on the backbone.

How many tokens one round yields. m is the number of consecutive drafts kept. The output of the round is those m drafts, plus the token the backbone itself picks at the first row that "differs", so m + 1 in all. When every draft is rejected, m = 0 and the round still yields 1 token, as many as not guessing at all. Code fact (ds4_model.cu lines 8011–8012) That token does not enter this round's state. It becomes y of the next round.

What rollback undoes. The backbone wrote state for all k + 1 rows, but only the first m + 1 rows are valid: y plus the m accepted drafts. The rest must be undone. The rows of the window ring that the new rows overwrite are backed up before the verify window starts, and rollback restores them. Code fact (ds4_model.cu line 10104) The compressor's partial group is saved as a snapshot first. Rollback restores it, then replays the kept rows. Code fact (ds4_model.cu lines 10137–10140) The compressed KV rows and indexer keys stored by position need no handling, because they are overwritten when those positions come around again. Code fact (ds4_model.cu lines 8027–8028, ds4_model.cu line 8015) Finally, the draft model is re-seeded with the m + 1 kept rows. Code fact (ds4_model.cu line 8016)

If you studied CS: Guess first, verify later is a CPU's branch prediction plus a pipeline flush. The k drafts in the window are the "predicted branches", verification is "branch resolution", and rollback is the "pipeline flush". Rollback also uses an old database trick: keep a backup or snapshot before you change anything, restore it on failure, and commit it on success. Different kinds of state use different backup methods: ring rows use a backup, the compressor uses a snapshot plus replay, and rows stored by position rely on being overwritten. Chapter 18, section 18.4 covers this. The difference is that the main line's Qwen "whiteboard" is the GDN recurrent state, while here the material is the window ring and the compressor.

The measured acceptance rate. A comment in the engine has one number: on one machine, whether the draft takes the argmax or samples from the draft distribution, 31–32% of the 5 drafts are accepted (the comment calls the machine only Uranus and does not give its full hardware). Upstream report (ds4_model.cu lines 1052–1054) By this number, when all 5 drafts are verified, 1.6 are accepted on average and each round yields about 2.6 tokens. Teaching estimate (0.315 × 5 ≈ 1.58; 1 + 1.58 ≈ 2.6 tokens) On another machine, or with another kind of content, the number will change. At the end of each request the engine prints "drafts X of Y kept". It also prints kept versus reached for each position: the share of draft i that is kept when the first i − 1 drafts were all kept. That is exactly the definition of cᵢ above, so it can be measured directly. Code fact (ds4_model.hpp lines 103–104, ds4_main.cpp lines 150–151) To draw a calibration plot of "confidence versus true acceptance rate", use --spec-eval to verify every draft (--dspark-conf 0), and have DS4_ROUND_LOG write one line per round with the number of drafts, the number accepted and each confidence. Code fact (ds4_main.cpp lines 1223–1225) This page does not have that data.

Compared with the Qwen path: The main line's default verification rule is "accept only if the draft equals the target's sampled result exactly". The classic min(1, p ÷ q) needs the switch STRATA_SPEC_PROB=1, which is off by default (Chapter 18, section 18.5). The verify of dsv41 writes the classic rule directly, and this page found no such switch in src/dsv41. The two guarantee different things: exact equality guarantees that the same seed writes the same tokens, while the classic rule guarantees only that each token's distribution is unchanged.

5.4 The async mailbox: let the CPU and GPU work in parallel inside one layer

The problem. The experts in a verify window fall into two kinds. Those in VRAM are computed by the GPU itself. Those that are not go to the CPU lane: they are read from a RAM slot or the SSD, and the CPU computes them. Page 2 explained how they are split. Until the routing result of a layer is out, nobody knows which expert of this layer is on which side. How can the CPU's share overlap with the GPU's share?

The synchronous path: the GPU waits. The GPU first computes the routing, copies the selected expert ids and the input to the host, and the host waits for the event to finish, then plans, then computes the CPU-lane experts. During this time the GPU can only compute the shared expert first, and then wait. Code fact (ds4_model.cu line 10430, ds4_model.cu line 10455)

The async mailbox: the GPU does not wait. The device writes each layer's routing result and FFN input into a host-mapped ring of memory, called the mailbox, with 64 slots in all. Code fact (ds4_kernels.cuh line 218) After the data is written, it passes a system fence, and only then is the sequence number written. Code fact (ds4_kernels.cuh lines 215–217) A service thread on the host sees the new sequence number, computes the weighted part of this layer's CPU-lane experts, and writes it into a reply slot. Meanwhile the GPU keeps computing the shared expert and the experts in VRAM, and waits for the reply only just before the experts are summed. Code fact (ds4_model.cu lines 1117–1119, ds4_model.cu lines 10302–10305)

If you studied CS: The mailbox is a lock-free ring queue with a single producer and a single consumer. The producer writes the data, passes a fence, and publishes the sequence number last. The consumer polls the sequence number and reads only after it sees a new one. Writing the sequence number last guarantees that when the consumer sees it, the data is complete. This is the same kind of problem as "committed does not mean completed" in Chapter 14, section 14.3. Here the sequence number announces "completed".

The mailbox carries more than routing. The device also publishes its guess for the next layer's picks together with this layer's routing. The service thread uses it to read those experts early, so the SSD starts reading while this layer is still computing. This prefetch affects only the page cache, so the output does not change, and it is on by default. Code fact (ds4_model.cu lines 1137–1143) The lookahead described on page 2 is exactly this.

Which windows use the mailbox. The mailbox is only for small windows. With a single card and DS4_SYNC unset, a window with rows ≤ DS4_ASYNC_T goes async. The default is 8, and larger windows go sync. The multi-card thread mode (--threads or tensor parallelism) ignores this value and always goes async. Code fact (ds4_model.cu line 1136, ds4_model.cu line 7787, ds4_model.cu line 9568) The number of rows in a verify window is the number of kept drafts plus 1. So with the default of 8, even the 6-row window of 5 drafts goes async. Set it to 4, and a window that keeps more than 4 drafts goes sync instead. Teaching estimate (rows = k + 1 ≤ T. T = 8: k ≤ 7, so a block size of 5 is fully inside; T = 4: k ≤ 3)

The counterexample on Strix Halo. This is a unified-memory Ryzen AI Max machine with 128 GB. On unified-memory machines, setup writes DS4_ASYNC_T=4, because the default mailbox path is slower here. Conditions: 2.00 bpw, engine 0.1.51, greedy, 256 tokens. Code answers go from 15.87–16.33 to 20.14–21.28 tokens/s (upstream writes +31%; computed from the ends of the ranges it is about +27% to +30%). The agent task goes from 15.93 to 18.48 (+16%). Chat goes from 10.33 to 11.30 (+9%). The tokens that come out are exactly the same; only the scheduling differs. Upstream report (STRIX_HALO.md lines 79–84, test_dsv41_async_t.py lines 3–5) The document's explanation is that the mailbox path was designed for machines where "the graphics card holds most of the experts". Upstream report (DEEPSEEK41.md lines 53–58) The document gives no finer reason, and this page does not guess one. Setup writes this value only for unified-memory cards. STRATA_DSV41_ASYNC_T=8 restores the default, and any other number overrides it directly. Discrete graphics cards keep the engine default of 8. Code fact (setup.py lines 8376–8388)

Compared with DeepInfer: A cluster also fears that the GPU will stop and wait for the CPU, but it waits for something else: the few milliseconds the CPU spends queuing the next step. DeepInfer's answer is to let the CPU line up the next batch one step ahead, called the zero-overhead batch scheduler. Upstream report (see DeepInfer's spec-sched page; that column was checked at a679bb86) Here the wait is for the CPU-lane experts inside the same step. The idea is the same in both places: do not let the expensive side sit idle.

5.5 Conversation parking: store a conversation, and read on when it returns

The problem. An agent with several sub-agents takes turns using the same model. Each time the turn changes, the model holds someone else's state. When the turn comes back, a prompt of tens of thousands of tokens must be read again. A comment in the engine records one set of numbers: two conversations of 70k and 185k tokens alternate, and every switch costs 75–200 s of re-reading (about 930 tokens/s). Upstream report (ds4_main.cpp lines 402–405) Let us check: Teaching estimate (70,000 ÷ 930 ≈ 75 s; 185,000 ÷ 930 ≈ 199 s) Both ends match. So 75–200 s is the cost of re-reading without parking.

How parking works. When a request arrives, the engine first checks whether it continues the current conversation (the token prefix matches and is longer). If so, it continues in place and needs no parking. If not, it first parks the current conversation, then looks among the parked conversations for one that this prompt can continue. If there is one, it takes it back. If there is none, it returns to the nearest checkpoint, or reads from the start. Code fact (ds4_main.cpp lines 795–812)

What gets parked. The position, the token list, the window ring of every layer (including the rings of the draft model's blocks), the compressor's partial group, and the compressed KV and indexer keys of every KV source. Only text conversations are parked: a conversation that contains images is not parked, and a prompt with images is not taken back either. Code fact (ds4_model.cu lines 5786–5794) For the size of the state, the document gives one number: about 17 MB for one conversation of 6.5K tokens. Upstream report (DEEPSEEK41.md lines 116–119) Teaching estimate (17 × 10⁶ ÷ 6,500 ≈ 2.6 KB per token) Extrapolate linearly from this number: Teaching estimate (70,000 × 2.6 KB ≈ 183 MB; 185,000 × 2.6 KB ≈ 484 MB) This is an upper bound, because a ring of 128 rows has a fixed size and the marginal cost per token is smaller. Take the 3.6 GB/s NVMe of the RTX 5070 machine: reading back 183 MB takes about 0.05 s. Upstream report (DEEPSEEK41.md line 63) Teaching estimate (0.183 GB ÷ 3.6 GB/s ≈ 0.05 s) That is three orders of magnitude below the 75 s of re-reading. A real take-back also has to copy the data into VRAM and write it back into each ring. The engine prints "took back a N-token conversation … (X s)" in its log. Code fact (ds4_main.cpp lines 638–642) This page has no such measured number, so it can give only a lower bound.

Even when the prompt changes, you can read less. When a client continues a conversation, it re-renders the whole history into a prompt. That prompt may not match the engine's stored token stream token for token. For example, the rendering may leave out earlier thinking text. The engine makes two preparations for this. While reading a prompt, it saves one checkpoint one token before the end of the prompt and one at the end. The prompt re-rendered in the next round will match at least the part before one of those two points. Code fact (ds4_main.cpp lines 856–857) When it takes back a parked conversation and the prompt matches only part of it, it takes back to the nearest checkpoint where the prompt still matches: the end of the prompt, the position before the end, or the anchor where this run of prompts started. Code fact (ds4_main.cpp lines 586–590) So even when the whole conversation cannot be continued, it re-reads only the part that differs.

Two tiers of storage. A conversation goes into RAM first, then spills into the folder. RAM holds at most 4 (STRATA_DS4_SLOT_CAP). Beyond that, the least recently used one is written to a file. When the engine exits, everything in RAM is written out and reused on the next start. A conversation shorter than 1024 tokens is not parked: re-reading takes about as long as taking it back, so parking is not worth it. Code fact (ds4_main.cpp lines 549–575, ds4_main.cpp lines 1025–1028, ds4_main.cpp lines 417–423) A file is written to .tmp first and then renamed. The .meta file records the model identity, the tokens and the size. Nothing is written if less than 8 GiB of space is free. Code fact (ds4_main.cpp lines 512–541)

Capacity and cleanup: the two layers have different defaults. The engine itself defaults to parking off, with a folder cap of 16 GiB. The serving layer defaults to on, sets the cap to 2 GiB, and puts the folder in ds4-slots next to the run logs. Code fact (ds4_main.cpp lines 417–423, server.py lines 3653–3667) The serving layer sets 2 GiB and turns parking on. One week is the engine's own default, and the serving layer does not set it. Over the cap, the least recently used is deleted first, and the one just written is never deleted, so even a single conversation larger than the cap is kept. Code fact (ds4_main.cpp lines 489–490) At startup the engine scans the folder and deletes anything that belongs to another model, is corrupted, or has not been used for more than 7 days. Code fact (ds4_main.cpp line 679) How much fits in 2 GiB: Teaching estimate (2 GiB ÷ 17 MB ≈ 126 conversations of 6.5K tokens; 17 MB is the document's original value)

A shared beginning. The serving layer also counts how many system or developer messages sit at the start of a request, converts that count to a token count N, and sends it to the engine as pin=N (except for requests with images). The engine saves a checkpoint at that position (at least 256 tokens). Sub-agents of the same agent use the same system prompt and tools, so they start from the checkpoint and do not need to re-read it. Code fact (server.py lines 5325–5335, ds4_main.cpp lines 868–870)

Compared with the Qwen path: The main line's checkpoint chain (Chapter 20, section 20.4) rolls back inside one session and mostly stores the fixed-size GDN "whiteboard". Its optional conversation-parking area lives only in RAM and is not concurrent (Chapter 25, section 25.1). On the DeepSeek side, the state grows with the conversation: the rings are fixed, but the compressed KV and the indexer keys keep growing. So what gets parked is the whole conversation's state, and it can also go to disk and survive a restart. Also, dsv41 handles only one request at a time. --parallel is ignored with a warning, and several people take turns on the same model by parking. Upstream report (DEEPSEEK41.md line 126) Code fact (server.py lines 985–988)
Compared with DeepInfer: The cluster puts the KV cache in a dedicated SSD cluster (3FS, about 100 PiB). It keeps Agent traffic for 3 days and chat traffic for 7 days. Upstream report (see DeepInfer's pd-kv page; that column was checked at a679bb86) One computer's 2 GiB folder with a 7-day retention is the same idea at a different scale: cache the result of the last round, and on a hit in the next round, do not recompute.

5.6 Thinking effort and tool calls: two translations in the serving layer

Thinking is on by default. The model's own template sets thinking to on. To turn it off, write reasoning_effort: "none" in the request, or chat_template_kwargs.enable_thinking: false. Upstream report (DEEPSEEK41.md lines 108–109) The switch lives in the prompt: with thinking off, the rendered prompt ends with <｜User｜>hi<｜Assistant｜></think>, which closes an empty thinking block for the model in advance. Code fact (test_dsv41.py lines 400–406)

Effort is one line written to the model. low, medium, high and max map to 50, 62, 75 and 100, and you can also pass an integer from 1 to 100 directly. Upstream report (DEEPSEEK41.md lines 108–109) These four numbers are a table in the template. When rendering, in thinking mode, the system part starts with one line: "Reasoning Effort: 75 (range 1-100, the higher the value, the more thorough the reasoning)". Code fact (chat_template.jinja lines 23–29, chat_template.jinja line 209) The serving layer's tests check this line case by case: low writes 50, medium writes 62, xhigh writes 100, passing 40 writes 40, and passing extreme returns 400. Code fact (test_dsv41.py lines 424–434) This number is only words written for the model to read. The engine receives only token ids (Code fact (ds4_main.cpp lines 9–12)), and the engine has no thinking budget. The serving layer has its own: when neither the request nor the config sets one, DeepSeek-V4.1 gets a default budget of 32,768 tokens. When the budget is reached, the serving layer forces the thinking to end and turns thinking off. Code fact (server.py line 218, server.py line 5856) reasoning_budget_tokens can change this value, and 0 means no budget. Upstream report (release-notes-0.2.4.md line 41) So the effort number does not count anything. The budget is what counts.

Default sampling. When a request sets no parameters, the temperature is 1.0 and top_p is 1.0. Upstream report (DEEPSEEK41.md line 115) So a default request is a sampling request, and verification follows the p(d) rule of section 5.3.

Tool calls: from DSML to OpenAI and Anthropic. The model writes its own tool calls in the DSML format: <｜DSML｜ calls> wraps several <｜DSML｜ invoke name="…">, and each parameter is one <｜DSML｜ parameter name="…" string="true">. The serving layer converts them into OpenAI's tool_calls and Anthropic's tool_use, including tool_choice, streamed arguments and calls written inside the thinking. Upstream report (DEEPSEEK41.md lines 112–114) The conversion is not a separate second implementation. DsmlTranslator rewrites the DSML text, as it streams, into the tool-call text that the main-line Qwen uses, and then hands it to the shared OutputParser. So the two output shapes, tool_choice, streamed arguments, and the split between thinking and answer behave the same for DeepSeek as for other models, and only one place knows "how DSML is spelled". Code fact (dsml.py lines 1–19)

Streaming details. While rewriting, only a fragment that "could still become a tag" is held back, such as < or <｜DS. All other text passes through unchanged. Code fact (dsml.py lines 39–45) When a parameter has string="true", its value stays a string, and "123" is not treated as a number. Code fact (dsml.py lines 183–197) How streaming events are cut and accumulated is in Chapter 23, section 23.5.

Two patches that 2-bit quantization left behind. First, the 2-bit file set often writes the whole answer after <think> and then stops without writing </think>. The whole text is then taken as thinking, and the answer is empty. A comment says 4 prompts out of 4 did this. When a turn ends with stop and has neither an answer nor a call, the parser hands the thinking text over as the answer. Upstream report (dsml.py lines 172–175) Second, the spelling in the template: the V4.1 model writes "<｜DSML｜ calls>" (with a space before calls), while some other packs ship the V4-Flash template, which writes "<｜DSML｜tool_calls>". The model sees one spelling in the prompt and writes the other, and only 2 of 11 tool calls became real calls. On the same pack, the comment records 0/4 versus 6/6, and the latter came after switching to the template with the space. Upstream report (dsml.py lines 226–232) So the serving layer checks the template that the pack ships, and if the spelling is wrong, it uses its own copy instead. Code fact (dsml.py lines 226–232)

Compared with the Qwen path: The main line's Qwen model writes Qwen-style call text directly, and the serving layer has only one OutputParser. On the DeepSeek side, only one translator is added at the very front, and everything after it is reused. How streamed output is accumulated by byte, by event and by JSON level is still what Chapter 23 covers. Nothing here is new.

Remember these three

  1. DSpark gives 5 drafts and 5 confidences in one block forward pass. --dspark auto does not load it when the experts are more than 1.5 times the VRAM. Two gates (a floor of 0.5 for each draft, and the running product of confidences, set to 0.5 by default only on RDNA4) trim the window. If no draft passes the gates in one round, the next round rests.
  2. The verify window has k + 1 rows and is verified in one pass. A sampling request keeps a draft with min(1, p ÷ q). The draft's q is a single point, so the probability is simply the backbone's p(d) for that token. Each round yields m + 1 tokens, and the rest is rolled back. In the window, the experts on the CPU lane go through the host-mapped mailbox. Rows ≤ DS4_ASYNC_T (default 8) go async. On Strix Halo it is switched to sync, which makes code answers about 30% faster (upstream writes 31%).
  3. Conversation parking puts the whole conversation state in RAM first (up to 4), then spills it to the ds4-slots folder: 2 GiB in the serving layer, 16 GiB by engine default, cleaned after 7 days. A conversation of 6.5K tokens takes about 17 MB, and by estimate, taking it back is faster than re-reading by several orders of magnitude. Thinking effort is one number written into the prompt, and tool calls reach the parser shared with the main line through one translator.

Common misconception: "The higher the confidence, the more likely the draft is accepted."

Confidence only decides "does this draft enter the verify window". Whether it is kept is up to the backbone: a greedy request checks whether the backbone's argmax equals the draft, and a sampling request keeps the draft by p(d). Code fact (ds4_main.cpp lines 238–244, ds4_model.cu lines 7979–7992) Confidence is the draft model's estimate about itself, and the engine uses it to save verification cost. A high value says only "worth verifying", and does not promise "will be kept". This page has no data on how it matches the true acceptance rate. The engine provides a way to measure it (--spec-eval plus DS4_ROUND_LOG), but there is no ready-made result.
