Another engine, another view

The earlier pages were about "computing": where to put the experts, how to swap attention. This page is about "looking up". The DeepSeek-V4.1-Flash files hold one very large table. The three low-bit files (1.75, 2.00 and 2.25 bits per weight, bpw) share one copy that is 111 GB. UD-Q8_K_XL brings its own copy of 203 GB. The table does no multiplication. For each token the model writes, it turns over only 48 rows: about 7 KB for the 111 GB copy, about 12.7 KB for the 203 GB copy. Yet the engine keeps a group of disk-read threads and a row cache just for those 7 KB, and it must have the rows ready before layer 1 and layer 14. After this page you can answer three questions: how one token becomes 48 row numbers; how the rows you fetch change the model's state; and whether SSD speed is limited by this table or by something else.

In one line: Engram is a hash table that is only looked up, never computed on. For each token, hashing gives 48 row numbers (24 in layer 1 and 24 in layer 14). The engine reads them from the SSD, decodes them into numbers, passes them through a gate and adds the result back to the model state. Only 7 to 12.7 KB of useful bytes are involved, so the hard part is latency: send the read request as soon as the token is known, collect the result just before it is needed, and let the disk-read threads and the row cache hide the wait. The 48 to 111 MB per token in the Mac document is almost all experts, not this table.

4.2 How one token becomes 48 row numbers

Row numbers come entirely from hashing. There is no neural network and no dictionary lookup. The algorithm lives in eg_issue and has four steps.

Step 1: turn the token id into a compressed token id. A comment in the reference implementation describes the mapping: a token goes through NFKC, NFD, accent stripping, lowercasing and whitespace merging, and tokens that look the same afterwards share one new id.Code fact (engram_hash.py lines 5–7) The engine does not do this itself; it reads a ready-made mapping table from engram.bin in the model pack.Code fact (ds4_model.cu lines 405–430) A token at an image position has no compressed id and is recorded as −1. No n-gram crosses an image, and image positions take no rows.Code fact (lines 6256–6260; line 6298)

Step 2: look back, and multiply each id by a fixed odd number. Take the current token and the few tokens before it, and multiply each id by a number: the compressed id of the s-th token back is multiplied by the s-th multiplier. At the start of the text, or at an image, the walk stops and the remaining positions use a fixed padding id.Code fact (ds4_model.cu lines 6304–6307) The multipliers form one set per layer and come with the model pack. The reference implementation generates them from a fixed seed: 10007 times the layer number, with the result forced odd.Code fact (engram_hash.py lines 82–89) So nothing here is a learned index, and the same n-gram always lands on the same row.

Step 3: XOR level by level, then take the remainder for each column. The products are XORed into one number, nearest first: XOR the first two terms to get the hash of the 2-gram, then XOR in the third term to get the hash of the 3-gram, and so on.Code fact (ds4_model.cu lines 6309–6311) Each length has several columns (heads). Each column has its own prime and start offset: row number = hash mod prime + start offset.Code fact (line 6314) The prime acts as the number of buckets. The start offset is the sum of the primes of all earlier columns in the same layer, so each column owns its own stretch of the layer's table and no two overlap.Code fact (engram_hash.py lines 73–79)

Step 4: read the file by row number. Row number times bytes per row, plus the start of the tensor, gives the position in the file. The table has rows only and no keys: the read code never compares a key.Code fact (ds4_model.cu lines 6337–6340) The row cache uses "row number × 8 + Engram layer index (0 or 1)" as its key.Code fact (line 6317) The number of columns per layer = (n-gram limit − 1) × number of heads.Code fact (line 6279) The files used for this page do not say what the limit and the head count are, so I do not report them. Only the product is certain: 24 columns per layer.

What about collisions? One row number may be shared by many n-grams. That is the price of not storing keys. Chapter 11 covers the same trade-off (Chapter 11 “Hash tables and hash functions”). Here is one more guess: the row you fetch is sometimes not the right one, so a gate follows and lets the current state decide how much to trust it.Teaching estimate

A walk-through with small numbers. The compressed ids of the last three tokens are 4, 9 and 6 (6 is the current token), the multipliers are 3, 5 and 7, and the two columns have primes 11 (start 0) and 13 (start 11). The products are 18, 45 and 28. 18 ⊕ 45 = 63, and 63 mod 11 = 8, so the first column reads row 8. 63 ⊕ 28 = 35, and 35 mod 13 = 9; add the start offset 11 and the second column reads row 20.Teaching estimate (toy numbers, same rules; Figure DS4-2 draws the same example)

If you studied CS: this is the "hashing trick" from machine learning: keys are not stored, and the row number is used directly as an array index. It differs from a hash table in that it does not handle collisions. The compressed id in step 1 works like input normalization: spellings that differ in case, accents or whitespace merge into one key and share one row. The hash function itself is in Chapter 11.

Compared with the Qwen path: The Qwen hash in Chapter 11 multiplies token ids directly. It uses the last 2 and the last 3 tokens, 8 heads each, 16 rows in all, and each head's modulus is around 20 million. DeepSeek compresses the token id first, has 24 columns per layer, and each column's prime is around 16 million (derived in the previous section); the two layers compute separately. Both sides "multiply, XOR, take the remainder", and neither stores keys. (For the Qwen side see Chapter 11, checked there)

4.3 How the 48 fetched rows change the model's state

First, turn the rows back into numbers. One IQ4_NL block is 32 numbers in 18 bytes: one fp16 scale plus 16 bytes of 4-bit codes.Code fact (ds4_model.cu lines 1089–1091) The engine dequantizes each row to F32.Code fact (line 10021) For how quantization stores and restores numbers, see Chapter 4 “Integer quantization and error”.

24 rows become one long vector, which goes through one matrix multiply. 24 × 256 = 6,144 numbers, one set per token and per Engram layer.Teaching estimate Multiply by this layer's engram.wkv matrix to get (H + 1) × D numbers.Code fact (ds4_model.cu line 10038) H is the number of streams in the model state (called hc in the code), and D is the width of each stream. The real shape given in the lab comment is H = 4 and D = 5,120.Code fact (ds4_lab.cu lines 1–3) So the output is 5 × 5,120 = 25,600 numbers.Teaching estimate

The output splits into 4 keys and 1 value. The first 4 segments each belong to one stream and are called keys. The last segment is the value, shared by all streams.Code fact (ds4_kernels.cu lines 1546–1550)

The gate decides how much each stream takes. For stream k: apply RMSNorm to the state h and to the key separately, multiply each by this stream's own weight w dimension by dimension, take the dot product, and scale by the dimension count. Take the signed square root and pass it through a sigmoid to get a gate value g between 0 and 1. Finally h ← h + g × value.Code fact (ds4_kernels.cu lines 1543–1565) w is the element-wise product of two learned vectors, q and k. Some packs have it multiplied already; for the others the engine multiplies them at load time.Code fact (ds4_model.cu lines 4343–4352; DEEPSEEK41.md line 46)

How to read the formula. The value is like a page of notes on "what usually follows these tokens", and the key is like "what kind of context this page suits". The gate compares the current state with the key: if they match, it adds more.Teaching estimate (this is a reading of the formula; the source does not explain it this way) The result is added back before attention, so this step uses no KV cache.Teaching estimate

4.4 Reading the disk: send the request when the token is known, collect it just before use

Row numbers depend only on the tokens, so the read can start early. The 48 row numbers of a token depend only on the current token and the ids of a few tokens before it. They do not depend on any earlier layer's computation. As soon as the token is known, the read request can go out; the result is collected only just before the layer that uses it.Code fact (ds4_engram_io.hpp lines 5–10) The layer 1 rows hide behind "embedding plus layer 0", and the layer 14 rows hide behind layers 0 to 13.Code fact (same file, lines 6–7) When the tokens of a window are all there, the requests for both Engram layers go out together, with layer 1 first in the queue.Code fact (ds4_model.cu lines 9720–9728; hpp lines 7–8) The time spent sending requests, plus the part not yet finished when the engine collects them, is counted in engram_ms.Code fact (lines 9741–9743)

How long a window is. In token-by-token decoding and draft verification, a window holds at most 16 tokens.Code fact (ds4_kernels.cuh line 18) In token-by-token decoding the window is 1 token: step feeds in only one token.Code fact (ds4_model.cu line 8071) The verify window of the draft model is longer, carrying n + 1 tokens at a time, and the rows go out together.Code fact (lines 7950–7960; for the draft, see page 5) The default chunked prompt takes another path: each chunk is a few hundred to a few tens of thousands of tokens, and a helper thread reads the rows one chunk ahead.Code fact (lines 6420–6424) So in token-by-token decoding, the layer 1 rows have only the short stretch of "embedding plus layer 0" to hide in. This is the tightest link.Teaching estimate (an inference from reading the comments)

Disk-read threads. The engine keeps a group of threads just for reading Engram. Each thread has its own file handle and takes work from a first-in, first-out queue.Code fact (ds4_engram_io.hpp lines 129–146) The default thread count is min(16, max(4, logical processors ÷ 2)). The Mac build fixes it at 2. The comment says the reason is "enough threads to keep the SSD queue busy", and fewer are needed when reading from the page cache.Code fact (ds4_model.cu lines 2844–2853) The more reads are in flight at once, the higher the SSD's small random read throughput (Chapter 5 “Bandwidth and latency”). On Windows each ReadFile call is synchronous, so the thread count equals the queue depth. The comment records two measurements: Project Maya, on a 20-core PC reading a 28K-token prompt, took 17.1 seconds with 10 threads and 13.4 seconds with 64 threads; Strata, on a 6-core machine, ran a 4K prompt 4.5% faster with 64 threads, and decoding did not speed up.Upstream report (lines 2847–2851)

The Mac uses only 2 threads. The comment says that with more than 2 threads, decoding the same prompt differed from the serial result in 3 to 9 of 16 runs, while 24 runs with 1 or 2 threads never differed. The cause has not been found.Upstream report (lines 2855–2856) The document says this makes the prompt 3% to 12% slower and leaves the answer speed unchanged.Upstream report (DEEPSEEK_MAC.md lines 79–81) The document does not explain why only the prompt is affected. One reasonable guess: token-by-token decoding has only 48 reads per token, which 2 threads can handle; reading a 3,000-token prompt can issue up to 3,000 × 48 = 144,000 reads, and with few threads the threads easily become the bottleneck.Teaching estimate (rows that hit the row cache need no read, so this is an upper bound)

The row cache. When the same n-gram appears again and again, its row need not be read again. The engine keeps a row cache in the process. It replaces entries with the clock algorithm: each row has a "recently used" mark that gives it a second chance.Code fact (ds4_engram_io.hpp lines 38–91) Its capacity is 1/64 of free memory, at least 16 MiB and at most 256 MiB. DS4_ENGRAM_CACHE_MB can change it, and 0 turns it off.Code fact (ds4_model.cu lines 2861–2864) Each slot stores hd + hd ÷ 32 = 264 bytes, so 256 MiB holds about 1 million rows.Teaching estimate (268,435,456 ÷ 264 ≈ 1,016,800; for the slot width see line 2846) That is only 0.13% of the whole table. It relies on repetition, not coverage.Teaching estimate A hit is a copy, not a read, and the output is exactly the same as a disk read.Code fact (hpp lines 9–10) If the same row appears twice in one window, it is read only once.Code fact (lines 6275–6276) The document gives no hit rate. When a run ends, the engine prints a line "Engram per token: …% without a read", and you can look at it yourself.Code fact (ds4_main.cpp lines 1574–1581)

Which path the read takes. The default is a buffered read: pread on the file, through the operating system's page cache.Code fact (ds4_engram_io.hpp lines 235–254) A direct read that bypasses the page cache exists only on Windows. It needs DS4_EG_DIRECT=1 and is off by default; the comment records that it made a 4K prompt 8% slower.Upstream report (ds4_model.cu lines 2867–2873)

Another point: Engram's pages share the page cache with experts that are read in place. A source comment says that copying experts into the engine's own memory means "the page cache is not lost to Engram table and file churn".Code fact (ds4_model.cu lines 5340–5341; for how experts are tiered, see page 2)

One last point: if a row cannot be read, the engine does not crash. It treats that row as zero.Code fact (ds4_model.cu line 6388) So when disk reads go wrong, the symptom may be answers that quietly get worse, not an error. The Mac build prints a warning line to stderr; other builds do not.Teaching estimate

If you studied CS: splitting "send the request" and "collect the result" into two calls is the future in asynchronous I/O: you get a ticket first and wait only when you need the result. You can estimate the queue depth with Little's law: reads in flight = throughput × latency of one read. So small random reads get their concurrency from many threads, not from a faster single read (Chapter 14 “Synchronous and asynchronous”, Chapter 6 “Files, memory mapping and the page cache”).

Compared with the Qwen path: The main-line PLE reads in almost the opposite way. By default it reads directly and bypasses the page cache; its row cache is 8-way set associative, 1,048,576 rows of 90 bytes each, about 94 MB. DeepSeek reads buffered by default and shares the page cache with the experts; its row cache is clock plus second chance, with a cap of 256 MB. The main-line table is used in one layer only, so it has just one window to hide in, "embedding plus layer 0"; here the second window (layers 0 to 13) is much roomier.Teaching estimate (for the Qwen side see Chapter 11 “Direct-mapped, set-associative, fully associative”, checked there)

4.5 Where SSD speed really limits you

The document gives a total, not an Engram account. The table in the Mac document has a row "Read from the SSD per word": 48 MB for the 2.00 bundle and 111 MB for the 2.25 bundle.Upstream report (DEEPSEEK_MAC.md line 50; conditions: M5 Max 128 GB, the 0.2.7.1 packaged engine, two Engram read threads; during the measurement an idle 60 GB Qwen service also shared the file cache, see lines 35–39) The document does not say which counter measured that row. The closest one in the engine is disk_mb: how many bytes this process made the storage device read, including experts read in place; on a Mac, reads that hit the page cache do not count.Code fact (ds4_main.cpp lines 62–85; lines 954–957) Treating the row in the document as this kind of counter is my inference.Teaching estimate

How much of it is Engram. Each token takes 48 rows, and each row costs at least one page. With 4 KiB pages that is usually 48 × 4 KiB = 192 KiB, about 0.2 MB, with an extra page now and then when a row crosses a page boundary. Apple chips use 16 KiB pages, so about 48 × 16 KiB = 768 KiB, about 0.8 MB.Teaching estimate (the bigger the page, the more a small read is amplified; a 144-byte row rarely crosses a page) Against 48 MB and 111 MB, Engram is about 1.6% and 0.7%. There is also a cleaner argument: both bundles use the same table.Upstream report (DEEPSEEK41.md line 39) The 111 − 48 = 63 MB difference comes essentially from experts (Engram's share of the difference is only about 0.8 MB).Teaching estimate

So on a Mac, when "a slow SSD drags down every token", it is mostly the experts that it drags. The document says the same: a decoded token is limited by these SSD reads and by a CPU lane that computes the experts that did not fit on the GPU, not by the GPU.Upstream report (DEEPSEEK_MAC.md lines 57–62) For how experts are tiered across VRAM, RAM and SSD, see page 2.

Then why does Engram still need threads and a cache? Because it needs latency, not bandwidth. 48 small random reads must be back before layer 1 and layer 14. The repository's disk-read benchmark script says so too (translated): gathering 48 rows per token over 110 GB is random, and IOPS matter as much as MB/s.Code fact (engram_iq4nl_bench.py line 45) The time to finish reading is roughly ⌈rows ÷ threads⌉ × latency of one random read.Teaching estimate (a teaching model) Assume 100 microseconds per read and 4 threads: ⌈48 ÷ 4⌉ × 100 µs = 1.2 ms. At 15 tokens per second, one token takes about 67 ms, which spread over 40 layers is about 1.7 ms per layer.Teaching estimate (1000 ÷ 15 ≈ 67; 67 ÷ 40 ≈ 1.7) The two numbers are of the same order, which is why layer 1 rows go first in the queue. The model has a flaw: the Mac uses only 2 threads, so it would predict that answer speed suffers, yet the document says it does not. So real latency is shorter, or the cache hits a lot. It only shows the order of magnitude.

Turn read speed into a token-rate bound. How many MB each token must read depends on the model pack and on memory; how many MB per second can be read depends on the disk. Bound = read speed ÷ MB per token. The figure below draws the two lines together: the horizontal axis is SSD read speed and the vertical axis is the token-rate bound. The interactive version lets you drag the read speed and the MB per token. The document does not say which speeds that row corresponds to; the figure takes the short-answer values from the code hints.

Three reminders for reading this figure. First, it is an upper bound, and real speed is lower: the experts still have to be computed on the CPU.Upstream report (DEEPSEEK_MAC.md lines 57–62) The document does not give this Mac's disk speed. If it also had 3.6 GB/s, both dots would sit far below the bound, which shows that token rate is not decided by read speed alone. Second, take the read speed "for your way of reading": experts are read in large blocks, close to sequential reads; Engram does small random reads, with much lower throughput.Teaching estimate Third, MB per token is not a constant: with more RAM, more experts stay resident and disk reads drop.Upstream report (same, lines 57–59) The 3.6 GB/s comes from a 5070 machine in the document (12 GB VRAM, 64 GB RAM). Measure it on your own machine. Every 8 tokens the engine sends the monitor a STAT line containing disk_mb (MB read from disk per token) and engram_ms (milliseconds per token spent sending Engram requests plus waiting for reads to finish).Code fact (ds4_main.cpp lines 937–957; line 976) When a command-line run ends, it prints "Engram per token" and "decode reads from the disk: N MB a token".Code fact (lines 1574–1584) Upstream has not published measured values for these numbers, and neither does this page. Compared with DeepInfer: The DeepInfer pages checked so far do not discuss this table, so this page does not answer "where would it live" for a cluster. Something else can be compared: a cluster also uses an SSD tier, but it holds the KV cache, not the model's parameters (see DeepInfer page 3, checked at 774ce244). A single computer keeps the table on the SSD because 111 GB is more than an ordinary machine's RAM; the GPU receives only the few rows that were read. What it reads is the model's own weights.

Remember these three

  1. Engram is a hash table of about 768 million rows, with one copy for each of two layers. Each token uses multiply, XOR and remainder to get 48 row numbers; a row is 144 bytes, about 7 KB in all. The table holds no keys and collisions are allowed. The fetched rows go through a gate and are added back to the state.
  2. The hard part is latency, not bandwidth. Row numbers depend only on the tokens, so the read request goes out as soon as the token is known and the result is collected just before use; disk-read threads, the row cache and the page cache together hide the wait. For stable results the Mac uses only 2 threads, at the cost of a prompt that is 3% to 12% slower.
  3. The 48 MB and 111 MB per token in the Mac document are almost all experts; Engram is about 1.6%. Token-rate bound = SSD read speed ÷ MB per token. Using the midpoints of the short-answer code hints, the Mac's token rate needs only 0.75 to 1.67 GB/s of read speed (15.6 × 48, 15.0 × 111; teaching estimate).

Common misconception: "Engram is 111 GB, so it eats the SSD's bandwidth."

A big table and a lot of reading are two different things. A token turns over only 48 rows, about 7 KB; even if every row read a whole page, it would be under 1 MB. In the Mac document, the 48 MB and 111 MB per token come from two bundles that use the same table, and the 63 MB gap comes essentially from experts (Engram's part of the gap cannot exceed 0.8 MB).Teaching estimate (the arithmetic is in section 4.5) What Engram needs is low latency and enough concurrent reads, not bandwidth. Put the model files on a slow disk and both kinds of reads slow down, but what slows down is mostly the experts.

Where the document, the comments and the code disagree, the code wins. ① The top of engram_iq4nl_bench.py says "random 2.3 KB row reads" (line 7), which does not match the 144 bytes above. The file calls itself a "Phase 1.3 skeleton" and says the row width comes from the GGUF header ("nothing is hardcoded here"). This page goes by hd = 256 in the lab and by the prime-sum check. The same file also mentions O_DIRECT: the table does not fit in memory, so it skips the page cache. That was the idea at the time; the current engine reads buffered by default, and direct reads are only an option on Windows. ② DEEPSEEK41.md line 17 says "the table is read from the SSD", and line 39 says "read from memory or SSD". The two do not conflict: a page that is in the page cache is read from memory.

What was not checked. ① How the 24 columns split into n-gram lengths times heads: that is only in the packed file, and the files used here do not say. ② That there are exactly two Engram layers: the comment at ds4_model.cu line 6, the "two Engram tables" in DEEPSEEK41.md line 46, and the assumption "24 columns in each of two layers" behind the prime sum all agree, but I did not read the header of a model pack. ③ The counter behind the "read the SSD per token" row of the Mac document: this page infers disk_mb from its type. ④ Engram's hit rate and measured engram_ms: upstream has not published them, and this page has none. ⑤ Why results differ with more threads on a Mac: the code comment and the document both say "not found yet", and this page does not guess. ⑥ The 100 µs single-read latency is an assumed value, not a measurement.
