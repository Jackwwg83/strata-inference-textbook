A different engine

For the first 28 chapters, Strata ran the mainline model Qwen3.8-Flash-Next on one computer. Since v0.2.4 it can also run DeepSeek-V4.1-Flash on the same kind of computer. It does this through a newly ported engine path, strata-dsv41 (a CMake comment calls it the third engine path; it shares no symbols with the mainline kernels). The port comes from maya-ds4 in the open-source Project Maya. This page lays the foundation: where the engine comes from, where the 500 GB of files go, and under what conditions the measured speeds were taken. Every page in this column follows one question: on what machine was this number measured?

In one line: strata-dsv41 is the third engine path: a standalone executable that shares no symbols with the Qwen kernels and serves one request at a time through one pipe. One computer stores the experts in tiers. The Engram table of the UD set sits on the SSD, and the 111 GB table of the 2-bit sets is read from RAM or the SSD. Every number on this page carries its measurement conditions (machine, file set, version, default parameters). When you move a number, move its conditions with it.

1.1 Another engine: a piece of code ported from Maya

This is a port, not a rewrite, and it does not share kernels. A CMake comment in Strata calls src/dsv41 "the third engine path (…from Project Maya's maya-ds4, MIT, third_party/project-maya)". It has its own kernel library, strata_dsv41_kernels, and its own executable, strata-dsv41. It shares no symbol with the mainline strata_kernels. The comment says so in these words: "no symbol is shared with strata_kernels". The build option STRATA_BUILD_DSV41 is OFF by default. Code fact (CMakeLists.txt, lines 906–920)

The desktop app and the command line both install this engine: the Terminal from 0.2.4, the desktop app from 0.2.5. Upstream report (AI_REFERENCE.md, line 32) One protocol adapter layer, and each side runs its own engine. The server-side StrataEngine wrapper class starts the resident engine (one strata --serve process). By default it handles one request at a time (batch=0), because dsv41 has no batch slots. Code fact (server.py, line 985, line 997, runner.py, line 1496, line 1503) On the engine side, the pipe protocol is the same one: INFO lines report status, READY reports the context length, GEN/GENI come in, STOP and QUIT control, and requests are split by command line. Code fact (ds4_main.cpp, lines 9–13, line 391, lines 741–750) The protocol has the same shape, but what is inside the shape differs: this model has its own tokenizer, its own template and its own DSML tool-call format. Page 5 covers the details (conversation state on disk).

One kernel-launch syntax spans CUDA and Metal: CUDA's triple-angle-bracket call is mapped to a Metal dispatch (Chapter 22, “Portability”). Code fact (ds4_launch.h, lines 1–3) From 0.2.7, the packaged engine carries three kinds of NVIDIA machine code: sm_86, sm_89 and sm_120. (Before that, RTX 40 series cards ran the sm_86 code through CUDA's same-generation rule.) Upstream report (DEEPSEEK41.md, lines 67–68) The Strix Halo integrated GPU is tested on Windows (gfx1151). Upstream report (AI_REFERENCE.md, line 32) Line 32 of AI_REFERENCE also says “Not on Mac, Intel Arc or Strix Halo on Linux yet” and “8K context”. Two of these claims are out of date: the Mac has its own document and measurements (text mode), and 8,192 is only the default context, which --context can raise to 1M. All Strix Halo measurements were taken on Windows, so the sentence “not on Linux yet” has not been disproved. This page follows the code and the body of the documents.

If you studied CS: think of a JDBC-style interface layer that puts two database engines behind one client. StrataEngine starts the resident process, queues requests and parses the output lines. The queue handles one request at a time by default (batch=0), and dsv41 has no batch slots to fill. What is unified is the shape of the protocol, not the insides of the two engines (Chapter 25).

1.2 Model shape and packaging layout: 500 GB and 257 GB are different accounts

Model shape. DeepSeek-V4.1-Flash is a mixture-of-experts model with 40 layers and 384 experts per layer. It uses 6 experts to write each token. Beside the experts sits a 203 GB n-gram lookup table. Upstream report (DEEPSEEK41.md, lines 3–4) 40 × 384 = 15,360 experts, which matches the "routed experts (15,360 of 18.8 MB)" in the placement table of the document. Teaching estimate The cluster-side check table says "384 routed experts plus 1 shared expert, 6 chosen per token" (DeepInfer column overview).

The book's mainline takes another route: Qwen3.8-Flash-Next has 48 layers, 512 routed experts plus 1 shared expert, and 10 chosen per token (Chapter 10; compare the model row of the DeepInfer column overview).

The default context is 8,192 tokens. This is the length used when the engine was tested. The model natively reads 1,048,576 positions, --context takes 8K to 1M, and nothing above 256K has been tested. Upstream report (line 93, line 96) AI_REFERENCE says "8K context". Read it as a ceiling and you will be wrong: the default length and the upper limit are two different things.

Packaging layout. The model list in setup.py names six file sets: three IST-DAS 2-bit sets (IQ1_M at 1.75 bpw, IQ2_XXS at 2.00 bpw, IQ2_XS at 2.25 bpw), Unsloth's UD-Q8_K_XL, and two low-bit Unsloth packs, UD-IQ1_S and UD-IQ1_M. Nobody has compared the last two with the original for quality. The notes in setup.py advise choosing 2.00 or 2.25 if you can install them. Short answers, code and tool calls look fine; long, detailed work is weaker. Code fact (setup.py, line 798, lines 836–854)

The two packaging layouts add up differently. UD-Q8_K_XL is one self-contained file set: 288.8 GB of experts in MXFP4, the other 16.8 GB in BF16, plus a 202.8 GB Engram lookup table. 288.8 + 16.8 + 202.8 = 508.4, which is exactly the sum of the 9 shards, and is the 508 GB tier in the documents (this page calls it 500 GB for short). Teaching estimate Each of the three 2-bit sets brings its own 4 model shards (121 / 138 / 155 GB). All three share one 111 GB IQ4_NL Engram table and an 8 GB DSpark draft model. The 2.00 set takes 138 + 111 + 8 = 257 GB of disk in total, the 2.25 set takes 274 GB, the 1.75 set takes 239 GB, and installing all three takes 533 GB. The 239 in the document is a rounded total; adding the rounded values 121 + 111 + 8 gives 240. Upstream report (lines 29–31) In the GGUF layout the Engram is a single file: setup.py records 110,595,290,816 B (110.6 GB, which the document writes as about 111 GB). The 202.8 GB table of the UD set and the 4-bit IQ4_NL table (111 GB) shared by the IST-DAS sets are two different files. The documents do not say why they differ so much in size.

1.3 Three-tier placement: what goes in VRAM, RAM and the SSD

First remember three words: VRAM, RAM, SSD. One computer puts the experts into three tiers, from fast to slow. If an expert fits in VRAM, it goes there. The rest are computed in place on the CPU, read straight from the model file. The Engram lookup table of the UD set sits entirely on the SSD. The 111 GB table of the 2-bit sets is read from RAM or the SSD. The table does not count toward RAM, but every token written reads a few rows of it.

Where the 500 GB set (UD-Q8_K_XL, 508.4 GB) goes. The measured machine is 4× R9700 (32 GB per card, 128 GB of VRAM in total) plus 251 GB of RAM. The placement result: 6,197 experts (116.5 GB) sit in VRAM and 9,163 (172.3 GB) sit on the CPU side. 116.5 + 172.3 = 288.8, exactly the total size of the experts, so every expert is either in VRAM or read in place on the CPU side. The other dense weights (attention and so on) take 16.8 GB, about 3.9 GB on each of the four cards (on a one-card machine all 16 GB go on that one card). The 202.8 GB Engram table sits on the SSD. Upstream report (DEEPSEEK41.md, lines 15–21) 16.8 + 202.8 + 288.8 = 508.4: the sum matches exactly, and the 500 GB account balances. Teaching estimate 4× R9700 is a multi-card path that starts at 2 cards (Chapter 21). Count the 251 GB of RAM as a number from the placement table, not as a "requirement". Still, the 172.3 GB on the CPU side needs about the same amount of free RAM to stay cached. With less RAM, these experts are read from the SSD instead, and speed drops.

Where the 257 GB set (2.00 set) goes. On the Ryzen AI Max "Strix Halo" with 128 GB of unified memory, under the default Faster profile, VRAM and the CPU share one memory pool. About 109 GB of the experts of the 2.00 set stay in memory. The 128 GB unified pool is a 64 GB BIOS reservation plus the 64 GB that Windows sees, and the engine counts it only once. From the pool it subtracts only the dense weights and 12 GB left for Windows and the desktop. About 109 GB remain for experts. The other 23 GB of experts are read straight from the SSD. Upstream report (lines 51–55)

The Mac side. On an M5 Max with 128 GB, a 128 GB Mac keeps about 68 GB of experts in memory. This share is not decided by "how much memory is left at that moment". It is decided by the total memory: subtract 40%, then subtract the memory the engine itself takes. Upstream report (DEEPSEEK_MAC.md, line 57) Check: 128 × 60% = 76.8 GB; after the engine footprint, 68 GB is in the right range. Teaching estimate A Mac needs at least 64 GB of memory and 260–280 GB of free disk, and the disk must be fast (257 GB for the 2.00 set; 274 GB for the 2.25 set; the two share the one 111 GB table). Upstream report (line 7, lines 41–49)

If you studied CS: this three-tier placement replays the memory hierarchy: VRAM ≈ cache, RAM ≈ main memory, SSD ≈ swap space. Fetching experts on demand is like demand paging, and hot experts are like a working set. Getting "how much stays resident, how much is read from disk" right means balancing two bandwidths. For the comparison, read Chapter 12, “The expert cache” and Chapter 13, “CPU + GPU”. The moving itself uses pinned memory and DMA, see Chapter 14. Strata already did the same tiering on the Qwen mainline. The difference is that DeepSeek scales the account up to 288.8 GB of experts and a lookup table of about 100 GB.

Compared with the Qwen path: The mainline Qwen3.8-Flash-Next is also "tiered experts plus table lookup", with smaller experts and a thinner table. If you map this page's three tiers straight onto the mainline, you miss the differences in placement and bandwidth that come from the number of DeepSeek experts. Page 2 goes into this.

What this computer cannot do yet. It handles one request at a time (on any machine --parallel is ignored with a warning). On the Mac, image input is off: DeepSeek's image reader has never run on the Metal engine, so the Mac reads text only, and the 319 MiB vision tower bundled with the desktop engine takes no part Upstream report (DEEPSEEK_MAC.md L18, DEEPSEEK41.md L121). On the Mac, DSpark is off: the answers are the same and there is no speedup Upstream report (L74). Contexts above 32K have not been tested on the Mac Upstream report (L75). On the PC side, machines with under 40 GB of RAM have not been tested; setup warns but still installs Upstream report (DEEPSEEK41.md L65).

If you studied CS: this comparison is close to an embedded database against a database cluster. One computer is like single-connection SQLite running inside the application process, one query at a time. The cluster is like a full database stack with a load balancer and a shared storage layer, "spreading" bandwidth and latency over dozens of cards. One saves the cost of moving data. The other buys a higher concurrency ceiling.

  • Page 4, The Engram big table: how the 111 GB IQ4_NL table is read directly token by token, the read threads, and slow disks. Read first Chapter 11, “PLE and n-grams” and Chapter 6, “Model loading”.
  • Page 5, DSpark and verification: the draft model, the verify window and DS4_ASYNC_T, conversation parking, DSML tool calls. Read first Chapter 18, “Speculative decoding” and Chapter 23, “From tokens to an API”.

Remember these three

  1. strata-dsv41 is a third engine path ported from Project Maya: a standalone executable, sharing no symbols with the mainline kernels, one request at a time through one pipe (--parallel is ignored, and there are no batch slots).
  2. One computer puts the experts in three tiers: VRAM → RAM (including the hot-expert profile, see page 2) → direct SSD reads. The Engram table does not count toward RAM. On the Mac, measured reads from the SSD total 48 MB (2.00) / 111 MB (2.25) per token written, and this includes the experts that sit on the SSD, not only the Engram.
  3. Never move speed and quality numbers away from their conditions: machine, file set, context, version and default parameters are all required. Before comparing across machines or versions, go back to the table in 1.4 and check the conditions.

Common misconception: "A 500 GB file needs a 500 GB computer."

File size is not a memory requirement. The 4× R9700 machine runs the 508.4 GB UD set with 251 GB of RAM: 116.5 GB in VRAM, 172.3 GB on the CPU side, and the 202.8 GB Engram table read directly from the SSD. A 128 GB Mac keeps only about 68 GB of experts in memory, and the rest are read from disk per token.
