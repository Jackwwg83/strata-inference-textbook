Quizá lo hayas notado

Si le das un documento largo a una IA de chat, la primera pregunta tarda un poco en empezar a responderse. Si sigues preguntando, la respuesta aparece casi al instante. El capítulo 20 explicó el truco de Strata: guarda como checkpoint el prefijo que ya leyó, en la RAM de tu propia computadora, y la próxima vez solo lee la parte nueva.

El servicio en línea de DeepSeek recibe incontables preguntas de seguimiento como esta cada día. Convirtió la misma idea en un sistema de clúster: leer el prompt y escribir la respuesta se reparten entre dos grupos de GPU, y la caché KV va a un clúster de SSD dedicado que la conserva 72 horas o más. Esta página responde tres preguntas. ¿Por qué separar las dos fases? ¿Dónde vive la caché KV? Tras un acierto, ¿cómo se retoma el trabajo, y cómo se recalcula menos cuando casi hubo acierto?

En una línea: El prefill consume cómputo y el decode consume ancho de banda, y en un mismo grupo de GPU se frenan entre sí. Por eso DeepSeek despliega por separado el codificador visual, el prefill y el decode. La caché KV vive en un clúster de almacenamiento 3FS dedicado y, si hay acierto, se lee de vuelta. Si falta el pequeño bloque de la ventana deslizante, solo se recalculan 128 tokens. El DeepInfer de código abierto trae los roles de motor y la disposición de caché que necesitan estas técnicas. No publica el código que une el sistema de caché KV con el despliegue desagregado.

3.1 Leer el prompt y escribir la respuesta: por qué van en dos grupos de GPU

El capítulo 16 explicó que una solicitud tiene dos fases. El prefill es «leer el prompt»: todos los tokens del prompt ya se conocen, se calculan miles a la vez, los pesos se leen una vez para todo el bloque y el cuello de botella es el cómputo. El decode es «escribir la respuesta»: en cada paso cada solicitud añade solo unos pocos tokens (DeepInfer usa decodificación especulativa; en las gráficas de velocidad son unos 3 por paso), pero cada paso debe leer los pesos y la caché KV una vez, así que el cuello de botella es el ancho de banda. Las dos fases quedan en lugares distintos del modelo Roofline. Mira el capítulo 5 «Cómputo y Roofline» y el capítulo 16 «Batching».

El usuario también nota dos métricas. El tiempo hasta el primer token (TTFT) es lo que pasa desde que envía la solicitud hasta que ve la primera palabra, y casi todo se gasta en el prefill. El tiempo entre tokens (TBT) es el intervalo entre dos tokens vecinos después de eso. Depende de lo rápido que sea cada paso de decode y de si algo lo interrumpe.

El problema aparece cuando las dos fases comparten el mismo grupo de GPU. El código abierto de DeepInfer trae justo ese motor «mixto», y su planificación es la mejor forma de ver el problema. Hecho de código El motor tiene tres roles: NORMAL hace las dos fases, PROMPT solo prefill y COMPLETION solo decode (engine_type.py). En cada paso, un motor NORMAL hace prefill en todo el grupo o decode en todo el grupo. Las GPU de un mismo grupo de paralelismo de datos (DP) deben hacer el mismo tipo de trabajo, y una votación las pone de acuerdo (scheduler.hpp). Por defecto, el punto de votación llega una vez cada 70 pasos de decode, y el prefill se ejecuta solo si todos los rank tienen trabajo de prefill. Hay además un punto de respaldo cada 100 pasos, donde el prefill se ejecuta si cualquier rank tiene trabajo (environ.py).

Con esta planificación, mientras corre un paso de prefill, el decode de todos los usuarios de ese grupo se detiene tanto como dure ese paso. La línea de tiempo de abajo pone los dos despliegues lado a lado. Las duraciones de los pasos salen de dos gráficas de velocidad del README de DeepInfer: un paso de prefill de 32.768 tokens tarda unos 376 ms y un paso de decode unos 13 ms. Estimación didáctica Las dos gráficas usan hardware distinto, así que solo tomamos prestado su orden de magnitud. Las condiciones están en «Más a fondo», al final.

La figura muestra dos cosas. Primero, con el despliegue mixto el intervalo entre pasos de decode a veces salta de 13 ms a 389 ms, y quien está leyendo la respuesta nota un tropiezo. La decodificación especulativa saca unos 3 tokens por paso, así que el promedio es de unos 4 ms por token y los tokens llegan a ráfagas. Aquí usamos el intervalo entre pasos para representar el TBT. Segundo, para parar menos veces, el motor mixto acumula trabajo de prefill, así que una solicitud nueva espera al siguiente punto de votación y el TTFT empeora. El motor mixto real es algo peor: justo después de un paso de prefill, el siguiente paso puede caer en un punto de votación y, si todos los rank aún tienen trabajo, el prefill continúa (scheduler.hpp). Hecho de código

Por eso el sistema de producción de DeepSeek despliega por separado el codificador visual (VE), el prefill y el decode, cada uno en sus propias GPU. Esto se llama desagregación E/P/D. El documento Q&A dice que tras la separación cada fase recibe sus propios recursos, de modo que el TTFT y el TBT se controlan y se optimizan por separado (documento Q&A). Informe upstream En el código abierto, un motor PROMPT debe «enviar» el prompt terminado «al completion engine», pero esa función está vacía (llm_engine.py). Hecho de código El README también dice que el despliegue desagregado no forma parte de esta versión, y solo que «la mayoría de las funciones de motor que necesita ya están implementadas» (README). Informe upstream

Si estudiaste informática: Es el viejo problema de las clases de sistemas operativos: las tareas interactivas y las de lotes se pelean por la misma CPU. Cuando un trabajo largo ocupa el procesador, la respuesta de las tareas cortas se alarga. El capítulo 25 lo llama efecto convoy y lo mostró con FIFO y round-robin (capítulo 25 «Algoritmos de planificación»). La desagregación equivale a darle a cada tipo de tarea su propia máquina. El mundo académico plantea el mismo argumento; mira el artículo de DistServe.

Frente a Strata: Strata corre en una sola computadora, así que leer el prompt y escribir la respuesta deben turnarse la misma GPU. En la tabla de velocidades del capítulo 16, la RTX 5070 lee un prompt de 32K a 2171 tokens por segundo y escribe la respuesta a 81,8 tokens por segundo Informe upstream. Por defecto, el servidor atiende una sola conversación a la vez (capítulo 17). Con un solo usuario, mientras se lee el prompt nadie espera el decode, así que separar no tiene sentido. En un clúster, el prefill de un prompt largo detendría el decode de cientos de usuarios del mismo grupo, y por eso hay que separar.

3.3 Dónde vive la caché KV: memoria de la GPU, RAM local, 3FS

El tercer objetivo que DeepSeek fijó para este sistema de inferencia es conservar la caché KV 72 horas o más. Una ventana más larga significa que quien vuelve al día siguiente con una pregunta de seguimiento sigue obteniendo aciertos, y se ahorra un prefill repetido. El costo es que hay que guardar mucho y administrar mucho (documento Q&A). Informe upstream El KV se reparte en tres lugares. La figura D3-3 los dibuja según la tabla del documento Q&A (tabla).

¿Por qué usar un clúster de almacenamiento dedicado en vez de la RAM y el disco de cada máquina? El documento Q&A da tres razones (documento Q&A). Informe upstream

  • Cualquier máquina de prefill puede acertar con cualquier prefijo. El balanceador de carga solo mira qué máquina está libre y no tiene que preocuparse de «en qué máquina está la caché de este usuario». Por eso el balanceo de carga del prefill tampoco hace enrutamiento por afinidad de prefijo (documento Q&A).
  • Los nodos de almacenamiento y los de cómputo pueden escalar por separado.
  • Si un nodo de cómputo se rompe, la caché KV no se pierde. Los nodos de cómputo fallan más de diez veces con más frecuencia que los de almacenamiento.

El KV que se produce durante el decode también se escribe en disco, para subir la tasa de aciertos (documento Q&A). Informe upstream La razón es simple: la respuesta que se escribe en esta ronda es el prefijo del prompt de la siguiente.

El servidor de almacenamiento recomendado tiene 20 SSD de 30,73 TB cada uno. Cada servidor debe ofrecer al menos 40 GB/s de lectura y 5 GB/s de escritura, la capacidad total debe alcanzar para 24 horas de datos, y el número de servidores crece con el tamaño del despliegue de inferencia. En tamaño lógico, cada GPU de inferencia en línea corresponde a unos 14,4 TB de almacenamiento, y la capacidad física necesaria es mayor (documento Q&A). Informe upstream

Hagamos una cuenta aproximada con estos números. La capacidad bruta de un servidor de almacenamiento es 20 × 30,73 ≈ 615 TB. El código de borrado 10 + 2 hace que el espacio físico sea 1,2 veces los datos lógicos, así que al dividir entre 1,2 salen unos 512 TB, que alcanzan para los datos lógicos de unas 512 ÷ 14,4 ≈ 36 GPU en línea. De esas 36 GPU, más o menos la mitad hace prefill y la otra mitad decode. Las GPU de decode no leen prefijos del almacenamiento, porque las GPU de prefill les envían su KV. Así que las que de verdad leen son unas 18 GPU de prefill, y si leen a la vez cada una recibe unos 40 ÷ 18 ≈ 2,2 GB/s. Estimación didáctica Es solo una cota inferior aproximada para dimensionar máquinas por capacidad. El documento Q&A no da una proporción entre servidores de almacenamiento y GPU, y una lectura se reparte entre muchos nodos de un grupo de borrado. La figura interactiva de la sección 3.5 vuelve a usar este número.

3FS es el sistema de archivos distribuido propio de DeepSeek (el repositorio de 3FS en GitHub). Debe mantener alta disponibilidad y alto rendimiento aunque fallen nodos y la red tenga fluctuaciones. Los datos se guardan con un código de borrado 10 + 2, así que cada grupo de borrado puede perder dos nodos a la vez. Según el texto del Q&A, una lectura envía solicitudes a 11 nodos del grupo al mismo tiempo (un grupo tiene 10 + 2 = 12 bloques), y bastan 10 respuestas cualesquiera para reconstruir los datos. Cada nodo de almacenamiento ejecuta un proceso de recolección (GC Worker) que limpia periódicamente la caché vieja por orden de menos recientemente usado (LRU) y mantiene el uso del disco por debajo de una marca de agua (documento Q&A). Informe upstream

Código de borrado: guarda unos bloques de control de más y los datos vuelven aunque se pierdan varios bloques

La forma más simple de no perder datos es guardar tres copias. Si fallan dos, queda una, pero cuesta el triple de espacio. Un código de borrado es más barato: corta los datos en k bloques, calcula m bloques de control y guarda k + m bloques en máquinas distintas. Mientras sobrevivan k bloques cualesquiera, se pueden volver a calcular los datos originales.

Definición: un código de borrado (k + m) tolera la pérdida simultánea de cualquier m bloques, y su sobrecosto de espacio es (k + m) ÷ k veces. Una construcción común es el código de Reed-Solomon. Trata los datos como valores de un polinomio, y los valores perdidos se recuperan por interpolación a partir de los puntos que quedan.

Un número concreto: 3FS guarda la caché KV con 10 + 2. Usa solo un 20% más de espacio, y perder dos nodos cualesquiera no pierde datos. Tres copias cuestan un 200% más y también soportan solo dos fallos. El precio es que cada lectura y escritura debe calcular el código, y una lectura debe reunir 10 bloques.

Su relación con esta página: una caché KV rota se puede recalcular, así que parece que no vale tanto cuidado. Pero debe aguantar de 3 a 7 días y unos 100 PiB, y el fallo de un solo nodo haría perder los aciertos de miles y miles de usuarios. El código de borrado permite que estos «datos recalculables» compren más disponibilidad con menos espacio.

Lecturas adicionales: Wikipedia: Reed-Solomon · Wikipedia: RAID · Wikipedia: Erasure code

La capa kvcache-store no tiene lógica de expiración; la reclamación depende por completo del GC propio de 3FS. 3FS ofrece unos 100 PiB de SSD para la caché KV. El tiempo de retención (TTL) es de 3 días para el tráfico de agentes y de 7 días para el tráfico de chat. El tráfico de chat tiene una cola larga más pesada, con una pequeña cantidad de KV leída muchas veces. Por experiencia, darle al tráfico de chat solo 3 días de TTL bajaría su tasa de aciertos entre un 0,5% y un 1% (documento Q&A). Informe upstream Es justo la tasa de aciertos y el conjunto de trabajo del capítulo 12: cuánto tiempo atrás cuenta todavía un acceso decide qué tan grande debe ser la caché (capítulo 12 «Tasa de aciertos y conjunto de trabajo»).

Si estudiaste informática: Un código de borrado 10 + 2 sigue la misma idea que RAID 6: guarda dos bloques de control de más y puedes recuperar dos bloques perdidos cualesquiera. «Enviar 11 solicitudes y decodificar cuando lleguen 10» es una lectura redundante: se envía una solicitud de más, se toman las primeras 10 que vuelven y no se espera a la más lenta. Así se recorta la latencia de la cola larga.

Frente a Strata: La caché KV de Strata también tiene niveles: normalmente está en la memoria de la GPU, y cuando el contexto pasa de 64K, el KV completo va a la RAM y la memoria de la GPU conserva solo las páginas calientes (capítulo 17 «La caché KV y la gestión por páginas»). Los checkpoints para reutilizar prefijos también están en la RAM local, de unos 118 MB cada uno, y se conservan como máximo 6 (capítulo 20). Una computadora atiende a una persona, y la siguiente pregunta vuelve a caer en la misma máquina, así que la RAM local basta. En DeepSeek, la siguiente solicitud de un usuario puede caer en cualquier máquina de prefill, y el KV debe conservarse de 3 a 7 días. Por eso solo cabe en un almacenamiento compartido al que todos lleguen.

3.4 Dos tipos de KV: KV por bloques paginado y estado SWA de tamaño fijo

La atención de V4.1 Flash tiene dos tipos de memoria. Una crece a medida que crece la conversación, como en el capítulo 17, y se administra con paginación. Se llama KV por bloques. La otra recuerda solo el tramo más reciente, y se llama estado SWA. La atención de ventana deslizante (SWA) es una forma simplificada de atención: cada token mira solo un tramo reciente anterior a él y no mira fuera de la ventana (sobre la atención en sí, mira el capítulo 8 «El mecanismo de atención»). La ventana de V4.1 es de 128 tokens (documento Q&A). Informe upstream El tamaño de la ventana sale del archivo de configuración del modelo (config.py), y ese archivo no está en el repositorio de código.

DeepInfer administra los dos tipos de memoria con dos asignadores (llm_engine.py). Hecho de código

  • El KV por bloques usa bloques de 128 tokens y se busca con una tabla de bloques, como la paginación del capítulo 17 (model_metadata_utils.py). El KV por bloques contiene el KV principal y la K del indexer (documento Q&A). Un registro KV son 512 números más factores de escala: 528 bytes en FP8 y 288 bytes en FP4 (cache_common.py). Una capa comprimida guarda un registro solo cada ratio tokens, así que un bloque de 128 tokens ocupa solo 128 ÷ ratio registros (cache_engine.py, el mismo archivo).
  • El estado SWA no va en bloques paginados. Cada secuencia ocupa una ranura de tamaño fijo en la caché de estado, llamada StateBlock. La ranura se divide en dos zonas según se archive o no: la parte delantera es el SWA que se archiva, y la trasera es lo que no se archiva, incluidos el SWA de las capas consumidoras de YoCo y el estado comprimido (cache_engine.py). Cada capa es un búfer circular que guarda 128 + 6 = 134 tokens, y los 6 extra se reservan para el retroceso de la decodificación especulativa (cache_engine.py, environ.py). Con la configuración por defecto, el token de la posición pos se escribe en la celda pos mod 134, y un token nuevo sobrescribe al más antiguo (prepare_tensor_input_v4.cpp).

Cuando llega una solicitud, el asignador le da de una vez una tabla de bloques y un número de ranura (block_manager.hpp). Hecho de código La figura D3-4 dibuja estas dos cosas.

De todo el estado SWA, solo la zona delantera necesita archivarse. El código llama a esta zona «to disk» («a disco»), pero el SWA no va a 3FS: vive en la RAM local, como se explica más abajo, y esta página lo llama siempre «archivo». El documento Q&A calcula su tamaño: 20 capas × 134 tokens × 528 bytes = 1.415.040 bytes, unos 1,4 MB por secuencia (documento Q&A). Informe upstream La fórmula del código coincide: el tamaño del archivo es «el número de capas archivadas × los bytes de 134 tokens por capa (alineados a 32 bytes)» (cache_engine.py). Hecho de código 134 × 528 = 70.752 bytes, que es justo un múltiplo de 32, así que la alineación no desperdicia espacio. Estimación didáctica «Las primeras 20 capas se archivan» es un número que da el Q&A; el código calcula el número de capas por su cuenta a partir de la configuración del modelo.

Este estado se archiva solo en múltiplos enteros de 128. La granularidad de archivo en el código es 128, y una posición de archivo que no sea múltiplo de 128 da un error de inmediato (cache_engine.py, el mismo archivo). Hecho de código Según el documento Q&A, durante el decode, cada vez que se cruza un límite de 128 se hace una copia de la ventana actual en la memoria de la GPU, y al terminar la solicitud el archivo se toma de la copia más reciente (documento Q&A). Informe upstream El código abierto tiene la función de copia, pero should_copy_state, que decide si copiar, siempre devuelve False (llm_engine.py). Hecho de código Cómo eligen el prefill y el decode la posición de archivo está en «Más a fondo», al final.

¿Dónde se guarda? El estado SWA no va a 3FS. Se queda solo en la RAM de la máquina que lo produjo. Las máquinas Entrypoint tienen un directorio en memoria. Lógicamente es uno solo, pero físicamente se reparte por clave entre las máquinas Entrypoint, y anota qué máquina tiene qué tramo de SWA. En un acierto, si la máquina local no lo tiene, se trae de otra por la VLAN de 400G (documento Q&A). Informe upstream Cuando el prefill pasa el trabajo al decode, el estado SWA viaja por el mismo camino que el KV por bloques. En el código, el estado que se envía al motor de decode es mayor que el que se archiva: también se envía la zona que no se archiva (el SWA de las capas consumidoras y el estado comprimido) (cache_engine.py). Hecho de código

En el código abierto, las interfaces de archivo y de transferencia existen, pero su contenido está vacío. LLMEngine tiene una fila de «funciones virtuales» que inicializan el despliegue desagregado, guardan KV y envían un prompt terminado al motor de decode, y por defecto no hacen nada (llm_engine.py). El objeto de secuencia deja campos como «número de tokens acertados» y «inicio válido de SWA» para que los rellene código externo, y un comentario dice «número de aciertos inyectado desde fuera» (sequence.hpp). Hecho de código En esta versión no encontré ningún código que consulte aciertos en un almacenamiento externo y los escriba en esos campos. Esto concuerda con el README (README).

Frente a Strata: El capítulo 20 compara los dos tipos de memoria con un cuaderno y una pizarra. La caché KV es como un cuaderno: escribes hacia delante por posición y, para volver atrás, basta con no mirar las últimas líneas. El estado recurrente de GDN es como una pizarra: cada token reescribe toda la pizarra, y el pasado solo se recupera con una foto tomada antes (capítulo 20 «Instantáneas y copia en escritura»). El KV por bloques de DeepInfer es el cuaderno, y el estado SWA se parece más a la pizarra: un búfer circular de tamaño fijo donde un token nuevo sobrescribe al más antiguo. No reescribe toda la pizarra en cada paso como GDN. Un paso cambia una celda. Lo que comparten es que la historia sobrescrita no se puede recuperar. Por eso, igual que el estado GDN de Strata, solo se puede archivar tomando una foto en posiciones acordadas. El checkpoint de Strata pesa unos 118 MB, y casi todo es esa pizarra. DeepInfer archiva solo unos 1,4 MB de SWA por secuencia, porque la ventana es de solo 134 tokens.

3.5 Si hay acierto se lee, si falta el SWA se recalculan solo 128: reproducción acotada

Llega una solicitud de longitud L. ¿Cuánto se puede reutilizar? La regla del documento Q&A es: la longitud del acierto la decide el KV por bloques, y si el último bloque debe recalcularse lo decide el estado SWA (documento Q&A). Informe upstream Son tres pasos:

  1. La longitud del acierto es como máximo L − 134: se reservan 128 tokens para la ventana y 6 para el retroceso de la decodificación especulativa.
  2. Se consulta el KV por bloques dentro de ese límite para obtener la longitud de acierto L1, que es múltiplo de 128.
  3. Luego se consulta el estado SWA. Si hay un archivo entre L1 − 128 y L1, la longitud del acierto es L1. Si no, se retrocede un bloque, el acierto es L1 − 128 y los 128 tokens que se cedieron se recalculan.

Tras retroceder un bloque, ¿cómo se recalcula? La forma exacta es reconstruir el estado SWA desde el principio, pero la ventana deslizante mira hacia atrás capa por capa y habría que rastrear muy lejos. DeepInfer usa la reproducción acotada (bounded replay): recalcula solo los últimos 128 tokens y corta la ventana dentro del tramo de reproducción. Si la reproducción empieza en la posición s, la consulta de la posición i ve solo las claves de max(s, i − 127) a i, y obtiene un estado SWA aproximado. El número de tokens por reproducir pasa a ser una constante, independiente de lo largo que sea el contexto, aunque esos 128 tokens siguen pasando por todas las capas (documento Q&A). Informe upstream En el código, para el prefill normal, el extremo izquierdo del rango visible del SWA es el mayor entre el «extremo izquierdo de la ventana» y el «inicio válido de SWA» (prepare_tensor_input_v4.cpp). La historia anterior al inicio válido se rellena con ceros y la atención no la ve (el mismo archivo). Hecho de código Esta es la implementación de max(s, i − 127) del Q&A, donde s es el inicio válido. Cuando está activado el recorte que se describe abajo, otra función toma un valor más, el «extremo izquierdo del recorte», y usa el mayor de los tres (el mismo archivo).

El mismo truco se usa en otro lugar, y sirve en cada prefill. Las capas de V4.1 Flash se dividen en dos mitades: las delanteras son «capas codificadoras» y las traseras son «capas decodificadoras». El KV por bloques de las capas decodificadoras no lo calculan ellas mismas, sino que se proyecta desde el estado oculto de la última capa codificadora, y cada capa solo necesita calcular su propio estado SWA. El código llama a esta estructura YoCo, y el artículo del mismo nombre, «You Only Cache Once», describe una estructura parecida de «decodificador-decodificador». Para calcular el SWA de las capas decodificadoras con exactitud, los últimos 2560 tokens deben recorrer las 20 capas decodificadoras. DeepInfer deja que solo un tramo final corto del prompt pase por esas 20 capas, y el resultado se usa solo para el decode y no entra en la caché de prefijos. El Q&A dice que esto recorta casi a la mitad el cómputo total del prefill (documento Q&A). Informe upstream 2560 es justo 20 × 128: con cada capa, la ventana deslizante mira otros 128 tokens más atrás. Estimación didáctica

Tras un acierto, ¿cómo vuelve el KV de 3FS a la memoria de la GPU? El documento Q&A lo divide en tres pasos (documento Q&A). Informe upstream Coincidencia: el Entrypoint compara prefijos a lo largo de una cadena de hashes. Solo toca metadatos, pero la longitud del acierto debe conocerse antes del enrutamiento, así que este paso no se puede ocultar. Obtener el KV: un proceso aparte mueve de forma asíncrona el KV de 3FS a la memoria compartida del host. Cargar a la GPU: un hilo del motor lo copia capa por capa a la memoria de la GPU, solapado con el cálculo hacia delante. Los bloques KV son pequeños y están dispersos, así que la carga usa GDR, que deja que la tarjeta de red RDMA llene el ancho de banda de PCIe y no usa ninguna unidad de cómputo de la GPU. Para la idea de «mover mientras se calcula», mira el capítulo 14 «Síncrono y asíncrono».

Cada servidor de almacenamiento lee al menos 40 GB/s Informe upstream. El prefill procesa unos 87.000 tokens fallados por GPU por segundo, según una gráfica de velocidad del README (4 GPU SM100, EP4DP4, contexto de 131.072) Informe upstream. Qué tan grande es el KV de un token, esta página no lo verificó, así que el valor por defecto es 8 KiB, que es un supuesto. Hay otro supuesto: los 87.000 de la gráfica son un rendimiento promedio, y aquí los usamos directamente para «la cola tras un prefijo largo». La cola debe calcular atención sobre más de 110.000 tokens, así que en realidad puede ser más lenta. Estimación didáctica

El resultado: leer es mucho más rápido que calcular. Para una solicitud de 128K con un 90% de aciertos, el prefill baja de unos 1,5 segundos a unos 0,18 segundos. El punto de equilibrio es «ancho de banda de lectura ÷ rendimiento del prefill»: 40 GB/s ÷ 87.000 token/s ≈ 449 KiB. Si el KV por token es menor que eso, leer es más rápido que calcular. Pero con la estimación de capacidad de la sección 3.3, unas 18 GPU de prefill leen de un mismo servidor de almacenamiento a la vez, y cada una recibe solo unos 2,2 GB/s, así que el punto de equilibrio cae a unos 25 KiB, solo 3 veces por encima de los 8 KiB supuestos. Estimación didáctica Por eso el ancho de banda de lectura del almacenamiento debe dimensionarse junto con el número de GPU en línea. Si no, el tiempo que ahorra un acierto se lo come la cola de lecturas.

Recuerda estas tres ideas

  1. El prefill consume cómputo y el decode ancho de banda. En un mismo grupo de GPU, un solo paso de prefill detiene el decode de todos. DeepSeek despliega por separado el codificador visual, el prefill y el decode: el prefill en máquinas de 8 GPU (EP2–8), el decode en supernodos de 64–128 GPU (EP64–128), y la unidad eficiente mínima es de 64 + 64 GPU.
  2. El KV por bloques se pagina en bloques de 128 tokens y se guarda en un clúster 3FS dedicado (código de borrado 10 + 2, unos 100 PiB, TTL de 3–7 días). El estado SWA es una ranura de tamaño fijo por secuencia, solo se archivan unos 1,4 MB y se queda en la RAM local.
  3. Un acierto llega como máximo a L − 134, redondeado a múltiplo de 128. Si falta el SWA, se retrocede un bloque y se recalculan solo 128 tokens con reproducción acotada, así que el costo es constante. La versión abierta trae los roles de motor, la disposición de caché y la reproducción acotada. No trae el código que une el sistema de caché KV con el despliegue desagregado.

Error común: «Un acierto de prefijo solo ahorra tiempo, y el resultado es exactamente igual que calcular desde cero.»

El KV por bloques se lee de vuelta tal cual, así que esa parte es idéntica. Pero cuando falta el estado SWA, la reproducción acotada produce un SWA aproximado: la ventana se corta dentro del tramo de reproducción y no puede ver tokens anteriores (documento Q&A). Cuando la reproducción acotada de las capas decodificadoras está activada, como en el uso por defecto del README, cada prefill se recorta, así que el resultado difiere del cálculo completo desde el principio. Lo que verifica examples/yoco es que los dos modos de recorte, mask y compact, coinciden entre sí, no que coincidan con no recortar. Si quieres una salida reproducible, mira la página de invariancia al lote.

Roles del motor y la votación del motor mixto

Los tres roles de motor se definen en engine_type.py: NORMAL y COMPLETION activan por defecto la planificación sin sobrecosto, y PROMPT no (para la planificación asíncrona, mira la página de DSpark y la planificación sin sobrecosto). El planificador reparte por rol: PROMPT llama solo a _schedule_prefill y COMPLETION llama solo a _schedule_decode (scheduler.hpp). En la votación de NORMAL, «quiere hacer prefill» significa que el uso de KV en la memoria de la GPU es como máximo del 90% y hay alguna solicitud esperando (marca de agua, want). El punto ALL reduce con MIN, así que el prefill se ejecuta solo si todos lo quieren; en el punto ANY, el prefill se ejecuta si cualquier rank lo quiere. Después hay una segunda ronda de votación para confirmar que algún rank programó de verdad trabajo de prefill. Un rank sin nada que hacer se une ejecutando un paso de prefill vacío, para que todos los rank mantengan la misma forma de paso. Los intervalos los controlan DEEPINFER_PREFILL_ATTEMPT_INTERVAL (por defecto 70) y DEEPINFER_PREFILL_ANY_ATTEMPT_INTERVAL (por defecto 100) (environ.py). Un motor que no es NORMAL llama a init_pd_split al inicializarse (llm_engine.py). Además, solo los motores que no son PROMPT usan CUDA Graph (model_runner.py): los pasos de decode son pequeños y frecuentes, así que grabar un grafo ahorra el costo de lanzamiento, que es justo lo que cubre el capítulo 15 «Sobrecarga de lanzamiento y fusión de kernels».

Tabla de bloques y ranuras de estado

Los dos asignadores son un BlockManager: los bloques libres se encadenan en una lista enlazada, los bloques llevan un contador de referencias y el bloque 0 no se usa (block_manager.hpp). El asignador de bloques administra bloques según num_gpu_blocks, y el asignador de ranuras administra ranuras según num_state_seqs (llm_engine.py). Cuando el número de bloques pedido no es menor que el total de bloques, devuelve NEVER y da error de inmediato. Cuando faltan temporalmente, devuelve LATER y la solicitud sigue en la cola (block_manager.hpp). try_allocate_seq asigna solo si hay bloques y ranura suficientes a la vez (el mismo archivo). El número de ranuras es int(max_num_seqs × 1.2) + 1, y la proporción la controla DEEPINFER_NUM_STATE_SLOTS_RATIO (cache_engine.py, environ.py). Al arrancar hay una comprobación más: el número de tokens que caben en los bloques, por 0.8, debe ser al menos la longitud máxima del modelo (llm_engine.py).

Disposición y archivo del estado SWA

Qué capas no archivan su SWA depende solo de la configuración del modelo: las capas con índice no menor que n_prefill_layer son capas consumidoras de YoCo (cache_engine.py). n_prefill_layer es el índice de la primera capa cuya razón de compresión es 1 (config.py). Cuando DEEPINFER_PREFILL_STORE_EXTRA_STATE está activado, el búfer circular que se usa para archivar guarda DEEPINFER_PREFILL_STORE_EXTRA_SIZE (por defecto 128) tokens más, y se suma KEEP_TOKENS cuando el recorte está activado. El comentario da esta razón: «el prefill puede no disparar la escritura a disco, así que guardar un tramo extra es lo que garantiza el acierto en varios turnos» (cache_engine.py). Lo que lee los datos del archivo es select_state_slice_to_store: al archivar, exige que la posición sea múltiplo de 128. Con TO_CE=True, construye el estado completo que se envía al motor de decode, incluida la zona no archivada (cache_engine.py). En sentido contrario, load_state_from_store_to_prefill_cache escribe los datos del archivo de vuelta en la ranura de estado del prefill (el mismo archivo).

Cuándo se guarda el estado SWA

La regla que da el documento Q&A (documento Q&A): Informe upstream cuando termina el prefill, primero se deja un token al final de la secuencia y luego se redondea hacia abajo a un múltiplo de 128. Si no hay un tramo completo, esta vez no se guarda nada. Con prefill por trozos, solo guarda el último trozo. Durante el decode se abre en la memoria de la GPU una zona de copia aparte, y cada vez que se cruza un límite de 128 se copia allí la ventana actual. Cuando termina la solicitud, el archivo se toma de la copia completa más reciente y el punto de enlace se redondea hacia abajo a 128. Una posición de copia puede pasarse del límite como máximo por 5 tokens, y las 6 posiciones extra de la ranura sobre la ventana lo cubren justo. En el código, la copia la hace do_copy_state, que copia el estado de la GPU en el búfer copy_state, mientras que should_copy_state, que decide si copiar, siempre devuelve False en la versión abierta (llm_engine.py). Interruptores y comprobaciones de la reproducción acotada

DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE toma off, mask o compact. DEEPINFER_YOCO_PREFILL_KEEP_TOKENS vale 0 por defecto y debe fijarse de forma explícita cuando el recorte está activado (environ.py). Hay dos comprobaciones: del lado de Python al cargar el modelo (model_runner.py) y del lado de C++ al preparar la entrada (prepare_tensor_input_v4.cpp). La longitud de retroceso DEEPINFER_MAX_BACKTRACKING_TOKENS se sube hasta al menos «número de borradores + 1»; el número de borradores por defecto es 5, así que es al menos 6 (environ.py). En modo compact, cada trozo conserva la intersección de [max(0, longitud total − KEEP_TOKENS), longitud total) con el trozo. Si el trozo entero queda antes de la zona conservada, aun así se deja el último token como marcador de posición (el mismo archivo). El recorte tiene dos modos: mask conserva todas las consultas y solo estrecha el rango visible; compact descarta las consultas de la zona recortada en la primera capa consumidora, lo que de verdad ahorra cómputo (environ.py). En el pase hacia delante del modelo, los metadatos se cambian a la vista compact en la primera capa consumidora (deepseek.py). El rango visible de los dos modos es la misma fórmula (yoco.py). Cuando el recorte está activado, las probabilidades por token del prompt (prompt logprobs) se desactivan a la fuerza: en modo compact las filas recortadas nunca se calcularon, y en modo mask las probabilidades de las filas anteriores al rectángulo no tienen sentido (llm_engine.py). El modelo de costos del planificador también cuenta por separado las filas de las capas consumidoras, así que sabe cuánto ahorra el recorte (flops_estimator.hpp). examples/yoco tiene dos niveles de verificación: L1 tarda unos segundos en una GPU y compara solo metadatos; L2 necesita 8 GPU y un checkpoint compatible, y compara logprob y top-K uno por uno. Los parámetros por defecto son --keep-tokens 140 --window 128 (examples/yoco/README.md).

Cómo corta el CP equilibrado

El README lo escribe como «Attention DP / balanced CP» (README), y activar CP en un motor de decode da error de inmediato (llm_engine.py). Una secuencia se corta en 2 × cp segmentos, y la GPU r toma el segmento r y el (r + 1)-ésimo segmento desde el final, uno delantero y uno trasero emparejados (prepare_cp_mirror.py; el cálculo de relleno bajo recorte usa el mismo emparejamiento, mira prepare_tensor_input_v4.cpp). Hecho de código ¿Por qué emparejarlos así? En la atención causal, cuanto más atrás está un token, más claves debe mirar. Si 4 GPU cortan la secuencia de corrido, la carga es de aproximadamente 1 : 3 : 5 : 7, y la GPU más ocupada tiene 1,75 veces el promedio. Con uno delantero y uno trasero emparejados, las cuatro GPU tienen la misma cantidad. Estimación didáctica Al planificar, la longitud de cada secuencia se alinea a cp × 2 (scheduler.hpp), y la longitud de cada rank es la suma sobre las secuencias de ⌈longitud ÷ 2cp⌉, por 2 (prepare_tensor_input_base.cpp). El kernel de la GPU calcula el número de bloque del segmento half como blk = rank + half × (2cp − 1 − 2 × rank): cuando half = 0 es el bloque rank, y cuando half = 1 es el bloque 2cp − 1 − rank (prepare_cp_mirror.py). El razonamiento de la carga: una longitud N se corta en 2cp segmentos, y un token del segmento i mira en promedio unas (i + 0,5) × N ÷ 2cp claves, así que el bloque r y el bloque 2cp − 1 − r suman siempre 2cp unidades, sin depender de r.
