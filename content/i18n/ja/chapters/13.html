直感に反する話

Strata は GPU と CPU を同時に働かせます。作業員が 2 人になるのだから、ぐっと速くなりそうです。ところが上流の開発記録に、こんな出来事があります。CPU が 1 トークンごとにこなすエキスパート計算を 18.2 ミリ秒から 10.2 ミリ秒へ減らしました。CPU の仕事は確かに半分近く減りました。それなのに、1 トークンを生成する合計時間はまったく変わりませんでした。上流レポート（include/strata/core/hit_hook.hpp のコメント）

節約した 8 ミリ秒はどこへ消えたのでしょう。この章は CPU と GPU の性格の違いから始めて、「誰が誰を待つのか」を考え、最後に 1 つの言葉にたどり着きます。クリティカルパスです。

ひとことで：エキスパートの計算はバイトを読む時間が大半です。そこで CPU は、メインメモリにあるエキスパートをその場で計算します。同じ層の中では、ヒットしたエキスパートを GPU が、ミスしたものを CPU が、同時に計算します。ただし層と層の間にはデータ依存があって、順番に待つしかありません。だから CPU の仕事は隠せず、キャッシュで減らすしかないのです。

13.1 2 種類のプロセッサ、2 種類の性格

CPU は、何でもこなせる数人のベテラン職人のようなものです。GPU は、千人規模の流れ作業の工場のようなものです。職人は人数が少ないものの、1 人ひとりが複雑で「やりながら考える」仕事を任せられます。工場は人数が多く、「全員が同時に同じ単純な動作をする」ことが得意です。図 13-1 は、そのイメージ図です。

CPU と GPU：SIMD と SIMT

CPU（中央演算処理装置）のコアは多くありません。上流が計測に使ったマシンの Ryzen 5 7600 は 6 コアです。上流レポート[S03] 各コアはとても「賢く」できています。大きなキャッシュを持ち、分岐を予測し、命令を順序を入れ替えて実行できます。制御の流れが複雑なプログラムに向いています。CPU は複数の数を一度に計算することもできます。SIMD（単一命令・複数データ）の命令 1 つで、並んだ数すべてに同じ演算を同時に行います。AVX-512 命令のレジスタは 512 ビット幅で、32 ビット浮動小数点数を一度に 16 個入れられます。つまり 16 本の「レーン」があります。Strata の CPU 用エキスパートカーネルは、AVX-512 または AVX2 で書かれています。上流レポート[S02]

GPU（グラフィックス処理装置）は、チップの面積を大量の単純な計算ユニットに使います。一般的なゲーム用グラフィックスカードなら数千個あります。実行方式は SIMT（単一命令・複数スレッド）といいます。NVIDIA の GPU は 32 スレッドを 1 組（1 つの warp）にまとめ、同じ組が同じ命令を同時に実行し、各スレッドは自分のデータを処理します。[R01] さらに、帯域幅がずっと大きい VRAM を備えています。RTX 5070 の VRAM は約 672 GB/s です。一方、デュアルチャネルの DDR5-5200 メモリは約 83 GB/s です（第 1 章に比較があります）。

両者に共通するのは、互いに無関係な同じ仕事を大量に同時にこなして初めて力を発揮できることです。毎ステップで前の結果を待つなら、レーンがいくらあっても 1 マスずつ進むしかありません。下のシミュレータで、その様子を目で確かめましょう。

さらに読む：Wikipedia：SIMD · Wikipedia: Single instruction, multiple threads · NVIDIA CUDA Programming Guide

CS を学んだ人へ：SIMD はベクトル命令のことです（x86 の SSE と AVX、ARM の NEON）。GPU の SIMT は、「ハードウェアが 1 組のスレッドを自動的に 1 本の幅広いベクトルにまとめて実行する」ものと考えられます。分岐の向きがそろわないと、組の中のスレッドは何回かに分けて実行されます。

13.2 CPU でもエキスパートを計算できる理由：大半はバイトを読む時間

GPU のほうがずっと速いのに、なぜ Strata は CPU にエキスパートを計算させるのでしょうか。エキスパートの計算で難しいのは、計算ではなく読み込みだからです。エキスパート 1 つは 1.38 MB で、各パラメータは 1、2 回しか乗算・加算されません。計算ユニットは、ほとんどの時間をメモリからデータが届くのを待って過ごします。上流の CPU 用エキスパートプールのコメントは率直です。エキスパートカーネルはメモリ帯域で頭打ちになり、6 コアの実測は約 42.55 GB/s で、速度はコア数にほぼ比例します。コード上の事実（include/strata/kernels/cpu/pool.hpp）

ボトルネックがバイトの読み込みなら、バイトの移動距離を短くすればよいのです。第 10 章で計算しました。ミスしたエキスパートを PCIe 経由でグラフィックスカードへ運ぶと、1 トークンあたり運ぶだけで 10 ミリ秒以上かかります。逆に「仕事」をデータのそばへ送れば、転送するものはずっと少なくなります。図 13-3 を見てください。

インターフェースの約束事はこうです。各層で、GPU は正規化後の入力と、選ばれた 10 個のエキスパート番号とその重みを CPU 側へ渡し、10 × 2560 個の数が戻ってくるのを待ちます。コード上の事実[S06] 数 1 つは 4 バイトなので、入力は約 10 KB、結果は約 100 KB です。13.8 MB より 100 倍以上小さくなります。教育用の試算

CPU 側はエキスパートプールです。物理コア 1 つにつきワーカースレッドを 1 本置き、最初のコアは、既定ではメインループ用に空けておきます。v0.1.40 からは、--host-core last を使うと、メインループを最後の物理コアへ移せます。これは Windows のための設定です。Windows はたいてい、GPU の割り込みを最初のコアに送ります。そこで空回りして待っているメインループは、割り込みで中断されてしまいます。各層の 10 個のエキスパートをこれらのスレッドに分けて同時に計算します。ホストは 10 個の結果をすべて集めて足し合わせないと次の層を始められません。つまり、どの層も「関所」になります。コード上の事実（pool.hpp）

OS を学んだ人へ：スレッドは論理プロセッサではなく、物理コアに固定します。1 つの物理コアの 2 本のハイパースレッドは、同じ実行ユニットとキャッシュを共有します。メモリを読むスレッドが 2 本ぶつかると、帯域は半分になります。ソースのコメントには、実測も記録されています。メインループのスレッドを自分のコアに固定しなかったとき、エキスパートプールは 36.32 GB/s から 26.9 GB/s に落ちました。上流レポート（pool.hpp のコメント）

上流の開発時の計測によると、エキスパートキャッシュが登場する前は、CPU が 1 トークンごとに 663.6 MB のエキスパートデータを読んでいました。約 40 GB/s で計算すると 16.2 ミリ秒で、当時の 1 トークンは約 53 ミリ秒でした。上流レポート[S05] CPU の分担分は、マシン全体で最大の出費でした。

13.3 1 つの層の中：ヒットは GPU、ミスは CPU、両方同時

エキスパートキャッシュがあると、1 つの層の 10 個のエキスパートは 3 組に分かれます。コード上の事実（src/core/expert_source.cpp、src/program/generate.cpp）

  1. VRAM にあるもの（ヒット）は、GPU がそのまま計算します。
  2. ミスしたもののうち、ある割合の分は、GPU が PCIe 経由でピン留めメモリから読んで計算します。この割合の既定値は、Q2_0 モデルで 0.2、ほかのネイティブ形式で 0.55 です。
  3. 残りのミスは、CPU がその場で計算します。

順番が肝心です。GPU の分を先に決めて先に公開し、GPU を先に動かします。そのあとで CPU が自分の分を始めます。コード上の事実（expert_source.cpp のコメント）上流のドキュメントによると、PCIe の割合を 0 にして、ミスをすべて CPU に戻すと、生成が遅くなります。上流レポート[S03]

下のシミュレータは、1 つの層をタイムラインとして描きます。数字は教育用の試算です。エキスパート 1 つは 1.38 MB、CPU は 40 GB/s、VRAM は 672 GB/s、PCIe は 63 GB/s で読むものとします。アテンションとルーティングは 0.25 ミリ秒、マージは 0.05 ミリ秒と仮定しています。

上流の最初のバージョンは、「どちらが先か」でつまずきました。当時は、GPU がヒット分を計算するステップが、CPU のエキスパートプールの後ろに置かれていました。CPU の仕事は確かに半分近くになりました（18.2 から 10.2 ミリ秒）。しかし GPU の半分は「横」から「後ろ」へ移っただけで、経路全体は少しも短くなりませんでした。その後、2 段階に改めました。GPU は別のバッファでヒットしたエキスパートの計算を先に始め、CPU は同時にミスした分を計算します。CPU の結果が GPU に届いたら、2 つの結果を足し合わせます。バッファが 1 つ増え、加算が 1 回増えましたが、その代わりに本当の並列が手に入りました。上流レポート（hit_hook.hpp のコメント）シミュレータで「両側が同時に計算」をオフにすれば、この出来事を再現できます。

13.4 層と層の間：データ依存が並列を阻む

1 つの層の中は並列にできるとして、CPU がまだ第 l 層を計算している間に、GPU が第 l + 1 層を始めることはできるでしょうか。できません。第 l + 1 層の入力は、第 l 層で 10 個のエキスパートをマージした結果そのものだからです。この線は鎖のようにつながっています。図 13-5 を見てください。

データ依存とクリティカルパス

2 つの計算があって、後のほうが前の結果を使うとき、両者の間にはデータ依存があるといいます（正確には「書いてから読む」依存です）。依存のある 2 つのステップは、順番にしか実行できません。依存のないものだけが、同時に実行できる可能性を持ちます。

すべての計算を 1 枚のグラフに描きます。各計算が点で、依存が矢印です。始点から終点までの最も長い矢印の連なりをクリティカルパスといいます。作業員が何人いても、全体はどんなに速くてもこれだけの時間がかかります。速くする方法は 2 つだけです。クリティカルパス上のあるステップを短くするか、クリティカルパス上のあるステップを脇へ移して、ほかのステップと並列にするかです。

逆に、クリティカルパス上にないステップを短くしても、まったく効果がありません。冒頭の話がまさにそうでした。CPU は 8 ミリ秒を減らしましたが、その 8 ミリ秒を外へ出したら GPU の分が代わりに入り込み、クリティカルパスの長さは変わりませんでした。これは第 5 章のアムダールの法則と同じ考え方です。一部だけを最適化しても、全体の改善は残りの部分に制限されます。

さらに読む：Wikipedia：クリティカル・パス · Wikipedia: Data dependency · Wikipedia: Critical path method

Strata のソースコードは、このことを結論として書いています。各層は 2 つの GPU 計算グラフに分かれます。前半はアテンションからルーティングと共有エキスパートまでを計算します。後半はエキスパートの結果をマージして本流へ書き戻します。後半は CPU が結果を返すまで起動できません。こうして、第 l 層のエキスパートの結果に、第 l 層自身のルーティング重みが組み合わされます。代償として、CPU と GPU が重なれる時間は、共有エキスパートの短い区間だけになります。コメントにはこうあります。層ごとに 1 回ある CPU エキスパートプールは、厳密に直列な残差の鎖の後ろには隠せません。コード上の事実[S13]

キャッシュのコメントには数字があります。当時のパイプラインは、19.035 ミリ秒の CPU 作業のうち 1.055 ミリ秒しか隠せず、96% がクリティカルパスの上に出ていました。理由は「残差の鎖が厳密に直列だから」です。だから唯一の出口は、読むバイトを減らすことです。エキスパートの一部を VRAM に置き、CPU にはミスした分だけを読ませます。上流レポート[S05] これが、第 12 章のエキスパートキャッシュが存在する理由です。

13.5 本当に並列になったと、どう証明するか

「CPU も GPU も忙しい」は、「同時に忙しい」と同じではありません。図 13-6 の 2 つのケースでは、両側の稼働時間の合計は同じですが、全体の所要時間は大きく違います。

Strata のセッションコードは、まさにこの点を数えます。各層で、ホストが「ドアベル」（GPU が出す「ルーティングが決まった」という合図）を見たとき、GPU の計算グラフがまだ実行中かどうかを調べます。まだ実行中なら、CPU には GPU と重なる時間帯があったことになります。すでに終わっていたら、CPU は GPU が空いているときに働いたことになり、パイプライン全体は直列と同じです。このカウンタは rings_mid_graph といい、コメントはこれを「ドアベルが飾りでないか」を判定するための診断量と呼んでいます。コード上の事実[S13]

コメントは、これが必要な理由もはっきり述べています。どちらの場合も正しいトークンが計算でき、層ごとの所要時間も同じです。違いは「重なりが何も隠せていない」という形でしか現れません。もう 1 つのカウンタは、計算グラフを起動してからドアベルを見るまでのミリ秒数を記録します。CPU が使える時間帯は、「層の長さからそれを引いたもの」です。コード上の事実[S13] 設定に書かれた「重なりを有効にする」は意図にすぎません。実際の挙動を示すのは、イベントのタイムラインです。

13.6 手を動かす：バランス点を探す

まず、この章の「1 つの層の中」シミュレータを使います。ヒット率を 0% にして、次に 65% にして、クリティカルパスがどこに移るかを見ましょう。「両側が同時に計算」をオフにして、上流の最初のバージョンの教訓を再現しましょう。「最適な割合に設定」を押して、2 つの分岐が同じ長さになる様子を見ましょう。そのあと、「一度に 16 個を計算」で 3 つのアルゴリズムをすべて動かします。

次に、この章のインタラクティブ実験「CPU と GPU の仕事の分け方」を開きます。分岐は 2 本だけです。CPU と、「PCIe 経由で GPU に任せる」分です。両側の有効速度と分担の割合を変えて、合計時間が最短になる割合を探します。実験の課題です。PCIe の分岐の有効速度を半分にします。なぜ最適な分担が「半分ずつ」ではなくなるのかを説明してください。注意点があります。実験もシミュレータも、2 つの分岐が資源を奪い合わないと仮定しています。実際のマシンでは、CPU のエキスパート読み込みと、PCIe 経由のピン留めメモリ読み込みは、同じメモリ帯域を使います。

この 3 点を覚えよう

  1. エキスパートの計算は、バイトを読む時間が大半です。CPU がメモリ上のエキスパートをその場で計算すれば、PCIe を通るのは 10 KB の入力と 100 KB の結果だけです。
  2. 同じ層の中では、ヒットしたエキスパートは GPU が、ミスの一部は PCIe 経由で GPU が、残りは CPU が、同時に計算します。合流するときは遅いほうを待ちます。
  3. 層と層の間にはデータ依存があり、48 層は 1 本のクリティカルパスです。CPU の仕事は隠せず、キャッシュで減らすしかありません。クリティカルパス上にないステップを最適化しても、効果はありません。

よくある誤解：「CPU と GPU が一緒に計算すれば、速度は 2 倍になる。CPU の仕事が半分になれば、合計時間もそれだけ減る。」

節約した部分がクリティカルパス上にあるときだけ、合計時間は短くなります。上流は CPU の仕事を 18.2 ミリ秒から 10.2 ミリ秒に減らしましたが、トークンは少しも速くなりませんでした。GPU の分が CPU の後ろに並べられたからです。上流レポート 同じように、「GPU 使用率 100%」も何も保証しません。空回りして待っているのかもしれないし、本来は並列にできた仕事を計算しているのかもしれません。見るべきなのは、クリティカルパスとイベントのタイムラインです。

もう一歩深く：分担の式、それが当たらない理由、並行処理の落とし穴

2 つの分岐の分担の式

残りの計算が必要なエキスパートデータの量を D とします。割合 f を「PCIe 経由の GPU の分岐」に渡し、残りを CPU に渡します。CPU の分岐の持続処理能力を毎秒 Bc バイト、PCIe の分岐を毎秒 Bp バイトに換算し、両者は互いに影響しないと仮定します。

T(f) ≈ max((1 − f)·D / Bc, f·D / Bp) ＋ Tマージ

2 つの分岐が同じ長さのときが最速で、f = Bp ÷ (Bc ＋ Bp) と求まります。Bc = 40、Bp = 20 なら f = 1/3 で、「半分ずつ」にはなりません。教育用の試算 ここでの Bp は PCIe の公称帯域ではありません。この分岐のコストをすべて含めた有効速度です。

実際の最適点がここにない理由

式は 2 つの分岐がそれぞれ別の資源を使うと仮定しています。しかし実際のマシンでは、両者は奪い合います。CPU のエキスパート読み込みと、GPU が PCIe 経由で行うピン留めメモリの読み込みは、同じメモリチャネル群を通ります。PCIe は、長いコンテキストの KV ページを同時に転送していることもあります。エキスパートのサイズ、1 つの検証ウィンドウ内で同じエキスパートが何トークンに再利用されるか、GPU の起動コスト、ホストスレッドのコア固定も、両側の有効速度を変えます。だから Strata の既定の割合（Q2_0 は 0.2、ほかのネイティブ形式は 0.55）は、この式ではなく実測から来ています。コード上の事実（generate.cpp）式は仮説を立てるのに向いています。チューニングでは、各分岐の完了時間、転送バイト数、合計時間を記録し、別のタスクで再検証してください。

計算は合っているか：時間は合うのに、結果が間違っていた

hit_hook.hpp には、教科書のような並行処理のバグが記録されています。最初のバージョンでは、「GPU がヒット分を先に計算する」ステップが、エキスパートプールのコールバックの中で決まるヒット名簿を読んでいました。そのコールバックは、このステップの後で実行されます。その結果、前の層の名簿を読み、前の層のエキスパートをこの層の位置で計算してしまいました。プログラムは普通にトークンを出力し、所要時間も正常でした。ところが標準の答えと比べると、平均 KL ダイバージェンスは 9.69×10⁻² から 1.03 に増え、最も可能性の高いトークンの一致率は 0.867 から 0.333 に落ちました。修正は、このステップがこの層のルーターが公開した番号を直接受け取るようにすることでした。コード上の事実（hit_hook.hpp）

スレッドプールの競合状態

CPU エキスパートプールは、あるバッチのタスクの完了を待つとき、最初は「完了カウント = タスク数」だけを待っていました。ところが VRAM が大きいカードでは、ほとんどのエキスパートがヒットするため、ワーカースレッドはよく眠っています。バッチが小さすぎると、眠っていたスレッドが起きる前に、そのバッチが終わってしまいます。起きたスレッドは、次のバッチからタスクを奪って同じタスクを 2 回実行したり、ホストがゼロクリアした後でカウントを加算したりします。すると「完了カウント = タスク数」は永遠に成り立たず、GPU はずっと待ち続けます。修正は、タスクを取るたびにバッチ番号を付けることでした。タスクポインタは 64 ビット語で、「バッチ | タスク数 | 連番」が入っています。タスクの取得にはコンペア・アンド・スワップを使い、バッチ番号が一致したときだけ成功します。遅れて来たスレッドは、自然にタスクを取れなくなります。コード上の事実（pool.hpp）上流のドキュメントは、このハングを issue #29 として記録し、エンジン 0.1.12 で修正されました。

コメントと設計が食い違うところ

session.hpp の後半には、少し古いコメントがあり、「重なりは層の遅延から生まれる。エキスパートプールの結果は次の層が消費する」と書かれています。コード上の事実（session.hpp）一方、前半の 2 つの計算グラフに関するコメントは正反対です。第 l 層のエキスパートに第 l + 1 層のルーティング重みが組み合わされるのを防ぐため、マージはこの層の中に置かなければなりません。コード上の事実[S13] このような矛盾に出会ったら、現在の呼び出し順序とテストを基準にしてください。

GPU と CPU が同じエキスパートを計算すると、最後の数桁が違うことがある

GPU と CPU のカーネルは、丸め方が違います。どのエキスパートを誰が計算するかは、キャッシュの状態と PCIe の割合で決まります。そのため、同じプロンプトを繰り返し実行しても、答えが 1 バイトも違わず同じになるとは限りません。上流のドキュメントによると、再現できる結果がほしいときは、PCIe の割合を 0 にするなどのスイッチがあります。代償として、生成は遅くなります。上流レポート[S03]
