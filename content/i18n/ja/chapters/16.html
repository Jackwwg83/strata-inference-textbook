同じ PC なのに、速さは 2 通り

Strata の上流の速度表には、数字の列が 2 つあります。RTX 5070 を積んだ同じ PC で、32K token のプロンプトを読むと 1 秒に 2,171 token。ところが答えを書くときは、1 秒に 81.8 token しか進みません。上流レポート[S03]

モデルも同じ、48 層も同じ、GPU（グラフィックスカード）も同じです。それなのに、なぜ「読む」ほうが「書く」より 20 倍以上も速いのでしょうか。カギは 1 つの言葉、「バッチ処理」です。この章では、まとめて計算するとなぜ 1 つずつより速いのか、チャンクはどれくらいの大きさがよいのか、そしてデータの転送と計算を同時に進めるにはどうするのかを説明します。

ひとことで：答えを書くときは、1 回に 1 token しか計算できません。重みを 1 回読んでも、使うのは 1 回だけです。問題を読むときは、プロンプトの token がすべて分かっています。数千 token をひとかたまりにして計算でき、重みを 1 回読めば、そのかたまり全体で使えます。Strata は 1 チャンクで最大 8,192 token を読みます。そして、現在の層を計算している間に、次の層のエキスパートの転送を始めます。

16.1 なぜ「問題を読む」ほうが「答えを書く」より 20 倍以上速いのか

まず数字を見ましょう。図 16-1 は、上流が同じ PC で測った 2 つの速度です。

測定条件は上流のドキュメントに書かれています。GPU は RTX 5070 12 GB、CPU は Ryzen 5 7600、メモリは 64 GB の DDR5-5200、OS は Windows、エンジンは 0.1.26、モデルは Q2_0 です。デコード時は投機的デコーディングを有効にしています。上流レポート[S03]

差が出る理由は、2 つの段階が本質的に違うからです。デコード（decode、「答えを書く」段階）では、次の token が何になるかは、前の token が選ばれるまで分かりません。1 つずつ進めるしかありません。プリフィル（prefill、「問題を読む」段階）では、プロンプトの token がすべて最初から手元にあります。大きなかたまりにして、まとめてモデルに送れます。ただし、「まとめて計算する」ことは「お互いにのぞき見る」ことではありません。5 番目の token が見えるのは、あくまで前の 4 つだけです。モデルの因果のルールは何も変わりません。変わるのは、計算の組み立て方だけです。

16.2 なぜまとめて計算すると速いのか：行列ベクトル積と行列積

選択式テストを採点する先生を想像してください。答案を 1 枚採点するたびに、棚から模範解答を取り出し、照合したら棚に戻します。答案が 1 枚ずつしか来ないなら、時間の大半は模範解答の出し入れに消えます。一度に 50 枚来るなら、模範解答を 1 回取り出して 50 枚を照合し、戻します。1 枚あたりでは、出し入れの時間はほとんどかかりません。

モデルでいう「模範解答」が重みです。1 層を計算するたびに、その層の重みを VRAM から計算ユニットへ読み込む必要があります。図 16-2 は、2 つの場合を並べて描いたものです。

バッチ処理：行列ベクトル積と行列積

直感：転送と計算は、別々の勘定です。token を 1 つずつ計算すると、そのたびに重み全体を転送します。転送が主な出費になります。token をまとめて計算すると、転送は 1 回だけです。計算量は少しも減りません。つまり、「1 バイト転送するごとにできる計算」が増えるのです。第 5 章で見たとおり、この比を演算強度と呼びます。演算強度は、プログラムがメモリ帯域に縛られるか、演算性能に縛られるかを決めます。

定義：ある層の重みは、m × n の行列 W です。1 token の入力は、長さ n のベクトル x です。W·x を計算するのが行列ベクトル積（GEMV）です。m × n 個の重みを読み、乗加算をおよそ 2mn 回行います。C 個の token のベクトルを並べて n × C の行列 X を作り、W·X を計算するのが行列積（GEMM）です。重みを読む量は同じ m × n 個のまま、計算はおよそ 2mnC 回になります。演算強度は、元のおよそ C 倍に上がります。

具体的な数字を 1 つ挙げます。Strata の投機的デコーディングのコントローラには、既定の表があります。「n 個の token の密な部分を同時に計算すると、1 token の何倍の時間がかかるか」を記録した表です。2 個なら 1.05 倍、4 個なら 1.45 倍、8 個なら 3.0 倍です。コード上の事実 つまり、8 token をまとめて計算すると、1 token あたりの平均は、単独で計算したときの 3.0 ÷ 8 ≈ 38% で済みます。教育用の試算

この章との関係：プリフィルでは、C が数千になることもあります。だからプリフィルはずっと速いのです。バッチ処理にも代償があります。ひとかたまり全体の中間結果を置く一時的な記憶領域が、もっと必要になります。また、1 チャンクが終わるまでの時間も長くなります。

もっと読む：Wikipedia：行列 · Wikipedia：行列の乗法 · Wikipedia：BLAS（GEMV と GEMM の由来）

Strata は、ほかの場所でも同じ工夫を使っています。投機的デコーディングの検証ウィンドウは、数個の token を一度に送り込みます。ソースコードには、このウィンドウのコストは「密な重みを 1 回だけ読み、T 個の token で共用する」ものだと書かれています。[S08] 混合残差の融合読み出しにも、複数 token 版があります。最大 8 token が重みを共有し、「重みは全員のために 1 回だけ読まれる」とあります。コード上の事実

CS を学んだ人へ：これは、コンピュータアーキテクチャの「メモリアクセスの局所性」と、数値線形代数の BLAS レベル分けの考え方そのものです。BLAS-2（行列ベクトル積）はメモリ帯域に縛られます。BLAS-3（行列積）なら、演算性能を使い切れます。プリフィルは、BLAS-2 の列を 1 つの BLAS-3 にまとめます。

16.3 エキスパートをまとめる：エキスパートごとにグループ化

密な部分は簡単です。すべての token が同じ重みを使います。エキスパートの部分は少し厄介です。各 token は層ごとに 10 個のエキスパートを選びますが、選ぶものは token ごとに違います。そこで Strata は、まずエキスパートごとにグループ化します。同じエキスパートを選んだ token を 1 か所に集めます。そのエキスパートの重みを 1 回読み、1 グループ分を計算し終えます。[S12] 図 16-4 は、縮小した例です。

実際の規模に拡大してみましょう。1 チャンクが 8,192 token で、各 token が層ごとに 10 個のエキスパートを選ぶと、1 層で 81,920 回のエキスパート呼び出しが起こります。一方、各層のエキスパートは 512 個しかありません。平均すると、1 つのエキスパートを 81,920 ÷ 512 = 160 個の token が共用します。教育用の試算 ソースコードのコメントにも、チャンクが 1,024 token 以上になると、各層の 512 個のエキスパートは「ほぼすべて選ばれる」とあります。コード上の事実

グループ化したあと、エキスパートはどこから来るのでしょうか。VRAM にキャッシュされている人気のエキスパートは、そのまま読みます。VRAM にないものは、RAM（メインメモリ）にあるエキスパート領域から送ります。ピン留めメモリの「リングキュー」を通し、専用のコピーストリームを使って GPU へ運びます。[S12] 計算が終わったら、結果を元の token の順に戻し、それぞれのルーティングの重みで足し合わせます。順序を 1 つ間違えると、結果がほかの token に足されてしまいます。

デコード時の役割分担とは違う点に注意してください。デコードでは、ヒットしなかったエキスパートは、主に CPU が RAM の中でその場で計算します（第 10 章）。プリフィルでは、エキスパートを何百、何千もの token が共用します。GPU へ運んでまとめて計算するほうが得になります。

16.4 チャンクの大きさ：大きいほどよいのか

プロンプトはチャンク（chunk）に切られ、1 チャンクずつ読まれます。各チャンクは 48 層すべてを通り抜けてから、次のチャンクへ進みます。[S12] チャンクが大きいほど、重みとエキスパートを多くの token で共用できます。ただし、大きければ大きいほどよいわけではありません。次の教育用モデルが、このトレードオフを描いています。

実際の Strata は、チャンクの大きさをどう選ぶのでしょうか。上流の説明では、長い文章は大きなチャンクで読みます。1 チャンクは最大 8,192 token で、長い文書でも毎秒 1,000 token 以上で読めます。[S02] --prefill auto に設定すると、エンジンは借用の上限を超えない範囲で、収まる最大のチャンクを探します。既定の最大値は 8,192 です。ユーザーが明示すれば、16,384 や 32,768 まで広げられます。コード上の事実 探し方は、v0.1.39 で一度変わりました。以前のエンジンは、固定の候補表（32,768、16,384、8,192、6,144……）から、収まる最初のものを選んでいました。この表は粗すぎました。約 8,700 token まで収まるマシンでも、8,192 しか使えなかったのです。いまは 256 token 刻みの格子上で二分探索をします。チャンクが大きいほど借りる VRAM は増える一方なので、「収まる最大のチャンク」は二分探索で求められます。コード上の事実 サーバー側も、「読み終えるまでどれくらい待つか」を見積もるときは、1 チャンクあたり最大 32,768 token として計算します。[S15]

チャンクが大きいことの代償は、一時的な VRAM です。8,192 token 分の中間結果は、かなりの場所を取ります。Strata の対処は、エキスパートキャッシュから「借りる」ことです。プリフィルの間、キャッシュの末尾のスロットをいくつかチャンクバッファに貸します。読み終えたら、元のエキスパートを埋め戻します。各リクエストは、自分のプロンプトに必要な大きさだけを借ります。[S12] 図 16-6 は、ソースコードのコメントにある実測値です。

速度の向上は 973 ÷ 791 ≈ 1.23 倍です。教育用の試算 チャンクをさらに大きくすれば、もう少し速くなります。コメントには、RTX 5090 で 32K プロンプトを読んだ例が記録されています。8,192 のチャンクでは毎秒 5,624 token、全体を 1 チャンク（32,768）にすると毎秒 6,465 token です。ただし、VRAM が十分に大きくないとできないので、既定では有効にしていません。コード上の事実

チャンクは小さすぎてもいけません。ソースコードのコメントによると、チャンクが約 1,000 token より小さいと、エンジンは別の GPU カーネルに切り替わり、Q2_0 の出力が変わってしまいます。そのため、「すべてのエキスパートを必ず転送する」モードは、下限を 1,024 にしています。コード上の事実 また、エンジンは各チャンクの開始前に「止めるかどうか」を 1 回確認します。チャンクが大きいほど、リクエストを取り消してから実際に止まるまでの待ち時間も長くなります。[S12]

16.5 パイプライン：この層を計算している間に、次の層はもう運ばれている

チャンクを切ったら、各チャンクは 48 層を通ります。各層の仕事は 2 つです。その層で使うエキスパートを GPU へ転送することと、計算することです。この 2 つを交互にやると、GPU が計算している間はコピーの経路が遊び、転送している間は GPU が遊びます。Strata は 2 つを重ねます。現在の層がアテンションを計算している間に、次の層のエキスパートが PCIe を通って運ばれてきます。[S02]

パイプライン：複数の工程を同時に動かす

直感：洗濯には「洗う」と「乾かす」の 2 段階があります。洗濯機と乾燥機が 1 台ずつなら、賢いやり方があります。1 かご目を乾燥機に入れるのと同時に、2 かご目を洗濯機に入れるのです。1 かごあたりの時間は変わりません。でも、洗濯物の山全体にかかる時間は、ぐっと短くなります。

定義：1 つの仕事を、前後につながったいくつかの工程に分けます。各工程は別々の部品が担当します。i 番目の仕事が 2 番目の工程をやっているとき、i+1 番目の仕事はもう 1 番目の工程を始めています。これがパイプラインです。安定したあとの総時間は、各工程の合計ではなく、いちばん遅い工程で決まります。図 16-7 は、2 工程・4 層の例です。

パイプラインには前提があります。2 つの工程が別々の部品を使うこと（ここではコピーエンジンと計算ユニット）。そして、間に「運ばれてきたが、まだ計算していないもの」を置くバッファがあることです。バッファが小さすぎると、転送は止まって待つことになります。

もっと読む：Wikipedia：パイプライン処理 · Wikipedia：命令パイプライン · Wikipedia: Pipeline (computing)

Strata のバッファは、あのピン留めメモリのリングキューです。ソースコードのコメントには、そのサイズがどれほど重要かが記録されています。8,192 のチャンクで Q2_0 を読むとき、リングキューが 96 スロットなら毎秒 1,153 token です。384 スロットに増やすと毎秒 1,294 token になります。理由は、「次の層のエキスパートが、現在の層のアテンション段階のうちに届く」からです。コード上の事実

リングキューとチャンクのバッファは、同じ VRAM から借ります。そこで v0.1.39 は、両方をまとめて計算するようにしました。リングのサイズはバイト単位で決まります。1 スロットに 1 つのエキスパートが丸ごと入るので、エキスパートが大きいモデルほどスロット数は少なくなります。チャンクを自動で選ぶときは、「リングキューが満杯のままでいられる」最大のチャンクを探します。ソースコメントには理由が残っています。4 枚の GPU を載せたマシンで 120K のプロンプトを読んだとき、リングのスロット 1 つの価値は毎秒約 0.53 token、チャンクの 1 token は約 0.05 token にすぎませんでした。だから、まずリングを確保し、それからチャンクを大きくします。以前の規則のチャンクに収まるプロンプトは、これまでどおりのリングを使い、結果もビット単位で変わりません。コード上の事実 もっと長いプロンプトでは、エキスパートが「キャッシュ上で計算」と「運んできて計算」に振り分けられる割合が変わり、ビット単位の結果も変わります。上流は FP16 のプリフィル経路と比べて測り、品質は元の範囲にとどまっています。上流レポート

GPU が複数あると、パイプラインはもう一段深くなります。各 GPU が連続する層の一部を担当します。前の区間は、1 チャンクの中間結果を後ろの区間に渡したら、すぐ次のチャンクを読み始めます。インターフェースのコメントの言葉では、後ろの区間がチャンク c を読んでいるとき、前の区間はもうチャンク c+1 を読んでいます。[S12]

最後に、引き継ぎを忘れてはいけません。1 チャンクを読み終えたら、エンジンはセッションの状態を「token を 1 つずつ読んでここまで来たときと同じ姿」にしておく必要があります。GDN の再帰状態と畳み込み履歴、QSA の KV キャッシュと indexer、PLE の履歴です。どれが欠けてもいけません。そうして初めて、デコードが次の token からそのまま続けられます。[S12]

16.6 手を動かす：速くて、しかも収まるチャンクを探す

  1. まず、上のインタラクティブ図（図 16-5）で遊びましょう。C を 1 から 8192 まで動かして、棒が「上昇」から「頭打ち」に変わる場所を見ます。次にパイプラインをオフにして、C = 1024 でそれぞれ 1 回ずつ再生し、2 回の「1 チャンクあたりの時間」を比べます。
  2. この本のインタラクティブ実験「チャンク分割と容量のトレードオフ」を開きます。この実験は、明示的に与えた再利用曲線のもとで、チャンクごとの速度と必要な容量を同時に計算します。まず、絶対に最速のチャンクを探します。次に、VRAM の予算を超えるものを除きます。「実行可能な最適」と「絶対的な最適」がどれくらい違うかを比べましょう。実験の再利用曲線と 1 token あたりの容量は人為的なパラメータで、Strata のアロケータではありません。
  3. 考えてみましょう。同じプロンプトを C = 1 で読んだときと C = 8192 で読んだときで、最後の状態は同じになるはずでしょうか。「もう一歩深く」を読んでから答えてください。

この 3 点を覚えよう

  1. デコードは行列ベクトル積で、重みを 1 回読んでも 1 token の役にしか立ちません。プリフィルは行列積で、重みを 1 回読めばひとかたまり全体の役に立ちます。同じ PC で、プリフィルはデコードより 20 倍以上速くなることがあります。
  2. エキスパートの部分は、エキスパートごとのグループ化でバッチ化します。同じエキスパートを選んだ token を集め、重みは 1 回だけ読みます。チャンクが大きいほど再利用は増えますが、借りる VRAM も増え、取り消しも遅くなります。Strata の既定は、1 チャンク最大 8,192 token です。
  3. パイプラインは、転送と計算を重ねます。現在の層を計算している間に、次の層のエキスパートはもう道中にいます。総時間は、いちばん遅い工程で決まります。

よくある誤解：「プリフィルでは token が全部分かっているから、お互いに見えてしまう。因果のルールは気にしなくていい。」

違います。バッチ処理が変えるのは、計算の組み立て方だけです。モデルのルールは変わりません。i 番目の token が見えるのは、その前の token だけです。プリフィルでも因果マスクは使います。再帰層も、チャンク全体を順番どおりに最後まで進めます。入力が「分かっている」ことと、意味の上で「未来を見てよい」ことは、別の話です。

もう一歩深く：状態の引き継ぎ、丸め誤差の違い、借用 VRAM の安全条件

状態の引き継ぎは、最後のベクトルを残すだけではない

1 チャンクを読み終えたとき、引き継ぐ状態には次のものが含まれます。GDN の再帰状態と畳み込み状態、QSA の KV と indexer、PLE の履歴、そしてドラフト層に関わる状態です。[S12][S13] 最後の 1 行の logits だけを残してこれらを捨てると、次のデコードはもう同じ履歴の続きではなくなります。

強力なテストがあります。同じ token 列を、C = 1、C = 7、C = 32 など違う切り方で読み終えます。そして、チャンク境界での状態と、そのあとの固定された履歴での出力を比べます。いちばんミスが出やすいのは、次のようなサンプルです。長さがちょうどチャンク境界をまたぐもの、最後のチャンクが埋まらないもの、プロンプトが極端に短いもの、読んでいる途中で取り消されるもの、読み終えた直後にデコードへ続くものです。

バッチ処理は丸めを変えるが、「浮動小数点だから」は万能の言い訳ではない

バッチ計算と 1 つずつの計算では、丸めの経路が違うことがあります。上流のドキュメントに例があります。IQ 系のモデルでは、CPU が 1 token のエキスパートを計算するときは ggml の内積を使います。複数 token を計算するときは、Strata 独自の複数 token 用カーネルを使います。この 2 つは丸めが少し違います。そのため、温度が 0 でも、同じプロンプトからドラフトの違いによって、別の同じくらいもっともらしい回答が出ることがあります。上流は、すべてのグループで複数 token 用カーネルを使うスイッチを用意しています。[S03]

だから、C = 1 と大きな C の出力が一字一句同じにならなくても、どちらかにバグがあると即断してはいけません。かといって、「ただの浮動小数点の誤差」の一言で見逃してもいけません。同じ固定された履歴の上で、中間テンソル、選ばれたエキスパートと index の番号、誤差がどの層から増え始めるかを比べます。そのうえで、事前に決めた許容誤差と品質基準で判断します。状態の位置、因果マスク、index の番号のような「数値でない契約」は、別に厳密に確認しなければなりません。

借用 VRAM の安全条件

チャンクバッファがエキスパートキャッシュからスロットを借りると、2 つの問題が起きます。1 つ目。借りている間、貸し出されたスロットにいた元のエキスパートはもういません。ルーティング表は、それらを「ヒット」として扱ってはいけません。ソースコードでは、これらのエキスパートはプリフィルの間 RAM から転送し、読み終えてから埋め戻します。[S12] 2 つ目。埋め戻しが完了してからでないと、そのスロットにどのエキスパートが入っているかを改めて宣言してはいけません。「予算を足しても VRAM を超えない」というだけでは、借用の安全性は証明できません。証明すべきなのは、「どの時点でも、ラベルとスロットの中のバイトが一致している」ことです。

ドキュメントに出てくるいくつかのチャンクサイズ

上流のあちこちに、違うチャンクサイズが登場します。説明ドキュメントは「最大 8,192 token」と書いています[S02]。詳細ドキュメントの内部の仕組みを説明する段落は、v0.1.38 では 2,048 と書かれたままで、v0.1.39 でようやく「最大 8,192、32,768 は手動で有効化」に直りました。0.1.13 の変更を書いた履歴の段落には、いまも「以前は 2,048」と残っています。サーバーは待ち時間の見積もりに、上限として 32,768 を使います[S15]。エンジンの自動モードは、既定の最大が 8,192 で、明示すれば 32,768 まで広げられます。コード上の事実 これらの数字は矛盾していません。答えている問いが違うのです（既定値、過去の値、上限）。式を書くときは、この本ではチャンクサイズを一貫して変数 C と書きます。

教育用コスト式の限界

この章のインタラクティブ図と実験「チャンク分割と容量のトレードオフ」は、簡略化したコスト式を使っています。形は T ≈ N ÷ r(C) ＋ ⌈N ÷ C⌉ × 1 チャンクあたりの固定コスト で、r(C) は明示的に設定した再利用曲線です。この式が説明できるのは、「固定コストが薄まる」ことと「容量の制約」の 2 つです。Strata の実際のスループットは予測できません。実際の速度は、エキスパートのヒット率、PCIe の帯域、CPU のコピースレッド、コンテキストが長くなるほど増えるアテンションの計算量なども左右します。

GPU の発展的な実験をするときは、毎回 C だけを変えます。ほかの設定（量子化、KV の形式、ドラフト、入力、キャッシュの状態）は固定したまま、速度と品質の変化を説明しましょう。
