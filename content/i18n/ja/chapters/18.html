ちょっとズルい高速化

Strata のドキュメントは、高速化の手段をこう紹介しています。小さくて速いアシスタントが、先に数語を推測する。大きなモデルは、その推測をまとめて 1 回で検査する。賛成できるものだけを残し、そのあとで次の 1 語を自分で書く。「アシスタントは推測するだけで、どの語もすべて大きなモデルが決めます。だから回答の品質は変わらず、1.6〜1.8 倍速くなるだけです。」上流レポート[S02]

推測するだけで、なぜ答えを変えずに計算が速くなるのでしょうか。推測が外れたら、どうなるのでしょうか。外れた推測をもとに計算してしまった結果は、どうやって「取り消す」のでしょうか。この章では、Strata の検証ウィンドウを使って、この 3 つの疑問に答えます。

ひとことで：ドラフト層が最大 3 個の token を先に推測します。ターゲットモデルは、それらを 1 つのウィンドウに入れて 1 回で計算します。左から右へ比べていき、最初に食い違った所までを受理し、残りはすべて破棄します。食い違った所ではターゲットが自分の選択を出すので、1 ラウンドで必ず 1 個以上進みます。これは、CPU の投機実行や、データベースの「まず仮書きし、次にコミットし、誤りならロールバックする」と同じ考え方です。

18.1 先に推測して、あとで検証する：外れても損はしない

第 16 章で見たとおり、複数の token をまとめて計算するほうが、1 個ずつ計算するよりずっと安上がりです。重みを 1 回読むだけで済むからです。ところが答えを書くときは、次の token が決まるまで、その次の token は分かりません。まとめて計算できないのです。投機的デコーディング（speculative decoding）は、これを次のように解決します。まず、安い方法で次の数 token を推測します。次に「前回の結果 ＋ これらの推測」を 1 つのバッチにして、大きなモデルに 1 回で計算させます。大きなモデルは、各位置で「ここなら私はこう書く」と答えを出します。それを推測と見比べれば、どれが当たったかが分かります。

推測を担当するのがドラフト（draft）、最終判断を下す大きなモデルがターゲットモデル（target）です。Strata のドラフトは、モデルに最初から付いている MTP（マルチトークン予測）層から来ます。最大 3 個を推測します。回答が前の文を繰り返しているとき（コードの修正や原文の引用など）は、前の文から最大 5 個を「コピーして」くることもできます。これを prompt lookup と呼びます。1 回の検証で 48 層すべてを通り、1 ラウンドあたり平均 2.4〜3.2 個の token が進みます。[S02] 図 18-1 で比べてみましょう。

なぜ、1 ラウンドで何個か多く検証しても、それほど負担にならないのでしょうか。ソースコードに勘定が書いてあります。1 つのウィンドウのコストは、「密な重みを 1 回だけ読み、T 個の token で共有する」ことに、「T 個の token それぞれがヒットしなかったエキスパートの和集合を、CPU で計算する」ことを足したものです。実際のデコード記録で集計すると、CPU で計算するミス側のエキスパートは、T ＝ 2 のとき 1 token の場合の 1.75 倍、T ＝ 3 のとき 2.4 倍、T ＝ 4 のとき 3.05 倍でした。[S08] token を 1 個多く検証する限界コストは、もう 1 ラウンド回すコストよりずっと小さいのです。

推測がどれだけ当たるかで、得られる利益が直接決まります。ソースコードのコメントによると、MTP 層が貪欲デコーディング（greedy）の結果を当てる割合は、1 ステップ目が 0.89、2 ステップ目が 0.86、3 ステップ目が 0.85 です。コード上の事実 上流のドキュメントも、出力速度は文章によって変わると注意しています。ドラフトが受理されるほど速くなり、同じプロンプトでも回答が違えば、速度が数パーセントも違うことがあります。[S03] 毎回いくつ推測するか、そもそも推測する価値があるかは、第 19 章の話題です。

18.2 受理するのは連続した先頭部分だけ

比べるルールは 1 つだけです。左から右へ、最初に食い違った所までを受理する。ウィンドウの 0 行目を、前回のラウンドで確定した token x とします。その後ろがドラフト d₁、d₂、d₃ です。ターゲットモデルは「x の後なら a を書く」「x、d₁ の後なら b を書く」……と計算します。これを順に比べます。

  • ターゲットは x の後に a を選び、ドラフト d₁ ＝ a なので、受理。
  • ターゲットは x、a の後に b を選び、ドラフト d₂ ＝ b なので、受理。
  • ターゲットは x、a、b の後に e を選び、ドラフト d₃ ≠ e なので、ここで停止。d₃ は破棄し、ターゲット自身の e に置き換えます。

Strata の生成ループでは、このルールがたった 1 行のコードです。while (a < T - 1 && window[a + 1] == outv[a]) ++a; のすぐあとに ver.commit(a + 1) が続きます。コード上の事実 ここで outv[t] は、ウィンドウの t 行目の後にターゲットが選ぶ token です。a は受理したドラフトの数です。食い違った所でターゲット自身が選んだ token も出力されます。だから 1 ラウンドで a ＋ 1 個進み、最低でも 1 個は進みます。投機コントローラのコメントにも「この検証の 1 回で、必ず 1 つの token をコミットする」とあります。[S09]

最初の食い違いより後のドラフトは、たとえ「正しそう」に見えても、なぜ必ず破棄するのでしょうか。それは、間違った token の後ろで推測したものだからです。前提がすでに崩れています。下のシミュレータは、まさにこの場面を用意してあります。ステップ実行で第 2 ラウンドを進めてみましょう。

CS を学んだ人へ：このルールの正しさは、数学的帰納法で証明できます。確定済みの履歴 H が、貪欲生成の結果に等しいとします。d₁ が H の後のターゲットの選択に等しければ、H＋d₁ もまだ貪欲生成の結果に等しくなります。以下同様に、最初の食い違いまで続きます。食い違い以降のドラフトは、誤った履歴をもとにしています。帰納の鎖が切れているので、受理する理由はありません。正しさは、先頭から続く部分に沿って連鎖的に成り立ちます。ウィンドウの各位置が、個別にチェックを付けられるわけではありません。

貪欲デコーディング（各ステップで確率が最大の token を取る方法）なら、Strata の検証ウィンドウは、さらに強い保証を与えます。ウィンドウの t 行目の結果は、通常の 1 個ずつの生成のその位置の結果とビット単位で一致します。ウィンドウ内の各カーネルは、1 token 用のカーネルそのものか、token ごとの演算が 1 token 版と完全に同じだからです。そのため、「ドラフトが受理された」ことは「通常の生成でもそれを書いた」ことと、ちょうど同じ意味になります。[S08]

18.3 投機実行：CPU は昔からやっている

「先に推測して進め、外れたら取り消す」という方法は、言語モデルが発明したものではありません。現代の CPU は、毎秒数十億回もこれをやっています。

投機実行と分岐予測

イメージ：食堂で並んでいると、前の人がまだ「麺にするかご飯にするか」決めていないのに、店の人は、その人のいつもの注文から先に麺を作り始めます。当たれば待ち時間が減ります。外れたら麺を脇に置いて作り直すだけです。無駄になることはあっても、間違った料理を出すことはありません。

定義：CPU はパイプライン（第 16 章で見ました）で命令を実行します。if のような分岐に来たとき、条件がまだ計算できていないと、次にどの命令を取ってくるべきか決まりません。分岐予測器は、過去の履歴から進む向きを推測します。CPU はその向きに実行を続けます。これが投機実行です。大事なのは、投機実行の結果は一時的な場所に置き、正式な状態には書き込まないことです。条件が計算できたあと、当たっていれば結果を「リタイア」（コミット）します。外れていれば、パイプライン中のそれらの命令を捨て、正しい向きからやり直します。

具体的な数字：現代のプロセッサでは、分岐予測の的中率はふつう 9 割を超えます。だから「たまに少し無駄にする」ほうが、「毎回止まって待つ」より、ずっと得です。外れたときの損失は、パイプラインが長いほど大きくなります。

この章との関係：ドラフトが分岐予測、検証ウィンドウが投機実行、commit(a + 1) がリタイアに当たります。どちらも同じ規律を守ります。推測の結果は、照合が済むまで有効にしてはいけません。

参考リンク：Wikipedia：投機的実行 · Wikipedia：分岐予測 · Wikipedia：命令パイプライン

18.4 まず仮書き、次にコミット：トランザクション式の状態管理

難しいのは「取り消し」です。検証ウィンドウが T 行を計算するとき、モデルのさまざまな状態が書き換わるかもしれません。KV キャッシュが T 枠増えます。GDN の再帰状態が先へ進みます。インデクサにキーがいくつか増えます。先頭の 2 行しか受理しなかったなら、残りの変更は、何もなかったことにしなければなりません。これは、データベースの「トランザクション」がまさに解決する問題です。

トランザクションのコミットとロールバック

イメージ：銀行の振込は 2 段階です。A 口座から 100 引き、B 口座に 100 足します。1 段階目が終わったところで停電したら、どうなるでしょう。銀行は、2 つの段階を 1 つのトランザクションにまとめます。全部が有効になるか、何も起きなかったことになるか、のどちらかです。

定義：トランザクションの実行中の変更は、まず一時的な場所（ログやコピー）に記録します。外からは見えません。すべての検査に通ったらコミット（commit）して、変更を一度に有効にします。途中で失敗したらロールバック（rollback）して、一時的な変更を捨て、トランザクション開始前の状態に戻します。ロールバックの実現方法は、よくあるものが 2 つあります。1 つ目は、先にスナップショットを保存し、失敗したら復元する方法です。2 つ目は、入力を記録しておき、確定してから入力どおりにやり直す方法です。ファイルシステムの「ジャーナル」（journaling）も、この考え方を使っています。

具体例：Strata の commit(n) は、「ウィンドウ全体をコミットするか、全部ロールバックするか」ではありません。「先頭の n 行だけをコミットする」のです。教科書のトランザクションより細かい仕組みです。1 つのウィンドウの中で、前半は有効になり、後半はロールバックされます。

この章との関係：状態ごとに、取り消し方が違います。次に 1 つずつ見ていきます。

参考リンク：Wikipedia：トランザクション · Wikipedia：ロールバック · OSTEP：Crash Consistency: FSCK and Journaling（PDF）

Strata の検証ウィンドウは、この点をはっきり書いています。ウィンドウの実行中は、T 個すべての位置について K/V とインデクサのキーを追記しますが、GDN の状態には触りません。そのあと commit(n) が先頭 n 個の token を有効にします。状態ごとに、それぞれのやり方があります。[S08]

  • GDN 再帰状態：ウィンドウの中では、状態をまったく書き換えません。各行の入力だけを保存します。コミットのとき、保存した入力で先頭 n 個の token を再生すると、状態は正しい位置まで進みます。「入力を記録し、確定してからやり直す」方法です。
  • インデクサのキー：まずウィンドウの前に保存したスナップショットを復元し、そのあと受理したキーを追記し直します。コメントに理由が書いてあります。拒否されたキーが、現在のブロックがこのあと使うスロットに入っているかもしれないからです。「スナップショット ＋ やり直し」の方法です。
  • PLE 履歴：n−1 個目の token の後のスナップショットを、そのまま設定します。
  • KV キャッシュ：余分に書いた枠には、何もしません。それらの位置は次のラウンドで処理し直され、どのクエリが読むより前に、新しい値が上書きされます。[S08] 第 17 章の KV ストリーミングも同じ決まりに従います。新しい token は、いつもメモリ上の正本に書きます。だから「ドラフトを拒否した」あとも、無効にすべき VRAM のスロットはありません。コード上の事実

ウィンドウの「行数」と「受理したドラフトの数」は、1 だけ違います。ウィンドウの 0 行目は前回のラウンドで確定した token で、これもこのラウンドで状態に書き込む必要があるからです。ドラフトを a 個受理したときにコミットするのは、a ＋ 1 行です。生成ループのコメントには、こうあります。「ウィンドウの先頭 a ＋ 1 個の token は、今セッションに入った。最後の出力はまだ入っていない。それは次のラウンドの 0 行目だ。」コード上の事実 ドラフト層の位置カウンタも、このずれに合わせて数えます。位置 p のウィンドウで a 個のドラフトを受理すると、次のウィンドウは p ＋ a ＋ 1 から始まります。[S07]

CS を学んだ人へ：新しい種類のシーケンス状態を足すたびに、4 つの問いに答えなければなりません。ウィンドウの実行中に、それに書き込むか。commit(n) で、どうやって先頭部分だけを残すか。拒否された部分は、どうやって無効にするか。非同期の読み書きは、誰が完了を確認するか。これは、データベースに新しいテーブルを足すとき、そのログと復旧を考え抜かなければならないのと同じことです。

18.5 サンプリング時の検証：ターゲットの抽選結果と完全に一致させる

貪欲デコーディングなら、比べるのは簡単です。その行で確率が最大の token が、ドラフトと同じかどうかを見ればいいのです。でもチャットでは、温度付きのサンプリングがよく使われます。毎ステップ、確率に従って 1 つ引きます。抽選の結果はそもそも乱数です。どうやって比べるのでしょうか。

Strata は、ターゲットモデルの抽選を再現できるようにしました。ウィンドウの t 行目の乱数は、「シード」とその行の絶対位置で決まります。そのうえで、サンプリングの全工程（繰り返しペナルティ、top-k、top-p、min-p、温度、最後に累積分布で 1 つ引く）を通します。ドラフトが受理されるのは、その行の抽選結果と完全に等しいときだけです。したがって、出力はシードだけで決まり、ドラフトが何かには依存しません。ドラフトが決めるのは、1 ラウンドで何ステップ進めるかだけです。[S07] 各行の繰り返しペナルティも、「その行より前にあるはずの履歴」で個別に用意されます。通常の 1 個ずつの生成で数えるものと同じです。[S08]

ターゲットの抽選に「ぶつかりやすい」ドラフトを作るには、どうすればいいでしょうか。Strata には、デフォルトで無効の「結合ドラフト」モードがあります。ドラフト層は、いちばん自信のある token をコミットするのをやめます。代わりに、ターゲットと同じサンプリングの工程を使い、ターゲットがこれから使うのと同じ乱数を添えて抽選します。2 つの分布が近ければ、同じ乱数で累積分布から引いたとき、結果が一致する確率は、「最大値を取って、乱数で引いたサンプルにぶつける」ときよりずっと高くなります。ターゲットの抽選は変わらないので、出力される文字も変わりません。[S07] 図 18-5 は、この考え方の模式図です。

注意してください。これは、投機的デコーディングの古典的な論文の方法とは別物です。古典的な方法では、min(1, p ÷ q) の確率でドラフトを受理します。拒否されたときは、修正した分布から 1 つ引き直します。こうして、出力の分布がターゲットと完全に一致することを保証します。[R04] この本で読んだ Strata のコードが使うのは、「ターゲットの抽選結果と完全に等しい」ことで、この式ではありません。2 つの方法は、分布の論証も、乱数の組み立て方も、実装の条件も違います。混ぜて書いてはいけません。

ドラフトが何を推測できるかには、現実的な制限もあります。MTP ドラフト層は、語彙の一部の中からしか token を提案できません。エンジン 0.1.27 以降、この部分集合に、中国語・日本語・韓国語の token がすべて加わりました。上流の実測では、これらの言語の回答が 15〜38% 速くなりました（Q2_0、RTX 5070）。[S03] 日本語のユーザーが得ている高速化の一部は、ここから来ています。

18.6 手を動かす：先頭部分を自分でコミットする

  1. この章のシミュレータ（図 18-2）で 5 ラウンド続けて走らせ、1 ラウンドあたりの平均出力 token 数を記録します。次に k を 1 と 5 に変えて、それぞれ走らせます。3 回の平均を比べましょう。考えてみてください。k が大きいほど、全部当たったときの利益は増えますが、検証も高くつきます。では最適な k は、何で決まるでしょうか。（答えは第 19 章にあります。）
  2. この本のインタラクティブ実験「受理された接頭辞だけをコミットする」を開きます。実際の状態の代わりに、おもちゃの再帰 s ← 0.5s ＋ t を使います。2 つ目のドラフトを拒否させてから、答えてください。位置カウンタだけを戻して再帰状態を復元しないと、どんなエラーが残るでしょうか。この実験は、ウィンドウ 0 行目のずれまでは再現していません。
  3. 図 18-4 を見ながら、「シーケンス内の統計バッファを新しく足す」ときのチェックリストを書きます。そのあと、この章の練習問題の模範解答と比べましょう。

この 3 点を覚えよう

  1. ドラフトが推測し、ターゲットが最終判断をします。比較は左から右へ、最初の食い違いまでを受理します。食い違いより後のドラフトは、たまたま正しくても破棄します。1 ラウンドで a ＋ 1 個の token が進み、最低でも 1 個です。
  2. CPU の投機実行と同じ規律です。推測の結果は、照合の前に有効にしてはいけません。Strata は commit(a + 1) で、ウィンドウの先頭部分だけを有効にします。
  3. 取り消しは、状態ごとに設計します。GDN は保存した入力を再生し、インデクサはスナップショットを復元してから追記し、PLE は対応するスナップショットに戻し、KV は余分に書いた枠が上書きされるのを待ちます。位置を 1 つ戻すだけでは足りません。

よくある誤解：「ドラフト層は小さくて精度が低いから、使うと回答の品質が落ちる。」

落ちません。ドラフトは提案するだけです。どの token も、ターゲットモデル自身の選択（または再現できる抽選結果）と完全に等しくなければ、残りません。推測が下手なら、1 ラウンドに進む量が減って速度が落ちるだけで、書かれる文字は変わりません。[S02][S07] 上流は、知っておくべき例外も記録しています。IQ 系列のモデルを使うと、CPU が 1 token を計算するときと、複数 token を計算するときで、エキスパートが 2 種類のカーネルを使い分けます。丸めが少し違うので、温度 0 でも、同じプロンプトがドラフトの違いによって、同じくらいもっともらしい別の回答になることがあります。すべてのグループで複数 token 用カーネルを使うスイッチを入れれば、答えはドラフトに依存しなくなります。[S03]

もう一歩深く：オフセット、非同期コミット、受け入れチェックリスト

ウィンドウ内のいくつかのカウントを、1 つに混ぜない

確定済みの長さを 100 とします。ウィンドウの 0 行目は、位置 100 の token x です。ドラフト d₁、d₂、d₃ は位置 101〜103 を占めます。d₁ だけが受理された（a ＝ 1）なら、2 行（位置 100 と 101）をコミットします。位置 101 の後のターゲットの選択が、次のウィンドウの 0 行目になり、次のウィンドウは位置 102 から始まります。[S07] 数学的には「このラウンドは、ターゲットが 1 つ進めることに、受理したドラフトの数を足したものが進む」と言えます。実装では、ウィンドウの開始位置、行番号、次の位置、commit(n_keep) の意味を 1 つずつ確認します。「受理したドラフトの数」と「コミットした行数」を、同じ変数として扱ってはいけません。結合ドラフトの乱数カウントにも、同じずれがあります。MTP の c 番目の枠で作ったドラフトは、カウンタ c ＋ 1 の行で検証されます。[S07]

各行のペナルティ履歴

繰り返しペナルティは、「この行より前にどの token が出たか」を数えます。ウィンドウの t 行目より前の履歴は、確定済みの内容に、ドラフト 1〜t を足したものです。Strata は、ウィンドウの各行に対して履歴を個別に用意します。0.1.19 より前は 0 行目の分しか用意しておらず、ドラフトの行は、まだ書かれていないスロットを読んでいました。[S08] この種のバグでは、プログラムは落ちません。ペナルティを有効にしているときだけ、結果が通常の生成と、静かにずれていきます。

非同期コミット

GPU が 1 枚のとき、commit() は、グラフの実行が終わるのを待たずに、デフォルトで戻ります。次のウィンドウは同じストリームの後ろに並びます。ドラフト層は、コミットが書いたものを読みません。そのため、コミットと次のラウンドのドラフトを重ねることができます。別のストリームやホストからセッションを読み書きする人（新しいリクエスト、チェックポイント、スナップショット、プリフィルの経路、実行終了）は、先に wait_commit() を呼ばなければなりません。[S08] これは、第 14 章の「同期と非同期」のもう 1 つの例です。速い経路は待ち時間を省きます。その代わり、横から読むすべての人が、自分で待つことを覚えていなければなりません。

ドラフト層の「手抜き」が、出力に影響しない理由

MTP ドラフト層の実装は、いくつかの点で簡略化されています。大きな射影は Q8_0 に量子化されています。アテンションは、見たことのあるすべての枠に対して密に計算します。512 個のエキスパートすべてが VRAM に常駐します（708 MB）。ソースコードにははっきり書いてあります。これらの選択はドラフトの品質にだけ影響し、出力には影響しません。出力される token はすべて、検証ウィンドウが決めるからです。投機的に書き込んだ枠は、インデクサの状態にも触れません。その位置が処理し直されるとき、そのまま上書きされます。コード上の事実

受け入れチェックリスト

投機的デコーディングのテストは、平均受理率だけを見てはいけません。最低でも、次をカバーします。すべて拒否、すべて受理、途中で拒否、コンテキスト上限の近く、終了記号に当たる、途中でキャンセル、繰り返しペナルティが有効、リクエスト間でサンプリングパラメータを切り替える。比べる相手は「同じ固定履歴で、投機を使わない基準の結果」です。ロジット、コミット後の状態、最終的な token が、すべて一致しなければなりません。新しいシーケンス状態を足すときは、18.4 節の 4 つの問いに 1 つずつ答え、対応するテストを足します。
