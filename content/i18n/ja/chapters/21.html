2 枚なのに、なぜ 2 倍にならないのか

Strata の README に、こんな一文があります。2〜3 枚の GPU（グラフィックスカード）でこのモデルをいっしょに動かせます。上流レポート[S01] 上流のドキュメントには実測値も載っています。RTX 5080 に RTX 3090 を足すと、長いプロンプトを読む速さは約 2 割上がります。ところが、答えを生成する速さは、5080 だけのときとほぼ同じです。

24 GB の GPU をもう 1 枚挿したのに、答えは速くなりません。お金はどこへ消えたのでしょうか。この章では 3 つのことをはっきりさせます。2 枚の GPU がどう分担するのか。なぜ 1 つの token は速くならないのか。そして、2 枚の GPU のあいだで、実際にどれだけのデータをやり取りするのか。

ひとことで：Strata は 48 層を前半と後半に切り、1 枚が 1 つの区間を担当します。1 つの token は、前の GPU を通ってから後ろの GPU を通ります。だから token 1 個あたりの速さは変わりません。本当の利点は 2 つです。2 枚ぶんで、エキスパートを 2 倍近くキャッシュできること。そして、プロンプトを読むとき、2 枚が流れ作業のように同時に働くことです。

21.1 2 枚の GPU は、どう分担できるか

2 人で引っ越しをするところを想像してください。1 人が寝室、もう 1 人がリビングを運ぶ方法があります。2 人で大きなソファを 1 つ抱える方法もあります。それぞれが自分の家を運ぶ方法もあります。どれも「2 人でやる」ことですが、相談する回数はまったく違います。複数の GPU でも同じで、よくある分担は 3 種類あります。図 21-1 を見てください。

Strata が使うのは 1 つ目のレイヤー分割です。モデルの層を順番に何区間かに切り、GPU ごとに連続した 1 区間を担当させます。上流のドキュメントははっきり書いています。これはパイプライン（層ごとの）並列であり、テンソル並列ではありません。1 つの token は、検証ウィンドウごとに 1 回だけ、ある GPU から次の GPU へ渡ります。層ごとに 2 回渡るわけではありません。上流レポート

コードでは、この仕組みは set_stage という関数にあります。各ステージ（stage、1 枚の GPU が担当する層の区間）は、[layer_begin, layer_end) の層だけを実行します。第 0 層から始まらないステージは、前の区間からデータを受け取ります。最後の層の手前で終わるステージは、データを次へ渡します。このとき出力ヘッドは持ちません。コード上の事実[S08]

パイプライン並列とテンソル並列

大きなモデルが 1 枚の GPU に収まらないとき、切り方は大きく 2 つあります。横に切って、層ごとに区間を分ける方法がパイプライン並列です。工場の流れ作業のように、第 1 工程が終わったら第 2 工程へ渡します。縦に切って、同じ層の大きな行列を何枚かに分ける方法がテンソル並列です。2 人でソファを抱えるように、一歩ごとに「せーの」と声をかけて合わせます。

2 つの切り方は、コストのかかる場所が違います。パイプラインは、区間の境目で 1 回データを渡すだけです。ただし 1 つのデータは、前の区間を通り終えてからでないと次の区間に入れません。1 つのデータの待ち時間は、減らせません。テンソル並列では、同じ層を 2 枚の GPU が本当に同時に計算します。その代わり、層を計算するたびに、2 つの半分の結果を合わせる必要があります。古典的な Megatron-LM の方式では、Transformer の 1 層の順伝播で、この合わせる作業を 2 回します。48 層なら 96 回です。

3 つ目はデータ並列です（ここではリクエスト並列と呼びます）。各 GPU がモデル全体を持ち、別々のリクエストを処理します。GPU 間の相談はほとんど要りません。ただし、1 枚にモデル全体が収まることが前提です。

Strata が向き合うのは「1 枚に収まらない」問題です。そして家庭用 PC の GPU 同士は、ふつう PCIe でつながっているだけで、専用の高速線はありません。そこで、相談がいちばん少ないレイヤー分割を選びました。

21.2 1 つの token は、やはり層を順番に待つ

答えを生成するとき、token は 1 つずつ、第 0 層から第 47 層まで進みます。第 19 層は第 18 層の結果を使い、第 18 層は第 17 層の結果を使います。この依存の鎖は切れません。だから、前の GPU が前半を計算しているあいだ、後ろの GPU は待つしかありません。後ろの GPU が後半を計算しているあいだは、前の GPU も遊んでいます。図 21-2 を見てください。

上流ドキュメントの実測も、これを裏づけています。RTX 5080 に RTX 3090 を足しても、生成速度は 5080 単体とほぼ同じです。コードを書かせたときは、少し速くなりました。上流レポート（Coder モデル、32K コンテキスト、CPU は Ryzen 9 9950X3D。物語の生成は、単体が毎秒 83〜87 token、2 枚の最良の分割が毎秒 84 token。コードの生成は、それぞれ 88〜105 と 110。ドキュメントにエンジンのバージョンは書かれておらず、結果ディレクトリの日付は 2026-09-29 です。）

では、2 枚目の GPU は何のためにあるのでしょうか。狙いは容量です。第 10 章で見たとおり、VRAM に載らなかったエキスパートは CPU が RAM の上で計算します。CPU の計算は遅いのです。レイヤー分割をすると、各 GPU は自分が担当する層のエキスパートだけをキャッシュします。2 枚ぶんを合わせると、1 枚のときの約 2 倍のエキスパートをキャッシュできます。上流ドキュメントによると、Coder モデルでは、16 GB と 24 GB の 2 枚で、ほぼ全エキスパートが収まります。「速度はここから来る」のです。生成のあいだ、CPU はほとんど出番がありません。上流レポート 図 21-3 は、各 GPU に何を置くかを示します。

代償にも注意してください。既定では、密な重みはどの GPU にもコピーを置く必要があります。どの GPU にも、自分のセッション状態とプロンプト用バッファが要ります。だから上流は、VRAM が 8 GB に満たない GPU を一緒に使うことを勧めていません。上流レポート v0.1.39 は、オプションのスイッチ STRATA_STAGE_TRIM=1 を加えました。各 GPU は自分の担当する層の密な重みだけを読み込み、節約できた VRAM をエキスパートキャッシュに回します。上流は 16 GB の MI50 を 2 枚使って Coder モデルを動かし、VRAM 内のエキスパートが 8,819 個から 10,626 個に増え、生成が毎秒 39.2 token から 41.7 token に上がったと報告しています。このスイッチは今のところ手動でオンにします。エキスパートを置く場所が変わるので、出力がわずかに違うこともあります。上流レポート v0.1.39 では、分割位置を手で指定したときにしか効きませんでした。v0.1.40 からは、自動分割でも後ろのほうの GPU も重みを削減できます。先頭の GPU は、今も手動指定のときだけ削減します。先頭の GPU の VRAM は、分割位置が計算されるより前に割り振られてしまうからです。コード上の事実

既定では、生成のとき 2 枚の GPU はこのように交代で働きます。v0.1.40 は、任意のスイッチ --pipeline-windows 2 を加えました。これを使うと、生成のときも 2 枚が同時に忙しくなります。後ろの GPU がまだ第 K ウィンドウを検証しているあいだに、前の GPU はもう第 K+1 ウィンドウを計算し始めます。コード上の事実 第 K+1 ウィンドウは「推測」です。第 K ウィンドウが丸ごと受理され、次のトークンがドラフト層の予測どおりになる、と推測します。当たれば、次のウィンドウは半分終わっています。外れたら、前の GPU は、あらかじめ保存しておいた再帰状態を元に戻し、本当のトークンで計算し直します。これは第 18 章の投機的デコーディングの「先に推測して、あとで検証する」という考え方そのものです。それを 2 枚の GPU のあいだで使っています。上流は RTX 4060 Ti と RTX 5080 で測り、生成速度が平均で毎秒 72.4 token から 84.0 token（+16%）に上がったと報告しています。代償は、各 GPU がエキスパートキャッシュに回せる量が 160 MiB 減ることです。オンにできるのは、GPU が 2 枚で、サーバーモードで、ドラフト層があるときだけです。初期状態ではオフです。上流レポート 依存の連鎖が断たれたわけではありません。同じトークンは、やはり前の GPU を通ってから後ろの GPU を通ります。2 枚が同時に忙しいのは、別々の 2 つのウィンドウを扱っているからです。

21.3 プロンプトを読むときに、パイプラインが回り出す

プロンプトを読むときは事情が違います。長いプロンプトは、読む前から全部分かっています。Strata はそれを多くのチャンク（chunk）に切って、1 チャンクずつ読みます。分割については第 16 章で見ました。すると、2 枚の GPU は作業をずらせます。後ろの GPU が第 c チャンクを読んでいるとき、前の GPU はもう第 c+1 チャンクを読んでいます。prefill インターフェースのコメントが書いているのは、まさにこれです。最後の層の手前のステージは、データを2 つのピン留めメモリのバッファにコピーします。別のスレッドで次のステージを起動します。「次のステージが第 c チャンクを読んでいるあいだ、このステージが第 c+1 チャンクを読めるように」です。コード上の事実[S12]

洗濯にたとえましょう。洗濯機は 1 回分を洗うのに 4 分、乾燥機は 1 回分を乾かすのに 5 分かかるとします。洗濯物が 1 回分なら、どうやっても 9 分です。8 回分あるなら、1 回目が乾燥機に入ったとき、2 回目を洗濯機に入れられます。乾燥機がリズムを決めます。5 分ごとに 1 回分が出てきます。合計は、最初の 4 分に、乾燥 8 回ぶんの 40 分を足して、44 分です。全部を直列にやれば 8 × 9 = 72 分かかります。

最初の「乾燥機が 1 回目を待っている」時間と、最後の「洗濯機にもう洗うものがない」時間を、バブルと呼びます。パイプラインのどこかの持ち場が、空いて待っている時間です。下のシミュレータは、2 枚の GPU を時間軸で描きます。各区間の時間、チャンク数、転送時間を変えて、バブルがどこにできるか見てみましょう。

シミュレータの結論を、上流の実測と照らし合わせましょう。同じ 5080 に 3090 を足した構成で、16K のプロンプトを読む速さは、単体の毎秒 1,726〜2,017 token から 2,039 token に上がりました。28K では 1,970 から 2,357 token に上がりました。ドキュメントは「各 GPU が自分の層を読み、そのあいだ、もう 1 枚が次のチャンクを読む」と説明しています。速度の向上は約 18%〜20% です。上流レポート（条件は前の節と同じ。）

CS を学んだ人へ：これは、コンピュータ構成の授業で習う命令パイプラインと同じことです。5 段のパイプラインは、1 つの命令を速くしません。毎サイクルどれかの命令が完了するようにするだけです。スループットは、いちばん遅い段で決まります。最初の充填と、依存で止まる分がバブルです。レイヤー分割では、「段」が層の 1 区間で、「命令」がプロンプトの 1 チャンクです。

21.4 受け渡す荷物の大きさと、道の広さ

2 枚の GPU が受け渡すとき、実際には何を渡すのでしょうか。直感では、層と層のあいだを流れるのは 2560 次元のベクトル、つまり 2560 個の数です。ところが Strata の受け渡しは、もっと大きいのです。verify.hpp は、受け渡しバッファに token ごとに 3 つのものを入れると定めています。残差 R（hc × n_embd 個の数）、前の層でまだ書き戻していないベクトル 1 本（n_embd 個の数）、そして hc 個の注入係数です。コード上の事実[S08] モデルの形状 hc = 4、n_embd = 2560 [S04] を代入します。

4 × 2560 + 2560 + 4 = 12,804 個の float ＝ 51,216 バイト / token

なぜ 2560 個では足りないのでしょうか。このモデルの残差は、もともと 2560 次元のベクトル 4 本です。しかも最後の層には、書き戻しが次の層の冒頭まで延期されているものがあります。次のステージが「分割していないときと同じように」続きを計算するには、これらがすべて必要です。コードのコメントによると、この分割はビット単位で一致します（bit-exact）。分割してもしなくても、計算結果はまったく同じです。コード上の事実[S08]

プロンプトを読むときに受け渡すのは、残差の部分です。token ごとに 4 × 2560 個の float で、40,960 バイトです。既定の 1 チャンクは 2048 token なので、2048 × 40,960 = 83,886,080 バイト、約 84 MB です。コード上の事実（src/prefill/prefill.cpp）教育用の試算 答えを生成するときは、ドキュメントによると、検証ウィンドウごとに 1 回受け渡し、「数百 KB、ピン留めメモリ経由」です。上流レポート token 1 個あたり 51,216 バイトで計算すると、5 token のウィンドウは約 256 KB で、ぴったり合います。

荷物の大きさが分かりました。次は、道の広さです。次のコラムで、2 枚の GPU をつなぐ道を見ます。

インターコネクト帯域：PCIe と NVLink

GPU は、マザーボードの PCIe スロットに挿します。PCIe はシリアルバスで、何本かのレーン（lane）を並べてできています。何車線もある道路のようなものです。「×16」は 16 レーン、「×4」は 4 レーンです。PCIe は、世代が上がるたびに、1 レーンの速度が倍になります。

片方向の理論ピークで言うと、PCIe 3.0 ×16 は約 15.8 GB/s、PCIe 4.0 ×16 は約 31.5 GB/s、PCIe 5.0 ×16 は約 63 GB/s です。×4 のスロットに挿すと、4 分の 1 になります。

NVLink は、NVIDIA が GPU 同士のあいだに引く専用の高速線です。データセンターの H100 には NVLink 4.0 のリンクが 18 本あります。両方向の合計が 900 GB/s で、片方向では約 450 GB/s です。PCIe 4.0 ×16 の十数倍にあたります。家庭用の 2 枚構成には、ふつうこれがなく、PCIe を使うしかありません。図 21-5 で、これらの道を並べて比べます。

帯域のほかにレイテンシもあります。1 バイトだけ送るときでも、起動と同期の固定コストを払います。大きな荷物を 1 回送るなら、レイテンシは 1 回だけです。小さな荷物を 96 回送るなら、96 回払います。第 5 章で帯域とレイテンシを詳しく見ます。第 1 章の「メモリ階層」のコラムには、各層の帯域の比較があります。

参考リンク：Wikipedia：PCI Express · Wikipedia：NVLink · NVIDIA NCCL ドキュメント：複数 GPU 通信の概要

21.5 各 GPU は、自分の層だけを担当する

層を切ったら、各 GPU は自分の「記憶」も持たなければなりません。各層の KV キャッシュや再帰状態です。初期のやり方では、どのステージも 48 層ぶんすべての状態を確保していました。実際に動かすのは、その一部の区間だけなのにです。session.hpp のコメントは、これを「モデル全体の大きさのバッファという、昔からの欠点」と呼んでいます。今は、各セッションが [layer_lo, layer_hi) の層の状態だけを持ちます。コード上の事実[S13]

ここに、間違えやすい点があります。コードの中の層は、今も全体での通し番号で数えます。ところが配列には、自分の区間の数行しか入っていません。だから g 番目の GDN 層の状態を取るときは、まず、この区間の最初の GDN 層の番号 gdn_ord0 を引かなければなりません。引き間違えると、別の層の状態を読んでしまいます。しかも、エラーは出ません。ある区間に QSA 層が 1 つもないときでも、コードは「主」の QSA 状態を 1 つ確保します。回転位置埋め込みのテーブルのように、モデル全体で共有するものを、そこから読むからです。コード上の事実[S13]

どの層で切るかにも、工夫があります。ある区間の層が何バイト必要かを計算する関数 session_bytes は、純粋な算術です。だから、メモリを確保する前に、候補の切り方の「見積もり」を出せます。コード上の事実[S13] 上流のドキュメントによると、既定の自動モードは、2〜4 枚の GPU のすべての切り方を試します（4 枚は v0.1.40 で加わりました）。そして、各 GPU のキャッシュにいちばん多くの「人気のエキスパート」が収まる切り方を選びます。起動ログに選択が表示されます。たとえば「K = 19、キャッシュは 12,288 個のプロファイル項目のうち 11,767 個を収められる」です。上流レポート

最後はセーブです。第 20 章でセッションのスナップショットを見ました。プロンプトを読んでいるとき、前の GPU は、後ろの GPU より 1 チャンク以上進んでいることがよくあります。ある瞬間に、2 枚の状態をそのままつなぎ合わせたらどうなるでしょう。「前半は第 3 チャンクまで読み、後半は第 2 チャンクまで読んだ」という、つぎはぎの怪物ができます。図 21-7 を見てください。

Strata は、各ステージにコールバック on_stage_chunk を持たせています。各 GPU が 1 チャンクを読み終え、自分の状態がちょうどそのチャンクの末尾に止まっているときに、呼び出します。コメントには、最後のステージが報告する時点で、前のステージは「すでに 1 チャンク以上先に進んでいる」と書かれています。だから、プロンプトの途中でセーブするときは、ここで各ステージの分を取るのです。コード上の事実[S12]

21.6 手を動かす：バブルを探し、GPU を足すべきか考える

この章には、独立した実験ページがありません。2 つのインタラクティブ図が、実験台です。次のように遊んでみてください。

  1. 「2 枚の GPU のパイプライン」で、a = 4、b = 5 に固定し、チャンク数を 1 から 8 まで増やします。そのたびに合計時間を記録して、5N + 4 を確かめます。次に、転送時間を 1 ms にして「token 1 個だけ計算」を押し、2 枚のほうがなぜ 1 枚より遅くなるのか見ます。
  2. a と b を大きくアンバランスにします（たとえば 2 と 8）。速いほうの GPU が、どれだけ待つか見ましょう。これが、上流が「いちばん速い GPU を先頭に置き、自動分割にキャッシュ能力で層を割り当てさせる」ことを勧める理由です。上流レポート
  3. 「受け渡し 1 回にかかる時間」で、接続を何種類か切り替え、遅延を変えます。テンソル並列とレイヤー分割の差は、おもにバイト数から来るのか、回数から来るのか見ましょう。

上流のドキュメントには、実用的な経験則もいくつかあります。シミュレータの結論を使って理解できます。上流レポート

  • ずっと遅い GPU を、数合わせで足さないこと。5080 と 3090 に、さらに RTX 2080 Ti を足すと、生成速度はかえって毎秒 68（物語）と 90（コード）token に下がりました。GPU が 1 枚増えるたびに、ウィンドウごとの受け渡しと待ちが 1 回ぶん増えます。
  • 1 枚に収まるなら、分割しないこと。0.1.31 版に、オプションのスイッチが加わりました。1 枚目の GPU に、プロファイル済みのエキスパートとコンテキストがすべて収まるときは、その 1 枚だけを使います。R9700 32 GB に RX 9070 XT を足した構成で Coder モデルを動かすと、オンにしたとき、4K のプロンプトが毎秒 1,244 から 1,776 token に上がりました。生成は約 51 から約 60 に上がりました。一方、16K のプロンプトは約 5% 遅くなりました。
  • 古い GPU は実験的な経路になります。マルチ GPU のドキュメントには、どの GPU もコンピュート能力 7.5 以上（RTX 20 シリーズ以降）が必要、と今も書かれています。v0.1.39 は、Pascal や Volta のような古いカード向けに、実験的な CUDA 12 エンジンも加えました。古いカードを扱うドキュメントには、V100 と RTX 30、40 が 1 つのモデルを共有するときは、両方のカードがこのエンジンで動く、ともあります。このドキュメントには、メンテナーはこれらのカードを持っておらず、コンパイルできることと単体テストが通ることしか確認していない、とも書かれています。ところが v0.1.40 のリリースノートには、メンテナーが P100（sm_60）を 1 枚手に入れ、3 種類の量子化で 10/10 一致を確認した、とあります。Volta の実機は今もありません。複数のドキュメントの言い方が違うので、「どのカードに対応するか」も、バージョンと出典を見る必要があります。

この 3 点を覚えよう

  1. 複数 GPU の分担は 3 種類です。レイヤー分割（パイプライン並列）、テンソル並列、リクエスト並列。Strata はレイヤー分割を使います。GPU 間の相談がいちばん少なく、家庭用の PCIe で足りるからです。
  2. 1 つの token の層は、順番に 1 層ずつ計算するしかなく、レイヤー分割はそれを速くしません。2 枚の GPU がもたらすのは、エキスパートを 2 倍キャッシュできることと、プロンプトを読むとき 2 枚が作業をずらせることです。合計時間 = a + b + (N − 1) × max(a, b)。
  3. 受け渡すのは、数学的な状態の完全なセットです。生成時は token 1 個あたり 51,216 バイト、プロンプトを読むときは 1 チャンクあたり約 84 MB です。バイト数は多くなく、回数も少ないので、通信コストは小さくなります。セーブは、各 GPU が同じチャンクを読み終えた時点にそろえます。

よくある誤解：「GPU を 2 枚挿せば、生成速度が 2 倍になる。」

同じ token の層には、前後の依存があります。2 枚は交互にしか計算できません。上流の実測では、5080 に 3090 を足しても、生成速度は 5080 単体とほぼ同じでした。さらに 2080 Ti を足すと、かえって遅くなりました。2 枚で速くなるのは、増えた VRAM のおかげで CPU が計算するエキスパートが減ることと、長いプロンプトを読むときのパイプラインのおかげです。「計算力が 2 倍に積み重なる」わけではありません。上流レポート

もう一歩深く：受け渡しの契約、ダブルバッファのプロトコル、2 枚の効果の評価方法

受け渡しが、なぜ 12,804 個の数でなければならないか

Verifier::set_stage のコメントには、受け渡しの token ごとに、残差 R（hc × n_embd）、最後の層でまだ書き戻していないベクトル bo（n_embd）、inject（hc）が入ると書かれています。次のステージは、最初の層を読むときにこの書き戻しを「折り込み」ます。分割しないウィンドウのやり方と完全に同じなので、分割はビット単位で一致します。2 つのポインタは、どちらもデバイスから見えるメモリでなければなりません（マップされたピン留めメモリ。2 つのステージが 2 枚の GPU にあるときは、portable でもあること）。コード上の事実[S08] 受け渡す浮動小数点数の個数は handoff_floats が返します。式は hc*n_embd + n_embd + hc そのものです。[S08]

2560 次元の「隠れ状態」だけを渡すと、残りの 3 本の残差と、延期された書き戻しが失われます。結果はクラッシュしません。静かに計算が間違うだけです。教訓はこうです。デバイスをまたぐ通信の形式には、数学的な契約の全体を反映させなければなりません。「隠れ次元は 2560 だから」と、手軽に削ってはいけません。上流には、検査用のモードもあります。--layer-split K --split-device 0 は、2 つのステージを同じ 1 枚の GPU で動かします。受け渡しがビット単位で一致することを確かめるためのもので、高速化モードではありません。上流レポート

ダブルバッファの受け渡しプロトコル

prefill.cpp では、前のステージが初期化のときに cudaHostAlloc(..., cudaHostAllocPortable) で、ピン留めメモリを 2 つ確保します。それぞれが、プロンプト 1 チャンクぶんの残差の行（chunk × D × 4 バイト、D = 4 × 2560）を収められます。コード上の事実 1 チャンクを読み終えるたびに、次の 4 つを順に行います。

  1. 残差の行を VRAM から、現在の受け渡しバッファにコピーし、コピーの完了を待つ。
  2. on_stage_chunk を呼ぶ。このとき、このステージの状態はちょうどこのチャンクの末尾に止まっている。
  3. 次のステージが、前のチャンクを読み終えるのを待つ（上書きされる直前のバッファを、まだ読んでいる状態にしないため）。
  4. 別のスレッドで、次のステージにこのチャンクを読ませ始め、もう一方のバッファに切り替えて、次のチャンクを読み続ける。

前のステージの 1 チャンクあたりの所要時間を a′（コピー出しを含む）、後ろのステージのそれを b′（コピー入れを含む）とします。手順 3 の意味は、前のステージが第 c+1 チャンクを読み始める時刻が、後ろのステージが第 c チャンクを読み始める時刻に等しい、ということです。ここから導けます。後ろのステージの隣り合う 2 チャンクの開始時刻は、max(a′, b′) だけ離れています。第 1 チャンクは a′ の時点で始まり、最後のチャンクは開始から b′ で終わります。だから合計時間 = a′ + b′ + (N − 1) × max(a′, b′) です。a′ = 4、b′ = 5、N = 8 なら 44 ms で、チャンクごとの直列なら 72 ms です。教育用の試算 この章のシミュレータは、このモデルを使っています。tests/viz-21.test.cjs では、チャンクごとに依存とバッファのルールを検査しています。

GPU が 3 枚以上のとき、v0.1.39 は手順 3 の待ち方を変えました。以前は、次のステージがチャンクを読み終えたあと、そのステージ自身の次のステージも待つ必要があり、待ちが最後の GPU まで順に伝わっていました。いまは各ステージが直接の後続だけを待ちます。途中のステージはチャンクを渡したらすぐ戻り、プロンプト全体を読み終えたところでまとめて後始末をします。コード上の事実[S12] 上流は RTX 3060 を 4 枚使って、プリフィルが 10%–28% 速くなったと測っています。上流レポート 2 枚のときは途中のステージがないので、パイプラインはこれまでと同じです。

チャンクごとの転送も、重要なリソースを使うなら、a′ か b′ に入れなければなりません。ないものとして扱ってはいけません。PCIe で 2 枚が直接アクセスできるか。RAM を経由する必要があるか。マザーボードのトポロジー。NUMA ノードをまたぐか。これらはどれも、この数字を変えます。Strata は、いちばん保守的な道を選びました。すべて RAM 経由で中継し、GPU 同士の直接アクセスに頼りません。

全体での通し番号と「QSA 層のない区間」

セッション状態のコメントには、こう書かれています。qsa_states と gdn_state は全体での通し番号を保ち、配列は行数が減るだけです。だから、各層の利用者は gdn_ord0 を引く必要があります。以前は qsa_states[0] と書いていた、モデル全体にかかわる使い方（共有の RoPE テーブル、prefill の一時領域の識別、MTP が借りる rope）は、qsa_states[primary] を読むように変わりました。区間に QSA 層がないときも、主の状態を 1 つ確保します。既定の全範囲の確保は、昔のモデル全体の確保と、バイト単位で同一です。コード上の事実[S13] テストでは、「ある区間に QSA 層がない」「切れ目が第 1 層の近くに来る」といった境界ケースを、特に調べる必要があります。

セーブは、同じ境界に属していなければならない

on_stage_chunk の契約はこうです。各ステージが 1 チャンクを読み終え、自分のストリームが同期済みで、状態がこのチャンクの末尾に止まっているときに呼ぶ。最後のステージでは、on_chunk の前に呼ぶ。そのステージ自身のスレッドで動き、現在のデバイスもそのステージの GPU である。コード上の事実[S12] 上流ドキュメントはこう補足しています。セッションのセーブは、各 GPU の状態を保存して復元します。プロンプトの途中のセーブは、各 GPU がそのチャンクを読み終えた時点で、それぞれ自分の部分を保存します。上流レポート 逆に言えば、最後の GPU が完了を報告してから、前の GPU の「現在の状態」を取りにいくと、もっと先のチャンクの状態が取れてしまいます。そのセーブは整合しません。

2 枚の何が速いのかの判断

「2 枚のほうが 1 枚より速い」ことから、そのまま「パイプラインの効率が高い」とは言えません。増えた VRAM がエキスパートのヒット率を上げ、CPU の計算を減らしている。そちらが主な利益かもしれません。切り分けて測ります。各 GPU のエキスパートのヒット率、CPU プールの仕事量、受け渡しの所要時間、各ステージの所要時間です。上流の自動分割自体も、重点を示しています。選ぶのは「キャッシュにいちばん多くの人気エキスパートが収まる」切り方です。均等に分けるときは、いちばん埋まった GPU に最大の空きを残します。上流レポート

まだカバーしていない、または条件つきの場合

  • Windows と WSL2 の WDDM ドライバでは、エキスパート領域のうち 8 GiB だけをピン留めします。残りは、ピン留めのステージングリングを経由して流します。Linux のドライバには、この上限がありません。上流レポート
  • どの GPU にも、既定では密な重みのコピー（v0.1.39 からは STRATA_STAGE_TRIM=1 で自分の層だけを読み込めます）と、自分のプロンプト用バッファを置きます（既定のチャンク 2048 では 1 枚あたり約 1.5 GB）。そのため、8 GB に満たない GPU を一緒に使うことは勧められません。NVIDIA と AMD の GPU の混在はサポートしません。上流レポート
  • 1 チャンクに収まるプロンプトでは、2 つのステージが順番にしか読めず、どちらかの GPU が必ず遊びます。v0.1.39 はオプションの STRATA_PREFILL_HELP=1 を加えました。遊んでいる GPU が、自分の PCIe を通してエキスパートの一部を運び、計算したあと結果を送り返します。上流は RTX 3090 を 2 枚使って測り、1.1K のプロンプトが毎秒 496 token から 723 token に上がりました。約 3.3K 以上では分担をしません。そこでは 2 つのステージがもう重なっているからです。丸め方が既定の経路と違い、出力がビット単位で同じにならないので、手動でオンにします。上流レポート
  • Strata には、もう 1 つの 2 枚構成のモード --peer-device があります。2 枚目の GPU はエキスパートキャッシュとしてだけ使い、活性化と結果は、NVLink やほかの GPU 間アクセス経路で往復します。--layer-split とは排他で、どちらか一方しか選べません。上流レポート
  • 受け入れテストは、理想的な 2 枚のトポロジーで 1 回通すだけでは足りません。リクエストのキャンセル、極端に短い最後のチャンク、2 枚目の GPU のエラー、GPU 間アクセスが使えない場合も試します。そして結果を、1 枚の場合とバイト単位で比べます。
