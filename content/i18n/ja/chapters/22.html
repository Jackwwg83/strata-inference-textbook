見たことがあるかも

オープンソースのソフトをダウンロードするとき、リリースページにファイルがずらっと並んでいることがあります。windows-x64、linux-x64、macos-arm64……同じプログラムなのに、なぜこんなにたくさん用意するのでしょうか。

Strata の README の冒頭には、NVIDIA または AMD のグラフィックスカード、Windows または Linux と書かれています。上流レポート[S01] 原理ドキュメントはもっと端的です。NVIDIA（CUDA）と AMD（HIP）のカードで動くのは同じエンジンで、ただそれぞれ 1 回ずつコンパイルするだけ、というのです。[S02] この章では 2 つの問いに答えます。同じソースコードは、どうやって別々のマシンで動くプログラムになるのか。そして「動いた」ことは、何をどこまで証明するのか。

ひとことで：チップはそれぞれ自分の命令しか分かりません。Strata はソースを 1 つだけ書き、コンパイルスイッチ、条件付きコンパイル、そして CUDA→HIP の「名前の置き換え表」を使って、NVIDIA 版と AMD 版の 2 つのエンジンを作ります。CPU 側は、起動時に CPU が使える命令を問い合わせてから、AVX-512 か AVX2 のカーネルを選びます。コンパイルできた、テストに通った、実機で動いた、メンテナが検証した。この 4 つは、強さの違う 4 段階の証拠です。

22.1 同じレシピ、3 つの台所

レシピを書いて、3 軒のレストランに送るところを想像してください。1 軒はガスコンロ、1 軒は IH、1 軒はオーブンしかありません。レシピの「3 分炒める」は、各店が自分の設備での操作に読み替える必要があります。

プログラムも同じです。プログラマが書くのはソースコード、つまり人間が読める文字です。チップが実際に実行するのは機械語、つまり 2 進数の命令の列です。チップがどの命令を実行できるか、各命令をどう符号化するかは命令セットが決めます。「この台所にどんな電化製品があるか」にあたります。ソースコードを、ある命令セットの機械語に翻訳する仕事がコンパイラです。

図の sm_120 や gfx1100 はカードのアーキテクチャ番号で、台所の型番にあたります。Strata のビルドスクリプトは、NVIDIA カードの compute capability（計算能力）が 7.5 以上、つまり RTX 20 シリーズ以降であることを求めます。AMD 側は明示的なリストに載ったものだけを受け付け、リスト外のアーキテクチャはエラーにします。コード上の事実 v0.1.39 は、実験的な道をさらに 2 本開きました。Pascal や Volta の古いカード向けの CUDA 12 エンジンと、gfx906 向けの別ビルドです。22.3 節で触れます。上流レポート

コンパイラ、命令セット、条件付きコンパイル

命令セットは、ハードウェアとソフトウェアの間の約束です。チップは「この命令なら分かります」と約束し、ソフトウェアはその命令だけで話しかけます。同じファミリーのチップは、少しずつ新しい命令を足していきます。たとえば x86 CPU ファミリーでは、まず AVX2 ができ、その後もっと幅の広い AVX-512 が加わりました。古いチップは、知らない命令に出会うと「不正命令」と報告して、プログラムをクラッシュさせます。

コンパイラはソースコードを機械語に翻訳します。C と C++ のコンパイルは 2 段階です。まずプリプロセッサが文字の加工をし、次にコンパイラ本体が翻訳します。プリプロセッサの仕事は 3 つあります。#include したファイルをそのまま貼り込むこと。#define で定義したマクロを名前で置き換えること（「検索と置換」のようなものです）。そして #if の条件に合う 1 つの分岐だけを残し、ほかの分岐をまるごと消すこと。最後のものを条件付きコンパイルと呼びます。

これがまさに、Strata が AMD カードで「4 バイト内積」を書くやり方です。RDNA3 と RDNA4 のカード（v0.1.40 からは、RDNA3.5 の gfx1150 と gfx1151 も）は sudot4 命令を 1 つ使います。RDNA2 にはこの命令がないので、古い sdot4 を使います。RDNA1 の gfx1012 には sdot4 もないので、短いアセンブリを使い、4 回の乗算と 2 回の 3 数加算で同じ結果を組み立てます。それ以外の場合（v0.1.40.2 で加わった RDNA1 の gfx1010、gfx1011 と、RDNA3 内蔵 GPU の gfx1103 を含む）は、バイトごとに掛けて足すループに戻ります。4 つの道が出す整数はまったく同じで、速さだけが違います。コード上の事実 22.3 節で、実際にコンパイルして確かめます。

さらに読む：Wikipedia：コンパイラ · Wikipedia：命令セット · Wikipedia：C プリプロセッサ（英語） · cppreference：条件付きコンパイル（英語）

CS を学んだ人へ：「コンパイラ」の授業で習うのは、字句解析、構文解析、コード生成という本筋です。プリプロセスはそのすべてより前に行われる純粋なテキスト加工で、文法を理解しません。だからマクロ置換が間違っていると、エラーの位置がとても奇妙になることがよくあります。コンパイラが見ているのは、すでに置き換えられた後のコードだからです。

22.2 CPU：まず使える命令を確かめ、それからカーネルを選ぶ

第 10 章で見たように、GPU にキャッシュされていないエキスパートは、CPU がメモリ上でそのまま計算します。上流ドキュメントの要約では、この計算は AVX-512 か AVX2 のカーネルで行い、i-quant 形式のモデルは ggml のカーネルを使います。上流レポート[S02] ソースを見るともう少し細かく分かれています。i-quant 形式でも、1 グループに複数のトークンがあるときは、Strata 自前のマルチトークンカーネルに切り替わります。コード上の事実 ここでカーネルとは、猛烈に速く走るように特別に書かれた、中心的な計算コードのことです。

AVX2 も AVX-512 も SIMD 命令です。1 つの命令で、ひとならびの数をまとめて処理します（第 13 章で詳しく説明します）。違いは、このならびの幅です。AVX2 のレジスタは 256 ビット、AVX-512 は 512 ビットです。図 22-3 を見てください。

困るのはここです。プログラム全体を AVX-512 でコンパイルすると、コンパイラはどこにでも AVX-512 命令を挿入できてしまい、古い CPU ではクラッシュします。Strata のビルドスクリプトは、いくつかのカーネルのソースファイルにだけ AVX-512 または AVX2 のコンパイルスイッチを付けます（GCC なら -mavx512f のようなオプション、MSVC なら /arch:AVX512 です）。「CPU を調べる」担当のファイルには付けません。だからどの x86-64 CPU でも安全に動きます。コード上の事実

調べるには CPUID を使います。CPU に「自己紹介」をさせる命令で、ビット列が返り、各ビットが 1 つの機能に対応します。Strata は、AVX-512 の 5 つのサブ機能（F、BW、VL、VNNI、VBMI）がすべて揃っているかを確かめます。さらに、スレッドを切り替えるときに OS がこの大きなレジスタを保存してくれるかも確かめます。1 つでも欠ければ、AVX-512 はないものとして扱います。コード上の事実 そのうえで、次の順にカーネルを選びます。

いくつか、立ち止まって見ておきたい点があります。コード上の事実

  • AVX2 がなければ、既成のエンジンは起動しません。Strata 自前の CPU エキスパートのカーネルは、最低でも AVX2、FMA、F16C が必要で、リリース版の ggml-cpu も AVX2 でコンパイルされています。エンジンは CPU の型番を表示し、Intel Haswell（2013 年）、AMD Zen（2017 年）、またはそれ以降の CPU が必要だと伝えます。v0.1.39 からは、メッセージにもう 1 文あります。もっと古い CPU では、setup にそのマシン上で実験版のエンジンをビルドさせられます（STRATA_ISA_FLOOR=avx または none）。このバージョンの ggml-cpu は AVX または SSE4.2 でコンパイルされ、CPU 側のエキスパートの計算はすべてそれが担当します。コード上の事実 上流のインストール文書によると、このバージョンで動くのは i-quant モデルだけで、しかも遅くなります。Ryzen 5 7600 + RTX 5070 でこの道を強制し、エキスパートキャッシュを 1500 スロットに固定したとき、デコードは毎秒 26 token から、AVX 版で 11–17 token、SSE4.2 版で 3.5–3.8 token に下がりました。上流レポート
  • 標準 Q2_0 パッケージには AVX-512 カーネルしかありません。上流のインストールドキュメントによると、setup は AVX-512 CPU でだけ、Q2_0 用に約 40 GB のエキスパートのコピーを追加で書き出し、この高速カーネルに使わせます。上流レポート 起動時にすぐ拒否する理由は、ヘッダのコメントがはっきり書いています。古い CPU のユーザーに、0 秒目で原因を知らせるためです。4000 個目のトークンで不正命令にぶつかるよりずっとましです。
  • 環境変数でも道を変えられます。STRATA_NO_IQ512 を付けると、AVX-512 CPU が AVX2 カーネルに回ります。STRATA_NO_IQ256 を足すと AVX2 カーネルも止まり、ggml だけが残ります。同じマシン、同じプログラムでも、環境変数を変えるだけで計算の道が変わります。v0.1.40 からは、AVX2 カーネルが Alder Lake、Sapphire Rapids とそれ以降の CPU で AVX-VNNI 命令に切り替わることもあります。整数の和は変わりません。STRATA_NO_AVXVNNI=1 で止められます。上流は、結果がビット単位で同じで、行の計算が 4%〜25% 速いと述べています。上流レポート

CS を学んだ人へ：これは「実行時ディスパッチ」で、オブジェクト指向の仮想関数と同じ発想です。呼び出し側は変わらず、実際にどのコードが動くかは実行時に決まります。違いは、決め手がオブジェクトの型ではなく、CPUID が返す機能ビットだという点です。

22.3 GPU：CUDA 流の 1 つのソースから、NVIDIA と AMD の 2 つのエンジンを作る

CPU 側では、1 つのプログラムファイルに 2 セットのカーネルを入れて、実行時に選びます。GPU 側はもっと先へ進みます。NVIDIA と AMD のカードは命令がまったく違い、プログラミングのプラットフォームまで違うので、それぞれ別のエンジンをコンパイルするしかありません。

CUDA と HIP

CUDA は NVIDIA の GPU プログラミングプラットフォームです。C++ の拡張構文、ランタイム関数ライブラリ、そしてコンパイラ nvcc からなります。プログラマはこれで GPU 上で並列に動く関数を書き、cudaMalloc や cudaMemcpy のような関数で VRAM の確保やデータの転送をします。CUDA が作れるのは NVIDIA カードの機械語だけです。

HIP は、AMD が ROCm プラットフォームで提供する対応物です。意図的に CUDA に似せて設計されていて、関数名はほとんどの場合、接頭辞 cuda を hip に変えるだけです。たとえば cudaMalloc は hipMalloc に対応し、意味はほぼ同じです。だから 1 つの CUDA コードは、「名前を変える」だけで AMD カードでもコンパイルできることがよくあります。AMD は、自動で名前を変えるツール HIPIFY も公式に用意しています。

名前の置き換えだけでは済まない違いもあります。GPU は、スレッドを束ねて同期しながら実行します。この束を NVIDIA は warp、AMD は wavefront（略して wave）と呼びます。NVIDIA の束は常に 32 スレッドです。AMD の古いアーキテクチャでは 64、RDNA シリーズでは 32 にもなります。「1 束 32 個」を前提にしたコードを 64 のマシンに持っていくと、間違った結果になります。Strata の HIP バックエンドは wave32 だけをサポートし、起動時にもう一度確認します。コード上の事実 v0.1.39 は、wave64 の gfx906 向けに、手動でオンにするビルドを加えました。これは別の互換層を通り、CUDA の 1 warp を 64 スレッドの wavefront の半分に対応させます。HIP バックエンドとは、どちらか一方しか選べません。上流レポート スレッドや warp については、第 15 章で詳しく説明します。

この章との関係：Strata は、ツールでソースを書き換えるのではなく、「名前の置き換え表」をコンパイル時にすべてのソースファイルへ自動で差し込みます。その仕組みをこれから見ます。

さらに読む：ROCm ドキュメント：What is HIP（英語） · ROCm ドキュメント：CUDA から HIP への移植（英語） · NVIDIA：CUDA プログラミングガイド（英語） · Wikipedia：CUDA · Wikipedia：ROCm（英語）

Strata の GPU コードは CUDA 流の書き方で、.cu ファイルに入っています。src ディレクトリには 56 個あります。そのうち v0.1.40 で加わった 1 つは、RDNA3 カード向けの行列コアカーネルで、AMD ビルドでだけコンパイルされます。HIP ビルドのスイッチを入れると、3 つのことが起こります。コード上の事実

  1. ビルドスクリプトが、すべての .cu ファイルを HIP 言語としてマークし、AMD のコンパイラに渡します。
  2. コンパイルオプションに -include hip_compat/cuda_runtime.h を足し、このシムのヘッダを、すべてのソースファイルの先頭に強制的に差し込みます。ここでシム（shim）とは、2 つの層の間に挟まって違いをならすための、薄いコードの層のことです。
  3. シムの中には、#define cudaMalloc hipMalloc の形のマクロが 91 行あります。そのうちいくつかの名前は、HIP のバージョンやプラットフォームに応じて 2 通りの書き方があり、コンパイルのたびに 1 つだけが残ります。別の cublas_v2.h のシムが、行列ライブラリの名前を受け持ちます。新しい hipBLAS では 17 行、古いバージョン（0.x）ではさらに 15 行で、より低レベルの rocBLAS の名前に直接置き換えます。プリプロセッサが置き換えると、CUDA の名前が HIP の名前に変わります。

ビルドスクリプトは、CUDA と HIP の 2 つのスイッチを同時に入れられないことも定めています。1 回のビルドで作るバックエンドは 1 つだけです。コード上の事実

名前を変えるだけでは足りません。CUDA の GPU 組み込み関数の中には、HIP が RDNA カード向けに用意していないものがあり、シムが自分で実装するしかありません。たとえば 4 バイト内積 __dp4a です。2 つの 32 ビット整数をそれぞれ 4 つの符号付きバイトに分け、対応するもの同士を掛けて、アキュムレータに足します。シムは、カードのアーキテクチャによって 4 つの道に分けます（22.1 節のコラムを見てください）。もう 1 つは、warp 内でデータを交換する __shfl_xor_sync です。シムはまず「32 レーンすべてが参加しているか」を調べ、そうでなければすぐに中断します。この意味づけをこっそり落としたりはしません。コード上の事実

下のシミュレータは、3 行のソースをいろいろなターゲットカードに渡します。コンパイルを押して、流れのバーが 1 段ずつ進むのを見てください。

できあがったエンジンは、自分がどのアーキテクチャ向けに作られたかを覚えています。起動時に、エンジンはカードの実際のアーキテクチャをこのリストと照合し、wave32 であることも求めます。合わなければ、カードの名前とリストを添えてエラーで終了します。実行の途中で、意味の分からない「invalid device function」が出るのを待つことはしません。コード上の事実

NVIDIA 側でも、古いカードのために条件付きコンパイルを使っています。__dp4a は compute capability 6.1 からあります。6.0 の古いカード向けにコンパイルするときは、#if が 4 つの PTX vmad 命令に切り替えます。どの命令も、2 つのオペランドから同じ位置のバイトを 1 つずつ取り出して掛け、アキュムレータに足します。結果は、バイトごとに掛ける書き方と 1 ビットまで同じです。この道は実験スイッチ STRATA_EXPERIMENTAL_SM60 を手動で入れる必要があり、CUDA 12 も要ります。CUDA 13 はもうこれらの古いカード向けにコンパイルできないからです。コード上の事実 v0.1.40 では、ここはまだバイトごとに掛ける C コードでした。上流は新しい書き方と約 10.7 億通りの入力で比べ、違いは 1 つもありませんでした。単独で測ると、新しい書き方は P100 で約 2.2 倍速くなっています。上流レポート 整数の結果は変わらず、速くなっただけです。v0.1.39 からは、上流が CUDA 12.9 でビルドしたこうした実験エンジンも、Pascal や Volta の古いカード向けに公開しています。そのときメンテナーはこれらのカードを持っておらず、コンパイルできることと単体テストが通ることしか確認していませんでした。v0.1.40 からは、メンテナーが P100（sm_60）を 1 枚持っていて、3 種類の量子化で 10/10 一致を確認しています。Volta は今も実機で確認していません。上流レポート ところがビルドスクリプトのエラーメッセージには、いまも「上流は非サポート」と書かれています。メッセージの文面は、コードより遅れがちです。もう 1 つの例：CUDA 12.8 で RTX 50 シリーズ向けにコンパイルすると、ビルドスクリプトが警告を出します。そうして作ったエンジンが、長いプロンプトでクラッシュしたというユーザー報告があるからです。コード上の事実 コンパイラのバージョンそのものも変数だと分かります。

22.4 「コンパイルできる」から「サポート」までは、どれくらい遠いか

あなたのカードのアーキテクチャがリストにあり、エンジンもコンパイルできたとします。これは「サポート」でしょうか。Strata 自身のビルドスクリプトは、とても細かく答えています。AMD のアーキテクチャを 3 段に分け、CMake は設定時に段ごとに違う態度をとります。コード上の事実

  • メンテナが検証：gfx1100（RX 7900 XT / XTX）と gfx1201（RX 9070 シリーズ、Radeon AI PRO R9700）。メンテナが実機で動かしています。
  • ユーザーが検証：gfx1101 と gfx1200。カードの持ち主が動かして報告しました。設定時には 1 行のメッセージを出すだけです。
  • 未検証：gfx1010、gfx1011、gfx1012、gfx1102、gfx1103、gfx1030、gfx1031、gfx1034、gfx1150、gfx1151 の 10 種です。どれもコンパイルでき、設定時に警告が出て、結果の報告をお願いされます。コード上の事実 gfx1102 は付属テストに通り、さらに 1 人のユーザーが RX 7600 XT でモデルを丸ごと動かしました。リクエスト 146 件、コンテキストは最長 51K です。ただし報告は 1 件だけなので、ビルドスクリプトは今も未検証に分類しています。スクリプトのコメントには「モデルを動かした報告はまだない」とまで書かれていて、ドキュメントより遅れています。gfx1030 はコミュニティのマシンで動きましたが、メンテナはまだ自分では検証していません。gfx1012（RX 5500 XT、RDNA1）と gfx1031（RX 6700 XT）は v0.1.39 で新しく加わり、どちらもユーザーが自分のカードで動かしました。gfx1034 と gfx1151 は v0.1.40 で新しく加わりました。gfx1151 は、Ryzen AI Max（Strix Halo）チップに入っている Radeon 8060S / 8050S の内蔵 GPU（RDNA3.5）です。上流は実験的なものとして扱っています。リリースノートには Linux での実測がありますが、ビルドスクリプトは今も未検証に分類していて、Windows の実機ではまだ動かしていません。v0.1.40.2 では、さらに 4 種が加わりました。RDNA1 の gfx1010（RX 5700 XT、モデルを動かした人がいます）と gfx1011（コンパイルできることしか分かっておらず、実機で動かした人はまだいません）、そして 2 種類の内蔵 GPU、gfx1103（Radeon 780M、ポータブルなカーネルだけを使います）と gfx1150（Radeon 890M、コミュニティのマシン 1 台で動きました）です。上流レポート

Intel のグラフィックスカードは第 3 の道を通り、上の CUDA→HIP シムは経由しません。リポジトリの sycl/ ディレクトリが、Strata のエンジンを SYCL（Intel oneAPI が使う C++ のプログラミングモデル）に移植しています。独立した CMake プロジェクトで、これを有効にすると、ほかの CUDA / HIP の設定は一切使われません。今のところ、Linux でソースからビルドする方法しかありません。コード上の事実 この「サポート」という言い方そのものが、証拠の等級を考える例になります。v0.1.40.2 のリリースノートは Intel Arc を「正式サポート」と書き、実機で試した 2 枚のカード（Arc Pro B70 と Arc A750）を挙げています。本書が固定する v0.1.41 でも、README は Intel Arc をまだ「実験的で、コミュニティのメンバーが自分のマシンで書いてテストしたもの」の欄に置いています。INTEL_ARC.md の見出しにも「実験的」と書かれていて、本文はメンテナーの手元に Intel のカードがないと述べていますが、同じページの表には、メンテナー自身の B70 と A750 のテストマシンが載っています。上流レポート 3 つの文書に、3 通りの言い方があり、1 つは自己矛盾しています。サポートの宣言を読むときは、その裏にどの等級の証拠があるかを問いましょう。

2 つ目の落とし穴は数値です。図 22-5 の dp4a は整数演算なので、どの道も 1 ビットまで同じです。浮動小数点演算は違います。足し算の順序が変わると、下の数桁が変わることがあります（第 4 章で浮動小数点の丸めを説明しました）。Strata の AMD ドキュメントは、2 つのバックエンドが 1 ビットまで同じ答えを出すとは約束しない、と明記しています。上流レポート 同じマシンでもこれは起こります。IQ 系のモデルでは、CPU は 1 トークンずつ計算するときに ggml の内積を使い、まとめて計算するときは Strata のマルチトークンカーネルを使います。両者は丸めが少し違います。そして 1 グループに何トークン入るかは、ドラフトによって変わります。だから温度が 0 でも、同じプロンプトから、もう 1 つの同じくらいもっともらしい答えが返ることがあります。エンジン 0.1.30 以降は STRATA_IQ_MT_MIN=1 を設定してこの差をなくせますが、上流が Ryzen 7600（AVX-512）で測ったところ、IQ3_S のデコードが 1〜3% 遅くなります。上流レポート[S03] v0.1.41 からは、既定で有効なもう 1 つの原因があります。NVIDIA の GPU 1 枚が短いプロンプト（1,024 token 未満のチャンク）を読むとき、空いている CPU がエキスパートの一部を肩代わりします。CPU は自分の活性化フォーマットを使うので、出てくる行は GPU のものと 1 ビットまでは同じになりません。STRATA_PREFILL_CPU_SHARE=0 を設定すると止められます。コード上の事実 コードを読むと、CPU の分担量は実行時の計測で決まるので、同じプロンプトを 2 回続けて動かしても、末尾の数ビットが違うことがあります。これはコードを読んで得た推論で、本書では実測していません。コード上の事実

つまりビルド設定は実験条件であり、ハードウェアと同じようにレポートに書く必要があります。同じコミットでも、STRATA_PORTABLE を入れるかどうかで、ggml の CPU 部分は「AVX2 のある任意の CPU」向けか「このマシンの CPU」向けかが変わります。環境変数を 1 つ変えれば、計算の道も変わります。コード上の事実 README の速度表も見てみましょう。Q2_0 モデルの書き出し速度は、RTX 5070 のマシンで毎秒 94 トークン、RX 9070 XT のマシンで毎秒 60 トークンです。上流レポート[S01] 表の下の注記に書かれているのは、NVIDIA のマシンの条件だけです。Q2_0 はエンジン 0.1.36 で、残りの行は 0.1.26 で測り、答えの書き出しは 4K、プロンプトの読み込みは 32K で測っています。AMD のマシンにはエンジンのバージョンが書かれていません。v0.1.39 のリリースノートは、この表は今回は測り直していない、とわざわざ断っています。2 台の CPU も違います。1 台は AVX-512 のある Ryzen 5 7600、もう 1 台は AVX2 しかない Ryzen 9 3900X（Zen 2）です。この数字から言えるのは「どちらのマシンでも動く」ということまでで、NVIDIA と AMD のどちらが速いかの比較には使えません。

確かめるべき組み合わせはいくつあるでしょうか。ざっと計算してみましょう（図 22-7）。教育用の試算

計算式：GPU アーキテクチャは 12 種類（NVIDIA はビルドスクリプトに載っている RTX 20/30/40/50 の 4 世代、AMD は Windows 版エンジンに組み込まれる 8 種類）、CPU 経路は 3 本（AVX-512、AVX2、ggml）、OS は 2 種類、README に載っているモデルパッケージは 5 種類です。12 × 3 × 2 × 5 = 360。全部を試せる人はいません。現実的なのは層に分けるやり方です。純粋な数学の小さなサンプルでアルゴリズムをカバーする。フォーマットのテストで量子化のデコードをカバーする。バックエンドごとに代表的なカーネルを選んで比較テストをする。エンドツーエンドは、いちばん重要な数通りの組み合わせだけにする。

22.5 手を動かす：1 行のソースを 2 つのバックエンドに渡す

この章には独立したインタラクティブ実験がありません。2 つのシミュレータが実験台です。次の順で遊ぶのがおすすめです。

  1. 「1 つのソース、2 つのバックエンド」で、RTX 50、RX 7900、RX 6900 を順にコンパイルします。プリプロセス後の 3 行を見比べてください。どの名前が入れ替わったか、dp4a はどの分岐に落ちたか。例題の結果が、いつも 95 になることも確かめましょう。
  2. 「リスト外のアーキテクチャ」を選びます。CMake が最初の段階で断るほうを選ぶ理由を、味わってください。
  3. 「CPU カーネル選択器」で、CPU とモデルパッケージを固定し、環境変数とトークン数だけを変えます。数えてみましょう。同じマシンで、計算の道は何本に分かれるでしょうか。

手元に C コンパイラがある人は、もう 1 つ小さな実験ができます。スカラーの内積関数を書き、次に 8 個ずつ 1 組にして足し込む版も書きます。同じランダムな浮動小数点数の列で、2 つの結果と所要時間を比べてください。下の数桁が違うはずです。まずロジックが正しいことを確かめてから、性能を考えましょう。配列が小さすぎると、測った速さは本物の SIMD カーネルを代表しません。

22.6 境界：ライセンス、モデル、そしてこの教材自身

「ポータブル」には、もう 1 つの意味があります。コード、モデル、ドキュメントを、それぞれ誰が持っていき、どう使えるか、ということです。Strata リポジトリのコードは MIT ライセンスです。コード上の事実[S19] リポジトリのごく一部は別のライセンスです。third_party/ggml は llama.cpp / ggml（MIT）に由来し、Web アプリが使うフォントは SIL Open Font License です。モデルファイルはリポジトリには入っておらず、各モデルがそれぞれのライセンスに従います。上流レポート[S02]

この教材自体は静的な Web サイトです。HTML、CSS、JavaScript でできていて、推論エンジンは含まず、モデルの重みもダウンロードしません。どんな Web ホスティングに置いても、コースを公開しているだけです。そのサーバーで Strata が動いていることにはなりません。教材のインタラクティブな図はすべて教育用のシミュレーションです。Strata のソースにある判断ロジックを再現してはいますが、Strata のカーネルではなく、実際のどのマシンの性能も予測しません。

上流のコードを引用するときは、この本は固定したコミット番号を記録し、上流のフォントやモデルを再パッケージせず、これが独立して書かれた教材であり、元のプロジェクトやモデルの提供元の公式な認証を受けていないことを明記します。

この 3 点を覚えよう

  1. チップは自分の命令セットしか分かりません。同じソースでも、ターゲットごとに 1 回ずつコンパイルが必要です。条件付きコンパイルを使うと、1 つのソースから、コンパイルのたびにターゲットに合う分岐だけが残ります。
  2. Strata は CPU では実行時ディスパッチをします。まず CPUID で AVX-512 と AVX2 の有無を確かめ、それからカーネルを選びます。GPU ではコンパイル時ディスパッチをします。CUDA→HIP の名前の置き換え表と、自前で書いたいくつかの組み込み関数で、NVIDIA 版と AMD 版の 2 つのエンジンを作ります。
  3. コンパイルできる、テストに通る、実機で動く、メンテナが検証した。この 4 つは強さの違う 4 段階の証拠です。浮動小数点の結果は、バックエンドをまたぐと 1 ビットまで同じとは限りません。ビルド設定と環境変数も、実験条件として記録しましょう。

よくある誤解：「自分のカードでコードがコンパイルできたなら、自分のカードはサポートされている。」

コンパイルが通るのは、コンパイラがそのコードを理解できたということだけです。Strata のビルドスクリプトに、ちょうどよい反例があります。gfx1011 はコンパイルでき、上流のドキュメントにもコンパイル時のエラーが 0 件と書かれていますが、実機で動かした人はまだいません。だから設定時には「未検証」の警告が出ます。gfx1102 はもっと先まで進んでいます。付属テストに通り、1 人のユーザーがモデルを丸ごと動かしました。それでも「未検証」のままなのは、報告が 1 件だけで、メンテナーが再現していないからです。本当のサポートとは、実機で本物のモデルを動かし、結果が合っていて、誰かが再現できることです。

もう一歩深く：コンパイル時と実行時の役割分担、シムの境界、サポート宣言

なぜ AVX-512 スイッチは 1 つのファイルにだけ付けるのか

ビルドスクリプトのコメントが理由を説明しています。/arch:AVX512 でコンパイルしたソースファイルでは、コンパイラはどこにでも AVX-512 命令を使えます。「フォールバック」のつもりで書いたスカラーのコードの中にも、です。スカラーのフォールバックと AVX-512 カーネルを同じファイルに置くと、フォールバックはもうフォールバックではなくなり、古い CPU でやはりクラッシュします。そこで Strata は、スイッチをカーネルのファイルにだけ付けます。CPU を調べる関数はスイッチなしのファイルに置き、「問い合わせる」段階がどの x86-64 CPU でも安全であるようにしています。コード上の事実

調べる処理そのものにも条件付きコンパイルを使っています。同じ CPUID のコードでも、MSVC コンパイラは __cpuidex と _xgetbv を使い、GCC/Clang は __cpuid_count とインラインアセンブリの xgetbv を使います。XCR0 レジスタを調べるのは、スレッド切り替えのときに OS が AVX-512 の大きなレジスタを保存してくれるかを確かめるためです。CPU が対応していても OS が保存しないなら、やはり使えません。コード上の事実

シムの境界：こっそり意味を変えるくらいなら、中断する

CUDA の warp 交換関数には、「どのレーンが参加するか」を表すマスクの引数があります。HIP の対応する関数にはこの引数がありません。シムのやり方はこうです。現在のカーネルが使うのは全ビット 1 のマスクだけなので、そうでない呼び出しに出会ったらすぐ中断します（__builtin_trap）。マスクを捨てて計算を続けることはしません。__nanosleep は CUDA ではクロックサイクルで数えますが、AMD のスリープ命令は 0 から 15 までしか受け付けません。シムは思い切って最小の 1 に統一しています。ここでは「ちょっと待って」というヒントとしてしか使わないからです。コード上の事実

dp4a の 4 つの道にも、それぞれ工夫があります。RDNA3/RDNA4 の sudot4 命令は、2 つのオペランドそれぞれに符号の有無を指定できます。シムは両方を符号付きにして、はじめて CUDA の __dp4a と意味が一致します。RDNA2 の sdot4 は、もともと「符号付き × 符号付きを、2³² を法として足し込む」ものなので、意味は同じです。RDNA1 のアセンブリは、まず各バイトを符号拡張してから掛け（v_mul_i32_i24）、v_add3_u32 で 2 つの積ずつアキュムレータに足し込みます。32 ビット符号なしの足し算は、それ自体が 2³² を法とします。この書き方は llama.cpp から取り入れたものです。コンパイルスイッチ STRATA_GFX1012_PORTABLE_DOT を入れると、gfx1012 はポータブルなループに切り替わり、比べやすくなります。ポータブルなループは、符号なし 32 ビット整数で足し込んでから符号付きとして解釈し、結果はやはり 2³² を法とします。この章のシミュレータのテストファイルは、RDNA1 のアセンブリ、ポータブルなループ、NVIDIA の古いカード向けの vmad の書き方が、オーバーフローの境界でも参照値と 1 ビットまで同じことを 1 つずつ確かめています。

名前では形式は決まらない：型でディスパッチする

同じテンソル名でも、層によって量子化形式が違うことがあります。layer.cpp のコメントには、ある教訓が記録されています。初期のコードは「名前が形式を決める」と仮定していて、たとえば attn_qkv は必ずある K-quant だとしていました。ところが実際のモデルパッケージでは、36 個の GDN 層の attn_qkv に、IQ4_XS、Q3_K、Q2_0、Q4_K の 4 種類がありました。そこで規則を型によるディスパッチに改めました。2 ビット符号化は Q8_0 のアクティベーションを使い、それ以外の量子化形式は Q8_K を使います。間違えたときの行列ベクトル積の誤差は 0.6%〜1.4% です。出てくるのは、はっきり壊れたベクトルではなく「それらしく見える」ベクトルで、これがいちばん見つけにくいのです。コード上の事実[S14]

依存ライブラリも固定する

Strata の CPU エキスパートは ggml-cpu の内積を使い、ビルド時に llama.cpp のリポジトリから ggml を取ってきます。取るのは「最新版」ではなく、third_party/ggml/VERSION.txt に書かれた 1 つのコミット番号です。コード上の事実 理由は、この本が Strata のコミット番号を固定するのと同じです。依存が変わると、数値の道も変わるかもしれないからです。

最小限のサポート宣言

新しいバックエンドのサポート宣言を書くときは、少なくとも次のことを書きます。

  • ソースのコミット番号、コンパイラとそのバージョン、ターゲットアーキテクチャのリスト、すべてのコンパイルスイッチ、依存ライブラリのバージョン、実行時の環境変数。
  • 試したデバイス、ドライバ、モデルパッケージ、量子化形式、KV 形式、プリフィルとデコードの両方の経路、コンテキスト長の範囲。
  • 証拠を層ごとに分けて書く：コンパイルが通る、付属テストに通る、テンソル単位の比較（参照実装との誤差）、エンドツーエンドの品質、安定性、性能。
  • 試していない組み合わせは「未テスト」とはっきり書き、「全面的にサポート」とは書かない。

同じコミットから作った 2 つのバイナリでも、コンパイルスイッチが違えば、別のコードの道を通ることがあります。起動ログには、実際にどのバックエンド、どの CPU 経路を使ったか、フォールバックしたかどうかを書くべきです。Strata は、AVX-512 のない CPU で起動すると、AVX2 と ggml のどちらに切り替えたかを表示します。コード上の事実 ユーザーがファイル名から推測する必要があってはいけません。
