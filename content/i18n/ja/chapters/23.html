気づいたかも

チャットの画面では、答えが 1 文字ずつ現れます。ところが画面を介さず、コマンドラインからローカルの Strata の API を直接呼ぶと、まったく違う景色が見えます。data: {…} という行が並び、行と行の間は空行で、最後の行は data: [DONE] です。

この行は SSE（Server-Sent Events、サーバー送信イベント）と呼ばれます。サーバーを出るときはバイトの列ですが、あなたの手元に届くまでに、ネットワークが適当な大きさの塊に切り分けてしまいます。1 つの漢字が真っ二つになることもありますし、1 つのメッセージが 2 回に分かれて届くこともあります。この章では、そうした断片を、文字化けしない 1 つの完全な文に組み立て直す方法を説明します。

ひとことで：モデルが出したトークンが画面の文字になるまでに、3 つの関門を通ります。バイトを文字にする（UTF-8）、文字をイベントに切る（SSE の空行）、イベントを構造に読む（JSON）。どの関門でも、先に全部そろえてから処理します。

23.1 モデルとアプリの間には、もう 1 つサービスの層がある

推論エンジンが分かるのはトークン番号だけです。番号の列を渡すと、新しい番号を 1 つずつ出してきます。ところがあなたのアプリは別の言葉を話します。JSON 形式のチャットメッセージを送り、文字のまとまりを受け取りたいのです。その間を翻訳するのがサービス層です。図 23-1 が Strata のサービス層です。

serve/server.py の冒頭に、この層の役割が書かれています。「トークン番号をトークンに対応づけるどんなエンジン」の上でも、OpenAI 流と Anthropic 流の 2 種類の API を提供する、というものです。エンドポイントには POST /v1/chat/completions（OpenAI 流。ストリーミングも非ストリーミングも可）、POST /v1/messages（Anthropic 流）、GET /v1/models、GET /health などがあります。コード上の事実[S15] v0.1.39 は、OpenAI の Responses API POST /v1/responses も加えました。Codex CLI 向けです。これはステートレスで、サーバーは回答を保存せず、クライアントが毎回会話全体を送ります。ファイル冒頭のエンドポイント一覧にはまだ載っていません。コメントがコードに遅れています。コード上の事実

エンジンとの約束は、関数 1 つだけです。Engine.generate(prompt_ids, max_new, sampling, cancel) で、トークン番号を 1 つずつ出すイテレータを返します。本物の StrataEngine は strata --serve プロセスを常駐させ、標準入出力で話しかけます。MockEngine は台本どおりにトークンを出すので、GPU のないマシンでもすべての API の経路をテストできます。[S15]

serve/frontend.py の冒頭の一文は「ここにあるものはすべてテキストです。モデルも GPU もありません」です。仕事は 3 つあります。OpenAI 形式と Anthropic 形式のリクエストを、チャットテンプレートが求めるメッセージ一覧にそろえること。モデルに付属の Jinja テンプレートでプロンプトを組み立てること（Hugging Face の結果と一致することを、10 個のサンプルで確かめてあります）。ストリーミング出力を、思考、本文、ツール呼び出しへと少しずつ分けること。このときタグを半分だけ出すことは決してありません。コード上の事実[S16]

CS を学んだ人へ：これは「コンピュータネットワーク」で習う階層化の考え方の、小さな版です。各層は上下の層とだけやり取りし、インターフェースさえ決まっていれば、層の中身は自由に入れ替えられます。MockEngine が本物のエンジンの代わりになれるのは、境界が generate という関数 1 つだけだからです。

23.2 なぜ答えを書きながら送れるのか

普通の Web リクエストは 1 問 1 答です。ブラウザがリクエストを 1 つ送り、サーバーは答え全体を用意して、一度に返します。大規模モデルでは、最初の 1 文字が見えるまで何十秒も待つことになります。ストリーミングレスポンスはやり方を変えます。同じ答えを小さな断片に分け、1 つ書けたらすぐ 1 つ送るのです。図 23-2 で 2 つの方式を比べます。

HTTP とストリーミング（SSE）

HTTP は、ブラウザとサーバーが会話するときの決まりです。会話は 2 つの半分に分かれます。クライアントがリクエスト（どのパスにアクセスするか、どんなデータを持っていくか）を送り、サーバーがレスポンスを返します。レスポンスは、ステータスコード（200 は成功、400 はリクエストに問題あり、401 は認証に通らなかった、など）に、いくつかのヘッダと本文がついたものです。ヘッダの Content-Type は、本文がどんな形式かを相手に伝えます。

普通のレスポンスは、本文を一度に書き終えます。SSE は、レスポンスの Content-Type を text/event-stream にして、接続を閉じません。サーバーは思いついたものを 1 つずつ書き込み、その 1 つ 1 つをイベントと呼びます。形式はとても素朴です。

  • 1 つのイベントは何行かでできていて、data: で始まる行にデータが入ります。
  • 空行が 1 つ来ると、そのイベントはおしまいです。
  • コロンで始まる行はコメントで、クライアントは単に無視します。
  • 任意の event: 行で、イベントに名前を付けられます。

例を挙げます。サーバーが data: 你好、改行、さらに空行を書き出すと、クライアントは内容が「你好」の 1 つのイベントを受け取ります。仕様はさらに次のことを求めています。イベントストリームは UTF-8 でエンコードすること。改行は LF、CR、CRLF のどれでもよいこと。同じイベントの複数の data 行は改行でつなぐこと。イベントの途中でストリームが切れたら、その半端なイベントは捨てること（完全なものとして渡してはいけません）。[R05]

Strata との関係：/v1/chat/completions に "stream": true を付けると、答えが SSE で返ります。付けなければ、生成が終わるまで待って、JSON を 1 つまとめて返します。

さらに読む：MDN：HTTP の概要 · MDN：サーバー送信イベントの使用 · HTML 標準：Server-sent events（英語） · Wikipedia：HTTP

Strata が SSE を書き出すコードは短いものです。まずステータス 200 を返し、ヘッダに Content-Type: text/event-stream と Cache-Control: no-cache を書き、さらに X-Accel-Buffering: no を足します。これは nginx のようなリバースプロキシに、ためこまず、イベントを受け取ったらすぐ転送するよう頼むものです。コード上の事実 その後、答えの 1 つ 1 つは、data: に JSON を 1 つ付け、空行を 1 つ付けた形で書かれます。全部終わったら data: [DONE] を書きます。図 23-3 で、このバイト列を分解して見てみましょう。

途中の : keep-alive に注目してください。とても長い質問を読んでいる間、エンジンは何分もトークンを出さないことがあります。その間、Strata は 10 秒ごとに「ハートビート」を作り、HTTP 層がそれを SSE のコメントとして書き出します。コード上の事実 クライアントはコメントを無視しますが、バイトが流れてくるので、接続が切れたとは思いません。サーバーも、書き込みのついでに、相手がもういないことに気づけます（第 24 章で詳しく説明します）。v0.1.39 の Responses API は、もう一手間かけています。Codex CLI が「まだ働いている」と数えるのは本物のイベントだけで、コメントは見ません。そこで、長い質問を読んでいる間、サーバーは 15 秒ごとに response.in_progress イベントを余分に送ります。コード上の事実

23.3 1 つの漢字は 3 バイト

ネットワークが知っているのはバイトだけで、文字は知りません。簡略化したイベント data: {"delta":"你好"} を例にします。最後の空行まで含めると、回線の上では 26 バイトで、你 と 好 が 3 バイトずつです。ここで問題が起きます。TCP 接続がプログラムに渡す「1 塊」の大きさは、ネットワークと OS が決めるもので、文字の境目とはまったく関係がありません。1 つの漢字の 3 バイトのうち、最初の 1 バイトがこの塊に、残りの 2 バイトが次の塊に入ることも、十分ありえます。

UTF-8：1 文字は何バイトか

コンピュータの中では、どの文字にも番号があり、コードポイントと呼ばれます。たとえば「中」は U+4E2D です。UTF-8 は、コードポイントをバイトとして書くための規則です。英字のようによく使う文字は 1 バイトだけで、昔の ASCII とまったく同じです。ほとんどの漢字は 3 バイト、絵文字は 4 バイトです。

うまくできているのは、どのバイトも「自分の素性を持っている」ことです（図 23-4）。先頭バイトの冒頭に 1 がいくつ並ぶかで、その文字が何バイトかが分かります。後ろのバイトはすべて 10 で始まり、継続バイトと呼ばれます。だからデコーダは E4（2 進数で 1110 0100）を読むと、「後ろに継続バイトが 2 つ続くはずだ」と分かります。このとき塊がもう終わっていたら、正しいやり方はまず E4 を保留することです。次の塊が来てから、つなぎ合わせます。

Python の codecs.getincrementaldecoder も、ブラウザの TextDecoder（stream: true を付けたもの）も、このようなインクリメンタルデコーダ（増分デコーダ）です。逆に、塊ごとに単独でデコードすると、半分の文字は置換文字 � になり、二度と元に戻せません。

さらに読む：Wikipedia：UTF-8 · MDN：TextDecoder · Python ドキュメント：codecs · RFC 3629：UTF-8

Strata 自身も、この問題をもっと早い段階で処理しなければなりません。モデルの 1 トークンは、完全な 1 文字とは限らないからです。serve/server.py の Detokenizer は、各トークンのバイトをインクリメンタル UTF-8 デコーダに渡します。完全な文字はすぐに送り出し、トークンをまたぐ半分の文字は保留して、後のトークンが補うのを待ちます。コード上の事実 コードのコメントには、こんな計算も残されています。昔のやり方では、トークンが来るたびに、これまでに生成した番号をすべてデコードし直していました。答えが 8K トークンに達すると、トークンごとに 2 ミリ秒、16K では 4 ミリ秒余計にかかります。インクリメンタルデコードなら、トークンごとのコストは一定です。

サーバーがバイトを書き出した後は、クライアントが同じ問題をもう一度解かなければなりません。しかも、1 層多くなります。イベントも切られるからです。下のスライサーは、126 バイトの SSE ストリームをランダムに切って、2 つのクライアントに同時に受信させます。

何度か遊んでみると分かります。不注意なクライアントは、文字を落とすだけではありません。切られたイベントを不正なデータとして捨ててしまいます。間違い方は毎回違い、こうした出たり出なかったりするバグは、いちばん調べにくいものです。

23.4 JSON：イベントに入っているのは構造

SSE の仕事は、イベントを切り出すところまでです。イベントの中身には関知しません。Strata は data: の後ろに JSON を置きます。

JSON：人にもプログラムにも読めるデータ形式

JSON は、少ない決まりで構造のあるデータを表します。波括弧 {} は「名前: 値」の組、角括弧 [] はリストで、値には文字列、数値、true/false、null を使えます。さらにもう 1 層入れ子にもできます。たとえば {"delta":{"content":"你好"}} は、delta の中の content が「你好」である、という意味です。

JSON を読むには、1 つ厳しい条件があります。テキストが完全でなければならないことです。閉じ括弧が 1 つ足りなくても、引用符が半分欠けていても、パーサーはエラーを出します。だから、まず空行で完全なイベントを切り出してから読む必要があるのです。

JSON の文字列の中の ASCII 以外の文字には、2 通りの書き方があります。UTF-8 のバイトをそのまま書くか、中 のようなエスケープで書くかです。2 つは同じ意味ですが、バイト数が違います（図 23-6）。

さらに読む：Wikipedia：JSON · MDN：JSON · Python ドキュメント：json（ensure_ascii を含む） · RFC 8259

Strata がストリーミングイベントを書くときに呼ぶのは json.dumps(c, ensure_ascii=False) で、中国語は UTF-8 のまま書き出されます。コード上の事実 エスケープ形式に変えれば、回線の上はすべて ASCII バイトになり、「半分の漢字」はもう出ません。けれども、中国語のバイト数は 2 倍になりますし、SSE の仕様はもともと UTF-8 でデコードすることを求めています。イベントが切られる問題も、やはり残ります。だから正しい方向は、クライアントがきちんとインクリメンタルにデコードすることで、エスケープで逃げることではありません。

3 つの関門をつなぐと、順番は入れ替えられません。

  1. バイト → 文字：インクリメンタル UTF-8 デコード。不完全なバイトは保留する。
  2. 文字 → イベント：バッファにためて、空行が来たときだけ完全なイベントを切り出す。コメントは捨てる。
  3. イベント → 構造：完全な data を JSON として読み、文字を取り出す。

CS を学んだ人へ：これは「コンパイラ」で習う「文字ストリーム → 字句解析 → 構文解析」というパイプラインと同じ発想です。各層は、上の層が完全な単位を渡してくれてから働きます。そして TCP が保証するのはバイトの順序だけで、それより上のどんな単位の完全さも保証しません。

23.5 モデルの出力も「そろえてから送る」

同じ厄介事は、サーバーの内側でもう一度起こります。このモデルは、まず「考えて」から答えます。思考の内容は <think> と </think> の間に書かれます。ツールを呼ぶ必要があるときは、<tool_call><function=名前><parameter=引数>値</parameter>… のようなタグを書きます。これらのタグはプログラム向けで、あなたの画面に出てはいけません。

厄介なのは、タグも切られることがある点です。ある 1 歩で </th が出て、次の 1 歩でやっと ink> が出る、といった具合です。frontend.py の OutputParser は、まさにこのためにあります。切られたタグは保留しておき、完全になってから処理します。だからクライアントは、<tool_ や </thi のような半端なタグを目にすることがありません。コード上の事実[S16]

本物の OutputParser は、このウィジェットよりも 2 つ多くのことをします。1 つ目は、ツール呼び出しの進み具合を、書いている途中から報告することです。ツール名が現れた時点で開始イベントを出し、引数も少しずつ報告します。モデルが大きなファイルを書いている間、クライアントが何分も待ちぼうけにならないようにするためです。コード上の事実 2 つ目は、タグの前後の改行を丁寧に扱い、ストリーミング出力と一括出力の結果がまったく同じになるようにすることです。

ツール呼び出しは、安全性にも関わります。モデルが関数名を書いたからといって、システムがその実行を許可するわけではありません。モデルの出力は信頼できない入力です。実行する前に、引数と権限を確かめる必要があります。Strata が MCP ツールを提供するのは、はっきり要求したリクエスト（"strata_mcp": true 付き）だけで、ほかのクライアントから見える API は、これまでとまったく同じです。[S15] 「誰がモデルに何をさせる権限を持つか」は、第 24 章でも続けます。

23.6 手を動かす：同じストリームを好きな大きさに切る

この章のインタラクティブ実験「バイトの断片はイベントではない」を開いてください。中国語を含む SSE ストリームを、1〜32 バイトの固定サイズで切り、正しい 3 つの関門で復元します。順に 3 つ試してみましょう。

  1. 1 バイトから 32 バイトまで順に試す：どの切り方でも、復元した文字がまったく同じでなければなりません。1 つでも違うものがあれば、パーサーにバグがあります。
  2. CRLF 改行を入れる：SSE は 3 種類の改行を認めていて、パーサーはすべて認識する必要があります。
  3. 「未完了」のバッファに注目する：イベントの途中でストリームが切れたら、その半端なイベントは残すかエラーにするかのどちらかです。完全なふりをしてはいけません。

それから、この章の 2 つのインタラクティブ図で、断片の大きさを 1 バイトと 64 バイトにして、それぞれ走らせてみてください。塊が小さいほど、不注意な書き方の間違いがはっきり見えます。塊が大きいほど、間違いは深く隠れます。

この 3 点を覚えよう

  1. Strata のサービス層は、アプリの JSON リクエストをトークン番号に翻訳し、エンジンが出したトークンを文字に戻して、SSE のイベントストリームとして返します。エンジンとの間のインターフェースは Engine.generate だけです。
  2. バイトから文字までには、3 つの関門があります。UTF-8 のインクリメンタルデコード、空行によるイベントの切り出し、完全な JSON の解析です。ネットワークの塊の境目は、この 3 つの境目のどれとも無関係なので、どの関門でも先にそろえます。
  3. モデル出力の中のタグも切られます。Strata の OutputParser は、タグの先頭かもしれない末尾を保留し、半分のタグは決して出しません。完全なツール呼び出しは、書き終わってから初めて有効になります。

よくある誤解：「SSE のイベントを数えれば、モデルが何トークン生成したか分かる。」

両者に決まった関係はありません。Strata の最初のイベントは「アシスタントが話し始める」と告げるだけで、トークンは入っていません。長い質問を読んでいる間は、キープアライブのコメントが挟まります。1 つのトークンが漢字の半分だけを運んできたときは、その一歩では送る文字がありません。タグが保留されているときも、一時的に送らないことがあります。逆に、1 つのイベントの文字が、何個ものトークンから来ていることもあります。トークン数を知りたいときは、レスポンスの最後にある usage フィールドを見てください。イベントを数えてはいけません。

もう一歩深く：3 つの境界の厳密な要求、「互換」の範囲、検証の方法

3 つの境界を、仕様どおりに書く

SSE の仕様がパーサーに求めることは、次のようにまとめられます [R05]。イベントストリームは UTF-8 でデコードする。行末は CRLF、単独の LF、単独の CR のどれでもよい。空行が 1 回のイベント配信を引き起こす。同じイベントの複数の data 行は LF でつなぐ。コロンで始まる行はコメント。ストリームが終わったとき、空行で終わっていない半端なイベントは捨てる。

ここから、実装の順序が導かれます。インクリメンタルなバイトデコード → テキストを蓄積してイベントの境界で区切る → data のペイロードを解析する。塊を 1 つ読むたびに JSON.parse すると、文字の切断とイベントの切断の両方にやられます。この本のインタラクティブ実験が実装しているのは、data だけのサブセットで、LF と CRLF に対応しています。EventSource の自動再接続や、id、retry フィールドは実装していないので、完全な SSE クライアントとしては使えません。

例題：1 つの漢字が 3 つの塊にまたがる

「中」の 3 バイト E4 B8 AD が、3 つのネットワークの塊に分かれたとします。塊ごとに完全なテキストとしてデコードすると、置換文字が 3 つ出ます。インクリメンタルデコーダは、E4 を読んだ時点で「あと 2 バイト足りない」と分かって保留し、B8 を読むと「あと 1 バイト」、AD を読んでやっと「中」を出力します。同じように、data: {"delta":"中"} の後ろの 2 つの改行も、コロンや引用符の間、2 つの改行の間のどこで切られてもおかしくありません。ネットワークの塊の数とトークンの数の間に、決まった関係はありません。

「OpenAI 互換」とは、あるインターフェースのサブセットのこと

「互換」は、どのエンドポイントを、どのフィールドを、どんな意味で実装しているかで理解する必要があります。パスが /v1/... に似ているだけで、すべて互換だと判断してはいけません。この本が説明するのは、serve/server.py の冒頭に挙げられたエンドポイントと境界だけで [S15]、プロトコルのすべてのフィールドを 1 つずつ監査したわけではありません。v0.1.39 で加わった /v1/responses は、その一覧に載っていません。このストリーミングイベントには、1 つずつ event: の名前の行が付き、response.created で始まり、response.completed（または incomplete、failed）で終わります。これも、この本は監査していません。上流レポート ソースを読んで確認できる細部がいくつかあります。最初のイベントの delta は {"role":"assistant","content":""} であること。思考内容は reasoning_content フィールドに入ること。キャンセルによる終了は、クライアントには stop として報告されること。

ストリームが始まってから、エラーに気づいたら？

HTTP のステータスコードはレスポンスヘッダにあり、ヘッダは一度送ったら変えられません。そこで Strata は、事前に分かるエラーを、ストリームが始まる前に処理します。質問の長さに最大出力の長さを足してコンテキストを超えるときは、すぐに 400 で断り、こっそり切り詰めることは決してしません。[S15] ストリームが始まってからエンジンがエラーを出したとき（たとえばエンジンプロセスが突然終了したとき）は、ステータスコードがすでに 200 になっています。そこで Strata は、ストリームの中に error フィールド付きのイベントを書き、そのあと data: [DONE] で通常どおり締めくくります。Anthropic 流の API では、event: error イベントを書きます。コード上の事実 クライアントは、ステータスコードだけでなく、イベントの中身も確認しなければなりません。

テンプレートのサンドボックスは、テンプレートの層だけを守る

frontend.py は、Jinja の ImmutableSandboxedEnvironment でチャットテンプレートを描画します。[S16] これはテンプレート層の具体的な防御で、テンプレートのコードにできることを制限します。ツールの実行、画像 URL の取得、ローカルファイルの読み取りまでが安全だと、自動的に証明してくれるわけではありません。資源へのアクセスの種類ごとに、別々の脅威モデルが必要です。MCP ツールについては、Strata にもう 1 つ別の検査があります。Strata 自身の Web ページ（または設定で明示的に信頼した送信元）から、しかも JSON 形式で送られたときだけ、モデルにこれらのツールを使わせます。ツールは、あなたのこのコンピュータ上の権限で動くからです。コード上の事実

検証の方法と、証拠の境界

SSE 解析の検証：中国語を含む 2 つの JSON イベントを 1〜32 バイトで切り、どの切り方でも復元結果がまったく同じであることを求めます。CRLF、複数行の data、末尾の欠けたイベントもテストに加えます。欠けたイベントは、未完了のままにするかエラーにするかで、成功を偽装してはいけません。

MockEngine で確かめられるのは、ストリーミングと非ストリーミングのレスポンス、キャンセル、ツールの引数、エラー時の締めくくりのイベントです。ただし、GPU 推論の品質や、本物の性能の証明にはなりません。[S15] これが階層化したテストの利点であり、同時にその証拠の境界でもあります。
