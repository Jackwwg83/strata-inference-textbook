気づいたかも

チャット画面には「停止」ボタンがあります。押すと、文字はすぐに止まります。でも、GPU は本当に止まったのでしょうか。

Strata のソースには、とても正直なコメントがあります（issue 番号 #430、#431）。以前は、クライアントが切断したあとも、そのリクエストのせいでエンジンは忙しいままでした。答えを書き終えるか、質問をすべて読み終えるまで続いたのです。画面ではとっくに止まっているのに、GPU は、もういない人のために働き続けていました。この章では 3 つのことを説明します。リクエストはどう生まれ、どう終わるのか。「止まれ」は、どのように層を通って GPU まで伝わるのか。そして、誰があなたの GPU を働かせる資格を持つのか。

ひとことで：1 つのリクエストは、ブラウザ、HTTP 接続、サーバープロセス、エンジンプロセスの 4 層を通ります。「停止」は、層ごとに伝え、層ごとに確かめる信号です。「認証」は、誰がリクエストを送り込めるかを決めます。

24.1 「停止」を押したら、何が止まったのか

ボタンを押してから、GPU がそのリクエストの計算をやめるまでには、いくつもの層があります。「止まった」の意味は層ごとに違います（図 24-1）。

この話をはっきりさせるために、まずリクエストの状態機械を描いてみます。リクエストは、どの瞬間にも 1 つの状態にあり、決まったイベントだけが別の状態への移動を起こします。次は、この本の教育用のバージョンです。

  • キュー待ち：リクエストは着いたが、エンジンはほかの人に対応中。Strata は既定では一度に 1 つのシーケンスしか処理しないので、後から来たものは FIFO（先入れ先出し）キューで待ちます。[S15] v0.1.39 は、手動でオンにする "parallel": N を加えました。最大 N 件の会話がエンジンの中でいっしょにデコードされ、あふれたリクエストは空いたスロットを待ちます。上流レポート[S01] この章で扱うのは、既定の単一シーケンスの道だけです。
  • プリフィル：エンジンが質問を 1 チャンクずつ読みます（第 1 章で説明した prefill です）。
  • デコード：トークンを 1 つずつ書いて、答えを作ります。
  • 完了 / キャンセル済み / 失敗：3 つの終点です。どのリクエストも、最後は必ずこのどれかに着地します。宙ぶらりんは許されません。
  • キャンセル中：「止まれ」と叫んだが、エンジンがまだ止まったと確認していない状態。この中間状態は、いちばん見落とされがちです。

これらの状態名はこの本の抽象であり、上流コードの列挙型ではありません。Strata が実際に記録しているのは、リクエストが「キュー待ち」か「生成中」かの区別と、「質問を読み込み中」「回答中」のような段階の説明だけです。コード上の事実 下のシミュレータは、この過程をゆっくり見せます。

CS を学んだ人へ：「オペレーティングシステム」の授業で習うプロセスの状態遷移図（実行可能、実行中、待機、終了）も、同じように描きます。状態機械の良いところは、1 つずつ点検できることです。どの状態にどのイベントが来たら、どこへ行くのか。終点に永遠にたどり着けない状態はないか。

24.2 プロセスとスレッド：実際に働いているのは誰か

「止まれ」を誰に伝えるべきかを知るには、まず、誰が働いているのかを知る必要があります。

プロセスとスレッドのライフサイクル

プロセスは、実行中のプログラムです。OS は、独立したメモリのひと区画と、開いているファイルやネットワーク接続などの資源を割り当てます。2 つのプロセスは、既定では互いのメモリを見られず、パイプやネットワークなどの経路を通してメッセージをやり取りするしかありません。プロセスが終わると、OS は、そのプロセスが使っていたメモリや VRAM をまとめて回収します。

スレッドは、プロセスの中の 1 本の実行経路です。1 つのプロセスは複数のスレッドを持てます。スレッドは同じメモリを共有するので、データのやり取りはとても楽ですが、お互いの足を踏みやすくもあります。

どちらにもライフサイクルがあります。作成、実行、待機（ネットワークのデータを待つなど）、終了。終わり方は 2 通りで、自分で走り終えるか、ほかの者に終わらされるかです。Unix 系の OS では、あるプロセスがほかのプロセスにシグナルを送れます。SIGTERM は「終了してください」で、相手には先に片付ける機会があります。SIGKILL は「即座に終了」で、相手には後始末の機会がまったくありません。

Strata との関係：サーバーとエンジンは2 つのプロセスで、パイプを通して 1 行ずつテキストをやり取りします。サーバーの中にも、役割を分けたスレッドがいくつかあります（図 24-3）。

さらに読む：Wikipedia：プロセス · Wikipedia：スレッド · OSTEP：プロセス（英語） · Python ドキュメント：subprocess · man 7 signal

サーバーは、Python の subprocess.Popen で strata --serve を起動し、その標準入力と標準出力を両方ともパイプにつなぎます。コード上の事実 エンジンは重みを読み込み終えると、まず INFO を何行か書き、続いて、コンテキスト長を添えた READY を 1 行書きます。この行に stop も付いていれば、このエンジンのバージョンは途中での停止に対応しているということです。サーバーは READY を読んではじめて、エンジンを「生きている」とみなします。その後、サーバーが GEN コマンドを 1 行書いてリクエストを出すと、エンジンは T（トークン 1 つ）、PP（プリフィルの進み具合）、DONE（終了）、ERR（エラー）のどれかを返します。

専用の読み取りスレッドもあります。エンジンの出力を 1 行ずつキューに入れる役です。これで、リクエストを処理するスレッドは「タイムアウト付きで」次の行を待てます。待っても来なければ、先にハートビートを送ったり、キャンセルフラグを確認したりできます。ただぼんやり待ち続けることはありません。コード上の事実

エンジンプロセスが予期せず終了することもあります。コードには専用の EngineDied 例外があり、コメントには最もよくある原因が書かれています。Linux でメモリ不足のときに、OOM killer に終了させられることです。[S15] このとき、現在のリクエストはエラーで終わり、次のリクエストが来たときに、サーバーが同じコマンドでエンジンを再起動します。v0.1.39 からは、新しいプロセスが READY と言う前に終了した場合、サーバーは 15 秒おいてもう一度試し、最大 3 回まで繰り返します。死んだばかりのエンジンが握っていた VRAM は、戻ってくるまでしばらくかかることがあるからです。コード上の事実

エンジンを通常どおり止めるときにも、作法があります。サーバーは 3 段階で進め、各段階で最大 20 秒待ちます（図 24-4）。

コメントは、最初の手順が QUIT である理由を説明しています。エンジンは自分でメモリを解放しますが、数十 GB のピン留めメモリのロックを外すには、少し時間がかかるからです。コード上の事実 3 段階がすべて失敗すると、サーバーは EngineStuck を投げ、そのプロセスの記録を残したままにします。VRAM とメモリがもう返ったとは、主張しません。さらに Windows では、サーバーがエンジンを「閉じたら終了」を設定したジョブオブジェクトに入れます。こうすれば、コンソールウィンドウを直接閉じても、エンジンも一緒に終わり、管理者のいない孤児プロセスにはなりません。コード上の事実

24.3 キャンセル：「止まれ」を層ごとに伝える

キャンセル：なぜ「止まってください」とお願いするしかないのか

いちばん直接的なキャンセルは、働いているスレッドを外から断ち切ることです。ただし、これは危険です。そのスレッドは、ロックを持っている最中かもしれないし、データ構造を半分書きかけかもしれないし、VRAM の区画を借りている最中かもしれません。断ち切られると、ロックは誰にも解放されず、データは半分だけ新しくなり、後に続く人がみんな間違えます。

そこで、実際のシステムの多くは協調的キャンセルを使います。外側はキャンセルフラグを立てるだけです。働く側は、決めておいたチェックポイントでフラグをちらっと見ます。立っていれば、自分で後始末をして終わります。Python の threading.Event、Go の context、C# の CancellationToken は、どれもこの考え方です。

ここから 2 つの法則が出ます。1 つ目は、キャンセルは一瞬では終わらず、最悪の場合は次のチェックポイントまで待つこと。2 つ目は、チェックポイントの間隔が空くほど、キャンセルは遅くなること。だから「止まれと叫ぶ」ことと「本当に止まる」ことは別の話で、その間の時間が、図 24-2 の「キャンセル中」です。

さらに読む：Python ドキュメント：threading（Event オブジェクト） · OSTEP：並行性とスレッド（英語） · Wikipedia：マルチスレッド（英語）

Strata のキャンセルは協調的です。各リクエストの開始時に、サーバーはキャンセルフラグとして threading.Event を作ります。これを立てる道は 2 つあります。

  • 書き込めない：サーバーが接続に SSE イベントを書くときにエラーが出たら、クライアントがいなくなったということなので、すぐにフラグを立てます。コメントにはこう書かれています。「クライアントがいなくなった：エンジンを止める」コード上の事実
  • 監視スレッド：書き込みエラーだけでは足りません。長い質問を読んでいる間、サーバーはキープアライブのコメントをなかなか書きません。しかも、切断後の最初の書き込みは、たいてい「成功」してしまいます。そこで、リクエストごとに監視スレッドを別に立て、0.5 秒ごとに接続を確認します。接続が「読める」と表示されているのに、データが 1 つも読めなければ、相手が閉じたということなので、フラグを立てます。コード上の事実 これが、冒頭で触れた #430、#431 の修正です。

フラグが立ったあとは、チェックポイントを通して効き目が出ます（図 24-5）。

第 ⑤ 段階のチェックポイントはどこにあるでしょうか。デコード中は、トークンを 1 つ出すたびに、ループがフラグをちらっと見ます。プリフィル中は、エンジンが 1 チャンクずつ読みます。prefill.hpp の should_stop が、各チャンクを始める前に1 回確認し、真が返れば早めに終わります。エラーメッセージは “cancelled” です。コード上の事実[S12] サーバーのコメントにも、プリフィル中に出した STOP は、手元の 1 チャンクを読み終えるまで見てもらえない、と書かれています。1 チャンクは最大 32768 トークンです。[S15] インタラクティブな図の「最悪でどれだけ待つか」は、この数字で計算しています。

第 ⑥ 段階も同じくらい大切です。STOP を出したあと、サーバーはそのリクエスト自身の DONE が来るまでエンジンの出力を読み続け、その間ずっと FIFO ロックを持っています。コメントが理由を説明しています。早く手放すと、エンジンのキューに前のリクエストの DONE が残っていて、次のリクエストが、それを自分の終了の合図と取り違えてしまうからです。コード上の事実 この段階にも制限時間があります。STOP のエコーを待つときは、決して無期限には待ちません。待っている間は FIFO が占められていて、後ろの全員が並んでいるからです。

テストに使う MockEngine も、この約束を守ります。トークンを 1 つ出す前に、毎回キャンセルフラグをちらっと見ます。[S15] だから、キャンセルのロジックは、GPU のないマシンでもテストできます。

24.4 固まったらどうするか：ウォッチドッグ

キャンセルは、エンジンが「協力してくれる」ことを前提にしています。エンジンが固まって、何も言わなくなったらどうでしょう。サーバーにはウォッチドッグ（番犬）が必要です。しばらく何の動きもなければ、問題が起きたと判断する仕組みです。

難しいのは「どれくらいなら長すぎるか」です。エンジンがデコードしているときは、トークンごとに 1 行書くので、にぎやかです。ところが、とても長い質問を読んでいるときは、何分も黙っていることがあります。ウォッチドッグが一律の基準だと、真面目に質問を読んでいるエンジンを誤って殺してしまうか、本当に固まったエンジンをいつまでも待つことになります。Strata は、段階ごとに別の制限時間を決めています [S15]。

  • 基本の制限時間 300 秒：リクエストの処理中に、エンジンからの出力がこれだけ途絶えたら、応答なしと判断します。設定で変更でき、0 にすると永遠に待ちます。
  • プリフィルの最初のチャンク：300 秒に加えて、「いちばん遅いマシンでも毎秒 50 トークンは読める」として、そのチャンクにかかる時間を足します。
  • 1 チャンクを読み終えたあと：次のチャンクには、前のチャンクの実際の所要時間の最大 3 倍まで使えます。ただし 300 秒を下回りません。

図の数字は、コードの定数を代入して計算したものです。教育用の試算 最初のチャンク：300 + 32768 ÷ 50 ≈ 955 秒。速い PC は、上流の実測値の毎秒 2171 トークンで 32768 トークンの 1 チャンクを読むと約 15.1 秒で、3 倍は 45.3 秒です。300 秒に届かないので、制限時間は 300 秒のままです。遅い PC は毎秒 100 トークンなので、1 チャンクに 327.7 秒かかり、3 倍は約 983 秒です。

タイムアウトしたらどうするのでしょうか。コメントはこれを「両側のずれ」と呼んでいます。エンジンのメインスレッドは次のコマンドを待ち、サーバーはこのリクエストの終了を待っている状態です。サーバーはエンジンプロセスを終了させ、このリクエストはエラーで終わり、次のリクエストが来たときにエンジンを再起動します。[S15] プロセスを終わらせるのは乱暴ですが、VRAM もメモリも、プロセスと一緒に必ず戻ってくるという利点があります。

もっと低い層にも、同じ考え方があります。ドラフトトークンを検証する Verifier には release_gpu_waits があります。GPU 上の一連の計算が固まって、普通には終わらなくなったとき、GPU 上で待っているフラグをすべて強制的に通して、その計算を空にします。ただしそれ以後、この Verifier は、新しい計算ウィンドウの実行を拒否します。あの計算は、信頼できない条件のもとで走り終えたものだからです。コード上の事実[S08] 強制的に空にしたことは、正常な完了と同じではありません。何事もなかったふりをして、次のリクエストの処理を続けてはいけません。

24.5 誰があなたの GPU を使えるのか：認証と API キー

ここまでは「どう止めるか」の話でした。この節は「誰が始められるか」の話です。他人があなたの Strata に自由にリクエストを送れるなら、あなたの GPU は公共の資源になってしまいます。

認証と API キー

認証は「あなたは誰か」に答えるものです。認可は「あなたは何をしてよいか」に答えるものです。いちばん簡単な認証の方法が API キーです。サーバーとクライアントが、あらかじめとても長いランダムな文字列を共有しておき、クライアントは毎回、リクエストの HTTP ヘッダにそれを付けます。よくある書き方は Authorization: Bearer キー です。サーバーは、照合して一致すれば通し、一致しなければ 401 を返します。

API キーは、みんなで共有する 1 本の鍵のようなものです。手にした人は誰でもドアを開けられます。だから秘密にしておく必要があります。Web ページのソースに書いてはいけませんし、公開リポジトリにコミットしてもいけません。ネットワークで送るときは、できれば HTTPS を使います。そうでないと、途中にいる人に見られてしまいます。

照合の仕方にも注意が必要です。普通の文字列比較は、違う文字に出会うとすぐ戻ってきます。当てた先頭部分が長いほど、比較にかかる時間も長くなります。攻撃者が時間を測れば、キーを 1 文字ずつ当てられます。処理時間や消費電力のような「副産物」から情報を漏らす攻撃をサイドチャネル攻撃と呼び、そのうち時間を使うものをタイミング攻撃と呼びます。防ぐには、定数時間比較を使います。何文字目から違っていても、文字列全体を比べ終えてから結果を返す方法です。

さらに読む：Wikipedia：API key（英語） · Wikipedia：サイドチャネル攻撃 · MDN：Authorization ヘッダー · Python ドキュメント：hmac.compare_digest · RFC 6750：Bearer トークン

Strata の第 1 の防御線は、既定ではローカルだけを待ち受けることです。サーバーは既定で 127.0.0.1 を待ち受けるので、ほかの機器はそもそもつながりません。コード上の事実 このとき README は、アプリには API キーとして何を入れてもよい、と伝えています。[S01] スマホやほかのコンピュータからアクセスしたいときは、待ち受けを 0.0.0.0 に変える必要があります。README の原文は「必ずキーを設定すること」です。[S01] 待ち受けアドレスを変えたのにキーを設定していないと、サーバーは起動時に警告を 1 行出します。API キーがないので、ネットワーク内の誰でもこのモデルを使える、という警告です。コード上の事実

キーを設定したあとは、/v1/* へのリクエストは必ずキーを付けなければなりません。Authorization: Bearer … と書くか、x-api-key ヘッダに書きます（Anthropic 流のクライアントはこちらを使います）。照合には hmac.compare_digest を使い、コードのコメントには「定数時間」と書かれています。照合に失敗したら 401 を返し、種別は authentication_error です。コード上の事実 判断の全体は図 24-7 のとおりです。

なぜ定数時間でなければならないのでしょうか。下のシミュレータで、攻撃者になってみましょう。

現実の世界では、1 回の比較の差は数ナノ秒にすぎず、ネットワークの揺らぎは数ミリ秒あります。だから本物の攻撃では、同じ推測を何千回、何万回も繰り返して測り、統計の方法で違いを掘り出します。難しいことですが、不可能ではありません。hmac.compare_digest を使うのは、コード 1 行ですむことで、この危険を冒す理由はありません。

Strata は、もっと見えにくい攻撃にも備えています。DNS リバインディングです。あなたが開いた悪意のある Web ページが、自分のドメインを一時的に 127.0.0.1 に向けさせ、「自分のサイト」の顔をして、あなたのローカルのサービスにアクセスできてしまいます。そこで、キーが設定されていないときは、サーバーは、Host ヘッダが知っている名前（localhost や IP アドレスなど）であるリクエストにだけ応答します。見知らぬ Web ページを送信元とする POST リクエストも断ります。キーを設定したあとは、キーがすべてを決めます。他人の Web ページは、あなたのキーを手に入れられないからです。上流レポート

CS を学んだ人へ：この節は、「コンピュータネットワーク」や「情報セキュリティ」の基本概念にいくつか対応しています。認証と認可の違い、露出面の最小化（既定ではループバックアドレスだけを待ち受ける）、サイドチャネル攻撃。セキュリティ対策は何層にも重ね、各層は守るべきものだけを守ります。

24.6 手を動かす：自分の手でキャンセルする

この章に独立した実験ページはありません。2 つのインタラクティブ図が実験です。順に 3 つやってみましょう。

  1. ライフサイクルシミュレータで、キュー待ち、プリフィル、デコードの 3 つの状態それぞれで「キャンセル」を押し、「最悪でどれだけ待つか」を記録します。プリフィルでは約 15.6 秒、デコードでは約 0.51 秒です。考えてみましょう。自分で設計するなら、プリフィルでもっと早く止まるようにするには、どうしますか。代償は何でしょうか。
  2. キャンセルを押したあと、「キャンセル中」で「エンジンが応答しない」を押します。サーバーがどう収拾をつけるか、STOP のエコーを待つのに制限時間が必要な理由を見てください。
  3. タイミング攻撃シミュレータで、2 つの比較方法をそれぞれ 1 回ずつ破ってみて、何回試す必要があったかを数えます。

Python が書ける人は、Strata に付属する MockEngine（python -m serve.server --engine mock）を使えば、GPU のないマシンでサービスを起動できます。curl でストリーミングのリクエストを送り、途中で Ctrl+C で切断して、サーバーのウィンドウでこのリクエストの結末を確かめてください。[S15]

この 3 点を覚えよう

  1. 1 つのリクエストは、ブラウザ、HTTP 接続、サーバープロセス、エンジンプロセス、GPU を通ります。「止まった」の意味は層ごとに違うので、キャンセル信号は層ごとに伝え、確認しなければなりません。
  2. Strata のキャンセルは協調的です。監視スレッドが 0.5 秒ごとに接続を確認してキャンセルフラグを立て、エンジンはチェックポイントで止まり、サーバーはそのリクエスト自身の DONE を読んではじめて FIFO を解放します。プリフィル中はチェックポイントの間隔が長いので、キャンセルが遅くなります。
  3. Strata は既定ではローカルだけを待ち受けます。外部に公開するときは API キーが必須で、照合には定数時間の hmac.compare_digest を使い、タイミング攻撃を防ぎます。

よくある誤解：「ブラウザのページを閉じれば、GPU も止まる。」

ページを閉じて止まるのは、いちばん上の層だけです。サーバーが切断に気づき、エンジンに知らせ、エンジンが次のチェックポイントまで進んではじめて止まります。Strata でも、#430、#431 を直す前は、クライアントがとっくにいなくなったのに、エンジンが計算を続ける状況が実際にありました。「止まった」かどうかは、層ごとに別々に確かめる必要があります。

もう一歩深く：キャンセルの線形化点、遅れて届く古い応答、信頼の境界

キャンセルはどの瞬間から「効いた」ことになるのか

キャンセルは、次のように定義できます。確認済みのある境界から先は、ユーザーに新しいトークンを渡さず、関連する資源も最終的に使われなくなること。この境界が、キャンセルの線形化点です。フラグを立てただけで、プリフィルのチャンクループやデコードのループがまだそれを見ていなければ、キャンセルは完了していません。

この本が serve/server.py を読んで理解したところでは、まだキュー待ちのリクエストは、FIFO ロックを取り、GEN コマンドをエンジンに送ったあとで、はじめて、エンジンの出力を待つループの中でキャンセルフラグを確認します。最初のトークンかプリフィルの進み具合を 1 行受け取ったとき、または出力なしで 10 秒待ち切ったときです。コード上の事実 つまり、とっくに切断された、キュー待ちのリクエストでも、エンジンはまずその質問を読み始め、そのあとで STOP を受け取ります。取り組む価値のある発展課題があります。ロックを取ったあと、コマンドを送る前に、もう 1 回フラグを確認することです。

例題：タイムアウト後に届く古い応答

リクエスト A がタイムアウトし、サービスがリクエスト B を処理し始めたとします。A の遅れた結果がまだ共有の出力キューに書き込まれると、B は A のトークンを受け取ったり、A の DONE を自分の終了と取り違えたりするかもしれません。解決の方向は、出力に持ち主の検査を付けることと、古い実行が終わったと確認できるまで、同じ可変な状態を使い回さないことです。

Strata が採っているのは、まさに後者です。STOP を出したあとは、そのリクエスト自身の DONE まで読み続け、その間ずっと FIFO ロックを持っています。使用量を集計するときも、そのリクエストの期間中に届いた DONE だけを数えます。そうしないと、エラーで終わったリクエストや切断されたリクエストが、前のリクエストのデコード数を自分のものとして記録してしまいます。コード上の事実 この本は、上流のすべての出力の持ち主の経路を監査したわけではありません。授業では、わざと遅らせた mock エンジンでこのリスクを作り出し、修正を検証するとよいでしょう。

ウォッチドッグは作業の段階を理解しなければならない

「しばらく文字の出力がない」ことをすべてデッドロックとみなすと、長い質問を読んでいる健全なリクエストを誤って殺します。永遠に待つと、FIFO 全体が詰まります。まともな診断は、次を区別できなければなりません。キュー待ち、正当な長い計算、遅い I/O、子プロセスの応答なし、プロトコルのずれ。そして、あいまいな「タイムアウト」だけでなく、状態と最後の進み具合を報告します。Strata がプリフィルのチャンクごとに制限時間を調整し、応答なしの原因をエラーメッセージに書くのは、この考え方です。[S15]

同じように、「明示的なモデル制御」（ロードとアンロード）は、実行中やキュー待ちのリクエストを中断してはいけません。コードには、そのための ModelBusy が定義されています。[S15] 上流のドキュメントによると、このとき制御 API は 409 を返します。上流レポート

ツール、画像 URL、ローカルファイルは、どれも信頼の境界

モデルの出力は信頼できない入力です。ツールの引数は、構造の検証と権限の検査を通す必要があります。リモート URL の取得は、外部へのアクセスと資源の制限に関わります。ローカルパスの読み取りは、ファイルの権限とパスの範囲に関わります。Strata の画像入力は、base64 データ、http(s) の URL、ローカルファイルのパスの 3 種類の入力元に対応しています。[S15] v0.1.40 は、これらの入口に 3 つの検査を足しました。別のコンピュータを指すネットワークパスは、一切読みません。URL から読む画像は、最大 32 MiB までです。別のサイトの Web ページが、サーバーにこのマシンのファイルを画像として読ませることはできません。コード上の事実（server.py）上流自身も、入口を 1 つずつ直してきました。コミュニティから届いた修正は /v1/responses という入口を見落としていて、メンテナーがマージするときに足しました。上流レポート サーバーが http(s) の URL を取りに行く部分で SSRF を防げているかは、この教材では監査していません。安全は入口ごとに監査する必要があります。どこかで安全なライブラリを使っているからといって、全体が安全だと断言してはいけません。

frontend.py は、サンドボックス化した Jinja 環境でテンプレートを描画します。[S16] これはテンプレート層の具体的な選択であり、ツールの実行、URL の取得、ファイルへのアクセスがすべて安全であることを、自動的に証明するものではありません。資源の種類ごとに、別々の脅威モデルが必要です。

「キャンセル完了」の受け入れチェックリスト

mock エンジンに、次の状況を注入します。プリフィル中のキャンセル、出力の中断、重複したキャンセル、エンジンの無応答、古い結果の遅れ、復旧後の再リクエスト。受け入れ条件：ユーザーに見える新しいトークンをもう渡さない。バッファの読み書きに関わるタスクがすべて停止または完了している。キューと状態が次のリクエストに誤って使われない。遅れて届いた古い出力を識別して捨てられる。資源の解放は 1 回だけ。クライアントには、「成功」ではなく、明確な「キャンセル済み」か「失敗」が返る。

最後に 1 つ注意です。この教材は静的な Web サイトで、本物の推論 API キーは含まれていません。ブラウザからあなたのモデルサーバーに直接アクセスすることもありません。将来、本物の実験プラットフォームにつなぐときは、認証、クォータ、ジョブの分離、サーバー側のプロキシを別に用意すべきで、キーをコースのページに書いてはいけません。
