まず、ある起動時の警告から

Strata は以前、起動のたびに警告を 1 行表示していました。大意はこうです。GPU 上のエキスパート計算の経路は「正しくない」ので、そこから出る出力は何も信用できない。その後、issue #23 が、とても率直な問いを出しました。エキスパートキャッシュをオンにすると、答えは悪くなりますか。上流レポート

作者は実験をしました。同じ文章を、キャッシュありとなしで 1 回ずつ流し、位置ごとにモデルの予測を比べたのです。結果は少し直感に反していました。2%〜5% の位置で、両者が選ぶ「いちばんありそうな次の単語」が違う。それなのに全体としては、どちらが正確ということもない。違うのに、どちらも正しい。この章はここから始めます。「正解」さえはっきり言い切れないシステムを、どうやってテストするのでしょうか。

ひとことで：推論エンジンのテストは階層に分けます。小さな関数は正確な答えと照らし、1 つの演算子は独立した参照実装と照らし、モデル全体には同じ文章を入れて位置ごとに比べます。浮動小数点の下の数桁は計算の順序で変わるので、「等しい」は、まず許容差つきの比較として定義しなければなりません。そして良いテストは、わざと入れたバグを本当に捕まえられることを、証明する必要があります。

26.1 なぜ「正しく見える」のがいちばん危ないのか

プログラムの間違いには、2 つの姿があります。1 つはクラッシュです。エラー、終了、文字化けした出力。この種のバグは見つけやすく、最初の実行で露見します。もう 1 つはもっと厄介です。プログラムは普通に動き、普通の数を出力し、生成された文もなめらかなのに、中身はもう間違っているのです。図 26-1 は、2 つのバグを並べたものです。

推論エンジンは、右側のようなバグがとても出やすいものです。理由は簡単で、モデルが出力するのは確率の列なので、少し計算を間違えても、選ばれる単語は「それらしい単語」のままだからです。Strata のソースのコメントには、作者がこの種の落とし穴を 1 つずつ書き残しています コード上の事実。

  • アドレスでキャッシュする。各層がエキスパートに送る入力は、同じメモリ領域を使い、アドレスは変わらず、中身だけが層ごとに違います。これをアドレスでキャッシュすると、第 0 層のデータを後ろの 47 層でも使い回してしまい、「有限で、もっともらしく見えて、完全に間違ったトークン」が出てきます。[S06]
  • 重みを 2 回掛ける。エキスパートプールはルーティングの重みを掛けません。掛けるのは合流のステップです。両方で掛けてしまうと、1 層だけ見てもほとんど気づけませんが、48 層を重ねると誤差がどんどん増幅されます。[S06]
  • ヘッドの対応規則。GDN 層では、48 個の value ヘッドを 16 個の key ヘッドと対応づけます。正しい規則は剰余（h % 16）です。コメントはわざわざ、もう 1 つの「ブロックごとにまとめる」規則でも、形式の整った出力が出てしまう、と書いています。[S17]
  • アクティベーション形式の選び間違い。量子化された行列にどのアクティベーション形式を組み合わせるかは、その行列の名前ではなく、データ型で決まります。間違えると、行列ベクトル積の結果が 0.6%〜1.4% ずれます。コメントの原文は「壊れたベクトルではなく、もっともらしく見えるベクトル」です。[S14]

だから、推論エンジンのテストには、あるものが必要です。基準の答え、テストオラクル（test oracle）とも呼ばれるもので、「正しい結果は何であるべきか」を教えてくれる独立した情報源のことです。手計算した数でも、別の信頼できる実装でも、必ず成り立つべき法則でもかまいません。基準の答えがなければ、テストは「プログラムが落ちなかった」ことしか確かめられません。

26.2 テストは何層に分かれるか：1 行の計算式からセッション全体まで

推論エンジン全体を一度にテストするのは非現実的です。工学的なやり方は階層に分けることです。下の層のテストは小さくて速く、失敗したときにどの行かを正確に指せます。上の層のテストは遅いものの、ユーザーが実際に目にするものにいちばん近くなります。図 26-2 は、Strata に合わせて整理した「テストの階段」です。

いくつかの層で、Strata が実際にどうしているかを見てみましょう。

いちばん下は純関数です。32 ビット浮動小数点数を 16 ビットの BF16 形式に変換する関数の入力は、2³² 通り、およそ 43 億通りしかありません。Strata のテストは、思い切ってその全部を試します。入力のすべてを、ggml（llama.cpp の裏にある計算ライブラリ）の変換規則と比べ、数秒で走り終えます。このテストは本物のバグを捕まえたことがあります。古い丸めの書き方は、NaN（「数ではない」）に出会うと繰り上がりが起こり、NaN を −0 や無限大に変えてしまいました。上流から来た NaN が、こうして静かに隠されていたのです。コード上の事実（bf16_bits_test.cpp）

2 層目は、1 つの演算子です。どの GPU カーネルにも照合テストがあり、信頼できる参照実装と比べます。ビルドスクリプトのコメントがはっきり書いています。参照実装自身が、まず ggml と照合済みであること。「あるカーネルを、自分自身の別のコピーと比べても、何も証明できない」ということです。コード上の事実（CMakeLists.txt）

3 層目は、組み合わせと契約です。layout.hpp は、モデルを読み込む時点で、各テンソルの形状がカーネルの前提に合っているかを検査します。合っていなければ、テンソルの名前、実際の形状、求められる形状を報告します。コメントの原文は、エラーにするのは読み込み時であって、4000 個目のトークンで行列積の中の間違った数になってからではない、というものです。[S04] 同じコメントには、実際にあった教訓も記されています。ある開発の 1 周で、indexer の key キャッシュを「4 ヘッド」としてサイズ計算していましたが、実際には共有ヘッドが 1 つだけで、4 倍大きかったのです。この間違いは、予算をより保守的にするだけだったので、誰もどこかおかしいとは思わず、コードの中で 1 周生き延びました。[S04]

上の 2 層は、モデル全体を走らせる必要があります。26.4 節で詳しく説明します。

階段のどの層も省けません。Strata には、ちょうどよい悪い例があります。モデルには PLE というモジュールがあります（第 11 章で説明したテーブル引きのモジュールです）。部品はすべて書かれ、どれも単独で照合テストに通っていました。ところが、モデルのコードのどこも、それを実際に呼び出していなかったのです。その結果、モデル全体の検収の関門（コード名 C1）は通りませんでした。コード上の事実[S13] 部品がすべて緑でも、システムは間違ったままです。

ソフトウェアテストの階層

大きなシステムのテストは、ふつう何層かに分けます。単体テストは、1 つの関数か 1 つのクラスだけをテストし、入力を与えて出力を確認します。実行時間はミリ秒単位です。結合テストは、いくつかのモジュールをつなぎ、モジュール間の「インターフェースの約束」が両側で守られているかを確認します。システムテスト（エンドツーエンドテストとも呼ぶ）は、ユーザーの入口から入って、最終結果を見ます。ほかに、各層を貫く回帰テストがあります。バグを 1 つ直すたびに、それを再現するテストを残し、後でまた戻ってくるのを防ぎます。

よく言われる経験則が「テストピラミッド」です。下の層の単体テストは多くて速く、上の層のエンドツーエンドテストは少なくて遅い。理由はコストです。エンドツーエンドテストが失敗すると、どの層に問題があるのかを探す時間がまた必要です。単体テストが失敗すれば、たいてい数行のコードを直接指しています。

もう 1 つよく使う道具がテストダブルです。本物だけれど高価な部品の代わりに、偽物で、振る舞いを制御できるものを使います。Strata のサービス層には MockEngine があり、台本どおりにトークンを出すので、すべての API の経路を、GPU のないマシンでテストできます。コード上の事実[S15] これで「HTTP プロトコルの層は間違っていない」ことは証明できますが、本物のエンジンの計算が正しいことは証明できません。どの層のテストも、自分がカバーする層にだけ責任を持ちます。

さらに読む：Wikipedia：ソフトウェアテスト · Wikipedia：単体テスト · Wikipedia：回帰テスト · Python ドキュメント：unittest 単体テストフレームワーク

CS を学んだ人へ：これは「ソフトウェア工学」で習うテストピラミッドと V モデルそのものです。推論エンジンに特有なのは、中間に「参照実装との照合」という層が 1 つ多いことです。ほとんどの演算子は、正しい答えを手計算できません。独立した、信頼できる実装を見つけて比べるしかないのです。

26.3 浮動小数点の「等しい」は、まず定義する

冒頭の実験に戻りましょう。GPU と CPU が計算しているのは同じ量子化エキスパートで、データは 1 バイトも違わないのに、結果は小数点以下の下の数桁で違っていました。作者の説明はこうです。両者は浮動小数点演算の順序が違い、どちらもモデルにとって同じくらい良い近似である。上流レポート（cache-parity レポート）

順序はなぜ結果に影響するのでしょうか。コンピュータの浮動小数点数は桁数が限られていて、足し算のたびに 1 回ずつ四捨五入するからです。極端な例を挙げます。32 ビット浮動小数点数（FP32）では、1 億の付近で表せる隣り合う 2 つの数は 8 離れています。だから 1 億に 1 を足しても結果は 1 億のままで、その 1 は「食われて」しまいます。同じ 4 つの数でも、足す順序を変えると答えが変わります（図 26-3）。

この例は、わざと極端なものを選んでいます。本物の推論では、違いはたいてい下の 1、2 桁だけで、ULP（unit in the last place、最後の桁の 1 単位）が 1、2 個違う、と言います。それでも、a == b のようなテストを失敗させるには十分です。

工学的な解決策は、許容差つきの比較に切り替えることです。2 つの数の差が十分に小さければ、等しいとみなします。「十分に小さい」の測り方は 2 通りあります。相対許容差は、数の大きさに応じて割り引きます。たとえば 1 万分の 1 までの差を許す、という具合です。絶対許容差は固定の関門で、たとえば 10⁻⁶ 以内の差ならどれも等しいとみなします。たいてい両方を一緒に使います。なぜか、次のコラムで説明します。

浮動小数点比較の許容差

まず直感から。1 億と 1 億 8 を比べるとき、差の 8 は FP32 が区別できる最小の違いなので、等しいとみなすべきです。0.000001 と 0.000009 を比べるときは、差は 0.00001 に届きませんが、一方がもう一方の 9 倍なので、明らかに等しいとは言えません。だから「どれだけ違えば等しいとみなすか」は、数自身の大きさと結びつける必要があります。これが相対許容差です。

ただし相対許容差は、0 の付近では役に立ちません。ある結果が理論上は 0 のはずなのに、計算すると 2×10⁻⁸ になり、もう 1 つはちょうど 0 になったとします。相対差は 100% ですが、実際の意味ではまったく違いがありません。そこで、絶対許容差で下支えする必要があります。Python の標準ライブラリの math.isclose は、この 2 つを合わせています。

|a − b| ≤ max(rtol × max(|a|, |b|), atol)

既定値は rtol = 10⁻⁹、atol = 0 です。ドキュメントがわざわざ注意しています。0 と比べるとき、既定の設定では永遠に「等しくない」と判定されるので、自分で正の atol を与える必要があります。さらに、NaN はどんな数とも「近く」ありません。自分自身ともです。コラムの下の図 26-4 は、この規則を描いたものです。横軸が数の大きさ、縦軸が許される誤差です。

許容差をどれだけにするかに、万能の答えはありません。データ型（FP32 は有効数字が約 7 桁、FP16 は 3 桁あまり）、計算の連鎖の長さ、下流が誤差にどれだけ敏感かで決まります。確かな方法は、まずどちらも正しい2 つの実装の間の典型的な違いを測り、許容差をそれより上、明らかな間違いの差より下に決めることです。

見落とされがちな点がもう 1 つあります。許容差が見逃してよいのは、「順序が違う」ような正当な違いだけです。アルゴリズム自体が情報を失う問題は、救えません。図 26-3 では、2 つの経路がどちらも間違っています。許容差を、それらが「等しい」と言えるまで広げたら、テストは何も確かめなくなります。

さらに読む：Python ドキュメント：math.isclose · MDN：Number.EPSILON（マシンイプシロン） · Wikipedia：IEEE 754 · Wikipedia: Unit in the last place（英語）

では、いつ 1 ビットまで同じであることにこだわるべきでしょうか。答えは、両側がまったく同じ演算を、まったく同じ順序で行っているときです。たとえば、量子化データをある保存形式から別の形式へ変えるときは、バイトを並べ替えるだけなので、デコードした値は 1 ビットも違ってはいけません。Strata の canonical_xcheck.py は、まさにそう求めています。コード上の事実（canonical_xcheck.py）逆に、コンパイラの最適化でさえ順序を変えることがあります。Strata は、AMD の GPU で、2 つのファイルの「積和融合」（FMA）をわざと切っています。掛け算と足し算を 1 つの命令にまとめると、丸めが 1 回で済み、「ちょうど真ん中」のときの取捨の結果が変わるからです。コード上の事実（CMakeLists.txt）

CS を学んだ人へ：「数値解析」で習ったとおり、浮動小数点の足し算は交換法則は満たしますが、結合法則は満たしません。(a + b) + c と a + (b + c) は違うことがあります。GPU では何千ものスレッドが縮約を行い、足し算のグループ分けはスレッドの配置で決まります。だから「同じ式」でも、CPU と GPU で 1 ビットまで同じになることを、もともと期待してはいけません。

26.4 ほんの少しの差で、単語が変わる

数値のほんの少しの差は、目に見える結果を生むでしょうか。生みます。しかも、まさに「単語を選ぶ」ところで。モデルは最後に各候補の単語にスコアをつけ、これを logit（ロジット）と呼びます。スコアがいちばん高い単語が選ばれます。1 位と 2 位のスコアがほとんど同じなら、わずかな数値誤差で順位が入れ替わります。

例を見ましょう。参照エンジンが 2 つの候補単語に与えたスコアは [1.00000, 0.99999] で、最初のものが選ばれます。テスト対象のエンジンは [0.99998, 1.00001] と計算し、2 番目が選ばれます。両者の最大の差は 0.00002 しかないのに、選ばれた単語が変わりました。逆に、スコアが [10, 0] なら、誤差が 10 倍大きくても、単語は変わりません。だから「最大誤差が小さい」ことと「選ばれる単語が同じ」ことは別のことで、分けて確認する必要があります。

2 つのエンジンを比べるには、もう 1 つ面倒があります。それぞれ自由に生成させると、1 つの単語が違った時点で、その後の「前の文脈」が違ってしまい、さらに先のどのステップも比べられなくなります。解決策が teacher forcing（履歴の固定）です。エンジンに自分で続きを書かせず、両方に同じ基準の文章を入れて、各位置で「次の単語」の予測を比べます。図 26-5 が、2 つのやり方の比較です。

Strata が「キャッシュは出力を悪くするか」に答えたときに使ったのが、このやり方です。エンジンにはスイッチがあり、基準の文章をトークンごとに走らせ、各位置の logits をすべて書き出します。キャッシュをオフにすると、すべてのエキスパートを CPU が計算します。オンにすると、よく使う 5,130 個のエキスパートが GPU に置かれます。テスト条件は Q2_0 量子化、RTX 5070、固定した 3 つの文章の先頭 512 または 1,024 トークンです。上流レポート

表のパープレキシティ（perplexity、困惑度）は、モデルがその本物の文章にどれだけ「意外」を感じるかを測るもので、低いほど予測が正確です。レポートの結論は 3 つあります。キャッシュは、2%〜5% の位置で「ほぼ同点の 2 つの候補のどちらが勝つか」を変える。順位の入れ替わりの大半は、上位 2 つのスコア差が 0.5 に満たないところで起きる。両者のパープレキシティは標準誤差 1 つの範囲で同じで、どちらが正確ということはない。GPU と CPU は同じエキスパートを違う浮動小数点の順序で計算するが、どちらも同じくらい良い近似である。上流レポート（cache-parity レポート）

この表は、良い比較がどうあるべきかを示しています。離散的な判断（最有力の単語が同じか）も、連続的な品質（パープレキシティ）も見て、順位の入れ替わりがどこで起きたかも説明すること。「96% の単語が同じ」とだけ報告すれば、読者は 4% の箇所が間違っていると思うでしょう。「パープレキシティが同じ」とだけ報告すれば、ごく一部の位置だけで間違うバグを隠してしまうかもしれません。

26.5 テストをまず 1 回失敗させる：基準の答えと反例

テストが通ったことは、何を示すのでしょうか。そのテストが、本当にバグのあるプログラムに対しても通ってしまうなら、その「通過」にはまったく意味がありません。テスト自身を検査する素朴な方法があります。コードにわざとバグを入れて、テストがそれを捕まえられるか見るのです。これをミューテーションテストと呼び、壊した版を「ミュータント」と呼びます。

次の実験では、48 層のおもちゃのモデルでこれを実演します。4 つの版の実装と 5 つのテストを用意しました。先に当ててみてください。「重みを 2 回掛ける」バグを捕まえられるのは、どのテストでしょうか。

表でいちばん考えどころのあるのは、2 つのマスです。1 つ目は、「弱い単体テスト」が「重みを 2 回掛ける」を見逃したことです。このテストはたまたま重み 1.0 を使っていて、1.0 の 2 乗は 1.0 のままだからです。テストが選ぶ入力が「きれいすぎる」と、ある種のバグには生まれつき盲目になります。2 つ目は、「毎層で古い入力」が、2 つの単体テストをだましたことです。バグは、テスト対象の関数の中ではなく、関数をつなぐループの中にあるからです。これがまさに 26.2 節の「部品がすべて緑でも、システムは間違ったまま」です。

表でバグ捕獲にいちばん力を発揮したのは差分テストです。同じ入力の組を、テスト対象の実装と独立した参照実装の両方に入れ、出力を比べます。次のコラムで詳しく説明します。

差分テストとメタモルフィックテスト

多くの計算には、手計算できる正しい答えがありません。2560 次元の行列積を、紙の上で検算できる人はいません。差分テストの考え方は、独立に実装された版を参照として探し、両側に同じ入力を食べさせて、出力を比べることです。参照は遅くても、愚直でも、信頼できさえすればかまいません。Strata の照合テストはこうなっています。GPU カーネルを、検証済みのスカラーの参照経路と照らし、その参照経路自身も、まず ggml と照合済みです。

参照のカギは独立していることです。Strata の layer.cpp には教訓が記されています。2 つのパッキングツールが、ある量子化データのオフセット面を、どちらも mins というフィールド名で探していましたが、その面の本当の名前は offsets でした。2 つのツールが「満場一致」で、一緒に 54 個のテンソルのオフセット、合計 136 MiB を取りこぼしました。コメントの結論は、2 つのツールの意見が一致しても、それが証拠になるのは、両者が同じ誤った前提を共有していないときだけ、というものです。コード上の事実[S14]

参照すら見つけにくいときは、メタモルフィックテストも使えます。正しい答えがいくつかは分からなくても、「入力をこう変えたら、出力はこう変わるはず」ということは分かる、という場合です。たとえば Strata の KV キャッシュはページ単位で保存します。テストは、同じデータを 1 ページあたり 1、4、512 マスで保存し直し、ページテーブルをシャッフルして、アテンションの出力がまったく同じであることを求めます。[S18] 別の例は、投機的デコーディングの検証ウィンドウです。設計上、各位置で選ぶ単語は、1 トークンずつ生成したときと 1 ビットまで同じであることを求めています。[S08] これは既定の規則です。v0.1.40.2 では、既定でオフの「確率的受理」（STRATA_SPEC_PROB=1）が加わりました。サンプリングのリクエストでは、各位置の単語が同じ分布に従うことだけを保証し、1 ビットまで同じであることは保証しません。コード上の事実 こうした「変わらないはず」という法則は、正解の答えを必要としない参照になります。

さらに読む：Wikipedia: Differential testing（英語） · Wikipedia: Metamorphic testing（英語） · Wikipedia: Test oracle（英語） · Wikipedia：ミューテーション解析

差分テストは、Strata の本物のバグも捕まえています。Q2_0 量子化形式では、2 ビットのコード値 0〜3 をデコードするとき、まず 1 を引く必要があり、表せる値は {−d, 0, d, 2d} であって、{0, d, 2d, 3d} ではありません。この「1 を引く」を忘れると、ほとんどの値は正しく見えますが、実際にはどれも 1 目盛りずれます。そこで変換ツールは、ggml のデコード式をそのまま書き写し、1 ビットずつ照合しています。コード上の事実（canonical_xcheck.py）同じファイルには、Q8_0 形式の本物の失敗も記録されています。コード値が符号付きの数として保存されていて、自分自身のデコーダとは完全に一致していました。本物のモデルをパッキングしてはじめて、その 2 つのテンソルが、デコード後に全体でコード値 128 個ぶんずれていることが分かりました。ほかの 12 種類の型は正常でした。

CS を学んだ人へ：コンパイラの授業にある古典的な手法に、同じプログラムを 2 つのコンパイラに渡して実行結果を比べる、というものがあります。競技プログラミングで、力ずくの解法を書いて、最適化した解法と突き合わせるのも、同じ発想です。

26.6 手を動かす：小さなエンジンにテストを書く

この本には、純 Python の小さな推論エンジン labs/tiny_inference.py が付属しています。4 層、8 次元、各層 4 つのエキスパートから 2 つを選び、重みは固定の乱数で、GPU はいりません。Strata の互換実装ではなく、出力にも言語としての意味はありませんが、「エンコード → 層ごとの計算 → 単語の選択 → 保存と復元」という流れは本物です。付属の 10 個のテストは、この本の環境ではすべて通っています。

  1. まずテストを読む。labs/test_tiny_inference.py を開き、「分割して処理しても、一度に処理したのと等しい」テストを探します。これは完全一致を使っています。考えてみましょう。なぜここでは完全一致が正しいのでしょうか。（ヒント：2 つの経路が、完全に同じ順序で演算しています。）
  2. バグを 1 つ注入する。labs/README.md の 3 番目の課題に従い、再帰層の「先に減衰、次に更新」の順序を入れ替えます。どのテストが失敗するでしょうか。1 つも失敗しなければ、失敗するテストを足してください。
  3. 比較規則を書き換える。トークンごとのプリフィルを、全体をまとめて計算する行列積に置き換えたとします。演算の順序が変わりました。完全一致のテストを許容差つきの比較に書き換え、許容差をどう決めたかを説明してください。

この章の 2 つのインタラクティブ実験は、ブラウザの中で本当に計算します。数字は教育用の試算です。実験台の許容差の式は、Python の math.isclose と一致しています。ミューテーションテストが使うのはおもちゃのモデルで、Strata のカーネルではありません。

この 3 点を覚えよう

  1. 推論エンジンでいちばん危ないのは、「一見正常に見える」バグです。テストには独立した基準の答えが必要で、プログラムが落ちなかったことを確かめるだけでは足りません。
  2. 浮動小数点の結果は、計算の順序で変わります。同じ演算を同じ順序で行うときだけ、1 ビットまで同じであることを求めます。そうでなければ、相対と絶対の許容差を合わせて比べ、選ばれた単語は別に確認します。
  3. テスト自身も検査が必要です。わざとバグを入れて、失敗するかを見ます。参照実装は独立でなければならず、テスト対象のコードと同じ誤った前提を共有してはいけません。

よくある誤解：「CPU と GPU で出した数が違うなら、どちらかにバグがある。」

そうとは限りません。両者は浮動小数点演算の順序が違うので、下の数桁が違うのはもともと当たり前で、Strata の実測でも、両者が同じように正確なことが示されています。ただし、逆に何でも見逃してよいわけでもありません。あの「GPU の経路は正しくない」という起動時の警告は、もとは本物の不具合から生まれました。当時の出力は、第 0 トークンからすでに食い違っていたのです。のちに不具合は直され、エキスパートの照合テストでカバーされ、0.1.8 版から、警告は正確な説明の文に置き換えられました。上流レポート 2 つを見分けるには、規則性を見ます。正当な違いは、ほぼ同点の位置でだけ入れ替わり、パープレキシティは変わりません。本物のバグは、たいてい最初から食い違うか、品質の指標を系統的に悪くします。

もう一歩深く：5 層の証拠、指標の落とし穴、「1 ビットまで同じ」の境界

5 層の証拠の階段

1 層目は純関数です。アドレスのオフセット、容量、top-k、期待される長さ。2 層目は 1 つの演算子です。同じ入力で、出力と誤差を比べます。3 層目は組み合わせです。正規化、ゲート、エキスパートの重みづけ、状態の更新の先後の順序。4 層目は、固定した履歴のもとでのモデル全体の分布です。5 層目は、実際のタスクと長いセッションでの振る舞いです。下の層が通っても、上の層が通るとは言えません。「エキスパートプールは routing の重みを掛けない」という点や、GDN の β と状態軸についての説明は、組み合わせの間違いが、それぞれ単独ではテストに通るモジュールの間に隠れうることを示しています。[S06][S17]

teacher forcing で、どの指標を記録するか

最大絶対誤差、相対誤差、平均二乗誤差、KL ダイバージェンス、最有力の単語が変わったか、ルーティングが選んだエキスパートの番号や indexer が選んだ位置が変わったかを、記録できます。どの指標にも落とし穴があります。相対誤差は、参照値が 0 に近いと歪みます。KL ダイバージェンスでは、確率をどう正規化するか、確率 0 をどう扱うかを説明する必要があります。最有力の単語が同じ割合は、上位 2 つのスコア差の分布と一緒に見る必要があります。Strata の QSA indexer は、選ばれる位置が完全に同じでなければならない、と定めており、許容差を認めていません。違うマスが 1 つ選ばれると、アテンションの入力が変わってしまうからです。そのため、indexer の key を FP16 ではなく FP32 で保存しています。FP16 では、各スコアに約 2⁻¹¹ の相対的な揺れが生じ、それがちょうど選択の境界に当たるからです。代償は小さく、32K コンテキストでは、これらの FP32 の key は合計で約 50 MiB です。[S18]

そのまま使えるメタモルフィック関係

ページテーブルとデータに同じ置換を施しても、論理的なアテンションの結果は変わらないはずです。同じ入力を違うチャンクに分けても、チャンク間の状態の受け渡しは等価のはずです。保存して復元してから続けても、一度も離れなかったのと同じはずです。ドラフトを切っても、対応するターゲットの経路と意味が一致するはずです。[S08][S18] こうした関係からは、強いテストを大量に作れます。ただし、許容差と数値の経路を書いておく必要があります。CPU と GPU をまたぐとき、行列積の実装を替えるとき、量子化の経路を替えるときは、1 ビットまで同じとは限りません。すべての違いをそのまま見逃してもいけませんし、既知の丸めの境界を無視してもいけません。

「1 ビットまで同じ」という約束には、境界がある

Strata の検証ウィンドウは、ヘッダの中で約束しています。各位置の単語の選択が、1 トークンずつ生成したときと 1 ビットまで同じであること。[S08] この約束は、既定の完全一致に対するものです。オプションの確率的受理をオンにすると、サンプリングのリクエストでは分布が同じことだけが保証され、同じ乱数シードで書かれる文章もドラフトによって変わります。上流レポート ところが上流のドキュメントは同時にこう記録しています。IQ 系の量子化を使うと、CPU が 1 トークンを計算するときと複数トークンを計算するときとでは、丸めが少し違う 2 組のカーネルを使います。だから温度 0 の同じプロンプトでも、ドラフト、キャッシュの状態、セッションの復元の違いによって、もう 1 つの同じくらい良い答えが出ることがあります（issue #152）。STRATA_IQ_MT_MIN=1 を設定すると、すべての場合がマルチトークンのカーネルを通り、答えがドラフトに依存しなくなります。サービスでバイト単位の再現性を得るには、さらに --prompt-cache 0 --adapt-swaps 0 --pcie-frac 0 も加えます。作者の実測（IQ3_XXS、3.6K トークンのプロンプト、4 回繰り返し）：3 つのスイッチをすべて付けると、4 回で答えは 1 種類だけ。--pcie-frac 0 を付けないと 2 種類（1 回目だけ違う）。すべて既定値でも 2 種類でした。上流レポート[S03] NVIDIA の GPU 1 枚で、バッチスロットを使わないときは、この一覧にもう 1 項目足りません。v0.1.41 から、短いプロンプト（1,024 token 未満のチャンク）を読むとき、CPU が既定で一部のエキスパートを肩代わりします。CPU は自分の活性化形式を使うので、計算結果は GPU とビット単位では一致しません。だから STRATA_PREFILL_CPU_SHARE=0 も加えて、出力を肩代わりがオンになる前のバイトに戻します。コード上の事実（prefill.cpp）上流のドキュメントでは、あの設定の例は更新されておらず、CPU の肩代わりを説明する節にだけ、このスイッチが書かれています。ドキュメントとコードが食い違うときは、コードを正とします。コードを読むと、肩代わりの割合も、肩代わりするかどうかも、層ごとの計時で決まります。その計時の状態はリクエストをまたいで積み重なります。そのため、オンのままだと、同じリクエストをくり返しても、違うバイトが出るかもしれません。上流が測ったのはオンとオフの差だけで、くり返し実行は測っていません。この本も実測していません。コード上の事実（prefill.cpp）ヘッダに書かれているのは設計の目標、ドキュメントに書かれているのは実測の境界、コードに書かれているのは今の動作です。3 つとも読む必要があります。

わざと注入する反例のリスト

テストに、次の間違いをわざと注入します。ヘッドの対応を剰余から整数除算に変える。L2 正規化の代わりに RMS 正規化を使う。各層のアクティベーションキャッシュをポインタだけで判断する。ルーティングの重みを二重に掛ける。位置カウンタを凍結する。セッションの復元で PLE の履歴を落とす。テストは安定して失敗し、最初に破られた契約を指さなければなりません。注入しても通ってしまうなら、それはたぶん「プロセスが落ちなかった」ことしか見ていません。参照実装は、テスト対象のコードと同じ誤った前提を共有してはいけません。layer.cpp にある、2 つのツールがどちらもフィールド名を間違えて探した事例は、授業で議論するのに向いています。[S14]

公開リポジトリで走らせられるテスト

Strata の CMakeLists.txt のコメントには、完全なテストスイートとマイクロベンチマークは tests/ と bench/micro/ にあり、公開ソースには含まれていないので、テストをビルドするスイッチは既定でオフだ、と書かれています。コード上の事実（CMakeLists.txt）同じように、gdn.hpp のコメントで触れている参照実装 ref/gdn.py も、公開リポジトリの ref/ ディレクトリには見当たらず、そこにあるのは load.py だけです。この章が引用する照合テストと実測は、公開されたソースのコメント、テストファイル、レポートによるものです。この本は、それらを GPU で再実行してはいません。

この本に付属するテストが証明するもの

labs/tiny_inference.py のテストが確かめるのは、分割処理、保存と復元、参照の再生、制御されたドラフトの受理です。証明しているのはこの本の教育用コードであって、上流 Strata の GPU 実装ではありません。Strata のディスパッチ、量子化、非同期実行、本物の重みは、それぞれの環境で独立に検証する必要があります。
