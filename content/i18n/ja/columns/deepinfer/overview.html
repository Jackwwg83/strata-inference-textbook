見方を変えてみる

この本はずっと、ひとつのことをしてきました。普通のコンピュータで大きなモデルを動かし、ひとりの人に使ってもらう、ということです。Strata の README も冒頭でこの目標を掲げています。GPU（グラフィックスカード）は VRAM 12 GB から。上流レポート[S01]

推論のもう一方の端にあるのが、DeepSeek のオンラインサービスです。DeepSeek 自身の説明では、1 つのクラスタが 1 日に 155 兆トークンを処理します。上流レポート（Q&A ドキュメント 17 行目）2026 年 10 月 20 日、DeepSeek はこのサービスを支える推論フレームワーク DeepInfer をオープンソースにしました。このページでは、3 つの問いに答えます。DeepInfer とは何か、どこまで公開されたのか、Strata とどこが違うのか。

ひとことで：DeepInfer は、DeepSeek-V4.1-Flash 用のクラスタ推論エンジンです。プリフィル、デコード、ビジョンエンコードを別々のマシンに分け、エキスパートを数十枚のカードに敷き詰めます。今回公開されたのはエンジン本体で、オフライン推論ができます。KV キャッシュシステム、3 つの段階をつなぐ接着コード、データ並列のロードバランサーは、リポジトリに入っていません。

1.1 もう一方の端：同じ概念を、数百枚のカードに広げる

DeepInfer は推論フレームワークです。Strata と同じく、第 1 章で話した「厨房」の層にあたります（第 1 章）。README の最初の一文によると、DeepSeek の大規模オンラインサービスを支える高性能な推論フレームワークで、今回公開されたバージョンは、オフライン推論と、大規模サービスに必要なコア機能を提供します。上流レポート（README 3 行目）対応するモデルは今のところ 1 つだけ、DeepSeek-V4.1-Flash です。

Strata と同じ概念を扱っています。MoE のエキスパート、KV キャッシュ、プリフィル（prefill）とデコード（decode）、投機的デコーディング、バッチ処理です。違いは規模です。Strata は 1 台のコンピュータにモデルを押し込む工夫をします。DeepInfer は、たくさんのマシンでたくさんの人に同時にサービスする工夫をします。DeepSeek の Q&A ドキュメントには、このシステムが最初から掲げた 3 つの目標が書かれています。上流レポート（Q&A 7–13 行目）

  1. 複数のベンダーのアクセラレータカードに対応し、各プラットフォームの性能を使い切る。
  2. 普通のハードウェアでプリフィルとデコードを組む。プリフィルは普通の 8 カードのマシン、デコードは普通の 64–128 カードのスーパーノード、つまり高速インターコネクトで 1 つにつないだカードの集まりを使う。
  3. KV キャッシュを 72 時間以上保持する。古い会話が戻ってきても、キャッシュにヒットすれば、プリフィルをやり直さなくて済む。

まず規模の差を感じてみましょう。Q&A ドキュメントによると、デコードは EP64 から始めるのがお勧めで、プリフィルとデコードのカード数はおよそ 1:1 です。そのため「最小の効率的なデプロイ単位」は、プリフィル用 64 枚とデコード用 64 枚になります。上流レポート（Q&A 65–67 行目）EP はエキスパート並列（EP）のことで、第 2 ページで詳しく扱います。図 D1-1 に両端を並べました。

1.2 1 つのリクエストの旅：本番システムの地図

DeepSeek は Q&A ドキュメントに参照アーキテクチャ図を載せています。システムは、E/P/D 分離の計算ノードと、専用のストレージノードでできています。上流レポート（Q&A 41–43 行目）E はビジョンエンコーダー（VE）で、画像をベクトルに変えます。P はプリフィル、D はデコードです。別々にデプロイすると、各段階にリソースを個別に割り当てられ、最初のトークンまでの時間（TTFT）とトークン間隔（TBT）も別々に調整できます。上流レポート（Q&A 27–31 行目）

アテンションの部分はデータ並列（DP）を使い、DP の数は EP の数と同じです。各カードが自分の担当するリクエストのアテンションを計算し、MoE 層ではエキスパート並列で協力します。レプリカがこれだけ多いと仕事の割り振りが必要なので、DeepSeek は 4 つのロードバランサーを作りました。プリフィル、デコード、VE の 3 つがデータ並列レプリカ間の割り当てを受け持ち、エキスパート負荷分散（EPLB）がエキスパートをカードにどう配るかを受け持ちます。プリフィルのやり直しを避けるために、KV キャッシュのストレージもあります。上流レポート（Q&A 33 行目）入口と出口には DeepSeek Recipe もあり、API プロトコルとトークン列の間を変換します。

下の地図は、そのアーキテクチャ図を描き直し、各部品がオープンソースかどうかをリポジトリで確かめたものです。ブロックをクリックすると説明が出ます。1 歩進むを押すと、1 つのリクエストが入口から出口まで進む様子を追えます。

この図でいちばん見落としやすいのは、Entrypoint が最初に行う手順です。まず KV ストレージを調べて、このリクエストの先頭部分がどこまでヒットするかを計算し、そのあとでようやくルーティングできます。Q&A ドキュメントは、この手順を別の仕事の陰に隠せないと特に述べています。上流レポート（Q&A 157 行目）ヒットが長いほどプリフィルで計算する量が減るので、「どこまでヒットするか」で、このリクエストにどれだけ重い仕事を割り当てるかが決まります。各段階にカードをどう割り当てるか、KV をどう保存するか、P から D へどう送るかは、すべて第 3 ページにあります。4 つのロードバランサーのアルゴリズムは第 2 ページにあります。

CS を学んだ人へ：これは Web バックエンドの古典的な階層構造です。ゲートウェイがプロトコルを変換し（Recipe）、ロードバランサーがリクエストをアプリケーションサーバー群（P と D）に振り分け、状態は独立したストレージクラスタ（3FS）に置きます。違うのは、ここでの 1 台の「アプリケーションサーバー」が、数十枚のカードでできた 1 つの通信ドメインだという点です。Wikipedia：サーバロードバランスを参照してください。

Strata と比べると：Strata は、この図を 1 台のコンピュータに押し込みました。serve/server.py が HTTP とキューを担当し、serve/frontend.py がテンプレートの適用と出力の解析を担当します（第 23 章）。エンジンは同じカードの上で、先にプリフィル、次にデコードをします（第 16 章）。既定の設定では、1 つのロックがリクエストを 1 本の列に並べます（第 25 章）。クラスタでは、各層を独立したサービスに分けなければなりません。1 台のマシンはすべてのユーザーを収容できず、かといってすべてのユーザーを 1 本の列に並ばせることもできないからです。

1.3 公開の境界：リポジトリにあるもの、ないもの

README は境界をはっきり書いています。今回公開された機能は次のとおりです。最適化されたカーネルとモデル、サンプラーのランタイム。アテンションのデータ並列と、均衡のとれたコンテキスト並列（CP）、MoE のエキスパート並列と EPLB。DSpark と、信頼度に応じてスケジューリングする検証。スライディングウィンドウ・アテンション（SWA）の有界リプレイ。非同期スケジューリング、つまりゼロオーバーヘッド・バッチスケジューラー。バッチ不変（batch-invariant）な推論。決定的サンプリング。構造化出力。上流レポート（README 9–18 行目）

「完全な推論サービスには必要だが、今回は含まれていない」ものも 3 つ挙げています。上流レポート（README 38–42 行目）

  • KV キャッシュシステム。
  • VE / プリフィル / デコードの分離デプロイ（README は、エンジンに必要な機能の大部分はすでに実装済み、と補足しています）。
  • プリフィルとデコードの、データ並列レプリカ間のロードバランシング。

Q&A ドキュメントは理由を挙げています。KV キャッシュの管理とロードバランシングは DeepSeek 社内のインフラと結びつきが強すぎて、いまのところ完全には公開されていない、というものです。上流レポート（Q&A 21 行目）DeepSeek Recipe は、別のリポジトリ deepseek-recipe として単独で公開されました。上流レポート（Q&A 19 行目）

「大部分はすでに実装済み」という言葉は、コードの中に裏づけがあります。エンジンには 3 つのタイプがあります。NORMAL はプリフィルもデコードも行い、PROMPT はプリフィルだけ、COMPLETION はデコードだけを行います。コード上の事実（engine_type.py。C++ 側でも scheduler.hpp で同じものを定義しています）ところが、メインのエンジンクラス LLMEngine には「ここから先はすべて仮想関数」というコメントがあります。PD 分離の初期化、プリフィル後の KV 保存、KV 保存、処理が終わったリクエストのデコードエンジンへの送信、の各関数には、1 行の説明があるだけで、関数本体がありません。リポジトリには、これらを実装する別のクラスもありません。コード上の事実（llm_engine.py 800–858 行目）図 D1-3 に、この境界を描きました。

もうひとつ誤解しやすい点があります。リポジトリには deepinfer/entrypoints/ というディレクトリがありますが、図 D1-2 の本番の Entrypoint ではありません。中にあるのはオフライン用の LLM クラスだけです。このクラスは、同じプロセスの中でエンジンを作り、プロンプトの束を渡し、すべて終わるまで step() を繰り返し呼びます。コード上の事実（llm.py）リポジトリにある HTTP サーバーは、既定で無効の性能サンプリング用エンドポイント POST /profile だけで、ユーザーのリクエストは受け付けません。コード上の事実（profile_server.py）

Q&A ドキュメントは、本番ではいまのところテンソル並列（TP）と CP は使わないと言っていますが、README と例はどちらも CP に対応しています（例には --cp 8 があります）。上流レポート（Q&A 53 行目、examples/README 6–8 行目）両者は矛盾しません。一方は本番での構成、もう一方はコードにできることを述べています。

1.5 誰が動かせるか、何枚のカードが要るか、壊れたらどうするか

まず、参入のハードルです。ハードウェアは 2 種類だけで、NVIDIA SM100 GPU と Huawei Ascend 950 NPU です。ソフトウェアは Linux、GCC 13 以上、Python 3.12 が必要で、NVIDIA は CUDA 13、Ascend は CANN 9.2 が必要です。上流レポート（README 33–52 行目）オフラインの例の既定の引数は --ep 8 で、8 カードのマシン 1 台を想定して書かれています。コード上の事実（offline_inference.py）ベンチマークの規模は環境で決まります。ep_size = WORLD_SIZE × 見えるカード数 で、WORLD_SIZE はノード数です。上流レポート（examples/README 61 行目）

そのため、このコラムの読者の多くは DeepInfer を動かせませんし、この本も動かしていません。下の数字はすべて DeepSeek 自身の報告で、この本では再測定していません。

2 つの性能グラフは、どちらも README が述べているベンチマークです。プリフィルは SM100 4 枚、デコードは SM100 64 枚で、それぞれ 1 つのスケールアップドメインの中で測っています。上流レポート（README 83 行目）デコードのグラフのスループットは、実測の受理率ではなく、仮定した受理率で換算したものです。この計算の仕方は第 4 ページで詳しく扱います。

155 兆トークンとは、どれくらいの規模でしょうか。1 日 86,400 秒で割ると、155 × 10¹² ÷ 86,400 ≈ 18 億 token/s です。Strata は RTX 5070 1 枚で答えを書くのに約 93 token/s（第 1 章）なので、18 億 ÷ 93 ≈ 1900 万です。教育用の試算 この比は桁数の感覚をつかむためだけのものです。Q&A ドキュメントは、155 兆のうち入力がどれだけ、キャッシュヒットがどれだけかを述べていませんし、Strata の 93 は出力だけを数えています。

弾力的なスケーリングと耐障害性。Q&A ドキュメントには、本番でトラフィックの増減や故障したカードにどう対応するかを説明した節があります。上流レポート（Q&A 193–211 行目）プリフィルは「キャッシュにミスしたトークンの数」で必要な台数を決め、デコードは「実行中のリクエスト数」で調整します。調整のたびに速度が制限され、上限と下限もあります。デコードエンジンは停止の通知を受けると 1 分間の猶予期間があり、終わっていないリクエストは KV キャッシュごとまとめて別のデコードエンジンに渡され、続きが処理されます。普段から余裕を残しています。プールには待機中の空きマシンがあり、オンラインのインスタンスも計算上の需要より多く用意されています。クォータ使用率が 0.8 を超えているときは、縮小が禁止されます。再起動には数分かかるので、耐障害性は、冗長性とリクエスト単位の再ルーティングに頼っており、個々のエンジンの再起動を速くすることには頼っていません。

ワイドエキスパート並列には、特有の弱点があります。1 つのインスタンスのすべてのカードが 1 つの通信ドメインを作るので、1 枚壊れると、インスタンス全体が使えなくなります。再起動のとき、プラットフォームは正常なカードの数から EP のサイズを決め直します。これに対応するものがコードにあります。冗長エキスパートの数は、「エキスパートの総数が ep_size で割り切れる」まで自動で増やされるので、EP のサイズは 384 の約数でなくてもかまいません。コード上の事実（eplb/__init__.py）これと障害復旧との関係は、この本の推論で、Q&A ドキュメントにはそう書かれていません。教育用の試算

Strata と比べると：Strata にはマシンが 1 台しかなく、引き継いでくれる「別のカード」がありません。ライフサイクルの問題は、プロセスをどう起動し、リクエストをどうキャンセルするか（第 24 章「キャンセル」）で、キューの問題は、1 本の列をどう並べるか（第 25 章「待ち行列理論の入門」）です。クラスタでは、カードの故障が日常なので、「カードが 1 枚減っても、サービスを続けられるか」が設計の一部になります。

1.6 このコラムの読み方

このあとの 4 ページでは、それぞれ本番システムの一部を取り上げ、その仕組みを説明してから、コードに降りていきます。どのページも、まずこの本で学んだ概念に戻り、そのうえで、クラスタではどこが違うかを説明します。図 D1-5 が道案内です。

  • 第 2 ページ ワイドエキスパート並列：アテンションはデータ並列、エキスパートはエキスパート並列で処理する。EP64 が EP8 よりスループットが高い理由。EPLB と 3 つのデータ並列ロードバランサーが、どう仕事を分けるか。先に第 10 章と第 21 章「パイプライン並列とテンソル並列」を読んでください。
  • 第 3 ページ E/P/D 分離と 72 時間の KV キャッシュ：VE、P、D をなぜ分けるのか。KV キャッシュを SSD クラスタにどう保存し、ヒットしたあと、ごく一部だけをどう再計算するのか。先に第 17 章「ページング管理」と第 20 章を読んでください。
  • 第 4 ページ DSpark 投機的デコーディングとゼロオーバーヘッド・スケジューリング：ドラフトが一度に何個推測し、信頼度で何個検証するかを決める仕組み。CPU が次のステップを準備している間も GPU が止まらない仕組み。先に第 18 章と第 25 章「連続バッチ処理」を読んでください。
  • 第 5 ページ バッチ不変、決定的サンプリング、構造化出力：同じ入力が、サーバーでなぜ変わってしまうのか、どうすれば同じに戻せるのか。モデルに有効な JSON だけを出力させるにはどうするか。先に第 26 章と第 2 章を読んでください。

この 3 点を覚えよう

  1. DeepInfer と Strata は同じ概念を扱いますが、難題は正反対です。Strata はモデルを 1 台のコンピュータに押し込まなければならず、DeepInfer は数百枚のカードで多くの人に同時にサービスしなければなりません。
  2. 本番システムは、Recipe、Entrypoint、E/P/D 分離された VE / P / D、4 つのロードバランサー、KV ストレージクラスタでできています。今回公開されたのはエンジン本体と EPLB で、オフライン推論ができます。
  3. KV キャッシュシステム、3 つの段階をつなぐ接着コード、データ並列ロードバランサーは、リポジトリにありません。エンジンはそれらのためにタイプと空のフックを残してあり、デプロイする人が自分で補う必要があります。

よくある誤解：「DeepInfer がオープンソースになったから、持ってくれば DeepSeek のようなオンラインサービスが組める。」

今回のリポジトリが提供するのはオフライン推論だけです。1 つのプロセスがプロンプトの束を受け取り、計算が終わったら終了します。ユーザーのリクエストを受ける HTTP サービスも、KV キャッシュシステムも、プリフィルとデコードをつなぐ接着コードも、データ並列ロードバランサーもありません。README が挙げるハードウェアは SM100 と Ascend 950 だけで、Q&A ドキュメントが勧める最小の効率的な単位は 128 枚のカードです。いちばんの価値は、本番級のエンジンが内部でどう書かれているかを見られることです。

コマンドラインからカーネルまで

python examples/offline_inference.py を例にします。下の各ステップは、固定したコミット 774ce244 のソースと突き合わせて確かめました。

  1. プロセスを起動する。例の既定は --ep 8 です（offline_inference.py 12–17 行目）。examples/_launch.py の run_dp は、RANK と WORLD_SIZE に従って、このノードが担当する DP ランクごとに子プロセスを 1 つ起動します（26–40 行目）。
  2. エンジンを作る。LLM.__init__ は offline_inference=True で EngineArgs を作り、LLMEngine.from_engine_args を呼びます（llm.py 70–84 行目）。EngineArgs のエンジンタイプの既定は NORMAL です（arg_utils.py 41 行目）。
  3. ゼロオーバーヘッド・スケジューリングは既定でオン。environ.py の DEEPINFER_ZERO_OVERHEAD_SCHEDULING の元の既定値はオフです（179 行目）。しかし、ユーザーが設定していなければ、EngineArgs.__post_init__ がエンジンタイプに応じてオンにします。NORMAL と COMPLETION はオン、PROMPT はオフです（arg_utils.py 48–55 行目、engine_type.py 15–17 行目）。そのため、README の「既定で有効」はコードと一致します。
  4. トークン化と投入。generate() は各プロンプトを _add_request に渡します。トークン ID が与えられていなければ、Hugging Face のトークナイザーでエンコードします（llm.py 144–166 行目）。本番では、この手順は Recipe が行います。
  5. メインループ。_run_engine は、未完了のリクエストがなくなるまで LLMEngine.step() を繰り返し呼び、最後に処理中の結果を出し切ります（168–195 行目）。LLMEngine は C++ 拡張 deepinfer._C.engine から Scheduler、BlockManager などをインポートします（llm_engine.py 19–31 行目）。この拡張は、setup.py が csrc/ 以下のソースファイルをコンパイルして作るもので、cuda_utils、engine、graph_timer の 3 つのサブモジュールに分かれています（pybind.cpp）。
  6. 各カードの上で。Worker が毎ステップのフォワード、後処理、サンプリングを進め（worker.py）、ModelRunner がモデルを実行します（model_runner.py）。モデルはレジストリで見つけます。アーキテクチャ名 DeepseekV41ForCausalLM は deepseek_vl.DeepseekVLForCausalLM に対応し（models/__init__.py 15–17 行目）、これはテキスト専用の DeepseekForCausalLM を継承しています（deepseek_vl.py 26 行目）。
  7. カーネルに行き着く。プラットフォームクラスが、どの TileLang 演算子を使うかを決めます。GPU は cuda、NPU は asc です（platform.py 55–88 行目）。残りの演算子は、表 D1-2 のカーネルライブラリから来ます。
