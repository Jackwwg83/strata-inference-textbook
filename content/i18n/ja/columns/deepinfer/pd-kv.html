こんな経験はありませんか

長い文書をチャット AI に渡すと、最初の質問は答えが出るまで少し待たされます。ところが続けて質問すると、答えはほとんどすぐに返ってきます。第 20 章で Strata のやり方を説明しました。読み終えたプレフィックスをチェックポイントとして手元のメモリに保存し、次は新しく足された部分だけを読む方法です。

DeepSeek のオンラインサービスは、こうした追加の質問を毎日数えきれないほど受けています。同じことをクラスタ全体のシステムとして作り上げました。問題を読む段階と答えを書く段階を 2 組の GPU に分け、KV キャッシュは専用の SSD クラスタに入れて 72 時間以上保持します。このページでは 3 つの問いに答えます。なぜ分けるのか。KV キャッシュはどこに置くのか。ヒットした後はどうつなぎ、惜しくもヒットしなかったときはどうやって計算を減らすのか。

ひとことで：プリフィル（prefill）は演算性能を使い、デコード（decode）はメモリ帯域を使います。同じ GPU 組に詰め込むと互いに足を引っ張るので、DeepSeek はビジョンエンコーダー、プリフィル、デコードを別々にデプロイしています。KV キャッシュは専用の 3FS ストレージクラスタに置き、ヒットすれば読み戻します。スライディングウィンドウの小さな部分が欠けても、再計算するのは 128 トークンだけです。オープンソースの DeepInfer には、これらの方式に必要なエンジンの役割とキャッシュのレイアウトが入っています。KV キャッシュシステムと分離デプロイをつなぐコードは公開されていません。

3.1 問題を読む段階と答えを書く段階は、なぜ 2 組の GPU に分けるのか

第 16 章で、1 回のリクエストは 2 つの段階に分かれると説明しました。プリフィル（prefill）は「問題を読む」段階です。プロンプトのトークンはすべて分かっているので、数千個をまとめて計算し、重みは 1 回読めばブロック全体で使い回せます。ボトルネックは演算性能です。デコード（decode）は「答えを書く」段階です。1 ステップでリクエストごとに増えるトークンは数個だけです（DeepInfer は投機的デコーディングを使っていて、ベンチマーク図では平均で 1 ステップあたり約 3 個）。それでも重みと KV キャッシュを 1 回読む必要があるので、ボトルネックはメモリ帯域です。2 つの段階はルーフライン上の位置が違います。第 5 章「演算性能とルーフライン」と第 16 章「バッチ処理」を見てください。

ユーザーの体感も 2 つの指標に対応します。最初のトークンまでの時間（TTFT）は、リクエストを送ってから最初の 1 文字が見えるまでの時間で、ほとんどプリフィルに使われます。トークン間隔（TBT）は、その後の隣り合う 2 つのトークンの間の時間です。デコードの 1 ステップがどれだけ速いか、途中で止められないかで決まります。

困ったことが起きるのは、2 つの段階が同じ GPU 組に詰め込まれたときです。DeepInfer のオープンソースコードには、まさにこの「混合」エンジンがあります。スケジューリングを見るのがいちばん分かりやすいでしょう。コード上の事実エンジンには 3 つの役割があります。NORMAL は両方の段階を行い、PROMPT はプリフィルだけ、COMPLETION はデコードだけを行います（engine_type.py）。NORMAL エンジンは、1 ステップごとに、組の全員がプリフィルをするか、全員がデコードをするかのどちらかです。同じデータ並列（DP）グループの GPU は同じ種類の仕事をしなければならず、1 回の投票でそろえます（scheduler.hpp）。投票点は既定ではデコード 70 ステップに 1 回で、すべての rank にプリフィルの仕事があるときだけ全員で実行します。ほかに 100 ステップに 1 回の保険の点があり、どれかの rank に仕事があれば全員で実行します（environ.py）。

この方式では、プリフィルを 1 ステップ実行している間、その GPU 組にいる全ユーザーのデコードが同じ時間だけ止まります。下のタイムラインで 2 つのデプロイを並べて見てみましょう。ステップの長さは DeepInfer の README にある 2 枚のベンチマーク図から取りました。プリフィル 1 ステップ（32,768 トークン）は約 376 ms、デコード 1 ステップは約 13 ms です。教育用の試算2 枚の図はハードウェア構成が違うので、ここでは桁だけを借ります。条件は末尾の「もう一歩深く」を見てください。

図から分かることが 2 つあります。1 つ目。混合デプロイでは、デコードのステップ間隔がときどき 13 ms から 389 ms に跳ね上がり、答えを読んでいるユーザーは一瞬止まったように感じます。投機的デコーディングは 1 ステップで約 3 個のトークンを出すので、トークン 1 個あたりの平均は約 4 ms になり、トークンはまとめて届きます。ここではステップ間隔を TBT の代わりに使っています。2 つ目。止まる回数を減らすために、混合エンジンはプリフィルをためてから実行します。すると新しいリクエストは次の投票点まで待つことになり、かえって TTFT が長くなります。実際の混合エンジンはもう少し悪くなります。プリフィルを 1 ステップ終えた直後の次のステップが投票点にあたり、各 rank にまだ仕事があれば、そのまま続けて実行するからです（scheduler.hpp）。コード上の事実

そこで DeepSeek の本番システムは、ビジョンエンコーダー（VE）、プリフィル、デコードを別々にデプロイし、それぞれ専用の GPU を使います。これを E/P/D 分離と呼びます。Q&A ドキュメントによると、分けた後は段階ごとにリソースを別々に割り当てられるので、TTFT と TBT を別々に制御し、別々に最適化できます（Q&A ドキュメント）。上流レポートオープンソースのコードでは、PROMPT エンジンが処理を終えたプロンプトを「completion engine に送る」ことになっていますが、その関数は空です（llm_engine.py）。コード上の事実README にも、分離デプロイは今回のリリースに含まれず、「必要なエンジン機能の大部分は実装済み」であるにとどまると書かれています（README）。上流レポート

CS を学んだ人へ：これは OS の授業で習う、対話型タスクとバッチタスクが同じ CPU を取り合う昔からの問題です。長いジョブがプロセッサを握ると、短いタスクの応答が引き延ばされます。第 25 章ではこれを護送船団効果と呼び、FIFO とラウンドロビンで示しました（第 25 章「スケジューリングアルゴリズム」）。3 段分離は、2 種類のタスクにそれぞれ 1 台ずつ機械を与えることにあたります。学術界にも同じ議論があります。DistServe の論文を見てください。

Strata と比べると：Strata は 1 台の PC で動くので、問題を読む段階と答えを書く段階は、同じ GPU を交代で使うしかありません。第 16 章のベンチマーク表では、RTX 5070 は 32K のプロンプトを 1 秒に 2,171 トークンで読み、答えは 1 秒に 81.8 トークンで書きます上流レポート。サーバーは既定では一度に 1 つの会話しか動かしません（第 17 章）。1 人で使うなら、問題を読んでいる間にデコードを待っている人はいないので、分けても意味がありません。クラスタでは、長いプロンプトのプリフィルが同じ組の数百人のデコードをまとめて止めてしまうので、分ける必要があります。

分けた後は、段階ごとに自分のボトルネックに合わせて並列方式を選べます。Q&A ドキュメントの構成は次のとおりです（目標、並列方式）。上流レポート

両端の選び方は正反対です。プリフィルは 1 ステップに最初から数万個のトークンがあり、エキスパートごとのトークンも十分に多いので、行列積を満杯で回せます。EP が小さいほうが GPU 間の通信も減らせます。デコードは 1 ステップでリクエストごとに数個のトークンしかないので、たくさんのリクエストのトークンを同じエキスパートに集めて、ようやくまともなバッチになります。だから EP は大きいほど良いのです。教育用の試算この計算はワイドエキスパート並列のページで詳しく見ます。スーパーノードとは、64–128 枚の GPU を高速インターコネクトでつなぎ、1 つのまとまりとして扱えるシステムのことです。

デプロイできる最小の構成は、プリフィルのインスタンス 1 つとデコードのインスタンス 1 つです。実際には P と D の GPU 数はおよそ 1 : 1 で、デコードは EP64 以上を推奨しているので、最小の効率的な単位は、プリフィル用 64 GPU とデコード用 64 GPU です（Q&A ドキュメント）。上流レポート図 D3-2 にこの単位を描きました。

P と D を別々のデータセンターに置けるでしょうか。Q&A ドキュメントは置けると言っています。V4.1 Flash は KV キャッシュをとても小さく圧縮するので、データセンター間で送ることができます。GPU 8 枚あたり約 400 Gbps のインターコネクト帯域を確保します。代償は信頼性です。2 つの拠点の間の光ファイバーは、工事でショベルの一撃を受ければ切れてしまうかもしれません。DeepSeek は実際には、推論ノードを別々の、ただし隣り合ったデータセンターに置いています（Q&A ドキュメント）。上流レポート

表には本番では CP を使わないとありますが、オープンソースのコードには CP が入っていて、README の機能一覧にも「balanced CP」と書かれています（README）。両者は矛盾しません。コードは対応していて、本番では有効にしていないだけです。コンテキスト並列（CP）は、1 つの長いプロンプトをいくつかに切り、複数の GPU でアテンションを一緒に計算する方式です。コードではプリフィルだけが使えます（llm_engine.py）。コード上の事実「バランスの取れた」切り方は、末尾の「もう一歩深く」で説明します。

GPU の枚数も固定ではありません。Q&A ドキュメントによると、プリフィルは「キャッシュにヒットしなかったトークンがどれだけあるか」で必要なマシン数を決め、デコードは「動いているリクエストがどれだけあるか」で調整します（Q&A ドキュメント）。上流レポートつまり、ヒット率がプリフィル用マシンを何台動かすかを直接決めます。スケールの増減と障害対応の残りの詳細は概要のページを見てください。

3.3 KV キャッシュはどこに置くか：GPU メモリ、手元のメモリ、3FS

DeepSeek がこの推論システムに掲げた 3 つ目の目標は、KV キャッシュを 72 時間以上保持することです。窓が長いほど、翌日に戻ってきたユーザーの追加の質問でもヒットし、繰り返しのプリフィルを省けます。代償は、たくさん保存し、たくさん管理しなければならないことです（Q&A ドキュメント）。上流レポートこの KV は 3 か所に置かれます。図 D3-3 は Q&A ドキュメントの表をもとに描いたものです（表）。

なぜ、各マシンのメモリとディスクではなく、専用のストレージクラスタを使うのでしょうか。Q&A ドキュメントは 3 つの理由を挙げています（Q&A ドキュメント）。上流レポート

  • どのプリフィル用マシンも、どのプレフィックスにもヒットできます。ロードバランサーは「どのマシンが空いているか」だけを見ればよく、「このユーザーのキャッシュはどのマシンにあるか」を気にする必要がありません。そのため、プリフィルのロードバランスではプレフィックス親和性によるルーティングもしません（Q&A ドキュメント）。
  • ストレージノードと計算ノードを別々にスケールさせられます。
  • 計算ノードが壊れても、KV キャッシュは失われません。計算ノードの故障率は、ストレージノードより 1 桁以上高いからです。

デコード中に作られた KV も同じようにディスクに書きます。ヒット率を上げるためです（Q&A ドキュメント）。上流レポート理由は簡単です。今回書いた答えが、次のターンのプロンプトのプレフィックスになるからです。

ストレージサーバーの推奨構成は、30.73 TB の SSD を 20 本です。1 台あたり少なくとも 40 GB/s の読み出しと 5 GB/s の書き込みを提供し、総容量は 24 時間分のデータを保存できる大きさにして、推論デプロイの規模に合わせて台数を足します。論理サイズで数えると、オンラインの推論 GPU 1 枚あたり約 14.4 TB のストレージに相当し、実際に必要な物理容量はもっと多くなります（Q&A ドキュメント）。上流レポート

この数字でざっと計算してみましょう。ストレージサーバー 1 台の生の容量は 20 × 30.73 ≈ 615 TB です。10 + 2 の消失訂正符号では物理容量が論理データの 1.2 倍になるので、1.2 で割って約 512 TB。これで約 512 ÷ 14.4 ≈ 36 枚のオンライン GPU の論理データがまかなえます。この 36 枚のうち、プリフィルとデコードがそれぞれ約半分です。デコード用 GPU はストレージからプレフィックスを読みません。KV はプリフィル用 GPU から送られてくるからです。つまり実際に読むのは約 18 枚のプリフィル用 GPU で、同時に読むと 1 枚あたり約 40 ÷ 18 ≈ 2.2 GB/s になります。教育用の試算これは容量でマシン台数を決めるときの、おおまかな下限にすぎません。Q&A ドキュメントにはストレージサーバーと GPU の比率は書かれていませんし、1 回の読み出しは消失訂正グループの複数のノードに分散されます。3.5 節のインタラクティブな図でも、この数字を使います。

3FS は DeepSeek が自分で作った分散ファイルシステムです（3FS の GitHub リポジトリ）。ノード障害やネットワークの揺らぎがあっても、高可用性と高性能を両立しなければなりません。データは 10 + 2 の消失訂正符号で保存するので、各グループは 2 つのノードが同時に壊れても大丈夫です。Q&A の原文では、読むときにグループ内の 11 ノードへ同時にリクエストを送り（1 グループは 10 + 2 = 12 ブロック）、任意の 10 個が返ればデータを復元できます。各ストレージノードではガベージコレクション用のプロセス（GC Worker）が動き、最近最少使用（LRU）の順に古いキャッシュを定期的に消して、ディスク使用量を水位線以下に保ちます（Q&A ドキュメント）。上流レポート

消失訂正符号：チェック用のブロックを少し余分に持てば、数ブロック壊れても元に戻せる

データを失わないいちばん簡単な方法は、3 つコピーを持つことです。2 つ壊れても 1 つ残りますが、容量は 3 倍かかります。消失訂正符号はもっと節約できます。データを k ブロックに切り、チェック用のブロックを m 個計算して、全部で k + m ブロックを別々のマシンに置きます。任意の k ブロックが残っていれば、元のデータを計算し直せます。

定義：(k + m) 消失訂正符号は、任意の m ブロックが同時に失われても耐えられ、容量のオーバーヘッドは (k + m) ÷ k 倍です。よく使われる構成はリード・ソロモン符号です。データを多項式の値と見なし、失われた値を残りの点から補間して取り戻します。

具体的な数字：3FS は KV キャッシュを 10 + 2 で保存します。容量は 20% 増えるだけで、どの 2 ノードが壊れてもデータは失われません。3 コピーなら 200% 増えるうえ、耐えられるのもやはり 2 つまでです。代償は、読み書きのたびに符号化の計算が必要になることと、読むときに 10 ブロックを集める必要があることです。

このページとの関係：KV キャッシュは壊れても計算し直せるので、ここまで気を使う必要はないように見えます。しかし、3〜7 日、約 100 PiB を持ちこたえなければならず、1 回のノード故障で、何千何万ものユーザーのヒットが失われます。消失訂正符号があるおかげで、この「計算し直せるデータ」を、少ない容量で高い可用性を持たせて保てるのです。

参考文献：Wikipedia：リード・ソロモン符号 · Wikipedia：RAID · Wikipedia: Erasure code

kvcache-store の層には有効期限のロジックがなく、回収はすべて 3FS 自身の GC に任せています。3FS は KV キャッシュに約 100 PiB の SSD を提供します。保持期間（TTL）は、エージェントのトラフィックが 3 日、チャットのトラフィックが 7 日です。チャットのトラフィックはロングテールが重く、少量の KV が何度も繰り返し読まれます。経験的には、TTL を 3 日にするとチャットのヒット率が 0.5%–1% 下がります（Q&A ドキュメント）。上流レポートこれはまさに第 12 章で説明したヒット率とワーキングセットです。どのくらい前のアクセスまで数えるかで、キャッシュに必要な大きさが決まります（第 12 章「ヒット率とワーキングセット」）。

CS を学んだ人へ：10 + 2 の消失訂正符号は RAID 6 と同じ考え方です。チェック用を 2 つ余分に持てば、どの 2 つが壊れても復元できます。「11 個にリクエストを送り、10 個返ったらデコードする」のは冗長読み出しです。リクエストを 1 つ余分に送り、先に返ってきた 10 個を使って、いちばん遅い 1 つは待ちません。ロングテールのレイテンシを抑えるためです。

Strata と比べると：Strata の KV キャッシュも階層になっています。ふだんは GPU メモリにあり、コンテキストが 64K を超えると、完全な KV はメモリに置いて、GPU メモリにはよく使うページだけを残します（第 17 章「KV キャッシュとページング管理」）。プレフィックス再利用のチェックポイントも手元のメモリにあり、1 つ約 118 MB で、最大 6 個まで残します（第 20 章）。1 台の PC が 1 人にしかサービスせず、次の質問も同じマシンに来るので、手元のメモリで足ります。DeepSeek では、ユーザーの次のリクエストがどのプリフィル用マシンに行くか分からず、KV も 3〜7 日残す必要があるので、誰からも届く共有ストレージに置くしかありません。

3.4 2 種類の KV：ページ化されたブロック KV と、固定長の SWA 状態

V4.1 Flash のアテンションには 2 種類の記憶があります。1 つは第 17 章と同じで、会話が長くなるにつれて増え、ページングで管理します。これをブロック KV と呼びます。もう 1 つは直近の短い区間だけを覚えるもので、SWA 状態と呼びます。スライディングウィンドウ・アテンション（SWA）は、アテンションを簡単にしたものです。各トークンは自分より前の直近の区間だけを見て、ウィンドウの外は見ません（アテンション自体は第 8 章「アテンション機構」を見てください）。V4.1 のウィンドウは 128 トークンです（Q&A ドキュメント）。上流レポートウィンドウの大きさはモデルの設定ファイルから来ており（config.py）、設定ファイル自体はコードリポジトリに入っていません。

2 種類の記憶を、DeepInfer は 2 つのアロケーターで別々に管理します（llm_engine.py）。コード上の事実

  • ブロック KV は 128 トークンで 1 ブロックとし、第 17 章のページングと同じようにブロックテーブルで探します（model_metadata_utils.py）。ブロック KV には、メイン KV とインデクサーの K が入ります（Q&A ドキュメント）。KV レコード 1 件は 512 個の数にスケール係数を加えたもので、FP8 では 528 バイト、FP4 では 288 バイトです（cache_common.py）。圧縮層は ratio 個のトークンごとにやっと 1 件のレコードを保存するので、128 トークンの 1 ブロックは 128 ÷ ratio 件しか使いません（cache_engine.py、同じファイル）。
  • SWA 状態 はページ化されたブロックには入りません。各シーケンスは状態キャッシュの中に固定長のスロットを 1 つ持ち、これを StateBlock と呼びます。スロットはアーカイブするかどうかで 2 つの領域に分かれます。前半はアーカイブする SWA、後半はアーカイブしない部分で、YoCo の消費層の SWA と圧縮状態が入ります（cache_engine.py）。各層はリングバッファで、128 + 6 = 134 トークンを入れます。余分な 6 つは、投機的デコーディングのロールバック用です（cache_engine.py、environ.py）。既定の設定では、位置 pos のトークンは pos mod 134 番目のマス目に書かれ、新しいトークンがいちばん古いものを上書きします（prepare_tensor_input_v4.cpp）。

リクエストが来ると、アロケーターはブロックテーブル 1 つとスロット番号 1 つをまとめて渡します（block_manager.hpp）。コード上の事実図 D3-4 にこの 2 つを描きました。

SWA 状態のうちアーカイブが必要なのは前半の領域だけです。コードではこの領域を to disk（「ディスクへ書く」）と呼んでいますが、SWA は 3FS には入らず、後で説明するように手元のメモリに置かれます。このページでは一貫して「アーカイブ」と呼びます。Q&A ドキュメントがそのサイズを計算しています。20 層 × 134 トークン × 528 バイト ＝ 1,415,040 バイトで、1 シーケンスあたり約 1.4 MB です（Q&A ドキュメント）。上流レポートコードの式も合っています。アーカイブのサイズは「アーカイブする層数 × 1 層あたり 134 トークン分のバイト数（32 バイトにアライン）」に等しくなります（cache_engine.py）。コード上の事実134 × 528 ＝ 70,752 バイトで、ちょうど 32 の倍数なので、アラインしても余計な場所を取りません。教育用の試算「前半 20 層をアーカイブする」というのは Q&A が示した数で、コードはモデル設定から層数を自分で計算します。

この状態は、128 の整数倍の位置でしかアーカイブしません。コードでのアーカイブの粒度は 128 で、アーカイブの位置が 128 の倍数でなければ、そのままエラーにします（cache_engine.py、同じファイル）。コード上の事実Q&A ドキュメントによると、デコード中は 128 の境界を 1 つ越えるたびに、GPU メモリの中で現在のウィンドウをコピーし、リクエストが終わるときに、いちばん新しいコピーからアーカイブします（Q&A ドキュメント）。上流レポートオープンソースのコードにコピー関数はありますが、「コピーするかどうか」を決める should_copy_state は常に False を返します（llm_engine.py）。コード上の事実プリフィルとデコードがそれぞれアーカイブ位置をどう選ぶかは、末尾の「もう一歩深く」を見てください。

どこに保存するのでしょうか。SWA 状態は 3FS には入らず、それを作ったマシンのメモリにだけ残ります。Entrypoint のマシンにはメモリ上のディレクトリがあります。論理的には 1 つで、物理的にはキーごとに各 Entrypoint マシンに分散していて、どのマシンがどの SWA 区間を持っているかを記録しています。ヒットしたときに手元になければ、400G VLAN 経由で別のマシンから取り寄せます（Q&A ドキュメント）。上流レポートプリフィルからデコードへ送るときも、SWA 状態はブロック KV と同じ経路を通ります。コードでは、デコードエンジンに送る状態はアーカイブされるものより多く、アーカイブしない領域（消費層の SWA と圧縮状態）も一緒に送られます（cache_engine.py）。コード上の事実

オープンソースのコードには、アーカイブと転送のインターフェースはありますが、中身は空です。LLMEngine には「仮想関数」が並んでいます。分離デプロイの初期化、KV の保存、処理済みのプロンプトをデコードエンジンへ送る関数で、既定では何もしません（llm_engine.py）。シーケンスのオブジェクトには「ヒットしたトークン数」「SWA の有効な開始位置」などのフィールドが用意され、外部が埋めるようになっていて、コメントには「ヒット数は外部から注入する」と書かれています（sequence.hpp）。コード上の事実今回のリリースには、外部ストレージからヒットを調べ、これらのフィールドに書き込むコードは見つかりませんでした。これは README と一致します（README）。

Strata と比べると：第 20 章では、2 種類の記憶をノートとホワイトボードにたとえました。KV キャッシュはノートのようなものです。位置の順に後ろへ書いていき、戻るときは後ろの数行を見なければ済みます。GDN の再帰状態はホワイトボードのようなものです。トークンごとに全体を書き換えるので、過去の姿は事前に撮った写真でしか戻せません（第 20 章「スナップショットとコピーオンライト」）。DeepInfer のブロック KV はノートで、SWA 状態はどちらかといえばホワイトボードに近いものです。固定長のリングバッファで、新しいトークンがいちばん古いものを上書きします。GDN のように 1 ステップごとに全体を書き直すわけではなく、1 ステップで変わるのは 1 マスです。共通するのは、上書きされた履歴は戻せないという点です。そのため Strata の GDN 状態と同じく、決めた位置で写真を撮ってアーカイブするしかありません。Strata のチェックポイントは約 118 MB で、大部分がそのホワイトボードです。DeepInfer が 1 シーケンスごとにアーカイブする SWA は約 1.4 MB だけです。ウィンドウが 134 トークンしかないからです。

3.5 ヒットすれば読み、SWA が欠けても 128 個だけ再計算する：有界リプレイ

長さ L のリクエストが来たとき、どれだけ再利用できるでしょうか。Q&A ドキュメントの決まりはこうです。ヒット長はブロック KV で決まり、最後の 1 ブロックを再計算するかどうかは SWA 状態で決まります（Q&A ドキュメント）。上流レポート具体的には 3 ステップです。

  1. ヒット長は最大でも L − 134 です。ウィンドウ用に 128 トークン、投機的デコーディングのロールバック用に 6 トークンを残します。
  2. この上限の範囲でブロック KV を調べ、ヒット長 L1 を得ます。L1 は 128 の倍数です。
  3. 次に SWA 状態を調べます。L1 − 128 から L1 の間にアーカイブがあれば、ヒット長は L1 です。なければ 1 ブロック戻って L1 − 128 にヒットしたことにし、戻した分の 128 トークンを再計算します。

1 ブロック戻った後、どうやって再計算するのでしょうか。正確な方法は SWA 状態を最初から計算し直すことですが、スライディングウィンドウは層ごとに前を見るので、ずっと遠くまでさかのぼることになります。DeepInfer が使うのは有界リプレイ（bounded replay）です。直近の 128 トークンだけを再計算し、ウィンドウをリプレイ区間の内側で打ち切ります。位置 s からリプレイを始めるとき、位置 i のクエリは max(s, i − 127) から i までのキーだけを見て、近似した SWA 状態を作ります。リプレイするトークン数は定数になり、コンテキストがどれだけ長くても関係ありません。ただし、この 128 トークンはやはりすべての層を通ります（Q&A ドキュメント）。上流レポートコードでは、通常のプリフィルの SWA の見える範囲の左端は、「ウィンドウの左端」と「SWA の有効な開始位置」のうち大きいほうです（prepare_tensor_input_v4.cpp）。有効な開始位置より前の履歴はゼロで埋められ、アテンションからは見えません（同じファイル）。コード上の事実これが Q&A にある max(s, i − 127) の実装で、s が有効な開始位置です。後で説明する打ち切りが有効なときは、別の関数が「打ち切りの左端」をもう 1 つ加えて、3 つのうち最大のものを取ります（同じファイル）。

同じ工夫は別の場所でも使われていて、しかもプリフィルのたびに使えます。V4.1 Flash の層は 2 つに分かれていて、前半が「エンコーダー層」、後半が「デコーダー層」です。デコーダー層のブロック KV はその層自身では計算せず、最後のエンコーダー層の隠れ状態から射影して作ります。各層が計算する必要があるのは自分の SWA 状態だけです。コードはこの構造を YoCo と呼んでいます。同名の論文『You Only Cache Once』にも、似た「デコーダー・デコーダー」構造が書かれています。デコーダー層の SWA を正確に求めるには、最後の 2,560 トークンを 20 個のデコーダー層に通す必要があります。DeepInfer は、プロンプトの最後の短い区間だけをこの 20 層に通し、結果はデコード専用で、プレフィックスキャッシュには入れません。Q&A は、これでプリフィルの総計算量がほぼ半分になると言っています（Q&A ドキュメント）。上流レポート2,560 はちょうど 20 × 128 です。1 層進むごとに、スライディングウィンドウがさらに 128 トークン前を見るからです。教育用の試算

この部分のスイッチは、README とコードに具体的に書かれています。DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=compact、DEEPINFER_YOCO_PREFILL_KEEP_TOKENS=140 と設定するのが V4.1 の既定の使い方で、残す末尾はウィンドウに最大のロールバック長を足した分をカバーしなければなりません（README）。上流レポートコードは KEEP_TOKENS ≥ ウィンドウ + ロールバック、つまり少なくとも 128 + 6 ＝ 134 を要求します。モデルの読み込み時に 1 回、入力を準備するたびにもう 1 回調べ、満たさなければエラーにします（model_runner.py、prepare_tensor_input_v4.cpp。規則は environ.py の説明に書かれています）。コード上の事実Q&A はデコーダー層が再計算するのは「最後の 128 トークン」だけだと言っていますが、コードと README は実際には KEEP_TOKENS 個を残し、既定の使い方では 140 個です。このページはコードを基準にします。

ヒットした後、KV は 3FS からどうやって GPU メモリに戻るのでしょうか。Q&A ドキュメントは 3 ステップに分けています（Q&A ドキュメント）。上流レポートマッチング：Entrypoint がハッシュチェーンでプレフィックスを照合します。触るのはメタデータだけですが、ヒット長はルーティングの前に求める必要があるので、このステップは隠せません。KV の取得：別のプロセスが非同期に KV を 3FS からホストの共有メモリへ運びます。スワップイン：エンジンの中の 1 つのスレッドが、層ごとに GPU メモリへコピーし、順伝播の計算と重ねます。KV ブロックは小さくて散らばっているので、スワップインには GDR を使い、RDMA の NIC で PCIe の帯域を使い切らせて、GPU の演算ユニットは使いません。「運びながら計算する」考え方は第 14 章「同期と非同期」を見てください。

では、読み戻すと再計算よりどれだけ得になるのでしょうか。次の計算では、DeepSeek が報告した数字を既定値にします。ストレージサーバーは 1 台あたり少なくとも 40 GB/s で読めます上流レポート。プリフィルは 1 GPU あたり 1 秒に約 87,000 個の、ヒットしなかったトークンを処理します。これは README のベンチマーク図によります（SM100 を 4 枚、EP4DP4、コンテキスト 131,072）上流レポート。1 トークンあたりの KV の大きさは、このページでは確認していないので、既定では 8 KiB とします。これは仮定です。もう 1 つ仮定があります。ベンチマーク図の 87,000 は平均のスループットで、ここでは「長いプレフィックスの後の末尾」の計算にそのまま使っています。末尾は 11 万個余りのトークンに対してアテンションを計算するので、実際にはもっと遅いかもしれません。教育用の試算

計算してみると、読むほうが計算するよりずっと速いことが分かります。128K のリクエストで 90% ヒットすると、プリフィルは約 1.5 秒から約 0.18 秒に下がります。分かれ目は「読み出し帯域 ÷ プリフィルのスループット」です。40 GB/s ÷ 87,000 token/s ≈ 449 KiB で、1 トークンあたりの KV がこれより小さければ、読むほうが計算より速くなります。しかし 3.3 節の容量の概算どおりなら、約 18 枚のプリフィル用 GPU が 1 台のストレージサーバーから同時に読むので、1 枚あたり約 2.2 GB/s しか割り当てられず、分かれ目は約 25 KiB まで下がります。仮定の 8 KiB とは 3 倍しか違いません。教育用の試算したがって、ストレージの読み出し帯域は、オンラインの GPU 数に合わせて用意する必要があります。そうしないと、ヒットで節約した時間が、読み出し待ちの行列に食われてしまいます。

この 3 点を覚えよう

  1. プリフィルは演算性能を使い、デコードはメモリ帯域を使います。1 組の GPU に詰め込むと、プリフィル 1 ステップで全員のデコードが止まります。DeepSeek はビジョンエンコーダー、プリフィル、デコードを別々にデプロイします。プリフィルは 8 GPU のマシン（EP2–8）、デコードは 64–128 GPU のスーパーノード（EP64–128）で、最小の効率的な単位は 64 + 64 GPU です。
  2. ブロック KV は 128 トークンごとにページ化し、専用の 3FS クラスタ（10 + 2 の消失訂正符号、約 100 PiB、TTL 3–7 日）に保存します。SWA 状態は 1 シーケンスにつき固定長のスロット 1 つで、アーカイブするのは約 1.4 MB だけ、手元のメモリに残ります。
  3. ヒットは最大で L − 134 まで、128 の倍数に丸めます。SWA が欠けたら 1 ブロック戻り、有界リプレイで 128 トークンだけ再計算します。コストは定数です。オープンソース版には、エンジンの役割、キャッシュのレイアウト、有界リプレイがありますが、KV キャッシュシステムと分離デプロイをつなぐコードはありません。

よくある誤解：「プレフィックスがヒットしても時間が省けるだけで、計算結果は最初から計算した場合とまったく同じ。」

ブロック KV はそのまま読み戻すので、この部分は同じです。しかし SWA 状態が欠けたときは、有界リプレイが作るのは近似の SWA です。ウィンドウがリプレイ区間の中で打ち切られ、それより前のトークンは見えません（Q&A ドキュメント）。デコーダー層の有界リプレイを README の既定の使い方どおりに有効にすると、プリフィルのたびに打ち切るので、結果は最初から完全な計算と違います。examples/yoco が検証しているのは、mask と compact の 2 種類の打ち切りが互いに一致することで、打ち切りなしと一致することではありません。再現できる出力が欲しいときは、バッチ不変のページを見てください。

もう一歩深く：環境変数から関数まで、コードと 1 つずつ照らし合わせる

エンジンの役割と、混合エンジンの投票

3 つのエンジンの役割は engine_type.py で定義されています。NORMAL と COMPLETION は既定でゼロオーバーヘッドのスケジューリングを有効にし、PROMPT は有効にしません（非同期スケジューリングはDSpark とゼロオーバーヘッド・スケジューリングのページを見てください）。スケジューラは役割ごとに振り分けます。PROMPT は _schedule_prefill だけを呼び、COMPLETION は _schedule_decode だけを呼びます（scheduler.hpp）。NORMAL の投票で「プリフィルをしたい」の条件は、GPU メモリの KV 使用量が 90% 以下で、待っているリクエストがあることです（水位線、want）。ALL の点は MIN で集約するので、全員がしたいときだけ実行します。ANY の点は、どれかの rank がしたいときに実行します。その後に 2 回目の投票があり、本当にプリフィルを割り当てられた rank があることを確かめます。仕事のない rank は、一緒に空のプリフィルステップを実行して、ステップの形をそろえます。間隔は DEEPINFER_PREFILL_ATTEMPT_INTERVAL（既定 70）と DEEPINFER_PREFILL_ANY_ATTEMPT_INTERVAL（既定 100）で制御します（environ.py）。NORMAL 以外のエンジンは、初期化のときに init_pd_split を呼びます（llm_engine.py）。また、CUDA Graph を使うのは PROMPT 以外のエンジンだけです（model_runner.py）。デコードのステップは小さくて頻繁なので、グラフを記録しておけば起動のオーバーヘッドを節約できます。これがまさに第 15 章「カーネルの起動オーバーヘッドと演算子融合」で説明したことです。

ブロックテーブルと状態スロット

2 つのアロケーターはどちらも BlockManager です。空きブロックをリンクリストでつなぎ、ブロックには参照カウントがあり、0 番のブロックは使いません（block_manager.hpp）。ブロックのアロケーターは num_gpu_blocks でブロックを管理し、スロットのアロケーターは num_state_seqs でスロットを管理します（llm_engine.py）。要求したブロック数が総ブロック数以上のときは NEVER を返し、そのままエラーにします。一時的に足りないときは LATER を返し、リクエストはキューに残ります（block_manager.hpp）。try_allocate_seq は、ブロックとスロットの両方が足りるときだけ割り当てます（同じファイル）。スロット数は int(max_num_seqs × 1.2) + 1 で、割合は DEEPINFER_NUM_STATE_SLOTS_RATIO で制御します（cache_engine.py、environ.py）。起動時にはもう 1 つ検査があります。ブロックに入るトークン数に 0.8 を掛けた値が、モデルの最大長以上でなければなりません（llm_engine.py）。

SWA 状態のレイアウトとアーカイブ

どの層の SWA をアーカイブしないかは、モデルの設定だけで決まります。層番号が n_prefill_layer 以上のものが YoCo の消費層です（cache_engine.py）。n_prefill_layer は、圧縮比が 1 になる最初の層の番号です（config.py）。DEEPINFER_PREFILL_STORE_EXTRA_STATE を有効にすると、アーカイブ用のリングバッファに DEEPINFER_PREFILL_STORE_EXTRA_SIZE（既定 128）個のトークンを余分に保存し、打ち切りが有効なときはさらに KEEP_TOKENS を加えます。コメントの理由は「プリフィルではディスクへの書き込みが起きないことがあるので、余分に保存しておかないと複数ターンのヒットを保証できない」です（cache_engine.py）。アーカイブのデータを読み出すのは select_state_slice_to_store です。アーカイブするときは、位置が 128 の倍数であることを要求します。TO_CE=True のときは、デコードエンジンへ送る完全な状態を、アーカイブしない領域も含めて組み立てます（cache_engine.py）。逆方向の load_state_from_store_to_prefill_cache は、アーカイブのデータをプリフィルの状態スロットに書き戻します（同じファイル）。

SWA 状態をいつ保存するか

Q&A ドキュメントの規則です（Q&A ドキュメント）。上流レポートプリフィルが終わるとき、まずシーケンスの末尾にトークンを 1 つ残し、それから 128 の倍数に切り下げます。1 区間に満たなければ、今回は保存しません。分割プリフィルでは、最後の区間でだけ保存します。デコード中は、GPU メモリの中に別のコピー領域を用意し、128 の境界を越えるたびに、現在のウィンドウをそこへコピーします。リクエストが終わるときは、最後に完了したコピーからアーカイブし、接続点は 128 に切り下げます。コピーの位置は境界を最大 5 トークン越えることがあり、スロットがウィンドウより 6 位置多いので、ちょうど受け止められます。コード側では、コピーは do_copy_state が GPU 上の状態を copy_state バッファにコピーして行います。一方、「コピーするかどうか」を判断する should_copy_state は、オープンソース版では常に False を返します（llm_engine.py）。コード上の事実

有界リプレイのスイッチと検査

DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE は off、mask、compact のいずれかを取ります。DEEPINFER_YOCO_PREFILL_KEEP_TOKENS の既定値は 0 で、打ち切りを有効にするときは明示的に設定する必要があります（environ.py）。検査は 2 か所あります。Python 側はモデルの読み込み時（model_runner.py）、C++ 側は入力を準備するときです（prepare_tensor_input_v4.cpp）。ロールバック長 DEEPINFER_MAX_BACKTRACKING_TOKENS は、少なくとも「ドラフト数 + 1」まで引き上げられます。ドラフト数の既定は 5 なので、少なくとも 6 です（environ.py）。compact モードでは、各区間が [max(0, 全体の長さ − KEEP_TOKENS), 全体の長さ) とその区間の共通部分を残します。区間全体が残す領域より前にあるときも、最後の 1 トークンを場所取りとして残します（同じファイル）。打ち切りには 2 つのモードがあります。mask はすべてのクエリを残して見える範囲だけを狭め、compact は最初の消費層で打ち切り領域のクエリをそのまま捨てて、本当に計算を節約します（environ.py）。モデルの順伝播では、最初の消費層でメタデータを compact のビューに差し替えます（deepseek.py）。2 つのモードの見える範囲は同じ式です（yoco.py）。打ち切りが有効なとき、プロンプトのトークンごとの確率（prompt logprobs）は強制的にオフになります。compact モードでは、切り捨てられた行はそもそも計算されておらず、mask モードでは、矩形より前の行の確率には意味がないからです（llm_engine.py）。スケジューラのコストモデルも、消費層の行数を別に数えるので、打ち切りでどれだけ節約できたかを把握しています（flops_estimator.hpp）。examples/yoco には 2 段階の検証があります。L1 は GPU 1 枚で数秒、メタデータだけを比べます。L2 は GPU 8 枚と互換性のあるチェックポイントが必要で、logprob と top-K を 1 つずつ比べます。既定のパラメータは --keep-tokens 140 --window 128 です（examples/yoco/README.md）。

バランス型 CP の切り方

README はこれを「Attention DP / balanced CP」と書いています（README）。デコードエンジンで CP を有効にすると、そのままエラーになります（llm_engine.py）。1 本のシーケンスを 2 × cp 個の区間に切り、r 番目の GPU は r 番目の区間と、後ろから r + 1 番目の区間を受け持ちます。前と後ろを組にするのです（prepare_cp_mirror.py。打ち切りのときの穴埋め計算も同じ組み合わせで行います。prepare_tensor_input_v4.cppを見てください）。コード上の事実なぜこう組にするのでしょうか。因果アテンションでは、後ろのトークンほど見なければならないキーが多くなります。4 枚の GPU で順に切ると、仕事量はおよそ 1 : 3 : 5 : 7 になり、いちばん忙しい 1 枚は平均の 1.75 倍です。前と後ろを組にすると、4 枚とも同じ量になります。教育用の試算スケジューリングのとき、各シーケンスの長さは cp × 2 にそろえられます（scheduler.hpp）。各 rank の長さは、各シーケンスの ⌈長さ ÷ 2cp⌉ の合計に 2 を掛けたものです（prepare_tensor_input_base.cpp）。GPU 上のカーネルは、blk = rank + half × (2cp − 1 − 2 × rank) で half 番目の区間に対応するブロック番号を求めます。half = 0 のときは rank 番目のブロック、half = 1 のときは 2cp − 1 − rank 番目のブロックです（prepare_cp_mirror.py）。仕事量の推論：長さ N を 2cp 個の区間に切ると、i 番目の区間のトークンは平均で約 (i + 0.5) × N ÷ 2cp 個のキーを見るので、r 番目のブロックと 2cp − 1 − r 番目のブロックを足すと、r に関係なく常に 2cp 単位になります。教育用の試算

このページの数字の条件

README の 2 枚のベンチマーク図：プリフィルは SM100 を 4 枚、デコードは 64 枚で、それぞれ 1 つのスケールアップドメインの中にあります（README）。プリフィルの図のタイトルには、EP4DP4、384 + 32 個のエキスパート、コンテキスト 131,072、デコーダー有界リプレイ 140 トークンと書かれています。縦軸は 1 GPU あたり 1 秒に処理する、ヒットしなかったトークンの数です。図から私が読み取った点は、1 ステップあたり 4,096 トークンで約 68 ms、8,192 で約 114 ms、16,384 で約 200 ms、32,768 で約 376 ms、65,536 で約 731 ms です。上流レポート（図の読み取りには誤差があります。）デコードの図のタイトルには、EP64DP64、384 + 64 個のエキスパート、コンテキスト 131,072、nextn = 3 固定、ドラフトトークン 1 個あたりの受理率 75%、τ = 3.25 と書かれています。rank あたり 64 リクエストのとき、ユーザー 1 人あたり約 246 トークン/秒なので、デコード 1 ステップは約 3.25 ÷ 246 ≈ 13 ms です。教育用の試算τ の数え方は DSpark のページを見てください。3.3 節のストレージの数字はすべて Q&A ドキュメントによるもので、3FS クラスタの読み出し帯域の実測分布は DeepSeek からは公開されていません。
