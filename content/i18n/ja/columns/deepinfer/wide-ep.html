1 台のコンピューターから 1 つのスーパーノードへ

第 10 章でひとつ計算をしました。Strata が 1 台のコンピューターで token を 1 つ生成するとき、約 664 MB のエキスパートデータを読みます。VRAM にはすべてのエキスパートが入りません。そこで人気のあるものだけをキャッシュし、残りは CPU に任せます。これは「1 人、1 台」のやり方です。

DeepSeek のオンラインサービスは、同時に会話する何千何万という人を相手にします。デコードは 1 枚の GPU ではなく、64〜128 枚の GPU でできたスーパーノードで動かします。これらの GPU は高速な相互接続でつながっているので、ひとかたまりとして使えます。上流レポート（Q&A の 11 行目）このページは 3 つの問いに答えます。数百のエキスパートを数十枚の GPU にどう分けるのでしょうか。GPU が増えるほどデコードがお得になるのはなぜでしょうか。人気のエキスパートが 1 枚の GPU に集まったら、どうするのでしょうか。

ひとことで：DeepInfer のデコードでは、アテンションをデータ並列（DP）で動かし、各 GPU が自分のリクエストの束を受け持ちます。ルーテッドエキスパート（ルーターが選ぶエキスパート）はエキスパート並列（EP）で動かし、64–128 枚の GPU に分けます。1 枚の GPU が 1 層で持つのは数個だけです。GPU が増えるほど、1 枚の GPU がステップごとに読むエキスパートの重みは減り、1 回の読み出しが処理する token は増えます。代わりに、層ごとに 2 回の全対全通信（all-to-all）が必要です。また、いちばん忙しい GPU が全体の速さを決めます。そこでエキスパート負荷分散（EPLB）で、人気のエキスパートを複製して散らします。

2.1 2 つの分け方を重ねる：アテンションはリクエストで、エキスパートは番号で分ける

第 21 章では、複数の GPU で仕事を分ける 3 つの方法（レイヤー分割、テンソル並列、リクエスト並列）を説明しました。Strata はレイヤー分割を選びました。DeepInfer が使うのはそのうちデータ並列だけで、しかもアテンションにだけです。そこに、第 21 章で扱わなかったもう 1 つ、エキスパート並列を重ねます。図 D2-1 を見てください。

  • アテンションはデータ並列（DP）を使います。各 GPU が完全なアテンションを 1 つずつ持ち、それぞれ別のリクエストを処理します。上流の説明はこうです。DeepSeek-V3 / R1 と同じく、アテンションの DP の数はエキスパート並列の数に等しくします（#DP = #EP）。今のところ、テンソル並列（TP）もコンテキスト並列（CP）も使いません。上流レポート（Q&A の 33–53 行目）コードにはコンテキスト並列があり、README にも載っています。ただ、上流のデプロイ設定では使いません。
  • MoE はエキスパート並列（EP）を使います。各層のルーテッドエキスパートを番号で EP 個に切り、各 GPU はそのうち 1 つだけを持ちます。ルーターと共有エキスパートは、どの GPU も完全な 1 組を持ちます。コード上の事実（moe.py の 24–67 行目、77–110 行目）

エキスパートの数は、GPU の数で割り切れなければなりません。DeepInfer は 3 つの数を区別します。モデルが定義する論理エキスパート：ルーターはこの中から選びます。実際に重みを割り当てた物理エキスパート = 論理エキスパート + 冗長コピー。各 GPU の上にあるローカルエキスパート = 物理エキスパート ÷ EP。コードは、物理エキスパートの数が EP で割り切れることを要求し、そうでなければエラーにします。コード上の事実（moe.py の 91–95 行目）冗長コピーは 2.4 節の主役です。

MoE の層ごとに GPU 間で token を交換するので、1 つのグループの中で、ある GPU はプリフィル、ある GPU はデコード、という状態は許されません。プリフィルとデコードを同時に行うエンジンでは、スケジューラがチェックポイントごとにグループ全体で投票し、このステップの種類をそろえます。グループの中にプリフィルをする GPU があれば、仕事のない GPU も空のプリフィルステップを一緒に回します。コード上の事実（scheduler.hpp の 295–340 行目：「DP グループ内では同じ種類でなければならず、投票でそろえる」）

上流のデプロイでは、2 つの段階の幅がかなり違います。プリフィルは EP2–8 で、GPU メモリ（HBM）に収まる範囲で小さいほどよいとされます。デコードは EP64–128 で、GPU が足りる範囲で大きいほどよいとされます。上流はこれをワイドエキスパート並列（Wide-EP）と呼びます。上流レポート（Q&A の 45–53 行目）2 つの段階を別々にデプロイする理由は、3 ページ目「E/P/D 分離と 72 時間の KV キャッシュ」を見てください。次の節では、デコードを広く展開する理由を説明します。

CS を学んだ人へ：これは並列計算の「バルク同期」パターンです。各自が 1 区間を計算し、全員でデータを 1 回交換し、そろって次の区間に進みます。書きやすく、考えやすいのが利点です。代わりに、どの区間も一番遅い人を待ちます。

Strata と比べると：Strata は GPU が 2 枚あるとき、レイヤーで前半と後半に分けます（第 21 章）。GPU 間でデータを渡すのは境目の 1 回だけです。家庭用 PC の GPU 間は、たいてい PCIe しかないからです。DeepInfer のスーパーノードには高速な相互接続があります。だから、層ごとにすべての GPU が互いにデータを交換する設計にできます。相互接続のコストが、分け方を決めます。

2.2 GPU が増えるほどお得：1 枚の GPU がステップごとに読むエキスパートが減る

第 5 章のルーフラインモデルを思い出してください。デコードでは、ステップごとに使う重みをすべて読みます。重みを読む時間は、計算より長いことが多いです。1 回読んだ重みが処理する token が多いほど、お得です。

ここで 1 枚の GPU に立って、MoE の 1 層、デコード 1 ステップを見ましょう。バッチが十分に大きければ、この GPU が受け持つエキスパートはほぼすべて、少なくとも 1 つの token に選ばれます。だから、この GPU は自分のエキスパートをすべて読みます。この GPU のエキスパートの数が、読む重みの組の数です。教育用の試算

DeepSeek-V4.1-Flash は 1 層にルーテッドエキスパートをいくつ持つでしょうか。DeepInfer はこの数を、Hugging Face 上のモデルの config.json から読みます。リポジトリにこのファイルはなく、数も直接は書かれていません。コード上の事実（config.py の 164–174 行目）リポジトリの比較図には「384+64 experts」とあります。Q&A も、EP64 のとき切り上げ後は 1 枚の GPU に 7 個、と言っています。上流レポート（wide_ep_decode_pareto.png、Q&A の 103 行目）この 2 つは合います。384 ÷ 64 = 6 に冗長 1 個を足すと、ちょうど 7 です。このページは 384 で計算します。1 つのエキスパートが何バイトか、token が何個のエキスパートを選ぶかは、リポジトリから調べられません。そこでこのページは具体的な数を書かず、S と k で表します。

すると、簡単な式ができます。1 枚の GPU が 1 層で持つエキスパート数 = (384 + 冗長数) ÷ EP。1 枚の GPU がステップごとに読むエキスパートの重み ≈ この数 × S。教育用の試算「1 枚の GPU に少なくとも冗長 1 個」で切り上げると、EP8 は 49 個、EP64 は 7 個、EP128 は 4 個です。EP8 から EP64 まで、1 枚の GPU がステップごとに読むエキスパートの重みは約 1/7 に減ります。

下のシミュレーターは、3 つのことをまとめて見せます。1 枚の GPU が持つエキスパート数、1 回読んだエキスパートの重みが平均で何個の token を処理するか、1 枚の GPU がステップごとに送る隠れベクトルの数です。EP8、EP64、EP128 を押して、どの数が変わり、どの数がほとんど動かないかを見てください。1 枚の GPU の 1 ステップあたりの token 数 T は、既定で 384 です。サンプルの benchmark は既定で GPU あたり 64 リクエスト、各リクエストは 1 ステップあたり 1 + 5 個の token として数えます。上流レポート（examples/README の 45 行目）

節約できるのは、読むバイト数だけではありません。バッチが GPU あたり T 個の token に固定されているとき、グループ全体では 1 ステップに EP × T 個の token、EP × T × k 回のエキスパート選択があります。負荷が均等なら、各 GPU に T × k 回が来ます。それをこの GPU のエキスパートに分けると、重み 1 組が処理する token は T × k ÷ (GPU あたりのエキスパート数) 個です。教育用の試算 EP64 は EP8 の 7 倍です。これはまさに第 5 章の「みんなで囲む食卓」の話です。同じ 1 皿を食べる人が多いほど、お得になります。

上流の実測図は、この方向を裏づけています。上流レポート 条件：DeepSeek-V4.1-Flash、コンテキスト 131,072、ドラフト長は 3 に固定、ドラフト token ごとの受理率 75% で換算（図には τ = 3.25 とあります）。EP64DP64 は 384+64 個、EP8DP8 は 384+32 個のエキスパートを使います。この図には GPU の型番がありません。README が性能図に書いている条件は SM100 で、各 GPU グループは 1 つの scale-up ドメインに収まっています（README の 83 行目）。DP rank あたり 64 リクエストのとき、図から読むと、EP64 は GPU あたり毎秒約 1.57 万 token、ユーザーあたり毎秒約 246 token です。EP8 は約 1.27 万、約 198 です。つまり、スループットとユーザーあたりの速度が、どちらも良くなります。（Q&A の 55–59 行目）

この図を読むときの注意点が 1 つあります。リポジトリの benchmark スクリプトは、DEEPINFER_FORCE_LOAD_BALANCE=1 を無条件で設定します。各 token のルーティングスコアを乱数に置き換えるので、エキスパートの負荷は最初から均等です。コード上の事実（benchmark.py の 158–168 行目、input_metadata.py の 48–50 行目）つまりこれは「負荷が完全に均等」なときの上限です。上流は、オンラインの負荷分散でこのオフライン上限の約 80% に届く、と言っています。上流レポート（Q&A の 125–127 行目）

Strata と比べると：Strata が一度に相手にする会話はごくわずかで、token 1 つが約 480 個のエキスパートを読みます（第 10 章）。Strata もエキスパートごとにグループ化しますが、重み 1 組を共有できるのは、1 つの検証ウィンドウの数個の token の間だけです（第 16 章）。そのため、重点は人気のエキスパートを VRAM に置いて、遅い経路を減らすことにあります（第 12 章）。DeepInfer は逆です。1 枚の GPU が数個のエキスパートだけを受け持ち、数百から数千の token を 1 つのバッチにためて、重みを 1 回読むたびに使い切ります。

2.3 層ごとに全対全が 2 回：ディスパッチとコンバイン

エキスパートはいろいろな GPU に散らばっているので、token がエキスパートを探しに行かなければなりません。MoE の層ごとに、DeepInfer は 4 つのことをします。コード上の事実（mlp.py の 565–616 行目）

  1. ルーティング。この GPU のルーターが、この GPU の token ごとにエキスパートを選びます。ルーターは「論理エキスパート → 物理コピー」の対応表を受け取ります。選ばれるのは論理エキスパートで、どのコピーに送るかは、この表が決めます。（359–401 行目）複数のコピーからどう選ぶかはカーネルライブラリの中に書かれていて、本書では確認していません。
  2. ディスパッチ（dispatch）。各 token の隠れベクトルを、選ばれたエキスパートがいる GPU に送ります。この処理は DeepEP の EPBuffer.dispatch が行います。ついでに、この GPU のエキスパートごとに「このステップで受け取った token 数」を加算します。これが 2.4 節の EPLB の元データです。（461–490 行目）
  3. エキスパートの計算。この GPU は、受け取った token をエキスパートごとにグループ化して、グループ化行列積を行います（第 16 章で「エキスパートごとのグループ化」を説明しました）。ルーティングの重みは、この段階で掛けます。（406–459 行目）続いて、この GPU は共有エキスパートで、自分の token を計算します。
  4. コンバイン（combine）。エキスパートの結果を、token がもともといた GPU に送り返して足し合わせ、さらに共有エキスパートの結果を足します。（493–511 行目）

ディスパッチとコンバインは、どちらも全対全通信（all-to-all）です。どの GPU も、ほかのすべての GPU に別々のデータを送ります。

集団通信：all-to-all

直感：オフィスに 4 人います。各自が手紙の束を持っていて、宛先はほかの人たちです。all-to-all は「全員が同時に、全員の郵便受けに手紙を入れる」ことです。終わると、各自の手元には自分宛ての手紙だけが残ります。

定義：P 個のプロセスのグループがあり、各プロセスは P 個のデータを用意し、j 番目をプロセス j に送ります。これは集団通信の一種です。ほかによくある操作には、ブロードキャスト（1 人が全員に送る）、all-reduce（全員のデータを足し合わせ、全員が合計を受け取る）、all-gather（各自が 1 個ずつ持ち、最後に全員が全部を受け取る）があります。

例：GPU 4 枚、GPU あたり token 8 個、token ごとにエキスパート 2 個を選び、エキスパートは均等に分布するとします。各 GPU は 16 個のベクトルを送り出し、そのうち約 12 個（3/4）がほかの GPU に向かいます。GPU が 64 枚になると、ほかの GPU に向かう割合は 63/64 になり、総数は変わりません。だから幅を広げても、GPU あたりの通信量はほとんど増えません。増えるのは、参加する GPU の数と、「一番遅い GPU を待つ」リスクです。

DeepInfer との関係：MoE の層ごとに、ディスパッチ 1 回とコンバイン 1 回があり、どちらも all-to-all 1 回です。DeepInfer は負荷を集計するときに、all-reduce と all-gather も使います（2.4 節）。

さらに読む：Wikipedia: All-to-all (parallel pattern) · Wikipedia: Collective operation · NCCL ドキュメント：集団通信操作 · PyTorch ドキュメント：torch.distributed

EP グループ全体が 1 つの高速な相互接続ドメインに収まるとき（NVIDIA の GPU では 1 つの NVLink ドメイン）、DeepInfer は別の道を通ります。Mega MoE です。コード上の事実 この道は、Python 側では呼び出しが 1 回だけです。ルーティング結果、2 組のエキスパートの重み、対称 VRAM の領域を DeepGEMM の fp8_fp4_mega_moe に渡し（活性化が BF16 のときは bf16_mega_moe に替わります。mlp.py の 254–256 行目）、この層の出力を受け取ります。途中に、個別のディスパッチやコンバインの呼び出しはありません。共有エキスパートも一緒に渡します。（mlp.py の 184–188 行目、528–563 行目）上流は、1 つの scale-up ドメインの中なら、EP がどれだけ広くても、バッチがどれだけ大きくても、Mega MoE は融合しない方法より明らかに速い、と言っています。上流レポート（Q&A の 229–231 行目）このカーネルが内部で通信と計算をどう重ねるかは、DeepGEMM のコードが今回のリポジトリにないため、本書では確認していません。

2.4 人気のエキスパートが集まる：EPLB は人気のものを複製し、置き直す

グループ全体が 1 ステップずつそろって進むので、1 ステップの時間はいちばん忙しい GPU で決まります。人気のエキスパートがたまたま同じ GPU に何個も載ると、その GPU が計算する token はほかの数倍になり、ほかの GPU は待つしかありません。DeepInfer はこれを 1 つの数で測ります。moe_lb = いちばん忙しい GPU が受け取った token 数 ÷ GPU あたりの平均受け取り token 数。コード上の事実（eplb/__init__.py の 167–193 行目、stats_logger.py の 238–241 行目）1.0 が完全な均等です。

対策がエキスパート負荷分散（EPLB）です。物理スロットは、論理エキスパートより数個多くなっています。この余分なスロットが冗長エキスパートで、人気のエキスパートのコピーを置くために使います。上流の説明はこうです。各 GPU は、自分が受け持つエキスパートに加えて、冗長エキスパートを数個置きます。上流レポート（Q&A の 97 行目）人気のエキスパートに 3 つのコピーがあれば、その token は最大 3 枚の GPU に分けられます。置くとき、2 つのコピーが同じ GPU に載ることもあります。EPLB は次のように動きます。コード上の事実（eplb/__init__.py の 131–165 行目、222–278 行目）

  1. 集計。ステップごとに、ディスパッチの際、この GPU のエキスパートごとに受け取った token 数を加算し、スライディングウィンドウに保存します。
  2. 定期的な再配置。M ステップごとに、グループ全体でウィンドウ内のカウントを all-reduce で足し合わせ、再配置のポリシーに渡します。最初の再配置は M/4 ステップに早め、コールドスタート時の偏りを早く直します。
  3. 人気のものを複製。ポリシーは 1 ラウンドにコピーを 1 つ渡します。毎ラウンド、「コピーを 1 つ増やしたとき、最大の 1 コピーあたりの負荷がいちばん下がる」エキスパートに渡します。（policy.py の 105–123 行目）
  4. 置き直し。すべてのコピーを負荷の大きい順に並べ、1 つずつ、「置いたあと、各ステップで最も忙しい GPU の負荷を足した合計がいちばん小さくなる」GPU に置きます。GPU が満杯になるまで置きます。（policy.py の 12–70 行目）これは貪欲法です。毎回、目の前で最善の選択だけをします。全体の最適は保証しませんが、速いです。
  5. 重みの移動。新旧の対応表にしたがって、GPU 間でエキスパートの重みを移します。GPU で、しかも同じ NVLink ドメイン内なら、相手の GPU 上のミラーを直接読みます。そうでなければ、torch.distributed の 1 対 1 送受信を使います（NVIDIA では NCCL。Ascend ではミラーの経路を使いません）。（eplb/__init__.py の 195–202 行目）移し終えてから、対応表を入れ替えます。（shuffle.py の 1–6 行目）

手順 3 と 4 の前提に注意してください。エキスパートにコピーがいくつあっても、その負荷はコピーの数で均等に分けられます。コード上の事実（policy.py の 31–37 行目）下のシミュレーターは同じアルゴリズムを移植し、規模を 16 個のエキスパートと 4 枚の GPU に縮めています。

コードでは、EPLB は既定でオフです。再配置の間隔 DEEPINFER_EXPERT_REARRANGEMENT_STEP_INTERVAL は既定で 0 で、再配置しない意味です。冗長の下限 DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS は既定で 0 です。統計ウィンドウは既定で 100 ステップです。コード上の事実（environ.py の 113–121 行目）冗長の下限はグループ全体の合計で、GPU あたりの数ではありません。コードは、「384 + 冗長」が EP で割り切れるよう切り上げます。（eplb/__init__.py の 21–28 行目）上流が公開した設定と実測は次のとおりです。上流レポート（Q&A の 93–103 行目）

デコードGPU あたり 1 個、切り上げ1,000 ステップ10,000 ステップごと1.090

「GPU あたり 1 個」をコードの書き方に直すと、冗長の下限を EP に設定することです。教育用の試算 EP64 では 384 + 64 = 448 で、ちょうど割り切れ、1 枚あたり 7 個になり、上流の説明と一致します。

Strata と比べると：Strata のエキスパートキャッシュも「最近の人気者は誰か」を追跡し、4 ラウンドごとに減衰カウントで、人気のエキスパートを VRAM に入れ替えます（第 12 章）。解くのは「どこで計算するか」、つまり VRAM か CPU かです。EPLB が解くのは「誰がいちばん忙しいか」で、人気のエキスパートを何個かコピーして、数枚の GPU に分けます。どちらも過去から未来を予測します。どちらも重みのコピーを終えてから、対応表を切り替えます。

2.5 リクエストを GPU にどう振り分けるか：3 つのデータ並列の負荷分散器

EPLB が扱うのは MoE の部分だけです。アテンションの部分がどれだけ忙しいかは、各 GPU に割り当てられたリクエストの数と、そのコンテキストの長さで決まります。これを担当するのは、DP レベルの負荷分散器です。これらはオンラインシステムと強く結びついているため、今回はオープンソースになっていません。README は、プリフィルとデコードの DP 負荷分散を「含まれないもの」に挙げています。Q&A は、負荷分散のコンポーネントが社内インフラと強く結びついていてまだ完全には公開されていない、と言い、ビジョンエンコーダーの負荷分散器もその中に入っています。上流レポート（README の 38–42 行目、Q&A の 21 行目）以下の 3 つは、どれも Q&A の記述だけが出どころです。上流レポート（Q&A の 105–127 行目）

  • プリフィルの負荷分散器。リクエストを総コンテキスト長で 4 つの帯に分けます。16K 未満、16–64K、64–256K、256K 以上です。各帯に何台のエンジンを割り当てるかは、前のラウンドの各帯の計算需要に応じて動的に調整します。エンジンは、残りの計算枠に応じて、自分から仕事を取りに来ます。どのエンジンもどのプレフィックスにもヒットできるので（ブロック単位の KV キャッシュは独立した 3FS ストレージクラスターにあります。Q&A の 141 行目、3 ページ目を参照）、プレフィックスの親和性では割り当てません。DP グループに入ったら、各リクエストは、現在の枠の負荷がいちばん低い rank に渡されます。
  • デコードの負荷分散器。すべてのデコードインスタンスのすべての GPU をまとめて割り当て、2 つの量を同時にそろえます。リクエスト数（1 ステップのバッチサイズを決めます）と、KV キャッシュの総長（アテンションのコストを決めます）です。経験則は、短いリクエストは並行数が少なく KV 総長が大きい GPU に、長いリクエストは KV 総長が小さい GPU に送ることです。
  • ビジョンエンコーダーの負荷分散器。プリフィルのマシンが、ビジョンエンコーダー（VE）をデプロイしたマシンを 1 台ランダムに選び、そのマシンの中で、いま処理しているタイル数がいちばん少ない GPU に画像を渡します。タイル数は、サイズからそのまま計算します。(幅 ÷ タイルの一辺) × (高さ ÷ タイルの一辺) です。

2 層の負荷分散は、どちらも欠かせません。DP の負荷分散器は、各 GPU のアテンションをほぼ同じ忙しさにし、EPLB は、各 GPU の MoE をほぼ同じ忙しさにします。上流は、全体で、完全に均等なオフラインベンチマークの約 80% に届く、と言っています。上流レポート

幅の広さにはコストもあります。1 つのデコードインスタンスのすべての GPU は 1 つの通信ドメインです。1 枚の GPU が壊れると、インスタンス全体が使えなくなります。再起動のとき、プラットフォームは、その時点で健全な GPU の数から EP の幅を決め直します。上流レポート（Q&A の 209–211 行目）スケールイン・スケールアウトなどの耐障害性の手段は、1 ページ目を見てください。

2.6 エキスパートの重みに FP4：ステップごとに読むバイトがさらに半分に

1 枚の GPU がステップごとに読むエキスパートの重み = エキスパートの数 × 1 つのエキスパートのバイト数。2.2 節は前者を減らし、FP4 は後者を減らします。上流は、ルーテッドエキスパートの重みに MXFP4 を使うと言っています。32 個の重みごとに 1 つの ue8m0 スケールを共有します。メイン KV とインデックス KV にも FP4 を使っていますが、それは3 ページ目の話題です。上流レポート（Q&A の 213–221 行目）

コードはこの説明と一致します。モデルを読み込むとき、config.json の量子化設定に、エキスパートは FP4、スケールは ue8m0 と書かれていなければならず、そうでなければ読み込みを拒否します。コード上の事実（config.py の 253–264 行目）エキスパートの重みは e2m1 形式で 2 個ずつ 1 バイトに詰められ、スケールは別に保存されます。（weights.py の 281–288 行目）行列積では、活性化に FP8、エキスパートの重みに FP4 を使います。（mlp.py の 177–182 行目、109–128 行目）

重み 1 個あたりのビット数を計算します。32 個の重み × 4 ビットに、8 ビットのスケール 1 個を足して、合計 136 ビット、平均で 1 個あたり 4.25 ビットです。教育用の試算 FP8 の 8 ビットと比べると、ステップごとに読むエキスパートのバイト数はほぼ半分になります。

Strata と比べると：Strata の Q2_0 は重み 1 個あたり 2.25 ビットです（第 4 章「量子化」）。目的は、34 GB のエキスパートをできるだけ多く 12 GB の VRAM に入れることで、入りきらなかったものは CPU が計算します。DeepInfer のエキスパートはすべて GPU の上にあります。片方ではエキスパートを数十枚の GPU に分け、もう片方では 4 ビット形式を使い、両側から、1 枚の GPU がステップごとに読むバイト数を減らします。

この 3 点を覚えよう

  1. アテンションはデータ並列で、各 GPU が自分のリクエストを受け持ちます。ルーテッドエキスパートはエキスパート並列で、EP 枚の GPU に分かれます。MoE の層ごとに、ディスパッチとコンバインの 2 回の全対全があるので、グループ全体が 1 ステップずつそろって進みます。
  2. デコードでは、GPU が増えるほど、1 枚の GPU が 1 層で持つエキスパートは減ります（EP8 は 1 枚あたり 49 個、EP64 は 7 個）。ステップごとに読むエキスパートの重みが減り、重み 1 組が処理する token が増えます。GPU あたりの通信量はほとんど変わりません。
  3. いちばん忙しい GPU が、グループ全体の速さを決めます。EPLB は各エキスパートの負荷を集計し、定期的に人気のエキスパートにコピーを足して置き直し、GPU 間で重みを移します。上流がデコードで報告した moe_lb は 1.090 です。

よくある誤解：「EP は広いほどよい。GPU が増えるほど速くなるので、いくらでも増やせる。」

GPU を増やして節約できる読み出し帯域は、だんだん小さくなります。EP8 から EP64 では、1 枚あたりのエキスパートが 49 個から 7 個に減ります。さらに倍の EP128 にしても、7 個から 4 個に減るだけです。教育用の試算 EP グループが NVLink ドメインを超えても、通常の DeepEP の経路は使えます。ただし、Mega MoE と 1 台の中での重みのミラー移動は、ドメインの中でしか使いません。通信ドメインが大きいほど、一番遅い GPU を待つリスクが高くなり、1 枚が壊れたときに止まる GPU も増えます。上流のデコードの幅は EP64–128 で、これは 64–128 枚の GPU のスーパーノードに対応します。上流レポート

エキスパートの番号の付け方

FusedExperts のドキュメント文字列は、4 つの数を定義しています。logical = n_routed_experts で、ルーターはこの中から選びます。extra = n_redundant_experts で、model_loader._configure_moe_redundancy が書き込みます。physical = logical + extra で、ep_size で割り切れなければなりません。local = physical // ep_size です。（moe.py の 1–8 行目）切り上げは resolve_num_extra_experts が行います。padding = -(num_routed_experts + min_num_extra_experts) % ep_size です。（eplb/__init__.py の 21–28 行目、model_loader.py の 83–106 行目）初期配置は [0 … n−1、続いて 0, 1, 2 … のコピー] で、すべての層が同じものを使います。（31–39 行目）重みを読み込むとき、各 rank はこの初期配置にしたがって、自分のエキスパートだけを読み、冗長コピーは同じ HF の重みを再利用します。（weights.py の 248–272 行目）重みの形が同じ MoE 層を 1 つのグループにまとめ、グループごとに ExpertLoadBalancer を 1 つ持ちます。（deepseek.py の 323–365 行目）

1 ステップごとに何をするか

ExpertLoadBalancer.step は、サンプリング段階がステップごとに 1 回呼び出します。EP が 1 のときはすぐに戻ります。やることは 3 つです。このステップの expert_count をウィンドウに保存し、必要なら再配置する。負荷の統計を累計する。expert_count をゼロに戻す。（131–165 行目）NORMAL エンジン（プリフィルとデコードを同時に行う）は、既定でプリフィルのステップを飛ばします。そのステップのカウントはウィンドウに入らず、再配置のカウントも進めません。DEEPINFER_REARRANGE_AFTER_PREFILL_IN_NORMAL_ENGINE=1 を設定すると、プリフィルのステップのカウントもウィンドウに入り、次のプリフィル以外のステップですぐに再配置します。（83–84 行目、146–165 行目）負荷の統計は DEEPINFER_MOE_LB_STAT_INTERVAL（既定は 128）ステップごとに all-gather を 1 回行い、各 GPU の token 数の平均と最大を得ます。この 2 つの比が、ログの moe_lb です。（167–193 行目）

ポリシーの 2 段の貪欲法

rebalance_experts_global は、先に複製し、あとで置きます。複製の段階では、毎ラウンド、候補のエキスパート j ごとに「j にコピーを 1 つ足したあと、各ステップでの最大の 1 コピーあたり負荷」を計算し、ステップ方向に合計して、最小になる j を選びます。スコアには j × 1e-4 を足し、各エキスパートのスコアが重ならないようにします。（policy.py の 73–140 行目）置く段階の目標はコメントに書かれています。「各ステップで最も忙しい GPU の負荷」の合計をできるだけ小さくし、同点なら番号の小さい GPU を選びます。リポジトリの単体テストは、2 つの対応表が互いに逆写像であること、コピーの総数が物理スロット数に等しいこと、同じ入力なら 2 回の結果がまったく同じであることを確かめます。（test_eplb_policy.py の 27–62 行目）このページのシミュレーターは、これを 1 層、倍精度浮動小数点に簡略化しています。同点の扱いは、PyTorch の単精度版と少し違うかもしれません。

重みの移し方

最初の再配置では、メモリ不足を防ぐため、先に PyTorch の VRAM キャッシュを空にします。EP グループが NVLink ドメイン内にあり、しかも GPU のときは、1 層分の重みだけを載せる対称 VRAM のミラーを作り、層ごとに更新します。各 GPU は、対になる送信側のミラーから、足りないエキスパートを直接コピーします。そうでなければ、torch.distributed のバッチ化した 1 対 1 送受信（NVIDIA では NCCL）を使い、DEEPINFER_REARRANGE_P2P_GROUPS でバケットに分けます。同じエキスパートに送信側が複数あるときは、受信側が決まった規則で送信側に均等に割り振ります。送信側と受信側は同じ関数で対を決めるので、必ず対応が合います。（eplb/__init__.py の 195–220 行目、shuffle.py の 47–53 行目、94–147 行目）重みを移し終えてから、copy_ で新しい対応表に差し替えます。（261–278 行目）

benchmark の条件

benchmark のデコードのスループットは「全部受理」で数えます。各リクエストは 1 ステップに 1 + nextn 個の token として数え、ドラフトが実際にいくつ受理されたかは関係ありません。（examples/README の 55 行目）README のトップページにあるデコードの図と、幅の比較図は、別の基準を使っています。作図スクリプトが 2 つの軸の両方に τ = 1 + nextn × 受理率を掛けていて、サブタイトルには受理率 75%、τ = 3.25 で換算したと書かれています。（plot_pareto.py の 58–67 行目）そのため、benchmark が直接出力する全部受理のスループットは、図の数字より高くなります。さらに DEEPINFER_FORCE_LOAD_BALANCE=1 を付けると、これらの図は「負荷が完全に均等」なときの数字になります。こうした基準の細かい違いは、4 ページ目でも出てきます。
