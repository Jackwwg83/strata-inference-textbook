이런 적 있나요?

같은 큰 파일인데, 처음 열 때는 한참 걸리고 두 번째는 거의 순식간에 열려요. 더 이상한 일도 있어요. mmap으로 30 GB짜리 모델 파일을 "열면" 함수가 눈 깜짝할 사이에 끝나요. 그런데 이 시점에는 SSD에서 읽은 바이트가 하나도 없어요.

모델 파일은 거대한 바이트 덩어리예요. 엔진이 원하는 것은 모양과 타입이 딱 맞는 텐서들이고요. 이 장은 그 사이의 길을 다뤄요. 파일 안에 무엇이 들어 있는지, "열기"와 "메모리에 읽어 들이기"가 왜 다른 일인지, 그리고 엔진이 읽은 바이트가 정말 자기가 생각한 그 바이트임을 어떻게 증명하는지 살펴봐요.

한마디로: 모델 파일이 쓸 만한 텐서가 되려면 세 관문을 통과해야 해요. 목차를 읽어 내기, 모든 텐서가 파일 안에 온전히 들어 있음을 증명하기, 바이트를 실제로 메모리에 올리기. 어느 관문에서든 오류는 "조용히" 생길 수 있어요. 그래서 Strata는 관문마다 직접 검사해요. 틀린 바이트로 계산하느니 차라리 시작을 거부해요.

6.1 모델 파일 안에는 무엇이 있을까

모델 파일을 책 한 권이라고 생각해 보세요. 표지에는 제목과 판본이 적혀 있어요. 다음은 목차로, 각 장이 몇 쪽에서 시작하는지 알려 줘요. 본문은 맨 마지막에 나와요. Strata가 읽는 GGUF 형식은 llama.cpp 생태계에서 흔히 쓰는 모델 파일 형식인데, 구조가 바로 이래요. 그림 6-1을 보세요.

메타데이터는 "데이터에 대한 데이터"예요. 모델이 어떤 아키텍처인지, 층이 몇 개인지 같은 정보죠. 텐서 목차는 텐서마다 다섯 가지를 적어 둬요. 이름, 차원 수, 각 차원의 길이, 저장에 쓴 데이터 타입, 데이터 영역의 몇 번째 바이트에서 시작하는지예요.

Strata의 GGUF 리더는 파일을 열자마자 검사를 시작해요. 코드 사실 처음 4바이트는 "GGUF"여야 하고, 버전은 3이어야 해요. 메타데이터의 아키텍처는 qwen4exp여야 하고, 층 수 48, 폭 2560, 어텐션 헤드 24개, KV 헤드 2개도 모두 맞아야 해요. 하나라도 다르면 어느 키가, 기대값은 얼마고 실제값은 얼마인지 알려 주고 실행을 거부해요(gguf_reader.hpp 423–427행, 573–603행). 이 엔진은 모델 하나만을 위해 만들어졌어요. "대충 돌아간다"는 그냥 에러를 내는 것보다 더 위험해요.

모양과 타입을 알면 텐서 하나가 몇 바이트인지 계산할 수 있어요. Strata의 주력 형식인 Q2_0은 수 64개를 18바이트에 담아요. 수 하나당 2.25 bit예요. 코드 사실(gguf_reader.hpp 120–121행, 213–216행) 2560 × 640 전문가 행렬에는 수가 1,638,400개 있어요. 블록으로는 25,600개이고, 25,600 × 18 = 460,800바이트를 차지해요. 전문가 하나에는 이런 행렬이 세 개 있어서 합계 1,382,400바이트예요. 소스 코드에 고정해 둔 전문가 크기와 정확히 같아요. 교육용 추정[S06]

6.2 "열기"와 "읽어 들이기"는 달라요: mmap과 페이지 캐시

파일을 읽는 방법은 두 가지예요. 첫째는 "복사"예요. read를 부르면 운영체제가 지정한 바이트를 미리 준비한 메모리에 복사해 줘요. 둘째는 "대출증"이에요. mmap을 부르면 운영체제가 주소 범위를 하나 주면서 "이 주소들이 그 파일이야"라고 말해요. 바이트가 SSD에서 실제로 올라오는 때는, 쓰려고 할 때까지 미뤄져요.

파일, 메모리 매핑, 페이지 캐시

파일은 SSD에 있는, 이름 붙은 바이트 줄이에요. 프로그램은 SSD 위에서 곧바로 덧셈이나 곱셈을 할 수 없어요. 데이터가 먼저 메모리에 올라와야 해요. 운영체제가 메모리를 관리하는 단위를 페이지라고 하고, 흔한 크기는 4 KiB예요.

메모리 매핑(mmap)은 파일을 프로세스의 주소 공간에 "걸어" 두는 기능이에요. 주소 base + i가 파일의 i번째 바이트에 대응해요. 매핑을 만들 때 운영체제는 대응 관계만 적어 둘 뿐 데이터는 읽지 않아요. 프로그램이 어떤 페이지에 처음 접근하면, 하드웨어는 이 페이지가 아직 메모리에 없다는 것을 알아채고 페이지 폴트(page fault)를 일으켜요. 운영체제가 넘겨받아 SSD에서 이 페이지를 읽어 오고, 프로그램은 이어서 실행돼요. 프로그램은 이 멈춤을 전혀 눈치채지 못해요. 그 순간만 느려질 뿐이에요.

읽어 온 페이지는 바로 버려지지 않고 페이지 캐시에 남아요. 같은 파일에 다시 접근하면 메모리에서 바로 가져와요. "두 번째가 훨씬 빠른" 이유가 이거예요. 메모리가 부족하면 운영체제는 한동안 안 쓴 깨끗한(clean) 페이지를 회수하고, 나중에 필요하면 SSD에서 다시 읽어요. 칼럼 뒤의 그림 6-2가 이 세 계층의 관계를 보여 줘요.

이 장과의 관계: Strata가 GGUF 파일 헤더를 읽을 때는 mmap을 쓰고, 저메모리 모드에서 전문가를 읽을 때도 보통 mmap을 써요(예외는 6.3절을 보세요). 그래서 "매핑 성공"은 주소가 준비됐다는 뜻일 뿐이에요. 데이터가 이미 메모리에 있다는 뜻도 아니고, 나중에 접근할 때 SSD 때문에 멈추지 않는다는 뜻은 더더욱 아니에요.

CS를 배운 분께: 《운영체제》에서 배운 요구 페이징(demand paging)이 바로 이거예요. mmap은 "파일 I/O"를 "메모리 접근"으로 바꿔 주고, 페이지 폴트 처리 루틴이 대신 read를 해 줘요. 가상 메모리와 페이지 테이블의 자세한 내용은 14장에서 다뤄요.

페이지 캐시는 좋은 도우미지만, 무엇을 남기고 무엇을 버릴지는 자기 규칙으로 정해요. 규칙이 내 접근 방식과 맞지 않으면 어떻게 될까요? Strata의 소스에는 실제로 겪은 교훈이 적혀 있어요. 코드 사실 초기 버전은 Windows에서 전문가 파일을 열 때 운영체제에 "랜덤 접근" 힌트를 줬어요. 이 힌트는 미리 읽기(read-ahead)를 끄고, 읽은 페이지를 되도록 빨리 버리게 해요. 이유는 "큰 파일을 랜덤하게 접근하면 읽은 것을 다시 읽지 않는다"는 것이었죠. 그런데 전문가 파일은 정반대예요. 토큰마다 고르는 전문가는 랜덤해 보이지만, 읽은 바이트는 다음 토큰에서 거의 다시 읽어요. 결과는 속도가 1.93 GB/s로 떨어지고, 토큰 하나에 344 ms가 걸렸어요. 25개 토큰을 돌려도 따뜻해지지(warm-up) 않았는데, 페이지가 읽혀 오는 만큼 빨리 버려졌기 때문이에요. 주석의 결론은 이래요. 올바른 힌트는 힌트를 주지 않는 것이고, 핵심은 페이지를 붙들어 둘 수 있느냐예요(expert_source.cpp 508–518행).

아래 시뮬레이터는 이 일을 파일 16구간으로 줄여 보여 줘요. 토큰마다 같은 앞쪽 W구간을 순서대로 읽고, 페이지 캐시는 "가장 오래 안 쓴 것부터 내보내기"(LRU)로 자리를 만들어요.

이 "전부 아니면 전무" 현상은 12장에서 캐시 교체를 다룰 때 다시 만나요. 저장 계층마다 대역폭이 얼마나 차이 나는지는 1장의 「저장 계층 구조」 칼럼을 보세요.

6.3 Strata는 바이트를 어디에 둘까: 복사, 매핑, 직접 읽기

같은 엔진이 데이터 종류에 따라 완전히 다른 세 가지 방식으로 바이트를 둬요. 그림 6-4를 보세요. 무엇을 고를지는 두 질문으로 정해져요. 이 데이터를 토큰마다 반복해서 읽나요? 메모리에 다 들어가나요?

기본 모드: 복사하고 고정해요. 메모리가 충분하면 전문가 전부(23–50 GB, 양자화 버전에 따라 달라요)를 메모리에 복사하고 페이지 고정(pinning)을 해요. 업스트림 보고[S03] 페이지 고정은 운영체제에 "이 페이지들은 SSD로 내보내면 안 돼"라고 알리는 거예요. 고정해 두면 GPU(그래픽 카드)가 DMA로 이 메모리에서 데이터를 바로 가져갈 수 있어요. CPU가 중간에서 한 번 옮겨 줄 필요가 없어요. [S06] 플랫폼 계층의 고정 함수는 Linux에서 mlock, Windows에서 VirtualLock을 호출해요. 일부만 고정했을 때는 성공한 척하지 않고 사실대로 보고해요. 코드 사실(platform/memory.hpp 1–24행)

저메모리 모드: 매핑해서 페이지 캐시에 맡겨요. 메모리에 전문가 전부가 안 들어갈 때(엔진 0.1.26부터)는, 설치 프로그램이 모델 디렉터리의 experts.bin을 매핑해요. GPU에 캐시되지 않은 전문가는 운영체제의 파일 캐시가 맡고, 메모리가 부족하면 돌려줄 수 있어요. 남은 메모리로 이 바이트들을 붙들어 둘 수조차 없으면, 엔진은 매핑을 쓰지 않고 페이지 캐시를 우회해 SSD에서 전문가를 곧바로 읽어요. Windows는 예전부터 이렇게 했어요. v0.1.40부터는 Linux도 같은 규칙으로 판단하고, O_DIRECT를 써요. 코드 사실(expert_source.cpp 377–381행) 업스트림 보고에 따르면 Coder 버전 엔진의 커밋된 메모리가 36 GB에서 약 13 GB로 줄었고 답은 그대로였어요. 다만 GPU가 작으면 대부분의 전문가를 SSD에서 읽어야 해서 훨씬 느려져요. 업스트림 보고[S03]

n-gram 표: 메모리에 올리지 않고 SSD에서 바로 읽어요. 이 표는 320,001,536행이고, 기본 표는 IQ4_NL 형식으로 행당 90바이트라서 합계 약 28.8 GB(26.8 GiB)예요. 코드 사실 v0.1.40부터 리더는 Q4_0, Q5_1, Q8_0, BF16 같은 형식의 표도 받아들이고, 행당 90~320바이트예요(ngram.hpp 44–58행). 리더 설계는 이 표가 메모리를 절대 차지하지 않도록 요구해요. 페이지 캐시도 차지하지 않아요. 행마다 버퍼를 거치지 않는 4 KiB 읽기로 SSD에서 바로 가져오고, 토큰 하나에 16행을 읽어요. 이 16행은 서로 다른 16개 페이지에 흩어져 있어요(ple_reader.hpp 1–5행). 밑바닥의 직접 읽기 모듈에는 이유가 적혀 있어요. 메모리 매핑으로는 "페이지 캐시에 넣지 않겠다"는 약속을 지킬 수 없고, 버퍼를 거치지 않는 읽기는 지킬 수 있어요. 대신 오프셋, 길이, 버퍼 주소가 모두 4096의 배수여야 해요(direct_file.hpp 3–9행). 이 표가 무엇에 쓰이는지는 11장에서 자세히 다뤄요.

6.4 텐서마다 보안 검색대를 통과해요

목차는 "텐서 X는 오프셋 o에서 시작하고 길이는 n바이트"라고 말해요. 엔진이 이 말을 믿어도 될까요? 파일이 다운로드 도중 끊겼을 수도 있고, 다른 도구가 잘못 써 놨을 수도 있고, 애초에 다른 모델의 파일일 수도 있어요. 엔진은 텐서를 읽기 전에 [o, o+n) 구간이 파일 안에 온전히 들어 있음을 먼저 증명해야 해요.

가장 손쉬운 방법은 o + n ≤ F를 검사하는 거예요(F는 데이터 영역의 길이예요). 그런데 컴퓨터의 정수는 자릿수가 정해져 있어요. 부호 없는 정수는 계산 결과가 상한을 넘으면 아주 작은 수로 슬쩍 "되돌아가요". 이것을 오버플로라고 해요. 목차의 o가 아주 큰 수로 잘못 써져 있으면 o + n이 작은 수로 되돌아가서 검사가 속아 넘어가요.

Strata는 오버플로가 없는 방식을 써요. 먼저 o ≤ F를 확인하고, 그다음 n ≤ F − o를 확인해요. 첫 단계가 뺄셈의 결과가 음수가 되지 않게 보장하고, 둘째 단계에는 덧셈이 없어요. 코드 사실(gguf_reader.hpp 530–536행) 아래 시뮬레이터는 정수를 8비트로 줄여서 오버플로가 눈에 보이게 해 줘요.

CS를 배운 분께: C/C++에서 부호 없는 정수의 오버플로는 "잘 정의된" 동작이에요. 264로 나눈 나머지를 취하고, 에러도 크래시도 없어요. 조용하기 때문에 오히려 위험해요. 부호 있는 정수의 오버플로는 미정의 동작이라서, 컴파일러가 검사 코드를 아예 최적화로 지워 버릴 수도 있어요.

바이트 수를 계산할 때의 곱셈도 오버플로할 수 있어요. 텐서의 원소 개수는 각 차원의 길이를 곱한 값이라서, 차원이 네 개면 64비트를 넘기기 쉬워요. Strata는 차원 d를 곱하기 전에 매번 "지금까지의 곱 ≤ 상한 ÷ d"를 검사해요. 만족하지 않으면 0을 돌려주는데, "이 모양으로는 올바른 크기를 계산할 수 없다"는 뜻이에요. 코드 사실(gguf_reader.hpp 475–488행)

이것은 검사의 일부일 뿐이에요. 같은 리더는 다음 파일도 거부해요. 두 텐서의 이름이 같은 파일(그러면 찾을 때 앞쪽이 이기고, 엉뚱한 텐서를 조용히 쓰게 돼요), 차원 수가 0이거나 4를 넘는 파일, 메타데이터 배열 길이가 224를 넘는 파일, 데이터 영역의 시작점이 파일 끝 뒤에 있는 파일이에요. 코드 사실(gguf_reader.hpp 326행, 437–446행, 458행) 전문가 파일을 매핑하기 전에도 엔진은 파일 크기가 전문가 레이아웃이 요구하는 바이트 수와 정확히 같은지 확인하고, 1바이트만 달라도 거부해요(expert_source.cpp 563–573행).

바이트 범위가 맞아도 모양까지 맞아야 해요. layout.hpp는 로드할 때 층마다 모든 텐서의 모양을 확인해요. 그 이름의 텐서가 커널이 생각하는 바로 그 모양인지를 봐요. 헤더 파일에 목표가 적혀 있어요. 로드할 때 텐서 이름, 실제 모양, 요구되는 모양을 알려 주자는 거예요. 4000번째 토큰에서 행렬 곱셈 안의 엉뚱한 숫자로 나타나게 하지 말자는 거죠. 코드 사실[S04]

6.5 바이트가 맞을까: 체크섬과 해시

범위 검사는 "바이트가 파일 안에 있는가"에 답해요. 하지만 답하지 못하는 질문이 있어요. 이 바이트가 원래 그 바이트인가요? 다운로드하다가 바이트 하나가 깨져도 파일 크기는 그대로라서 범위 검사는 그냥 통과해요. 이 질문에 답하려면 데이터의 "지문"을 계산해야 해요.

체크섬과 해시

직관: 책이 가득 든 큰 상자를 부칠 때, 가는 길에 빠지거나 바뀌지 않았는지 어떻게 알 수 있을까요? 먼저 총 쪽수를 세어 상자에 적어 두고, 받은 뒤에 다시 세면 돼요. 이 "총 쪽수"가 가장 소박한 체크섬(checksum)이에요. 아주 짧은 수 하나로 큰 데이터 덩어리를 요약해서, 양쪽을 비교하면 바뀌었는지 알 수 있어요.

가장 간단한 체크섬은 모든 바이트를 더하는 거예요. "어떤 바이트가 바뀌었다"는 알아내지만, "두 바이트가 자리를 바꿨다"는 알아내지 못해요. 덧셈은 순서를 신경 쓰지 않기 때문이에요. 더 좋은 검사 알고리즘인 CRC(순환 중복 검사)는 순서에 민감해서, 전송과 저장 중에 생기는 랜덤 오류를 찾는 데 흔히 써요.

암호학적 해시는 한 걸음 더 나아가요. SHA-256이 예예요. 길이가 얼마든 데이터를 256비트 요약값으로 바꾸고, 두 가지 성질이 있어요. 입력의 1비트만 바꿔도 요약값의 비트 절반 정도가 바뀌어요(눈사태 효과). 그리고 요약값이 같은 서로 다른 두 파일을 일부러 만들어 내는 것은 지금의 계산 능력으로는 불가능해요. 그래서 우연한 손상뿐 아니라 누군가 고의로 바꿔치기한 것도 알아낼 수 있어요. 칼럼 뒤의 그림 6-6이 작은 예예요.

이 장과의 관계: 수십 GB짜리 모델 파일은 파일 이름과 크기만으로는 "크기가 비슷한 파일이 있다"는 것밖에 증명하지 못해요. 해시를 한 번 계산해야 "바로 그 파일이다"를 증명할 수 있어요.

더 읽을거리: 위키백과: 체크섬 · 위키백과: 해시 함수 · 위키백과: SHA-2 · 위키백과: 순환 중복 검사 · MDN: 브라우저에서 SHA-256 계산하기 · OSTEP 45장: 데이터 무결성

Strata의 설치 스크립트는 Unsloth의 두 가지 모델 파일에 대해 해시를 완전히 대조해요. 실험용인 UD-Q4_K_XL(조각 4개)과, v0.1.39부터 일반 선택지가 된 UD-IQ4_XS(조각 3개)예요. 코드 사실 조각(shard)마다 바이트 수와 SHA-256이 스크립트에 고정되어 있어요. 다운로드가 끝나면 먼저 바이트 수를 비교하고, 다르면 바로 에러를 내요. 그다음 16 MiB씩 파일 전체를 읽으며 SHA-256을 계산해요. 일치하지 않으면 파일을 지우고 다시 받으라고 안내해요. 111 GB인 UD-Q4_K_XL을 한 번 계산하는 데 약 5분이 걸려서, 결과를 "완료 표시" 파일에 기록해 두고 다음 시작에는 다시 계산하지 않아요(setup.py 155–175행, 220행, 1316–1338행). 다른 모델 파일은 해시를 하지 않고, 설치 스크립트가 텐서 목차를 한 번 읽어서 대조해요(155–156행의 주석).

해시는 "파일이 맞는지"를 책임져요. 바이트가 메모리에서 VRAM으로 옮겨진 뒤에는 한 번 더 확인해야 해요. 전문가 캐시에는 verify_slot 함수가 있어요. VRAM의 슬롯 하나에서 바이트를 다시 읽어 와서, 메모리의 원본과 바이트 단위로 비교해요. 주석에 따르면 이것이 "캐시 안의 것이 정말 그 전문가임을 증명하는 유일한 수단"이에요. 슬롯 번호는 맞는데 바이트가 틀리면, 그럴듯해 보이는 틀린 토큰이 나오기 때문이에요. [S05] 실제로 문제를 잡아낸 적도 있어요. 첫 버전은 시작 시 채우기에 비동기 복사를 썼는데, 이 복사가 되읽기 검사와 같은 실행 순서에 있지 않았어요. 검사는 실행 전체를 거부하며 "slot 0 differs from the arena at byte 0"이라고 보고했어요. 주석의 평가는 이래요. 이게 바로 검사가 제 할 일을 한 것이다. 코드 사실[S05]

6.6 직접 해 보기: 모델을 내려받지 않고도 로더를 연습해요

이 장에는 별도의 실험 페이지가 없어요. 위의 두 인터랙티브 그림이 실험이에요. 이 순서로 놀아 보세요.

  1. 「페이지 캐시 시뮬레이터」에서 먼저 C ≥ W로 토큰 10개를 돌려 보세요. 그다음 C를 W − 1로 바꿔 보세요. 두 번의 히트율을 적어 두고, 슬롯이 하나만 모자라도 히트율이 100%에 가깝던 것이 0%로 떨어지는 이유를 한 문장으로 설명해 보세요.
  2. 「범위 검사」에서 n을 100으로 고정하고 o = 150부터 위로 끌어 보세요. 방식 A가 처음 속는 o 값을 찾고, o + n − 256으로 답을 검증해 보세요.

심화 연습: 128바이트짜리 가짜 GGUF 파일을 직접 설계해 보세요. 목차에는 텐서 세 개를 적어요. 차례로 시험해 보세요. 올바른 구간, 딱 끝까지 닿는 구간, 1바이트 넘치는 구간, 아주 큰 오프셋, 차원 곱셈 오버플로, 이름이 같은 텐서 두 개. 합격 기준은 "나쁜 파일에서 크래시가 난다"가 아니라 어떤 계산이 시작되기도 전에, 사람이 알아볼 수 있는 한 문장으로 거부 이유를 알려 주는 것이에요.

이 세 가지를 기억하기

  1. mmap은 "주소 ↔ 파일" 대응 관계만 만들어요. 바이트는 처음 접근할 때 페이지 폴트로 SSD에서 읽혀 오고, 이후 페이지 캐시에 남아요. 매핑 성공이 데이터가 이미 메모리에 있다는 뜻은 아니에요.
  2. Strata는 접근 방식에 따라 배치를 골라요. 반복해서 읽고 다 들어가는 전문가는 메모리에 복사해 페이지를 고정해요. 다 안 들어가면 페이지 캐시에 맡겨요. 28.8 GB짜리 n-gram 표는 페이지 캐시를 우회해 SSD에서 직접 읽어요.
  3. 텐서마다 보안 검색대를 통과해야 해요. 범위 검사는 o ≤ F 그리고 n ≤ F − o로 써야 오버플로가 없어요. 모양은 로드할 때 확인해요. 파일 전체는 SHA-256 같은 해시로 "바로 그 파일"임을 증명해요.

흔한 오해: "mmap이 성공했으니 모델은 이미 메모리에 있다."

mmap이 돌아왔을 때 운영체제는 대응 관계만 적어 두었고, 한 페이지도 읽지 않았을 수 있어요. 진짜 읽기는 처음 접근할 때 일어나요. 게다가 읽어 온 페이지도 메모리가 부족하면 회수될 수 있어서, 다음에 접근할 때 다시 SSD에서 읽어요. Strata의 소스에도 기록이 있어요. 페이지가 읽혀 오는 만큼 빨리 버려지면 속도가 SSD 수준으로 떨어져요.

한 걸음 더: 일치한다고 맞는 건 아니다, 소유권과 수명, 문서와 코드가 다르면 누구를 믿을까

두 도구가 일치해도 함께 틀릴 수 있어요

layer.cpp에는 아주 값진 장애 기록이 두 개 남아 있어요. [S14] 첫째: 어떤 함수가 양자화 텐서의 세 덩어리(코드, 스케일 계수, 오프셋)의 크기를 스스로 다시 유도했는데, 스케일 계수가 4바이트라고 가정했어요. 그런데 양자화 텐서 303개 중 90개는 스케일 계수가 2바이트 fp16이었어요. Q2_0 전문가 텐서 58개 전부가 여기에 들어가요. 그래서 계산된 스케일 계수 덩어리가 두 배로 커졌고, 세 덩어리를 합쳐도 텐서 전체 크기와 맞지 않았어요. 첫 반응은 목록에 적힌 그룹 크기가 틀렸나 하는 의심이었어요. 303개 텐서를 모두 감사해 보니 그룹 크기는 문제가 없었고, 빠뜨리고 확인하지 않은 입력은 스케일 계수의 폭이었어요.

둘째: 패킹 도구 두 개가 모두 mins라는 이름의 데이터 블록을 찾았지만, 진짜 키 이름은 offsets였어요. 두 도구가 "똑같이" Q4_K/Q5_K 텐서 54개의 오프셋 블록을 놓쳤어요. 메모리 예산이 136 MiB 적게 계산됐고, 그 바이트들은 복사되지도 않았어요. 주석의 결론은 이래요. 두 도구의 일치는, 둘이 같은 잘못된 가정을 공유하지 않을 때만 증거가 된다. 지금의 plane_ptrs는 스스로 유도하지 않아요. 로더가 기록한 세 덩어리 크기의 합이 텐서 전체 바이트 수와 같은지, "오프셋 블록이 있는가" 플래그가 오프셋 블록 크기와 맞는지만 확인하고, 맞지 않으면 거부해요. 코드 사실[S14]

테스트 설계에 주는 시사점: 오라클(oracle, 맞고 틀림을 판정하는 참조 구현) 두 개는 정말로 독립이어야 해요. 하나는 형식 규격에 따라 순서대로 해석하고, 다른 하나는 손으로 만들어 바이트 단위로 확인한 고정 샘플을 쓰세요. 둘이 같은 레이아웃 유도 함수를 공유하게 해 놓고 "결과가 같다"를 강한 증거로 삼지 마세요.

헤더 커서 속의 덧셈 하나

파일 헤더를 읽는 Cursor::need는 pos_ + n > size_라고 써 있어요(gguf_reader.hpp 240–242행). 6.4절에서 말한 바로 그 덧셈 방식이에요. 헤더의 고정 길이 필드는 아주 작아서 문제가 없어요. 하지만 문자열 길이 n은 파일에서 읽어 온 값이에요. 연습: n이 264에 가까운 값으로 조작되면 이 비교가 되돌아감에 속을까요? 힌트: 속더라도 다음 줄에서 n으로 std::string을 만들 때 길이가 상한을 넘으면 예외가 던져져서 파일은 여전히 거부돼요. 다만 에러 메시지가 정확한 "unexpected end of file"이 아니게 돼요. 안전은 흔히 여러 겹의 방어선에 기대지만, 겹마다 제대로 써 둘 가치가 있다는 뜻이에요.

RAII가 관리하는 것과 못 하는 것

C++의 RAII(자원 획득은 초기화)는 객체가 소멸할 때 자원을 자동으로 풀어 줘요. GGUF 리더는 생성 도중 실패하면 먼저 매핑을 해제하고 파일을 닫은 뒤에 예외를 던져요(gguf_reader.hpp 342–345행, 410–419행). 하지만 추론 엔진의 자원은 메모리와 파일 핸들만이 아니에요. VRAM, 고정 메모리, CUDA stream, event도 있어요. 스마트 포인터는 자기가 들은 소유권만 알아요. 비동기 복사가 끝나기를 대신 기다려 주지는 않아요.

그래서 인터페이스 계약은 "주소를 넘겨준다"가 아니라 "복사 완료 이벤트가 확인될 때까지 호출자가 이 버퍼를 쥐고 있는다"로 써야 해요. expert_source.hpp는 포인터의 수명을 아주 분명히 적어 뒀어요. 일반 소스가 돌려주는 포인터는 다음번 blob() 호출까지만 살아 있음이 보장돼요. 캐시가 있는 소스는 캐시 자체를 가리키는 포인터를 돌려줘야 하고, 재사용될 임시 영역을 가리키면 안 돼요. 그러지 않으면 CPU가 이 전문가를 계산할 때 읽는 것이 이미 다음 전문가의 바이트일 수 있어요. GGUF 조각에서 그때그때 이어 붙여 만든 "임시" 전문가 블록은 현재 층과 그 뒤 한두 층 안에서만 유효해요. 더 오래 두려면 copy_blob으로 복사본을 만들어야 해요. [S06] 세션 메모리를 풀기 전에 session_release는 다른 모듈이 등록해 둔 외부 포인터(예: 회전 위치 임베딩의 각도 표)를 먼저 취소해요. 새 세션이 이미 해제된 주소를 들고 계산하지 않게 하려는 거예요. [S13]

문서와 코드의 말이 다르면 누구를 믿을까

Strata의 설명 문서는 n-gram 표를 "운영체제 캐시를 통해 몇 행씩 읽는다"고 써요(docs/HOW_IT_WORKS.md 31행). 반면 리더의 헤더 파일은 "메모리에 절대 올리지 않고, 행마다 버퍼를 거치지 않는 4 KiB 읽기를 쓴다"고 써요(ple_reader.hpp 3–4행). 이 책은 고정된 커밋의 소스를 기준으로 서술하고, 이런 불일치는 있는 그대로 짚어요. 오픈소스 프로젝트를 읽을 때 문서는 저자의 의도이고 코드는 실제 동작이에요. 둘이 다르면 실행하고 테스트할 수 있는 쪽을 따르되, 불일치는 따로 적어 두고 어느 쪽도 감싸 주지 마세요.

왜 "비동기 반환"을 "복사 완료"로 보면 안 될까

비동기 복사 함수가 돌아왔다는 것은 작업이 큐에 들어갔다는 뜻일 뿐이에요. DMA 엔진은 아직 원본 버퍼를 읽지 않았을 수 있어요. 이때 원본 버퍼를 재사용하거나 해제하면, 복사되는 것은 절반은 옛 바이트, 절반은 새 바이트일 수 있어요. 올바른 재사용 허가는 같은 stream 위의 완료 이벤트이거나, 계약에 분명히 적힌 동기화 지점이에요. expert_cache.hpp의 그 "slot 0 differs" 실패는 본질적으로 두 실행 순서가 맞춰지지 않아서 생긴 일이에요. [S05]
