겪어 본 적 있을 거예요

Strata를 처음 켜면 컴퓨터가 1~2분 동안 버벅거리고, 마우스도 잘 안 따라와요. README가 미리 알려 줘요. 모델을 시작할 때 35~55 GB를 메모리로 읽고, 그중 일부를 그래픽 카드가 쓰도록 「잠가」 둬요. 그동안 컴퓨터가 느려지거나 응답이 없어지는 건 정상이니 기다리면 된다고요. 업스트림 보고[S01]

메모리는 왜 「잠가」야 할까요? 잠그면 그래픽 카드가 무엇을 할 수 있고, 안 잠그면 어떤 일이 생길까요? 이 장은 운영체제의 가장 기본적인 속임수에서 시작해요. 프로그램이 보는 메모리 주소는 사실 「가짜」예요.

한마디로: 운영체제는 메모리 페이지를 언제든 옮길 수 있어요. 그런데 그래픽 카드의 DMA 엔진은 작업을 시작할 때 받은 물리 주소만 알아요. 그래서 옮길 메모리는 먼저 페이지를 고정해야 해요. 옮기기는 비동기라서 함수가 돌아왔다고 데이터가 도착한 게 아니에요. 완료 신호를 기다려야 해요. 버퍼 두 개를 번갈아 써서 「한쪽은 옮기고 한쪽은 계산」하면 옮기는 시간을 숨길 수 있어요. 단, 덮어쓰기 전에는 매번 「다 썼음」 신호를 기다려야 해요.

14.1 지금 보는 메모리 주소는 「가짜」예요

프로그램 안의 포인터, 예를 들어 0x7f3a_0000_1000은 메모리 모듈 위의 실제 위치가 아니에요. 이것은 가상 주소예요. 운영체제와 CPU가 함께 가상 주소를 물리 주소로 번역해야 비로소 메모리 모듈을 실제로 읽어요. 이 번역 단계 덕분에 프로그램마다 자기가 큰 연속 메모리를 혼자 쓰는 줄 알아요. 운영체제도 뒤에서 마음대로 조정할 수 있게 돼요.

가상 메모리와 페이징

운영체제는 메모리를 크기가 고정된 조각으로 나눠요. 이것을 페이지라고 하고, 가장 흔한 크기는 4 KiB예요. 프로그램의 가상 주소 공간도 페이지 단위로 자르고, 물리 메모리도 같은 크기로 잘라요. 물리 쪽 조각은 페이지 프레임이라고 해요. 프로그램마다 페이지 테이블이 하나씩 있어서 「가상 페이지 → 물리 페이지 프레임」을 기록해요. CPU는 메모리에 접근할 때마다 이 테이블부터 찾아봐요. 그림 14-1을 보세요.

이 구조에는 세 가지 장점이 있어요. 프로그램끼리 서로 격리돼요. 메모리가 모자라면 자주 안 쓰는 페이지를 SSD로 스왑 아웃했다가 필요할 때 다시 읽어 와요. 물리 메모리를 조각조각 나눠 할당해도 프로그램에는 연속된 주소로 보여요. 대가도 있어요. 같은 가상 페이지가 지금 어느 프레임에 있는지는 운영체제가 정하고, 언제든 바뀔 수 있어요.

접근할 때마다 페이지 테이블을 찾으면 너무 느려요. 그래서 CPU 안에 번역 결과를 캐시하는 작은 부품이 있어요. 이것이 TLB(변환 색인 버퍼)예요. 몇천 개밖에 못 담아요. Strata 소스는 이런 계산을 해 두었어요. 33.97 GB의 전문가 가중치를 4 KB 페이지로 자르면 830만 페이지예요. 어떤 TLB도 못 담아서, 전문가를 읽을 때마다 계속 테이블을 찾게 돼요. 2 MB 큰 페이지로 바꾸면 1만 6천 페이지 남짓이면 돼요. 코드 사실(include/strata/core/pinned.hpp) 아쉽게도 Windows에서는 일반 사용자 계정에 큰 페이지를 쓸 권한이 기본으로 없어요. 그래서 일반 페이지가 흔한 경우이고, 엔진은 시작할 때 어느 쪽을 받았는지 알려 줘요. 코드 사실(pinned.hpp)

운영체제를 배운 분께: 「페이지 테이블 + TLB + 페이지 폴트」 이야기 그대로예요. 이 장이 관심 있는 건 그 부작용이에요. 페이지 테이블은 언제든 바뀌는데, 외부 장치는 그 사실을 몰라요.

14.2 그래픽 카드가 직접 옮기게 하기: DMA와 페이지 고정

데이터를 RAM에서 그래픽 카드로 보낼 때 CPU가 바이트를 하나하나 옮길 필요는 없어요. 그래픽 카드에는 전용 복사 엔진이 있어요. CPU는 「어디서, 얼마나, 어디로 옮길지」만 알려 주면 돼요. 그러면 복사 엔진이 PCIe 버스를 따라 데이터를 알아서 끌어가요. 이렇게 「장치가 메모리를 직접 읽고 쓰는」 방식을 DMA(직접 메모리 접근)라고 해요.

DMA: 장치가 메모리에 직접 접근해요

DMA가 없으면 CPU가 모든 바이트를 메모리에서 읽어 장치에 써 줘야 해요. 그동안 다른 일은 하나도 못 해요. DMA가 있으면 CPU는 「옮기기 지시서」 하나만 보내요. 장치의 DMA 엔진이 지시서대로 옮기고, 끝나면 CPU에게 알려요. 디스크, 네트워크 카드, 그래픽 카드가 모두 이렇게 일해요.

핵심은 이거예요. DMA 엔진은 CPU의 페이지 테이블을 거치지 않고 물리 주소만 알아요. 드라이버가 작업 시작 전에 가상 주소를 번역해서 물리 페이지 프레임 번호 목록을 넘겨줘요. 옮기는 도중에 운영체제가 어떤 페이지를 옮겨 버리면 DMA 엔진은 그 사실을 모르고 원래 프레임을 그대로 읽어요. 그런데 그 프레임에는 지금 다른 프로그램의 데이터가 들어 있을 수 있어요.

그래서 DMA가 쓰는 메모리는 먼저 페이지 고정(pinning, 「페이지 잠금」이라고도 해요)을 해야 해요. 이 페이지들은 잠금을 풀기 전까지 옮기지도, 스왑 아웃하지도 말라고 운영체제에게 알리는 거예요. CUDA에서는 고정 메모리를 바로 요청할 수도 있고, 이미 있는 메모리를 고정 메모리로 「등록」할 수도 있어요. 일반(페이징 가능) 메모리를 복사할 때는 드라이버가 보통 데이터를 자기 소유의 고정 중계 영역에 먼저 복사한 뒤 DMA로 옮겨요. 복사가 한 번 더 들어가는 거예요.[R01]

글만으로는 「페이지가 옮겨진다」는 게 추상적이에요. 아래 시뮬레이터는 옮기기 한 번을 천천히 보여 줘요. 「옮기는 도중 메모리가 부족해지는」 상황을 직접 만들어 볼 수 있어요.

Strata는 전문가 가중치를 모두 고정 메모리에 둬요. 업스트림 보고[S02] 소스의 설명은 더 직설적이에요. 이 「전문가 영역」이 엔진의 진짜 워킹 세트이고, 복사 엔진이 대역폭을 끝까지 쓰려면 고정돼 있어야 한다고요. 코드 사실(pinned.hpp) 구체적인 방법은 이래요. 큰 메모리 덩어리를 먼저 예약하고, 그 어느 페이지에도 손대기 전에 덩어리 전체를 CUDA 고정 메모리로 등록해요. 그리고 그래픽 카드의 주소 공간에 매핑해요. 전체 등록이 실패하면 구간별로 등록하고, 남은 부분에는 운영체제의 「상주」 잠금을 써서 적어도 스왑 아웃은 막아요. v0.1.40부터는 이 메모리가 큰 페이지(large page)이면 이 단계를 생략해요. 큰 페이지는 원래 스왑 아웃되지 않기 때문이에요. 코드 사실(src/core/pinned.cu) 업스트림의 문제 해결 표에도 있어요. Windows에서 로그에 전체 등록 「메모리 부족」이 나오는 건 정상이고, 엔진이 층 단위로 나눠 잠그는 방식으로 바꿔요.

페이지를 고정하고 나면 데이터가 그래픽 카드로 가는 길은 세 가지예요. 그림 14-3을 보세요.

Strata의 전문가 소스 인터페이스는 뒤의 두 길을 모두 겉으로 드러내요. pinned()는 「이 전문가가 고정되고 등록된 메모리에 있어서, CPU가 먼저 복사하지 않고 바로 DMA를 할 수 있는가」에 답해요. device_alias()는 이 전문가의 그래픽 카드 주소 공간 안 주소를 알려 줘서, GPU가 PCIe로 직접 읽을 수 있게 해요. 코드 사실[S06] 주의하세요. 「GPU가 읽을 수 있다」는 「이미 VRAM에 있다」와 달라요. ③ 번 길로 가면 읽을 때마다 PCIe를 지나야 하고, 여전히 버스 대역폭에 묶여요.

고정하지 못한 전문가는 어떻게 할까요? 긴 프롬프트를 읽을 때 엔진에는 보조 스레드 몇 개가 있어요. 이 스레드들이 미리 고정 버퍼 묶음에 복사해 두었다가 복사 엔진에 넘겨요. 업스트림 보고[S03] 소스 주석에 따르면 예전에는 복사를 시작한 스레드가 직접 복사했어요. 그러면 매번 약 2 MB를 복사하는 동안 GPU는 줄 선 일이 없어서 놀았어요. IQ3_S에서 32K 프롬프트를 읽을 때 이렇게 헛되이 쓴 시간이 약 15초였어요. 업스트림 보고(src/prefill/prefill.cpp 주석)

14.3 「제출됨」은 「완료됨」이 아니에요

복사 엔진에게 옮기라고 시킨 뒤, CPU는 옆에서 끝나기를 기다려야 할까요? 기다려도 되고 안 기다려도 돼요. 이것이 두 가지 호출 방식이에요.

동기와 비동기

동기 호출은 함수가 돌아왔을 때 일이 이미 끝나 있어요. 창구에서 업무를 볼 때 끝날 때까지 서서 기다리는 것과 같아요. 비동기 호출은 함수가 일을 「제출」하고 바로 돌아와요. 일은 뒤에서 진행돼요. 인터넷으로 주문하면 주문만 넣고 다른 일을 하러 가고, 택배가 오면 알려 주는 것과 같아요.

비동기의 장점은 멍하니 기다리지 않아도 된다는 거예요. 그림 14-4를 보세요. 대가도 있어요. 함수가 돌아왔을 때 일이 끝났다고 가정하면 안 돼요. 결과를 쓰려면 분명한 완료 신호를 기다려야 해요. CUDA에서 같은 스트림(stream)에 제출한 일은 순서대로 실행돼요. 스트림을 넘나들거나 호스트가 결과를 읽어야 할 때는 이벤트(event)를 써요. 스트림에 이벤트를 기록해 두고 그 이벤트가 「완료」되면, 그 앞에 제출한 일은 모두 끝난 거예요.[R01]

Strata의 소스 코드에는 「돌아옴은 완료가 아니다」라는 경고가 곳곳에 있어요.

  • 검증 윈도우의 커밋은 계산 그래프가 끝나기를 기다리지 않고 돌아올 수 있어요. 그래서 다음 단계의 드래프트 생성이 동시에 진행돼요. 하지만 다른 스트림이나 호스트에서 세션 상태를 읽거나 쓰는 코드(새 요청, 저장, 스냅샷 등)는 모두 먼저 wait_commit()을 호출해야 해요. 코드 사실[S08]
  • 층마다 도는 메인 루프는 「스트림 전체가 끝나기를 기다리는」 함수를 부르지 않고 이벤트 하나를 조회해요. 소스 주석에는 함정 하나도 적혀 있어요. 토큰마다 고정 버퍼를 한 번씩 해제했는데, 고정 메모리를 해제하면 장치 전체가 암묵적으로 동기화돼요. 그래서 토큰이 끝날 때마다 장치 전체 대기가 한 번씩 더 생겼어요. 세션을 시작할 때 한 번 할당해서 계속 쓰는 것으로 고쳤어요. 코드 사실(include/strata/core/session.hpp)

11장의 디스크 읽기도 같은 발상이에요. 토큰이 정해지는 즉시 읽기 요청 16개를 제출하고, 1번째 층에서 필요하기 직전에야 결과를 가져와요.

14.4 더블 버퍼링: 한쪽은 옮기고, 한쪽은 계산하고

비동기 옮기기를 가장 흔히 쓰는 방법은 옮기기와 계산을 겹치는 거예요. 데이터 블록이 줄줄이 있다고 해 봐요. 블록마다 먼저 그래픽 카드로 옮기고(3 ms), 그다음 계산해요(5 ms). 버퍼가 하나뿐이면 「다 옮기고 나서 계산, 다 계산하고 나서 옮기기」밖에 못 해요. 버퍼가 두 개면 한 블록은 계산하고, 그동안 다른 버퍼에서 다음 블록을 옮길 수 있어요. 이것을 더블 버퍼링이라고 해요.

계산해 볼게요. 블록이 4개면 직렬로는 4 × (3 + 5) = 32 ms가 걸려요. 더블 버퍼링이면 첫 블록의 옮기기와 마지막 블록의 계산은 겹칠 수 없고, 중간의 각 단계는 느린 쪽 기준이에요. 3 + (4 − 1) × max(3, 5) + 5 = 23 ms예요. 이 공식이 성립하려면 복사 엔진과 계산 유닛이 정말로 독립된 두 자원이어야 해요.

시뮬레이터가 가장 보여 주고 싶은 건 「신호를 기다리지 않고 덮어쓰는」 순간이에요. 더블 버퍼링이 옳은 건 「메모리를 두 개 할당해서」가 아니라 두 가지 신호 덕분이에요. 복사가 끝나야 읽을 수 있고, 다 쓰고 나야 쓸 수 있어요. 버퍼 하나하나가 작은 상태 기계예요. 그림 14-6을 보세요.

Strata는 긴 프롬프트를 읽을 때 이런 링 버퍼를 써요. VRAM에 없는 전문가는 고정된 링 슬롯 묶음을 거쳐, 별도의 복사 스트림에서 그래픽 카드로 보내져요. 코드 사실[S12] 슬롯마다 이벤트가 두 개 붙어요. 하나는 「복사 끝」, 하나는 「다 썼음」이에요. 코드 사실(prefill.cpp) 앞에서 말한 보조 복사 스레드도 같은 규칙을 따라요. j번째 작업은 j mod 16번째 고정 버퍼(기본 16개)에 쓰고, 그 전에 j − 16번째 작업이 이 버퍼에서 시작한 DMA가 끝나기를 먼저 기다려야 써 넣을 수 있어요. 코드 사실(prefill.cpp)

링을 얼마나 크게 할지도 고민거리예요. 소스 주석에 측정이 하나 기록돼 있어요(Q2_0, 블록당 토큰 8192개). 링 슬롯을 96개에서 384개로 늘리자 프롬프트 읽기가 초당 토큰 1,153개에서 1,294개로 올랐어요. 다음 층의 전문가가 이 층의 어텐션 계산 중에 미리 도착할 수 있었기 때문이에요. 반대로 많은 전문가를 호스트 복사에 의존해야 할 때는 큰 링이 오히려 더 느려요. 병목이 호스트 복사라서, 늘어난 슬롯이 캐시 자리만 차지하기 때문이에요. 업스트림 보고(prefill.cpp 주석) 여러 GPU로 층을 나눌 때는 단계마다 고정된 인계 버퍼도 두 개씩 있어요. 다음 단계가 c번째 블록을 읽는 동안 이 단계는 이미 c + 1번째 블록을 처리해요. 코드 사실[S12] 이것이 더블 버퍼링이에요.

14.5 페이지 고정은 공짜가 아니에요

페이지 고정이 이렇게 좋다면 메모리를 전부 고정하면 안 될까요? 안 돼요. 고정한 페이지는 운영체제가 옮길 수도, 스왑 아웃할 수도 없고, 메모리가 부족해도 회수할 수 없어요. 많이 고정할수록 시스템, 다른 프로그램, 파일 캐시에게 남는 여유가 줄어요.[R02]

Strata는 이 점에 신중해요. 저메모리 「상주」 모드는 시스템에 4 GiB의 빈 메모리를 남겨 둬요. 업스트림 보고[S03] --resident-budget-gib로 메모리 예산을 정해 주면, Windows에서는 이 예산이 「커밋 가능 메모리」(commit limit)의 제한도 받아요. 넘으면 엔진이 예산을 낮추고 안내 메시지를 띄워요. 코드 사실(src/core/expert_source.cpp) Windows에서는 그래픽 카드에 매핑된 고정 메모리가 「공유 VRAM」 예산도 차지해요. 소스에는 63 GB짜리 컴퓨터 사례가 있어요. 드라이버가 거부할 때까지 구간별로 잠갔더니 28 GiB를 잠갔고, 그러자 그 예산이 가득 차서 이후 VRAM 할당이 전부 「메모리 부족」이 났어요. 그래서 엔진은 선택적인 상한 설정을 제공해요. 하지만 기본값은 아니에요. 64 GB 컴퓨터에서는 더 많이 잠가도 문제가 없다고 실측됐고, 상한을 두면 프롬프트 읽기가 약 20% 느려지기 때문이에요. 코드 사실(pinned.cu) 이런 트레이드오프에는 어디서나 통하는 답이 없어요. 기계에 맞춰 재 봐야 해요.

재미있는 비교가 하나 더 있어요. 긴 컨텍스트의 KV 페이지 캐시(12장에서 언급했어요)는 KV 데이터 전체를 고정되고 그래픽 카드에 매핑된 메모리에 두고, VRAM에는 일부 페이지만 둬요. 그리고 「페이지 번호 → VRAM 슬롯」 표로 누가 VRAM에 있는지 기록해요. 코드 사실(include/strata/kernels/kv_stream.hpp) 이건 거의 미니 가상 메모리예요. 페이지 테이블, 페이지 폴트, 교체를 모두 GPU가 스스로 해요.

14.6 직접 해 보기: 경쟁 상태를 매번 재현하기

이 장에는 따로 인터랙티브 실험이 없어요. 시뮬레이터 두 개가 실험대예요. 「더블 버퍼링」에서 버퍼 1개, 2개, 3개로 한 번씩 재생하고 총 시간을 적어 보세요. 2개로 돌아와 「신호 안 기다리고 덮어쓰기」를 켜고, 어느 블록이 ✗로 표시되는지 보세요. 그다음 복사를 느리게, 계산을 빠르게 바꿔서 다시 해 보세요. 이번에는 왜 「우연히」 오류가 안 났을까요? 「가끔은 맞고 가끔은 틀리는」 이런 오류가 가장 잡기 어려워요.

「DMA와 페이지 고정」에서는 「페이지 고정」을 끈 채로, 그리고 켠 채로 한 번씩 해 보세요. 4단계와 5단계에서 페이지 테이블과 DMA가 쥔 프레임 번호를 비교해 보세요.

마지막으로 종이 위의 실험이에요. 배열 두 개로 더블 버퍼링을 흉내 내고, 소비자가 다 읽기 전에 생산자가 배열을 일부러 덮어쓰게 하는 테스트를 써 보세요. 테스트가 실패하는지 확인해요. 그다음 「다 썼음」 신호를 더하고 테스트가 통과하는지 확인해요. 마지막으로 「완료 이벤트」를 몇 단계 일부러 늦춰서, 시스템이 반쯤 새것이고 반쯤 낡은 데이터를 몰래 읽지 않고 제대로 기다리는지 확인해요.

이 세 가지를 기억하기

  1. 프로그램의 주소는 가상이고, 운영체제는 언제든 페이지를 옮길 수 있어요. DMA는 물리 주소만 알아서, DMA가 쓰는 메모리는 페이지를 고정해야 해요. Strata의 전문가 영역은 모두 고정되고 그래픽 카드에 매핑돼요.
  2. 비동기 호출에서 「돌아옴」은 「완료」가 아니에요. 결과를 쓰려면 완료 이벤트를, 버퍼를 재사용하려면 「다 썼음」 이벤트를 기다려요.
  3. 더블 버퍼링은 옮기는 시간을 계산 뒤로 숨겨요. 총 시간 ≈ 첫 블록 복사 + (블록 수 − 1) × 느린 구간 + 마지막 블록 계산이에요. 페이지 고정에는 대가가 있으니 시스템에 여유를 남겨야 해요.

흔한 오해: 「비동기 복사 함수가 돌아왔으니 데이터가 도착했고, 원본 버퍼도 바로 고쳐도 된다.」

함수가 돌아왔다는 건 일이 제출됐다는 뜻일 뿐이에요. 복사는 아직 시작도 안 했을 수 있어요. 이때 원본 버퍼를 고치면 그래픽 카드가 새것과 낡은 것이 섞인 데이터를 받을 수 있어요. 원본을 해제하면 복사가 이미 남이 쓰는 메모리를 읽을 가능성이 더 커요. 재사용해도 되는지는 완료 신호만 알려 줘요. 중간에 「0.1초 기다리기」를 넣는 것도 해결책이 아니에요. 느린 기계에서는 여전히 틀리고, 빠른 기계에서는 괜히 느려져요.

한 걸음 더: 생산자-소비자 프로토콜, 스트림의 순서 경계, 메모리 예산

가장 작은 생산자-소비자 프로토콜

생산자가 바이트를 채우고 나서 「준비됨」을 공개해요. 소비자는 「준비됨」을 보고 읽은 뒤 「다 썼음」을 공개해요. 생산자는 「다 썼음」을 본 뒤에야 덮어쓸 수 있어요. 교육용 상태 기계는 이래요. 비어 있음 → 채우는 중 → 준비됨 → 읽는 중 → 비어 있음. 「준비됨」에서 바로 「비어 있음」으로 돌아갈 수 없어요. 장치를 넘나드는 순서 보장을 일반 변수나 volatile로 대신할 수도 없어요. 어떤 펜스, 이벤트, 스트림 의미론을 쓸지는 대상 플랫폼의 규칙을 따라야 해요.[R01]

스트림의 순서는 보장하는 범위 안에서만 성립해요

같은 스트림에 순서대로 제출한 연산에는 저절로 선후 관계가 생겨요. 서로 다른 스트림 사이, 호스트 읽기와 기본 스트림 사이에는 순서를 마음대로 가정하면 안 돼요. 전문가 캐시의 부팅 채우기가 바로 여기서 넘어졌어요. 데이터는 논블로킹 스트림에서 복사했고 검증은 레거시 스트림에서 읽었어요. 둘 사이에 순서가 없어서, 검증이 아직 복사가 안 끝난 슬롯을 읽었어요. 코드 사실[S05] 검증 윈도우의 비동기 커밋도 마찬가지예요. 호출하는 쪽이 기다림을 건너뛸 수 있는 조건은 뒤따르는 일이 같은 스트림에 있고, 드래프트 생성이 그 커밋이 쓰는 것을 읽지 않는 거예요. 다른 스트림이나 호스트가 세션 상태를 읽어야 하면 먼저 기다려야 해요. 코드 사실[S08]

같은 동시성 교훈을 두 번 썼어요

보조 복사 스레드는 작업을 가져올 때 「묶음 번호 | 작업 수 | 순번」으로 묶은 원자 변수를 써요. 묶음 번호가 맞을 때만 작업을 가져올 수 있어서, 늦게 온 스레드는 다음 묶음의 작업을 가져갈 수 없어요. 소스 주석에 따르면 이것은 CPU 전문가 풀이 멈췄던 일(issue #29)의 교훈이에요. 코드 사실(prefill.cpp) 13장에서 그 멈춤의 전말을 다뤘어요.

메모리 예산을 이중으로 세지 마세요

튼튼한 메모리 예산은 여러 양을 구분해야 해요. 예약된 것(주소는 차지했지만 아직 실제로 할당되지 않음), 커밋된 것(시스템이 줄 수 있다고 약속함), 상주하는 것(지금 물리 메모리에 있음), 고정된 것(스왑 아웃 금지), 그래픽 카드에 별도 사본이 있는 것이에요. 이 양들은 같은 물리 페이지를 가리킬 수 있어서 단순히 더하면 이중으로 세게 돼요. 겹치는지부터 확인한 뒤에 합계를 내세요.[R02] 호스트에는 서비스 프로세스, 파일 캐시, 페이지 테이블, 입력 버퍼, 복구 가능한 세션 상태도 있어서 물리 메모리 전부를 전문가에게 나눠 줄 수는 없어요.

검수: 드문 오류를 매번 재현되게 만들기

테스트는 순탄한 길만 가면 안 돼요. 일부러 이런 상황을 만들어야 해요. 소비자가 「다 썼음」을 한참 안 돌려줄 때 생산자가 한 바퀴 돌아와 덮어쓰지는 않는가. 완료 이벤트를 일부러 늦췄을 때 시스템이 기다리는가, 반쯤 만들어진 데이터를 읽는가. 라운드마다 데이터에 증가하는 세대 번호를 붙여서, 소비자가 읽은 세대가 기대한 세대와 같아야 하게 하기. 타임아웃이 난 뒤에는 이 버퍼를 다시 쓰면 안 돼요. 11장의 디스크 읽기 모듈에는 「읽기마다 일부러 지연」하는 장애 주입이 내장돼 있어요. 바로 이런 검수를 위해서예요.
