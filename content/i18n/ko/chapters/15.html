이상한 시간 측정값

Strata 소스 코드의 주석에 이상한 이야기가 하나 적혀 있어요. gdn_gate라는 GPU 작은 프로그램이 숫자를 겨우 48개 처리하는데, 한 번 돌 때마다 28 마이크로초가 걸린다는 거예요. 작성자의 평가는 이래요. 이렇게 작은 커널(kernel)이 실제로 28 마이크로초나 실행될 리 없다는 것이죠. 코드 사실[S13]

숫자 48개는 GPU가 눈 깜짝할 새에 계산해요. 그럼 남는 시간은 어디에 쓰였을까요? 답은 「접수」예요. CPU가 GPU에 작은 프로그램을 하나 맡길 때마다 먼저 제출 절차를 한 번 거쳐야 해요. 하나씩 제출하면 토큰 하나를 만드는 데 제출을 2천 번쯤 해요. 이 장에서는 GPU가 일을 나누는 방식, 접수비가 어디서 생기는지, 그리고 Strata가 2천 번의 접수를 수십 번, 심지어 한 번으로 줄이는 방법을 다뤄요.

한마디로: GPU에서 도는 작은 프로그램을 커널(kernel)이라고 해요. 커널은 시작할 때마다 수십 마이크로초의 고정 비용이 들어요. Strata는 두 가지로 이 비용을 줄여요. 커널 여러 개를 하나로 융합하고, 한 층의 커널들을 CUDA Graph로 녹화해 한 번에 제출해요. 대신 그래프는 인자를 녹화 시점의 값으로 고정해 버려요. 그래서 매 단계 바뀌는 「위치」는 주소가 고정된 GPU 메모리 조각에 넣어야 해요.

15.1 GPU가 일을 나누는 법: 스레드, 스레드 블록, 워프

먼저 큰 채점 현장을 떠올려 보세요. 시험지가 수만 장 있고, 선생님 한 분이 한 장씩 채점해요. 선생님들은 여러 시험장으로 나뉘고, 각 시험장 안에서는 32명씩 한 줄로 앉아요. 한 줄은 같은 구령을 들어요. 「넘기세요」 「1번 문제 보세요」 「점수 매기세요」. 구령은 같지만 손에 든 시험지는 제각각이에요.

GPU도 이렇게 일해요. CPU가 GPU에 넘기는 작은 프로그램이 커널(kernel, GPU 함수)이에요. 커널을 한 번 시작하면 GPU는 수천수만 개의 스레드(thread)를 만들어요. 모든 스레드가 같은 코드를 실행하고, 처리하는 데이터 번호만 달라요. 스레드는 먼저 여러 스레드 블록(block)으로 묶여요. 한 블록의 스레드는 같은 연산 유닛에서 돌고, 작고 빠른 저장 공간을 함께 쓸 수 있어요. 블록 안의 스레드는 다시 32개씩 워프(warp)로 묶여요. 같은 워프의 스레드 32개는 같은 명령을 동시에 실행해요.[R01] 그림 15-1은 이 세 층을 한 장에 그렸어요.

Strata 곳곳에 이런 배치가 있어요. 예를 들어 17장에서 다룰 KV 페이지 교체에 대해 소스는 「스레드 1,024개짜리 블록 하나로, 선택된 번호들을 한 번 훑는다」라고 적어 두었어요. 코드 사실 GDN 층의 점화식도 있어요. 소스 주석에 따르면 식의 각 행은 상태의 한 열만 건드리고 열끼리는 서로 상관이 없어요. 그래서 「스레드 하나가 열 하나를 통째로 맡을 수 있고, 한 단계 내내 스레드끼리 서로 기다릴 필요가 없다」고 해요.[S17]

GPU 프로그래밍 모델: 스레드, 스레드 블록, 워프

직관: CPU는 만능 교수 몇 분이에요. 각자 복잡한 분기와 판단을 처리할 수 있어요. GPU는 조교 수천 명이에요. 각자 구령에 맞춰 단순한 일만 하지만 사람이 많아요. GPU를 빠르게 쓰려면 일을 서로 의존하지 않는 작은 작업 수천수만 개로 쪼개야 해요.

정의: 프로그래머는 커널 함수를 쓰고, 시작할 때 「스레드 블록을 몇 개, 블록당 스레드를 몇 개 열지」 지정해요. CUDA에서는 vecAdd<<<4, 256>>>(A, B, C)처럼 써요. 블록 4개에 블록당 스레드 256개, 합쳐서 1,024개예요. 각 스레드는 threadIdx.x + blockDim.x × blockIdx.x로 자기가 맡을 원소 번호를 계산해요. 현재 NVIDIA GPU에서 스레드 블록 하나는 최대 1,024개 스레드를 가질 수 있고, 블록 안의 스레드는 32개씩 워프가 돼요.[R01]

구체적인 숫자 하나: 워프가 GPU 메모리를 읽을 때 스레드 32개가 이웃한 주소를 읽으면 하드웨어가 이를 몇 번 안 되는 메모리 트랜잭션으로 합칠 수 있어요. 이것을 병합 접근(coalesced access)이라고 해요. 주소가 서로 멀리 떨어져 있으면 트랜잭션이 아주 많이 쪼개지고, 매번 일부 바이트만 써요. 다음 절의 Strata 사례가 그 차이가 얼마나 큰지 보여 줘요.

이 장과의 관계: 커널은 CPU가 GPU에 넘기는 가장 작은 작업 단위예요. 커널이 작고 많을수록 「넘기는 일」 자체의 비용이 눈에 띄어요.

CS를 배운 분께: 워프는 SIMT(단일 명령 다중 스레드)의 실행 단위예요. 명령 하나가 스레드 32개를 움직이는 점은 SIMD의 벡터 명령과 비슷해요. 다만 스레드마다 자기 레지스터와 프로그램 카운터가 있어서 다른 분기로 갈 수 있어요. 대가로 분기의 양쪽을 번갈아 실행해야 해요. 13장에서 SIMD와 SIMT의 차이를 자세히 다뤄요.

15.2 이웃한 스레드는 이웃한 주소를 읽는다: 데이터 배치가 중요하다

같은 수학이라도 데이터를 어떻게 놓느냐에 따라 속도가 몇 배씩 달라져요. 그림 15-2가 두 가지 읽기 방식을 비교해요.

Strata의 GDN 층이 이 문제로 손해를 봤어요. 융합 커널의 주석에 따르면 원래 방식은 워프 하나가 상태의 한 열을 맡고, 스레드 32개가 128개 행을 따라 내려갔어요. 그런데 상태는 「행, 헤드, 열」 순서로 저장돼 있어서 이웃한 두 스레드가 읽을 데이터가 약 24.5 KB나 떨어져 있었어요. 그 결과 32바이트 섹터를 가져올 때마다 4바이트만 쓰게 됐고, 층마다 6.3 MB의 상태를 옮기는 데 47.6 마이크로초가 걸렸어요. 코드 사실

고친 뒤에는 스레드 블록 하나가 헤드 하나를 통째로 맡아요. 스레드 512개가 「행 묶음, 열」 순서로 펼쳐지고, 한 행의 128개 열이 딱 512바이트 연속 읽기가 돼요. 코드 사실 원리는 그림 15-2와 같아요. 이웃한 스레드가 이웃한 주소를 읽게 하는 거예요. GDN의 기본 커널도 이 규칙을 지켜요. 상태를 (i, h, j) 순서로 저장하고 j가 가장 빨리 변하므로, i가 고정되면 워프가 j를 따라 읽는 데이터가 연속 메모리예요.[S17]

데이터 배치는 「공짜」로 고를 수 있는 선택이에요. 상태는 실행 중에 쓰는 버퍼이지 모델 가중치가 아니니까 원하는 대로 놓아도 돼요. 하지만 소스가 특별히 경고하는 점이 있어요. 두 배치 모두 같은 세 숫자로 인덱싱하기 때문에, 읽는 쪽과 쓰는 쪽의 배치가 다르면 프로그램은 그대로 돌면서 결과만 조용히 틀려요.[S17]

15.3 커널을 한 번 시작할 때마다 「접수비」를 낸다

처음의 이상한 이야기로 돌아가요. CPU가 GPU에 커널 하나를 돌리게 하려면 드라이버를 거쳐야 해요. 인자를 검사하고, 명령을 포장하고, 제출 큐에 넣어요. 이 절차는 CPU에서 하므로 시간이 걸리고, 이를 런치 오버헤드(launch overhead, 시작 비용)라고 해요. 커널 자체는 몇 마이크로초만 계산하는데 절차에 십몇~이십 마이크로초가 들면, GPU는 하나를 끝내고 다음 것을 멍하니 기다리게 돼요. 그림 15-3이 이 「기다림」을 보여 줘요.

가상의 이야기가 아니에요. Strata의 주석은 이렇게 결론을 내려요. 「이 엔진은 대역폭이 아니라 런치 오버헤드에 묶여 있다」. GDN 층의 커널은 전부 약 0.028 밀리초로 측정돼요. 숫자 48개만 처리하는 gdn_gate도 마찬가지예요. 이 기기에서 평범한 커널 시작 한 번의 비용이 딱 그만큼이에요. GDN 층 하나는 커널을 약 19번, 완전한 층 블록 하나는 약 45번 시작해요. 코드 사실[S13] 주석에는 측정에 쓴 그래픽 카드와 드라이버 버전이 적혀 있지 않아요. 아래 숫자는 규모감을 잡는 용도로만 보세요.

계산해 봐요. 다른 주석에 따르면 커널을 하나씩 시작할 때 토큰 하나당 약 2,000번을 시작하고, 드라이버 호출 한 번의 비용은 10–22 마이크로초로 실측됐어요. 코드 사실 「접수」만으로도 토큰 하나당 2,000 × 10 µs = 20 밀리초에서 2,000 × 22 µs ≈ 44 밀리초가 들어요. 속도로 바꾸면, GPU가 계산을 전혀 안 해도 초당 토큰 23–50개가 한계예요. 교육용 추정

커널 런치 오버헤드와 연산자 융합

직관: 병원에서는 접수하려면 줄을 서야 해요. 작은 검사마다 새로 접수하면 오전이 접수 창구에서 다 가요. 방법은 두 가지예요. 하나는 검사 여러 개를 한 번으로 합치는 것(연산자 융합, operator fusion)이에요. 다른 하나는 의사가 검사 목록 전체를 한 번에 써 주고 간호사가 목록대로 진행하는 것(CUDA Graph)이에요.

정의: 런치 오버헤드는 CPU가 커널 하나를 준비해 제출하는 고정 비용이고, 커널이 얼마나 계산하는지와는 거의 상관없어요. 커널 하나의 계산에 w 마이크로초, 제출에 L 마이크로초가 든다고 해요. 커널 n개를 하나씩 제출할 때, w < L이면 총 시간은 약 n × L + w이고 GPU는 대부분 기다려요. w ≥ L이면 총 시간은 약 L + n × w이고 제출 비용이 계산 뒤에 숨어요. 교육용 추정

융합의 장점은 접수 횟수가 줄어드는 것만이 아니에요. 연산자 여러 개를 커널 하나로 합치면 중간 결과를 레지스터나 칩 안의 저장 공간에 둘 수 있어서, GPU 메모리에 썼다가 다시 읽을 필요가 없어요. 대가로 이 커널은 더 복잡해지고, 레지스터를 더 쓰며, GPU에서 동시에 돌 수 있는 스레드가 줄어들 수 있어요. CUDA Graph는 커널 자체를 바꾸지 않아요. 연산 여러 개와 의존 관계를 녹화해 두었다가 나중에 한 번에 제출해 통째로 재생해요. 줄이는 것은 CPU 쪽 제출 비용이에요.[R01]

이 장과의 관계: Strata는 두 방법을 다 써요. 다음 절에서 구체적인 숫자를 볼게요.

15.4 아끼는 두 가지 방법: 융합과 CUDA Graph

그림 15-4는 두 방법을 나란히 비교해요. 융합은 GPU에서 무엇을 돌리는지를 바꾸고, 그래프는 CPU가 어떻게 제출하는지를 바꿔요.

융합. Strata에는 파일 이름에 fused_가 붙은 커널이 여러 개 있어요. 예를 들어 fused_gdn_conv_l2 커널 하나가 원래의 「합성곱과 SiLU」 및 L2 노름 두 번, 합쳐서 세 번의 시작을 대신해요. fused_gdn_ab는 행렬-벡터 곱 두 번과 원소별 커널 두 개를 대신해요. 코드 사실 혼합 잔차 읽기는 원래 한 번에 커널 여섯 개가 필요했고 토큰 하나당 96번 돌았어요. 융합 후에는 커널 두 개로 줄었어요. 코드 사실

CUDA Graph. Strata는 층마다 커널을 그래프로 녹화해요. 주석에 실측값이 있어요. 같은 층 블록의 노드 43개를 하나씩 시작하면 2.393 밀리초가 걸리고, 그래프로 녹화해 재생하면 1.585 밀리초밖에 안 걸려요. 1.51배 빠르고, 줄어든 시간은 「전부 런치 오버헤드」예요. 코드 사실[S13] 다른 주석은 더 직설적이에요. 재생과 하나씩 시작하는 방식은 산술이 완전히 같고, 다른 점은 「커널 시작 약 2,000번이 그래프 시작 48번으로 바뀐다」는 것뿐이에요. 코드 사실

더 나아갈 수 있을까요? 있어요. Windows의 디스플레이 드라이버 모드에서는 그래프 시작 한 번에도 약 0.3–0.4 밀리초가 들어요. 층별 루프는 토큰마다 그래프를 96번 시작하고, 실측으로 토큰 하나에 48.6 밀리초가 걸리는데 GPU에서 진짜 커널이 차지하는 시간은 12 밀리초뿐이에요. 그래서 Strata는 「토큰 하나를 그래프 한 장으로」 만드는 버전도 썼어요. 48개 층을 전부 한 그래프에 담아요. 코드 사실 그림 15-5가 세 단계를 한 줄로 늘어놓아요.

처음부터 토큰 전체를 녹화하지 않은 이유가 뭘까요? 층 중간에 CPU 전문가 풀과 주고받는 지점이 있기 때문이에요. GPU가 라우터 단계까지 계산해야 CPU가 어떤 전문가를 계산할지 알아요. Strata가 처음에 「한 층」을 그래프 단위로 잡은 것은 층과 층 사이에 호스트가 끼어들어서, GPU가 다음 구간을 도는 동안 CPU 전문가 풀이 동시에 일하게 하려는 거였어요.[S13] 토큰 전체 그래프는 방식을 바꿨어요. GPU 위의 단일 스레드 커널이 장치 쪽에서 호스트가 플래그를 쓸 때까지 기다리고, 호스트는 더 이상 드라이버를 호출하지 않아요. 코드 사실

15.5 그래프는 인자를 고정해 버린다: 얼어붙은 위치

CUDA Graph에는 버릇이 하나 있어요. 녹화할 때 커널의 인자가 그대로 그래프에 복사되고, 이후 재생할 때마다 그 사본을 써요. Strata는 이를 확인하는 작은 실험을 따로 만들었어요. 그래프는 재생할 때 입력 버퍼의 데이터는 다시 읽지만 커널 인자는 다시 읽지 않아요. 코드 사실

문제는 어떤 인자는 토큰마다 바뀐다는 점이에요. 가장 대표적인 것이 위치, 곧 몇 번째 토큰이냐예요. 위치를 KV 캐시에 쓰는 커널의 인자로 넘기면, 녹화할 때 0이었으니 이후 재생할 때마다 계속 0이에요. 아래 시뮬레이터는 이 과정을 천천히 보여 줘요. 먼저 「값으로 그래프에 녹화」를 고르고 한 단계씩 토큰 몇 개를 진행해 보세요.

Strata의 qsa.hpp는 이 오류의 결과를 아주 구체적으로 적어 두었어요. 위치가 얼어붙으면 모든 토큰이 0번 칸에 쓰이고, 점수 계산과 선택은 1칸만 보고, 어텐션은 계속 과거를 한 칸만 봐요. 주석의 평가는 「충돌보다 나쁘다」예요. 출력은 유한하고 그럴듯한 숫자라서 증상이 「모델이 문맥을 쓰지 못한다」와 똑같아요. 사람들은 KV 캐시, 선택 알고리즘, 가중치를 의심하고, 그래프는 생각도 못 해요. 코드 사실[S18]

해결책은 「함수 시그니처 여섯 개를 고치는 대신 GPU 메모리 한 조각」이에요. 매 단계 바뀌는 숫자 네 개를 작은 step 버퍼에 넣어요.

  • step[0] = pos: 새 토큰의 위치
  • step[1] = n_kv = pos + 1: 캐시에 몇 칸이 있는지
  • step[2] = n_bid: 4칸짜리 블록이 몇 개 찼는지
  • step[3] = width: 이번 단계에서 몇 칸을 고르는지. min(n_kv, 2051)과 같아요.[S18]

모든 커널이 이 메모리에서 필요한 숫자를 읽어요. 그래서 인자 목록은 토큰이 바뀌어도 완전히 그대로이고, QSA 경로 전체를 그래프로 녹화할 수 있어요. 호스트는 매 단계 작은 복사 한 번으로 이 메모리의 내용만 고쳐 써요. 코드 사실[S18] 네 숫자는 서로 의존하므로 한곳에 두고 코드 한 군데에서 계산하면 「pos만 고치고 n_kv를 잊는」 일이 생기지 않아요.

CS를 배운 분께: C 언어의 「값 전달」과 「포인터 전달」의 차이와 똑같아요. 그래프가 녹화한 것이 값이면 영원히 그 값이고, 포인터이면 역참조할 때마다 새 내용을 읽어요. 단, 포인터가 가리키는 메모리가 계속 유효해야 하는데, 이것은 그래프가 스스로 검사할 수 없어요.

같은 이치가 샘플링에도 쓰여요. 온도와 top-p 같은 인자는 요청마다 다를 수 있어요. 그래서 Strata는 샘플링을 녹화되는 그래프의 바깥에 둬요. 그렇지 않으면 이 인자들이 「그래프에 영구히 구워져」 버려요. 코드 사실[S08]

15.6 직접 해 보기: 병목과 고정 현상을 스스로 찾아보기

이 장의 인터랙티브 그림 두 개는 작은 실험으로 쓸 수 있어요.

  1. 런치 오버헤드 타임라인(그림 15-3): 먼저 기본값으로 재생하고 세 방식의 총 시간과 GPU 가동 비율을 적어 두세요. 그다음 커널당 계산 시간 w를 5 µs에서 40 µs까지 천천히 늘려, 「그래프가 더 이상 눈에 띄게 빠르지 않은」 지점을 찾아보세요. 대략 w가 L에 가까워지는 곳에서 나타나요. 커널이 제출보다 길어지면 제출 비용은 자연히 숨어요.
  2. 얼어붙은 위치(그림 15-6): 두 방식으로 각각 토큰 4개를 진행하세요. KV 칸과 「어텐션이 볼 수 있는 칸 수」를 비교하세요. 그리고 생각해 보세요. 「프로그램이 오류를 냈는가, 출력이 유한한 숫자인가」만 확인한다면 잘못된 방식을 발견할 수 있을까요?

실제 GPU에서 검증하려면 state[pos] = token만 하는 작은 그래프를 만들어 pos = 0, 1, 2로 각각 재생하고 세 위치가 모두 쓰였는지 확인하세요. 마지막 반환값이 「성공」인 것만 보는 것으로는 부족해요.

이 세 가지를 기억하기

  1. GPU는 수천수만 개의 스레드로 일해요. 스레드는 블록으로 묶이고, 블록 안에서 32개씩 워프가 돼요. 이웃한 스레드가 이웃한 주소를 읽게 해야 데이터 이동이 낭비되지 않아요.
  2. 커널은 시작할 때마다 고정 비용이 들어요. Strata는 원래 토큰 하나에 커널을 약 2,000번 시작했어요. 융합으로 커널 수를 줄이고, CUDA Graph로 제출을 층마다 한 번, 다시 토큰마다 한 번으로 줄여요.
  3. 그래프는 커널 인자를 고정해요. 매 단계 바뀌는 값(위치, n_kv, 선택 폭)은 주소가 고정된 GPU 메모리 버퍼에 넣고, 커널이 매번 읽게 해야 해요.

흔한 오해: 「CUDA Graph는 커널 여러 개를 큰 커널 하나로 합치는 것이다.」

아니에요. 그래프는 연산 여러 개와 그 의존 관계를 녹화할 뿐이에요. 재생할 때 각 노드는 여전히 독립된 커널이고, 중간 결과도 여전히 GPU 메모리에 써요. 그래프가 줄이는 것은 CPU 쪽 제출 비용이에요. 계산을 진짜로 커널 하나로 합치는 것은 연산자 융합이고, 이쪽은 커널을 다시 써야 해요. 두 방법은 서로 다른 문제를 풀고, Strata는 둘 다 써요.[R01]

한 걸음 더: 융합의 대가, 녹화의 세 가지 의무, 검증 방법

융합은 공짜가 아니다

연산자 여러 개를 커널 하나에 쓰면 시작 횟수가 줄고, 중간 결과를 쓰고 읽는 횟수도 줄어요. 대가가 있어요. 커널 안에서 동시에 살아 있는 변수가 늘어나서 스레드마다 레지스터를 더 써요. 레지스터 총량은 정해져 있어서 스레드가 많이 쓰면 동시에 상주하는 스레드가 줄고, GPU가 메모리 대기를 가리는 데 쓰는 「예비 스레드」도 줄어요. 이것을 점유율(occupancy) 하락이라고 해요. 구현도 더 복잡하고 테스트하기도 어려워요. 그래서 융합은 측정 결과를 보고 정해요. 예를 들어 Strata의 혼합 잔차 융합 읽기에는 변형이 여럿 있어요. 엔진은 카드마다 먼저 무작위 가중치로 한 번 돌려 보고, 기준 구현과 비트 단위로 같은 최신 변형만 채택해요. 코드 사실

교육용 계산 예: 한 층에서 시작이 20번이고 시작마다 호스트 비용이 5 µs이면, 시작만으로 약 100 µs예요. 매번 몇 마이크로초만 계산하는 작은 연산자에게는 상당한 양이에요. 커널 하나가 몇 밀리초씩 계산한다면 같은 100 µs는 잔돈일 뿐이에요. 모두 가정값이고, 「최적화할 가치가 있는가」를 판단하는 용도예요. 실측이 아니에요. 교육용 추정

녹화의 세 가지 의무

graph.hpp는 세 가지를 인터페이스의 전제로 적어 두었어요. 각각 전용 작은 실험에서 나온 결론이에요. 코드 사실

  1. 기다릴 때는 드라이버를 호출해야 하고, 메모리만 읽어서는 안 된다. Windows 디스플레이 드라이버 모델에서는 명령 제출이 모아서 이루어져요. 메모리만 읽고 드라이버를 호출하지 않는 스핀 루프는 500 밀리초 동안 5,907,703번 돌았는데 커널은 시작조차 하지 않았어요. 어떤 코드가 드라이버를 호출하고 나서야 데이터가 뒤집혔어요. 그래서 대기 방식을 이벤트 조회 반복으로 바꿨어요. 조회 한 번에 약 0.021 밀리초이고, 이것은 「조회」이지 「동기화」가 아니에요.
  2. 그래프는 입력 버퍼를 다시 읽고, 커널 인자는 다시 읽지 않는다. 재생 8번 동안 매번 고정(pinned) 입력을 바꿔 넣어도 결과가 따라왔어요. 반면 인자는 녹화할 때 노드에 복사되고 다시는 읽지 않아요. 매 단계 바뀌는 값(위치, 페이지 테이블 기준 주소, 토큰 번호)은 반드시 GPU 메모리 속의 데이터여야 하고, 인자여서는 안 돼요.
  3. 고정 주소는 호출하는 쪽의 책임이다. 그래프가 가지는 것은 그래프이지 메모리가 아니에요. 녹화되는 코드가 쓰는 모든 버퍼는 녹화 전에 할당해 두어야 하고, 이후 다시 할당하면 안 돼요.

방어책이 두 가지 더 있어요. 녹화 결과가 노드 0개이면 바로 오류를 내요. 「아무것도 하지 않는 그래프」는 영원히 조용히 재생되어 오류도 출력도 내지 않기 때문이에요. 녹화 중에 CUDA 오류가 남아 있으면 이번 녹화를 포기하고, 망가진 그래프를 인스턴스화하지 않아요. 코드 사실

실행 경로 하나를 전체로 착각하지 마라

Strata에는 그래프가 여러 종류 함께 있어요. SessionGraphs는 층마다 한두 장(라우팅 전 구간, 전문가 병합 후 구간)이에요.[S13] 추측 디코딩의 검증 윈도우에 쓰는 다중 토큰 그래프(18장)도 있어요.[S08] 토큰 전체를 담는 TokenGraph도 있고, 구간별 시간을 재는 접두 그래프도 있어요. 어떤 헤더 파일에 「층마다 그래프 한 장」이라고 적혀 있다고 해서 엔진이 더 큰 그래프를 영원히 녹화하지 않는다고 단정하면 안 돼요. 소스에는 참조 경로, 디버그 경로, 빠른 경로, 장치 성능에 따라 고르는 구현이 흔히 함께 있어요. 호출 맥락과 활성화 조건도 결론의 일부예요. 컴파일러 수업에서 「같은 함수에 특수화 버전이 여럿 있다」고 배운 것과 같은 이야기예요.

검증: 주소, 수치, 상태 세 가지

그래프 최적화는 적어도 세 가지를 검증해야 해요. 매 단계 바뀌는 값이 매 라운드 올바르게 갱신되는지, 녹화된 주소가 모든 재생 동안 유효한지, 재생 후 상태가 그래프 없이 돌린 참조 경로와 같은지예요. 전형적인 생애 주기 함정이 있어요. 요청이 끝날 때 버퍼를 해제하고는 그래프 객체를 다음 요청에 쓰려고 남겨 두면, 다음 재생이 이미 해제된 메모리를 읽고 써요.

테스트도 오류를 「볼 수 있어야」 해요. 같은 프롬프트, 같은 온도로 한 번 더 돌리는 것으로는 인자 전환이 맞다는 걸 증명하지 못해요. 더 좋은 방법이 있어요. logits를 고정하고 연속된 두 요청을 각각 그리디와 높은 온도(또는 서로 다른 고정 난수)로 돌려요. 그래프 없는 참조 구현과 실제로 쓰인 인자와 결과를 비교해요. 두 번째 요청은 첫 번째와 다르면서 예측 가능한 분기를 타야 해요.

고급 GPU 과제에서는 프로파일러가 필요해요. 시작 시간, 커널 시간, 레지스터 사용량, 재생 시간을 기록하고, 끝에서 끝까지 A/B 비교로 국소 최적화가 임계 경로를 정말 줄였는지 판단해요. Strata의 주석에 반례가 있어요. 어떤 라운드에서 그래프 없는 모드로 잰 구간별 시간이, 같은 구간을 그래프로 돌린 실제 비용보다 4배 컸고, 하마터면 최적화 방향을 잘못 잡을 뻔했어요. 코드 사실
