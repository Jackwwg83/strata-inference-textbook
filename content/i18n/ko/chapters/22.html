본 적 있을 거예요

오픈소스 소프트웨어를 내려받을 때, 릴리스 페이지에 파일이 줄줄이 늘어서 있는 걸 본 적 있을 거예요. windows-x64, linux-x64, macos-arm64... 같은 프로그램인데 왜 이렇게 여러 개를 준비할까요?

Strata의 README는 첫머리에 이렇게 적어요. NVIDIA 또는 AMD 그래픽 카드, Windows 또는 Linux. 업스트림 보고[S01] 원리 문서는 더 분명하게 말해요. NVIDIA(CUDA)와 AMD(HIP) 그래픽 카드에서 같은 엔진이 돌아가고, 각자 한 번씩 컴파일할 뿐이라고요. [S02] 이 장은 두 질문에 답해요. 같은 소스가 어떻게 서로 다른 기계에서 도는 프로그램이 될까요? 그리고 「돌아간다」는 사실은 무엇을 얼마나 증명할까요?

한마디로: 칩마다 자기 명령어만 알아들어요. Strata는 소스를 한 벌만 쓰고, 컴파일 스위치, 조건부 컴파일, CUDA→HIP 「이름 변환표」로 NVIDIA용 엔진과 AMD용 엔진을 각각 만들어요. CPU 쪽은 시작할 때 CPU가 어떤 명령을 아는지 먼저 물은 뒤 AVX-512 커널이나 AVX2 커널을 골라요. 컴파일됨, 테스트 통과, 실제 카드에서 동작, 메인테이너 검증은 서로 다른 네 단계의 증거예요.

22.1 같은 레시피, 세 가지 주방

레시피를 써서 식당 세 곳에 보낸다고 상상해 보세요. 한 곳은 가스레인지, 한 곳은 인덕션, 한 곳은 오븐뿐이에요. 레시피에 적힌 「3분간 볶기」는 식당마다 자기 도구에 맞는 동작으로 바꿔야 해요.

프로그램도 마찬가지예요. 프로그래머가 쓰는 것은 소스 코드, 사람이 읽을 수 있는 글이에요. 칩이 실제로 실행하는 것은 기계어, 이진 명령의 나열이에요. 칩이 어떤 명령을 실행할 수 있는지, 명령마다 어떻게 인코딩하는지는 그 칩의 명령어 집합이 정해요. 「이 주방에 어떤 도구가 있는가」에 해당해요. 소스 코드를 어떤 명령어 집합의 기계어로 번역하는 일은 컴파일러가 해요.

그림의 sm_120, gfx1100은 그래픽 카드 아키텍처 번호예요. 주방의 모델명이라고 보면 돼요. Strata의 빌드 스크립트는 NVIDIA 카드의 컴퓨트 능력이 최소 7.5, 즉 RTX 20 시리즈 이상이어야 한다고 요구해요. AMD는 명시한 목록만 받아요. 목록에 없는 아키텍처는 바로 오류가 나요. 코드 사실 v0.1.39는 실험 경로를 두 개 더 열었어요. Pascal, Volta 구형 카드용 CUDA 12 엔진과, gfx906 전용 빌드예요. 22.3절에서 다뤄요. 업스트림 보고

컴파일러, 명령어 집합, 조건부 컴파일

명령어 집합은 하드웨어와 소프트웨어 사이의 계약이에요. 칩은 「이 명령들을 알아요」 하고 약속하고, 소프트웨어는 그 명령으로만 말할 수 있어요. 같은 계열의 칩은 새 명령을 계속 더해 가요. 예를 들어 x86 CPU 계열은 먼저 AVX2를 갖췄고, 나중에 더 넓은 AVX-512를 더했어요. 오래된 칩이 모르는 명령을 만나면 「잘못된 명령」 오류를 내고 프로그램이 죽어요.

컴파일러는 소스 코드를 기계어로 번역해요. C와 C++의 컴파일은 두 단계예요. 먼저 전처리기가 글을 가공하고, 그다음 컴파일러 본체가 번역해요. 전처리기가 하는 일은 세 가지예요. #include한 파일을 그대로 붙여 넣어요. #define으로 정의한 매크로를 이름으로 바꿔 쳐요. 「찾아 바꾸기」와 같아요. #if 조건에 따라 분기 하나만 남기고 나머지는 통째로 지워요. 이 마지막 수법이 조건부 컴파일이에요.

Strata가 AMD 그래픽 카드에서 「4바이트 내적」을 구현하는 방식이 바로 이래요. RDNA3, RDNA4 카드(v0.1.40부터는 RDNA3.5의 gfx1150, gfx1151도)는 sudot4 명령 하나를 써요. RDNA2에는 이 명령이 없어서 더 오래된 sdot4를 써요. RDNA1의 gfx1012에는 sdot4마저 없어서 짧은 어셈블리로 곱셈 4번과 3항 덧셈 2번을 이어 붙여 같은 결과를 만들어요. 그 밖의 경우(v0.1.40.2에서 새로 들어온 RDNA1 gfx1010, gfx1011과 RDNA3 내장 GPU gfx1103 포함)에는 바이트마다 곱해서 더하는 루프로 돌아가요. 네 길이 계산하는 정수는 똑같고, 속도만 달라요. 코드 사실 22.3절에서 직접 컴파일해 볼 거예요.

CS를 배운 분께: 《컴파일러》 수업은 어휘 분석, 구문 분석, 코드 생성이라는 주된 흐름을 가르쳐요. 전처리는 그 모든 것보다 앞서 일어나는 순수한 텍스트 가공이라서 문법을 몰라요. 그래서 매크로 치환이 잘못되면 오류 위치가 이상하게 나오는 일이 많아요. 컴파일러가 보는 것은 이미 치환이 끝난 코드이기 때문이에요.

22.2 CPU: 어떤 명령을 아는지 먼저 묻고, 그다음 커널을 골라요

10장에서 봤듯이, 그래픽 카드에 캐시되지 않은 전문가는 CPU가 RAM(메인 메모리)에서 그 자리에서 계산해요. 업스트림 문서는 이렇게 요약해요. 이 계산에는 AVX-512 또는 AVX2 커널을 쓰고, i-quant 형식 모델에는 ggml의 커널을 쓴다고요. 업스트림 보고[S02] 소스는 더 세분화해 놓았어요. i-quant 형식도 한 묶음에 토큰이 여러 개면 Strata가 직접 만든 다중 토큰 커널로 바꿔요. 코드 사실 여기서 커널은 아주 빠르게 돌도록 따로 쓴 핵심 계산 코드를 말해요.

AVX2와 AVX-512는 둘 다 SIMD 명령이에요. 명령 하나가 숫자 한 줄을 동시에 처리해요(13장에서 자세히 다뤄요). 차이는 그 한 줄의 너비예요. AVX2 레지스터는 256비트, AVX-512는 512비트예요. 그림 22-3을 보세요.

골치 아픈 점은 이거예요. 프로그램 전체를 AVX-512로 컴파일하면, 컴파일러가 어디에든 AVX-512 명령을 끼워 넣을 수 있어요. 그러면 오래된 CPU에서 프로그램이 죽어요. Strata의 빌드 스크립트는 일부 커널 소스 파일에만 AVX-512나 AVX2 컴파일 옵션을 붙여요(GCC에서는 -mavx512f 같은 인자, MSVC에서는 /arch:AVX512). 「CPU 탐지」를 맡은 파일에는 붙이지 않아요. 그래서 어떤 x86-64 CPU에서도 안전하게 돌아가요. 코드 사실

탐지는 CPUID로 해요. CPU에게 「자기소개」를 시키는 명령이고, 비트 한 줄을 돌려줘요. 비트마다 기능 하나를 뜻해요. Strata는 AVX-512의 하위 기능 다섯 가지(F, BW, VL, VNNI, VBMI)가 모두 있는지 확인하고, 운영체제가 스레드를 바꿀 때 이 큰 레지스터를 저장해 주는지도 확인해요. 하나라도 빠지면 AVX-512가 없는 것으로 쳐요. 코드 사실 그다음 아래 순서로 커널을 골라요.

22.3 GPU: CUDA 방식 하나로 NVIDIA 엔진과 AMD 엔진을 만들어요

CPU 쪽은 프로그램 파일 하나에 커널 두 벌을 넣어 두고 실행 시점에 골라요. GPU 쪽은 한 걸음 더 나가요. NVIDIA와 AMD 그래픽 카드는 명령이 완전히 다르고 프로그래밍 플랫폼까지 달라서, 회사마다 엔진을 따로 컴파일해야 해요.

CUDA와 HIP

CUDA는 NVIDIA의 GPU 프로그래밍 플랫폼이에요. C++ 확장 문법 한 벌, 런타임 함수 라이브러리 한 벌, 그리고 컴파일러 nvcc로 이루어져요. 프로그래머는 이것으로 GPU에서 병렬로 실행되는 함수를 쓰고, cudaMalloc, cudaMemcpy 같은 함수로 VRAM을 할당하고 데이터를 옮겨요. CUDA로는 NVIDIA 그래픽 카드용 기계어만 만들 수 있어요.

HIP는 AMD가 ROCm 플랫폼에서 내놓은 대응물이에요. 일부러 CUDA를 본떠 설계했어요. 함수 이름은 대부분 접두어 cuda를 hip으로 바꾼 것뿐이에요. 예를 들어 cudaMalloc은 hipMalloc에 대응하고, 의미도 거의 같아요. 그래서 CUDA 코드는 「이름만 바꾸면」 AMD 그래픽 카드에서도 컴파일되는 경우가 많아요. AMD는 자동으로 이름을 바꿔 주는 도구 HIPIFY도 제공해요.

이름을 바꿔도 남는 차이가 있어요. GPU는 스레드 한 무리를 묶어서 동시에 실행해요. NVIDIA는 이것을 warp, AMD는 wavefront(줄여서 wave)라고 불러요. NVIDIA는 한 묶음이 항상 32개 스레드예요. AMD의 옛 아키텍처는 64개이고, RDNA 시리즈는 32개일 수 있어요. 「한 묶음 32개」를 가정한 코드를 64개짜리 기계로 옮기면 틀려요. Strata의 HIP 백엔드는 wave32만 지원하고, 시작할 때 한 번 더 확인해요. 코드 사실 v0.1.39는 wave64인 gfx906을 위해 직접 켜야 하는 빌드를 하나 더 추가했어요. 이 빌드는 다른 호환 계층을 써서 CUDA의 warp 하나를 64스레드 wavefront의 절반에 대응시키고, HIP 백엔드와는 둘 중 하나만 고를 수 있어요. 업스트림 보고 스레드와 warp 같은 개념은 15장에서 자세히 다뤄요.

이 장과의 관계는 이래요. Strata는 도구로 소스를 고쳐 쓰지 않아요. 대신 「이름 변환표」 하나를 컴파일할 때 모든 소스 파일에 자동으로 끼워 넣어요. 바로 아래에서 그 방법을 볼게요.

  3. shim 안에는 #define cudaMalloc hipMalloc 꼴의 매크로가 91줄 있어요. 그중 몇 개는 HIP 버전이나 플랫폼에 따라 두 가지로 적혀 있고, 컴파일할 때마다 하나만 남아요. 또 다른 cublas_v2.h shim이 행렬 라이브러리 이름을 맡아요. 새 hipBLAS에는 17줄을 쓰고, 오래된 버전(0.x)에는 15줄을 따로 써서 더 낮은 수준의 rocBLAS 이름으로 바로 바꿔요. 전처리기가 치환하면 CUDA 이름이 HIP 이름으로 바뀌어요.

빌드 스크립트는 CUDA 스위치와 HIP 스위치를 동시에 켤 수 없게 막아요. 한 번의 빌드에는 백엔드 하나만 컴파일해요. 코드 사실

이름만 바꿔서는 부족해요. CUDA의 일부 GPU 내장 함수는 RDNA 그래픽 카드의 HIP에 기성품이 없어서, shim이 직접 구현해요. 예를 들어 4바이트 내적 __dp4a는 32비트 정수 두 개를 각각 부호 있는 바이트 4개로 쪼개서 짝끼리 곱한 뒤 누산기에 더해요. shim은 이것을 그래픽 카드 아키텍처에 따라 네 길로 나눠요(22.1절의 칼럼 참고). 또 warp 안에서 데이터를 맞바꾸는 __shfl_xor_sync도 있어요. shim은 먼저 「32개 레인이 모두 참여하는가」를 확인하고, 아니면 슬그머니 그 의미를 버리는 대신 바로 중단해요. 코드 사실

아래 시뮬레이터는 소스 세 줄을 서로 다른 대상 그래픽 카드에 넘겨요. 컴파일을 누르고 진행 바가 한 단계씩 나아가는 것을 보세요.

만들어진 엔진은 자기가 어떤 아키텍처용으로 컴파일됐는지 기억해요. 시작할 때 엔진은 그래픽 카드의 실제 아키텍처를 이 목록과 대조하고 wave32인지도 확인해요. 맞지 않으면 카드 이름과 목록을 함께 보여 주며 오류로 종료해요. 실행 중에 알 수 없는 「invalid device function」이 튀어나오기를 기다리지 않아요. 코드 사실

NVIDIA 쪽도 조건부 컴파일로 구형 카드를 챙겨요. __dp4a는 컴퓨트 능력 6.1부터 있어요. 6.0 구형 카드용으로 컴파일하면 #if가 PTX vmad 명령 4개로 바꿔 줘요. 각 명령은 두 피연산자에서 같은 위치의 바이트를 하나씩 꺼내 곱한 뒤 누산기에 더하고, 결과는 바이트마다 곱하는 방식과 비트까지 같아요. 이 길은 실험 스위치 STRATA_EXPERIMENTAL_SM60을 직접 켜야 하고 CUDA 12도 써야 해요. CUDA 13은 이 구형 카드용으로는 컴파일할 수 없기 때문이에요. 코드 사실 v0.1.40에서는 여기가 아직 바이트마다 곱하는 C 코드였어요. 업스트림은 새 방식을 옛 방식과 입력 약 10.7억 쌍으로 비교했고, 다른 결과는 하나도 없었어요. 따로 재면 새 방식이 P100에서 약 2.2배 빨라요. 업스트림 보고 정수 결과는 그대로이고 더 빨라졌을 뿐이에요. v0.1.39부터 업스트림은 CUDA 12.9로 컴파일한 이런 실험용 엔진도 배포해요. Pascal, Volta 구형 카드용이에요. 당시 관리자에게는 이런 카드가 없어서, 컴파일되는지와 단위 테스트가 통과하는지만 확인했어요. v0.1.40부터 관리자에게 P100(sm_60)이 한 장 생겼고, 양자화 3종에서 10/10 일치를 얻었어요. Volta는 여전히 실물 카드로 검증하지 못했어요. 업스트림 보고 그런데 빌드 스크립트의 오류 메시지에는 아직 「업스트림은 지원하지 않는다」고 적혀 있어요. 안내 문구는 코드보다 뒤처지기 일쑤예요. 또 다른 예로, CUDA 12.8로 RTX 50 시리즈용을 컴파일하면 빌드 스크립트가 경고를 내요. 이렇게 만든 엔진이 긴 프롬프트에서 죽었다는 사용자 보고가 있었기 때문이에요. 코드 사실 컴파일러 버전 자체도 변수라는 걸 알 수 있어요.

22.4 「컴파일된다」와 「지원한다」 사이의 거리

내 그래픽 카드 아키텍처가 목록에 있고 엔진도 컴파일됐다고 해 볼게요. 이것이 「지원」일까요? Strata의 빌드 스크립트가 아주 세밀한 답을 줘요. AMD 아키텍처를 세 단계로 나누고, CMake 설정 때 단계마다 태도가 달라요. 코드 사실

  • 메인테이너 검증: gfx1100(RX 7900 XT / XTX)과 gfx1201(RX 9070 시리즈, Radeon AI PRO R9700). 메인테이너가 실제 카드에서 돌려 봤어요.
  • 사용자 검증: gfx1101과 gfx1200. 카드 주인이 돌려 보고 알려 줬어요. 설정 때 안내 한 줄만 나와요.
  • 미검증: gfx1010, gfx1011, gfx1012, gfx1102, gfx1103, gfx1030, gfx1031, gfx1034, gfx1150, gfx1151, 모두 10종이에요. 이들은 컴파일은 되고, 설정 때 경고를 내며 사용자에게 결과를 알려 달라고 해요. 코드 사실 gfx1102는 자체 테스트를 통과했고, 사용자 한 명이 RX 7600 XT로 전체 모델을 돌렸어요. 요청 146개, 컨텍스트는 최대 51K였어요. 하지만 보고가 한 건뿐이라 빌드 스크립트는 여전히 미검증으로 분류해요. 스크립트 주석에는 「모델을 돌렸다는 보고는 아직 없다」는 말까지 남아 있어서, 문서보다 뒤처져 있어요. gfx1030은 커뮤니티 머신 한 대에서 동작했지만 메인테이너가 직접 검증하지는 않았어요. gfx1012(RX 5500 XT, RDNA1)와 gfx1031(RX 6700 XT)은 v0.1.39에서 새로 들어왔고, 둘 다 사용자가 자기 카드에서 돌려 봤어요. gfx1034와 gfx1151은 v0.1.40에서 새로 들어왔어요. gfx1151은 Ryzen AI Max(Strix Halo) 칩 안의 Radeon 8060S / 8050S 내장 GPU(RDNA3.5)예요. 업스트림은 실험적이라고 표시해요. 릴리스 노트에는 Linux에서 잰 결과가 있지만, 빌드 스크립트는 여전히 미검증으로 분류하고, Windows 실물 머신에서는 아직 돌려 보지 않았어요. v0.1.40.2에서 4종이 더 들어왔어요. RDNA1의 gfx1010(RX 5700 XT, 모델을 돌린 사람이 있어요)과 gfx1011(컴파일만 확인됐고 실물 카드에서 돌린 사람은 아직 없어요), 그리고 내장 GPU 두 종인 gfx1103(Radeon 780M, 이식 가능한 커널만 써요)과 gfx1150(Radeon 890M, 커뮤니티 머신 한 대에서 동작했어요)이에요. 업스트림 보고

Intel 그래픽 카드는 세 번째 길을 가요. 위의 CUDA→HIP shim을 거치지 않아요. 저장소의 sycl/ 디렉터리가 Strata 엔진을 SYCL(Intel oneAPI가 쓰는 C++ 프로그래밍 모델)로 옮겨 놓았어요. 이것은 독립된 CMake 프로젝트예요. 이 프로젝트를 켜면 나머지 CUDA / HIP 설정은 하나도 실행되지 않아요. 지금은 Linux에서 소스로만 빌드할 수 있어요. 코드 사실 이 「지원」 표현 자체가 증거 등급의 한 예예요. v0.1.40.2 릴리스 노트는 Intel Arc를 「공식 지원」한다고 쓰고, 실제로 테스트한 카드 두 장(Arc Pro B70과 Arc A750)을 나열해요. 같은 버전의 README는 여전히 Intel Arc를 「실험적, 커뮤니티 구성원이 자기 머신에서 작성하고 테스트함」 칸에 놓아요. INTEL_ARC.md의 제목도 아직 「실험적」이라고 쓰고, 본문은 메인테이너에게 Intel 그래픽 카드가 없다고 말해요. 업스트림 보고 글이 셋인데 말이 셋이에요. 지원 선언을 읽을 때는 그 뒤에 어느 등급의 증거가 있는지 물어야 해요.

두 번째 함정은 수치예요. 그림 22-5의 dp4a는 정수 연산이라 어느 길이든 비트까지 같아요. 부동소수점은 달라요. 덧셈 순서가 바뀌면 마지막 몇 자리가 달라질 수 있어요(4장에서 부동소수점 반올림을 다뤘어요). Strata의 AMD 문서는 두 백엔드가 비트까지 같은 답을 낸다고 약속하지 않는다고 분명히 밝혀요. 업스트림 보고 같은 머신에서도 그래요. IQ 계열 모델을 쓸 때 CPU는 토큰 하나를 계산할 때는 ggml의 내적을, 묶음으로 계산할 때는 Strata의 다중 토큰 커널을 써요. 둘은 반올림이 조금 달라요. 한 묶음에 토큰이 몇 개인지는 다시 드래프트에 따라 달라지고요. 그래서 온도가 0이어도 같은 프롬프트에서 똑같이 그럴듯한 다른 답이 나올 수 있어요. 엔진 0.1.30부터는 STRATA_IQ_MT_MIN=1을 설정해서 이 차이를 없앨 수 있어요. 대가로 업스트림은 Ryzen 7600(AVX-512)에서 IQ3_S 디코드가 1~3% 느려진다고 측정했어요. 업스트림 보고[S03]

그래서 빌드 설정은 실험 조건이고, 하드웨어처럼 보고서에 적어야 해요. 같은 커밋이라도 STRATA_PORTABLE을 켰는지에 따라 ggml의 CPU 부분이 「AVX2를 가진 아무 CPU」 기준으로 컴파일될지 「이 머신의 CPU」 기준으로 컴파일될지 달라져요. 환경 변수 하나만 바꿔도 계산 경로가 바뀌어요. 코드 사실 README의 속도 표도 보세요. Q2_0 모델은 RTX 5070 머신에서 초당 토큰 94개를, RX 9070 XT 머신에서 초당 60개를 써요. 업스트림 보고[S01] 표 아래의 설명은 NVIDIA 머신의 조건만 적어 놓았어요. Q2_0은 엔진 0.1.36으로, 나머지 행은 0.1.26으로 쟀고, 답 쓰기는 4K로, 문제 읽기는 32K로 쟀어요. AMD 머신은 엔진 버전을 적지 않았어요. v0.1.39의 릴리스 노트는 이번에 이 표를 다시 측정하지 않았다고도 따로 밝혔어요. 두 머신의 CPU도 달라요. 한쪽은 AVX-512가 있는 Ryzen 5 7600이고, 다른 쪽은 AVX2만 있는 Ryzen 9 3900X(Zen 2)예요. 이 숫자는 「두 머신 모두 돌아간다」는 것을 보여 줄 뿐이에요. NVIDIA와 AMD 중 어느 쪽이 빠른지 비교하는 데 쓸 수는 없어요.

검증해야 할 조합은 얼마나 될까요? 대충 세어 봐요. 그림 22-7을 보세요. 교육용 추정

계산식: GPU 아키텍처 12종(NVIDIA는 빌드 스크립트가 나열한 RTX 20/30/40/50 네 세대, AMD는 Windows 판 엔진에 들어간 8종), CPU 경로 3개(AVX-512, AVX2, ggml), 운영체제 2종, README에 나열된 모델 팩 5종. 12 × 3 × 2 × 5 = 360. 아무도 전부 테스트할 수 없어요. 현실적인 방법은 층을 나누는 거예요. 순수 수학의 작은 표본이 알고리즘을 덮고, 형식 테스트가 양자화 디코딩을 덮어요. 백엔드마다 대표 커널을 골라 비교 테스트를 하고, 엔드투엔드는 가장 중요한 조합 몇 가지만 덮어요.

22.5 직접 해 보기: 소스 한 줄을 두 백엔드에 넘겨 보기

이 장에는 따로 떼어 놓은 상호작용 실험이 없어요. 시뮬레이터 두 개가 곧 실험대예요. 이 순서로 해 보세요.

  1. 「소스 하나, 백엔드 둘」에서 RTX 50, RX 7900, RX 6900을 차례로 컴파일해 보세요. 전처리 후의 세 줄을 비교해요. 어떤 이름이 바뀌었는지, dp4a가 어느 분기에 들어갔는지 보세요. 예제 결과가 늘 95인지도 확인하세요.
  2. 「목록에 없는 아키텍처」를 골라 보세요. CMake가 왜 첫 단계에서 거부하는 쪽을 택하는지 느껴 보세요.
  3. 「CPU 커널 선택기」에서 CPU와 모델 팩을 고정하고 환경 변수와 토큰 수만 바꿔 보세요. 같은 머신에서 서로 다른 계산 경로가 몇 개 나오는지 세어 보세요.

C 컴파일러가 있는 분은 작은 실험을 하나 더 해 보세요. 스칼라 내적 함수를 하나 쓰고, 숫자 8개씩 묶어서 누적하는 버전을 하나 더 써요. 같은 무작위 부동소수점 수열로 두 결과와 실행 시간을 비교해요. 마지막 몇 자리가 다르게 나오는 걸 볼 수 있어요. 먼저 논리가 맞는지 확인하고 나서 성능을 따지세요. 배열이 너무 작으면 측정한 속도가 진짜 SIMD 커널을 대표하지 못해요.

22.6 경계: 라이선스, 모델, 그리고 이 교재 자신

「이식성」에는 또 다른 뜻이 있어요. 코드, 모델, 문서를 각각 누가 가져다 어떻게 쓸 수 있느냐예요. Strata 저장소의 코드는 MIT 라이선스예요. 코드 사실[S19] 저장소의 일부는 라이선스가 따로 있어요. third_party/ggml은 llama.cpp / ggml(MIT)에서 왔고, 웹 앱이 쓰는 글꼴은 SIL 오픈 폰트 라이선스예요. 모델 파일은 저장소에 없고, 모델마다 자기 라이선스가 적용돼요. 업스트림 보고[S02]

이 교재 자체는 정적 웹사이트예요. HTML, CSS, JavaScript로 되어 있고 추론 엔진은 들어 있지 않으며 모델 가중치도 내려받지 않아요. 아무 웹 호스팅 서비스에 올려도 강좌를 공개하는 것일 뿐, 그 서버에서 Strata를 실행하는 것은 아니에요. 교재의 상호작용 그림은 모두 교육용 시뮬레이션이에요. Strata 소스의 판단 로직을 재현했을 뿐 Strata의 커널은 아니고, 실제 기계의 성능을 예측하지도 않아요.

업스트림 코드를 인용할 때 이 책은 고정된 커밋 번호를 기록해요. 업스트림의 글꼴이나 모델을 다시 묶어 배포하지 않아요. 또 이 책은 독립적으로 쓴 교재이며, 원 프로젝트나 모델 제작사의 공식 인증을 받지 않았다고 밝혀 둬요.

이 세 가지를 기억하기

  1. 칩은 자기 명령어 집합만 알아요. 같은 소스라도 대상마다 한 번씩 컴파일해야 해요. 조건부 컴파일은 소스 한 벌에서 컴파일할 때마다 대상에 맞는 분기만 남겨 줘요.
  2. Strata는 CPU에서는 런타임 디스패치를 해요. CPUID로 AVX-512와 AVX2가 있는지 먼저 묻고 커널을 골라요. GPU에서는 컴파일 시점 디스패치를 해요. CUDA→HIP 이름 변환표와 직접 쓴 내장 함수 몇 개로 NVIDIA용과 AMD용 엔진을 각각 만들어요.
  3. 컴파일됨, 테스트 통과, 실제 카드에서 동작, 메인테이너 검증은 서로 다른 네 단계의 증거예요. 부동소수점 결과는 백엔드가 달라지면 비트까지 같다고 보장되지 않아요. 빌드 설정과 환경 변수도 실험 조건으로 기록해야 해요.

흔한 오해: 「내 그래픽 카드에서 코드가 컴파일되면, 내 그래픽 카드를 지원한다는 뜻이다.」

컴파일이 통과했다는 것은 컴파일러가 이 코드를 알아봤다는 뜻일 뿐이에요. Strata의 빌드 스크립트에 이미 반례가 있어요. gfx1011은 컴파일되고 업스트림 문서에도 컴파일 오류가 0개라고 적혀 있지만, 실물 카드에서 돌린 사람이 아직 없어서 설정 때 「미검증」 경고를 내요. gfx1102는 더 멀리 갔어요. 자체 테스트를 통과했고, 사용자 한 명이 전체 모델도 돌렸어요. 그래도 「미검증」으로 남아 있어요. 보고가 한 건뿐이고 메인테이너가 재현하지 못했기 때문이에요. 진짜 지원이란 실제 카드에서 실제 모델을 돌려 결과가 맞고, 누군가 그것을 재현할 수 있다는 뜻이에요.

한 걸음 더: 컴파일 시점과 실행 시점의 역할 분담, shim의 한계, 지원 선언

AVX-512 스위치를 파일 하나에만 붙이는 이유

빌드 스크립트의 주석이 이유를 설명해요. /arch:AVX512로 컴파일한 소스 파일에서는 컴파일러가 어디서든 AVX-512 명령을 쓸 수 있어요. 「대비책」이라고 생각한 스칼라 코드도 예외가 아니에요. 스칼라 대비책과 AVX-512 커널을 같은 파일에 두면 대비책은 더 이상 대비책이 아니고, 오래된 CPU에서 똑같이 죽어요. 그래서 Strata는 커널 파일에만 스위치를 붙여요. CPU를 탐지하는 함수는 스위치가 없는 파일에 두어서, 「물어보기」 단계가 어떤 x86-64 CPU에서도 안전하도록 해요. 코드 사실

탐지 자체에도 조건부 컴파일을 써요. 같은 CPUID 코드를 MSVC 컴파일러는 __cpuidex와 _xgetbv로, GCC/Clang은 __cpuid_count와 인라인 어셈블리 xgetbv로 써요. XCR0 레지스터를 확인하는 것은 운영체제가 스레드를 바꿀 때 AVX-512의 큰 레지스터를 저장해 주는지 보기 위해서예요. CPU가 지원해도 운영체제가 저장해 주지 않으면 역시 쓸 수 없어요. 코드 사실

shim의 한계: 의미를 슬그머니 바꾸느니 중단해요

CUDA의 warp 교환 함수에는 「어떤 레인이 참여하는가」를 나타내는 마스크 인자가 있어요. HIP의 대응 함수에는 이 인자가 없어요. shim은 이렇게 해요. 현재 커널은 전체 마스크만 쓰니까 전체 마스크가 아닌 호출을 만나면 바로 중단하고(__builtin_trap), 마스크를 버리고 계속 계산하지는 않아요. __nanosleep은 CUDA에서는 클럭 사이클 수로 세는데, AMD의 대기 명령은 0~15만 받아요. shim은 그냥 최솟값 1로 통일해요. 여기서는 「잠깐 기다려 줘」라는 힌트로만 쓰기 때문이에요. 코드 사실

dp4a의 네 길에도 각각 사연이 있어요. RDNA3/RDNA4의 sudot4 명령은 두 피연산자가 부호 있는지를 따로 지정할 수 있어요. shim은 둘 다 부호 있음으로 표시해야 CUDA의 __dp4a와 의미가 같아져요. RDNA2의 sdot4는 원래 「부호 있음 × 부호 있음, 2³²으로 나눈 나머지로 누적」이라서 의미가 같아요. RDNA1의 어셈블리는 바이트마다 부호를 확장한 뒤 곱하고(v_mul_i32_i24), v_add3_u32로 곱 두 개씩을 누산기에 더해요. 32비트 부호 없는 덧셈은 그 자체로 2³²으로 나눈 나머지예요. 이 코드는 llama.cpp에서 가져와 고친 것이에요. 컴파일 스위치 STRATA_GFX1012_PORTABLE_DOT를 켜면 gfx1012가 이식 가능한 루프를 대신 쓰므로 견주어 보기 좋아요. 이식 가능한 루프는 부호 없는 32비트 정수로 누적한 뒤 부호 있는 값으로 해석하는데, 결과는 역시 2³²으로 나눈 나머지예요. 이 장의 시뮬레이터 테스트 파일은 RDNA1 어셈블리, 이식 가능한 루프, NVIDIA 구형 카드의 vmad 방식이 오버플로 경계에서도 기준값과 비트까지 같음을 하나씩 확인해요.

이름이 형식을 정하지 않아요: 타입으로 디스패치해요

같은 텐서 이름도 층마다 다른 양자화 형식을 쓸 수 있어요. layer.cpp의 주석에 교훈이 기록돼 있어요. 초기 코드는 「이름이 형식을 정한다」고 가정했어요. 예를 들어 attn_qkv는 항상 어떤 K-quant라고요. 실제 모델 팩에서는 GDN 36개 층의 attn_qkv가 IQ4_XS, Q3_K, Q2_0, Q4_K 네 가지로 섞여 있었어요. 그래서 규칙을 타입별 디스패치로 바꿨어요. 2비트 인코딩은 Q8_0 활성값으로, 나머지 양자화 형식은 Q8_K로 보내요. 잘못 쓰면 행렬-벡터 곱의 오차가 0.6%~1.4%예요. 눈에 띄게 망가진 벡터가 아니라 「그럴듯해 보이는」 벡터가 나오기 때문에 가장 찾기 어려워요. 코드 사실[S14]

의존성도 못 박아야 해요

Strata의 CPU 전문가는 ggml-cpu의 내적을 써요. 빌드할 때 llama.cpp 저장소에서 ggml을 가져와요. 가져오는 것은 「최신 버전」이 아니라 third_party/ggml/VERSION.txt에 못 박아 둔 커밋 번호예요. 코드 사실 이유는 이 책이 Strata의 커밋 번호를 고정하는 것과 같아요. 의존성이 바뀌면 수치 경로도 바뀔 수 있어요.

최소한의 지원 선언

새 백엔드의 지원 선언을 쓸 때는 최소한 이것을 분명히 적어야 해요.

  • 소스 커밋 번호, 컴파일러와 버전, 대상 아키텍처 목록, 모든 컴파일 스위치, 의존 라이브러리 버전, 런타임 환경 변수.
  • 테스트한 장치, 드라이버, 모델 팩, 양자화 형식, KV 형식, 프리필과 디코드 두 경로, 컨텍스트 길이 범위.
  • 증거를 단계별로 나눠서 적기: 컴파일 통과, 자체 테스트 통과, 텐서 수준 비교(참조 구현과의 오차), 엔드투엔드 품질, 안정성, 성능.
  • 테스트하지 않은 조합은 분명히 「미테스트」로 적고, 「전면 지원」이라고 쓰지 않기.

같은 커밋에서 나온 바이너리 두 개라도 컴파일 스위치가 다르면 서로 다른 코드 경로를 탈 수 있어요. 시작 로그는 실제로 어떤 백엔드와 CPU 경로를 썼는지, 되돌아간 것은 없는지 밝혀야 해요. Strata도 AVX-512가 없는 CPU에서 시작할 때 AVX2로 갔는지 ggml로 갔는지 출력해요. 코드 사실 사용자가 파일 이름으로 짐작하게 해서는 안 돼요.

벡터화의 꼬리

벡터 길이가 레인 수로 나누어떨어지지 않으면, 남는 「꼬리」는 마스크나 별도의 스칼라 경로로 처리해야 해요. 편하자고 몇 바이트를 더 읽으면 다음 전문가의 데이터까지 읽을 수 있어요. 꼭 죽는 것은 아니지만 결과는 틀려요. Strata는 네이티브 전문가를 불러올 때 전문가 크기가 형식 블록 크기의 정수배인지 먼저 확인하고, 아니면 거부해요. 코드 사실
