눈치챘을 수도 있어요

채팅 웹페이지에서는 답변이 한 글자씩 톡톡 떠올라요. 그런데 웹페이지를 건너뛰고 명령줄로 내 컴퓨터의 Strata API를 직접 호출하면 전혀 다른 장면이 보여요. data: {…} 줄이 줄줄이 이어지고, 줄 사이마다 빈 줄이 하나씩 끼어 있고, 마지막 줄은 data: [DONE]이에요.

이 줄들을 SSE(Server-Sent Events, 서버 전송 이벤트)라고 불러요. 서버를 떠날 때는 바이트 한 줄기인데, 내 손에 닿기 전에 네트워크가 크기가 제각각인 덩어리로 마구 잘라 버려요. 한자 한 글자가 반으로 잘릴 수도 있고, 메시지 하나가 두 번에 나눠 도착할 수도 있어요. 이 장은 이 조각들을 다시 온전하고 깨지지 않는 한 문장으로 맞추는 방법을 설명해요.

한마디로: 모델이 내놓은 토큰이 내 화면의 글자가 되기까지 문이 세 개 있어요. 바이트를 글자로 잇기(UTF-8), 글자를 이벤트로 자르기(SSE의 빈 줄), 이벤트를 구조로 해석하기(JSON)예요. 문마다 먼저 다 모은 뒤에 처리해요.

23.1 모델과 내 앱 사이에는 서비스 계층이 있어요

추론 엔진은 토큰 번호만 알아요. 번호 한 줄을 주면 새 번호를 하나씩 내놓아요. 그런데 내 앱이 쓰는 말은 달라요. 앱은 JSON 형식의 채팅 메시지를 보내고, 글이 조각조각 돌아오기를 기대해요. 그 사이에서 통역을 맡는 것이 서비스 계층이에요. 그림 23-1이 Strata의 서비스 계층이에요.

23.2 답변을 쓰는 중에 보낼 수 있는 이유

보통의 웹 요청은 한 번 묻고 한 번 답해요. 브라우저가 요청을 보내면 서버는 답변 전체를 준비해서 한 번에 돌려줘요. 대형 언어 모델에서는 첫 글자를 보기까지 수십 초를 기다려야 한다는 뜻이에요. 스트리밍 응답은 방식을 바꿔요. 같은 답변을 여러 작은 조각으로 나눠서, 한 조각이 써지는 대로 보내요. 그림 23-2가 두 방식을 비교해요.

HTTP와 스트리밍 전송(SSE)

HTTP는 브라우저와 서버가 대화하는 규칙이에요. 대화 한 번은 두 반쪽으로 나뉘어요. 클라이언트가 요청을 보내고(어느 경로에 접근할지, 어떤 데이터를 실을지), 서버가 응답을 돌려줘요(상태 코드 하나, 예를 들어 200은 성공, 400은 요청에 문제가 있음, 401은 인증 실패. 거기에 헤더와 본문이 붙어요). 헤더의 Content-Type은 본문이 어떤 형식인지 상대에게 알려 줘요.

보통의 응답은 본문을 한 번에 다 써요. SSE는 응답의 Content-Type을 text/event-stream으로 두고, 연결을 닫지 않은 채 서버가 생각날 때마다 한 조각씩 써요. 조각 하나를 이벤트라고 해요. 형식은 아주 소박해요.

  • 이벤트 하나는 여러 줄로 이루어지고, data:로 시작하는 줄에 데이터를 담아요.
  • 빈 줄 하나가 이벤트의 끝을 뜻해요.
  • 콜론으로 시작하는 줄은 주석이고, 클라이언트는 그냥 무시해요.
  • 선택 사항인 event: 줄로 이벤트에 이름을 붙일 수 있어요.

예를 들어 서버가 data: 你好, 줄바꿈, 빈 줄 하나를 쓰면, 클라이언트는 내용이 你好(「안녕하세요」)인 이벤트 하나를 받아요. 규격은 이런 것도 요구해요. 이벤트 스트림은 반드시 UTF-8로 인코딩해야 해요. 줄바꿈은 LF, CR, CRLF 중 아무거나 될 수 있어요. 같은 이벤트 안의 여러 data 줄은 줄바꿈으로 이어 붙여요. 스트림이 이벤트 중간에서 끊기면 그 반쪽 이벤트는 버려야 하고, 완전한 것처럼 내보내면 안 돼요. [R05]

Strata와의 관계: /v1/chat/completions에 "stream": true를 붙이면 답변이 SSE 형태로 돌아와요. 안 붙이면 생성이 끝날 때까지 기다렸다가 JSON 하나로 한 번에 돌아와요.

더 읽을거리: MDN: HTTP 개요 · MDN: 서버 전송 이벤트 사용하기 · HTML 표준: Server-sent events · 위키백과: HTTP

Strata가 SSE를 쓰는 코드는 아주 짧아요. 먼저 상태 코드 200과 함께 Content-Type: text/event-stream, Cache-Control: no-cache 헤더를 보내고, X-Accel-Buffering: no도 더해요. nginx 같은 리버스 프록시에게 모아 두지 말고 이벤트가 오는 대로 바로 전달해 달라고 부탁하는 헤더예요. 코드 사실 그다음 답변 한 조각마다 data: 뒤에 JSON 한 조각, 그리고 빈 줄 하나를 써요. 모든 게 끝나면 data: [DONE]을 써요. 그림 23-3이 이 바이트 줄기를 풀어서 보여 줘요.

가운데 있는 : keep-alive에 주목하세요. 아주 긴 질문을 읽는 동안에는 엔진이 몇 분 동안 토큰을 하나도 내놓지 않을 수 있어요. 그동안 Strata는 10초마다 「하트비트」를 만들고, HTTP 계층이 이것을 SSE 주석으로 써요. 코드 사실 클라이언트는 주석을 무시하지만 바이트가 들어오는 것을 보고 연결이 끊겼다고 생각하지 않아요. 서버도 쓰는 김에 상대가 이미 떠났는지 알 수 있어요(24장에서 자세히 다뤄요). v0.1.39의 Responses 인터페이스는 한 걸음 더 나가요. Codex CLI는 주석을 보지 않고 진짜 이벤트만 「아직 일하는 중」으로 치기 때문에, 긴 질문을 읽는 동안 서버가 15초마다 response.in_progress 이벤트를 따로 보내요. 코드 사실

23.3 한자 한 글자, 바이트 세 개

네트워크는 바이트만 알고 글자는 몰라요. 단순화한 이벤트 data: {"delta":"你好"}를 예로 들어 볼게요. 끝의 빈 줄까지 합치면 선 위에서 26바이트이고, 그중 你와 好가 각각 3바이트예요. 문제는 이거예요. TCP 연결이 프로그램에 한 번에 넘겨주는 「한 덩어리」가 얼마나 큰지는 네트워크와 운영체제가 정하고, 글자의 경계와는 아무 상관이 없어요. 한자 한 글자의 3바이트 중 앞 1바이트는 이번 덩어리에, 뒤 2바이트는 다음 덩어리에 들어갈 수 있어요.

UTF-8: 글자 하나가 몇 바이트일까

컴퓨터 안의 모든 문자에는 번호가 있어요. 이것을 코드 포인트라고 해요. 예를 들어 한자 中은 U+4E2D예요. UTF-8은 코드 포인트를 바이트로 쓰는 규칙이에요. 영문자처럼 흔한 문자는 1바이트로 옛날 ASCII와 똑같고, 대부분의 한자와 한글은 3바이트, 이모지는 4바이트예요.

영리한 점은 모든 바이트가 「자기 신분」을 갖고 있다는 거예요. 그림 23-4를 보세요. 첫 바이트의 앞부분에 1이 몇 개 있는지가 그 문자의 바이트 수예요. 뒤따르는 바이트는 모두 10으로 시작하고, 연속 바이트라고 해요. 그래서 디코더가 E4(이진수 1110 0100)를 읽으면 뒤에 연속 바이트 2개가 와야 한다는 것을 알아요. 이때 덩어리가 이미 끝났다면, 올바른 처리는 E4를 일단 붙잡아 두고 다음 덩어리가 오면 이어 붙이는 거예요.

Python의 codecs.getincrementaldecoder, 브라우저의 TextDecoder(stream: true 옵션 포함)가 모두 이런 점진적 디코더예요. 반대로 덩어리마다 따로 디코딩하면 반쪽짜리 글자는 대체 문자 �가 되고, 다시는 이어 붙일 수 없어요.

더 읽을거리: 위키백과: UTF-8 · MDN: TextDecoder (영문) · Python 문서: codecs · RFC 3629: UTF-8

Strata는 이 문제를 더 앞단에서 이미 처리해야 해요. 모델의 토큰 하나가 온전한 글자라는 보장이 없기 때문이에요. serve/server.py의 Detokenizer는 토큰마다 바이트를 점진적 UTF-8 디코더에 넣어요. 온전한 글자는 바로 내보내고, 토큰에 걸쳐 잘린 반쪽 글자는 붙잡아 두었다가 뒤의 토큰이 채워 주면 내보내요. 코드 사실 코드 주석에는 계산도 적혀 있어요. 옛 방식은 토큰이 하나 올 때마다 지금까지 생성된 모든 번호를 처음부터 다시 디코딩했어요. 그래서 답변이 8K 토큰에 이르면 토큰마다 2밀리초, 16K에서는 4밀리초가 더 들었어요. 점진적 디코딩은 토큰당 비용이 일정해요.

서버가 바이트를 내보낸 뒤에는 클라이언트가 같은 문제를 다시 풀어야 해요. 게다가 한 겹이 더 있어요. 이벤트도 잘려요. 아래 슬라이서는 126바이트짜리 SSE 스트림을 무작위로 잘라서 클라이언트 두 개가 동시에 받게 해요.

몇 번 해 보면 알게 돼요. 부주의한 클라이언트는 글자만 잃는 게 아니에요. 잘린 이벤트를 나쁜 데이터로 보고 버리기도 해요. 틀리는 모양이 매번 다르고, 이렇게 있다 없다 하는 버그가 가장 찾기 어려워요.

23.4 JSON: 이벤트에 담기는 것은 구조예요

SSE는 이벤트를 잘라 내는 일만 해요. 이벤트 안에 무엇이 담기는지는 상관하지 않아요. Strata는 data: 뒤에 JSON 한 조각을 넣어요.

JSON: 사람도 프로그램도 읽을 수 있는 데이터 형식

JSON은 아주 적은 규칙으로 구조화된 데이터를 나타내요. 중괄호 {}는 「이름: 값」 묶음, 대괄호 []는 목록이에요. 값은 문자열, 숫자, true/false, null이거나 다시 한 겹 중첩될 수 있어요. 예를 들어 {"delta":{"content":"你好"}}는 delta 안의 content가 你好라는 뜻이에요.

JSON을 파싱하려면 꼭 지켜야 할 조건이 하나 있어요. 텍스트가 완전해야 해요. 닫는 괄호 하나, 따옴표 반쪽만 빠져도 파서는 오류를 내요. 먼저 빈 줄로 완전한 이벤트를 잘라 낸 뒤에 파싱해야 하는 이유가 이거예요.

JSON 문자열 안의 비ASCII 문자는 쓰는 방법이 두 가지예요. UTF-8 바이트로 그대로 쓰거나, \u4e2d 같은 이스케이프로 쓰는 거예요. 두 방법의 뜻은 같고 바이트 수가 달라요. 그림 23-6을 보세요.

더 읽을거리: 위키백과: JSON · MDN: JSON · Python 문서: json (ensure_ascii 포함) · RFC 8259

Strata는 스트리밍 이벤트를 쓸 때 json.dumps(c, ensure_ascii=False)를 불러서 중국어를 UTF-8 그대로 내보내요. 코드 사실 이스케이프 방식으로 바꾸면 선 위에는 ASCII 바이트만 흐르니까 「반쪽 한자」는 더 생기지 않아요. 하지만 중국어의 바이트 수가 두 배가 되고, SSE 규격은 원래 UTF-8 디코딩을 요구하며, 이벤트가 잘리는 문제도 그대로 남아요. 그래서 올바른 방향은 이스케이프로 피하는 게 아니라, 클라이언트가 성실하게 점진적 디코딩을 하는 거예요.

세 문을 이어 놓으면 순서가 바뀌면 안 돼요.

  1. 바이트 → 글자: 점진적 UTF-8 디코딩. 불완전한 바이트는 붙잡아 둬요.
  2. 글자 → 이벤트: 버퍼에 모으고, 빈 줄을 만나야 완전한 이벤트 하나를 잘라 내요. 주석은 버려요.
  3. 이벤트 → 구조: 완전한 data를 JSON으로 파싱해서 글자를 꺼내요.

CS를 배운 분께: 《컴파일러》에서 배운 「문자 스트림 → 어휘 분석 → 구문 분석」 파이프라인과 같은 발상이에요. 각 층은 앞 층이 완전한 단위를 내놓은 뒤에야 일하고, TCP는 바이트의 순서만 보장할 뿐 그보다 높은 층의 어떤 단위도 완전하다고 보장하지 않아요.

23.5 모델의 출력도 「다 모은 뒤 보내야」 해요

같은 골칫거리가 서버 안에서 한 번 더 나타나요. 이 모델은 먼저 「생각」하고 나서 답해요. 생각은 <think>와 </think> 사이에 쓰여요. 도구를 호출해야 할 때는 <tool_call><function=이름><parameter=인자>값</parameter>… 같은 태그를 써요. 이 태그들은 프로그램이 보라고 있는 거라서 내 화면에 나타나면 안 돼요.

문제는 태그도 잘릴 수 있다는 거예요. 이번 단계에서 </th가 나오고, 다음 단계에서야 ink>가 나와요. frontend.py의 OutputParser가 바로 이 일을 맡아요. 잘린 태그는 붙잡아 두었다가 완성되면 처리해요. 그래서 클라이언트는 <tool_이나 </thi 같은 반쪽 태그를 절대 보지 않아요. 코드 사실[S16]

실제 OutputParser는 이 컴포넌트보다 두 가지를 더 해요. 첫째, 도구 호출의 진행 상황을 쓰는 도중에 알려 줘요. 도구 이름이 나오자마자 시작 이벤트를 보내고, 인자도 조각조각 알려 줘서 모델이 큰 파일을 쓰는 몇 분 동안 클라이언트가 멍하니 기다리지 않게 해요. 코드 사실 둘째, 태그 앞뒤의 줄바꿈도 조심해서 처리해서, 스트리밍 출력과 한 번에 내는 출력의 결과가 완전히 같도록 해요.

도구 호출에는 보안 문제도 걸려 있어요. 모델이 함수 이름을 썼다고 해서 시스템이 그것을 실행해도 된다는 뜻은 아니에요. 모델의 출력은 신뢰할 수 없는 입력이라서, 실행 전에 인자와 권한을 검사해야 해요. Strata는 명시적으로 요구한 요청("strata_mcp": true를 붙인 것)에만 MCP 도구를 제공하고, 다른 클라이언트가 보는 API는 예전과 똑같아요. [S15] 24장에서 「누가 모델에게 무엇을 시킬 권한이 있는가」를 이어서 다뤄요.

23.6 직접 해 보기: 같은 스트림을 아무 크기로나 잘라 보기

이 장의 인터랙티브 실험 「바이트 조각은 이벤트가 아니에요」를 열어 보세요. 중국어가 든 SSE 스트림을 1~32바이트의 고정 크기로 잘라서, 올바른 세 문으로 복원해요. 이 순서로 세 가지를 해 보세요.

  1. 1바이트부터 32바이트까지 차례로 해 보세요. 어떻게 자르든 복원된 글자는 한 글자도 다르지 않아야 해요. 하나라도 다르면 파서에 버그가 있다는 뜻이에요.
  2. CRLF 줄바꿈을 켜 보세요. SSE는 줄바꿈 세 가지를 허용하고, 파서는 전부 알아봐야 해요.
  3. 「미완성」 버퍼를 눈여겨보세요. 스트림이 이벤트 중간에서 끊기면 그 반쪽 이벤트는 그대로 두거나 오류로 처리해야 해요. 이미 완성된 척하면 안 돼요.

그다음 이 장의 인터랙티브 그림 두 개로 돌아가서, 조각 크기를 1바이트와 64바이트로 맞춰 각각 돌려 보세요. 덩어리가 작을수록 부주의한 방식의 오류가 뚜렷하고, 클수록 오류가 깊이 숨는다는 것이 더 직관적으로 보일 거예요.

이 세 가지를 기억하기

  1. Strata의 서비스 계층은 앱의 JSON 요청을 토큰 번호로 번역하고, 엔진이 내놓은 토큰을 다시 글자로 바꿔 SSE 이벤트 스트림으로 돌려보내요. 이 계층과 엔진 사이의 인터페이스는 Engine.generate 하나뿐이에요.
  2. 바이트에서 글자까지 문이 세 개 있어요. 점진적 UTF-8 디코딩, 빈 줄로 이벤트 자르기, 완전한 JSON 파싱이에요. 네트워크 덩어리의 경계는 이 세 경계와 상관이 없으니, 문마다 먼저 다 모아야 해요.
  3. 모델 출력 속의 태그도 잘려요. Strata의 OutputParser는 태그의 시작일 수도 있는 꼬리를 붙잡아 두어 반쪽 태그를 절대 내보내지 않고, 완성된 도구 호출은 끝까지 다 쓴 뒤에야 인정해요.

흔한 오해: 「SSE 이벤트 개수를 세면 모델이 토큰을 몇 개 생성했는지 알 수 있다.」

둘 사이에는 고정된 관계가 없어요. Strata의 첫 이벤트는 「어시스턴트가 말을 시작해요」만 알리고 토큰이 하나도 없어요. 긴 질문을 읽는 동안에는 keep-alive 주석이 끼어들어요. 토큰 하나가 한자의 반쪽만 가져오면 그 단계에서는 보낼 글자가 없어요. 태그가 붙잡혀 있을 때도 잠시 아무것도 안 보낼 수 있어요. 반대로 이벤트 하나 속의 글이 여러 토큰에서 올 수도 있어요. 토큰 수를 세려면 이벤트가 아니라 응답 끝의 usage 필드를 보세요.

한 걸음 더: 세 경계의 엄격한 요구, 「호환」의 범위, 검증 방법

세 경계를 규격대로 분명히 하기

SSE 규격이 파서에 요구하는 것은 몇 가지로 정리돼요 [R05]. 이벤트 스트림은 UTF-8로 디코딩해요. 줄 끝은 CRLF, 단독 LF, 단독 CR 모두 가능해요. 빈 줄이 이벤트 전달을 한 번 촉발해요. 같은 이벤트의 여러 data 줄은 LF로 이어 붙여요. 콜론으로 시작하는 줄은 주석이에요. 스트림이 끝날 때 빈 줄로 끝나지 않은 반쪽 이벤트는 그냥 버려요.

여기서 구현 순서가 나와요. 점진적 바이트 디코딩 → 텍스트를 쌓고 이벤트 경계로 프레임 나누기 → data 페이로드 파싱이에요. 덩어리 하나를 읽을 때마다 JSON.parse를 하면 글자가 잘리는 문제와 이벤트가 잘리는 문제에 한꺼번에 걸려요. 이 책의 인터랙티브 실험은 data만 있는 부분 집합만 구현했고, LF와 CRLF를 지원해요. EventSource의 자동 재연결, id와 retry 필드는 구현하지 않았으니 완전한 SSE 클라이언트로 쓰면 안 돼요.

예제: 한자 한 글자가 세 덩어리에 걸릴 때

中의 세 바이트 E4 B8 AD가 네트워크 덩어리 세 개에 나뉘어 들어가요. 덩어리마다 완전한 텍스트로 보고 디코딩하면 대체 문자 세 개가 나와요. 점진적 디코더는 E4를 읽으면 2바이트가 더 필요하다는 걸 알고 붙잡아 둬요. B8을 읽으면 1바이트가 더 필요하고, AD를 읽고서야 中을 내놓아요. 마찬가지로 data: {"delta":"中"} 뒤의 줄바꿈 두 개도 콜론, 따옴표, 줄바꿈 두 개 사이 어디서든 잘릴 수 있어요. 네트워크 덩어리 수와 토큰 수 사이에는 고정된 관계가 없어요.

「OpenAI 호환」은 인터페이스의 부분 집합을 뜻해요

「호환」은 어떤 엔드포인트, 어떤 필드, 어떤 의미를 구현했는지로 이해해야 해요. 경로가 /v1/...처럼 생겼다는 것만으로 전부 호환된다고 판단하면 안 돼요. 이 책은 serve/server.py 맨 앞에 나열된 엔드포인트와 경계만 설명하고 [S15], 모든 프로토콜 필드를 하나하나 감사하지는 않았어요. v0.1.39에서 새로 생긴 /v1/responses는 그 목록에 없어요. 이 엔드포인트의 스트리밍 이벤트에는 모두 event: 이름 줄이 붙고, response.created로 시작해서 response.completed(또는 incomplete, failed)로 끝나요. 이 책은 이것도 감사하지 않았어요. 업스트림 보고소스를 읽어서 확인할 수 있는 세부 사항이 몇 가지 있어요. 첫 이벤트의 delta는 {"role":"assistant","content":""}예요. 생각은 reasoning_content 필드에 담겨요. 취소로 끝난 경우 클라이언트에게는 stop으로 보고해요.

스트림이 이미 시작된 뒤에 오류를 발견하면

HTTP 상태 코드는 응답 헤더에 있고, 응답 헤더는 한 번 나가면 바꿀 수 없어요. 그래서 Strata는 미리 알 수 있는 오류를 스트림이 시작되기 전에 처리해요. 질문 길이에 최대 출력 길이를 더한 값이 컨텍스트를 넘으면 곧바로 400으로 거부하고, 몰래 자르는 일은 절대 없어요. [S15] 스트림이 시작된 뒤에야 엔진이 오류를 내면(예를 들어 엔진 프로세스가 갑자기 종료되면) 상태 코드는 이미 200이에요. 이때 Strata는 스트림 안에 error 필드가 든 이벤트를 쓰고, 이어서 data: [DONE]으로 정상적으로 마무리해요. Anthropic 스타일 API는 event: error 이벤트를 써요. 코드 사실 클라이언트는 상태 코드만 보지 말고 이벤트 내용도 검사해야 해요.

템플릿 샌드박스는 템플릿 층만 지켜요

frontend.py는 Jinja의 ImmutableSandboxedEnvironment로 채팅 템플릿을 렌더링해요. [S16] 템플릿 코드가 할 수 있는 일을 제한하는, 템플릿 층의 구체적인 방어예요. 도구 실행, 이미지 URL 가져오기, 로컬 파일 읽기까지 저절로 안전하다는 것을 증명해 주지는 않아요. 자원 접근마다 별도의 위협 모델이 필요해요. Strata는 MCP 도구에 대해 검사를 하나 더 둬요. Strata 자체 웹 페이지(또는 설정에서 명시적으로 신뢰한 출처)이면서 JSON 형식으로 보낸 요청만 모델이 이 도구들을 쓰게 해 줘요. 도구는 이 컴퓨터에서 내 권한으로 실행되기 때문이에요. 코드 사실

검증 방법과 증거의 경계

SSE 파싱 검증은 이래요. 중국어가 든 JSON 이벤트 두 개를 1~32바이트로 잘라서, 어떻게 자르든 복원 결과가 완전히 같을 것을 요구해요. CRLF, 여러 줄 data, 끝이 잘린 이벤트를 테스트에 넣어요. 잘린 이벤트는 미완성 상태로 두거나 오류를 내야 하고, 성공한 것처럼 꾸미면 안 돼요.

MockEngine으로는 스트리밍과 비스트리밍 응답, 취소, 도구 인자, 오류가 났을 때의 마무리 이벤트를 검증할 수 있어요. 하지만 GPU 추론의 품질이나 실제 성능은 증명하지 못해요. [S15] 이것이 바로 계층별 테스트의 장점이면서 증거의 경계예요.
