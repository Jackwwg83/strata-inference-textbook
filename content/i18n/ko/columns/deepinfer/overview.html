이 책은 줄곧 한 가지 일을 해 왔어요. 평범한 컴퓨터에서 큰 모델을 돌려 한 사람을 위해 일하게 하는 거예요. Strata의 README도 첫머리에 이 목표를 적어 두었고, GPU(그래픽 카드)는 VRAM 12 GB부터 시작해요. 업스트림 보고[S01]

추론의 반대쪽 끝에는 DeepSeek의 온라인 서비스가 있어요. DeepSeek의 설명으로는 클러스터 하나가 하루에 155조 개의 토큰을 처리해요. 업스트림 보고(Q&A 문서 17행) 2026년 10월 20일, DeepSeek는 이 서비스를 떠받치는 추론 프레임워크 DeepInfer를 오픈소스로 공개했어요. 이 페이지는 세 가지 질문에 먼저 답해요. DeepInfer는 무엇인지, 어느 부분이 공개됐는지, Strata와 무엇이 다른지예요.

한마디로: DeepInfer는 DeepSeek-V4.1-Flash를 위한 클러스터 추론 엔진이에요. 프리필, 디코드, 비전 인코딩을 서로 다른 머신에 나누고, 전문가를 수십 장의 카드에 펼쳐 놓아요. 이번에 공개된 것은 엔진 본체로, 오프라인 추론을 할 수 있어요. KV 캐시 시스템, 세 단계를 이어 주는 접착 코드, 데이터 병렬 로드 밸런서는 저장소에 없어요.

1.1 반대쪽 끝: 같은 개념을 수백 장의 카드로 넓히면

DeepInfer는 추론 프레임워크예요. Strata와 같은 층, 곧 1장에서 말한 "주방"에 해당해요(1장). README의 첫 문장은 DeepSeek의 대규모 온라인 서비스를 떠받치는 고성능 추론 프레임워크라고 말하고, 이번에 공개한 버전은 오프라인 추론과 대규모 서비스에 필요한 핵심 기능을 제공한다고 해요. 업스트림 보고(README 3행) 지금은 모델 하나만 지원해요. DeepSeek-V4.1-Flash예요.

Strata와 같은 개념을 다뤄요. MoE 전문가, KV 캐시, 프리필(prefill)과 디코드(decode), 추측 디코딩, 배치 처리예요. 차이는 규모예요. Strata는 모델 하나를 컴퓨터 한 대에 밀어 넣을 방법을 찾고, DeepInfer는 많은 머신이 함께 많은 사람을 서비스할 방법을 찾아요. DeepSeek의 Q&A 문서에는 이 시스템이 처음부터 정한 세 가지 목표가 적혀 있어요. 업스트림 보고(Q&A 7–13행)

  1. 여러 업체의 가속기 카드를 지원하고, 플랫폼마다 성능을 끝까지 끌어내요.
  2. 평범한 하드웨어로 프리필과 디코드를 구성해요. 프리필은 평범한 8카드 머신, 디코드는 평범한 64–128카드 슈퍼노드를 써요. 슈퍼노드는 고속 인터커넥트로 한 덩어리처럼 묶은 카드 묶음이에요.
  3. KV 캐시를 72시간 넘게 보관해요. 오래된 대화가 다시 와도 캐시에 히트하면 프리필을 다시 하지 않아도 돼요.

규모 차이를 먼저 느껴 봐요. Q&A 문서에 따르면 디코드는 EP64부터 시작하길 권하고, 프리필과 디코드의 카드 수는 대략 1:1이에요. 그래서 "가장 작은 효율적 배포 단위"는 프리필 64장과 디코드 64장이에요. 업스트림 보고(Q&A 65–67행) EP는 전문가 병렬(EP)이고, 2페이지에서 자세히 다뤄요. 그림 D1-1은 두 끝을 나란히 놓았어요.

아래 표는 두 끝을 나란히 놓아요. Strata 열은 이 책의 각 장에서, DeepInfer 열은 README, Q&A 문서, 코드에서 가져왔어요.

1.2 요청 하나의 여정: 프로덕션 시스템 지도

DeepSeek는 Q&A 문서에 참조 아키텍처 그림을 그려 두었어요. 시스템은 E/P/D 분리 계산 노드와 전용 스토리지 노드로 이루어져요. 업스트림 보고(Q&A 41–43행) E는 이미지를 벡터로 바꾸는 비전 인코더(VE)이고, P는 프리필, D는 디코드예요. 따로 배포하면 단계마다 자원을 따로 배정할 수 있고, 첫 토큰까지의 시간(TTFT)과 토큰 간 간격(TBT)도 따로 조절할 수 있어요. 업스트림 보고(Q&A 27–31행)

어텐션 부분은 데이터 병렬(DP)을 쓰고, DP 개수는 EP 개수와 같아요. 카드마다 자기 몫의 요청에 대한 어텐션을 맡고, MoE 층에서는 전문가 병렬로 협력해요. 복제본이 이렇게 많으면 일을 나눠 줘야 해서, DeepSeek는 로드 밸런서 네 개를 만들었어요. 프리필, 디코드, VE 세 개는 데이터 병렬 복제본 사이의 배정을 맡고, 전문가 부하 분산(EPLB)은 전문가를 카드에 어떻게 나눌지를 맡아요. 프리필을 되풀이하지 않도록 KV 캐시 스토리지도 있어요. 업스트림 보고(Q&A 33행) 입구와 출구에는 DeepSeek Recipe도 있어서, API 프로토콜과 토큰 시퀀스 사이를 변환해요.

아래 지도는 그 아키텍처 그림을 다시 그린 것이고, 블록마다 오픈소스인지 저장소에서 확인했어요. 블록을 클릭하면 설명이 보여요. 한 단계 진행을 누르면 요청 하나가 입구에서 출구까지 가는 길을 따라가요.

이 그림에서 가장 놓치기 쉬운 것은 Entrypoint가 가장 먼저 하는 일이에요. KV 스토리지를 조회해서 이 요청의 접두부가 얼마나 길게 히트하는지 계산해야 비로소 라우팅할 수 있어요. Q&A 문서는 이 단계를 다른 일 뒤에 숨길 수 없다고 특별히 말해요. 업스트림 보고(Q&A 157행) 히트가 길수록 프리필이 계산할 양이 줄어요. 그래서 "얼마나 길게 히트하나"가 이 요청에 얼마나 무거운 일을 줄지 정해요. 단계마다 카드를 어떻게 배정하는지, KV를 어떻게 저장하는지, P에서 D로 어떻게 보내는지는 모두 3페이지에 있고, 로드 밸런서 네 개의 알고리즘은 2페이지에 있어요.

CS를 배운 분께: 웹 백엔드의 고전적인 계층 구조예요. 게이트웨이가 프로토콜을 변환하고(Recipe), 로드 밸런서가 요청을 애플리케이션 서버 무리(P와 D)에 나눠 주고, 상태는 독립된 스토리지 클러스터(3FS)에 둬요. 다른 점은 여기서 "애플리케이션 서버" 한 대가 수십 장의 카드로 이루어진 통신 도메인 하나라는 거예요. 위키백과: 부하분산을 보세요.

Strata와 비교하면: Strata는 이 그림을 컴퓨터 한 대에 눌러 담았어요. serve/server.py가 HTTP와 큐를 맡고, serve/frontend.py가 템플릿을 씌우고 출력을 파싱해요(23장). 엔진은 같은 카드에서 먼저 프리필하고 그다음 디코드해요(16장). 기본 설정에서는 잠금 하나가 요청을 한 줄로 세워요(25장). 클러스터에서는 층마다 독립된 서비스로 쪼개야 해요. 머신 한 대에는 모든 사용자가 들어갈 수 없고, 모든 사용자를 한 줄로 세울 수도 없기 때문이에요.

1.3 공개의 경계: 저장소에 있는 것과 없는 것

README는 경계를 아주 분명히 적어 두었어요. 이번에 공개한 기능은 다음과 같아요. 최적화된 커널과 모델, 샘플러 런타임. 어텐션의 데이터 병렬과 균형 잡힌 컨텍스트 병렬(CP), MoE의 전문가 병렬과 EPLB. DSpark와 신뢰도에 따라 스케줄링하는 검증. 슬라이딩 윈도 어텐션(SWA)의 유계 재생(bounded replay). 비동기 스케줄링, 곧 제로 오버헤드 배치 스케줄러. 배치 불변(batch-invariant) 추론. 결정적 샘플링. 구조화 출력. 업스트림 보고(README 9–18행)

"완전한 추론 서비스에는 필요하지만 이번에는 포함하지 않은" 것도 세 가지 적어 두었어요. 업스트림 보고(README 38–42행)

  • KV 캐시 시스템.
  • VE / 프리필 / 디코드를 나눠 배포하는 구성(README는 엔진에 필요한 기능 대부분은 이미 구현됐다고 덧붙여요).
  • 프리필과 디코드에서 데이터 병렬 복제본 사이의 로드 밸런싱.

Q&A 문서는 이유를 들어요. KV 캐시 관리와 로드 밸런싱이 DeepSeek 내부 인프라와 너무 단단히 묶여 있어서, 당분간 완전히는 공개하지 않았다는 거예요. 업스트림 보고(Q&A 21행) DeepSeek Recipe는 따로 deepseek-recipe라는 다른 저장소로 공개됐어요. 업스트림 보고(Q&A 19행)

"대부분 이미 구현됐다"는 말은 코드에서 근거를 찾을 수 있어요. 엔진에는 타입이 세 가지 있어요. NORMAL은 프리필과 디코드를 모두 하고, PROMPT는 프리필만, COMPLETION은 디코드만 해요. 코드 사실(engine_type.py, C++ 쪽도 scheduler.hpp에 같은 것을 정의해요) 그런데 메인 엔진 클래스 LLMEngine에는 "여기부터는 전부 가상 함수"라는 주석이 있어요. PD 분리 초기화, 프리필 후 KV 저장, KV 저장, 계산을 마친 요청을 디코드 엔진에 보내기, 이 함수들에는 설명이 한 줄 있을 뿐 함수 본문이 없어요. 저장소에는 이것을 구현하는 다른 클래스도 없어요. 코드 사실(llm_engine.py 800–858행) 그림 D1-3이 이 경계를 그렸어요.

오해하기 쉬운 점이 하나 더 있어요. 저장소에 deepinfer/entrypoints/라는 디렉터리가 있지만, 그림 D1-2의 프로덕션 Entrypoint가 아니에요. 안에는 오프라인용 LLM 클래스 하나뿐이에요. 이 클래스는 같은 프로세스 안에서 엔진을 만들고, 프롬프트 묶음을 넣고, 모두 끝날 때까지 step()을 반복해서 불러요. 코드 사실(llm.py) 저장소의 유일한 HTTP 서버는 기본으로 꺼져 있는 성능 프로파일링 엔드포인트 POST /profile이고, 사용자 요청은 받지 않아요. 코드 사실(profile_server.py)

Q&A 문서는 프로덕션에서 당분간 텐서 병렬(TP)과 CP를 쓰지 않는다고 하는데, README와 예제는 둘 다 CP를 지원해요(예제에 --cp 8이 있어요). 업스트림 보고(Q&A 53행, examples/README 6–8행) 둘은 모순이 아니에요. 하나는 실서비스를 어떻게 구성하는지, 다른 하나는 코드가 무엇을 할 수 있는지를 말해요.

1.4 저장소 지도: 코드가 어디에 사는지

고정한 커밋의 저장소에는 파일이 342개 있고, 펼쳐지지 않은 서브모듈이 6개 더 있어요. 코드 사실 "사용자에게서 얼마나 먼가" 순서로 위에서 아래로 나열하면 그림 D1-4와 같아요.

표 D1-1은 디렉터리를 하나씩 설명해요. 모든 행은 고정한 커밋의 파일과 맞춰 보았어요. "어디서 읽나" 열은 그 디렉터리를 칼럼에서 자세히 다루는 페이지를 가리켜요.

1.5 누가 돌릴 수 있고, 카드는 몇 장 필요하고, 고장 나면 어떻게 하나

먼저 문턱부터 볼게요. 하드웨어는 두 가지뿐이에요. NVIDIA SM100 GPU와 Huawei Ascend 950 NPU예요. 소프트웨어는 Linux, GCC 13 이상, Python 3.12가 필요하고, NVIDIA는 CUDA 13, Ascend는 CANN 9.2가 필요해요. 업스트림 보고(README 33–52행) 오프라인 예제의 기본 인자는 --ep 8이에요. 8카드 머신 한 대를 기준으로 쓴 거예요. 코드 사실(offline_inference.py) 벤치마크 규모는 환경이 정해요. ep_size = WORLD_SIZE × 보이는 카드 수이고, WORLD_SIZE는 노드 수예요. 업스트림 보고(examples/README 61행)

그래서 이 칼럼의 독자 대부분은 DeepInfer를 돌릴 수 없고, 이 책도 돌려 본 적이 없어요. 아래 숫자는 모두 DeepSeek가 직접 보고한 것이고, 이 책이 다시 측정하지 않았어요.

155조 토큰은 어느 정도 규모일까요? 하루 86,400초로 펼치면 155 × 10¹² ÷ 86,400 ≈ 18억 token/s예요. Strata는 RTX 5070 한 장에서 답을 쓸 때 약 93 token/s예요(1장). 18억 ÷ 93 ≈ 1900만이에요. 교육용 추정 이 비율은 자릿수 감각을 잡기 위한 것뿐이에요. Q&A 문서는 155조 가운데 입력이 얼마이고 캐시 히트가 얼마인지 말하지 않고, Strata의 93은 출력만 세요.

탄력적 확장과 장애 대응. Q&A 문서에는 실서비스가 트래픽 변동과 고장 난 카드에 어떻게 대응하는지 다룬 절이 있어요. 업스트림 보고(Q&A 193–211행) 프리필은 "캐시에 미스한 토큰 수"로 필요한 머신 수를 정하고, 디코드는 "실행 중인 요청 수"로 조절해요. 조절할 때마다 속도 제한이 있고, 상한과 하한도 있어요. 디코드 엔진은 내리라는 알림을 받으면 1분의 유예 기간이 있고, 끝내지 못한 요청은 KV 캐시와 함께 한꺼번에 다른 디코드 엔진으로 넘어가 이어서 처리돼요. 평소에도 여유를 남겨 둬요. 풀에는 대기 중인 빈 머신이 있고, 온라인 인스턴스도 계산된 수요보다 많아요. 쿼터 사용률이 0.8을 넘으면 축소가 금지돼요. 재시작에는 몇 분이 걸려서, 장애 대응은 여유분과 요청 단위 재라우팅에 기대고, 엔진 하나를 더 빨리 재시작하는 데는 기대지 않아요.

와이드 전문가 병렬에는 특별한 약점이 하나 있어요. 인스턴스 하나의 모든 카드가 통신 도메인 하나를 이루기 때문에, 카드 한 장이 고장 나면 인스턴스 전체를 못 써요. 재시작할 때 플랫폼은 지금 멀쩡한 카드 수에 맞춰 EP 크기를 다시 정해요. 코드에는 이것과 짝이 되는 부분이 있어요. 중복 전문가 수는 "전문가 총수가 ep_size로 나누어떨어질 때까지" 자동으로 채워지므로, EP 크기가 384의 약수일 필요는 없어요. 코드 사실(eplb/__init__.py) 이것과 장애 복구의 관계는 이 책의 추론이고, Q&A 문서는 그렇게 말하지 않아요. 교육용 추정

Strata와 비교하면: Strata에는 머신이 한 대뿐이라 넘겨받을 "다른 카드"가 없어요. 생명주기 문제는 프로세스를 어떻게 시작하고 요청을 어떻게 취소하느냐(24장 「취소」)이고, 대기 문제는 줄 하나를 어떻게 세우느냐(25장 「대기행렬 이론 입문」)예요. 클러스터에서는 카드 고장이 일상이라서, "카드가 한 장 줄어도 계속 서비스할 수 있나"가 설계의 일부가 돼요.

1.6 이 칼럼을 읽는 법

뒤의 네 페이지는 각각 프로덕션 시스템의 한 부분을 골라 원리를 설명하고, 그다음 코드로 내려가요. 페이지마다 먼저 이 책에서 배운 개념으로 돌아가고, 클러스터에서는 어디가 다른지 말해요. 그림 D1-5가 로드맵이에요.

  • 2페이지 와이드 전문가 병렬: 어텐션은 데이터 병렬, 전문가는 전문가 병렬로 나눠요. EP64가 EP8보다 처리량이 높은 이유, EPLB와 데이터 병렬 로드 밸런서 세 개가 일을 어떻게 나누는지 다뤄요. 먼저 10장과 21장 「파이프라인 병렬과 텐서 병렬」을 읽어 보세요.
  • 3페이지 E/P/D 분리와 72시간 KV 캐시: VE, P, D를 왜 나누는지, KV 캐시를 SSD 클러스터에 어떻게 저장하는지, 히트한 뒤 작은 한 구간만 어떻게 다시 계산하는지 다뤄요. 먼저 17장 「페이징 방식 관리」와 20장을 읽어 보세요.
  • 4페이지 DSpark 추측 디코딩과 제로 오버헤드 스케줄링: 드래프트가 한 번에 몇 개를 추측하고, 신뢰도로 몇 개를 검증할지 정하는 방법, CPU가 다음 단계를 짜는 동안 GPU가 멈추지 않는 방법을 다뤄요. 먼저 18장과 25장 「연속 배칭」을 읽어 보세요.
  • 5페이지 배치 불변, 결정적 샘플링, 구조화 출력: 같은 입력이 서버에서 왜 달라지는지, 어떻게 다시 같게 만드는지, 모델이 유효한 JSON만 출력하게 하려면 어떻게 하는지 다뤄요. 먼저 26장과 2장을 읽어 보세요.

이 세 가지를 기억하기

  1. DeepInfer와 Strata는 같은 개념을 다루지만 난제는 반대예요. Strata는 모델을 컴퓨터 한 대에 밀어 넣어야 하고, DeepInfer는 수백 장의 카드가 함께 많은 사람을 서비스하게 해야 해요.
  2. 프로덕션 시스템은 Recipe, Entrypoint, E/P/D로 분리된 VE / P / D, 로드 밸런서 네 개, KV 스토리지 클러스터로 이루어져요. 이번에 공개된 것은 엔진 본체와 EPLB이고, 오프라인 추론을 할 수 있어요.
  3. KV 캐시 시스템, 세 단계를 이어 주는 접착 코드, 데이터 병렬 로드 밸런서는 저장소에 없어요. 엔진은 이것들을 위해 타입과 빈 훅을 남겨 두었고, 배포하는 사람이 직접 채워야 해요.

흔한 오해: "DeepInfer가 오픈소스가 됐으니, 가져다 쓰면 DeepSeek 같은 온라인 서비스를 만들 수 있다."

이번 저장소가 제공하는 것은 오프라인 추론뿐이에요. 프로세스 하나가 프롬프트 묶음을 받아 계산을 마치면 끝나요. 사용자 요청을 받는 HTTP 서비스도, KV 캐시 시스템도, 프리필과 디코드를 이어 주는 접착 코드도, 데이터 병렬 로드 밸런서도 없어요. README가 나열한 하드웨어는 SM100과 Ascend 950뿐이고, Q&A 문서가 권하는 가장 작은 효율적 단위는 카드 128장이에요. 가장 큰 가치는 프로덕션급 엔진이 속으로 어떻게 짜여 있는지 볼 수 있다는 점이에요.

한 걸음 더: 오프라인 추론 한 번의 호출 사슬, 그리고 공개 경계를 직접 확인하는 법

명령줄에서 커널까지

python examples/offline_inference.py를 예로 들어요. 아래 단계는 모두 고정한 커밋 774ce244의 소스와 맞춰 보았어요.

  1. 프로세스 시작. 예제의 기본값은 --ep 8이에요(offline_inference.py 12–17행). examples/_launch.py의 run_dp는 RANK와 WORLD_SIZE에 따라 이 노드가 맡은 DP 랭크마다 자식 프로세스를 하나씩 띄워요(26–40행).
  2. 엔진 생성. LLM.__init__는 offline_inference=True로 EngineArgs를 만들고, LLMEngine.from_engine_args를 불러요(llm.py 70–84행). EngineArgs의 엔진 타입 기본값은 NORMAL이에요(arg_utils.py 41행).
  3. 제로 오버헤드 스케줄링은 기본으로 켜짐. environ.py에서 DEEPINFER_ZERO_OVERHEAD_SCHEDULING의 원래 기본값은 꺼짐이에요(179행). 하지만 사용자가 설정하지 않았으면 EngineArgs.__post_init__가 엔진 타입에 따라 켜 줘요. NORMAL과 COMPLETION은 켜고, PROMPT는 꺼요(arg_utils.py 48–55행, engine_type.py 15–17행). 그래서 README의 "기본으로 켜짐"은 코드와 맞아요.
  4. 토큰화와 제출. generate()는 프롬프트마다 _add_request에 넘겨요. 토큰 번호가 없으면 Hugging Face 토크나이저로 인코딩해요(llm.py 144–166행). 프로덕션에서는 이 단계를 Recipe가 해요.
  5. 메인 루프. _run_engine은 끝나지 않은 요청이 없을 때까지 LLMEngine.step()을 거듭 부르고, 마지막으로 처리 중이던 결과를 모두 내보내요(168–195행). LLMEngine은 C++ 확장 deepinfer._C.engine에서 Scheduler, BlockManager 등을 임포트해요(llm_engine.py 19–31행). 이 확장은 setup.py가 csrc/ 아래 소스 파일을 컴파일해서 만들고, cuda_utils, engine, graph_timer 세 서브모듈로 나뉘어요(pybind.cpp).
  6. 카드마다. Worker가 매 단계의 순전파, 후처리, 샘플링을 이끌고(worker.py), ModelRunner가 모델을 돌려요(model_runner.py). 모델은 레지스트리로 찾아요. 아키텍처 이름 DeepseekV41ForCausalLM은 deepseek_vl.DeepseekVLForCausalLM에 대응하고(models/__init__.py 15–17행), 이것은 텍스트 전용 DeepseekForCausalLM을 상속해요(deepseek_vl.py 26행).
  7. 커널에 닿기. 플랫폼 클래스가 어느 TileLang 연산자 묶음을 쓸지 정해요. GPU는 cuda, NPU는 asc예요(platform.py 55–88행). 나머지 연산자는 표 D1-2의 커널 라이브러리에서 와요.

이 페이지가 "공개되지 않았다"고 판단한 부분은 클론 하나에서 명령 세 개로 다시 확인할 수 있어요.

  • git show 774ce244:deepinfer/engine/llm_engine.py | sed -n '800,858p': "여기부터는 전부 가상 함수"라는 주석과, 설명만 있는 함수들이 보여요.
  • git grep -n "def send_processed_prompts" 774ce244: 정의는 llm_engine.py의 한 곳뿐이고, 이것을 구현하는 서브클래스는 없어요.
  • git grep -n -w "3FS" 774ce244 -- '*.py' '*.cpp' '*.hpp'와 git grep -n "kvcache-store\|kvcache_store" 774ce244 -- '*.py' '*.cpp' '*.hpp': 둘 다 결과가 없어요. 3FS와 kvcache-store는 Q&A 문서에만 나와요. (-i는 붙이지 마세요. 대소문자를 구분하지 않으면 로그 형식 문자열의 %.3fs가 잘못 걸려요.)

이 페이지가 확인하지 않은 것

vendor/ 아래 서브모듈 6개는 이 책이 쓴 클론에서 펼쳐져 있지 않아요. 그래서 이 페이지는 DeepInfer가 그것들을 어떻게 임포트하는지만 적고, 구현은 평가하지 않아요. deepseek-recipe는 다른 저장소이고, 이 페이지의 설명은 모두 Q&A 문서 19행, 35행, 290–312행에서 왔어요. 모델 구조는 Hugging Face의 커밋 1bae0e10에 있는 config.json에서 왔고, DeepInfer의 고정 커밋에 묶이지 않아요. 두 성능 그래프의 수치는 이 책이 그래프에서 읽은 값이고, 정밀도는 눈금의 절반쯤이에요.
