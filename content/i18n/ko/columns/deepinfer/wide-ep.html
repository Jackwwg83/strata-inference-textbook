컴퓨터 한 대에서 슈퍼노드 하나로

10장에서 계산을 하나 했어요. Strata가 컴퓨터 한 대에서 token 하나를 만들 때, 전문가 데이터를 약 664 MB 읽어요. VRAM에는 전문가가 전부 들어가지 않아요. 그래서 인기 있는 전문가만 캐시하고 나머지는 CPU에 맡겨요. 「한 사람, 한 대」를 위한 방식이에요.

DeepSeek의 온라인 서비스는 동시에 대화하는 수천수만 명을 상대해요. 디코드는 GPU 한 개가 아니라 GPU 64~128개로 이루어진 슈퍼노드에서 돌아가요. 이 GPU들은 고속 인터커넥트로 이어져 있어서, 하나의 덩어리처럼 쓸 수 있어요. 업스트림 보고(Q&A 11행) 이 페이지는 세 가지 질문에 답해요. 전문가 수백 개를 GPU 수십 개에 어떻게 나눌까요? GPU가 많을수록 디코드가 더 이득인 이유는 무엇일까요? 인기 전문가가 GPU 한 개에 몰리면 어떻게 할까요?

한마디로: DeepInfer의 디코드에서 어텐션은 데이터 병렬(DP)로 돌아가고, 각 GPU가 자기 요청 묶음을 맡아요. 라우팅 전문가(라우터가 고르는 전문가)는 전문가 병렬(EP)로 돌아가요. GPU 64–128개에 나누어, GPU 한 개가 한 층에서 맡는 전문가는 몇 개뿐이에요. GPU가 많을수록 GPU 한 개가 단계마다 읽는 전문가 가중치는 줄고, 한 번 읽은 가중치가 처리하는 token은 늘어요. 대가로 층마다 전체 대 전체 통신(all-to-all)이 두 번 필요해요. 또 가장 바쁜 GPU가 그룹 전체의 속도를 정해요. 그래서 전문가 부하 분산(EPLB)으로 인기 전문가를 복제해서 흩어 놓아요.

2.1 두 가지 분할을 겹치기: 어텐션은 요청별로, 전문가는 번호별로 나눠요

21장에서는 GPU 여러 개가 일을 나누는 세 가지 방법(레이어 분할, 텐서 병렬, 요청 병렬)을 설명했어요. Strata는 레이어 분할을 골랐어요. DeepInfer는 그중 데이터 병렬만, 그것도 어텐션에만 써요. 그 위에 21장에서 다루지 않은 한 가지, 전문가 병렬을 겹쳐요. 그림 D2-1을 보세요.

  • 어텐션은 데이터 병렬(DP)을 써요. 각 GPU가 완전한 어텐션을 하나씩 갖고, 서로 다른 요청을 처리해요. 업스트림의 설명은 이래요. DeepSeek-V3 / R1과 마찬가지로, 어텐션의 DP 개수는 전문가 병렬 개수와 같아요(#DP = #EP). 지금은 텐서 병렬(TP)도 컨텍스트 병렬(CP)도 쓰지 않아요. 업스트림 보고(Q&A 33–53행) 코드에는 컨텍스트 병렬이 있고 README에도 나와 있어요. 다만 업스트림의 배포 설정에서는 쓰지 않아요.
  • MoE는 전문가 병렬(EP)을 써요. 각 층의 라우팅 전문가를 번호순으로 EP개로 자르고, 각 GPU는 그중 한 덩어리만 가져요. 라우터와 공유 전문가는 모든 GPU가 완전한 한 벌씩 가져요. 코드 사실(moe.py 24–67행, 77–110행)

전문가 개수는 GPU 개수로 나누어떨어져야 해요. DeepInfer는 세 가지 수를 구분해요. 모델이 정의하고 라우터가 그중에서 고르는 논리 전문가, 실제로 가중치가 할당된 물리 전문가 = 논리 전문가 + 중복 복사본, 각 GPU 위에 있는 로컬 전문가 = 물리 전문가 ÷ EP예요. 코드는 물리 전문가 수가 EP로 나누어떨어지도록 요구하고, 아니면 곧바로 오류를 내요. 코드 사실(moe.py 91–95행) 중복 복사본은 2.4절의 주인공이에요.

MoE 층마다 GPU끼리 token을 주고받기 때문에, 한 그룹 안에서 어떤 GPU는 프리필을 하고 어떤 GPU는 디코드를 하는 것은 안 돼요. 프리필과 디코드를 함께 하는 엔진에서는, 스케줄러가 체크포인트마다 그룹 전체가 투표해서 이번 단계의 종류를 통일해요. 그룹 안에 프리필을 하는 GPU가 있으면, 할 일이 없는 GPU도 빈 프리필 단계를 함께 돌아야 해요. 코드 사실(scheduler.hpp 295–340행: "DP 그룹 안에서는 같은 종류여야 하며, 투표로 통일한다")

업스트림 배포에서는 두 단계의 너비가 크게 달라요. 프리필은 EP2–8을 쓰고, GPU 메모리(HBM)에 들어가는 한 작을수록 좋아요. 디코드는 EP64–128을 쓰고, GPU가 충분한 한 클수록 좋아요. 업스트림은 이것을 와이드 전문가 병렬(Wide-EP)이라고 불러요. 업스트림 보고(Q&A 45–53행) 두 단계를 따로 배포하는 이유는 3페이지 「E/P/D 분리와 72시간 KV 캐시」를 보세요. 다음 절에서는 디코드를 넓게 펼치는 이유를 설명해요.

CS를 배운 분께: 이것은 병렬 계산의 「벌크 동기」 패턴이에요. 각자 한 구간을 계산하고, 모두가 데이터를 한 번 교환하고, 함께 다음 구간으로 들어가요. 쓰기 쉽고 따져 보기 쉬워요. 대가로 모든 구간이 가장 느린 사람을 기다려요.

Strata와 비교하면: Strata는 GPU가 두 개일 때 레이어로 앞뒤 두 토막으로 나눠요(21장). GPU 사이에서 데이터를 넘기는 것은 경계에서 한 번뿐이에요. 가정용 PC의 GPU 사이에는 보통 PCIe뿐이기 때문이에요. DeepInfer의 슈퍼노드에는 고속 인터커넥트가 있어요. 그래서 층마다 모든 GPU가 서로 데이터를 교환하는 설계를 할 수 있어요. 인터커넥트의 비용이 분할 방식을 정해요.

2.2 GPU가 많을수록 이득: GPU 한 개가 단계마다 읽는 전문가가 줄어요

5장의 루프라인 모델을 떠올려 보세요. 디코드는 단계마다 쓰는 가중치를 전부 읽어요. 가중치를 읽는 시간이 계산보다 긴 경우가 많아요. 한 번 읽은 가중치가 처리하는 token이 많을수록 이득이에요.

이제 GPU 한 개에 서서 MoE 한 층의 디코드 한 단계를 보세요. 배치가 충분히 크면, 이 GPU가 맡은 전문가는 거의 다 token 하나 이상에 선택돼요. 그래서 이 GPU는 자기 전문가를 전부 읽어요. 이 GPU에 있는 전문가 수가 읽는 가중치 묶음의 수예요. 교육용 추정

DeepSeek-V4.1-Flash는 한 층에 라우팅 전문가가 몇 개일까요? DeepInfer는 이 수를 Hugging Face에 있는 모델의 config.json에서 읽어요. 저장소에는 이 파일이 없고, 수가 코드에 박혀 있지도 않아요. 코드 사실(config.py 164–174행) 저장소의 비교 그림에는 "384+64 experts"라고 적혀 있고, Q&A도 EP64일 때 올림 후 GPU 한 개에 전문가 7개라고 말해요. 업스트림 보고(wide_ep_decode_pareto.png, Q&A 103행) 두 곳이 맞아떨어져요. 384 ÷ 64 = 6에 중복 1개를 더하면 딱 7이에요. 이 페이지는 384로 계산해요. 전문가 하나가 몇 바이트인지, token 하나가 전문가를 몇 개 고르는지는 저장소에서 찾을 수 없어요. 그래서 이 페이지는 구체적인 수를 쓰지 않고 S와 k로 나타내요.

그러면 간단한 식이 나와요. GPU 한 개가 한 층에서 맡는 전문가 수 = (384 + 중복 수) ÷ EP이고, GPU 한 개가 단계마다 읽는 전문가 가중치 ≈ 이 수 × S예요. 교육용 추정 "GPU마다 중복 1개 이상"으로 올림하면, EP8은 49개, EP64는 7개, EP128은 4개예요. EP8에서 EP64까지, GPU 한 개가 단계마다 읽는 전문가 가중치는 약 1/7로 줄어요.

아래 시뮬레이터는 세 가지를 한꺼번에 보여 줘요. GPU 한 개가 맡는 전문가 수, 전문가 가중치를 한 번 읽을 때 평균 몇 개의 token을 처리하는지, GPU 한 개가 단계마다 보내는 은닉 벡터 수예요. EP8, EP64, EP128을 눌러서 어떤 수가 변하고 어떤 수가 거의 안 변하는지 보세요. GPU 한 개의 단계당 token 수 T는 기본값이 384예요. 예제 benchmark는 기본으로 GPU마다 요청 64개이고, 요청 하나는 단계당 1 + 5개의 token으로 계산해요. 업스트림 보고(examples/README 45행)

아끼는 것은 읽는 바이트만이 아니에요. 배치가 GPU마다 T개의 token으로 고정되면, 그룹 전체는 한 단계에 EP × T개의 token과 EP × T × k번의 전문가 선택을 해요. 부하가 고르면 GPU마다 T × k번이 돌아와요. 이것을 이 GPU의 전문가에 나누면, 가중치 한 묶음이 처리하는 token은 T × k ÷ (GPU당 전문가 수)개예요. 교육용 추정 EP64는 EP8의 7배예요. 이것이 바로 5장에서 말한 「한 상에 둘러앉아 먹기」예요. 같은 요리라도 먹는 사람이 많을수록 이득이에요.

업스트림의 실측 그래프가 이 방향을 뒷받침해요. 업스트림 보고 조건: DeepSeek-V4.1-Flash, 컨텍스트 131,072, 드래프트 길이 3으로 고정, 드래프트 token마다 수락률 75%로 환산(그래프에는 τ = 3.25라고 적혀 있어요). EP64DP64는 384+64개, EP8DP8은 384+32개의 전문가를 써요. 이 그래프에는 GPU 모델이 적혀 있지 않아요. README가 성능 그래프에 적은 조건은 SM100이고, 각 GPU 그룹은 하나의 scale-up 도메인 안에 있어요(README 83행). DP rank마다 요청 64개를 돌릴 때 그래프에서 읽으면, EP64는 GPU당 초당 약 1.57만 token, 사용자당 초당 약 246 token이에요. EP8은 약 1.27만, 약 198이에요. 즉 처리량과 사용자당 속도가 함께 좋아져요. (Q&A 55–59행)

이 그래프를 읽을 때 주의할 점이 하나 있어요. 저장소의 benchmark 스크립트는 DEEPINFER_FORCE_LOAD_BALANCE=1을 무조건 설정해요. token마다 라우팅 점수를 난수로 바꾸기 때문에, 전문가 부하가 처음부터 고르게 돼요. 코드 사실(benchmark.py 158–168행, input_metadata.py 48–50행) 그래서 이것은 「부하가 완전히 균등」할 때의 상한이에요. 업스트림은 실서비스의 부하 분산이 이 오프라인 상한의 약 80%까지 간다고 말해요. 업스트림 보고(Q&A 125–127행)

Strata와 비교하면: Strata는 한 번에 아주 적은 수의 대화만 처리하고, token 하나가 전문가 약 480개를 읽어요(10장). Strata도 전문가별로 묶지만, 가중치 한 묶음을 나눠 쓸 수 있는 것은 검증 창 하나의 몇몇 token 사이뿐이에요(16장). 그래서 Strata의 중점은 인기 전문가를 VRAM에 두어 느린 길을 덜 타는 거예요(12장). DeepInfer는 반대예요. GPU 한 개가 전문가 몇 개만 맡고, 수백에서 수천 개의 token을 한 배치로 모아서, 가중치를 한 번 읽을 때마다 꽉 채워 써요.

2.3 층마다 전체 대 전체가 두 번: 디스패치와 컴바인

전문가가 여러 GPU에 흩어져 있으니, token이 전문가를 찾아가야 해요. MoE 층마다 DeepInfer는 네 가지 일을 해요. 코드 사실(mlp.py 565–616행)

  1. 라우팅. 이 GPU의 라우터가 이 GPU의 token마다 전문가를 골라요. 라우터는 「논리 전문가 → 물리 복사본」 매핑 표를 받아요. 선택되는 것은 논리 전문가이고, 어느 복사본으로 보낼지는 이 표가 정해요. (359–401행) 복사본 여러 개 중에서 어떻게 고르는지는 커널 라이브러리 안에 있어서, 이 책에서는 확인하지 못했어요.
  2. 디스패치(dispatch). 각 token의 은닉 벡터를 선택된 전문가가 있는 GPU로 보내요. 이 단계는 DeepEP의 EPBuffer.dispatch가 처리해요. 그러면서 이 GPU의 전문가마다 「이번 단계에 받은 token 수」를 더해 두는데, 이것이 2.4절 EPLB의 원본 데이터예요. (461–490행)
  3. 전문가 계산. 이 GPU는 받은 token을 전문가별로 묶어서 그룹 행렬 곱을 해요(16장에서 「전문가별 묶기」를 설명했어요). 라우팅 가중치는 이 단계에서 곱해요. (406–459행) 이어서 이 GPU는 공유 전문가로 자기 token을 계산해요.
  4. 컴바인(combine). 전문가의 결과를 token이 원래 있던 GPU로 돌려보내 더하고, 공유 전문가의 결과도 더해요. (493–511행)

디스패치와 컴바인은 둘 다 전체 대 전체 통신(all-to-all)이에요. 모든 GPU가 다른 모든 GPU에게 서로 다른 데이터를 보내요.

집합 통신: all-to-all

직관: 사무실에 4명이 있어요. 각자 편지 한 묶음을 들고 있고, 수신인은 다른 사람들이에요. all-to-all은 「모두가 동시에 모두의 우편함에 편지를 넣는 것」이에요. 끝나면 각자 손에는 자기에게 온 편지만 남아요.

정의: 프로세스 P개의 그룹이 있어요. 각 프로세스는 데이터 P개를 준비하고, j번째를 프로세스 j에게 보내요. 집합 통신의 한 종류예요. 흔한 다른 연산으로는 브로드캐스트(한 명이 모두에게 보냄), all-reduce(모두의 데이터를 더해서 모두가 합계를 받음), all-gather(각자 하나씩 갖고, 마지막에 모두가 전부를 받음)가 있어요.

예: GPU 4개, GPU마다 token 8개, token마다 전문가 2개를 고르고, 전문가는 고르게 분포한다고 해요. GPU마다 벡터 16개를 내보내고, 그중 약 12개(3/4)가 다른 GPU로 가요. GPU가 64개가 되면 다른 GPU로 가는 비율은 63/64가 되고, 전체 개수는 그대로예요. 그래서 너비를 넓혀도 GPU당 통신량은 거의 늘지 않아요. 늘어나는 것은 참여하는 GPU 수와 「가장 느린 GPU를 기다리는」 위험이에요.

DeepInfer와의 관계: MoE 층마다 디스패치 한 번, 컴바인 한 번이고, 각각 all-to-all 한 번이에요. DeepInfer는 부하를 집계할 때 all-reduce와 all-gather도 써요(2.4절).

EP 그룹 전체가 하나의 고속 인터커넥트 도메인 안에 있을 때(NVIDIA GPU에서는 하나의 NVLink 도메인), DeepInfer는 다른 길로 가요. Mega MoE예요. 코드 사실 이 길은 Python 쪽에서 호출이 한 번뿐이에요. 라우팅 결과, 전문가 가중치 두 벌, 대칭 VRAM 한 덩어리를 DeepGEMM의 fp8_fp4_mega_moe에 넘기고(활성값이 BF16이면 bf16_mega_moe로 바뀌어요. mlp.py 254–256행), 이 층의 출력을 돌려받아요. 중간에 따로 디스패치나 컴바인 호출은 없어요. 공유 전문가도 함께 넘겨요. (mlp.py 184–188행, 528–563행) 업스트림은 하나의 scale-up 도메인 안에서는 EP가 얼마나 넓든 배치가 얼마나 크든 Mega MoE가 융합하지 않은 방식보다 확실히 빠르다고 말해요. 업스트림 보고(Q&A 229–231행) 이 커널이 내부에서 통신과 계산을 어떻게 겹치는지는, DeepGEMM 코드가 이번 저장소에 없어서 이 책에서는 확인하지 못했어요.

2.4 인기 전문가가 몰릴 때: EPLB는 인기 전문가를 복제하고 다시 배치해요

그룹 전체가 단계마다 함께 움직이므로, 한 단계의 시간은 가장 바쁜 GPU가 정해요. 인기 전문가 몇 개가 하필 같은 GPU에 올라가 있으면, 그 GPU가 계산할 token은 다른 GPU의 몇 배가 되고, 다른 GPU는 기다릴 수밖에 없어요. DeepInfer는 이것을 수 하나로 재요. moe_lb = 가장 바쁜 GPU가 받은 token 수 ÷ GPU당 평균 받은 token 수. 코드 사실(eplb/__init__.py 167–193행, stats_logger.py 238–241행) 1.0이 완전한 균형이에요.

해결책이 전문가 부하 분산(EPLB)이에요. 물리 슬롯은 논리 전문가보다 몇 개 더 많아요. 남는 슬롯을 중복 전문가라고 부르고, 인기 전문가의 복사본을 놓는 데 써요. 업스트림의 설명은 이래요. 각 GPU는 자기가 맡은 전문가 외에 중복 전문가를 몇 개 더 놓아요. 업스트림 보고(Q&A 97행) 인기 전문가가 복사본 3개를 가지면, 그 token은 최대 3개의 GPU에 나눌 수 있어요. 배치할 때 복사본 두 개가 같은 GPU에 놓일 수도 있어요. EPLB는 이렇게 돌아가요. 코드 사실(eplb/__init__.py 131–165행, 222–278행)

  1. 집계. 단계마다 디스패치할 때, 이 GPU의 전문가별로 받은 token 수를 더해서 슬라이딩 윈도에 저장해요.
  2. 주기적 재배치. M단계마다 그룹 전체가 윈도 안의 카운트를 all-reduce로 합쳐서 재배치 정책에 넘겨요. 첫 재배치는 M/4단계로 앞당겨서, 콜드 스타트 때의 불균형을 일찍 바로잡아요.
  3. 인기 전문가 복제. 정책은 한 라운드에 복사본을 하나씩 줘요. 매 라운드, 「복사본을 하나 더 늘렸을 때 가장 큰 복사본 하나당 부하가 가장 많이 줄어드는」 전문가에게 줘요. (policy.py 105–123행)
  4. 다시 배치. 모든 복사본을 부하가 큰 순서로 줄 세우고, 하나씩 「놓은 뒤 단계별로 가장 바쁜 GPU의 부하를 더한 합이 가장 작아지는」 GPU에 놓아요. 각 GPU가 가득 찰 때까지 놓아요. (policy.py 12–70행) 이것은 탐욕 알고리즘이에요. 매번 눈앞에서 가장 좋은 선택만 해요. 전체 최적은 보장하지 않지만 빨라요.
  5. 가중치 이동. 새 매핑과 옛 매핑에 따라 GPU 사이에서 전문가 가중치를 옮겨요. GPU이고 같은 NVLink 도메인 안이면 상대 GPU의 미러를 직접 읽어요. 아니면 torch.distributed의 점대점 송수신을 써요(NVIDIA에서는 NCCL이고, Ascend에서는 미러 경로를 쓰지 않아요). (eplb/__init__.py 195–202행) 다 옮긴 뒤에 매핑 표를 바꿔요. (shuffle.py 1–6행)

3번과 4번 단계의 가정 하나를 기억하세요. 전문가에게 복사본이 몇 개 있든, 그 부하는 복사본 수만큼 똑같이 나뉘어요. 코드 사실(policy.py 31–37행) 아래 시뮬레이터는 같은 알고리즘을 옮겨 오고, 규모를 전문가 16개와 GPU 4개로 줄였어요.

코드에서 EPLB는 기본으로 꺼져 있어요. 재배치 간격 DEEPINFER_EXPERT_REARRANGEMENT_STEP_INTERVAL의 기본값은 0이고, 재배치하지 않는다는 뜻이에요. 중복 하한 DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS의 기본값은 0이에요. 통계 윈도의 기본값은 100단계예요. 코드 사실(environ.py 113–121행) 중복 하한은 그룹 전체의 합계이고, GPU당 개수가 아니에요. 코드는 이것을 「384 + 중복」이 EP로 나누어떨어지도록 올림해요. (eplb/__init__.py 21–28행) 업스트림이 공개한 설정과 실측은 아래와 같아요. 업스트림 보고(Q&A 93–103행)

단계중복 시작값통계 윈도재배치 간격업스트림 실측 moe_lb
프리필GPU당 4개, 올림100단계1,000단계마다1.074（EP4DP4）· 1.045（EP2DP2）

「GPU당 1개」를 코드의 표현으로 바꾸면 중복 하한을 EP로 설정하는 거예요. 교육용 추정 EP64에서는 384 + 64 = 448로 딱 나누어떨어지고, GPU당 7개가 되어 업스트림의 설명과 일치해요.

Strata와 비교하면: Strata의 전문가 캐시도 「최근에 누가 인기인지」를 추적하고, 4라운드마다 감쇠 카운트로 인기 전문가를 VRAM에 들여놔요(12장). Strata가 푸는 문제는 「어디서 계산할까」, 즉 VRAM이냐 CPU냐예요. EPLB가 푸는 문제는 「누가 가장 바쁜가」로, 인기 전문가를 몇 개 더 복제해서 여러 GPU에 나눠 줘요. 둘 다 과거로 미래를 예측해요. 둘 다 가중치 복사를 마친 뒤에 매핑을 바꿔요.

2.5 요청을 GPU에 어떻게 나눌까: 데이터 병렬 부하 분산기 세 가지

EPLB는 MoE 부분만 맡아요. 어텐션 부분이 얼마나 바쁜지는 GPU마다 요청이 몇 개 배정되고 그 컨텍스트가 얼마나 긴지에 달려 있어요. 이것은 DP 수준의 부하 분산기가 맡아요. 이들은 온라인 시스템과 강하게 엮여 있어서 이번에는 오픈소스로 공개되지 않았어요. README는 프리필과 디코드의 DP 부하 분산을 「포함하지 않음」 목록에 넣었어요. Q&A는 부하 분산 구성 요소가 내부 인프라와 강하게 엮여 있어 아직 완전히 공개되지 않았다고 말하고, 비전 인코더의 부하 분산기도 그중 하나예요. 업스트림 보고(README 38–42행, Q&A 21행) 아래 세 가지는 모두 Q&A의 설명에서만 나왔어요. 업스트림 보고(Q&A 105–127행)

  • 프리필 부하 분산기. 요청을 전체 컨텍스트 길이에 따라 네 구간으로 나눠요. 16K 미만, 16–64K, 64–256K, 256K 이상이에요. 구간마다 엔진을 몇 대 배정할지는 지난 라운드의 구간별 연산 수요에 따라 동적으로 조정해요. 엔진은 남은 연산 할당량에 맞춰 스스로 일을 가져가요. 어떤 엔진이든 어떤 프리픽스에도 히트할 수 있기 때문에(블록 KV 캐시는 독립된 3FS 스토리지 클러스터에 있어요. Q&A 141행, 3페이지 참고), 프리픽스 친화도로는 배정하지 않아요. DP 그룹에 들어오면 각 요청은 현재 할당량 부하가 가장 낮은 rank에 넘겨져요.
  • 디코드 부하 분산기. 모든 디코드 인스턴스의 모든 GPU를 한데 묶어 배정하고, 두 가지 양을 함께 맞춰요. 요청 수(단계마다의 배치 크기를 정해요)와 KV 캐시 총 길이(어텐션 비용을 정해요)예요. 경험칙은 이래요. 짧은 요청은 동시 처리 수는 낮지만 KV 총 길이가 큰 GPU로, 긴 요청은 KV 총 길이가 작은 GPU로 보내요.
  • 비전 인코더 부하 분산기. 프리필 머신이 비전 인코더(VE)가 배포된 머신을 무작위로 하나 고르고, 그 머신에서 지금 처리 중인 타일이 가장 적은 GPU에 이미지를 넘겨요. 타일 수는 크기로 바로 계산해요. (너비 ÷ 타일 한 변) × (높이 ÷ 타일 한 변)이에요.

두 층의 균형 맞추기는 둘 다 꼭 필요해요. DP 부하 분산기는 GPU마다 어텐션이 비슷하게 바쁘도록 하고, EPLB는 GPU마다 MoE가 비슷하게 바쁘도록 해요. 업스트림은 전체가 완전히 균등한 오프라인 기준의 약 80%까지 간다고 말해요. 업스트림 보고

넓은 것에는 대가도 있어요. 디코드 인스턴스 하나의 모든 GPU는 하나의 통신 도메인이에요. GPU 한 개가 고장 나면 인스턴스 전체를 쓸 수 없게 돼요. 다시 시작할 때 플랫폼은 그 시점에 정상인 GPU 수에 맞춰 EP 너비를 다시 정해요. 업스트림 보고(Q&A 209–211행) 규모 확장·축소와 그 밖의 장애 대응 수단은 1페이지를 보세요.

2.6 전문가 가중치에 FP4: 단계마다 읽는 바이트가 다시 절반으로

GPU 한 개가 단계마다 읽는 전문가 가중치 = 전문가 수 × 전문가 하나의 바이트 수예요. 2.2절은 앞의 것을 줄였고, FP4는 뒤의 것을 줄여요. 업스트림은 라우팅 전문가의 가중치에 MXFP4를 쓴다고 말해요. 가중치 32개마다 ue8m0 스케일 하나를 같이 써요. 메인 KV와 인덱스 KV에도 FP4를 쓰는데, 그것은 3페이지의 이야기예요. 업스트림 보고(Q&A 213–221행)

코드는 이 설명과 일치해요. 모델을 불러올 때 config.json의 양자화 설정에 전문가는 FP4, 스케일은 ue8m0이라고 적혀 있어야 하고, 아니면 불러오기를 거부해요. 코드 사실(config.py 253–264행) 전문가 가중치는 e2m1 형식으로 두 개씩 한 바이트에 담기고, 스케일은 따로 저장돼요. (weights.py 281–288행) 행렬 곱에서는 활성값에 FP8, 전문가 가중치에 FP4를 써요. (mlp.py 177–182행, 109–128행)

가중치 하나가 몇 비트인지 계산해 보세요. 가중치 32개 × 4비트에 8비트 스케일 하나를 더하면 모두 136비트이고, 평균 가중치 하나에 4.25비트예요. 교육용 추정 FP8의 8비트와 비교하면, 단계마다 읽는 전문가 바이트가 거의 절반으로 줄어요.

Strata와 비교하면: Strata의 Q2_0은 가중치당 2.25비트예요(4장 「양자화」). 목표는 34 GB의 전문가를 최대한 많이 12 GB VRAM에 넣는 것이고, 못 들어간 것은 CPU가 계산해요. DeepInfer의 전문가는 전부 GPU 위에 있어요. 한쪽으로는 전문가를 GPU 수십 개에 나누고, 다른 쪽으로는 4비트 형식을 써서, 양쪽에서 GPU 한 개가 단계마다 읽는 바이트를 줄여요.

이 세 가지를 기억하기

  1. 어텐션은 데이터 병렬이고, 각 GPU가 자기 요청을 맡아요. 라우팅 전문가는 전문가 병렬이고, EP개의 GPU에 나뉘어요. MoE 층마다 디스패치와 컴바인, 전체 대 전체가 두 번 있어서, 그룹 전체가 단계마다 함께 움직여요.
  2. 디코드에서는 GPU가 많을수록 GPU 한 개가 한 층에서 맡는 전문가가 줄어요(EP8은 GPU당 49개, EP64는 7개). 단계마다 읽는 전문가 가중치가 줄고, 가중치 한 묶음이 처리하는 token이 늘어요. GPU당 통신량은 거의 그대로예요.
  3. 가장 바쁜 GPU가 그룹 전체의 속도를 정해요. EPLB는 전문가마다 부하를 집계하고, 주기적으로 인기 전문가에 복사본을 더해 다시 배치한 뒤, GPU 사이에서 가중치를 옮겨요. 업스트림이 디코드에서 보고한 moe_lb는 1.090이에요.

흔한 오해: 「EP는 넓을수록 좋다. GPU가 많을수록 빠르니 계속 늘려도 된다.」

GPU를 늘려서 아끼는 읽기 대역폭은 점점 줄어요. EP8에서 EP64까지는 GPU당 전문가가 49개에서 7개로 줄지만, 한 번 더 두 배인 EP128로 가면 7개에서 4개로만 줄어요. 교육용 추정 EP 그룹이 NVLink 도메인을 넘어도 일반 DeepEP 경로는 쓸 수 있어요. 하지만 Mega MoE와 한 대 안의 가중치 미러 이동은 도메인 안에서만 써요. 통신 도메인이 클수록 가장 느린 GPU를 기다릴 위험이 커지고, GPU 한 개가 고장 났을 때 멈추는 GPU도 많아져요. 업스트림의 디코드 너비는 EP64–128이고, 이것은 GPU 64–128개의 슈퍼노드에 해당해요. 업스트림 보고

한 걸음 더: EPLB의 코드 경로, 환경 변수, benchmark 기준

전문가에 번호를 매기는 방법

FusedExperts의 문서 문자열은 네 가지 수를 정의해요. logical = n_routed_experts로, 라우터가 이 중에서 골라요. extra = n_redundant_experts로, model_loader._configure_moe_redundancy가 써 넣어요. physical = logical + extra이고, ep_size로 나누어떨어져야 해요. local = physical // ep_size예요. (moe.py 1–8행) 올림은 resolve_num_extra_experts가 해요. padding = -(num_routed_experts + min_num_extra_experts) % ep_size예요. (eplb/__init__.py 21–28행, model_loader.py 83–106행) 초기 배치는 [0 … n−1, 이어서 0, 1, 2 … 의 복사본]이고, 모든 층이 같은 것을 써요. (31–39행) 가중치를 불러올 때 각 rank는 이 초기 배치에 따라 자기 전문가 몇 개만 읽고, 중복 복사본은 같은 HF 가중치를 다시 써요. (weights.py 248–272행) 가중치 모양이 같은 MoE 층은 한 그룹으로 묶고, 그룹마다 ExpertLoadBalancer 하나를 둬요. (deepseek.py 323–365행)

단계마다 하는 일

ExpertLoadBalancer.step은 샘플링 단계에서 단계마다 한 번 호출돼요. EP가 1이면 바로 돌아가요. 하는 일은 세 가지예요. 이번 단계의 expert_count를 윈도에 저장하고 필요하면 재배치하기, 부하 통계 누적하기, expert_count를 0으로 되돌리기예요. (131–165행) NORMAL 엔진(프리필과 디코드를 함께 하는 엔진)은 기본적으로 프리필 단계를 건너뛰어요. 그 단계의 카운트는 윈도에 들어가지 않고 재배치 카운트도 올리지 않아요. DEEPINFER_REARRANGE_AFTER_PREFILL_IN_NORMAL_ENGINE=1로 설정하면 프리필 단계의 카운트도 윈도에 들어가고, 다음 프리필이 아닌 단계에서 바로 재배치해요. (83–84행, 146–165행) 부하 통계는 DEEPINFER_MOE_LB_STAT_INTERVAL(기본 128)단계마다 all-gather를 한 번 해서 GPU별 token 수의 평균과 최댓값을 얻어요. 이 둘의 비가 로그의 moe_lb예요. (167–193행)

정책의 두 단계 탐욕

rebalance_experts_global은 먼저 복제하고 나중에 배치해요. 복제 단계에서는 매 라운드, 후보 전문가 j마다 「j에 복사본을 하나 더한 뒤 단계별 가장 큰 복사본 하나당 부하」를 계산하고, 단계에 걸쳐 합해서 가장 작은 j를 골라요. 점수에 j × 1e-4를 더해서 전문가마다 점수가 겹치지 않게 해요. (policy.py 73–140행) 배치 단계의 목표는 주석에 적혀 있어요. 「단계별로 가장 바쁜 GPU의 부하」의 합을 최대한 작게 하고, 동점이면 번호가 작은 GPU를 골라요. 저장소의 단위 테스트는 두 매핑 표가 서로 역함수인지, 복사본 총수가 물리 슬롯 수와 같은지, 같은 입력이면 두 번의 결과가 완전히 같은지를 확인해요. (test_eplb_policy.py 27–62행) 이 페이지의 시뮬레이터는 이것을 한 층, 배정밀도 부동소수점으로 단순화했어요. 동점 처리는 PyTorch의 단정밀도 버전과 조금 다를 수 있어요.

가중치를 옮기는 방법

첫 재배치 때는 메모리가 모자라지 않도록 먼저 PyTorch의 VRAM 캐시를 비워요. EP 그룹이 NVLink 도메인 안에 있고 GPU일 때는, 한 층의 가중치만 담는 대칭 VRAM 미러를 만들어서 층마다 새로 고쳐요. 각 GPU는 짝이 되는 송신 쪽 미러에서 모자란 전문가를 바로 복사해요. 아니면 torch.distributed의 일괄 점대점 송수신(NVIDIA에서는 NCCL)을 쓰고, DEEPINFER_REARRANGE_P2P_GROUPS에 따라 버킷으로 나눠요. 같은 전문가에 송신 쪽이 여러 개이면, 수신 쪽이 정해진 규칙으로 송신 쪽에 고르게 나눠요. 송신과 수신 양쪽이 같은 함수로 짝을 지어서 반드시 맞아떨어져요. (eplb/__init__.py 195–220행, shuffle.py 47–53행, 94–147행) 가중치를 다 옮긴 뒤에야 copy_로 새 매핑 표로 바꿔요. (261–278행)

benchmark 기준

benchmark의 디코드 처리량은 「전부 수락」으로 계산해요. 요청마다 단계당 1 + nextn개의 token으로 세고, 드래프트가 실제로 몇 개 수락됐는지는 상관없어요. (examples/README 55행) README 첫 페이지의 디코드 그래프와 너비 비교 그래프는 다른 기준을 써요. 그래프를 그리는 스크립트가 두 축에 모두 τ = 1 + nextn × 수락률을 곱하고, 부제에는 수락률 75%, τ = 3.25로 환산했다고 적혀 있어요. (plot_pareto.py 58–67행) 그래서 benchmark가 직접 출력하는 전부 수락 처리량은 그래프의 숫자보다 높아요. DEEPINFER_FORCE_LOAD_BALANCE=1을 붙이면 이 그래프들은 모두 「부하가 완전히 균등」할 때의 숫자예요. 이런 기준의 세부 사항은 4페이지에서도 다뤄요.

이 페이지에서 확인하지 못한 것

  • DeepEP와 DeepGEMM의 서브모듈은 이번 저장소 체크아웃에 없어요. 디스패치, 컴바인, Mega MoE가 내부에서 어떻게 동작하는지, 라우터가 복사본 여러 개 중에서 어떻게 고르는지는 이 책에서 확인하지 못했어요.
  • 라우팅 전문가 384개는 업스트림 범례와 Q&A에서 추산한 거예요. 모델의 config.json은 저장소에 없어요. 전문가 하나의 바이트 수, token 하나가 고르는 전문가 수, MoE 층 수는 이 페이지에 쓰지 않았어요.
  • DP 부하 분산기 세 가지는 오픈소스가 아니고, Q&A의 글로 된 설명만 있어요.
