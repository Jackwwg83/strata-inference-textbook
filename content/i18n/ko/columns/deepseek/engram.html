다른 엔진으로 보기

앞 페이지들은 모두 "계산" 이야기였어요. 전문가를 어디에 둘지, 어텐션을 어떻게 바꿀지요. 이 페이지는 "조회" 이야기예요. DeepSeek-V4.1-Flash 파일에는 아주 큰 표가 하나 들어 있어요. 저비트 파일 세 가지(1.75, 2.00, 2.25 bpw)가 함께 쓰는 표는 111 GB이고, UD-Q8_K_XL에 딸린 표는 203 GB예요. 이 표는 곱셈을 한 번도 하지 않아요. 모델이 토큰을 하나 쓸 때마다 표에서 48행만 넘겨 봐요. 111 GB짜리는 약 7 KB, 203 GB짜리는 약 12.7 KB예요. 그런데 엔진은 이 7 KB를 위해 디스크 읽기 스레드 한 무리와 행 캐시 한 덩어리를 따로 두고, 1층과 14층에 닿기 전에 행을 준비해 놓아요. 이 페이지를 다 읽으면 세 가지 질문에 답할 수 있어요. 토큰 하나가 어떻게 행 번호 48개가 되는지, 넘겨 본 행이 모델의 상태를 어떻게 바꾸는지, SSD 속도가 정말 이 표에서 막히는지 아니면 다른 곳에서 막히는지요.

한마디로: Engram은 조회만 하고 계산하지 않는 해시 표예요. 토큰마다 해시로 행 번호 48개(1층과 14층에 각각 24개)를 계산해 SSD에서 읽어 오고, 값으로 복원한 뒤 게이트를 통과시켜 모델의 상태에 더해요. 유효한 바이트는 7~12.7 KB뿐이라서 어려운 점은 지연 시간이에요. 토큰이 정해지는 즉시 읽기 요청을 보내고 쓰기 직전에 회수해서, 디스크 읽기 스레드와 행 캐시로 대기 시간을 숨겨요. Mac 문서의 토큰당 48~111 MB 디스크 읽기량은 거의 전부 전문가가 읽는 양이고, 이 표가 아니에요.

4.1 조회만 하고 계산하지 않는 표: 어느 단계에서 쓰고, 얼마나 클까

먼저 어느 단계에서 쓰는지 볼게요. 엔진 소스 맨 앞에 한 층의 흐름이 그려져 있어요. Engram이 있는 두 층에서는 이 표가 가장 앞에 와요. 어텐션과 전문가보다 먼저예요. 이 단계는 한 줄뿐이에요. h += gate(h, key) × value이고, value 값은 24행짜리 n-gram 표에서 와요. 코드 사실(ds4_model.cu 5–7행) 주석에는 1층과 14층이라고 적혀 있지만, 실제 층 번호는 모델 설정의 engram_layer_ids가 정해요. 코드 사실(532행) 모델은 모두 40층이고, 나머지 38층은 이 표를 건드리지 않아요. 교육용 추정(40 − 2. 40층은 DEEPSEEK41.md 3–4행 참고)

n-gram이 무엇이고 왜 해시 행 번호로 조회하는지는 11장에서 이미 설명했어요(11장 「n-gram 언어 모델」). 주 흐름인 Qwen3.8-Flash-Next에도 이런 표가 있고, 소스에서는 PLE라고 불러요. 이 페이지는 DeepSeek 쪽 방식만 다뤄요.

이 표는 모델의 일부예요. Engram 층마다 텐서가 하나씩 있고, 이름은 layers.<층 번호>.engram.embed.weight예요. 코드 사실(2894행) 저비트 파일 세 가지(1.75, 2.00, 2.25 bpw)는 같은 Engram 파일 하나를 함께 써요. 형식은 IQ4_NL이고 111 GB예요. 한 번 내려받으면 세 가지가 모두 써요. 업스트림 보고(DEEPSEEK41.md 39행) UD-Q8_K_XL에 딸린 표는 202.8 GB이고 형식은 MXFP8이에요. 업스트림 보고(17행, dsv41_fit.py 8행) 문서는 일부러 한마디를 덧붙여요. 이 표는 메모리에 올리지 않지만, 디스크가 느리면 모든 토큰이 느려지므로 모델 파일을 NVMe 디스크에 두어야 한다는 거예요. 업스트림 보고(위와 같은 문서 17행)

한 행은 얼마나 넓을까요? 디스크 읽기 코드는 GGUF 행 형식 세 가지와 옛 패킹 형식 한 가지(코드와 스케일을 텐서 두 개로 나눈 것)를 알아봐요. MXFP8은 값 32개에 33바이트, Q6_K는 값 256개에 210바이트, IQ4_NL은 값 32개에 18바이트예요. 코드 사실(ds4_engram_io.hpp 93–95행, ds4_model.cu 2902–2913행) 한 행에 값이 몇 개인지는 모델 패키지의 헤더가 알려 주고, 소스에는 박혀 있지 않아요. 코드 사실(413–416행) lab 도구는 "실제 모양" 주석 아래에 층마다 24행, 행마다 값 256개라고 적어 두었어요. 코드 사실(ds4_lab.cu 1–5행, 315행) 이 모양은 파일 크기로 검산할 수 있어요.

파일 크기로 검산해 볼게요. 행마다 값 256개로 계산하면 IQ4_NL은 한 행이 8블록 × 18 = 144바이트이고, MXFP8은 한 행이 8블록 × 33 = 264바이트예요. 교육용 추정 setup.py 주석에는 합쳐진 Engram 텐서가 110,595,290,400바이트라고 적혀 있어요. 업스트림 보고(setup.py 743행) 이것을 144로 나누면 정확히 768,022,850행이에요. 교육용 추정 이번에는 engram_hash.py 규칙대로 소수 48개를 골라요(두 층에 각각 24열이고, 16,000,000부터 위로 서로 다른 소수를 차례로 골라요). 이 소수들의 합도 768,022,850이에요. 교육용 추정(규칙은 engram_hash.py 34–39행, 59–65행. 16,000,000은 제가 시험해서 찾은 시작점이고 파일에는 이 수가 없어요. 계산식은 이 페이지 끝에 있어요.) 일의 자리까지 맞아요. 한 행 144바이트, 층마다 24열, 모두 48열이에요. MXFP8 표도 192바이트만 빼고 맞아요. 이 192바이트는 아마 GGUF 메타데이터와 정렬 패딩일 텐데, 확인하지는 않았어요. 교육용 추정(dsv41_fit.py 32행에 202,758,032,592가 적혀 있어요)

토큰 하나에 몇 바이트를 가져올까요? 엔진은 토큰마다 48행을 가져와요. 두 층에서 각각 24행이에요. 코드 사실(engram_iq4nl_bench.py 4–5행: "for one token, gathers 48 rows") 48 × 144 = 6,912바이트, 약 7 KB예요. MXFP8 표는 48 × 264 = 12,672바이트예요. 교육용 추정 표 전체는 111 GB인데 토큰 하나는 그중 7 KB만 넘겨 봐요. 203 GB짜리라면 토큰 하나가 12.7 KB를 넘겨 봐요. 이것이 "조회"와 "계산"의 차이예요. UD-Q8_K_XL에서는 전문가 하나가 18.8 MB이고, 이 가중치를 전부 훑어야 해요. 업스트림 보고(DEEPSEEK41.md 15행) 2비트 패키지의 전문가는 더 작아요. Engram은 작은 행 수십 개만 가져와요.

Qwen 경로와 비교하면: 11장의 PLE 표는 320,001,536행이고 행마다 90바이트, 모두 28.8 GB예요. 토큰마다 16행을 가져오고 한 층에서만 써요. DeepSeek의 이 표는 7.68억 행이고 행마다 144바이트예요. 토큰마다 48행을 가져오고 두 층에서 써요. 표는 약 3.8배 커졌고(110.6 ÷ 28.8), 토큰당 가져오는 행은 Qwen의 3배이며, 행 너비는 60% 늘었어요(144 ÷ 90). 교육용 추정(Qwen 쪽 수치는 11장에서 가져왔고 거기서 이미 검증했어요) 두 쪽의 길은 같은 줄기예요. 먼저 해시하고, 행 단위로 디스크에서 읽고, 모델에 넣어요. 차이는 규모와, 아래 몇 절에서 다룰 읽는 방식에 있어요.

4.2 토큰 하나가 어떻게 행 번호 48개가 될까

행 번호는 전부 해시로 계산해요. 신경망도 없고 사전 조회도 없어요. 알고리즘은 eg_issue 안에 있고 모두 네 단계예요.

1단계, 토큰 번호를 압축 토큰 번호로 바꿔요. 참조 구현의 주석에 바꾸는 방법이 적혀 있어요. 토큰은 먼저 NFKC, NFD, 악센트 제거, 소문자 변환, 공백 병합을 거치고, 처리한 뒤 같아진 토큰들은 새 번호 하나를 공유해요. 코드 사실(engram_hash.py 5–7행) 엔진은 이 일을 직접 하지 않고 모델 패키지의 engram.bin에서 만들어 둔 매핑 표를 읽어요. 코드 사실(ds4_model.cu 405–430행) 이미지 위치의 토큰에는 압축 토큰 번호가 없어서 −1로 기록해요. 어떤 n-gram도 이미지를 넘지 않고, 이미지 위치에서는 행을 가져오지도 않아요. 코드 사실(6256–6260행, 6298행)

2단계, 거슬러 올라가며 고정된 홀수를 각각 곱해요. 현재 토큰과 그 앞의 몇 개 토큰에 각각 수를 곱해요. 거슬러 올라가 s번째 토큰의 압축 토큰 번호에 s번째 곱수를 곱하는 식이에요. 텍스트의 처음이나 이미지를 만나면 멈추고, 나머지 위치에는 고정된 패딩 토큰 번호를 써요. 코드 사실(ds4_model.cu 6304–6307행) 곱수는 층마다 한 벌이고 모델 패키지가 가져와요. 참조 구현은 고정된 시드로 곱수를 만들어요. 시드는 10007에 층 번호를 곱한 값이고, 결과는 홀수로 맞춰요. 코드 사실(engram_hash.py 82–89행) 그래서 여기에는 학습으로 얻은 인덱스가 하나도 없고, 같은 n-gram은 언제나 같은 행으로 가요.

3단계, 단계적으로 XOR한 다음 열마다 나머지를 구해요. 곱한 값들을 가까운 쪽부터 먼 쪽으로 하나씩 같은 수에 XOR해요. 앞의 두 항을 XOR하면 2-gram의 해시가 나오고, 세 번째 항을 XOR하면 3-gram의 해시가 나오는 식이에요. 코드 사실(ds4_model.cu 6309–6311행) 길이마다 열(헤드)이 여러 개 대응해요. 열마다 자기 소수와 시작점이 있어요. 행 번호 = 해시 mod 소수 + 시작점이에요. 코드 사실(6314행) 소수는 버킷의 개수와 같고, 시작점은 같은 층에서 앞쪽 열들의 소수를 모두 더한 값이에요. 그래서 열마다 이 층의 표 안에서 자기 구간을 차지하고 서로 겹치지 않아요. 코드 사실(engram_hash.py 73–79행)

4단계, 행 번호로 파일을 읽어요. 행 번호에 행당 바이트 수를 곱하고 텐서의 시작 위치를 더하면 파일 안의 위치가 돼요. 표에는 행만 있고 키가 없어요. 디스크 읽기 코드에는 키를 맞춰 보는 단계가 전혀 없어요. 코드 사실(ds4_model.cu 6337–6340행) 행 캐시는 "행 번호 × 8 + Engram 층의 순번(0 또는 1)"을 키로 써요. 코드 사실(6317행) 층마다 열 수 = (n-gram 상한 − 1) × 헤드 수예요. 코드 사실(6279행) 상한과 헤드 수가 각각 얼마인지는 이 페이지에서 쓴 파일에 적혀 있지 않아서 말하지 않아요. 확실한 것은 곱뿐이고, 층마다 24열이에요.

충돌하면 어떻게 될까요? 행 번호 하나를 여러 n-gram이 함께 쓸 수 있어요. 키를 저장하지 않는 데 따르는 대가예요. 11장에서 같은 맞바꿈을 다뤘어요(11장 「해시 테이블과 해시 함수」). 여기에 추측 하나를 더해요. 가져온 행이 때로는 맞지 않을 수 있어요. 그래서 뒤에 게이트가 있어서, 현재 상태가 그 행을 얼마나 믿을지 정해요. 교육용 추정

작은 숫자로 한 번 따라가 볼게요. 최근 토큰 세 개의 압축 토큰 번호가 4, 9, 6(6이 현재 토큰)이고, 곱수는 3, 5, 7이며, 두 열의 소수는 11(시작점 0)과 13(시작점 11)이라고 해요. 곱은 18, 45, 28이에요. 18 ⊕ 45 = 63이고 63 mod 11 = 8이라서 첫 번째 열은 8행을 읽어요. 63 ⊕ 28 = 35이고 35 mod 13 = 9에 시작점 11을 더하면 두 번째 열은 20행을 읽어요. 교육용 추정(장난감 숫자이고 규칙은 위와 같아요. 그림 DS4-2에 같은 예를 그려 두었어요)

CS를 배운 분께: 머신러닝의 "특징 해싱"(hashing trick)이에요. 키를 저장하지 않고 행 번호를 곧바로 배열 인덱스로 써요. 해시 테이블과 다른 점은 충돌을 처리하지 않는다는 거예요. 1단계의 압축 토큰 번호는 입력 정규화와 비슷해요. 대소문자, 악센트, 공백이 다른 표기를 같은 키 하나로 합쳐서 한 행을 함께 써요. 해시 함수 자체는 11장을 보세요.

Qwen 경로와 비교하면: 11장의 Qwen 해시는 토큰 번호를 곧바로 곱해요. 최근 2개와 최근 3개 토큰을 쓰고, 각각 헤드 8개라서 모두 16행이에요. 헤드마다 나누는 수는 2000만 근처예요. DeepSeek은 먼저 토큰 번호를 압축하고, 한 층이 24열이며, 열마다 소수가 1,600만 근처예요(앞 절에서 추산했어요). 두 층이 각자 계산해요. 두 쪽 모두 "곱하기, XOR, 나머지"이고, 둘 다 키를 저장하지 않아요. (Qwen 쪽은 11장을 보세요. 거기서 이미 검증했어요.)

4.3 가져온 48행이 모델의 상태를 어떻게 바꿀까

먼저 행을 값으로 복원해요. IQ4_NL의 한 블록은 값 32개, 18바이트예요. fp16 스케일 하나와 4비트 코드 16바이트로 이루어져요. 코드 사실(ds4_model.cu 1089–1091행) 엔진은 행마다 F32로 역양자화해요. 코드 사실(10021행) 양자화가 어떻게 저장하고 어떻게 복원하는지는 4장 「정수 양자화와 오차」를 보세요.

24행을 긴 벡터 하나로 이어 붙이고 행렬 곱을 한 번 해요. 24 × 256 = 6,144개 값이고, 토큰마다 Engram 층마다 하나씩 있어요. 교육용 추정 이 층의 engram.wkv 행렬을 곱하면 (H + 1) × D개 값이 나와요. 코드 사실(ds4_model.cu 10038행) H는 모델 상태의 스트림 수(코드에서는 hc)이고, D는 스트림 하나의 너비예요. lab 주석이 알려 주는 실제 모양은 H = 4, D = 5,120이에요. 코드 사실(ds4_lab.cu 1–3행) 그래서 출력은 5 × 5,120 = 25,600개 값이에요. 교육용 추정

출력을 key 4개와 value 1개로 나눠요. 앞의 4구간은 각각 스트림 하나에 속하고 key라고 불러요. 마지막 1구간은 모두가 함께 쓰는 value예요. 코드 사실(ds4_kernels.cu 1546–1550행)

게이트가 스트림마다 얼마나 가져갈지 정해요. k번째 스트림에서는 상태 h와 key를 각각 RMS로 정규화하고, 이 스트림 자신의 가중치 w를 차원마다 곱한 뒤 내적을 구하고 차원 수로 스케일해요. 부호를 유지한 제곱근을 취하고 sigmoid를 통과시키면 0에서 1 사이의 게이트 값 g가 나와요. 마지막으로 h ← h + g × value예요. 코드 사실(ds4_kernels.cu 1543–1565행) w는 학습된 벡터 q와 k를 원소별로 곱한 값이에요. 어떤 패킹은 이미 곱해 두었고, 그렇지 않으면 엔진이 로드할 때 곱해요. 코드 사실(ds4_model.cu 4343–4352행, DEEPSEEK41.md 46행)

이 공식을 읽는 법. value는 "이 토큰들 뒤에 흔히 무엇이 오는지"를 적은 메모 한 장 같고, key는 "이 메모가 어떤 문맥에 어울리는지"를 적은 표지 같아요. 게이트는 현재 상태를 key와 견줘 봐요. 맞으면 더 많이 더해요. 교육용 추정(이 공식을 이렇게 읽는다는 것이고, 소스에는 이런 설명이 없어요.) 더하는 위치는 어텐션 앞이라서 이 단계는 KV 캐시를 차지하지 않아요. 교육용 추정

4.4 디스크 읽기: 토큰이 정해지면 바로 요청하고, 쓰기 직전에 회수해요

행 번호는 토큰만으로 정해져서 미리 읽을 수 있어요. 토큰 하나의 행 번호 48개는 현재 토큰과 그 앞 몇 개 토큰의 번호로만 정해지고, 앞쪽 어떤 층의 계산에도 의존하지 않아요. 토큰이 정해지면 바로 읽기 요청을 보낼 수 있고, 그 행을 쓰는 층 직전에 회수하면 돼요. 코드 사실(ds4_engram_io.hpp 5–10행) 1층의 행은 "임베딩 + 0층" 뒤에 숨고, 14층의 행은 0~13층 뒤에 숨어요. 코드 사실(위와 같은 파일 6–7행) 한 윈도의 토큰이 모이면 두 Engram 층의 요청이 함께 나가고, 1층 요청이 대기열 맨 앞에 서요. 코드 사실(ds4_model.cu 9720–9728행, hpp 7–8행) 요청을 보내는 시간과, 회수할 때 아직 다 읽지 못한 만큼의 시간은 모두 engram_ms에 들어가요. 코드 사실(9741–9743행)

윈도는 얼마나 길까요? 토큰별 디코드와 드래프트 검증에서는 윈도 하나에 토큰이 최대 16개예요. 코드 사실(ds4_kernels.cuh 18행) 토큰별 디코드에서는 윈도에 토큰이 1개뿐이에요. step이 토큰 하나만 먹여요. 코드 사실(ds4_model.cu 8071행) 초안 모델의 검증 윈도는 더 길어서 한 번에 토큰 n + 1개를 실어 보내고, 행도 함께 요청해요. 코드 사실(7950–7960행. 드래프트는 5쪽) 기본값인 청크 프롬프트는 다른 길로 가요. 청크마다 토큰이 수백에서 수만 개이고, 보조 스레드가 한 청크 앞서 행을 읽어요. 코드 사실(6420–6424행) 그래서 토큰별 디코드에서는 1층의 행이 "임베딩 + 0층"이라는 아주 짧은 시간 동안만 숨을 수 있고, 이 부분이 가장 빠듯해요. 교육용 추정(주석을 읽고 한 추론이에요)

디스크 읽기 스레드. 엔진에는 Engram만 읽는 스레드 한 무리가 있어요. 스레드마다 자기 파일 핸들이 있고, 선입선출 큐에서 일을 가져가요. 코드 사실(ds4_engram_io.hpp 129–146행) 스레드 수의 기본값은 min(16, max(4, 논리 프로세서 수 ÷ 2))이고, Mac 버전은 2로 고정이에요. 주석이 든 이유는 "SSD 큐가 계속 바쁘도록 스레드가 충분히 많아야 한다"는 것이고, 페이지 캐시에서 읽을 때는 스레드가 적어도 된다고 해요. 코드 사실(ds4_model.cu 2844–2853행) 동시에 진행 중인 읽기가 많을수록 SSD의 작은 블록 무작위 읽기 처리량이 높아져요(5장 「대역폭과 지연 시간」). Windows에서는 ReadFile 호출이 동기식이라 스레드 수가 곧 큐 깊이예요. 주석에는 측정 두 가지가 적혀 있어요. Project Maya가 코어 20개 컴퓨터에서 28K 토큰 프롬프트를 읽을 때 스레드 10개는 17.1초, 64개는 13.4초였어요. Strata는 코어 6개 기계에서 스레드 64개로 4K 프롬프트가 4.5% 빨라졌고, 디코드는 빨라지지 않았어요. 업스트림 보고(2847–2851행)

Mac은 스레드를 2개만 열어요. 주석에는 이렇게 적혀 있어요. 스레드가 2개보다 많으면 같은 프롬프트의 디코드가 16번 중 3~9번은 직렬 결과와 달라졌고, 스레드 1~2개일 때는 24번 모두 같았어요. 원인은 아직 찾지 못했어요. 업스트림 보고(2855–2856행) 문서는 이 때문에 프롬프트 속도가 3%~12% 느려지고 답 속도는 그대로라고 해요. 업스트림 보고(DEEPSEEK_MAC.md 79–81행) 문서는 왜 프롬프트에만 영향이 있는지 설명하지 않아요. 합리적인 추측은 이래요. 토큰별 디코드는 토큰마다 읽기가 48개뿐이라 스레드 2개로 감당이 돼요. 토큰 3,000개짜리 프롬프트를 읽으면 읽기를 최대 3,000 × 48 = 144,000개 보내야 하고, 스레드가 적으면 병목이 되기 쉬워요. 교육용 추정(행 캐시에 적중한 행은 읽지 않아도 되니까 이 값은 상한이에요.)

행 캐시. 같은 n-gram이 반복해서 나오면 그 행을 다시 읽지 않아도 돼요. 엔진은 프로세스 안에 행 캐시를 두고, 클럭 알고리즘으로 교체해요. 행마다 "최근에 썼다"는 표시가 있어서 두 번째 기회를 줘요. 코드 사실(ds4_engram_io.hpp 38–91행) 용량은 여유 메모리의 1/64이고, 하한 16 MiB, 상한 256 MiB예요. DS4_ENGRAM_CACHE_MB로 바꿀 수 있고 0이면 꺼요. 코드 사실(ds4_model.cu 2861–2864행) 슬롯 하나는 hd + hd ÷ 32 = 264바이트를 저장하므로, 256 MiB에는 대략 100만 행이 들어가요. 교육용 추정(268,435,456 ÷ 264 ≈ 1,016,800. 슬롯 너비는 2846행 참고) 이것은 표 전체의 0.13%뿐이에요. 이 캐시는 범위를 덮는 것이 아니라 반복에 기대요. 교육용 추정 적중한 행은 읽기가 아니라 복사이고, 출력은 디스크에서 읽은 것과 완전히 같아요. 코드 사실(hpp 9–10행) 한 윈도 안에서 같은 행이 두 번 나와도 한 번만 읽어요. 코드 사실(6275–6276행) 문서는 적중률을 주지 않아요. 엔진은 실행이 끝나면 "Engram per token: …% without a read"라는 줄을 출력하니까 직접 볼 수 있어요. 코드 사실(ds4_main.cpp 1574–1581행)

읽기는 어느 길로 갈까요? 기본값은 버퍼 읽기예요. pread로 파일을 읽고 운영체제의 페이지 캐시를 거쳐요. 코드 사실(ds4_engram_io.hpp 235–254행) 페이지 캐시를 건너뛰는 직접 읽기는 Windows에만 있어요. DS4_EG_DIRECT=1로 설정해야 하고 기본값은 꺼짐이에요. 주석에는 이것이 4K 프롬프트를 8% 느리게 했다고 적혀 있어요. 업스트림 보고(ds4_model.cu 2867–2873행)

한 가지 더 있어요. Engram의 페이지는 제자리에서 읽는 전문가와 페이지 캐시를 함께 써요. 소스 주석은 전문가를 자기 메모리로 복사해 두면 "Engram 표와 파일의 들쑤심에 페이지 캐시를 빼앗기지 않는다"고 해요. 코드 사실(ds4_model.cu 5340–5341행. 전문가를 어떻게 계층에 나누는지는 2쪽 참고)

마지막으로, 행 하나를 읽지 못해도 엔진은 죽지 않고 그 행을 0으로 처리해요. 코드 사실(ds4_model.cu 6388행) 그래서 디스크 읽기에 문제가 생기면 증상이 오류가 아니라 답이 조용히 나빠지는 모습일 수 있어요. Mac 버전은 stderr에 경고 한 줄을 출력하지만, 다른 버전은 출력하지 않아요. 교육용 추정

CS를 배운 분께: "요청 보내기"와 "결과 받기"를 호출 두 개로 나눈 것은 비동기 I/O의 future와 같아요. 먼저 증표를 받고, 필요할 때 기다리는 거예요. 큐 깊이는 리틀의 법칙으로 어림할 수 있어요. 동시에 진행 중인 읽기 수 = 처리량 × 읽기 한 번의 지연 시간이에요. 그래서 작은 블록 무작위 읽기는 한 번의 읽기를 빠르게 하는 것이 아니라 스레드 여러 개로 동시성을 받쳐서 감당해요(14장 「동기와 비동기」, 6장 「파일, 메모리 매핑, 페이지 캐시」).

Qwen 경로와 비교하면: 주 흐름 PLE의 읽기 방식은 거의 정반대예요. 기본값이 직접 읽기여서 페이지 캐시를 건너뛰어요. 행 캐시는 8웨이 집합 연관이고 1,048,576행, 행마다 90바이트로 약 94 MB예요. DeepSeek은 기본값이 버퍼 읽기라서 전문가와 페이지 캐시를 함께 써요. 행 캐시는 클럭에 두 번째 기회를 더한 방식이고 상한이 256 MB예요. 주 흐름의 표는 한 층에서만 써서 "임베딩 + 0층"이라는 윈도 하나에만 숨을 수 있어요. 여기서는 두 번째 윈도(0~13층)가 훨씬 넉넉해요. 교육용 추정(Qwen 쪽은 11장 「직접 매핑, 집합 연관, 완전 연관」을 보세요. 거기서 이미 검증했어요.)

4.5 SSD 속도는 정확히 어디에서 막힐까

문서가 주는 것은 합계이고, Engram의 장부가 아니에요. Mac 문서의 표에는 "Read from the SSD per word"라는 행이 있어요. 2.00 세트는 48 MB, 2.25 세트는 111 MB예요. 업스트림 보고(DEEPSEEK_MAC.md 50행. 조건: M5 Max 128 GB, 0.2.7.1 패키지 엔진, Engram 읽기 스레드 2개. 측정할 때 옆에서 놀고 있는 60 GB Qwen 서비스가 파일 캐시를 함께 썼어요. 35–39행 참고) 문서는 이 행을 어떤 카운터로 쟀는지 적지 않았어요. 엔진에서 가장 가까운 것은 disk_mb예요. 이 프로세스가 저장 장치에서 읽게 만든 바이트 수이고, 제자리에서 읽는 전문가도 포함해요. Mac에서는 페이지 캐시에 적중한 읽기는 세지 않아요. 코드 사실(ds4_main.cpp 62–85행, 954–957행) 문서의 그 행이 이런 종류의 카운터라고 보는 것은 제 추론이에요. 교육용 추정

그중 Engram은 얼마일까요? 토큰마다 48행이고, 행마다 적어도 한 페이지를 읽어요. 페이지를 4 KiB로 치면 보통 48 × 4 KiB = 192 KiB, 약 0.2 MB이고, 가끔 페이지를 넘나들면 한 페이지를 더 읽어요. Apple 칩의 페이지는 16 KiB라서 48 × 16 KiB = 768 KiB, 약 0.8 MB예요. 교육용 추정(페이지가 클수록 작은 읽기가 더 많이 증폭돼요. 행 하나가 144바이트라 페이지를 넘나드는 일은 드물어요.) 48 MB와 111 MB에 견주면 Engram은 약 1.6%와 0.7%예요. 더 깔끔한 근거도 있어요. 두 세트가 같은 표를 써요. 업스트림 보고(DEEPSEEK41.md 39행) 111 − 48 = 63 MB의 차이는 사실상 전문가에서 나와요(Engram의 차이는 0.8 MB 안팎뿐이에요). 교육용 추정

그러니 Mac에서 "SSD가 느려서 모든 토큰이 느려진다"고 할 때 영향을 받는 것은 주로 전문가예요. 문서 자신의 설명도 같아요. 디코드 토큰 하나는 이런 SSD 읽기와, GPU에 다 들어가지 않은 전문가를 계산하는 CPU 경로에 막히고, GPU에 막히지 않는다는 거예요. 업스트림 보고(DEEPSEEK_MAC.md 57–62행) 전문가가 VRAM, 메모리, SSD 사이에서 어떻게 계층을 나누는지는 2쪽을 보세요.

그런데 Engram에는 왜 스레드와 캐시가 필요할까요? 필요한 것이 대역폭이 아니라 지연 시간이기 때문이에요. 무작위 작은 읽기 48개가 1층과 14층 직전에 돌아와야 해요. 저장소의 디스크 읽기 벤치마크 스크립트도 이렇게 적어요(번역). 토큰마다 48행을 모으는 일은 110 GB 위에서 무작위이고, IOPS와 MB/s가 똑같이 중요하다. 코드 사실(engram_iq4nl_bench.py 45행) 다 읽는 데 걸리는 시간은 대략 ⌈행 수 ÷ 스레드 수⌉ × 무작위 읽기 한 번의 지연 시간이에요. 교육용 추정(교육용 모델) 읽기 한 번이 100마이크로초, 스레드가 4개라고 가정하면 ⌈48 ÷ 4⌉ × 100 µs = 1.2 ms예요. 15 토큰/초라면 토큰 하나가 약 67 ms이고, 40층으로 나누면 층마다 평균 약 1.7 ms예요. 교육용 추정(1000 ÷ 15 ≈ 67, 67 ÷ 40 ≈ 1.7) 두 수가 비슷해요. 이것이 1층의 행을 대기열 맨 앞에 세우는 이유예요. 이 모델에는 허점이 있어요. Mac은 스레드를 2개만 여는데, 모델대로라면 답 속도가 영향을 받아야 하지만 문서는 그렇지 않다고 해요. 실제 지연 시간이 더 짧거나 캐시 적중이 많다는 뜻이에요. 이 모델은 크기의 단위만 알려 줘요.

읽기 속도를 토큰 속도의 상한으로 바꿔요. 토큰마다 몇 MB를 읽어야 하는지는 모델 패키지와 메모리가 정하고, 1초에 몇 MB를 읽을 수 있는지는 디스크가 정해요. 상한 = 읽기 속도 ÷ 토큰당 MB예요. 아래 그림은 두 선을 함께 그려요. 가로축은 SSD 읽기 속도, 세로축은 토큰 속도 상한이에요. 인터랙티브 버전에서는 읽기 속도와 토큰당 MB를 끌어서 바꿀 수 있어요. 문서는 그 행이 어느 속도 조합에 해당하는지 적지 않아서, 그림에서는 코드 프롬프트의 짧은 답 값을 썼어요.

이 그림을 볼 때 짚을 점 세 가지. 첫째, 이것은 상한이고 실제 속도는 더 낮아요. 전문가가 CPU에서 계산도 해야 하기 때문이에요. 업스트림 보고(DEEPSEEK_MAC.md 57–62행) 이 Mac의 디스크 속도는 문서에 없어요. 이 Mac도 3.6 GB/s라면 두 점은 상한보다 한참 아래이고, 토큰 속도가 읽기 속도 하나로 정해지지 않는다는 뜻이에요. 둘째, 읽기 속도는 "내가 읽는 방식"에 맞게 골라야 해요. 전문가는 큰 덩어리로 읽어서 순차 읽기에 가깝고, Engram은 작은 덩어리를 무작위로 읽어서 처리량이 훨씬 낮아요. 교육용 추정 셋째, 토큰당 MB는 상수가 아니에요. 메모리가 많으면 붙잡아 두는 전문가가 늘어서 디스크 읽기량이 줄어요. 업스트림 보고(위와 같은 문서 57–59행) 3.6 GB/s는 문서에 나온 5070 기계(VRAM 12 GB, 메모리 64 GB)에서 왔고, 그 행은 토큰당 MB를 주지 않아서 그림에는 그 기계의 토큰 속도를 그리지 않았어요. 업스트림 보고(DEEPSEEK41.md 63–64행)

내 기계에서 재 보기. 엔진은 토큰 8개마다 모니터에 STAT 한 줄을 보내요. 여기에 disk_mb(토큰당 디스크 읽기 MB)와 engram_ms(토큰마다 Engram 요청을 보내는 시간과 다 읽기를 기다린 시간, 밀리초)가 있어요. 코드 사실(ds4_main.cpp 937–957행, 976행) 명령줄 실행이 끝나면 "Engram per token"과 "decode reads from the disk: N MB a token"을 출력해요. 코드 사실(1574–1584행) 업스트림은 이 수들의 실측값을 공개하지 않았고, 이 페이지에도 없어요. disk_mb와 내 디스크 속도를 가지고 위 그림으로 돌아가면, 내 기계가 디스크 읽기에서 막히는지 다른 곳에서 막히는지 판단할 수 있어요.

DeepInfer와 비교하면: 클러스터(GPU 배포)는 여기와 다르게 둬요. 표를 어휘를 따라 ENP 조각으로 나눠 각 머신의 호스트 메모리에 두고, rank마다 1/ENP 조각 하나만 저장해요. 이 조각은 RDMA로 읽을 수 있게 등록돼 있어요. 모델 forward가 시작되면 커널 하나가 단방향 RDMA 읽기를 내고, NIC가 백그라운드에서 행을 호스트 메모리에서 GPU 메모리로 복사해요. 업스트림 보고(Q&A 83–85행, DeepInfer 2쪽 2.7절 참고, a679bb86에서 검증했어요) Strata의 표는 한 부뿐이고 나누지 않으며, 컴퓨터 한 대의 SSD에 둬요. 111 GB가 일반적인 기계의 메모리를 넘기 때문이에요. GPU는 읽어 낸 몇 행만 받아요. 어느 쪽도 표 전체를 GPU 메모리에 올리지는 않아요. 교육용 추정

이 세 가지를 기억하기

  1. Engram은 약 7.68억 행짜리 해시 표이고, 두 층에 각각 한 벌씩 있어요. 토큰마다 곱하기, XOR, 나머지로 행 번호 48개를 계산하고, 행마다 144바이트라서 모두 약 7 KB예요. 표에는 키가 없고 충돌을 허용해요. 가져온 행은 게이트를 통과해 상태에 더해져요.
  2. 어려운 점은 대역폭이 아니라 지연 시간이에요. 행 번호는 토큰만으로 정해지므로 토큰이 정해지면 읽기 요청을 보내고 쓰기 직전에 회수해요. 디스크 읽기 스레드, 행 캐시, 페이지 캐시가 함께 대기 시간을 숨겨요. Mac은 결과를 안정적으로 만들려고 스레드를 2개만 열고, 그 대가로 프롬프트가 3%~12% 느려져요.
  3. Mac 문서의 토큰당 48 MB와 111 MB 디스크 읽기량은 거의 전부 전문가가 읽는 양이고, Engram은 약 1.6%예요. 토큰 속도 상한 = SSD 읽기 속도 ÷ 토큰당 MB예요. 짧은 답 코드 프롬프트의 중간값으로 어림하면 Mac의 토큰 속도가 요구하는 읽기 속도는 0.75~1.67 GB/s뿐이에요(15.6 × 48, 15.0 × 111. 교육용 추정).

흔한 오해: "Engram이 111 GB니까 SSD 대역폭을 다 먹는다."

표가 큰 것과 많이 읽는 것은 별개예요. 토큰 하나는 48행, 약 7 KB만 넘겨 봐요. 행마다 페이지 전체를 읽는다고 해도 1 MB가 안 돼요. Mac 문서의 토큰당 48 MB와 111 MB 디스크 읽기량에서 두 세트는 같은 표를 쓰고, 차이 63 MB는 사실상 전문가에서 나와요(Engram의 차이는 0.8 MB를 넘지 않아요). 교육용 추정(계산식은 4.5절에 있어요) Engram이 필요로 하는 것은 낮은 지연 시간과 충분한 동시 읽기이고, 대역폭이 아니에요. 모델 파일을 느린 디스크에 두면 두 가지 읽기가 모두 느려지지만, 느려지는 것은 주로 전문가예요.

2단계, 4.1절의 소수 합을 검증해요. 아래 코드는 표준 라이브러리만 써요. 16,000,000부터 위로 이웃한 소수 48개를 골라 합을 구하고, 행당 바이트 수를 곱해요. 출력은 768022850, 110595290400, 202758032400이어야 해요.

python3 -c "
def p(n): return n > 1 and all(n % i for i in range(2, int(n ** .5) + 1))
c, s = 16_000_000, 0
for _ in range(48):
    c += 1
    while not p(c): c += 1
    s += c
print(s, s * 144, s * 264)"

110,595,290,816 − 110,595,290,400 = 416이고, 202,758,032,592 − 202,758,032,400 = 192예요. 둘 다 파일 헤더의 몇백 바이트예요. 시작점 16,000,000은 시험해서 찾은 가정이에요. 8,000,000이나 4,000,000으로 바꾸고 행당 값을 512개나 1,024개로 맞추면 계산한 행 수가 파일 크기와 맞지 않아요.

페이지 캐시 경로의 행 속도. ds4_model.cu 2867–2870행의 주석에 따르면, 여러 스레드가 같은 파일의 페이지 캐시에서 읽을 때 그 Windows 기계에서는 초당 약 25.5만 행이에요. 업스트림 보고 토큰별 디코드는 토큰마다 48행이므로 15 토큰/초면 720행/초만 필요하고, 0.3%를 차지해요. 프롬프트를 읽을 때는, Mac 문서에서 2.00 세트가 32,000 토큰짜리 프롬프트를 609 토큰/초로 읽어요(DEEPSEEK_MAC.md 49행). 최대 609 × 48 ≈ 29,000행/초가 필요해요. 두 수는 서로 다른 기계에서 나왔고 크기만 견주는 용도예요. 행 캐시에 적중한 행은 읽지 않아도 되므로 29,000은 상한이에요. 교육용 추정

파일 배치 두 가지. 문서에 따르면 ISTA-DASLab이 10월 27일에 파일을 다시 나눴어요. 새 여섯 조각 배치에서는 Engram 표 두 개가 텐서 하나로 합쳐지고 바이트는 그대로예요. 게이트 가중치에는 q와 k의 곱이 저장돼요. Engram은 "이름도 크기도 같지만 해시가 달라서" 어느 배치에서나 어느 표든 쓸 수 있어요. 업스트림 보고(DEEPSEEK41.md 46–48행) 코드 쪽에서는 게이트 가중치를 두 방식 모두 알아봐요. engram.gate.weight가 있으면 그대로 쓰고, 없으면 q_weight와 k_weight를 읽어 원소별로 곱해요. 코드 사실(ds4_model.cu 4343–4352행) 패킹 스크립트도 메타데이터 철자 두 가지를 알아봐요. engram.*와 llama.cpp 스타일의 ple.*예요. 코드 사실(pack_gguf.py 236–259행) "해시가 다르다"가 구체적으로 어떤 수가 다르다는 뜻인지는 문서에 없고, 이 페이지도 검증하지 않았어요.

문서, 주석, 코드가 서로 맞지 않는 곳은 코드를 따라요. ① engram_iq4nl_bench.py의 첫머리에는 "무작위 2.3 KB 행 읽기"(7행)라고 적혀 있어서 위의 144바이트와 맞지 않아요. 이 파일은 스스로 "Phase 1.3 skeleton"이라 부르고, 행 너비는 GGUF 헤더를 따른다고 해요("nothing is hardcoded here"). 이 페이지는 lab의 hd = 256과 소수 합 검산을 기준으로 삼아요. 같은 파일에는 O_DIRECT도 적혀 있어요. 표가 메모리에 들어가지 않으니 페이지 캐시를 쓰지 않는다는 거예요. 이것은 당시의 구상이었고, 지금의 엔진은 기본값이 버퍼 읽기이고 직접 읽기는 Windows에서 옵션으로만 있어요. ② DEEPSEEK41.md 17행은 "표를 SSD에서 읽는다"고 하고, 39행은 "메모리나 SSD에서 읽는다"고 해요. 두 문장은 충돌하지 않아요. 페이지 캐시에 있는 페이지는 메모리에서 읽은 것이니까요.

검증하지 못한 것. ① 24열이 n-gram 길이 × 헤드 수로 어떻게 나뉘는지: 패킹된 파일에만 있고, 이 페이지에서 쓴 파일에는 없어요. ② Engram 층이 정말 두 개인지: ds4_model.cu 6행의 주석, DEEPSEEK41.md 46행의 "Engram 표 두 개", 소수 합의 "두 층에 각각 24열"이라는 가정이 서로 맞아떨어지지만, 모델 패키지의 헤더는 읽지 못했어요. ③ Mac 문서의 "토큰당 SSD 읽기" 행이 쓴 카운터: 이 페이지는 disk_mb의 종류로 추정했어요. ④ Engram의 적중률과 engram_ms의 실측값: 업스트림이 공개하지 않았고, 이 페이지에도 없어요. ⑤ Mac에서 스레드가 여러 개일 때 결과가 달라지는 원인: 코드 주석과 문서가 모두 "아직 찾지 못했다"고 해서, 이 페이지는 추측하지 않아요. ⑥ 읽기 한 번에 100 µs라는 지연 시간은 가정이고 측정값이 아니에요.
